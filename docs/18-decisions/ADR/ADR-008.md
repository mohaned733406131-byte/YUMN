# ADR-008: React Native 0.73 + Next.js 14 for all client surfaces

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Technical lead, Product owner, Design lead (RTL/design system), QA lead (device lab `DEP-12`) |
| **Informed** | Engineering team, DevOps lead (release pipelines), STK-03/STK-04 (users of the surfaces) |

## Context

yumn ships **four surface families, five client applications** (`05-frontend/README.md` §1): `S1` customer web storefront, `S2` vendor panel, `S3` admin console — all one Next.js 14 App Router application with three shells (`INFERENCE`, `architecture-overview.md` §6) — plus `S4` customer mobile and `S5` courier mobile as two React Native 0.73 binaries sharing one design system and one API SDK.

Forces:

- **Performance `NFR-002`**: LCP < 2.5 s on 4G and customer-web JS < 200 KB gzipped — server rendering and route-level code splitting are not optional for a discovery-driven storefront (`FR-009` is the front door).
- **Localization `NFR-013` / `C-24`**: Arabic default with full English parity; RTL is a *structural* property (`dir="rtl"` baseline, logical properties, icon mirroring — `05-frontend/rtl-and-styling.md`), not a stylesheet afterthought (`P7`).
- **Compatibility `NFR-015`**: last-2 versions of Chrome/Safari/Firefox/Edge, Android 10+, iOS 15+ — a five-surface matrix that must be affordable for a small team.
- **Dependency `DEP-12`**: the test device lab (Android versions, iOS, carrier SIMs) is *not started*; without it mobile QA cannot complete — `RISK-016` links `DEP-12`, `NFR-015` and this ADR directly.
- **Runtime baseline `DEP-01`**: Node 20 LTS + TypeScript 5.x — one language is already a project fact (`technology-stack.md` §1), and `ADR-003` makes the backend TypeScript too.
- **Security split**: `SEC-REQ-004` — every frontend guard is UX only, the server is the sole authorization boundary; `SEC-REQ-003` — refresh tokens live in httpOnly + SameSite cookies on web (never `localStorage`) and in secure storage on mobile (`05-frontend/authentication-handling.md`).
- **Delivery constraint `C-16`**: no GPS anywhere, no location SDK in either mobile app; delivery completion is a 6-digit code entry with 3 attempts → 24 h lock (`BR-SHP-03`). `architecture-decisions-reference.md` §3 explicitly reserves this rejected-option for *this* ADR.
- **Server authority**: prices, totals, VAT, stock, limits and the 17 order states are always recomputed by the backend (`BR-CRT-04`, `C-09`); clients format integer YER (`BR-PAY-10`, decision `D-02`) but never recompute.
- **Neighbouring decisions**: `ADR-003` (NestJS) shares the language and domain vocabulary; `ADR-010` fixes the token model these clients must implement; `ADR-006` supplies the search API behind `S1`/`S4`.

## Decision

**All client surfaces are built with TypeScript from two stacks: Next.js 14 (App Router) for the three web shells, and React Native 0.73 for the two mobile apps.** The web application renders `S1`/`S2`/`S3` with SSR/ISR for catalog and product pages and CSR dashboards for authenticated work, structural RTL as the default direction, and the documented performance budget. The mobile applications are two separate binaries from one codebase, sharing design-system and API-SDK packages with the web shells in a monorepo (`05-frontend/frontend-architecture.md`). No third client framework, no Flutter, no native Kotlin/Swift pair, and **no location SDK in any client** — delivery confirmation stays the 6-digit code (`C-16`). Every client treats the server as the sole source of truth and mirrors, never enforces, authorization.

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **Flutter for both mobile apps** | Single mobile codebase; consistent rendering; strong RTL support | Second language (Dart) breaks the one-language stack shared with `ADR-003` and the TS domain vocabulary; separate toolchain, hiring and testing story; `DEP-01` runtime baseline is TypeScript | Rejected: stack inconsistency — `technology-stack.md` §2 records Flutter as the rejected alternative for exactly this reason |
| **Two native apps (Kotlin + Swift)** | Best platform integration and performance | Doubles build/QA cost on a small team; two design implementations of the same Arabic-first UI; `NFR-015` matrix roughly doubles; `DEP-12` lab would need two pipelines | Rejected: cost and consistency — one RN codebase covers both OS targets |
| **SPA-only React + Vite (no Next.js)** | Simpler build; no server rendering to operate | Weaker first paint and SEO for storefront discovery; no ISR for the catalog crawl surface (`FR-009`, `NFR-002`); re-invents routing/data patterns Next already provides | Rejected: SSR/ISR is the stated reason Next.js is in the register (`technology-stack.md` §2) |
| **Three separate web applications (one per role)** | Independent deploys and permission isolation per surface | Triplicates i18n/RTL, auth handling, design system, error model and perf budgets; three things to keep in parity for a small team | Rejected: canon already fixes *one* Next.js application with three shells (`architecture-overview.md` §6); role isolation is a server concern (`SEC-REQ-004`) |
| **PWA / responsive web instead of native apps** | No store review pipelines; instant updates | No dependable APNs/FCM push (`FR-017`), weaker offline-tolerant courier flows, no device-camera UX story for code/proof capture; `DEP-12` device lab exists precisely because native apps are planned | Rejected: courier and customer mobile are first-class surfaces in `FR-015`/`FR-001`; a PWA cannot meet the push and deep-link expectations |
| **Angular (web) / Nuxt (Vue)** | Mature frameworks | Heavier or second framework; splits the stack away from the React/RN ecosystem shared packages assume | Rejected: stack consistency (`technology-stack.md` §2 alternatives) |

## Consequences

**Positive**

- One language across five surfaces: shared validation schemas (`DOC-FE-005`), shared API/typed SDK, shared money formatting (integer YER + `Intl.NumberFormat('ar-YE')` — decision `D-02`), shared error-code mapping (`07-api/error-model.md`) — contract drift becomes a compile error, not a QA finding.
- SSR/ISR on `S1` meets `NFR-002` and gives search/category/product pages real crawlability; the bundle budget is enforced in CI (`05-frontend/frontend-performance.md`).
- Structural RTL (logical properties, per-locale axe scans, RTL visual regression) is achievable identically on web and RN because both consume the same design tokens (`11-ui-ux/design-system.md`) — directly serving `C-24`, `NFR-013` and `RISK-015` mitigation.
- One test strategy for clients: Playwright (web, both locales) + device-lab runs (RN), feeding `NFR-011`/`NFR-015` gates.
- Web shells can be split later (separate deploys per role) without touching the API or the RN apps — an operational change, not an architecture change.

**Negative**

- Two client stacks (Next.js + React Native) must be built and maintained rather than one — shared packages reduce but do not remove the duplication (RTL behaviour, list virtualization and navigation still differ per platform).
- React Native upgrades are major-line changes: 0.73 → a newer line needs a stack-register entry and an ADR (stack register §8), and `RISK-016` (device/OS fragmentation) stays live until `DEP-12` is delivered.
- SSR couples storefront availability to the web deployment — mitigated because authenticated areas are CSR shells and API degradation is handled by honest error states (`NFR-007`, `P9`), never by fake client-side data.
- App-store review and signing mechanics add release lead time (`14-devops-infrastructure/` release notes; `DEP-12` gates final QA).

**Neutral**

- The absence of a location SDK is a *constraint compliance* outcome (`C-16`), not a capability gap: courier workflows are built around the pickup hub, scans and the 6-digit code (`BR-SHP-03`, `BR-SHP-05`).
- Guest browsing stays server-rendered and cacheable; authentication deep links and silent refresh are specified in `05-frontend/authentication-handling.md`, independent of this choice.
- A future PWA or desktop shell is not excluded — it would be a new surface and therefore a new ADR (numbering from `ADR-011`).

**Risks introduced:** mobile platform fragmentation feeds **`RISK-016`** (MEDIUM — `DEP-12` device lab + `NFR-015` matrix); Arabic-first UX quality feeds `RISK-015`; bundle/perf budget misses feed `RISK-008` at the edge of `NFR-002`. None of these alter the server architecture.

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-18` custom build** | Client applications are purpose-built for yumn — no commerce-platform theme, template or hosted storefront is adopted (holds for ADR-001…ADR-010) |
| **`C-16` no GPS / 6-digit code confirm** | **No location SDK in either mobile app** (the reserved rejected option in `architecture-decisions-reference.md` §3); courier UI is scan + code entry with lockout after 3 attempts (`BR-SHP-03`); schema/API carry no coordinates |
| **`C-24` Arabic-first RTL + English parity** | `dir="rtl"` structural default, logical properties, mirrored icons, bilingual message catalogs, per-locale accessibility and RTL visual regression — on all five surfaces |
| **`C-22` Docker Compose** | The Next.js web container runs as an ordinary Compose service; mobile binaries are built and signed in CI and distributed via stores — they add no runtime service to the topology |
| **`NFR-002` client performance** | SSR/ISR for discovery, route code splitting, image pipeline through the CDN, < 200 KB gzipped customer-web budget enforced in CI |
| **`NFR-015` compatibility** | Browser matrix (last-2 versions) and Android 10+/iOS 15+ are the release gates; no surface ships unsupported outside the matrix |
| **`NFR-011` accessibility** | WCAG 2.1 AA on every surface in both locales — axe scans per locale plus manual audit (`12-non-functional/accessibility.md`) |
| **`SEC-REQ-003` / `SEC-REQ-004`** | httpOnly+SameSite cookies (web) and secure storage (mobile) for tokens — never `localStorage`; all route guards mirrored by server-side authorization |
