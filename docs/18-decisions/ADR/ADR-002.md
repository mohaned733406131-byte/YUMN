# ADR-002: Modular monolith instead of microservices

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Technical lead, DevOps lead, Engineering team (STK-09), QA team (STK-10) |
| **Informed** | Product owner, STK-14 (infrastructure), all implementation roles |

## Context

yumn decomposes into 13 business blocks (`B01…B13` — identity, catalog, store, search, cart, orders, wallet/escrow, shipping, returns, notifications, analytics, content, administration). The delivery team is small and its operational capacity is explicitly a risk (`RISK-005`, STK-14: "small team vs 99.99% target"). Money flows (wallet debit → order creation → escrow → commission → payout) must remain strictly correct (`NFR-008`, `AC-S-14/15`).

Forces:

- **Constraint `C-21`: modular monolith — no microservices.** Canon records the rationale as *team size and operability* and cites **`ADR-002`** by number, so this ADR is canon-locked (DOC-ARCH-010 §2 rule 2).
- **Quality attribute `NFR-009`**: modules with *enforced* boundaries — lint/type/test gates in CI, docs current. A "modular" claim without enforcement is not acceptable.
- **Quality attribute `NFR-010`**: all business logic unit-testable without network calls — microservices would make local testing require fakes for peers.
- **Transaction semantics**: with `ADR-001` (single PostgreSQL), an in-process call can participate in one ACID transaction; across services it would need sagas everywhere. Canon already accepts sagas for the *multi-step* order creation case (`BR-PLT-04`, `module-boundaries.md` F9) — the goal is to keep that pattern the exception, not the default.
- **Scale target**: `C-25` (10K concurrent) is achievable with a stateless monolith behind a load balancer (`P8`, `NFR-018`) — microservices are not required for this scale.
- **Neighbouring decisions**: `ADR-003` (NestJS) supplies the module/DI mechanics; `ADR-004` (Compose) deploys one API plus one worker from the same image; `ADR-005` (BullMQ) carries async work so request paths stay simple.

## Decision

**yumn is delivered as a single deployable modular monolith: one NestJS application (plus the same image running BullMQ workers) internally partitioned into 13 modules with mechanically enforced boundaries.** Each module owns its public surface, its PostgreSQL schema (`b01…b13`), its queues (`{block}.{entity}.{action}`), and its tests. Cross-module interaction happens only through exported ports/services, in-process domain events, or jobs — never through network calls, cross-schema SQL, or direct access to another module's repositories. Extraction of a module is a *documented seam*, not a plan; microservices are out of scope for v1 and may be reconsidered only through a future ADR (which would require formally revisiting `C-21`).

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **Microservices (one service per block)** | Independent deploy/scale per block; technology freedom; failure isolation | Distributed transactions across money paths (wallet/order/escrow) become the norm; network as a failure mode on every call; 13 services to operate, observe, and secure on a small team; local dev and tests need the whole fleet running | **Rejected by `C-21`**: operability and team size dominate; at `C-25` scale microservices buy nothing that stateless horizontal scaling (`NFR-018`) does not already provide; would multiply `RISK-005` |
| **"Big ball of mud" monolith (no enforced boundaries)** | Fastest short-term delivery; zero boundary tooling cost | `NFR-009` unmeasurable; module ownership dissolves; money code becomes entangled with UI/admin logic; regression risk on every change (`RISK-001` exposure) | Rejected: violates `NFR-009`'s *enforced* requirement; without CI boundary gates the monolith degrades within months — this is precisely why `module-boundaries.md` defines forbidden patterns F1–F10 with build failures |
| **Modular monolith with event-mesh/service-bus backbone** | Loose coupling; attractive diagram | Extra infrastructure (broker) beyond `C-20` (BullMQ only); two integration styles to reason about; complexity tax with no product benefit | Rejected: `C-20` permits only Redis/BullMQ; the in-process `DomainEventBus` + outbox bridge in the shared kernel provides the same decoupling without new infrastructure |
| **Serverless functions per capability** | Auto-scaling; no server ops | Cold starts hurt `NFR-001`; state/transactions split across functions; cloud lock-in vs `NFR-016`; no local-first dev story | Rejected: lock-in and latency; contradicts `NFR-016` portability and `C-22` self-hosted posture |
| **Two-tier split (API tier + separate money service)** | Isolates the highest-risk domain | Only *some* paths become distributed; adds a network hop and a second deployment for the part that must be most correct — worst of both | Rejected: concentrates risk without removing distribution; money correctness benefits more from one ACID boundary (`ADR-001`) than from a process boundary |

## Consequences

**Positive**

- One deployment, one image, one rollback story — directly supports `RISK-005` mitigation, `C-26` restart/health mechanics, and `NFR-020` zero-downtime deploys.
- In-process calls + single database keep money operations in one ACID transaction where needed; saga usage stays limited to the documented multi-step flows (`BR-PLT-04`).
- Boundaries are testable: dependency-graph checks, ESLint import rules, and architecture tests ("only `LedgerService` writes ledger") make `NFR-009`/`AC-S-02` measurable in CI.
- Developer ergonomics: one repo, one toolchain, fast feedback (`NFR-010`), trivial local environment (Compose).
- Horizontal scaling of stateless API/worker replicas covers `C-25` without any inter-service traffic management.

**Negative**

- Failure isolation is weaker: a memory leak or event-loop block in one module can affect the whole process — mitigated by module-level resource discipline, queue-based async for slow work (F10), and worker separation for background load.
- Deploy is all-or-nothing: a change to any block ships with the whole app — mitigated by expand-contract migrations (`DATA-REQ-005`) and feature-level testing discipline.
- The enforceability of boundaries depends on tooling vigilance; a bypassed lint rule silently erodes `NFR-009` — the gate must stay mandatory on every push.

**Neutral**

- The schema-per-block layout and public-port discipline mean a future extraction (if `C-21` were ever relaxed) follows existing seams (`module-boundaries.md` §7) — useful, but explicitly out of scope for v1.
- Teams can still parallelize work by block ownership; coordination cost is code-review based rather than contract based.

**Risks introduced:** operational single-point behavior feeds `RISK-019` (single-host availability) and `RISK-005` (ops load) — both have mitigation plans; boundary erosion feeds `RISK-017` (key-person concentration) unless knowledge is documented, which this knowledge base addresses.

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-18` custom build** | No commerce platform adopted — the monolith *is* the custom build (satisfied by ADR-001…ADR-010 collectively) |
| **`C-21` modular monolith, no microservices** | The decision restates and implements `C-21`; numbering (`ADR-002`) is canon-locked by `C-21`'s citation |
| **`C-19` PostgreSQL 16 only** | Modules share one engine with schema ownership — no per-service datastore sprawl |
| **`C-20` BullMQ only** | Cross-module async uses the shared queue API only; no broker (F-patterns forbid side channels) |
| **`C-22` Docker Compose** | One deployable (api + worker from one image) fits the Compose topology (`deployment-view.md` §2) |
| **`C-25` / `C-26`** | Stateless replicas scale horizontally; single-image rolling restart + readiness gates support availability targets |
| **`C-23` greenfield** | No strangler/adapter patterns for legacy coexistence needed |
