# ADR-003: NestJS 10 as the backend framework

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Technical lead, Engineering team (STK-09), Security officer (guards/RBAC fit) |
| **Informed** | QA team, DevOps lead, Product owner |

## Context

The backend hosts all synchronous domain logic for 13 blocks (`B01…B13`) behind a REST API consumed by five client surfaces (three web shells + two React Native apps). Requirements shaping the framework choice:

- **`DEP-01`**: Node.js 20 LTS + TypeScript 5.x is the available runtime — the choice is constrained to the Node ecosystem (dependency status: `Available`, no development start without it).
- **`C-21` / `ADR-002`**: modular monolith with *enforced* module boundaries (`NFR-009`) — the framework must make modules a first-class construct, not a folder convention.
- **`NFR-010`**: business logic must be unit-testable without network; that requires dependency injection with swappable ports (the `*Port` pattern used throughout `module-boundaries.md` and `10-integrations/`).
- **Security**: server-side authorization on every endpoint (`SEC-REQ-004`), global validation pipes, rate limiting (`SEC-REQ-009`) — guards/interceptors/pipes must be structural, not per-handler discipline.
- **Performance**: p95 < 200 ms reads at 10K concurrency (`NFR-001`, `C-25`) — the framework must not add per-request overhead or block the event loop by design.
- **Stack neighbours**: `ADR-008` shares TypeScript across web/mobile (one language), and `technology-stack.md` §2 records the alternatives already weighed.

## Decision

**The backend is built with NestJS 10 on Node.js 20 LTS and TypeScript 5.x.** Each block `B01…B13` maps to one NestJS module with a public surface (`*.public.ts`/exported providers) and a private interior; controllers stay transport-thin (no business logic, F5), services hold domain logic, guards enforce RBAC/ownership (`SEC-REQ-004`), pipes perform validation, and providers are injected through the DI container so every external dependency (database, queues, provider adapters) sits behind a port that tests can fake. The same codebase builds the `api` image and the `worker` image (BullMQ consumers), per `deployment-view.md` §2.

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **Express (bare)** | Ubiquitous; minimal learning curve; huge middleware ecosystem | No module/DI discipline: boundaries, validation, and guards become conventions enforced by review only → `NFR-009` unmeasurable; RBAC and validation drift per route (`SEC-REQ-004` risk); structure must be invented and re-argued | Rejected: **no module discipline** — it would weaken `ADR-002`'s enforcement story, which is the core of `C-21` compliance |
| **Fastify (direct, with plugins)** | Faster raw throughput; schema-first validation | Structural patterns (modules, guards, interceptors) must be assembled manually; smaller ecosystem of *architectural* patterns for a 13-module monolith; team would own framework plumbing | Rejected: performance delta is immaterial next to DB/cache-bound p95 budgets; the missing structure costs more than it saves (viable Fastify-under-Nest adapter remains possible later without changing this ADR's surface) |
| **Spring Boot / Django / Laravel (different languages)** | Mature ecosystems; batteries included | Breaks the single-TypeScript stack shared with `ADR-008` clients; violates the `DEP-01` runtime baseline; hiring/stack mismatch recorded as `INFERENCE` in `technology-stack.md` §1 | Rejected: **different language/stack** — would split domain vocabulary between server and clients and contradict `DEP-01` |
| **AdonisJS / hapi (Node alternatives)** | Some modular structure; TypeScript capable | Smaller community and ecosystem than Nest; fewer teams/mature patterns; still requires proving DI/testing story | Rejected: NestJS's module system maps 1:1 to `B01…B13` with the least adaptation; ecosystem size matters for a long-lived platform |
| **tRPC / RPC-first API layer** | End-to-end type safety with clients | Couples clients to server internals; five surfaces including React Native need a stable, language-neutral contract; `07-api/` is specified as REST conventions | Rejected: canon's API contract is REST + JWT (`architecture-overview.md` §6); a future RPC surface would be a new ADR |

## Consequences

**Positive**

- Modules, DI, guards, pipes, and interceptors give `ADR-002` and `NFR-009` concrete mechanics: import rules are lint-checkable against Nest module paths.
- Ports + DI satisfy `NFR-010`: services test without network, adapters (`mFloosAdapter`, `SmsProviderPort`) are fake-able in unit tests.
- Global validation pipe + exception filter produce the stable error model defined in `07-api/error-model.md`; guards centralize `SEC-REQ-004` checks instead of per-route implementations.
- Mature testing story: Jest integration is first-class (`technology-stack.md` §5), supporting coverage gates (`AC-S-08`).
- TypeScript end-to-end with `ADR-008` clients shares domain vocabulary and reduces contract drift.

**Negative**

- Framework magic (decorators, IoC container) has a learning cost and can obscure call flow — mitigated by documenting placement rules in `06-backend/business-logic-placement.md`.
- Decorator-heavy code increases build times and refactoring surface; DI misuse (service-locator patterns) can quietly violate boundaries — mitigated by review checklist and architecture tests.
- Nest releases are annual-ish; version upgrades (10 → 11) need an ADR/stack-register note when the major line changes.

**Neutral**

- Runtime performance will be dominated by PostgreSQL/Redis/ES latency, not framework overhead.
- NestJS is opinionated about project layout — our layout is already canon (`06-backend/backend-architecture.md`), so opinions align.

**Risks introduced:** framework-level upgrade churn feeds `RISK-021` (supply chain — mitigated by `SEC-REQ-012` scanning); the single-language stack concentrates knowledge in the backend team, feeding `RISK-017` (key-person) unless documented.

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-18` custom build** | NestJS is a framework (libraries), not a commerce platform — no Shopify/Medusa/WooCommerce/Saleor component exists |
| **`C-21` modular monolith** | NestJS modules are the implementation vehicle for `ADR-002`; one deployable, in-process composition |
| **`C-19` PostgreSQL 16 only** | Data access via Prisma inside modules — no per-framework datastore introduced |
| **`C-20` BullMQ only** | Nest workers consume BullMQ queues through the shared kernel queue API; no framework-specific bus |
| **`C-22` Docker Compose** | Builds to plain Node images run by Compose (`node dist/main`, `node dist/worker`) |
| **`C-06…C-08` auth** | Guards/interceptors carry JWT verification (`ADR-010`) and RBAC; framework does not add social/biometric auth |
| **`C-25` / `C-26`** | Event-loop-friendly async I/O with stateless handlers; readiness endpoints `BR-PLT-07` exposed by the app |
