# ADR-007: MinIO for object storage

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Technical lead, DevOps lead (backup/restore), Security officer (upload & bucket policy), Product owner (media UX) |
| **Informed** | Engineering team, QA team, STK-11 (security/compliance) |

## Context

yumn is a media-heavy marketplace: product images (≤10 per product, ≤5 MB each — `BR-CAT-08`), review images (≤5 — `BR-REV-03`), return evidence photos, KYC identity documents, bank-transfer receipts, optional delivery proof photos, category icons, and self-hosted WOFF2 font subsets. None of this belongs in relational rows, and all of it must survive without any cloud-vendor account.

Forces acting on this decision:

- **Dependency `DEP-07`** names *MinIO / S3-compatible object storage* for product and review images; status is `Available`, so the media path is not on the critical path (`DEP-06` is).
- **Portability `NFR-016`**: zero cloud-vendor proprietary services or SDKs in the runtime dependency graph — "object storage accessed only through the S3-compatible MinIO abstraction (`DEP-07`)" is stated verbatim in `../../02-requirements/core/NFR-016.md`; the dependency audit in `12-non-functional/maintainability.md` (`AC-NFR-016-02`) bans cloud SDKs outright.
- **Deployment `C-22` / `ADR-004`**: everything runs as Compose services on a single host — object storage must fit that topology (`CNT-09` in `container-view.md`), not a managed SaaS endpoint.
- **Data posture**: `08-database/database-overview.md` fixes the split — PostgreSQL stores only object **keys** and checksums (`product_image.object_key`, `b03.kyc_document.object_key`), never bytes; `DB-D-04` states Redis/Elasticsearch/MinIO hold only rebuildable or non-row data. Weekly job `J9` reconciles keys ↔ objects (`16-data/data-quality.md`).
- **Security**: `SEC-REQ-011` mandates the upload pipeline (jpg/png/webp ≤5 MB, magic-byte + declared-type check, EXIF strip, no SVG/HTML, malware scan before retrieval, inert serving); KYC documents are `RESTRICTED` with AES-256 at rest and presigned-URL-only access (`16-data/data-classification.md`, `09-security/data-protection.md`). Finding **`SEC-008`** (bucket listing / presigned-URL exposure) is open and must be designed against, not discovered later.
- **Reliability `NFR-007`**: MinIO down ⇒ new uploads paused with a clear message, existing media served from CDN/edge cache, orders and wallet unaffected (degradation matrix in `12-non-functional/reliability.md`; `FM-17`; readiness is **non-gating** for reads — `15-deployment/health-checks.md`).
- **Recovery**: `DATA-REQ-004`/`NFR-006` cover PostgreSQL with WAL + snapshots; object bytes get a nightly snapshot with a documented ≤24 h object RPO (`INFERENCE` — canon fixes the DB RPO only), and the KYC bucket is copied with the pre-deploy snapshot (`14-devops-infrastructure/backup-recovery.md`). Retention rules `RC-05`/`RC-07` are expressed as MinIO lifecycle rules (`16-data/retention-and-archival.md`).
- **Neighbouring decisions**: `ADR-001` keeps object keys as relational data; `ADR-004` runs MinIO as a Compose service; `ADR-008` delivers images through the CDN/edge budget (`NFR-002`).

## Decision

**MinIO is yumn's only object store: self-hosted, S3-API-compatible, running as a Docker Compose service with its own `miniodata` volume.** Buckets are separated by sensitivity — a media bucket readable through the edge/CDN path, and a private bucket for KYC documents and bank-transfer receipts reachable only through short-lived presigned URLs issued by the API. Object names are server-generated and non-enumerable; PostgreSQL stores only keys, checksums and dimensions. Every upload passes the `SEC-REQ-011` validation pipeline before an object becomes retrievable. No cloud object storage (S3, GCS, Azure Blob) and no local-filesystem storage of business objects may appear in any environment; a future move to a managed store requires a superseding ADR (`decision-log.md` §3 — cloud migration candidate).

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **Local filesystem / host volume only** | Zero extra service; simplest possible write path | Tied to one host's disk (worse than the rest of the stack, which is at least portable); no S3 semantics, no presigned URLs, no lifecycle rules; backup/restore becomes bespoke scripting; no growth path (`technology-stack.md` §3 records this alternative) | Rejected: cannot deliver presigned private KYC access, retention lifecycle, or the portability story `NFR-016` requires |
| **Cloud object storage (AWS S3 / GCS / Azure Blob)** | Highest durability numbers; zero ops; lifecycle/CDN features mature | Direct `NFR-016` lock-in; cloud account/payment friction in this market; adds cloud SDKs to the runtime graph, which `AC-NFR-016-02` explicitly forbids; KYC/PII leaves the self-hosted perimeter (`SEC-008`, `RISK-009`) | Rejected: portability and data-perimeter requirements; revisited only via the reserved cloud-migration ADR |
| **Store image bytes in PostgreSQL (`bytea`/large objects)** | One backup story; no second service | Bloats the system-of-record database and its WAL — punishing the 100M-row capacity plan (`NFR-017`) and the RPO story; contradicts `database-overview.md`'s explicit row/object split and `DB-D-04` | Rejected: object payloads do not belong in rows; the DB must stay fast for checkout (`RISK-008`) |
| **Ceph / SeaweedFS-style self-hosted cluster** | S3-compatible; self-hosted | Ceph needs a real cluster (monitors, OSDs) — operability far beyond a small team (`RISK-005`) and beyond single-host `C-22`; MinIO is what `DEP-07` names and tests against | Rejected: complexity vs team capacity; single-node MinIO with snapshots matches the v1 posture |
| **Third-party image CDN/resizer (Cloudinary-style SaaS)** | Automatic transforms, bandwidth offload | Recurring cost; vendor lock-in; product/KYC media leaves the self-hosted perimeter; contradicts the zero-cloud-SDK audit | Rejected for v1: thumbnails are derived at upload and the edge cache (`DEP-08`) already covers delivery; a future edge-strategy ADR exists (`DOC-ARCH-010` §4) |

## Consequences

**Positive**

- Media is isolated from the OLTP database: images can be backed up, restored, lifecycle-purged and CDN-cached independently of WAL and query load.
- The S3 API is the industry portability contract — lifting MinIO to any S3-compatible target later is an ops change, not an application rewrite (aligns with `NFR-016` and the reserved cloud-migration ADR).
- Private bucket + server-generated keys + short-lived presigned URLs is a simple, testable answer to `SEC-008` and to `DATA-REQ-002` minimization for `RESTRICTED` KYC documents.
- Lifecycle rules implement retention (`RC-05` product images referenced by orders, `RC-07` KYC sets) without application code, and orphan-key sweeps (`J9`, `DATA-REQ-006`) keep keys and objects honest.
- Degradation is graceful and product-shaped: uploads pause with an honest message, reads ride the edge cache, and no money/order path depends on media (`NFR-007`, `P9`).

**Negative**

- A second stateful service to patch, monitor and back up — adds to the small-team operational load (`RISK-005`).
- Object recovery RPO (≤24 h nightly snapshot, `INFERENCE`) is materially weaker than the database RPO (≤15 min); losing a day of newly uploaded KYC documents would require re-collection — mitigated by copying the KYC bucket with every pre-deploy snapshot.
- Single-instance media availability on one host: a host outage takes uploads and (until restore) image reads down together with everything else — this is the same residual already tracked for the topology (`RISK-019`), not a new one.
- Image transformations (thumbnails, variants) are derived at upload time, so a change to transform rules requires a backfill job over existing objects.

**Neutral**

- Version drift within the current MinIO major line needs no ADR (stack register §8); a major-line or product change does.
- Font subsets and CMS attachments share the same bucket policy and pipeline — no per-content-type service sprawl.
- Bucket policy, TLS posture between app and MinIO (`MINIO_USE_SSL` on the internal network) and credential rotation (S-09, 90 days) are operational settings, not architecture changes.

**Risks introduced:** exposure of bucket contents or long-lived presigned URLs (finding `SEC-008`) rolls into **`RISK-009`** (data breach / PII leak — MEDIUM); operational load feeds `RISK-005`; the weaker object RPO is recorded as an accepted `INFERENCE` in `backup-recovery.md` and is re-checked at every DR drill (`AC-S-17`).

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-18` custom build** | MinIO is infrastructure, not a commerce platform — no Shopify/Medusa/WooCommerce/Saleor component exists anywhere (holds for ADR-001…ADR-010) |
| **`C-22` Docker Compose** | `minio` runs as a Compose service (`CNT-09`) with healthcheck and the `miniodata` volume; no managed endpoint is required (`deployment-view.md`) |
| **`NFR-016` portability / no cloud lock-in** | Self-hosted, S3-compatible API; cloud SDKs banned from the runtime graph (`AC-NFR-016-02`); any Docker host runs the stack |
| **`C-19` PostgreSQL 16 only** | Bytes never enter the database — only keys, checksums and dimensions are relational (`DB-D-04`) |
| **`C-21` modular monolith** | Media upload/read is served by the monolith's media paths and worker jobs; MinIO is a data service, not a separately deployed application |
| **`NFR-006` / `DATA-REQ-004` recovery** | Nightly object snapshots with manifest checksums, pre-deploy copy of the KYC bucket, restore target ≤60 min (`backup-recovery.md`) |
| **`NFR-007` degradation** | MinIO readiness is non-gating for reads; uploads fail gracefully (`FM-17`); orders/wallet unaffected |
| **`SEC-REQ-011` upload security** | Type/size/magic-byte validation, EXIF strip, no SVG, AV scan before retrieval, inert serving — enforced before any object is written (`SEC-C-22`) |
