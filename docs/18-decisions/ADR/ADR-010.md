# ADR-010: Phone + OTP authentication with short-lived JWTs

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Security officer (STK-11), Technical lead, Business development (`DEP-06`), Product owner |
| **Informed** | Engineering team, QA team, Operations/support (lockout & session tooling) |

## Context

`FR-001` defines identity for a market where the phone number — not email — is universal. Authentication must be usable on low-end devices over variable networks, resist credential stuffing and OTP pumping, and still allow the stateless horizontal scale-out that `NFR-018`/`P8` assume.

Forces:

- **Constraints**: `C-06` — phone + OTP only as primary identifier and verification channel, no email-primary auth, no social login; `C-07` — no biometrics as server authentication; `C-08` — access token 15 minutes, refresh token 7 days with single-use rotation. These three are the fixed frame of this ADR.
- **Requirements**: `SEC-REQ-001` (OTP for registration, password reset and sensitive changes — 6 digits, 5 min, 3 attempts), `SEC-REQ-003` (RS256 JWT, httpOnly + SameSite cookies, ≤5 devices), `SEC-REQ-004` (server-side authorization on every request), `SEC-REQ-002` (bcrypt cost 12, no plaintext), `SEC-REQ-005` (5 failures → 15-min lockout), `SEC-REQ-009` (per-IP/per-user rate budgets).
- **Rules**: `BR-AUTH-01…BR-AUTH-08` — phone `^7[0-9]{8}$` unique, password policy, OTP parameters, lockout, single-use refresh with family revocation, 5-session cap, reset revokes all sessions, email never used for login or OTP.
- **Channel reality**: OTP delivery is SMS primary with automatic WhatsApp failover inside the 5-minute validity window (`BR-NTF-03`, `INT-REQ-003/004`); there is **no email fallback** (`BR-NTF-01`, `GAP-03`). `DEP-06` (SMS contract + WhatsApp Business approval) is **NOT STARTED** and is the Phase 0 gate — `RISK-006` is CRITICAL and finding `SEC-011` rates the channel dependency CRITICAL.
- **Open canon ambiguity**: `SEC-012` records that `FR-001`/`BR-AUTH-04` scope OTP to registration, reset and sensitive changes (login = phone + password), while a broader reading of `SEC-REQ-001` suggests OTP on every authentication. This ADR follows the requirement statements and `FR-001`; the ambiguity must be resolved before implementation.
- **Scale**: sessions must not require a synchronous store hit on every request — token verification is local, while revocation is enforced through the session registry (Redis `DEP-03`, durable record in PostgreSQL) checked against the token's `sid`.
- **Neighbouring decisions**: `ADR-003` (guards/interceptors carry this design), `ADR-005` (Redis counters, OTP TTL keys), `ADR-008` (cookie vs secure-storage handling per client), `ADR-002` (identity is module `B01`).

## Decision

**Identity is the Yemeni mobile number (`BR-AUTH-01`), paired with a password (bcrypt cost 12) and verified by 6-digit OTP delivered over SMS (primary) with automatic WhatsApp fallback — never email — for registration, password reset and sensitive changes.** Sessions use **RS256 JWTs: a 15-minute access token plus a 7-day single-use refresh token that rotates on every use within a session family**; reuse of a consumed refresh token revokes the whole family and alerts the user (`BR-AUTH-05`). Tokens travel as httpOnly + SameSite cookies on web and in platform secure storage on mobile — never in `localStorage`. A session registry (Redis with a durable PostgreSQL record) enforces the ≤5-device cap (`BR-AUTH-06`) and immediate revocation (password reset ⇒ all sessions dead, `BR-AUTH-07`); authorization is re-evaluated server-side on every request (`SEC-REQ-004`), and OTP/rate counters are server-side in Redis. No social login, no server-side biometrics, no email identity and **no additional MFA factor in v1** (decision `D-06`; privileged-role gap tracked as `SEC-012`).

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **Email as primary identity / email OTP** | Familiar pattern globally; free channel | Email is not universal in the target market; no email delivery stack exists in v1 (`BR-NTF-01`, `GAP-03`); recovery would depend on a channel the project deliberately excluded | **Excluded by `C-06`** and `BR-AUTH-08`; also blocked by scope (`BR-NTF-01`) |
| **Social login (Google/Apple) / SSO** | Zero-password UX; no OTP cost | Requires provider accounts the audience may not have; adds an external identity dependency and PII sharing; excluded by canon | **Excluded by `C-06`** — phone is the only primary identifier in v1 |
| **Biometric authentication as server factor** | Strong, frictionless on device | Device sensors vary wildly; server cannot verify a biometric reliably; recovery paths multiply; no coverage guarantee across the device matrix (`DEP-12`) | **Excluded by `C-07`** — device-level biometrics may unlock the app locally only, never authenticate to the server |
| **Opaque server-side sessions only (no JWT)** | Instant revocation; no token theft surface | Every request hits the session store, coupling read throughput to Redis/Postgres at `C-25` scale and weakening the `P8` stateless-tier design; contradicts the lifetimes fixed by `C-08` | Rejected: canon mandates the JWT lifetime model — and the hybrid (short JWT + registry check on `sid`) already yields immediate revocation without a store read per field |
| **Long-lived JWTs without rotation (30+ days, no refresh)** | Fewer round trips; simpler clients | A stolen token is valid for months; no theft detection; no family revocation; unbounded blast radius on a money platform (`RISK-001` exposure) | Rejected: violates `C-08` directly and removes `BR-AUTH-05`'s theft signal |
| **TOTP app / hardware-key MFA for all users** | Strong second factor | New secret store, enrollment and recovery paths the market does not require; support load on a small team; no requirement mandates it | Rejected for v1 (`INFERENCE`): OTP already acts as a second factor on high-risk events; privileged-role MFA is the reserved future ADR candidate (`decision-log.md` §3, `SEC-012`) |
| **Password-only, no OTP anywhere** | Cheapest; no SMS cost | Registration and phone-number claims would be unverified (SIM ownership is the identity proof); reset would not verify possession; violates `SEC-REQ-001` | Rejected: OTP is required precisely where possession of the phone must be proven |

## Consequences

**Positive**

- Stateless scale-out: API replicas verify JWTs locally (`P8`, `NFR-018`), while the registry keeps revocation, device cap and family-theft response immediate — the combination satisfies both scale and control goals.
- A 15-minute access window bounds token-theft blast radius; single-use rotation with family revocation turns refresh-token theft from a silent, long-lived compromise into a detected, alertable event (`AC-SR003-02`).
- Phone + OTP matches the market: no email dependency, works on any handset, and the two-channel chain (SMS → WhatsApp) covers single-provider failure (`AC-IR003-01`) without inventing an insecure third path.
- Uniform server-side enforcement: guards/pipes in `ADR-003` apply the same checks on all five surfaces; clients cannot weaken security because they only mirror it (`SEC-REQ-004`).
- Counters shared through Redis (`ADR-005`) make lockout, cooldown and resend budgets correct across replicas and defeat OTP pumping (`TM-02`, `SEC-006` remediation).

**Negative**

- Registration, reset and sensitive changes are unavailable if both SMS and WhatsApp are degraded — there is **no third recovery path** (finding `SEC-001`); until `DEP-06` is contracted, this is the hardest project blocker (`RISK-006`, `SEC-011`).
- OTP delivery costs money per send and is metered (60 s cooldown, ≤3 resends/10 min) — abuse control and unit economics pull in the same direction.
- SIM-swap interception remains possible (`SEC-004`, `RISK-010`): possession of the SIM is the identity proof by design; mitigations are rate budgets, security notices (`BR-NTF-02`) and support tooling, not a second identity channel.
- Cookie transport on web requires CSRF defense (`SEC-REQ-008`) and careful CORS (`SEC-010`), and clock-skew sensitivity in reuse detection must be pinned down (`SEC-009`, NTP-synced hosts).
- Privileged roles (ADMIN, SUPER_ADMIN) have no *additional* factor at login — consciously accepted for v1 and tracked as `SEC-012` (HIGH, OPEN).

**Neutral**

- Algorithm is pinned to RS256 (`alg: none` and HMAC-confusion vectors rejected — `AC-SR003-04`); key custody and rotation live in `09-security/secrets-management.md`.
- Login is phone + password with 5-failure/15-minute lockout (`BR-AUTH-04`); OTP is bound to its purpose tag, so a reset code can never complete a registration (`SEC-001` scope note).
- Session state in Redis is disposable — losing it degrades revocation checks, never money data (`RISK-023` design rule: PostgreSQL is the durable session record).

**Risks introduced:** channel dependency is registered as **`RISK-006`** (CRITICAL, score 20 — `DEP-06` Phase 0 gate, dual-provider failover, honest OTP-screen states); SIM-swap/false-claim fraud feeds `RISK-010`; open findings carried by this design are `SEC-001`, `SEC-004`, `SEC-006`, `SEC-009`, `SEC-011`, `SEC-012`.

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-06` phone + OTP only** | Phone `^7[0-9]{8}$` is the unique primary identifier; verification via SMS/WhatsApp OTP; no email-primary path, no social/SSO endpoint exists (`TST-CON-06`) |
| **`C-07` no biometrics as server auth** | No biometric enrollment, verification or recovery endpoint; device biometrics are client-side unlock only |
| **`C-08` JWT lifetimes** | Access 15 min, refresh 7 days single-use rotation — enforced in token config and boundary-tested (14:59 accept / 15:01 reject, `AC-SR003-01`) |
| **`C-18` custom build** | Identity, OTP, sessions and RBAC are purpose-built in module `B01` — no external IAM, identity SaaS or commerce-platform auth is adopted (holds for ADR-001…ADR-010) |
| **`C-21` modular monolith** | Auth is one NestJS module (`B01`) with guards shared in-process; no separate auth service deployment |
| **`C-22` Docker Compose** | Stateless API containers plus Redis/PostgreSQL services; session and counter state needs no new topology |
| **`SEC-REQ-001` / `SEC-REQ-003`** | OTP parameters fixed server-side (6 digits, 5 min, 3 attempts, 60 s cooldown); RS256 tokens, cookie/secure-storage transport, ≤5 devices with oldest-eviction (`AC-SR003-03`) |
| **`NFR-018` scale-out** | Token verification is local to each replica; shared Redis counters keep rate limits correct across replicas without a per-request database read |
