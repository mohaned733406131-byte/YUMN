# ADR-009: Wallet-only payments with provider adapters

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Finance (Admin) STK-07, Legal/sponsor (regulatory exposure), Technical lead, Business development (`DEP-05`) |
| **Informed** | Engineering team, QA team, Product owner, STK-12 (payment partners) |

## Context

yumn handles real money in a market with no usable card/credit rails for its audience. The money model is the product's trust promise: buyers pre-fund, the platform escrows, vendors get paid after delivery. That promise is only coherent if the *entire* payment surface is inside one controlled ledger.

Forces:

- **Constraints `C-01…C-05`** fix the model: wallet-only (COD prohibited — `C-01`), no cards (`C-02`), no BNPL/credit (`C-03`), no crypto and single currency YER (`C-04`), and exactly two top-up rails — mobile wallet (m-Floos, OneCash) and admin-verified bank transfer (`C-05`).
- **Trust model**: escrow requires pre-funding — COD has no buyer protection and a high return-to-origin rate (rationale of `C-01`); escrow holds funds 7 days from DELIVERED (`C-12`) and pays out per sub-order with commission (`FR-014`, `BR-ESC-01…05`).
- **Requirements**: `FR-013` (wallet, top-ups, payments, double-entry ledger, freezes), `INT-REQ-001` (initiate → signed callback / reconciled poll → credit ledger, sandbox before production), `INT-REQ-002` (manual admin verification of bank transfers), `INT-REQ-008` (provider abstraction — no vendor types in domain code).
- **Integrity rules**: every balance change posts balanced double-entry rows (`BR-PAY-06`), the ledger is append-only (`DATA-REQ-007`), balances never go negative (`BR-PAY-05`), all money operations are idempotent (`BR-PAY-08`, `BR-PLT-03`), refunds credit the wallet — never an external cash-out (`BR-PAY-07`), and daily reconciliation compares ledger vs provider statements (`BR-ESC-08`, `BR-FIN-03`, job family `J1…J6`).
- **Unresolved external dependencies**: `DEP-05` (m-Floos + OneCash merchant API access) is **NOT STARTED** and blocks production top-ups → **`RISK-003`**; `DEP-10` (Central Bank position on closed-loop wallets) is **NOT STARTED** and is marked *existential* for this model → **`RISK-012`** (CRITICAL, linked to `ADR-009` by name in the risk register).
- **Degradation**: one provider down ⇒ that top-up method is disabled, the other provider still offered; both down ⇒ top-up UI degrades to bank transfer only with a localized banner (`10-integrations/integration-overview.md` §4).
- **Neighbouring decisions**: `ADR-001` gives money one ACID boundary; `ADR-005` carries every async money job (callbacks, reconciliation, escrow timers); `ADR-002`/`ADR-003` keep the wallet inside the monolith behind `PaymentProviderPort`.

## Decision

**yumn's only payment method is the platform wallet: orders pay exclusively from wallet balance (`BR-PAY-01`), and wallets are funded only by m-Floos/OneCash top-ups credited after a verified provider callback or reconciled poll (`BR-PAY-03`), or by admin-verified bank transfer (`BR-PAY-04`).** All balance, escrow, commission, refund and payout movements post balanced rows to the append-only double-entry ledger inside the single PostgreSQL transaction boundary (`ADR-001`). External payment providers are reached **only** through `PaymentProviderPort` adapters (m-Floos, OneCash, bank-manual) that own credentials, HTTP calls, payload mapping and signing, normalize errors to the fixed taxonomy, and are selected by configuration — vendor IDs, SDK types and error strings never appear in domain code (`INT-REQ-008`, enforced by CI import rules `AC-IR008-01/03`). Cash on delivery, card payments, BNPL, crypto, multi-currency balances and any external cash-out are excluded for v1; adding any of them would require revising a constraint (`C-01…C-04`) and therefore a new ADR.

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **Cash on Delivery** | Familiar in the market; removes top-up friction | No buyer protection, high RTO, no escrow possible (funds are not pre-funded), manual cash reconciliation for every order | **Excluded by `C-01`** — the escrow trust model cannot exist without pre-funding; vendor COD pressure (`STK-04`) is a known business tension, not an architecture option |
| **Card gateway (Stripe / Moyasar / Tap)** | Familiar checkout; instant funding | Card-network licensing/PCI scope and regulatory exposure the project explicitly refuses; breaks the single-currency, single-ledger posture | **Excluded by `C-02`**; `technology-stack.md` §7 lists all card processors as forbidden |
| **BNPL / installments / credit** | Raises basket size | Credit risk, licensing, collections — an entire regulated business inside the platform | **Excluded by `C-03`** |
| **Crypto / stablecoin rails** | Programmable settlement | Regulatory and volatility risk; unusable for the target audience; violates single-currency rule | **Excluded by `C-04`** |
| **Third-party custodial wallet / external escrow (provider holds balances)** | Shifts some regulatory burden off the platform | Loses the in-platform double-entry ledger, commission engine and reconciliation that `FR-013`/`FR-014` require; still depends on `DEP-10` legitimacy; splits money truth across two systems | Rejected: the ledger *is* the product's trust core (`NFR-008`, `RISK-001`) — custody questions are handled by engaging the regulator (`DEP-10`), not by outsourcing correctness |
| **Direct bank API for top-ups and payouts** | Removes manual verification labour | No bank API access exists in this market context; would also add a third provider integration before `DEP-05` is even contracted | Rejected for v1: `INT-REQ-002` fixes manual admin verification; bank transfer doubles as the fallback rail when wallet providers are down |
| **Single wallet provider only** | One integration to build | No failover — a provider outage blocks all top-ups (the exact failure `RISK-003` rates HIGH) | Rejected: `INT-REQ-001` requires m-Floos **and** OneCash with configuration-based selection through the port |

## Consequences

**Positive**

- One controlled, auditable money truth: balanced postings, append-only history, idempotent operations and daily reconciliation give the zero-imbalance invariant (`NFR-008`, `AC-S-14/15`) a single place to be enforced and tested.
- Escrow, commission and payout logic (`C-12`, `BR-ESC-01…08`) are pure ledger arithmetic — no provider round-trip inside an order transition, so the 17-state machine (`C-09`) never waits on a network call.
- Adapter isolation makes provider churn cheap: sandbox → production credential swap, provider failover, and even a provider replacement require zero domain edits (`AC-IR008-02`), which is the direct mitigation for `RISK-003`.
- Bank transfer is a permanent, provider-independent fallback rail, keeping top-ups possible during wallet-provider outages and when both circuits are open.
- No card fields, no PAN storage, no PCI scope; refund abuse paths are bounded (wallet-only refunds, `BR-PAY-07`).

**Negative**

- Pre-funding friction: customers must top up before buying — a conversion cost accepted as the price of buyer protection (`C-01` rationale); top-up UX carries callback/poll latency and must show honest pending states.
- Manual bank verification is labour-bound: admin capacity is part of the availability of the credit path (`API-ADM-030/031`, `BR-PAY-04`).
- Production top-ups are blocked until `DEP-05` sandbox acceptance passes (`AC-IR001-05`), and the whole model is exposed to `DEP-10` — both dependencies are **NOT STARTED** today.
- Two provider integrations plus a manual flow must each be reconciled, and provider statements arrive on their own schedules — reconciliation mismatches require a finance runbook.

**Neutral**

- Single currency YER with integer amounts means no FX code paths exist anywhere (`C-04`, decision `D-01`); commission tiers (5–20%, default 10%) and payout batching are unaffected by provider choice.
- Wallet freezes (`BR-PAY-09`) and admin verification tooling live in the admin console regardless of provider.
- Card/BNPL/crypto remain excluded until the sponsoring constraints are formally revised — an ADR alone can never override them (`DOC-ARCH-010` §6).

**Risks introduced:** **`RISK-003`** (third-party wallet provider outage/commercial failure — HIGH, score 15: dual providers, configuration failover, bank-transfer fallback, reconciliation continues for in-flight transactions) and **`RISK-012`** (Central Bank position on closed-loop wallets — CRITICAL, score 20: existential for this ADR; sponsor-owned, gated by `DEP-10`/`ASM-12` before payment build locks). Residual: `RISK-010` (payment fraud / false disputes — mitigated by `SEC-REQ-005/009`, webhook signature verification and idempotency keys) and `RISK-001` (ledger integrity — mitigated by the design above).

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-01` wallet-only payments, no COD** | Order creation rejects any `payment_method != wallet` (`TST-CON-01`, `BR-PAY-01`); no COD flow, state or endpoint exists |
| **`C-02` no card payments** | No card fields, no card endpoints, no card processors in the dependency graph (`technology-stack.md` §7) |
| **`C-03` no BNPL / credit** | Balances cannot go negative (`BR-PAY-05`); no credit or instalment concept exists in wallet, order or payout code |
| **`C-04` no crypto, single currency YER** | Integer YER only, `CHECK (currency = 'YER')` on money tables; no digital-asset integration |
| **`C-05` top-up methods** | Exactly m-Floos, OneCash and admin-verified bank transfer — each an adapter/flow behind `PaymentProviderPort`; constraint test `TST-CON-05` |
| **`C-12` escrow** | 7-day hold from DELIVERED, dispute freeze, commission at release — all ledger movements inside the single ACID boundary |
| **`C-18` custom build** | The wallet, ledger, escrow and payout engine are purpose-built; only *rails* are external, and they sit behind adapters (holds for ADR-001…ADR-010) |
| **`C-19` PostgreSQL 16 only** | One ACID store holds balance, escrow and ledger — no second financial datastore and no provider-side balance is authoritative |
| **`C-21` / `C-22` topology** | `WalletModule` (B07) is a monolith module; callbacks, reconciliation and payouts run as BullMQ jobs (`ADR-005`) on the Compose topology (`ADR-004`) |
| **`NFR-008` data integrity** | Balanced double-entry postings, idempotency keys, append-only ledger, daily reconciliation — verified by `AC-S-14`/`AC-S-15` and `BR-ESC-08` |
