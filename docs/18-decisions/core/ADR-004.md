# ADR-004: Docker Compose deployment; no Kubernetes in v1

|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |

| **Informed** | Engineering team, QA team, Product owner, sponsor (STK-01) |

## Context

yumn must run in production at **99.99% availability with RTO ≤ 1 h and RPO ≤ 15 min (`C-26`, `NFR-005/006`)** while serving **10K concurrent users (`C-25`)**, on infrastructure operated by a small team. The deployment reality in Yemen (host availability, connectivity, cloud payment friction) favours self-hosting, and `NFR-016` explicitly forbids cloud-vendor lock-in in v1.

Forces:

- **Constraint `C-22`: Docker + Docker Compose deployment; no Kubernetes in v1**, cited in canon together with **`ADR-004`** (DOC-ARCH-010 §2 rule 2 — the number is canon-locked).
- **Operability risk `RISK-005`**: STK-14 identifies small team vs 99.99% as a standing risk; canon's stated mitigation is operational simplicity (`C-21`, `C-22`).
- **Environment parity (`NFR-016`, `NFR-020`)**: dev/staging/prod must behave the same — layered Compose files with identical images achieve this without cluster machinery.
- **Workload shape**: one API, one worker, plus data services (PostgreSQL, Redis, ES, MinIO, Prometheus/Grafana) and an Nginx edge — nothing in v1 needs pod scheduling across nodes (`deployment-view.md` §8).
- **Neighbouring decisions**: `ADR-002` keeps one deployable; `ADR-007` (MinIO) and `ADR-005` (Redis) assume self-hosted services in the same topology; `ADR-001`'s backup story (WAL/snapshots) is designed for a single primary host.

## Decision

**Production, staging, and development are deployed with Docker and Docker Compose on a single host (or tightly coupled host set): one `compose.yaml` base plus per-environment overrides (`compose.override.yaml`, `compose.staging.yaml`, `compose.prod.yaml`), identical images across environments, Nginx (or equivalent) as the only published edge, health/readiness-gated rolling restarts, and automated backups. No Kubernetes, Nomad, Swarm, or any orchestrator is introduced in v1.** Container images and service definitions remain portable so that a future orchestrator (which would require a formal `C-22` change and a superseding ADR) can adopt them without rewrite.

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **Kubernetes (any distribution)** | Autoscaling, self-healing, rolling orchestration, ecosystem | etcd/CNI/ingress/RBAC operational surface dwarfs the team (`RISK-005`); control-plane ops consume the very availability budget it promises; single-region single-site reality means node-level redundancy is mostly theoretical; cost (even "free" K8s is staff time) | **Rejected by `C-22`** — explicitly excluded in v1; `deployment-view.md` §8 documents that our workload needs nothing pod scheduling provides |
| **Nomad / Docker Swarm** | Lighter than K8s; native Compose-ish | Still a cluster control plane with its own failure modes; no added value for one backend + data services; two things to learn | Rejected: unneeded complexity vs `C-22`'s simplicity intent; Compose already covers parity, restarts, and healthchecks |
| **VM images / bare scripts (no containers)** | No container runtime dependency | Environment drift between dev/staging/prod (the exact problem `NFR-016` parity solves); slower onboarding; inconsistent rollback | Rejected: containers are the parity mechanism; VM-only deploys raise `RISK-005` by making every environment bespoke |
| **Cloud-vendor PaaS (ECS/App Service/managed K8s)** | Managed control plane; less hardware ops | Violates `NFR-016` no-lock-in; payment/access friction for cloud accounts in this market; egress and region latency uncertainty | Rejected: lock-in and access risk; portability is a stated v1 requirement (cloud may return via a future ADR) |
| **Compose on multiple replicated hosts without an orchestrator** | Partial redundancy | Split-brain, failover, and deploy coordination become manual scripts — worse ops than either extreme | Rejected: manual multi-host coordination is the worst operability profile for the team; real multi-host HA belongs to the future ADR triggered by `RISK-019` |

## Consequences

**Positive**

- One comprehensible deployment artifact: `docker compose up` with layered parity gives fast onboarding, deterministic environments, and simple rollback (previous image tags) — directly mitigating `RISK-005`.
- Native fit with the CI/CD design: build images per commit, run integration tests against a Compose stack, deploy by pulling tags (`deployment-view.md` §7) — supports `NFR-020` zero-downtime rolling restarts of stateless `api` replicas.
- Health/readiness gates (`BR-PLT-07`), restart policies, graceful shutdown, and network isolation (`net-edge`/`net-app`) are all expressible in Compose without extra agents.
- Portability: images + compose files map 1:1 onto any future orchestrator; adopting one later is an ops change, not an application rewrite.

**Negative**

- **Single-host failure domain:** host loss, disk failure, or site outage exceeds the 4.32-min/month `C-26` budget until restore completes — availability depends on hardware reliability, backups, and fast recovery rather than on redundancy.
- Vertical scaling limits: beyond `C-25`, growth requires the documented `NFR-018` path (API replicas within the host, read replica) and eventually a multi-host decision.
- Some rolling-update guarantees are hand-rolled (health gates + restart policies) instead of platform-provided — deploy correctness depends on pipeline discipline.

**Neutral**

- Kubernetes remains excluded, not forbidden forever: any change requires a formal `C-22` revision and a new ADR (DOC-ARCH-010 §6 precedence).
- Monitoring/backup tooling (Prometheus, Grafana, WAL archiving) run as ordinary Compose services.

**Risks introduced:** **single-host residual risk vs `C-26` is tracked as `RISK-019`** (HIGH — plan: WAL/snapshot restore drills `AC-S-17`, monitored budget consumption, documented multi-host escalation path); day-to-day ops load feeds `RISK-005`; infra readiness feeds `RISK-014` (`DEP-08` domains/TLS/CDN at the edge).
