# ADR-006: Elasticsearch 8 for search & discovery

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Technical lead, Product owner (discovery quality), QA team (relevance tests), DevOps lead (cluster ops) |
| **Informed** | Engineering team, Design (search UX), STK-03/STK-04 (users of discovery) |

## Context

`FR-009` (Search & Discovery) demands Arabic-aware full-text search, filters, sorting, category browse, and merchandising at marketplace scale — with the quality bar that discovery *is* the storefront for most customers. The specific forces:

- **Arabic-first (`C-24`)**: Arabic morphology (affixes, stem variation) needs a real analyzer chain; `ASM-15` assumes the Elasticsearch Arabic analyzer (stemming) suffices without custom NLP — **unverified until the Phase 1 relevance spike**.
- **Performance**: search endpoints are among the hottest reads under `C-25`; p95 < 200 ms (`NFR-001`); catalog caching targets ≥ 80% (`NFR-004`) but facet/aggregation queries do not belong on the OLTP database.
- **Reliability**: `NFR-007` requires graceful degradation — search/cache down must not break browse; `DEP-04` (Elasticsearch 8) is `Available`, with the documented fallback being browse-by-category only.
- **Data rules**: index content is *derived* — nightly/on-demand reconciliation `J8` compares index vs ACTIVE products with auto-reindex; index is rebuildable, hence **no backup required** (`deployment-view.md` §4).
- **Security**: `SEC-007` flags that index PII protection is unspecified — indexing must stay within a field allowlist (`DATA-REQ-002`).
- Neighbours: `ADR-001` remains the system of record; `ADR-005` carries index-refresh jobs; `ADR-002` gives Search (`B04`) read-only access to Catalog/Content.

## Decision

**Elasticsearch 8 is the search and discovery engine for `FR-009`: full-text (Arabic analyzer + stemming), filters, facets/aggregations, sorting, and typeahead are served from an ES index that is strictly derived from PostgreSQL.** The index contains only allow-listed public catalog fields (no PII beyond what product display requires), is updated by module-owned BullMQ jobs, is reconciled by `J8` (nightly + on-demand) with auto-reindex on drift, and is treated as **rebuildable state**: when ES is unavailable, readiness still reports OK for core routes and the product falls back to category browse with honest UX (`NFR-007`).

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **PostgreSQL full-text search (tsvector + pg_trgm)** | No new dependency; transactional consistency with `ADR-001`; simpler ops | Weaker Arabic handling (no mature Arabic stemmer/analyzer comparable to ES); facet/aggregation performance poor at 10M products; every heavy query competes with money/OLTP traffic → `NFR-001` risk; limited relevance tuning tooling | Rejected: `technology-stack.md` §3 — **weaker Arabic handling and scale**; would put discovery load on the database that must stay fast for checkout (`RISK-008`) |
| **Meilisearch / Typesense** | Very fast to integrate; pleasant typo tolerance; low ops burden | Smaller aggregation/facet surface needed for marketplace filtering and merchandising (`FR-009`); Arabic analysis maturity is thinner; scaling multi-node later is less proven | Rejected: **smaller feature/aggregation surface**; facet-heavy category browsing and merchandising rules favour ES |
| **Managed search service (Algolia, OpenSearch SaaS)** | Zero ops; excellent relevance UX | Direct `NFR-016` lock-in; recurring cost in a price-sensitive market; catalog data leaves the self-hosted perimeter (PII/index controls, `SEC-007`) | Rejected: portability + data-perimeter requirements; any future move is a candidate ADR (`decision-log.md` §3) |
| **No dedicated search (browse + SQL LIKE)** | Minimal work | Discovery quality fails `FR-009`; Arabic relevance unachievable; conversion collapse in a marketplace | Rejected: search is a Critical-path functional requirement, not an optimisation |
| **Custom NLP service for Arabic** | Potentially best relevance | Unbounded scope, new models/infrastructure, unverifiable before launch; `ASM-15` explicitly tests whether it is unnecessary | Rejected for v1: start with the ES Arabic analyzer (the `ASM-15` spike decides); a custom-NLP path remains a future decision if the spike fails |

## Consequences

**Positive**

- Arabic-aware relevance plus facets/aggregations deliver `FR-009` quality that relational FTS cannot reach at target scale (canon rationale, DOC-ARCH-010 §1).
- OLTP database stays free of heavy search load — protecting `NFR-001` for money/checkout paths (`ADR-001` synergy).
- Derived, rebuildable index makes failure cheap: delete and reindex is a supported recovery, simplifying backup planning (`deployment-view.md` §4 volume table).
- `J8` reconciliation + auto-reindex provides self-healing detection for index drift (`DATA-REQ-006`).
- Search is already isolated in module `B04` behind read-only dependencies (`module-boundaries.md` D9), so scaling or replacing the engine later is a bounded change.

**Negative**

- A second stateful service to operate (heap sizing, shard/mapping discipline, upgrades) — adds to small-team load (`RISK-005`).
- Eventual consistency: products can lag the database between refresh cycles; UI must tolerate short windows where a just-published product is not yet searchable (`J8` cadence bounds this).
- Relevance quality for Arabic is *unproven* until the Phase 1 spike — the design accepts a measured risk rather than assuming success.

**Neutral**

- Single-node ES is acceptable for v1 (dev/staging), with a documented path to 1–3 nodes; multi-node topology is a reserved future ADR triggered when single-node no longer meets `NFR-001` (DOC-ARCH-010 §4).
- Index snapshots are not part of the backup set; PII-in-index is governed by allowlist + deletion wiring (`SEC-007` remediation).

**Risks introduced:** search/ES degradation and Arabic relevance failure are registered as **`RISK-007`** (MEDIUM — spike, degradation contract, `J8`); capacity/latency pressure feeds `RISK-008`; operational surface feeds `RISK-005`.

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-18` custom build** | Elasticsearch is a search engine dependency — no commerce platform; search logic itself is purpose-built (`FR-009` custom ranking/merchandising) |
| **`C-19` PostgreSQL 16 only** | ES is *not* a relational database and holds no authoritative state — it is a derived index over `ADR-001` data |
| **`C-21` modular monolith** | Search is module `B04` inside the monolith; index writes flow through its own jobs/queues, not a separate service deployment |
| **`C-22` Docker Compose** | `elasticsearch:8` runs as a Compose service with healthcheck; no managed service |
| **`C-24` Arabic-first** | Arabic analyzer/stemming is the core reason for the choice; two-locale indexing with `ar` default |
| **`C-25` / `NFR-001`** | Facet/filters/aggregations offloaded from OLTP; p95 validated in k6 search scenarios |
| **`NFR-007` degradation** | ES down → category browse works; readiness unaffected for core routes; index rebuildable |
