# ADR-005: Redis 7 + BullMQ as the only queue/cache substrate

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Technical lead, DevOps lead, Engineering team, Security officer (rate-limit counters) |
| **Informed** | QA team, Product owner |

## Context

yumn needs four kinds of non-relational state: (1) **read cache** for catalog/discovery (≥ 80% hit ratio, `NFR-004`); (2) **durable background jobs** — notification fan-out, escrow maturity, payouts, TTL stock releases, search indexing, reconciliation `J1…J12` (`BR-PLT-01/02`, `../../16-data/core/data-quality.md`); (3) **short-lived coordination state** — OTP codes with 5-min TTL, rate-limit counters, session acceleration, distributed locks; (4) **eventual-consistency plumbing** such as outbox-to-queue bridging.

Forces:

- **Constraint `C-20`: BullMQ (Redis-backed) is the only job/queue system — no RabbitMQ, no Kafka.**
- `DEP-03` (Redis 7) is `Available`; `C-20` and `DEP-03` are the stated drivers in `technology-stack.md` §3.
- Business timers are pervasive: 15-minute reservations (`C-13`), 7-day escrow (`C-12`), 48-h KYC/return SLAs, OTP expiry — delayed jobs are the mechanism (`BR-PLT-01`).
- Reliability rules: retry 3× with exponential backoff, then dead-letter with depth alerting (`BR-PLT-02`); no silent data loss (`NFR-007`); observability via Prometheus/Grafana (`INT-REQ-007`).
- Anti-force: **Redis must never become a second system of record** — money, stock and orders live in PostgreSQL (`ADR-001`), and losing Redis must degrade, never corrupt (`P9`, `RISK-023`).

## Decision

**Redis 7 is the single cache/coordination substrate and BullMQ is the single job/queue system for every background workload.** All jobs use BullMQ with the naming scheme `{block}.{entity}.{action}` (`BR-PLT-01`), retries 3× with exponential backoff then DLQ with depth alerts (`BR-PLT-02`), and metrics exported to Prometheus/Grafana (`INT-REQ-007`). Redis also holds cache entries, TTL keys (OTP, reservations), rate-limit counters, and session acceleration — with **PostgreSQL remaining authoritative for sessions** so cache loss cannot strand revocations. No RabbitMQ, Kafka, SQS, sidekiq-style worker, cron-only scheduling, or in-process-only timers may be introduced. Jobs are idempotent and replayable so queue loss degrades throughput, not correctness.

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **RabbitMQ** | Mature broker; routing/exchange flexibility; strong delivery semantics | Second stateful infrastructure to operate (beyond `C-20` prohibition); two failure domains for ops; cache/counters still need Redis anyway — no consolidation benefit | **Excluded by `C-20`**; would add ops load against `RISK-005` while Redis remains required for cache |
| **Kafka / Redpanda** | Excellent throughput, replay, log retention, fan-out | Cluster operations (brokers, partitions, ISR) far beyond team capacity; overkill for a marketplace's job volume; still needs Redis for cache/counters | **Excluded by `C-20`**; complexity vs the single-host Compose posture (`ADR-004`) |
| **AWS SQS / cloud pub-sub** | Managed, no ops | Direct `NFR-016` lock-in violation; cloud account dependency in this market; hybrid state split | Rejected: portability requirement; cloud adoption would be its own future ADR |
| **PostgreSQL-only job queue (pg-boss style)** | One fewer dependency; transactional enqueue with business rows | Polling load on the money database; weak delayed-job ergonomics for the many timers; no built-in retry/backoff/DLQ maturity; still needs Redis for cache | Rejected: worsens `NFR-001` contention on `ADR-001`; `C-20` names BullMQ as the queue |
| **Cron / systemd timers + in-process schedulers** | Zero new components | No retries, no DLQ, no visibility, no per-tenant fan-out; multi-instance duplicate execution; violates `BR-PLT-02` | Rejected: cannot satisfy retry/DLQ/alerting requirements or the auditability expected of money-related jobs |
| **Memcached for cache (plus a queue)** | Simple cache | No structures/TTL semantics needed for counters/locks, no queues — would still require a second component | Rejected: `technology-stack.md` §3 — Redis alone covers cache, counters, TTL keys **and** queues |

## Consequences

**Positive**

- One dependency (`DEP-03`) covers cache, counters, TTL state, and durable jobs — smallest possible operational footprint for `C-25` read performance (`NFR-004`) and all background processing.
- BullMQ provides exactly the reliability primitives the rules require: retries/backoff (`BR-PLT-02`), delayed jobs for every business timer, DLQ with depth alerting, concurrency controls for workers.
- Queue naming `{block}.{entity}.{action}` aligns with `ADR-002` module ownership — each module produces/consumes its own queues; `J1…J12` reconciliation jobs fit the same scheme.
- Redis-shared counters make rate limits and OTP cooldowns correct across API replicas (`SEC-REQ-009`, `SEC-006`), enabling stateless horizontal scale (`NFR-018`).
- Clear metrics surface (queue depth, DLQ, cache hit ratio, outbox age) feeds `NFR-014` dashboards and `DQM-03`.

**Negative**

- Single Redis instance is a shared failure domain: cache stampede, memory exhaustion, or persistence misconfiguration can degrade multiple features at once (`RISK-023`).
- Queue data in Redis is only as durable as its persistence configuration (AOF) — job loss is possible on hard failure; design compensates with idempotent jobs + reconciliation (`J1…J6`) rather than assuming perfect durability.
- Two data technologies to tune (PostgreSQL + Redis) — acceptable because roles are disjoint and Redis is intentionally disposable.

**Neutral**

- BullMQ sits on the same Redis as cache; operational rule: **memory limits and eviction policy must protect queue keys** (documented in `14-devops-infrastructure/` at implementation).
- Version drift within Redis 7 / current BullMQ needs no ADR; a major-line change or queue-product change does (stack register §8).

**Risks introduced:** Redis/queue state loss is registered as `RISK-023` (MEDIUM — AOF, idempotent replay, Postgres-authoritative sessions, `J7/J11` drift detection); queue outages must degrade gracefully per `NFR-007` (browse and existing balances keep working).

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-18` custom build** | Redis/BullMQ are libraries/infrastructure — no commerce platform adopted (holds for all ten ADRs) |
| **`C-20` BullMQ only, no RabbitMQ/Kafka** | The decision *is* `C-20`; verification = dependency audit (`project-constraints.md`) |
| **`C-19` PostgreSQL 16 only** | Redis holds no authoritative business state; queues never replace the system of record |
| **`C-21` modular monolith** | BullMQ workers run from the same codebase/image; queues are module-owned (`BR-PLT-01`) |
| **`C-22` Docker Compose** | `redis:7` is a Compose service with healthcheck `redis-cli ping` and AOF volume (`deployment-view.md` §2/§4) |
| **`C-13` / `C-12` timers** | Delayed jobs implement 15-min reservation TTL and 7-day escrow maturity reliably with retries |
| **`C-25` / `C-26`** | Cache absorbs read load; durable async keeps request paths fast; DLQ alerts protect against silent backlog |
