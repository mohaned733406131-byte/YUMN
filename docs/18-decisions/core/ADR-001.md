# ADR-001: PostgreSQL 16 as the sole relational database

| Field | Value |
|---|---|
| **Status** | ACCEPTED |
| **Date** | 2026-09-26 |
| **Deciders** | project sponsor + architecture (analysis phase) |
| **Consulted** | Technical lead, Finance (Admin) — money integrity, Security officer — data protection, DevOps lead — backup/RPO |
| **Informed** | Engineering team, QA team, STK-07 (finance), STK-11 (security/compliance) |

## Context

yumn is a greenfield multi-vendor marketplace whose trust model rests on money correctness: a double-entry ledger with a zero-imbalance invariant (`NFR-008`, `AC-S-14`), 17-order-state transactions (`C-09`), 15-minute stock reservations (`C-13`), escrow holds (`C-12`), and 5-year financial retention (`NFR-019`). The system must also meet `C-25` (10,000 concurrent users) with `NFR-001` latency, `NFR-017` capacity (10M products, 100M order-line records), `NFR-006` RTO ≤ 1 h / RPO ≤ 15 min, and `NFR-016` portability (any Docker host, no cloud lock-in).

Forces acting on this decision:

- **Constraint `C-19`: PostgreSQL 16 is the only relational database** — this is not a preference but a baseline: alternatives are excluded before the analysis begins.
- **Integrity**: `DATA-REQ-001` requires referential integrity enforced *in the database*, not just the app; `DATA-REQ-007` requires append-only ledger postings (UPDATE/DELETE withheld from the application role); `DATA-REQ-004` requires continuous WAL + daily snapshots.
- **Consistency boundary**: money, stock, and order state must be committable in one ACID transaction (`BR-PLT-04`); multi-schema ownership is planned as PostgreSQL schemas `b01…b13` (`../../08-database/core/database-overview.md`).
- **Dependencies**: `DEP-02` (PostgreSQL 16 server) is already `Available` — the critical path can start immediately.
- **Neighbouring decisions**: `ADR-002` (modular monolith) keeps the money path in-process, which only works if the store is one ACID engine; `ADR-001` is the substrate that makes `ADR-002`'s "no distributed transactions" stance safe; `ADR-005` (Redis) explicitly must *not* become a second source of truth; Prisma 5 is the chosen ORM (`technology-stack.md` §3) because it gives typed models and parameterized queries by default (`SEC-REQ-008`).
- **Operability**: the team is small (`RISK-005`); one database to back up, patch, and restore fits `C-22` simplicity and the DR drills required by `AC-S-17`.

## Decision

**yumn uses PostgreSQL 16 as its only relational database and its sole system of record for every domain — identity, catalog, orders, wallet/ledger, escrow, shipping, returns, content, analytics source data, and audit — accessed through Prisma 5 with migrations, schemas `b01…b13`, and database-enforced integrity.** No other relational database may appear in any environment (dev, staging, prod), and no subsystem may introduce a second store with its own transaction semantics: Elasticsearch (`ADR-006`) is a rebuildable derived index, MinIO (`ADR-007`) holds objects, and Redis (`ADR-005`) holds cache, counters, and queues — none of them stores authoritative business state.

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|---|---|---|---|
| **MySQL 8** | Familiar; wide hosting support; good performance on simple OLTP | Weaker JSON/index feature set for metadata-heavy rows; no schema-per-block story as mature; different replication/backup muscle memory | **Excluded by `C-19`** — the constraint names PostgreSQL explicitly; considering it further would contradict canon (constraint outranks preference, DOC-ARCH-010 §6) |
| **MongoDB (document store)** | Flexible schema; horizontal document scaling; fast early iteration | No relational integrity for the ledger: no real FK/check enforcement, no multi-document ACID that matches `DATA-REQ-001`/`BR-PLT-04` comfort level; append-only + invariant checking become application-only — unacceptable for `RISK-001` | Rejected: **no relational integrity for a double-entry ledger**; would push money correctness into code, exactly the failure mode `DQ-08` exists to prevent |
| **PostgreSQL + a second OLAP store (e.g. ClickHouse) for analytics** | Analytical queries isolated from OLTP; faster dashboards (`FR-018`) | Second operational datastore: another backup, another failure domain, more ops load (`RISK-005`); contradicts the one-system-of-record posture | Rejected for v1: `FR-018` reporting can ride read paths and indexes; revisit only via a future ADR if `NFR-001` is threatened by analytics load |
| **Distributed/NewSQL store (CockroachDB, Yugabyte)** | Multi-node resilience; stronger availability story for `C-26` | Operational complexity far beyond a small team; `C-22` single-host Compose posture; latency unpredictability for p95 targets | Rejected: complexity vs `C-22`/`RISK-005`; availability is addressed by backup/restore (`NFR-006`) and by the future multi-host ADR path, not by a distributed database |
| **Stay with `C-19` but delay schema design (code-first ad hoc)** | Faster first feature | Migrations churn, integrity gaps, and late discovery of capacity limits (`NFR-017`) | Rejected: `DATA-REQ-001`/`DATA-REQ-005` require designed constraints and expand-contract migrations from the start |

## Consequences

**Positive**

- One ACID consistency boundary for money, stock, and order state — the strongest available foundation for the zero-imbalance invariant (`RISK-001` mitigation) and for idempotent money operations (`BR-PAY-08`).
- Integrity moves into the database: FKs, CHECK/UNIQUE constraints, `NOT NULL` owner keys (`DATA-REQ-008`, `DQ-01…DQ-18`) reject bad data at write time regardless of application bugs.
- Append-only ledger enforcement is a **privilege decision** (REVOKE UPDATE/DELETE), which is simple, auditable, and testable.
- Mature backup story (continuous WAL + snapshots) directly satisfies `NFR-006`/`DATA-REQ-004` and the `AC-S-17` restore drill; partitioning supports `NFR-017`.
- JSONB columns give metadata flexibility without a second store; full-text and trigram options exist as a fallback if search degrades (`RISK-007`).
- Team knows one datastore; ops load stays small (`RISK-005`).

**Negative**

- Write throughput and storage on a single node eventually cap; mitigated by the documented scale-out path (`NFR-018` read replicas) rather than by sharding — a real ceiling beyond `C-25`.
- Analytics (`FR-018`) shares the OLTP cluster; heavy reporting queries must be constrained (indexes, read replica later) or they will contest `NFR-001`.
- Schema migrations on 100M-row tables need expand-contract discipline (`DATA-REQ-005`) or deploys will block.

**Neutral**

- Version drift within the PostgreSQL 16 major line needs no ADR (stack register §8); moving to 17+ later is a stack-register change with an ADR.
- Cloud-managed Postgres is not adopted in v1 (`NFR-016`), but nothing in the design prevents lifting the same images later.

**Risks introduced:** residual single-node capacity/availability exposure rolls up into `RISK-008` (performance vs `C-25`) and `RISK-019` (single-host vs `C-26`); backup/restore failure would undermine `RISK-001` contingency and is covered by `AC-S-17`.

## Compliance

| Constraint | How this ADR satisfies it |
|---|---|
| **`C-18` custom build** | PostgreSQL is a library/service dependency, not a commerce platform — satisfied by every ADR-001…ADR-010; no Shopify/Medusa/WooCommerce/Saleor anywhere |
| **`C-19` PostgreSQL 16 only** | The decision *is* `C-19`: 16 is the target version in every environment; deployment config review is the verification (`project-constraints.md`) |
| **`C-21` modular monolith** | Schemas `b01…b13` give per-module ownership inside one engine; no cross-schema joins in app code (`module-boundaries.md` F1) |
| **`C-22` Docker Compose** | Official `postgres:16` image runs as a Compose service with healthcheck `pg_isready` (`deployment-view.md` §2) |
| **`C-25` / `C-26` quality** | Connection pooling, indexing plan, WAL/backup and readiness gates support concurrency and recovery targets; ceilings documented (`NFR-018`) |
| **`C-23` greenfield** | No legacy coexistence or migration adapters — clean schema design (`P10`) |
