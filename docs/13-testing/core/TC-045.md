# TC-045 — Customer cancellation at PLACED inside the window → CANCELLED → REFUNDED with wallet credit

| Field | Value |
|---|---|
| Objective | Verify that a customer cancels a `PLACED` order inside the `BR-ORD-04` window with a reason, that the state moves `PLACED → CANCELLED → REFUNDED`, and that the full amount returns to the wallet exactly once with escrow unwound. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (refund job via test clock) |

## Preconditions
- Order `ORD-045` (single vendor, total 14,875 YER) is `PLACED`; buyer `771234567` balance 35,125 YER; escrow holds 14,875 YER.
- Customer owns the order (foreign orders return `404 NOT_FOUND`, `BR-ORD-09`).

## Test Data

| Field | Value |
|---|---|
| Order | `ORD-045` / `SUB-045A`, state `PLACED`, total `14875` YER |
| Reason | `"تغيرت خطتي — ألغاء الطلب"` |
| Keys | `ord-045-cancel-01` (idempotent cancel), `ord-045-cancel-02` (late attempt) |
| Balance | before refund `35125` → after `50000` YER |

## Steps
1. Buyer `POST /orders/{id}/cancel` **without** `reason` (key `ord-045-cancel-01`).
2. Buyer `POST /orders/{id}/cancel` with `{"reason":"تغيرت خطتي — ألغاء الطلب"}` and `Idempotency-Key: ord-045-cancel-01`.
3. Repeat step 2 byte-identically; then attempt `POST /orders/{id}/cancel` with a **different** key and reason.
4. `GET /orders/{id}`, `GET /orders/{id}/timeline`, `GET /orders/{id}/refund`.
5. Run the refund job; `GET /wallet`, `GET /wallet/transactions?type=REFUND`, `GET /wallet/escrow?orderId={orderId}`.
6. SQL: history rows, refund ledger pair, escrow row for `SUB-045A`.

## Expected Result
- Step 1 → `422 REASON_REQUIRED`; state remains `PLACED`, history unchanged.
- Step 2 → `200 {"id":"SUB-045A","state":"CANCELLED","version":n,"refund":{"status":"PENDING"}}` (`API-ORD-012`, `AC-FR012-03` window still open at `PLACED`).
- Step 3 → identical replay returns the same result with **no** second cancellation (`BR-PAY-08`); the different-key attempt returns `409 STATE_CONFLICT` (state already `CANCELLED`).
- Step 4 → refund receipt `PENDING → CREDITED` after the job; timeline shows `PLACED→CANCELLED` (actor `CUSTOMER`, with reason) then `CANCELLED→REFUNDED` (actor `SYSTEM`).
- Step 5 → balance `50000`, one `REFUND` credit of `14875` with `balanceAfter 50000` (`BR-PAY-07`); no active escrow hold remains for the order (escrow unwound); no release job is ever enqueued.
- Step 6 → exactly one refund credit pair, `SUM(ledger) = 0`, history append-only (`BR-ORD-03`, `AC-FR012-05`); master state `CANCELLED`.
