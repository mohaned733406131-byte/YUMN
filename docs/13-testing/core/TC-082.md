# TC-082 — Admin resolves a dispute for the buyer: escrow unfreezes into the audited refund flow

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that only an `ADMIN` can resolve a dispute, that a buyer-win resolution unfreezes escrow (`DISPUTED → REFUNDED`) with a required reason and an audit entry, that the refund then credits the wallet (item value + vendor-fault shipping) drawing escrow first, and that re-resolution or late evidence is refused. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `DISPUTE-5512` is `OPEN` on `ORD-7F3A21` / `SUB-9C1104` (`DISPUTED`), opened `2026-09-26T10:00:00+03:00`, `evidenceDueBy = 2026-09-28T10:00:00+03:00`; escrow `frozenBy: "DISPUTE"`, `amountHeld = 14875`; buyer wallet **35,125 YER**. |
| 2 | Ground of the dispute is `NOT_AS_DESCRIBED` (vendor-side fault ⇒ shipping refundable, `BR-RET-03`). |
| 3 | Tokens: buyer `771234567`, vendor `779876543`, `ADMIN`, `MODERATOR`. |

## Test Data

| Field | Value |
|---|---|
| evidence | buyer `{"note":"original packaging photos","imageFileIds":["f-201"]}`, vendor `{"note":"warehouse QC record","imageFileIds":["f-301"]}` |
| forbidden resolve | `{"outcome":"BUYER","reason":"…"}` as buyer / vendor / moderator → expect `403 ARBITRATION_FORBIDDEN` |
| admin resolve | `POST /disputes/DISPUTE-5512/resolve {"outcome":"BUYER","reason":"item materially not as described; code proof covers handover, not cosmetic condition"}` |
| refund expectation | `amount = 13000` (12,500 + 500 shipping), wallet → **48,125 YER**, escrow `held → 1875` |

## Steps
1. Buyer and vendor each `POST /disputes/DISPUTE-5512/evidence` with their bodies; `GET /disputes/DISPUTE-5512` (evidence list).
2. As buyer, then vendor, then `MODERATOR`, attempt `POST /disputes/DISPUTE-5512/resolve` with the admin body.
3. As `ADMIN`, `POST /disputes/DISPUTE-5512/resolve {}` (no reason), then with the full admin body.
4. `GET /disputes/DISPUTE-5512`; `GET /orders/ORD-7F3A21`; `GET /wallet/escrow?orderId=ORD-7F3A21`.
5. Run the refund credit job; buyer `GET /wallet` balance and `GET /orders/ORD-7F3A21/refund`.
6. As `ADMIN`, resolve again; as buyer, submit more evidence; `GET /admin/audit-log?targetId=DISPUTE-5512`; as vendor, `GET /store/finance/overview?from=2026-09-01&to=2026-09-30`.

## Expected Result
- Step 1 → two `201 { evidenceId, at }` entries ≤5 files each, malware-scanned (`API-RET-016`, `SEC-REQ-011`); detail `200` lists both parties' evidence and timeline.
- Step 2 → buyer, vendor and moderator each get `403 ARBITRATION_FORBIDDEN` — arbitration is admin-only (`API-RET-017`, `SEC-REQ-004`).
- Step 3 → first call `422 REASON_REQUIRED`; second call `200 { state: "REFUNDED", escrowFrozen: false, resolution, auditId, refund: { status: "PENDING" } }` — buyer win executes the refund flow (`API-RET-017`, `AC-FR020-03`).
- Step 4 → dispute `state: "RESOLVED_BUYER"` with `resolution`; sub-order `SUB-9C1104` is `REFUNDED` (17 states, `C-09`); escrow `frozenBy: "NONE"`, `releasedAt: null` (unfrozen but drawn down by the refund, `BR-ORD-05`).
- Step 5 → refund `status: "CREDITED"` with `amount: 13000`, `shippingRefunded: true` — vendor-side fault includes shipping (`BR-RET-03`), credit ≤3 business days (`BR-RET-04`); wallet **48,125 YER** (35,125 + 13,000); escrow `totals.held = 1875` (14,875 − 13,000) — refund draws escrow first (`BR-ESC-07`, `BR-RET-07`).
- Step 6 → re-resolve `409 STATE_CONFLICT`; evidence after resolution `409 STATE_CONFLICT` (`API-RET-015/016`); audit log contains `dispute.resolve` with `outcome: "BUYER"`, `actorRole: "ADMIN"`, the reason and a `correlationId` — append-only (`BR-RET-06`, `BR-PLT-06`, `SEC-REQ-010`, `AC-FR020-01`); vendor finance shows the 13,000 refund in `period.refundsYER` (`AC-FR018-02`).
