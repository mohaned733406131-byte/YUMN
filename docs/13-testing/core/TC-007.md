# TC-007 — Sixth device login succeeds by evicting the oldest of five sessions

| Field | Value |
|---|---|
| Objective | Verify that a user with 5 active device sessions can still log in on a 6th device, that the oldest session is evicted, and that the evicted device fails on its next request while the other four keep working. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest |

## Preconditions
- Account `771234567` is verified; exactly 5 sessions were created by 5 sequential logins (devices D1…D5, D1 oldest).
- Each device holds its own access + refresh token pair.
- Session registry is inspectable via `GET /auth/sessions`.

## Test Data

| Field | Value |
|---|---|
| Phone | `771234567` |
| Devices | `D1` (oldest) … `D5`, new device `D6` |
| Session cap | 5 (`BR-AUTH-06`) |
| Password | `Yumn#2026a` |

## Steps
1. `GET /auth/sessions` with the D1 access token and record the 5 entries with `createdAt` ordering.
2. `POST /auth/login` from device `D6` with the correct password.
3. `GET /auth/sessions` again and count the entries.
4. `POST /auth/refresh` using D1's refresh token (the evicted session).
5. `GET /orders` using D5's access token and D6's access token.
6. `DELETE /auth/sessions/{sess_D1}` from D6's token (idempotency check on an already-revoked session).

## Expected Result
- Step 1 returns `total: 5`, ordered oldest-first; `D1` is the oldest entry.
- Step 2 returns `200` with a new token pair and `sessionId` for D6 — login is never refused solely because of the cap (`SESSION_LIMIT_REACHED` is not returned).
- Step 3 returns `total: 5`: D6 was added, D1 was removed (eviction of the oldest).
- Step 4 returns `401 SESSION_NOT_FOUND` — the evicted device can no longer refresh.
- Step 5: D5 returns `200`, D6 returns `200` — the four surviving sessions are untouched.
- Step 6 returns `204` even though D1 was already revoked (idempotent delete).
- An eviction event is written to the security log with actor and timestamp.
