# TC-071 — Third wrong code locks confirmation for 24 hours and auto-creates a support ticket

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that the 3rd wrong code returns `422 CODE_ATTEMPTS_EXCEEDED`, locks code confirmation for exactly 24 hours (correct code rejected with `403 CODE_LOCKED` during the lock), and auto-creates an `source: "AUTO"` support ticket carrying the full delivery timeline to the order owner and the admin queue. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `DLV-4471` is `OUT_FOR_DELIVERY` with `code.attemptsUsed = 2` (two prior wrong entries per `TC-070`), `lockedUntil` absent; sub-order `SUB-9C1104` is not `DELIVERED`. |
| 2 | Courier `790000011` (assignee), buyer/order owner `771234567`, and an `ADMIN` token are seeded; test clock is controllable (time service stub). |
| 3 | `GET /admin/tickets` is empty for `category` delivery before the run; support store is clean so the new ticket is uniquely identifiable. |

## Test Data

| Field | Value |
|---|---|
| delivery / order | `DLV-4471` / `ORD-7F3A21` / `SUB-9C1104` |
| 3rd wrong guess | `999999` |
| correct code | `482913` |
| lock window | `lockUntil = failedAt + 24h` (`retryAfterSeconds ≈ 86400`) |

## Steps
1. As courier `790000011`, `POST /deliveries/DLV-4471/code {"code":"999999"}` → capture the error envelope.
2. Immediately `POST /deliveries/DLV-4471/code {"code":"482913"}` (correct code during the lock).
3. `GET /deliveries/DLV-4471` → inspect `code.attemptsUsed`, `code.lockedUntil`, `state`.
4. As `ADMIN`, `GET /admin/tickets?source=AUTO` → find the auto-created ticket; then `GET /support/tickets/{id}` for its detail.
5. As buyer `771234567`, `GET /support/tickets` (own feed); as unrelated customer `771234568`, `GET /support/tickets/{id}` of that ticket.
6. Advance the test clock by 24 hours past `lockUntil`, then courier `POST /deliveries/DLV-4471/code {"code":"482913"}`.

## Expected Result
- Step 1 → `422 CODE_ATTEMPTS_EXCEEDED`, `retryable: false`, `retryAfterSeconds ≈ 86400`, `details.lockedUntil = failedAt + 24h` (`BR-SHP-03`, `C-16`); sub-order not `DELIVERED`.
- Step 2 → `403 CODE_LOCKED`, `retryable: true`; the correct code does **not** deliver during the lock and does not consume a further attempt.
- Step 3 → `code.attemptsUsed = 3`, `code.lockedUntil` set, `state ≠ "DELIVERED"` (`BR-ORD-08`) — lock duration exactly 24h from the 3rd failure (`BR-SHP-03`).
- Step 4 → `200` list item `{ source: "AUTO", status: "OPEN", userId: "771234567", orderId: "ORD-7F3A21" }` in the admin queue (`API-ADM-039`); detail `200` with `linked: { orderId, deliveryId }` and the full delivery timeline attached (`BR-SHP-03`, `UC-014` A1).
- Step 5 → the ticket appears in the order owner's own feed (`API-ADM-036`); the unrelated customer gets `404 NOT_FOUND` on the detail — a ticket is visible only to its opener and staff (`DATA-REQ-008`).
- Step 6 → after the lock expires, confirmation is allowed again and the correct code returns `200 { state: "DELIVERED", version, deliveredAt, proof: {…} }` with the escrow hold starting (`workflow-005` step 10, `BR-ESC-01`) — no delivery ever completed without a verified code (`BR-ORD-08`).
