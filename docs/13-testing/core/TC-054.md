# TC-054 — Saga failure after wallet capture: compensating release, idempotent retry, single net charge

| Field | Value |
|---|---|
| Objective | Verify that if order creation fails after the wallet capture leg, the saga's compensating action restores the balance with zero net effect (no double charge, no orphan order/escrow), and that retrying with the same `Idempotency-Key` produces exactly one order and one debit. |
| Level | integration |
| Priority | P0 |
| Automation | Yes — Jest + Supertest (fault injection on the order-insert leg) |

## Preconditions
- Buyer `771234567` wallet funded with 50,000 YER; valid checkout session `cs-054` (total 14,875 YER, reservation active).
- Fault-injection harness can fail the order-row insert **after** `API-WAL-007` capture executes.

## Test Data

| Field | Value |
|---|---|
| Keys | `ord-054-01` (fail + retry), `ord-054-02` (conflict probe) |
| Totals | `12500` + VAT `1875` + shipping `500` = `14875` YER |
| Balances | start `50000` → after failed attempt `50000` → after successful retry `35125` |
| Conflict body | same key `ord-054-01` with `{"checkoutSessionId":"cs-054","confirmTotals":false}` |

## Steps
1. `POST /orders` with `Idempotency-Key: ord-054-01` and the standard body while the order-insert fault is armed.
2. Inspect: response status/body, `GET /wallet`, `GET /wallet/transactions?type=ORDER_PAYMENT`, escrow rows, `orders` rows, payment status.
3. Disable the fault; `POST /orders` **identically** with the same key `ord-054-01`.
4. Repeat step 3 a third time with the same key.
5. `POST /orders` with key `ord-054-01` and the conflicting body above.
6. Run the reconciliation assertion (`SUM(ledger)`) and count orders/holds for this buyer.

## Expected Result
- Step 1 → `500 INTERNAL_ERROR` with `retryable:true`, a `correlationId` and a generic localized message — no stack trace or SQL text (`SEC-REQ-008`).
- Step 2 → balance restored to `50000`; the capture is undone by a compensating release (`API-WAL-008`), so **net debit = 0**; **0** order rows, **0** escrow rows, no stock deduction; the ledger contains the original pair **plus** its balancing pair with `SUM = 0` (`BR-PLT-04`).
- Step 3 → `201` with exactly one order in `PLACED`, balance `35125`, escrow funded once — one net debit of `14875` (`BR-PAY-08`, `AC-FR011-02`).
- Step 4 → the original order and original status code returned; **no** second order, **no** second debit.
- Step 5 → `409 IDEMPOTENCY_CONFLICT` — same key, different request fingerprint; state unchanged.
- Step 6 → exactly 1 order, 1 active escrow hold, 1 net capture; `SUM(ledger) = 0`; no orphan payment/hold rows (`AC-NFR-008-02`, `AC-S-15`).
