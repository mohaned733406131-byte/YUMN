# TC-100 — Server-side coupon validation computes discounts and rejects every invalid issue

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that `POST /coupons/validate` is the only judge of coupons: valid codes return a server-computed `discountAmount` with half-up rounding, a second coupon is refused with `COUPON_STACKING_NOT_ALLOWED`, and each documented invalid issue (unknown, expired, exhausted, already-used, min-not-met, wrong store) returns `COUPON_INVALID` with the correct `details[].issue`, with no order row ever created by validation. | integration | P1 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `CUSTOMER` token `771234567` with two carts on `tech-store`: cart `C-100` (items subtotal **12,500 YER**) and cart `C-100M` (subtotal **3,000 YER**). |
| 2 | Coupons seeded: `RAMADAN25` (25 %, `PLATFORM`, window open, `minOrderAmount: 5000`, per-user limit 1, remaining usage), `EXPIRED20` (`endsAt` past), `USEDUP10` (`usageLimit: 5`, `usageCount: 5`), `AGAIN15` (buyer already redeemed once, `perUserLimit: 1`), `BIGMIN50` (`minOrderAmount: 50000`), `OTHERSTORE5` (scope `STORE`, store B), `EXTRA5` (5 % active). |
| 3 | A checkout session already carries `STACKED5` (`POST /checkout/session` with `couponCode: "STACKED5"`), and `POST /coupons/validate` never creates orders (`BR-PRM-06`, `AC-FR019-03`); order count recorded before the test. |

## Test Data

| Field | Value |
|---|---|
| valid | `{"code":"RAMADAN25","cartSnapshot":"C-100"}` |
| probes | `GHOST99`, `EXPIRED20`, `USEDUP10`, `AGAIN15`, `BIGMIN50` (cart `C-100`), `OTHERSTORE5` |
| min-not-met | `{"code":"RAMADAN25","cartSnapshot":"C-100M"}` (3,000 < 5,000) |
| stacking | `{"code":"EXTRA5","cartSnapshot":"C-100"}` while `STACKED5` is active on the session |

## Steps
1. `GET /orders` count (probe baseline).
2. Post the valid body; inspect `valid`, `code`, `discountAmount`.
3. Post each probe code (GHOST99, EXPIRED20, USEDUP10, AGAIN15, BIGMIN50, OTHERSTORE5) against cart `C-100`; capture `error.code` and `details[].issue` for each.
4. Post `RAMADAN25` against cart `C-100M`; then post `EXTRA5` while `STACKED5` is active on the checkout session.
5. Re-count orders and re-check the cart/wallet.

## Expected Result
- Step 1 → baseline order count recorded.
- Step 2 → `200 { valid: true, code: "RAMADAN25", discountAmount: 3125 }` — `25 % × 12,500 = 3,125` whole YER, computed server-side with half-up rounding (`API-CNT-004`, `BR-FIN-01/05`); the client displays only this server figure (`content.md` §2).
- Step 3 → every probe → `422 COUPON_INVALID` with `details[].issue`: `GHOST99` → `NOT_FOUND`, `EXPIRED20` → `EXPIRED`, `USEDUP10` → `USAGE_LIMIT_REACHED`, `AGAIN15` → `ALREADY_USED_BY_USER`, `BIGMIN50` → `MIN_NOT_MET`, `OTHERSTORE5` → `NOT_APPLICABLE` (wrong store scope, `BR-PRM-01/04`); error-message fields carry `reasonKey` for localization (`error-model.md` envelope, `C-24`).
- Step 4 → cart `C-100M` → `422 COUPON_INVALID`, `details[].issue = "MIN_NOT_MET"` — `minOrderAmount` is re-checked against the cart (`BR-PRM-04`); `EXTRA5` → `422 COUPON_STACKING_NOT_ALLOWED` — a second coupon can never join an order that already has one (`BR-PRM-02`, `AC-FR019-02`).
- Step 5 → order count unchanged, cart and wallet untouched — validation is a pure read (`BR-PRM-06`, `AC-FR019-03`); customer role required: the same call as guest → `403 FORBIDDEN` (`API-CNT-004`).
