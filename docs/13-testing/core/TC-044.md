# TC-044 — Vendor cancellation at CONFIRMED moves the sub-order to CANCELLED and starts the refund path

| Field | Value |
|---|---|
| Objective | Verify that a vendor cancelling a `CONFIRMED` sub-order with a mandatory reason receives `CANCELLED` plus a `PENDING` refund, that the `SYSTEM` refund leg credits the customer wallet exactly once, and that the cancelled sub-order can never advance again. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (refund job driven by the BullMQ test clock) |

## Preconditions
- Order `ORD-044` (single vendor `tech-store`, total 14,875 YER) is at `CONFIRMED`; buyer balance 35,125 YER after payment; escrow holds 14,875 YER.
- Vendor `779876543` owns the sub-order; refund job queue drains on demand.

## Test Data

| Field | Value |
|---|---|
| Order | `ORD-044` / `SUB-044A`, state `CONFIRMED`, total `14875` YER |
| Reason | `"نفدت الكمية — نعتذر"` (missing-reason variant omits it) |
| Balance | before refund `35125` → after `50000` YER |

## Steps
1. Vendor `POST /store/orders/{id}/cancel` **without** `reason`.
2. Vendor `POST /store/orders/{id}/cancel` with `{"reason":"نفدت الكمية — نعتذر"}`.
3. `GET /orders/{id}`, `GET /orders/{id}/timeline`, `GET /orders/{id}/refund`.
4. Run the refund job; re-read `GET /orders/{id}/refund`, `GET /wallet`, `GET /wallet/escrow?orderId={orderId}`.
5. Attempt `POST /store/orders/{id}/processing` and a second `/cancel` on the same sub-order.
6. SQL: read the history rows and the refund ledger pair.

## Expected Result
- Step 1 → `422 REASON_REQUIRED`; state stays `CONFIRMED`, history unchanged.
- Step 2 → `200 {"id":"SUB-044A","state":"CANCELLED","version":n,"refund":{"status":"PENDING"}}` (`API-ORD-011`).
- Step 3 → timeline gains exactly two rows: `CONFIRMED→CANCELLED` with `actorRole VENDOR` + reason, and no other change; refund receipt shows `PENDING` with `amount 14875`.
- Step 4 → `SYSTEM` executes `CANCELLED → REFUNDED`; refund status `CREDITED` with `walletCredit.reference` and `creditedAt`; balance `50000`; the escrow hold for `SUB-044A` is unwound (no active held position remains).
- Step 5 → both attempts return `409 STATE_CONFLICT` — `CANCELLED` accepts no vendor fulfillment moves (`BR-ORD-01`, `C-09`); no second refund is created (`BR-PAY-08`).
- Step 6 → history rows immutable and append-only; exactly one refund credit pair; `SUM(ledger) = 0` (`BR-PAY-06`, `AC-FR012-05`).
