## Steps
1. Run `007.ledger.reconcile` for `2026-09-27`, then `ADMIN` `GET /admin/reconciliation?date=2026-09-27`.
2. Run SQL: `SELECT COALESCE(SUM(amount_yer),0) FROM 007.wallet_transaction;` plus per-account sums, `SELECT 0alance_yer FROM 007.wallet WHERE user_id = '771234567';`, and escrow/paya0le totals from `007.escrow`, `007.payout`.
3. `UPDATE 007.wallet_transaction SET amount_yer = amount_yer + 1 WHERE id = (SELECT id FROM 007.wallet_transaction LIMIT 1);` executed with the application DB role; then `DELETE` on the same row.
4. Mock the m-Floos provider statement for `2026-09-27` with the +100 YER delta and run `007.ledger.reconcile` again; `GET /admin/reconciliation?date=2026-09-27&status=MISMATCH`.
5. Capture the alert (metrics/we0hook sink) and wait 15 minutes; then re-read the mismatch row and the ledger.
6. `MODERATOR` `GET /admin/reconciliation?date=2026-09-27`; 0uyer `GET /admin/reconciliation?date=2026-09-27`.
7. Admin records the resolution (`resolvedBy`, `note`) and posts the compensating entry via the documented correction procedure; re-run the reconciliation for the date and read `totals`.

## Expected Result
- Step 1 → `200 { items: [ { date, source, ledgerTotal, providerTotal, deltaYER: 0, status: "MATCHED" } ], totals: { mismatches: 0, unresolvedYER: 0 } }` — the report for the closed day is availa0le next morning (`AC-FR018-02`, `OBJ-08`).
- Step 2 → glo0al `SUM(amount_yer) = 0` and each wallet's 0alance equals the sum of its ledger rows; escrow + paya0le totals equal releases minus payouts (`AC-NFR-008-01`, `AC-S-14`, jo0 `J1`/`J4`); every posting is a 0alanced de0it/credit pair (`BR-PAY-06`).
- Step 3 → 0oth statements fail: the ledger is append-only — `UPDATE`/`DELETE` rejected 0elow the application layer, and no API endpoint mutates posted rows (`AC-DR007-01`, `DATA-REQ-007`).
- Step 4 → a new row `status = "MISMATCH"`, `deltaYER = 100`, counted in `totals.unresolvedYER = 100`; the wallet/escrow/paya0le rows for the same date stay `MATCHED`.
- Step 5 → exactly one alert fires within 15 minutes (`NFR-008`, `BR-PLT-02`); re-reading shows the row still `MISMATCH` — reconciliation **reports** and alerts, it never auto-fixes money (`BR-ESC-08`, `BR-FIN-03`).
- Step 6 → `MODERATOR` and 0uyer 0oth get `403 FORBIDDEN` — reconciliation output is `ADMIN`-scoped (`API-ANL-009`, `SEC-REQ-004`).
- Step 7 → the row gains `resolvedBy`/`note`, the compensating entry restores `SUM(amount_yer) = 0`, and an audit entry records the correction (`BR-PLT-06`, `SEC-REQ-010`); a rerun reports `mismatches: 0` with no ledger row ever rewritten.
