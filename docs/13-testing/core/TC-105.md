# TC-105 — Audit rows are append-only: application role cannot UPDATE/DELETE and the API refuses every write

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that direct `UPDATE`/`DELETE`/`TRUNCATE` against `b13.audit_log` as the application database role fails with a privilege error, and that any API-level write or delete against the audit log is rejected with `405 AUDIT_LOG_IMMUTABLE` — with no row changed and nothing persisted. | security | P0 | Yes — Jest + superuser SQL harness |

## Preconditions

| # | Precondition |
|---|---|
| 1 | The seeded environment exposes both credentials: the application's database role (the role the API/worker connects with — holds `SELECT`, `INSERT` only on audit tables) and a superuser harness connection for assertions. |
| 2 | At least one audit row exists from a privileged action (fixture or created in-test); its `seq`, `before` and `after` values are recorded as the baseline. |
| 3 | `ADMIN` token available; `GET /readyz` → `200`. |

## Test Data

| Field | Value |
|---|---|
| target row | one seeded `b13.audit_log` row — record `seq`, `before`, `after`, `entry_hash` |
| SQL probes | `UPDATE b13.audit_log SET after = '{}';` · `DELETE FROM b13.audit_log WHERE seq = <seq>;` · `TRUNCATE b13.audit_log;` — all executed as the application role |
| API probes | `POST /admin/audit-log {"action":"test"}` · `PUT /admin/audit-log/{id} {"action":"test"}` · `DELETE /admin/audit-log/{id}` as `ADMIN` |

## Steps
1. Connect as the application database role; run the `UPDATE`, `DELETE` and `TRUNCATE` statements against `b13.audit_log`; capture the error for each.
2. Re-read the target row as the same role (`SELECT` must still work) and compare `before`, `after`, `entry_hash` with the baseline; re-count rows.
3. As `ADMIN`, issue `POST /admin/audit-log`, `PUT /admin/audit-log/{id}` and `DELETE /admin/audit-log/{id}`; capture status and `error.code` for each.
4. Re-read the target row and the row count; attempt the same three API probes without a token.

## Expected Result
- Step 1 → all three statements fail with a PostgreSQL insufficient-privilege error (SQLSTATE `42501`, "permission denied") — application roles hold `SELECT, INSERT` only; `UPDATE`, `DELETE`, `TRUNCATE` are revoked (`audit_log.md` §Invariants DB-enforced 1, `DATA-REQ-007`, `SEC-REQ-010` R1, `AC-SR010-01`).
- Step 2 → `SELECT` succeeds; the target row is byte-identical to the baseline (`before`, `after`, `entry_hash` unchanged) and the row count is unchanged — a failed write persists nothing.
- Step 3 → each probe returns `405 AUDIT_LOG_IMMUTABLE` (`error-model.md` 405; `admin.md` §1 — the log can never be written or deleted through the API, `SEC-REQ-010`, `DATA-REQ-007`); even Super Admin has no API path to edit the trail (`audit_log.md` §Invariants DB-enforced 1).
- Step 4 → unauthenticated probes return `401 AUTH_INVALID` before authorization is evaluated; the row and count remain unchanged — zero rows modified across all six negative steps.
