# TC-036 — Bank-transfer top-up stays PENDING until admin verification, then credits once; rejection posts nothing

| Field | Value |
|---|---|
| Objective | Verify `BR-PAY-04`: a BANK_TRANSFER top-up is credited only after an admin verifies the reference (with proof attached), stays uncredited while pending, credits idempotently once, and an admin rejection leaves the balance untouched. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (admin console actions via API) |

## Preconditions
- Customer `771234567` wallet `ACTIVE` with 5,000 YER; admin `775550010` holds role `ADMIN`.
- Bank beneficiary details fixture and a scanned slip `bank-slip-01.jpg` (≤5 MB, EXIF stripped) are available; audit log readable via `GET /admin/audit-log`.

## Test Data

| Field | Value |
|---|---|
| Top-up A | `{"amount":100000,"method":"BANK_TRANSFER","reference":"TRF-88214"}`, key `top-036-01` |
| Top-up B | `{"amount":15000,"method":"BANK_TRANSFER","reference":"TRF-99001"}`, key `top-036-02` |
| Balance | before `5000` → after verify A `105000` YER |
| Reject reason | `"المرجع غير موجود في كشف الحساب"` |

## Steps
1. `POST /wallet/topups` with `Idempotency-Key: top-036-01` → record `topupIdA`.
2. `POST /wallet/topups/{topupIdA}/proof` multipart `{"file": bank-slip-01.jpg}`.
3. `GET /wallet` and `GET /wallet/topups/{topupIdA}` before any admin decision; `GET /admin/topups?status=PENDING_VERIFICATION&method=BANK_TRANSFER` as admin.
4. `POST /admin/topups/{topupIdA}/verify` as `ADMIN`, body `{"note":"bank statement matched"}` → repeat the identical call once.
5. `POST /admin/topups/{topupIdA}/reject` after verification with a reason.
6. Create top-up B (`top-036-02`), then `POST /admin/topups/{topupIdB}/reject` with the reason above **without** verifying.
7. `GET /wallet`, `GET /wallet/topups/{topupIdB}`, `GET /wallet/transactions?type=TOPUP`, `GET /admin/audit-log?targetId={topupIdA}`.

## Expected Result
- Step 1 → `201 {status:"PENDING_VERIFICATION", paymentInstruction:{…bank beneficiary…}}`.
- Step 2 → `201 {proofFileId, status:"PENDING_VERIFICATION"}`; oversized/malformed files → `413 PAYLOAD_TOO_LARGE` / `415 UNSUPPORTED_MEDIA_TYPE`.
- Step 3 → balance still `5000`, **0** `TOPUP` ledger rows — credit before verification is impossible (`BR-PAY-04`); the pending item appears in the admin queue (`API-ADM-030`).
- Step 4 → first call `200 {topupId, status:"CREDITED", creditedAt, ledgerReference, auditId}`; replayed call returns the **same** result without a second posting (`BR-PAY-08`).
- Step 5 → `409 STATE_CONFLICT` (already decided) and the balance stays `105000`.
- Step 6 → `200 {status:"REJECTED", auditId}`; balance unchanged, **0** ledger rows for top-up B, `GET /wallet/topups/{topupIdB}` → `REJECTED` with `rejectionReason`.
- Step 7 → one balanced `TOPUP` pair only (Σ = 0, `AC-FR013-05`); audit entries exist for both decisions (actor, action, reason, `ipHash`, `correlationId`, `SEC-REQ-010`).
