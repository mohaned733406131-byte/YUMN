# TC-062 — An in-window return suppresses escrow release until it settles

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a return in any `RETURN_*` state suppresses the 7-day escrow release, that a rejection without a reason is refused, and that release resumes only after the return settles — while an approved return pays the refund from escrow instead of releasing it. | integration | P1 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Sub-order `SUB-9C1104` (`ORD-7F3A21`, 14,875 YER) is `DELIVERED` at `2026-09-19T10:00:00Z`, escrow `HELD`, product `هاتف سامسونج` with `isReturnable = true` and `returnPeriodDays = 7`. |
| 2 | Second fixture `SUB-44B207` (`ORD-2B8C55`, same totals) is `DELIVERED` the same day for the approved/refund branch. |
| 3 | Vendor `779876543` (Owner) and buyer `771234567` tokens exist; test clock is controllable; return pickup reuses the courier offer flow (`BR-SHP-04`). |

## Test Data

| Field | Value |
|---|---|
| return window | `deliveryConfirmedAt + 7 days` → deadline `2026-09-26T10:00:00Z` (`C-11`) |
| reason code | `DEFECTIVE` |
| refund estimate | item value 12,500 YER + shipping refundable only on platform/vendor fault (`BR-RET-03`) |
| escrow held | 14,875 YER per sub-order |
| commission at release | 1,250 YER (10% of 12,500) |

## Steps
1. Day 1 after delivery, buyer `POST /orders/ORD-7F3A21/returns` with `Idempotency-Key: ret-01`, body `{"items":[{"orderItemId":"oi-1","quantity":1,"reasonCode":"DEFECTIVE","note":"Deep scratch"}],"reasonCode":"DEFECTIVE"}`.
2. `GET /wallet/escrow?orderId=ORD-7F3A21` and `GET /returns/{id}`.
3. Advance the clock past `2026-09-26T10:00:00Z`, run `b07.escrow.release`, and attempt the internal release for `SUB-9C1104`.
4. Vendor `POST /store/returns/{id}/reject` with body `{"note":"no defect visible"}` (no `reason`).
5. Vendor `POST /store/returns/{id}/reject` with body `{"reason":"Item matches the listing photos"}`; then read `GET /returns/{id}` and run `b07.escrow.release` while the state is still `RETURN_REJECTED`.
6. Wait for the return to settle to `COMPLETED`, run `b07.escrow.release`, then `GET /wallet/escrow` and `GET /store/finance/overview`.
7. On `ORD-2B8C55`: open the same return, vendor `POST /store/returns/{id}/approve`, courier picks up (`RETURN_RECEIVED`), vendor `POST /store/returns/{id}/inspection` body `{"outcome":"PASS","notes":"Fault confirmed"}`, then run `b07.escrow.release` and `GET /orders/ORD-2B8C55/refund`.

## Expected Result
- Step 1 → `201 { returnId, state: "RETURN_REQUESTED", window: { deliveryAt, deadline: "2026-09-26T10:00:00Z", daysRemaining }, refundEstimate }`; a duplicate request inside the window is idempotent (`BR-PAY-08`).
- Step 2 → escrow `state = HELD`, `frozenBy = "RETURN"`; timeline gains `DELIVERED → RETURN_REQUESTED`.
- Step 3 → no release: `released_at IS NULL`, `availablePayable = 0`; direct attempt → `409 ESCROW_FROZEN` (`BR-ESC-02` — `RETURN_*` is in the exclusion set).
- Step 4 → `422 REASON_REQUIRED`; state stays `RETURN_REQUESTED`, history unchanged.
- Step 5 → `200 { state: "RETURN_REJECTED", version, historyEntry }`; the release run while the state is `RETURN_REJECTED` still performs no release — every `RETURN_*` state blocks (`BR-ESC-02`).
- Step 6 → once the return settles to `COMPLETED`, release succeeds exactly once: `commission_amount_yer = 1250`, payable 13,625 YER, one audit row `escrow.release` (`SEC-REQ-010`).
- Step 7 approved branch → `RETURN_APPROVED` schedules a pickup offer (`OFFERED`), inspection `PASS` moves the sub-order to `REFUNDED` with `refund.status = "PENDING"` and `expectedCreditBy` ≤ 3 business days (`BR-RET-04`); the release job then performs no release, the refund draws escrow-held funds first (14,875 YER, `BR-ESC-07`), commission was never booked for that sub-order, and `SUM(amount_yer) = 0`.
- Return decision landed within the 48 h SLA — `GET /store/returns` shows `overdue = false` (`BR-RET-05`).
