# TC-048 — 24-hour vendor SLA breach raises an escalation alert and queue flag but never auto-cancels

| Field | Value |
|---|---|
| Objective | Verify `BR-ORD-10`: a sub-order the vendor has not advanced within the 24-hour SLA (unconfirmed past `confirmDueAt`, or still `CONFIRMED` 24 h after confirmation) is escalated to admin review with a notification and the `SLA_24H` queue flag — and is never silently auto-cancelled. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (BullMQ test clock; notification sink asserted via `GET /notifications`) |

## Preconditions
- Order `ORD-048` is `PLACED` since `T0`; `GET /store/orders` exposes `confirmDueAt = T0 + 24 h`.
- Admin `775550010` has in-app + SMS notification channels enabled (`BR-NTF-03`); SLA job queue drains on demand.
- Second fixture `ORD-048B` confirmed at `T1` and left at `CONFIRMED`.

## Test Data

| Field | Value |
|---|---|
| Orders | `ORD-048` (`PLACED` at `T0`), `ORD-048B` (`CONFIRMED` at `T1`) |
| Clock points | `T0 + 23 h`, `T0 + 24 h 01 m`, `T1 + 24 h` |
| Flag / channel | `flags:["SLA_24H"]`; admin notification via `IN_APP` + `SMS`, locale `ar` |

## Steps
1. At `T0 + 23 h`: `GET /store/orders` and `GET /admin/orders?escalated=true`; run the SLA job once.
2. Advance the clock to `T0 + 24 h 01 m` and run the SLA job again.
3. `GET /admin/orders?escalated=true` and `GET /notifications` for the admin; read the sub-order state and history.
4. Re-run the SLA job twice more (idempotence probe).
5. Repeat steps 1–2 against `ORD-048B` with the clock at `T1 + 24 h`.
6. Vendor finally acts: `POST /store/orders/{id}/confirm` on `ORD-048`; re-run the SLA job.

## Expected Result
- Step 1 → no `SLA_24H` flag, no escalation notification, order still `PLACED` — escalation happens strictly after the 24-hour mark.
- Step 2 → the SLA job records one escalation for `ORD-048`.
- Step 3 → `GET /admin/orders` returns the order with `flags` containing `SLA_24H`; exactly one admin notification exists (order id, store name, SLA age); sub-order state is **still `PLACED`/`CONFIRMED`** with **no** `→ CANCELLED` history row, no refund, wallet and escrow untouched — never silently auto-cancelled without notification (`BR-ORD-10`).
- Step 4 → repeated job runs add **0** duplicate escalations or notifications (idempotent job, `BR-PLT-01/02`).
- Step 5 → `ORD-048B` escalates identically at `T1 + 24 h` while it remains `CONFIRMED` (the literal `BR-ORD-10` wording).
- Step 6 → `200 CONFIRMED` for `ORD-048`; a further job run creates no new escalation for it (the order has left the breach window).
- Notification text is localized (`ar` default) and carries no PII beyond order/store identifiers (`SEC-REQ-008`).
