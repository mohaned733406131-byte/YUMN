# TC-112 — An open dispute freezes escrow release for the affected sub-order and the admin resolution is written exactly once to the audit log

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that while a customer-raised dispute is open the 7-day escrow release is frozen for the affected sub-order (job no-op, direct release refused), that only an Admin may resolve, and that the resolution lands as exactly one complete, admin-readable audit entry — re-resolution refused without a second row. | integration | P1 | Yes — Jest + Supertest + BullMQ test clock |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Order `ORD-2B8C55` / sub-order `SUB-44B207` (14,875 YER) is `DELIVERED` at `2026-09-19T10:00:00Z` with escrow `HELD` (TC-061/TC-062 fixtures); release-eligible at `2026-09-26T10:00:00Z` (`C-12`). |
| 2 | Tokens: `ADMIN`, `MODERATOR`, buyer `771234567`; test clock controllable; queue `b07.escrow.release` triggerable. |
| 3 | No dispute exists on `SUB-44B207`; `t0` recorded; `J10` baseline PASS; `GET /readyz` → `200`. |

## Test Data

| Field | Value |
|---|---|
| open dispute | `POST /orders/ORD-2B8C55/dispute` buyer `{"subOrderId":"SUB-44B207","ground":"NOT_AS_DESCRIBED","note":"TC-112 probe"}` |
| clock | advance to `2026-09-26T10:00:01Z` (past release eligibility) |
| denied resolution | `POST /disputes/{id}/resolve` `MODERATOR` `{"outcome":"VENDOR","reason":"code and courier proof match"}` |
| admin resolution | same body as `ADMIN` |

## Steps
1. Buyer opens the dispute; capture `disputeId`; `GET /wallet/escrow?orderId=ORD-2B8C55`.
2. Advance the clock to `2026-09-26T10:00:01Z`; run `b07.escrow.release`; then attempt the internal release for `SUB-44B207`; re-read `GET /wallet/escrow?orderId=ORD-2B8C55`.
3. `MODERATOR` attempt the resolution; capture status; SQL-count resolution audit rows for the dispute.
4. `ADMIN` resolve with `{"outcome":"VENDOR","reason":"code and courier proof match"}`; capture `auditId`.
5. SQL by `auditId` — assert field completeness; count all resolution audit entries for the dispute.
6. `GET /admin/audit-log?targetId=<disputeId>&from=<t0>&to=<now>` as `ADMIN`.
7. `ADMIN` resolve again (byte-identical); recount resolution audit entries.

## Expected Result
- Step 1 → `201 { disputeId, state: "DISPUTED", escrowFrozen: true, evidenceDueBy }`; escrow view → `state = HELD`, `frozenBy = "DISPUTE"` (`API-RET-013`, `BR-ORD-05`).
- Step 2 → the release job performs **no release** (`released_at IS NULL`, `availablePayable = 0`) and the direct internal attempt returns `409 ESCROW_FROZEN` — escrow release is frozen for the affected sub-order until admin resolution (`BR-ORD-05`, `BR-ESC-02`, `AC-FR020-03` clause 1, `C-12`).
- Step 3 → `403 ARBITRATION_FORBIDDEN` (`API-RET-017`); the dispute stays `OPEN`; resolution-audit count = **0** — the denied attempt persisted nothing (`BR-RET-06`: Admin is final arbiter).
- Step 4 → `200 { state: "COMPLETED", escrowFrozen: false, resolution, auditId }` — resolution unfreezes into the vendor-win path (`API-RET-017`).
- Step 5 → the row behind `auditId` has `actor_user_id` = admin, `actor_role = 'ADMIN'`, `action = 'dispute.resolve'`, non-null `entity_type`/`entity_id` (the dispute), **both** `before` and `after` snapshots recording the state change, `reason = "code and courier proof match"`, `outcome = 'SUCCESS'`, non-null `ip`, `created_at` in `[t0, now]`, `correlation_id`, `prev_hash`/`entry_hash` (`BR-PLT-06`, `BR-RET-06` — the decision is written to the audit log, `AC-FR020-03` clause 2); SQL resolution-entry count for the dispute == **exactly 1**.
- Step 6 → `200 { items, page }` with exactly one item `{ action, actorRole: "ADMIN", targetId: <disputeId>, reason, correlationId }` — the decision is readable by support staff through the admin audit surface (`API-ADM-024`, `UC-036`).
- Step 7 → `409 STATE_CONFLICT` (`API-RET-017`); resolution-entry count still **1** — no duplicate audit row for a repeated decision.
