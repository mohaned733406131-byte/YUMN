# TC-104 — Coupon redemption at order creation computes type-specific discounts, enforces limits and books exactly one redemption row

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a checkout session applies each coupon type with server-side math (percent, fixed, free-shipping) and the VAT base reduced by the discount, that exhausted/per-user-exhausted coupons fail before any order row exists, and that confirming the order books exactly one `coupon_redemption` row, increments `used_count` once and debits the wallet once under an idempotent replay. | integration | P1 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Reserved-block customer `791100001` with an `ACTIVE` wallet ≥ 60,000 YER (money fixtures) and address `adr-7911` in zone `sanaa-center` (STANDARD = 500 YER). |
| 2 | Store `tech-store` (KYC `APPROVED`) sells `PRD-P1` at 12,500 YER with stock ≥ 10; cart holds `PRD-P1` × 2 → subtotal **25,000 YER**. |
| 3 | Coupons seeded within valid windows: `PERC10` (PERCENT 10 %, `usageLimit: 100`, `perUserLimit: 1`), `FIX500` (FIXED 500 YER), `FREESHIP` (`FREE_SHIPPING`, `free_shipping_scope: ALL`), `USEDUPQ` (`usageLimit: 1`, already redeemed once by another persona), `AGAINP` (`perUserLimit: 1`, this buyer already has one redemption in the fixture). |
| 4 | No checkout session or order exists for this buyer yet (order-count baseline recorded); `GET /readyz` → `200`. |

## Test Data

| Field | Value |
|---|---|
| buyer | `791100001`, wallet ≥ `60000` YER, address `adr-7911` |
| cart | `PRD-P1` × 2 @ `12500` → subtotal `25000`; STANDARD shipping `500` |
| percent session | `POST /checkout/session` `Idempotency-Key: chk-104-01` `{"addressId":"adr-7911","shippingMethod":"STANDARD","couponCode":"PERC10","paymentMethod":"wallet"}` → discount `2500`, vat `3375`, shippingFee `500`, grandTotal `26375` |
| fixed session | `Idempotency-Key: chk-104-02`, `"couponCode":"FIX500"` → discount `500`, vat `3675`, grandTotal `28175` |
| free-shipping session | `Idempotency-Key: chk-104-03`, `"couponCode":"FREESHIP"` → discount `0`, shippingFee `0`, vat `3750`, grandTotal `28750` |
| exhausted probes | `USEDUPQ`, `AGAINP` → expect `422 COUPON_INVALID` |
| confirm | `POST /orders` `Idempotency-Key: ord-104-01` `{"checkoutSessionId":"<chk-104-01>","confirmTotals":true}` |

## Steps
1. Record baselines: `GET /orders` total, `SELECT count(*) FROM b12.coupon_redemption`, `used_count` of `PERC10`, wallet `balance`.
2. Create the `FIX500` session and the `FREESHIP` session (one after the other); capture both `totals` objects.
3. `POST /checkout/session` with `USEDUPQ`; then with `AGAINP`; capture both error envelopes; re-count orders and redemptions.
4. Create the `PERC10` session (`chk-104-01`); capture `totals`.
5. `POST /orders` with `ord-104-01`; then replay the identical request with the same key and body.
6. SQL: `SELECT count(*), discount_yer FROM b12.coupon_redemption WHERE order_id = <orderId>`; re-read `PERC10.used_count`; read the wallet ledger rows for the order.
7. `GET /orders` total, wallet `balance`.

## Expected Result
- Step 2 → `201` with `FIX500` totals `{"subtotal":25000,"discount":500,"vat":3675,"shippingFee":500,"grandTotal":28175}` — VAT = 15 % × (25,000 − 500) = 3,675 (`BR-FIN-01`, `BR-PRM-05`); `FREESHIP` totals `{"subtotal":25000,"discount":0,"vat":3750,"shippingFee":0,"grandTotal":28750}` — the free-shipping coupon zeroes the shipping component only and never touches the VAT base (`BR-SHP-01`, `BR-FIN-01`); no order row is created by starting sessions.
- Step 3 → `USEDUPQ` → `422 COUPON_INVALID`, `details[].issue = "USAGE_LIMIT_REACHED"`; `AGAINP` → `422 COUPON_INVALID`, `details[].issue = "ALREADY_USED_BY_USER"` — limits are re-checked server-side before order creation (`BR-PRM-04`); order count and redemption count unchanged (`BR-PRM-06`, `AC-FR019-03`).
- Step 4 → `201` with `PERC10` totals `{"subtotal":25000,"discount":2500,"vat":3375,"shippingFee":500,"grandTotal":26375}` — discount = 10 % × 25,000 = 2,500, VAT = 15 % × (25,000 − 2,500) = 3,375, grand total inside the 500–5,000,000 YER bounds (`BR-FIN-01`, `C-14`).
- Step 5 → first call `201 { orderId, masterState: "PLACED", payment: { amount: 26375 }, … }`; byte-identical replay returns the **original** order with the original status code, the same `orderId` and no second payment (`API-ORD-002`, `AC-FR011-02`, `BR-ORD-06`).
- Step 6 → exactly **1** redemption row for the order (`count = 1`, `discount_yer = 2500`; `UNIQUE(coupon_id, order_id)` enforces one application per order, `BR-PRM-02`); `PERC10.used_count` incremented exactly once (baseline + 1, `BR-PRM-04`); exactly one `ORDER_PAYMENT` wallet debit of `26375` YER (`BR-PAY-06`, `BR-PAY-08`).
- Step 7 → order total +1 versus the step-1 baseline; wallet `balance` = baseline − 26,375; no ledger or order row was created by any of the failed coupon probes (nothing persisted).
