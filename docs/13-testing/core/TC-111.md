# TC-111 — Third failed delivery-code attempt locks confirmation and surfaces an AUTO ticket with the full timeline in the support console

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that the 3rd failed delivery-code attempt engages the 24-hour lock (correct code refused) and auto-creates a `source: AUTO` support ticket that support staff can find in the admin queue, open with linked entities and the full order timeline, assign (audited), and that the ticket owner sees the updated status in their own feed. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Delivery `DLV-4488` on order `ORD-7F3A21` / sub-order `SUB-9C1104` is `OUT_FOR_DELIVERY`; buyer knows code `482913`; `code.attemptsUsed = 2` (two prior wrong entries, TC-070 fixture pattern); `lockedUntil` absent; sub-order not `DELIVERED`. |
| 2 | Tokens: `ADMIN`, courier `790000011` (assigned), buyer `771234567`. |
| 3 | Baseline recorded: `GET /admin/tickets?source=AUTO&category=delivery&page=1&pageSize=50` → `total`; support queue contains no ticket for `ORD-7F3A21`. `GET /readyz` → `200`. |

## Test Data

| Field | Value |
|---|---|
| third wrong code | `POST /deliveries/DLV-4488/code {"code":"999999"}` as courier `790000011` |
| correct code during lock | `{"code":"482913"}` |
| admin queue filter | `GET /admin/tickets?source=AUTO&category=delivery&page=1&pageSize=50` |
| assign | `POST /admin/tickets/{id}/assign {}` as `ADMIN` (assign to self) |

## Steps
1. Record the baseline `total` for the AUTO delivery queue.
2. Courier posts the third wrong code; capture the error envelope.
3. Courier immediately posts the correct code `482913`; capture the response.
4. `GET /deliveries/DLV-4488` → inspect `code.attemptsUsed`, `code.lockedUntil`, `state`.
5. As `ADMIN`, `GET /admin/tickets?source=AUTO&category=delivery` → locate the new ticket; capture `ticketId` and item fields.
6. `GET /support/tickets/{id}` → inspect `linked` and `timeline`; `SELECT count(*) FROM order_status_history WHERE order_id = 'ORD-7F3A21'`.
7. `POST /admin/tickets/{id}/assign {}` → capture `auditId`.
8. As buyer `771234567`, `GET /support/tickets` → find the ticket's `status`.

## Expected Result
- Step 2 → `422 CODE_ATTEMPTS_EXCEEDED`, `retryable: false`, `retryAfterSeconds ≈ 86400`, `details.lockedUntil = failedAt + 24h` — the lock engages on the 3rd failure (`BR-SHP-03`, `C-16`, `AC-FR020-02`).
- Step 3 → `403 CODE_LOCKED` — the correct code does not deliver during the lock (`BR-ORD-08`); no further attempt consumed.
- Step 4 → `code.attemptsUsed = 3`, `code.lockedUntil` set, `state ≠ "DELIVERED"` — the 24-hour lock is in force (`BR-SHP-03`).
- Step 5 → `200 { items, page, total }` with `total = baseline + 1`; the new item carries `source: "AUTO"`, `category` delivery, `status: "OPEN"`, `orderId: "ORD-7F3A21"`, `userId` = buyer — the auto-created ticket is **visible to support staff in the console** (`API-ADM-039`, `BR-SHP-03`, `AC-FR020-02`).
- Step 6 → `200 { ticketId, number, category, status: "OPEN", messages, linked: { orderId, deliveryId }, timeline }` — `linked` carries both entities and `timeline` is an array whose entry count equals the `order_status_history` row count for `ORD-7F3A21` — the ticket carries the **full order timeline** (`FR-020` escalation queues, `BR-ORD-03`, `BR-ORD-09`, `API-ADM-037`).
- Step 7 → `200 { ticketId, status: "IN_PROGRESS", assignedTo, auditId }` (`API-ADM-040`); the `auditId` resolves to one complete append-only row (`actor_role = 'ADMIN'`, entity = ticket, non-null `ip`, `created_at`, `correlation_id`, both hashes — `BR-PLT-06`, `SEC-REQ-010`).
- Step 8 → the owner's own feed (`API-ADM-036`) lists the ticket with `status: "IN_PROGRESS"` and `unreadFromSupport` unchanged by the staff-side assignment — the flow is operable end-to-end by support staff (`AC-S-23` operational walkthrough input, `DATA-REQ-008` scoping keeps it owner-visible).
