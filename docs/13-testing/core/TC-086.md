# TC-086 — OTP delivery fails over from SMS to WhatsApp within the request window

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that when the primary SMS provider times out during an OTP request, the same template is automatically retried on WhatsApp before the request completes, both attempts appear in the delivery record, the healthy-path run uses SMS as primary with no fallback, and the OTP remains verifiable. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Buyer `771234567` has `SECURITY` notifications enabled on SMS and WhatsApp (defaults) and no prior pending OTP for `LOGIN`. |
| 2 | SMS provider mock is armed to **timeout** after 2 s for this run; WhatsApp mock is healthy and logs deliveries (`INT-REQ-003` sandbox). |
| 3 | Notification outbox and provider logs are empty for the run window; OTP attempt counters reset. |

## Test Data

| Field | Value |
|---|---|
| request | `POST /auth/otp/start {"phone":"771234567","context":"LOGIN","channel":"SMS"}` |
| expected channels record | `SMS {status:"FAILED"}` then `WHATSAPP {status:"SENT"}` — same template, both logged |
| control run | same request with a healthy SMS mock |

## Steps
1. With the SMS mock timing out, `POST /auth/otp/start {"phone":"771234567","context":"LOGIN","channel":"SMS"}` → measure that the response returns only after the WhatsApp attempt is logged.
2. `GET /notifications?category=SECURITY&limit=5` → inspect the item's `channels[]`; read the provider logs for both adapters.
3. Read the WhatsApp sandbox payload; verify the OTP code received there with `POST /auth/otp/verify {"phone":"771234567","code":"…","context":"LOGIN"}`.
4. Reset the mocks to healthy and repeat step 1 (control run) → re-read `channels[]` and logs.

## Expected Result
- Step 1 → `200 { status: "OTP_SENT", … }` returned **after** the fallback attempt — the failover happens within the request window (`AC-FR017-03`, `INT-REQ-003`).
- Step 2 → `channels[] = [ { channel: "SMS", status: "FAILED", sentAt }, { channel: "WHATSAPP", status: "SENT", sentAt } ]` for the same notification — both attempts appear in the delivery record (`BR-NTF-03`, `notifications.md` §3).
- Step 3 → the WhatsApp message carries the same localized template (Arabic, `BR-NTF-04`) and the 6-digit code verifies `200 { verified: true, accessToken… }` — delivery achieved despite the SMS outage (`BR-NTF-03`); wrong code → `422 OTP_VERIFICATION_FAILED` with `attemptsRemaining` (`BR-AUTH-03`).
- Step 4 → the control run records `channels[] = [ { channel: "SMS", status: "SENT", … } ]` with **no** WhatsApp attempt — failover only fires on SMS failure (`BR-NTF-03`).
