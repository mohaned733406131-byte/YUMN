# TC-013 — Privilege escalation attempts by Moderator, Customer and vendor staff are refused

| Field | Value |
|---|---|
| Objective | Verify that role boundaries hold server-side: a Moderator cannot execute finance/admin actions, a Customer cannot reach admin routes, and vendor staff cannot change their own role. |
| Level | integration |
| Priority | P0 (merge-blocking, also runs under SEC-P-05) |
| Automation | Yes — Jest + Supertest |

## Preconditions
- Seeded actors with valid tokens: `MODERATOR` (`773330001`), `CUSTOMER` (`771234567`), `ADMIN` (`772220001`), vendor Owner (`774440001`) and their `EDITOR` staff (`774440003`).
- Order `ORD-9002` is `REFUNDED`-eligible; top-up `TOP-551` is `PENDING_VERIFICATION`.
- The permission matrix from `09-security/rbac.md` is the reference.

## Test Data

| Field | Value |
|---|---|
| Moderator phone | `773330001` |
| Customer phone | `771234567` |
| Admin phone | `772220001` |
| Vendor staff phone | `774440003` (role `EDITOR`) |
| Target top-up | `TOP-551` |

## Steps
1. `POST /admin/topups/TOP-551/verify` with the Moderator token.
2. `POST /admin/orders/ORD-9002/transition` with the Moderator token and body `{"subOrderId":"SUB-1","toState":"REFUNDED","reason":"test"}`.
3. `POST /admin/users/771234567/suspend` with the Moderator token.
4. `GET /admin/users` and `GET /admin/audit-log` with the Customer token.
5. `PUT /admin/settings/commission.defaultRate` with the Customer token and body `{"value":0}`.
6. `PATCH /store/staff/774440003/role` with the staff member's own token and body `{"role":"OWNER","reason":"self"}`.
7. `POST /admin/users/771234567/role` with a plain `ADMIN` token (role management is Super Admin only).

## Expected Result
- Steps 1, 3 and 6 return `403 FORBIDDEN`; step 6 specifically returns `403 STAFF_SELF_ESCALATION` (`BR-VND-06`).
- Step 2 returns `403 FORBIDDEN` — Moderators are read-only outside content/support moderation; the order state is unchanged.
- Steps 4 and 5 return `403 FORBIDDEN`; the customer never receives admin data, and `commission.defaultRate` is unchanged.
- Step 7 returns `403 ROLE_ASSIGNMENT_FORBIDDEN` — only `SUPER_ADMIN` assigns roles.
- No state change, no ledger movement and no role mutation occurred anywhere in the run (DB diff = empty).
- The same calls with a valid `ADMIN`/`SUPER_ADMIN` token succeed (positive control), proving denial is role-based.
- Each denial is logged with actor, action, route, correlation ID (`BR-PLT-06`).
