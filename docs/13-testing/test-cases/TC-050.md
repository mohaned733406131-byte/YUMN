# TC-050 — Order status history is append-only: no mutation API, no in-place row rewrites

| Field | Value |
|---|---|
| Objective | Verify `BR-ORD-03`: `order_status_history` rows are only ever appended — there is no API to create, edit or delete them, the database rejects in-place modification, and previously written rows stay byte-identical across later transitions. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (SQL checksums before/after each transition) |

## Preconditions
- Order `ORD-050` (single vendor) exists in `PLACED` with one history row; checksum captured for that row.
- API DB role has no `UPDATE`/`DELETE` grant on `order_status_history`; the timeline route exposes read verbs only.

## Test Data

| Field | Value |
|---|---|
| Order | `ORD-050` / `SUB-050A` |
| Row snapshot | `{id, from_state, to_state, actor_role, reason, at}` + SHA-256 checksum |
| Tamper attempts | `PATCH`, `PUT`, `DELETE`, `POST` on `/orders/{id}/timeline` |
| SQL tamper | `UPDATE order_status_history SET reason='x' WHERE order_id='ORD-050';` and `DELETE …` |

## Steps
1. Read `GET /orders/{id}/timeline` and snapshot every row with checksums; record the row count.
2. Call `PATCH /orders/{id}/timeline`, `PUT /orders/{id}/timeline`, `DELETE /orders/{id}/timeline/{entryId}`, and `POST /orders/{id}/timeline` with a fabricated entry.
3. Attempt the SQL `UPDATE` and `DELETE` directly.
4. Drive three legal transitions (`CONFIRMED`, `PROCESSING`, `READY_FOR_PICKUP`) and snapshot the timeline again.
5. Compare snapshots: row count, order of rows, and each pre-existing row's checksum.
6. Validate each new row's payload (`from`, `to`, `actorRole`, `at`, `reason` where the transition requires one).

## Expected Result
- Step 2 → `405 METHOD_NOT_ALLOWED` for every mutation verb — the timeline has no write route (`error-model.md` §3); the fabricated `POST` never lands a row.
- Step 3 → both statements are rejected by the append-only constraint/role grant; affected row count = 0.
- Step 4 → three new rows appended in order (`PLACED→CONFIRMED`, `CONFIRMED→PROCESSING`, `PROCESSING→READY_FOR_PICKUP`).
- Step 5 → row count 1 → 4; every pre-existing row's checksum is identical — states are never overwritten (`AC-FR012-05`); no renumbering or timestamp drift.
- Step 6 → every row carries `actorRole` and `at`, plus `reason` on cancel/reject-style moves; every `from`/`to` pair exists in the canonical table (`C-09`).
- A refused tamper writes **0** audit-visible state change and leaves wallet/escrow untouched; the behavior feeds `AC-S-14` evidence for append-only financial-adjacent records.
