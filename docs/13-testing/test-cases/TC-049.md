# TC-049 — Master completes only when every sub-order settles; a dispute blocks only its own sub-order

| Field | Value |
|---|---|
| Objective | Verify `BR-ORD-07`: with two sub-orders the master reaches `COMPLETED` only after both are `COMPLETED` or `REFUNDED`, and that a dispute raised on one sub-order freezes **only** that sub-order's escrow while the other settles normally. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (test clock at the 7-day escrow boundary) |

## Preconditions
- Order `ORD-049` with sub-orders `SUB-049A` (tech-store, 29,250 YER) and `SUB-049B` (sanaa-perfumes, 9,600 YER), both `DELIVERED` at `T0`, escrow holds matching each total.
- Dispute fixture available (`API-RET-013`); admin `775550010` can arbitrate.

## Test Data

| Field | Value |
|---|---|
| Orders | `ORD-049`, `SUB-049A` (29,250 YER), `SUB-049B` (9,600 YER) |
| Dispute | `{"subOrderId":"SUB-049B","ground":"ITEM_DAMAGED","note":"الصندوق مكسور"}` |
| Clock | `T0` (delivered) → `T0 + 7 days + 1 min` (release run) |

## Steps
1. `GET /orders/{ORD-049}` → both sub-orders `DELIVERED`, `masterState` not `COMPLETED`, escrow `releaseEligibleAt = T0 + 7 d` on both.
2. Buyer `POST /orders/{ORD-049}/dispute` with the payload above.
3. Advance the clock to `T0 + 7 days + 1 min` and run the escrow release job.
4. `GET /wallet/escrow?orderId=ORD-049`, `GET /orders/{ORD-049}`, `GET /store/finance/overview` (vendor A) and `GET /disputes`.
5. Admin `POST /disputes/{id}/resolve` `{"outcome":"VENDOR","reason":"item verified intact"}`; re-run the release job for `SUB-049B`.
6. Re-read the master order, both escrow positions and the timelines.

## Expected Result
- Step 1 → `200` with `masterState` in `DELIVERED` (aggregation, not yet complete); two independent escrow holds.
- Step 2 → `201 {state:"DISPUTED", escrowFrozen:true, evidenceDueBy}`; only `SUB-049B` enters `DISPUTED` (`BR-ORD-05`).
- Step 3 → `SUB-049A` releases to vendor payable exactly once; `SUB-049B` is skipped — a release attempt against it returns `409 ESCROW_FROZEN` (`BR-ESC-02`).
- Step 4 → master `masterState ≠ COMPLETED` while `SUB-049B` is `DISPUTED`; escrow view shows `SUB-049A` released and `SUB-049B` `frozenBy:"DISPUTE"` with its 9,600 YER still held; `GET /disputes` lists the open case (`API-RET-014`).
- Step 5 → `200 {state:"COMPLETED", escrowFrozen:false, auditId}`; the follow-up release job releases `SUB-049B` once.
- Step 6 → `masterState COMPLETED` only now — when **all** sub-orders are `COMPLETED` or `REFUNDED` (`AC-FR012-04`); history shows the master completion row after the last sub-order settles; vendor A was never blocked by vendor B's dispute.
