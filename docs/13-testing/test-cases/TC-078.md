# TC-078 — Inspection PASS moves RETURN_RECEIVED to REFUNDED; FAIL routes to admin review as DISPUTED

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a vendor inspection recorded within the 72-hour window with `PASS` transitions `RETURN_RECEIVED → REFUNDED` and composes the refund, that `FAIL` routes the case to `DISPUTED` (admin review) with no refund and a frozen escrow, and that inspections are guarded by state and store scope. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `RET-8848` (order `ORD-7F3A21`, `SUB-9C1104`) is `RETURN_RECEIVED`, receivedAt `2026-09-26T08:00:00+03:00` ⇒ inspection deadline `2026-09-29T08:00:00+03:00`; clock `2026-09-26T10:00:00+03:00`. |
| 2 | `RET-8849` (order `ORD-7F3A25`, `SUB-9C1109`) is `RETURN_RECEIVED` (receivedAt `2026-09-26T07:00:00+03:00`) for the FAIL path; its escrow is `frozenBy: "NONE"` before the run. |
| 3 | `RET-8846` is `RETURN_REJECTED` (wrong-state guard); tokens: vendor `779876543`, foreign vendor `779876544`, buyer `771234567`. |

## Test Data

| Field | Value |
|---|---|
| PASS | `POST /store/returns/RET-8848/inspection {"outcome":"PASS","notes":"seal intact, accessories complete"}` |
| FAIL | `POST /store/returns/RET-8849/inspection {"outcome":"FAIL","notes":"cracked screen not declared by buyer"}` |
| refund expectation (PASS) | `refund: { status: "PENDING", expectedCreditBy }` = REFUNDED + 3 business days |

## Steps
1. As vendor `779876543`, `GET /store/returns/RET-8848` → inspect state and inspection SLA fields.
2. `POST /store/returns/RET-8848/inspection {"outcome":"PASS","notes":"seal intact, accessories complete"}`.
3. `GET /returns/RET-8848` → decision/inspection/refund blocks; `GET /orders/ORD-7F3A21` → sub-order state.
4. Repeat step 2 (duplicate inspection); then `POST /store/returns/RET-8846/inspection {"outcome":"PASS","notes":"n/a"}` (rejected return).
5. As foreign vendor `779876544`, `POST /store/returns/RET-8849/inspection {"outcome":"PASS","notes":"cross-store attempt"}`; then as owner vendor, `POST /store/returns/RET-8849/inspection {"outcome":"FAIL","notes":"cracked screen not declared by buyer"}`.
6. As buyer `771234567`, `GET /wallet/escrow?orderId=ORD-7F3A25`; read notification outbox for both parties.

## Expected Result
- Step 1 → `200 { state: "RETURN_RECEIVED", inspection: absent, refund: { status: … } }` with the 72-hour inspection window anchored at receivedAt (`BR-RET-05`).
- Step 2 → `200 { state: "REFUNDED", inspection: { outcome: "PASS", notes, at, autoApproved: false }, refund: { status: "PENDING", expectedCreditBy } }` — pass ⇒ refund, executed within the window (`API-RET-009`, `BR-RET-02`, `AC-FR016-02`); `expectedCreditBy` = REFUNDED + ≤3 business days (`BR-RET-04`).
- Step 3 → detail shows the inspection block and `refund.status: "PENDING"`; sub-order `SUB-9C1104` is `REFUNDED` (`BR-RET-02`, `C-09`) — 17 states only.
- Step 4 → duplicate inspection `409 STATE_CONFLICT`; inspection on the rejected return `409 STATE_CONFLICT` — only `RETURN_RECEIVED` accepts an inspection (`BR-RET-02`).
- Step 5 → cross-store attempt `404 NOT_FOUND` (`BR-ORD-09`, `DATA-REQ-008`); the owner's FAIL returns `200 { state: "DISPUTED", inspection: { outcome: "FAIL", … }, refund: null }` — fail ⇒ admin review, no refund initiated (`API-RET-009`, `BR-RET-06`).
- Step 6 → for `ORD-7F3A25`: escrow item shows `frozenBy: "DISPUTE"`, `releasedAt: null` — only the affected sub-order is frozen (`BR-ORD-05`); buyer and vendor are notified of both outcomes in their locale (`BR-NTF-04`).
