# TC-076 — Vendor decides a return inside the 48-hour SLA: approve schedules pickup, reject requires a reason

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that within the 48-hour decision SLA the vendor can approve (`RETURN_REQUESTED → RETURN_APPROVED`, return pickup offered through the delivery engine) or reject with a mandatory reason (`→ RETURN_REJECTED`), with duplicate decisions refused, foreign stores locked out, and both parties notified in their locale. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `RET-8845` (order `ORD-7F3A21`, `SUB-9C1104`) is `RETURN_REQUESTED`, openedAt `2026-09-25T11:00:00+03:00` ⇒ `decisionDueAt = 2026-09-27T11:00:00+03:00`; clock `2026-09-26T12:00:00+03:00` (not overdue). |
| 2 | `RET-8846` (order `ORD-7F3A23`, `SUB-9C1107`) is `RETURN_REQUESTED` with the same SLA window, reserved for the reject path. |
| 3 | Tokens: vendor owner `779876543` (tech-store, assignee of both returns), foreign vendor owner `779876544` (store B), buyer `771234567`. |

## Test Data

| Field | Value |
|---|---|
| approve | `POST /store/returns/RET-8845/approve {"note":"condition verified against policy"}` |
| reject without reason | `POST /store/returns/RET-8846/reject {}` → expect `422 REASON_REQUIRED` |
| reject with reason | `POST /store/returns/RET-8846/reject {"reason":"item shows use beyond policy inspection"}` |
| SLA | decisionDueAt `2026-09-27T11:00:00+03:00` for both |

## Steps
1. As vendor `779876543`, `GET /store/returns?page=1&sort=decisionDueAt_asc` → inspect both items.
2. `POST /store/returns/RET-8845/approve {"note":"condition verified against policy"}`.
3. Repeat step 2 verbatim (duplicate decision).
4. `GET /returns/RET-8845` and `GET /returns/RET-8845/pickup`.
5. `POST /store/returns/RET-8846/reject {}`, then `POST /store/returns/RET-8846/reject {"reason":"item shows use beyond policy inspection"}`.
6. As foreign vendor `779876544`, `GET /store/returns/RET-8845`, then `POST /store/returns/RET-8845/approve {}`.
7. Read notification outbox for buyer `771234567` and vendor `779876543`; read `order_status_history` for `SUB-9C1104` / `SUB-9C1107`.

## Expected Result
- Step 1 → `200` with both items `{ returnId, state: "RETURN_REQUESTED", openedAt: "2026-09-25T11:00:00+03:00", decisionDueAt: "2026-09-27T11:00:00+03:00", overdue: false }` — decisionDueAt = openedAt + 48 h (`returns.md` §1/§2).
- Step 2 → `200 { state: "RETURN_APPROVED", version, pickup: { status: "OFFERED" }, slaClearedAt }` with `slaClearedAt ≤ decisionDueAt` — approval schedules the return pickup through the delivery engine (`BR-SHP-04` mechanics, `API-RET-006`).
- Step 3 → `409 STATE_CONFLICT` — the return is no longer `RETURN_REQUESTED` (`C-09`, `BR-RET-02`).
- Step 4 → detail `200` with `decision: { outcome: "APPROVED", by: vendor, at }` and `pickup: { status: "OFFERED", deliveryId }`; `GET /returns/RET-8845/pickup` → `200 { status: "OFFERED" }` — read-only, no GPS anywhere (`C-16`); timeline append-only (`BR-ORD-03`).
- Step 5 → first call `422 REASON_REQUIRED`; second call `200 { state: "RETURN_REJECTED", version, historyEntry }` — rejection always carries a reason (`API-RET-007`).
- Step 6 → `404 NOT_FOUND` for both the read and the approve — a foreign store never sees or decides another store's return (`NOT_FOUND` per `API-RET-005`, `BR-ORD-09`, `DATA-REQ-008`).
- Step 7 → buyer receives approval (with pickup status) and rejection (with reason) notifications, vendor receives the request alert — Arabic templates for locale `ar` (`BR-NTF-01`, `BR-NTF-04`); history rows `RETURN_REQUESTED → RETURN_APPROVED` / `→ RETURN_REJECTED` in order (`BR-RET-02`, `AC-FR016-02`).
