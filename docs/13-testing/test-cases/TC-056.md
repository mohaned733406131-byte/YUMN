# TC-056 — DISPUTED opened before COMPLETED freezes escrow and blocks the 7-day release

| Field | Value |
|---|---|
| Objective | Verify `BR-ORD-05`: a dispute opened on a `DELIVERED` sub-order before `COMPLETED` moves it to `DISPUTED`, freezes its escrow (`frozenBy:"DISPUTE"`), and blocks the 7-day release until an admin resolves the case — while the disputed sub-order can open only one dispute at a time. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (test clock across the 7-day release boundary) |

## Preconditions
- Order `ORD-056` (single vendor `tech-store`, sub `SUB-056A`, total 14,875 YER) is `DELIVERED` at `T0`; escrow holds 14,875 YER with `releaseEligibleAt = T0 + 7 d`.
- Buyer `771234567` and admin `775550010` hold valid tokens; escrow-release and payout jobs drain on demand.

## Test Data

| Field | Value |
|---|---|
| Dispute body | `{"subOrderId":"SUB-056A","ground":"ITEM_NOT_AS_DESCRIBED","note":"المنتج مختلف عن الوصف","imageFileIds":["img-001"]}` |
| Clock points | `T0 + 6 d 23 h`, `T0 + 7 d + 1 min`, post-resolution re-run |
| Resolve body | `{"outcome":"VENDOR","reason":"photos confirm the item matches the listing"}` |

## Steps
1. Buyer `POST /orders/{id}/dispute` with the body above → record `disputeId`, `evidenceDueBy`.
2. Buyer repeats the dispute for the same `subOrderId`; buyer also attempts `POST /orders/{id}/dispute` while the order is already `DISPUTED`.
3. `GET /wallet/escrow?orderId={id}` and `GET /orders/{id}` before the release boundary.
4. Advance the clock to `T0 + 6 d 23 h` and run the release job (premature probe), then to `T0 + 7 d + 1 min` and run it again; attempt a direct release/payout against the frozen sub-order.
5. Admin `POST /disputes/{id}/resolve` with the resolve body; re-run the release job.
6. Re-read escrow, `GET /store/finance/overview`, order detail and timelines.

## Expected Result
- Step 1 → `201 {disputeId, state:"DISPUTED", escrowFrozen:true, evidenceDueBy}` (`API-RET-013`); the sub-order enters `DISPUTED` from `DELIVERED` (`DOC-SA-010` §2).
- Step 2 → `409 DISPUTE_ALREADY_OPEN` for the duplicate; no second dispute row (`BR-ORD-05`).
- Step 3 → escrow view shows `state DISPUTED` (or the active hold) with `frozenBy:"DISPUTE"` and `amountHeld 14875`; `masterState ≠ COMPLETED`.
- Step 4 → no release at 6 d 23 h **and none** at day 7: the release job skips the sub-order and a direct release attempt returns `409 ESCROW_FROZEN` (`BR-ESC-02`); payout requests that would draw on the frozen amount are withheld; ledger shows **0** release postings and `SUM = 0`.
- Step 5 → `200 {state:"COMPLETED", escrowFrozen:false, resolution, auditId}` (admin is final arbiter, `BR-RET-06`); the re-run releases the escrow exactly once.
- Step 6 → `frozenBy:"NONE"` after resolution; `GET /store/finance/overview` had kept the frozen 14,875 YER inside `escrowHeld` while frozen; timelines show `DELIVERED→DISPUTED` (actor CUSTOMER, with ground) and `DISPUTED→COMPLETED` (actor ADMIN, with reason) — append-only (`AC-FR012-05`).
- Forward coverage: escrow release/commission (`FR-014`, TC-057–064) and dispute arbitration/refund mechanics (`FR-016`, TC-075–084) build on this frozen state.
