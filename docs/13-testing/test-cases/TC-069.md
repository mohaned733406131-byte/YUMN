# TC-069 — Correct 6-digit code delivers the sub-order and starts the 7-day escrow hold

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that submitting the buyer's correct 6-digit code moves the sub-order to `DELIVERED` exactly once (idempotent replay), hides the code from the buyer, records delivery proof = code + timestamp + courier identity, and starts the 7-day escrow hold visible to the vendor. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `DLV-4471` is `OUT_FOR_DELIVERY`, assigned to courier `790000011`; sub-order `SUB-9C1104` (order `ORD-7F3A21`) is `OUT_FOR_DELIVERY`; code `482913` issued to buyer `771234567`, `code.attemptsUsed = 0`, not locked. |
| 2 | Payment captured at `PLACED`: subtotal 12,500 YER + VAT 1,875 YER + shipping 500 YER = grand total 14,875 YER; escrow funded from that capture (`BR-PAY-06`). |
| 3 | Vendor `779876543` owns store `tech-store` / `SUB-9C1104`; SMS/WhatsApp adapters are mock sandboxes logging deliveries. |

## Test Data

| Field | Value |
|---|---|
| delivery / order / sub-order | `DLV-4471` / `ORD-7F3A21` / `SUB-9C1104` |
| correct code | `482913` |
| escrow expectation | `amountHeld = 14875` YER, `releaseEligibleAt = deliveredAt + 7×24h`, `frozenBy: "NONE"` |
| actors | courier `790000011` (assignee), buyer `771234567`, vendor `779876543` |

## Steps
1. As buyer `771234567`, `GET /orders/ORD-7F3A21/delivery-code` → capture `code`, `issuedAt`, `attemptsRemaining`.
2. As courier `790000011`, `POST /deliveries/DLV-4471/code {"code":"482913"}`.
3. Repeat step 2 verbatim (replay of the same successful submission).
4. As buyer, `GET /orders/ORD-7F3A21/delivery-code` again.
5. As courier, `GET /deliveries/DLV-4471` → inspect `proof` and `code.attemptsUsed`.
6. As vendor `779876543`, `GET /wallet/escrow?orderId=ORD-7F3A21`.
7. As buyer, `GET /orders/ORD-7F3A21`; read `order_status_history` for `SUB-9C1104` and the notification outbox for buyer and vendor.

## Expected Result
- Step 1 → `200 { code: "482913", issuedAt, attemptsRemaining: 3 }` for the order owner only.
- Step 2 → `200 { state: "DELIVERED", version, deliveredAt, proof: { code: true, courierId: "790000011", verifiedAt } }`; sub-order `SUB-9C1104` is `DELIVERED` — `DELIVERED` is reachable only through a verified code (`BR-ORD-08`, `AC-FR015-02`).
- Step 3 → `200` with the same `state: "DELIVERED"` and unchanged `deliveredAt`; no duplicate escrow or ledger rows are written — first success wins, replay no-ops (`DOC-SA-010` §5, `BR-PAY-08`).
- Step 4 → `409 STATE_CONFLICT` (already delivered); the code is hidden again after successful verification (`API-SHP-013`).
- Step 5 → `proof.code = true`, `proof.courierId`, `proof.verifiedAt` present; no photo is attached yet the proof is complete — the photo is optional and never gates `DELIVERED` (`BR-SHP-07`); `code.attemptsUsed = 1`.
- Step 6 → `200` with an item for `SUB-9C1104`: `amountHeld = 14875`, active hold (`releasedAt: null`), `releaseEligibleAt` exactly `deliveredAt + 7×24h`, `frozenBy: "NONE"` (`BR-ESC-01`, `C-12`).
- Step 7 → sub-order `DELIVERED` but master order not yet `COMPLETED` (`BR-ORD-07`); one append-only history row with actor = courier (`BR-ORD-03`); buyer and vendor each receive one delivery notification on their opted-in channels using the Arabic template (`BR-NTF-01`, `BR-NTF-04`).
