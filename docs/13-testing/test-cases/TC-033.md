# TC-033 — Order total boundaries 499 / 500 / 5,000,000 / 5,000,001 YER enforced at confirmation

| Field | Value |
|---|---|
| Objective | Verify that the server-computed `totals.grandTotal` is accepted only inside the inclusive 500–5,000,000 YER band: 499 and 5,000,001 are rejected with `ORDER_VALUE_OUT_OF_RANGE` before any order row exists, while 500 and 5,000,000 succeed. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (boundary fixtures `B-499/B-500/B-5M/B-5M001` from DOC-TST-005) |

## Preconditions
- Buyer `771234567` wallet funded with 6,000,000 YER so funds never confound the boundary result.
- Four seeded carts exist whose server-computed grand totals are exactly `499`, `500`, `5000000` and `500001` YER (free-shipping coupon applied so shipping = 0, per `BR-SHP-01`).
- `GET /wallet` reports `limits {"topUpMin":1000,"topUpMax":5000000,"orderMin":500,"orderMax":5000000}`.

## Test Data

| Field | Value |
|---|---|
| Boundary totals | `499` (reject), `500` (accept), `5000000` (accept), `500001` (reject) YER |
| Cart fixtures | `B-499`, `B-500`, `B-5M`, `B-5M001` (DOC-TST-005 §4) |
| Keys | `chk-033-499/500/5M/5M001`, `ord-033-499/500/5M/5M001` |

## Steps
1. `GET /wallet` and assert the echoed `limits` band.
2. For each fixture: `POST /checkout/session` with its `Idempotency-Key` and body `{"addressId":"adr-771","shippingMethod":"STANDARD","paymentMethod":"wallet"}` → record `totals.grandTotal`.
3. `POST /orders` with the matching `Idempotency-Key`, body `{"checkoutSessionId":"cs-<fixture>","confirmTotals":true}`.
4. After each rejection, count `orders` and `wallet_transaction` rows for this buyer and re-read `GET /wallet`.
5. Re-run step 3 for `B-500` and `B-5M` a second time with the same keys.

## Expected Result
- Step 1 → `200` with `limits.orderMin 500` and `limits.orderMax 5000000`.
- Step 2 → each session echoes the exact boundary total; no client-side total is trusted (`BR-CRT-04`).
- Step 3, `499` → `422` `error.code = ORDER_VALUE_OUT_OF_RANGE`, `details[].field = "totals.grandTotal"`, `issue = OUT_OF_RANGE`, `retryable:false` (`AC-FR011-01`).
- Step 3, `500001` → `422 ORDER_VALUE_OUT_OF_RANGE` with the same envelope.
- Step 3, `500` and `5000000` → `201` with `masterState "PLACED"` and escrow funded for the exact total.
- Step 4 → after the two rejections: **0** new order rows, **0** ledger rows, balance unchanged — the bound is validated before any order row exists (`C-14`).
- Step 5 → `201` both times, returning the original orders (`BR-ORD-06`); totals stay integer YER (`BR-PAY-10`).
- Boundary results feed `TST-CON-14` evidence.
