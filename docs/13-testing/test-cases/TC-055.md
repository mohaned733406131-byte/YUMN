# TC-055 — BR-ORD-10 escalation timing boundary: silent at 23:59, fires exactly once at 24:00

| Field | Value |
|---|---|
| Objective | Verify the 24-hour SLA escalation boundary with an injectable clock: no escalation before 24 hours elapse, exactly one escalation (queue flag + notification) at or after the boundary, idempotent on re-run, and cleared from consideration once the order leaves `CONFIRMED`. |
| Level | integration |
| Priority | P2 |
| Automation | Yes — Jest + Supertest (injectable clock; BullMQ test clock; no wall-clock sleeps) |

## Preconditions
- Order `ORD-055` confirmed at `T1` (sub-order `CONFIRMED`, vendor has not advanced it); admin notification sink is empty.
- SLA job can be triggered on demand; clock injection shifts application time only.

## Test Data

| Field | Value |
|---|---|
| Order | `ORD-055` / `SUB-055A`, `CONFIRMED` at `T1` |
| Clock points | `T1 + 23h59m59s`, `T1 + 24h00m00s`, `T1 + 24h05m00s`, `T1 + 24h10m00s` (after `PROCESSING`) |
| Probes | `GET /admin/orders?escalated=true`, `GET /notifications` (admin), history row count |

## Steps
1. Set the clock to `T1 + 23h59m59s`; run the SLA escalation job; probe the queue and notifications.
2. Set the clock to `T1 + 24h00m00s`; run the job; probe again plus `GET /orders/{id}` state and history count.
3. Run the job again at `T1 + 24h05m00s` (duplicate-run probe) and count escalations/notifications.
4. Vendor `POST /store/orders/{id}/processing` (state → `PROCESSING`); set the clock to `T1 + 24h10m00s` and run the job once more.
5. Read `GET /admin/orders?escalated=true`, the order detail, timeline, wallet and escrow.

## Expected Result
- Step 1 → **0** escalations, **0** notifications, no `SLA_24H` flag — the rule fires strictly at/after 24 hours.
- Step 2 → exactly **1** escalation: the order appears in `GET /admin/orders` with `flags:["SLA_24H"]`, one admin notification is delivered (`API-ORD-013`), state still `CONFIRMED`, history row count unchanged — escalation never rewrites state and never auto-cancels (`BR-ORD-10`).
- Step 3 → still exactly 1 escalation and 1 notification — the job is idempotent per sub-order (`BR-PLT-01`, `BR-PLT-02`).
- Step 4 → after the order leaves `CONFIRMED`, the job creates **no new** escalation; the existing flag is no longer produced for a non-`CONFIRMED` order on re-run.
- Step 5 → `SUM(ledger) = 0`, escrow positions unchanged, no `CANCELLED` history row anywhere — money never moves because of an SLA escalation.
- All timing assertions use the injected clock; the suite never sleeps through a 24-hour window (testing-strategy §9).
