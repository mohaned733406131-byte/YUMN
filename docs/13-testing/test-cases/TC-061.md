# TC-061 — An open dispute freezes escrow until admin arbitration

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that opening a dispute freezes only the affected sub-order's escrow, blocks the 7-day release and any payout until an Admin resolves the case, and that both resolutions unfreeze escrow into the correct path (vendor win → release, buyer win → refund). | integration | P1 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Order `ORD-7F3A21` / sub-order `SUB-9C1104` (14,875 YER) is `DELIVERED` at `2026-09-19T10:00:00Z` with escrow `HELD` (TC-057/TC-058 fixtures). |
| 2 | Second fixture `ORD-2B8C55` / `SUB-44B207` (same totals) is `DELIVERED` the same day for the buyer-win branch. |
| 3 | `ADMIN` (`770000001`), `MODERATOR` (`770000003`) and buyer (`771234567`) tokens exist; test clock is controllable. |

## Test Data

| Field | Value |
|---|---|
| dispute ground | `NOT_AS_DESCRIBED` |
| escrow held | 14,875 YER per sub-order |
| release eligible at | `2026-09-26T10:00:00Z` (7 days, `C-12`) |
| commission at release | 12,500 × 10% = **1,250 YER** |
| payable after vendor win | 14,875 − 1,250 = **13,625 YER** |

## Steps
1. Buyer `POST /orders/ORD-7F3A21/dispute` body `{"subOrderId":"SUB-9C1104","ground":"NOT_AS_DESCRIBED","note":"Screen is cracked"}`.
2. Repeat step 1 byte-identical; then `GET /disputes?state=OPEN` and `GET /wallet/escrow?orderId=ORD-7F3A21`.
3. Set the clock to `2026-09-26T10:00:01Z`, run `b07.escrow.release`, then attempt an internal release call for `SUB-9C1104`.
4. Vendor `GET /store/finance/overview`, then vendor `POST /store/payouts` with `Idempotency-Key: pay-dispute-01` and body `{"amount":13625}`.
5. `MODERATOR` `POST /disputes/{id}/resolve` body `{"outcome":"VENDOR","reason":"code and courier proof match"}`.
6. `ADMIN` `POST /disputes/{id}/resolve` with the same body → read `GET /disputes/{id}`.
7. Run `b07.escrow.release` again; `GET /wallet/escrow`, `GET /store/finance/overview`.
8. Repeat steps 1–6 on `ORD-2B8C55` with `{"outcome":"BUYER","reason":"seller shipped a damaged unit"}`, then run `b07.escrow.release` and `GET /orders/ORD-2B8C55/refund`.

## Expected Result
- Step 1 → `201 { disputeId, state: "DISPUTED", escrowFrozen: true, evidenceDueBy }`; step 2 repeat → `409 DISPUTE_ALREADY_OPEN` — exactly one dispute row per sub-order.
- Step 2 escrow view → `state = HELD`, `frozenBy = "DISPUTE"`; `releaseEligibleAt` is still stamped but ignored while frozen.
- Step 3 → no release: `released_at IS NULL`, `availablePayable = 0`; the direct release attempt returns `409 ESCROW_FROZEN` (`BR-ESC-02`) — a freeze is re-checked inside the job, not only at enqueue time.
- Step 4 → `availablePayable = 0` and the payout returns `422 INSUFFICIENT_FUNDS`; no `b07.payout.execute` job exists (nothing was ever released).
- Step 5 → `403 ARBITRATION_FORBIDDEN`; the dispute stays `OPEN` — only Admin is final arbiter (`BR-RET-06`).
- Step 6 → `200 { state: "COMPLETED", escrowFrozen: false, auditId }` with the resolution and an audit row before/after (`BR-PLT-06`, `AC-FR020-03`).
- Step 7 → escrow `RELEASED` exactly once with `commission_amount_yer = 1250`, payable 13,625 YER, timeline `DELIVERED → COMPLETED` by `SYSTEM`.
- Step 8 buyer win → `200 { state: "REFUNDED", refund: { status: "PENDING" } }`; the release job then leaves escrow unreleased, the refund draws escrow-held funds first (14,875 YER, `BR-ESC-07`), commission is never booked for that sub-order, wallet credit lands within 3 business days (`BR-RET-04`), and `SUM(amount_yer) = 0`.
- The unaffected sub-order (if any) keeps settling — a freeze covers only the disputed sub-order (`BR-ORD-05`, `state-transitions.md` §4).
