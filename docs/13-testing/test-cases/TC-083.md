# TC-083 — Admin resolves a dispute for the vendor: sub-order completes and escrow releases once

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a vendor-win dispute resolution returns the sub-order to `COMPLETED` with escrow unfrozen and no buyer refund, that the master order completes when all sub-orders complete, and that the 7-day escrow then releases exactly once to vendor payable with the commission applied at release. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `DISPUTE-5513` is `OPEN` on `ORD-VND1` / `SUB-V1` (`DISPUTED`), delivered `2026-09-19T14:30:00+03:00` ⇒ `releaseEligibleAt = 2026-09-26T14:30:00+03:00`; escrow `amountHeld = 14875`, `frozenBy: "DISPUTE"`; clock `2026-09-26T12:00:00+03:00`. |
| 2 | Evidence already submitted by both parties; store `tech-store` commission tier 10 % (default, `BR-ESC-03`); payout threshold 1,000 YER. |
| 3 | Buyer `771234567` wallet **35,125 YER** (must not change); vendor `779876543` finance baseline captured; tokens: `ADMIN`, vendor, buyer. |

## Test Data

| Field | Value |
|---|---|
| admin resolve | `POST /disputes/DISPUTE-5513/resolve {"outcome":"VENDOR","reason":"delivery code proof and order timeline confirm the item matched the listing"}` |
| release probes | clock `2026-09-26T14:31:00+03:00` (release due), then a second release-job run |
| expected dispute state | `RESOLVED_VENDOR` |

## Steps
1. As `ADMIN`, `POST /disputes/DISPUTE-5513/resolve {"outcome":"VENDOR","reason":"delivery code proof and order timeline confirm the item matched the listing"}`.
2. `GET /disputes/DISPUTE-5513`; `GET /orders/ORD-VND1`; `GET /wallet/escrow?orderId=ORD-VND1`; buyer `GET /orders/ORD-VND1/refund`.
3. Advance the clock to `2026-09-26T14:31:00+03:00`; run the escrow release job; re-read `GET /wallet/escrow` and vendor `GET /store/finance/overview`.
4. Run the release job a second time (replay); re-read escrow, finance overview and the ledger feed for the release reference.
5. Buyer `GET /wallet` balance; `GET /admin/audit-log?targetId=DISPUTE-5513`.

## Expected Result
- Step 1 → `200 { state: "COMPLETED", escrowFrozen: false, resolution, auditId }` with **no** `refund` block — vendor win completes the sub-order without refunding the buyer (`API-RET-017`, `BR-RET-06`).
- Step 2 → dispute `state: "RESOLVED_VENDOR"`; sub-order `SUB-V1` `COMPLETED` and, being the only sub-order, the master order reaches `COMPLETED` (`BR-ORD-07`, `C-09`); escrow `frozenBy: "NONE"`, `releasedAt: null` (release not yet due); buyer refund receipt → `404 NOT_FOUND` (no refund exists for this order, `API-WAL-014`).
- Step 3 → escrow item `{ releasedAt: "2026-09-26T14:31:00+03:00", frozenBy: "NONE" }`, `totals.held` decreased by the full 14,875 — release happens only at `DELIVERED + 7 days` with no dispute (`BR-ESC-01`, `C-12`); finance overview: `escrowHeld` down, `availablePayable` up by `14875 − commissionYER`, `commissionRatePercent = 10` — commission is computed at release (`BR-ESC-03`); the release ledger posting is balanced (escrow debit = commission + payable credits, Σ = 0, `BR-PAY-06`).
- Step 4 → the replay changes nothing: same `releasedAt`, unchanged balances, no duplicate ledger rows — release runs exactly once (idempotent job, `BR-PAY-08`, `wallet.md` §2).
- Step 5 → buyer wallet still **35,125 YER** — vendor win never credits the buyer; audit log holds `dispute.resolve` with `outcome: "VENDOR"`, `actorRole: "ADMIN"`, reason and `correlationId` (`BR-RET-06`, `BR-PLT-06`, `SEC-REQ-010`, `AC-FR020-01`).
