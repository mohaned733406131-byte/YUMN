# TC-108 — Money-action audit rows older than the hot window stay queryable and exportable for at least 5 years

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that audit records for money actions older than the 12-month hot window — including rows past the 5-year floor — remain present, chain-verifiable, queryable through `GET /admin/audit-log` date filters and exportable through the audited admin export flow. | integration | P1 | Yes — Jest + job runner |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Seed script has appended a **closed, chain-valid** historical audit segment (self-consistent `prev_hash`/`entry_hash` range) containing money-action rows (`action = 'escrow.release'`, `entity` set) created exactly `2020-09-27` (6 years), `2022-09-27` (4 years) and `2024-09-27` (2 years) ago — all older than the 12-month hot partition (RC-03), all inside the ≥5-year floor and the 10-year RC-06 horizon. |
| 2 | Baseline: `J10` (audit hash-chain verification) reports PASS with `0` mismatches across **all** partitions including the historical segment. |
| 3 | `ADMIN` token; the audit console export flow is available (`UC-036` step 4 — CSV export of a filtered set); no other admin actions run during the test windows. `GET /readyz` → `200`. |

## Test Data

| Field | Value |
|---|---|
| aged rows | 1 row per vintage: `2020-09-27T10:00:00Z`, `2022-09-27T10:00:00Z`, `2024-09-27T10:00:00Z` — all `action = 'escrow.release'` |
| query 6-year window | `GET /admin/audit-log?action=escrow.release&from=2020-09-27T00:00:00Z&to=2020-09-28T00:00:00Z&limit=50` |
| query 4-year window | `?action=escrow.release&from=2022-09-27T00:00:00Z&to=2022-09-28T00:00:00Z&limit=50` |
| query 2-year window | `?action=escrow.release&from=2024-09-27T00:00:00Z&to=2024-09-28T00:00:00Z&limit=50` |
| export | audit console, same 6-year filter as the CSV export scope |

## Steps
1. SQL: count and read the seeded aged rows; verify `prev_hash`, `entry_hash`, `seq`, `created_at` per row; record the exact row ids.
2. Run `J10` over all partitions.
3. As `ADMIN`, issue the three date-windowed `GET /admin/audit-log` queries; capture items and `page` objects.
4. Record `t2`; run the admin audit export for the 6-year filter (CSV, `UC-036` step 4); capture the artifact; record `t3`.
5. SQL: count audit rows by this `ADMIN` actor with `created_at` in `[t2, t3]`; open the exported artifact and locate the seeded `2020-09-27` rows by id.

## Expected Result
- Step 1 → all three aged rows exist with non-null `prev_hash`/`entry_hash` — rows outside the hot window were archived, never row-deleted, inside retention (`audit_log.md` §Invariants DB-enforced 3: retention drops/archives whole partitions, never row-deletes inside the ≥5-year window; `DATA-REQ-003` R4, `NFR-019`).
- Step 2 → `J10` reports PASS, `0` mismatches — the historical segment is still chain-verifiable (`SEC-REQ-010` R4).
- Step 3 → each query returns `200 { items, page }` containing the matching seeded row(s) with the documented projection (`id`, `at`, `action`, `targetType`, `targetId`, `correlationId` — `API-ADM-024`, `UC-036`); the 6-year-old row is returned by the 2020 window — records older than the current window remain **queryable** per the ≥5-year retention configuration (`AC-SR010-04`).
- Step 4 → the export artifact (CSV) is produced for the filtered set and contains the `2020-09-27` row ids — the records remain **exportable** (`AC-SR010-04`, `UC-036` step 4); UC-036's "older archived entries served from cold storage if within retention" path (A3) is what the query exercises.
- Step 5 → exactly **1** new audit row by this admin in `[t2, t3]` — the export itself is audited (`UC-036` postcondition, `BR-PLT-06`, `SEC-REQ-010` R2); no other rows were written in the window.
