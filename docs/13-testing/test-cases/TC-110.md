# TC-110 — Platform settings take effect per documented precedence and role changes apply immediately, audited

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a Super Admin settings change (commission default) survives schema bounds and optimistic locking and is picked up by subsequent transactions per the configuration hierarchy, and that role grant/revoke by Super Admin takes effect immediately for the target account, is refused for everyone else, never demotes the final Super Admin, and every success is audited. | integration | P0 | Yes — Jest + Supertest + BullMQ test clock |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Tokens: `SUPER_ADMIN`, `ADMIN` (`770000001`/`770000002`, TC-060 fixture), `MODERATOR`. Reserved-block customer `791100003` (base `CUSTOMER`, no staff roles). Two seeded Super Admin personas exist (two-per-role rule, `test-data-and-environments.md` §3.4) so `LAST_SUPER_ADMIN` can be exercised without locking the environment out. |
| 2 | `commission.defaultRate` = `10`, version `v0 = 3`; store `tech-store` (`st-tech-01`) has `commission.source = "PLATFORM_DEFAULT"`. |
| 3 | Release fixture: sub-order `SUB-110A` in order `ORD-110A` `DELIVERED` with escrow `HELD` (14,875 YER: 12,500 items + 1,875 VAT + 500 shipping, no coupon), release-eligible 7 days after delivery; test clock controllable; queue `b07.escrow.release` triggerable. |
| 4 | `GET /readyz` → `200`. |

## Test Data

| Field | Value |
|---|---|
| band violation | `PUT /admin/settings/commission.defaultRate {"value":25,"expectedVersion":3}` → expect `400 VALIDATION_ERROR` |
| wrong role | same body with the plain `ADMIN` token → expect `403 FORBIDDEN` |
| valid write | `{"value":12,"expectedVersion":3}` → `200 { value: 12, version: 4, auditId }` |
| stale write | `{"value":12,"expectedVersion":3}` again → expect `409 SETTINGS_VERSION_CONFLICT` |
| release math | base `12500` × 12 % → `commission_amount_yer = 1500`, `commission_rate_bps = 1200`, payable `14875 − 1500 = 13375` |
| role grant | `POST /admin/users/791100003/role` `{"role":"MODERATOR","reason":"TC-110 immediacy probe"}` |
| role revoke | `DELETE /admin/users/791100003/role?role=MODERATOR&reason=TC-110%20revert` |

## Steps
1. Record the current `commission.defaultRate` value/version (`10` / `3`).
2. `ADMIN` attempt the valid write body → capture status/code.
3. `SUPER_ADMIN` attempt `value: 25`; then the valid `value: 12` write; then the stale `expectedVersion: 3` replay; capture codes and versions.
4. Read `GET /admin/stores/st-tech-01`; advance the clock 7 days past `SUB-110A`'s delivery, run `b07.escrow.release`; read `GET /wallet/escrow?orderId=ORD-110A`.
5. Revert `commission.defaultRate` to `10` (`expectedVersion: 4`).
6. `791100003` call `GET /admin/users` → capture status (baseline deny).
7. `ADMIN` attempt the role grant; `SUPER_ADMIN` perform the role grant; **immediately** `791100003` call `GET /admin/users` again — no reseed, no restart.
8. `SUPER_ADMIN` revoke `MODERATOR`; immediately `791100003` call `GET /admin/users` again.
9. Super Admin persona A revoke persona B's `SUPER_ADMIN` role; then attempt to revoke persona A's `SUPER_ADMIN` (the final one); re-grant persona B's `SUPER_ADMIN` to restore the baseline.
10. SQL by the captured `auditId`s; re-run `J10`.

## Expected Result
- Step 2 → `403 FORBIDDEN` — platform settings writes are `SUPER_ADMIN`-only (`API-ADM-023`, `rbac.md` row 24, `UC-035`).
- Step 3 → `value: 25` → `400 VALIDATION_ERROR` (commission tier must stay 5–20, `API-ADM-023`, `BR-ESC-03`); `value: 12` → `200 { key, value: 12, version: 4, auditId }`; stale replay → `409 SETTINGS_VERSION_CONFLICT` with the version unchanged at `4` — the rejected write persisted nothing (optimistic locking, `UC-035`).
- Step 4 → `st-tech-01` shows `tierPercent: 12` for the default-tier store (the DB setting layer now governs — configuration hierarchy layer 5, `configuration.md` §1, `CFG-3`: constraint-encoded values are not among the writable settings); after `b07.escrow.release`: escrow `RELEASED`, `commission_rate_bps = 1200`, `commission_base_yer = 12500`, `commission_amount_yer = 1500`, payable credit `13375` YER — the **subsequent transaction** ran with the new value, not the compiled default of 10 % (`AC-FR020-04`, `BR-ESC-03`); commission is booked once at release.
- Step 5 → `200 { value: 10, version: 5 }` — environment restored.
- Step 6 → `403 FORBIDDEN` for the unprivileged account (baseline).
- Step 7 → `ADMIN` grant → `403 ROLE_ASSIGNMENT_FORBIDDEN` (sole Super Admin capability, `API-ADM-025`, `rbac.md` row 23); `SUPER_ADMIN` grant → `200 { id, roles: [ …, "MODERATOR" ], auditId }`; the very next request by `791100003` returns `200` from `GET /admin/users` — role changes apply **immediately**, with no reseed or session restart (`AC-FR020-04`, `API-ADM-001`).
- Step 8 → `200 { id, roles: [ … ] }` without `MODERATOR`; the immediate follow-up returns `403 FORBIDDEN` — revocation is equally immediate.
- Step 9 → persona B demotion → `200` (another Super Admin remains); final-Super-Admin demotion → `409 LAST_SUPER_ADMIN` (`API-ADM-026`, `UC-037`) and persona A keeps `SUPER_ADMIN`; re-grant → `200` restoring two Super Admins.
- Step 10 → exactly **one** audit row per successful call — the band-violated, stale and forbidden attempts create **no** change row (nothing persisted): each success row has `actor_user_id`/`actor_role = 'SUPER_ADMIN'`, non-null `action`, `entity` (settings rows: `entity_id IS NULL`; role rows: target user), both `before`/`after` snapshots (settings: old/new value; roles: old/new role set), non-null `ip`, `created_at` in-window, `correlation_id` (`BR-PLT-06`, `AC-FR020-01`); `J10` reports PASS with `0` mismatches.
