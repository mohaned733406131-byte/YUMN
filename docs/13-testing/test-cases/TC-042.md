# TC-042 — Concurrent checkout race on the last unit: one winner, clean loser, zero oversell, zero orphan hold

| Field | Value |
|---|---|
| Objective | Verify that two simultaneous confirmations for the last available unit resolve to exactly one `201` and one clean `422 STOCK_UNAVAILABLE`, with no oversold stock, no duplicate debit, no orphan authorization hold and a balanced ledger. |
| Level | integration |
| Priority | P0 |
| Automation | Yes — Jest + Supertest (`Promise.all` over both confirmations, 20-iteration soak loop) |

## Preconditions
- Product `PRD-LAST` stock on hand = 1, no active reservations; both buyers' wallets funded for the full total.
- Two independent checkout sessions created at the same instant (distinct `Idempotency-Key`s).
- Ledger and escrow tables empty for these orders; invariant harness ready (`Σ ledger = 0`).

## Test Data

| Field | Value |
|---|---|
| Buyers | `771234567` (A) keys `chk-042-a`/`ord-042-a`; `779001122` (B) keys `chk-042-b`/`ord-042-b` |
| Totals | `6000` + VAT `900` + shipping `500` = `7400` YER each |
| Balances | `50000` each; expected winner balance `42600` |

## Steps
1. Seed stock = 1; create session A and session B for `PRD-LAST` ×1 (both see `shortfall 0`).
2. Fire both `POST /orders` calls concurrently via `Promise.all`, each with its own key and its own `checkoutSessionId`.
3. Record both responses (status, `error.code`, `orderId`).
4. Read stock (`on_hand`, `reserved`), both wallets, all ledger rows, escrow rows and authorization holds.
5. Repeat the winner's `POST /orders` byte-identically with the same key.
6. Run steps 1–5 twenty times in a loop and tally winners/losers; then run the daily reconciliation assertion.

## Expected Result
- Step 2 → exactly one `201 {masterState:"PLACED", …}` and one `422` with `error.code = STOCK_UNAVAILABLE`, `retryable:false` — the loser fails cleanly with a `correlationId`.
- Step 4 → stock `on_hand = 0`, `reserved = 0` (never negative, `BR-CAT-07`); winner debited `7400` once, loser debited **0** times; escrow holds exist only for the winner's order; the loser's authorization hold is `RELEASED` (no orphan hold, `API-WAL-008`).
- Ledger → `SUM(amount) = 0`, exactly one capture pair (`BR-PAY-06`, `AC-S-14`).
- Step 5 → the original order is returned with the original status code and **no** second debit (`BR-ORD-06`, `BR-PAY-08`, `AC-FR011-02`).
- Step 6 → 20 runs yield 20 winners, 20 losers, 20 units sold from a stock of 1 each round; zero oversold rows, zero orphan holds, zero duplicate side effects (`AC-NFR-008-02`, `AC-S-15`).
- No response exposes stack traces or internal identifiers (`SEC-REQ-008`).
