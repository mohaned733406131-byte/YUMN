# TC-081 — Opening a dispute freezes only the affected sub-order's escrow

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a buyer-opened dispute moves the sub-order to `DISPUTED`, sets `escrowFrozen: true` and `frozenBy: "DISPUTE"`, blocks the 7-day escrow release while frozen, isolates the freeze to the affected sub-order only, and refuses duplicates, missing grounds and cross-tenant access. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `ORD-7F3A21` / `SUB-9C1104` is `DELIVERED` at `2026-09-19T14:30:00+03:00`; escrow `amountHeld = 14875`, `releaseEligibleAt = 2026-09-26T14:30:00+03:00`, `frozenBy: "NONE"`, `releasedAt: null`; clock `2026-09-26T10:00:00+03:00`. |
| 2 | `ORD-MULTI` has two delivered sub-orders `SUB-M1` and `SUB-M2` (both `releaseEligibleAt = 2026-09-27T09:00:00+03:00`, `frozenBy: "NONE"`) for the isolation check; `ORD-NOG1` is delivered with no dispute for the missing-ground probe. |
| 3 | Buyer `771234567` owns all seeds; customer `771234568` owns none; tokens for buyer, `771234568`, and `ADMIN` seeded. |

## Test Data

| Field | Value |
|---|---|
| dispute | `POST /orders/ORD-7F3A21/dispute {"subOrderId":"SUB-9C1104","ground":"NOT_AS_DESCRIBED","note":"scratches on frame","imageFileIds":["f-101","f-102"]}` |
| missing ground | `POST /orders/ORD-NOG1/dispute {"subOrderId":"SUB-NOG1"}` → expect `422 EVIDENCE_REQUIRED` |
| expected disputeId | `DISPUTE-5512` |

## Steps
1. Buyer `771234567` submits the dispute body above.
2. Submit the same body again (duplicate); then `POST /orders/ORD-NOG1/dispute {"subOrderId":"SUB-NOG1"}` (no ground/evidence).
3. `GET /wallet/escrow?orderId=ORD-7F3A21`; `GET /orders/ORD-7F3A21` (sub-order state); `GET /disputes/DISPUTE-5512` as buyer.
4. Advance the clock to `2026-09-27T10:00:00+03:00` (past `releaseEligibleAt`) and run the escrow release job.
5. On `ORD-MULTI`, dispute only `SUB-M1`; re-read `GET /wallet/escrow?orderId=ORD-MULTI`; advance the clock to `2026-09-27T09:01:00+03:00` and run the release job again.
6. As customer `771234568`, `POST /orders/ORD-7F3A21/dispute` with a valid body, then `GET /disputes`; as buyer, `GET /disputes?limit=20`.

## Expected Result
- Step 1 → `201 { disputeId: "DISPUTE-5512", state: "DISPUTED", escrowFrozen: true, evidenceDueBy }` — sub-order `DELIVERED → DISPUTED` inside the 17-state machine (`API-RET-013`, `C-09`).
- Step 2 → `409 DISPUTE_ALREADY_OPEN` for the duplicate; `422 EVIDENCE_REQUIRED` for the groundless request — no dispute row created (`API-RET-013`).
- Step 3 → escrow item `{ subOrderId: "SUB-9C1104", frozenBy: "DISPUTE", releasedAt: null }`; sub-order state `DISPUTED` (`BR-ORD-05`); dispute detail `200` with `ground`, `evidence: []`, `timeline` for the opener only (`BR-ORD-09`).
- Step 4 → after the 7-day mark passes, `releasedAt` stays `null` — no release, no payout while disputed (`BR-ESC-02`, `BR-ORD-05`); buyer wallet unchanged (no premature refund).
- Step 5 → `SUB-M1` shows `frozenBy: "DISPUTE"` while `SUB-M2` stays `frozenBy: "NONE"`; after its `releaseEligibleAt`, `SUB-M2.releasedAt` is set — the freeze touches only the affected sub-order (`state-transitions.md` §4, `BR-ORD-05`).
- Step 6 → the foreign customer gets `404 NOT_FOUND` on the write (`DATA-REQ-008`); buyer's own list contains only `DISPUTE-5512` and `ORD-MULTI`'s dispute (`API-RET-014`, `BR-ORD-09`); parties and admin receive the dispute-opened notification (`BR-NTF-01`, `BR-NTF-04`).
