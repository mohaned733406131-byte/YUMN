# TC-029 — Cart guard ladder rejects the 6th vendor, 11th unit and 51st product without partial mutation

| Field | Value |
|---|---|
| Objective | Verify that `POST /cart/items` / `PATCH /cart/items/{id}` enforce ≤5 vendors, ≤10 units per product and ≤50 distinct products in ladder order, each rejection leaving the cart byte-identical. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (cart-limit fixtures 50/51 and 5/6 vendors from DOC-TST-005) |

## Preconditions
- Authenticated customer `771234567` with an empty cart.
- Seed data: ≥ 7 products across 6 distinct stores, each with `stock ≥ 20`; ≥ 51 distinct products available for the product-count probe.
- All products are ACTIVE, in stock, in-policy.

## Test Data

| Field | Value |
|---|---|
| Customer | `771234567` |
| Stores | `STORE-1` … `STORE-6` |
| Unit-limit probe | quantity `11` for a product already at `10` |
| Product-count probe | the 51st distinct product |
| Vendor-count probe | first product of `STORE-6` with 5 vendors already present |

## Steps
1. `POST /cart/items` five times, one product from each of `STORE-1`…`STORE-5`; `GET /cart` and snapshot.
2. `POST /cart/items` with a product from `STORE-6`.
3. `PATCH /cart/items/{line}` to `quantity: 10`, then to `quantity: 11`.
4. Seed `POST /cart/items` until the cart holds 50 distinct products (across ≤5 vendors); attempt the 51st.
5. Attempt to add an `INACTIVE` product and an out-of-stock product.
6. Re-read `GET /cart` and diff against the snapshots.
7. Repeat steps 2–4 but with a *guest* client-side cart attempt (no token) to confirm the guard is server-side only.

## Expected Result
- Step 1: five `201`s; `GET /cart` shows `distinctStores: 5`, `distinctProducts: 5`, correct per-store groupings.
- Step 2 returns `422 MAX_VENDORS_EXCEEDED` with `details: { limit: 5, current: 5 }` (`AC-FR010-01`, `C-15`).
- Step 3: `quantity: 10` → `200`; `quantity: 11` → `422 UNIT_LIMIT_EXCEEDED` and the stored quantity stays `10` (`AC-FR010-02`).
- Step 4: the 51st add returns `422 CART_LIMIT_EXCEEDED` (`BR-CRT-01`) — the count stays `50`.
- Step 5: inactive → `404 NOT_FOUND` (or `422 CART_ITEM_INELIGIBLE` when it becomes ineligible after being added); out of stock → `422 STOCK_UNAVAILABLE`.
- Step 6: after every rejection the cart snapshot is **byte-identical** — violations never partially mutate the cart (guard ladder, `BR-CRT-01`); the first violated guard decides the code.
- Step 7: unauthenticated calls return `401 AUTH_INVALID` — guards run server-side; client-side checks are UX only (`SEC-REQ-004`).
- All cart responses carry `Cache-Control: no-store`.
