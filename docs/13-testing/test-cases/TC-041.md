# TC-041 — Stock reservation TTL expiry during checkout blocks the order and never funds escrow

| Field | Value |
|---|---|
| Objective | Verify that when the 15-minute checkout reservation expires the confirmation is refused (`CHECKOUT_SESSION_EXPIRED`), and that a concurrent buyer consuming the released stock yields `STOCK_UNAVAILABLE` — in both cases no order row, no wallet debit and no escrow hold is created. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (injectable clock for the 15-minute TTL, no wall-clock sleeps) |

## Preconditions
- Product `PRD-LAST` (6,000 YER) has on-hand stock **1**; buyer `771234567` and rival buyer `779001122` both hold funded wallets.
- Clock injection available; `MockPaymentAdapter` idle; no orders exist for either buyer.

## Test Data

| Field | Value |
|---|---|
| Session A | buyer `771234567`, key `chk-041-01`, created at `T0`, `expiresAt = T0 + 15 min` |
| Confirm key | `ord-041-01` |
| Rival | buyer `779001122`, keys `chk-041-02`, `ord-041-02` |
| Totals | `6000` + VAT `900` + shipping `500` = `7400` YER each |

## Steps
1. Buyer A: `POST /checkout/session` (`chk-041-01`) → `201`; record `expiresAt` and `reserved` stock.
2. Advance the injected clock to `T0 + 15:01`; `POST /orders` (`ord-041-01`) with the original session id.
3. Assert stock row: `on_hand`, `reserved` after the TTL sweep, plus `orders`/`wallet_transaction`/`b07.escrow` counts and buyer A's balance.
4. Reset clock; buyer A builds a **fresh** session (`chk-041-01b`) while buyer B concurrently completes checkout on the same last unit (`ord-041-02`) → `201`.
5. Buyer A then `POST /orders` (`ord-041-01b`) on the fresh session.
6. Re-read both wallets, the stock row and escrow rows.

## Expected Result
- Step 2 → `409` `error.code = CHECKOUT_SESSION_EXPIRED`, `retryable:true` — reservation/session older than 15 minutes (`C-13`, `API-ORD-002`).
- Step 3 → after TTL expiry the reservation is released (`reserved 0`); **0** order rows, **0** ledger rows, **0** escrow rows; buyer A balance unchanged — escrow is never funded for a failed confirmation.
- Step 4 → buyer B receives `201`, stock goes `1 → 0` atomically with a permanent deduction (`BR-CAT-07`).
- Step 5 → buyer A receives `422 STOCK_UNAVAILABLE` (`BR-CAT-07`), `retryable:false`.
- Step 6 → buyer A balance unchanged with **0** debits; buyer B debited exactly `7400`; exactly **1** escrow hold (buyer B's); `SUM(ledger) = 0`; stock never negative.
- Both error bodies carry `messageKey errors.<CODE>` and `correlationId`.
