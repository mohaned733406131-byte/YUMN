# TC-113 — Health gating: /healthz ignores dependencies, /readyz gates on required checks and degrades without failing

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that `/healthz` stays `200` during a database outage and reports `503` during shutdown, that `/readyz` returns `503` with names-only check detail when a required dependency is down, that a degraded Elasticsearch flips readiness to `READY_DEGRADED` without failing it, and that both probes answer in under 1 second. | integration | P1 | Yes — Jest + compose chaos harness |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Full stack running via `docker compose` (local environment, `test-data-and-environments.md` §1); the harness can stop/start the `postgres` and `elasticsearch` containers and send `SIGTERM` to the `api` container. |
| 2 | Baseline healthy: `GET /healthz` → `200`, `GET /readyz` → `200` with all required checks `UP`. |
| 3 | Both endpoints are public (no token) and never cached (`Cache-Control: no-store`, `admin.md` §5). |

## Test Data

| Field | Value |
|---|---|
| probes | `GET /healthz` · `GET /readyz` (timed, unauthenticated) |
| required-dependency outage | stop container `postgres` → probe both endpoints |
| degraded dependency | stop container `elasticsearch` → `GET /readyz` |
| shutdown | `SIGTERM` to `api` → probe during the drain window (`stop_grace_period: 60s`) |

## Steps
1. Time and capture `GET /healthz` and `GET /readyz`; record `durationMs` and both bodies.
2. Stop `postgres`; re-probe `/healthz` then `/readyz`; capture status codes and the `/readyz` body verbatim; search the body for hostnames, ports, credentials.
3. Restart `postgres`; `GET /readyz` until green; capture the recovered body.
4. Stop `elasticsearch`; `GET /readyz`; capture body; restart `elasticsearch`; `GET /readyz`.
5. Send `SIGTERM` to `api`; during the drain window `GET /healthz` and `/readyz`; after restart `GET /readyz`.

## Expected Result
- Step 1 → `/healthz` → `200 { status: "UP", version, uptimeSeconds }` with `version` non-empty (deployed build is assertable); `/readyz` → `200 { status: "READY", checks: [ { name, status: "UP", latencyMs }… ] }` including the required Postgres, Redis and BullMQ checks; each probe `durationMs < 1000` (`API-ADM-042/043`, `BR-PLT-07`, `AC-NFR-020-01`, health-checks §1).
- Step 2 → `/healthz` **still `200`** — liveness runs no dependency checks, so a DB outage cannot restart-loop healthy app processes (health-checks §1 rule, `C-26` defense); `/readyz` → `503 SERVICE_UNAVAILABLE` with per-check detail showing the Postgres check `DOWN` (`API-ADM-043`, `NFR-007`); the 503 body carries check **names only** — no hostnames, ports or credentials anywhere in the payload (`SEC-REQ-008`, health-checks §1 "503 never leaks internals").
- Step 3 → `/readyz` returns to `200 { status: "READY", … }` once the required check recovers (edge upstream re-enables after a successful probe, health-checks §3.2).
- Step 4 → `/readyz` → `200` with `status: "READY_DEGRADED"` and the Elasticsearch check reported `DEGRADED` — a non-gating dependency never fails readiness (`health-checks` §2, `API-ADM-043`, `AC-NFR-007-01`); **not** `503`.
- Step 5 → during the drain `/healthz` → `503 SERVICE_UNAVAILABLE` so the edge stops routing to the draining instance (health-checks §1 shutdown awareness, §5); after restart `/readyz` is green before traffic resumes (health-checks §5).
