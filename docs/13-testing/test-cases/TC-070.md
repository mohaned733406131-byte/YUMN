# TC-070 — First two wrong code entries report remaining attempts without delivering

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that the 1st and 2nd wrong code submissions return `422 CODE_INVALID` with `attemptsRemaining` 2 then 1, never deliver the order, do not re-issue or reset the buyer's code, and that a correct submission inside the 3-attempt budget still delivers. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `DLV-4471` is `OUT_FOR_DELIVERY` with freshly issued code `482913`; `code.attemptsUsed = 0`, no lock; sub-order `SUB-9C1104` is `OUT_FOR_DELIVERY`. |
| 2 | Courier `790000011` is the assignee and holds an active token; buyer `771234567` is reachable in-app. |
| 3 | Notification outbox for the delivery-code event contains exactly one entry (the original issuance from `TC-068`). |

## Test Data

| Field | Value |
|---|---|
| delivery / order | `DLV-4471` / `ORD-7F3A21` / `SUB-9C1104` |
| wrong guesses | `000000` (attempt 1), `111111` (attempt 2) |
| correct code | `482913` |
| expected attempts | `attemptsRemaining` 2 after attempt 1, 1 after attempt 2 |

## Steps
1. As courier `790000011`, `POST /deliveries/DLV-4471/code {"code":"000000"}` → capture the error envelope.
2. `GET /deliveries/DLV-4471` → inspect `state`, `code.attemptsUsed`, `code.lockedUntil`.
3. As buyer `771234567`, `GET /orders/ORD-7F3A21/delivery-code`; then courier `POST /deliveries/DLV-4471/out-for-delivery` to resume the final leg; buyer reads the code again; check the notification outbox for a second code issuance.
4. As courier, `POST /deliveries/DLV-4471/code {"code":"111111"}` → capture the error envelope.
5. `GET /deliveries/DLV-4471` again → inspect `state`, `code.attemptsUsed`, `code.lockedUntil`.
6. Courier `POST /deliveries/DLV-4471/out-for-delivery`, then `POST /deliveries/DLV-4471/code {"code":"482913"}`.

## Expected Result
- Step 1 → `422 CODE_INVALID`, `retryable: true`, `details.attemptsRemaining = 2`; sub-order stays short of `DELIVERED` (`BR-ORD-08`).
- Step 2 → `state: "IN_TRANSIT"` — a failed code entry returns the delivery to transit for a later retry (`workflow-005` step 7, `business-processes.md` fulfilment failure path); `code.attemptsUsed = 1`; `code.lockedUntil` absent (no lock before the 3rd failure — `BR-SHP-03`).
- Step 3 → buyer still sees `code: "482913"` with `attemptsRemaining: 2`; re-entry returns `200 { state: "OUT_FOR_DELIVERY", version }`; no second code notification is emitted and the buyer's code is unchanged — one code per delivery, attempt budget persists across re-entries (`BR-SHP-02`, `BR-SHP-03`).
- Step 4 → `422 CODE_INVALID`, `retryable: true`, `details.attemptsRemaining = 1`.
- Step 5 → `state: "IN_TRANSIT"`, `code.attemptsUsed = 2`, still no lock; never `DELIVERED`.
- Step 6 → re-entry `200 { state: "OUT_FOR_DELIVERY", version }`, then `200 { state: "DELIVERED", version, deliveredAt, proof: { code: true, courierId, verifiedAt } }` — a correct code inside the budget delivers (`AC-FR015-02`); escrow hold starts per `TC-069`.
