# TC-080 — Refund composition, wallet credit within 3 business days, and idempotent execution

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a buyer-side-fault refund credits exactly the item value (shipping excluded) to the buyer's wallet within 3 business days of `REFUNDED`, exactly once (idempotent replay, balanced ledger), while a platform/vendor-fault refund includes shipping, escrow absorbs the refund first, and vendor finance reports the refunds. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `RET-8852` (order `ORD-7F3A21`, `SUB-9C1104`, buyer-fault reason) is `REFUNDED` at `2026-09-26T11:00:00+03:00`; itemValue 12,500 YER, shipping 500 YER; buyer wallet balance **35,125 YER**; escrow `amountHeld = 14875`, `releasedAt: null`. |
| 2 | `RET-8853` (order `ORD-7F3A27`, `SUB-9C1111`, vendor-fault reason `VENDOR_DELAY`) is already `CREDITED` — its refund receipt shows the shipping-inclusive composition. |
| 3 | Credit scheduler (BullMQ) runs on demand in tests; store `tech-store` commission tier 10 % (default, `BR-ESC-03`); ledger is append-only. |

## Test Data

| Field | Value |
|---|---|
| buyer-fault refund | `amount = 12500`, `shippingRefunded = false` |
| vendor-fault refund | `amount = 13000` (12,500 + 500), `shippingRefunded = true` |
| wallet | before 35,125 → expected after 47,625 YER |
| escrow | before `held = 14875` → expected after `held = 2375` (refund draws escrow first) |

## Steps
1. As buyer `771234567`, `GET /orders/ORD-7F3A21/refund` → capture `status`, `amount`, `shippingRefunded`, `expectedCreditBy`.
2. Run the credit job; `GET /orders/ORD-7F3A21/refund` again; `GET /wallet` (balance) and the ledger feed for the refund reference.
3. Re-run the credit job a second time (replay); re-read balance, refund receipt and ledger rows for the same reference.
4. `GET /orders/ORD-7F3A27/refund` (vendor-fault composition).
5. `GET /wallet/escrow?orderId=ORD-7F3A21`; as vendor `779876543`, `GET /store/finance/overview?from=2026-09-01&to=2026-09-30`.

## Expected Result
- Step 1 → `200 { subOrders: [ { subOrderId: "SUB-9C1104", status: "PENDING", amount: 12500, itemValue: 12500, shippingRefunded: false, expectedCreditBy } ] }` — refund amount = item value; shipping excluded for buyer-side fault (`BR-RET-03`, `API-WAL-014`); `expectedCreditBy` = REFUNDED + ≤3 business days (`BR-RET-04`, `AC-FR016-04`).
- Step 2 → `status: "CREDITED"`, `walletCredit: { reference, creditedAt }` with `creditedAt ≤ expectedCreditBy` (≤3 business days of `REFUNDED`); wallet balance **47,625 YER** (35,125 + 12,500); ledger holds exactly one refund credit plus its balanced counter-entry — Σ of the posting = 0 (`BR-PAY-06`, `BR-PAY-07`).
- Step 3 → balance unchanged at **47,625 YER**, same `walletCredit.reference`, no additional ledger rows — refund execution is idempotent (`BR-PAY-08`, `returns.md` §3).
- Step 4 → `amount: 13000`, `shippingRefunded: true`, `status: "CREDITED"` — shipping is refunded when the fault is platform/vendor-side (`BR-RET-03`).
- Step 5 → escrow `totals.held = 2375` (14,875 − 12,500) with `releasedAt: null` — the refund drew escrow first and no payout ran (`BR-ESC-07`, `BR-RET-07`); vendor finance `period.refundsYER = 12500`, `commissionRatePercent = 10` — commission is charged only at release, so none is taken on the refunded amount (`BR-ESC-03`).
