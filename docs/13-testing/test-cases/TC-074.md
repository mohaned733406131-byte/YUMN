# TC-074 — Return request accepted inside the window (day 0, deadline instant, and 14-day policy from COMPLETED)

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a return request on a delivered sub-order is accepted while the window is open (including the exact deadline instant), that the window equals `deliveryConfirmedAt + product.returnPeriodDays`, and that a `COMPLETED` sub-order with a 14-day policy accepts a day-10 request. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | `ORD-7F3A21` / `SUB-9C1104` is `DELIVERED` at `2026-09-19T14:30:00+03:00`; product `isReturnable: true`, `returnPeriodDays: 7` ⇒ deadline `2026-09-26T14:30:00+03:00`; orderItemId `OI-9C1104-1`, qty 1, itemValue 12,500 YER, shipping 500 YER. |
| 2 | Seed `ORD-7F3A22` / `SUB-9C1105` delivered at the same instant (7-day product) for the deadline-boundary probe; no return open on it yet. |
| 3 | Seed `ORD-9B4402` / `SUB-2D7781` is `COMPLETED` (escrow released), delivered `2026-09-20T12:00:00+03:00`, product `returnPeriodDays: 14` ⇒ deadline `2026-10-04T12:00:00+03:00`. |
| 4 | Buyer `771234567` owns all three orders; vendor `779876543` owns the stores; controllable test clock. |

## Test Data

| Field | Value |
|---|---|
| main case | `ORD-7F3A21` / `SUB-9C1104` / `OI-9C1104-1`, reasonCode `CHANGED_MIND` |
| clock probes | `2026-09-26T10:00:00+03:00` (day 7), `2026-09-26T14:30:00+03:00` (exact deadline), `2026-09-30T09:00:00+03:00` (day 10 of 14) |
| expected returnIds | `RET-8841`, `RET-8842`, `RET-8843` |

## Steps
1. Clock `2026-09-26T10:00:00+03:00`; buyer `POST /orders/ORD-7F3A21/returns {"items":[{"orderItemId":"OI-9C1104-1","quantity":1,"reasonCode":"CHANGED_MIND","note":"no longer needed"}],"reasonCode":"CHANGED_MIND"}`.
2. `GET /returns/RET-8841` and `GET /returns?limit=20` (own feed); read the notification outbox for buyer and vendor.
3. Clock `2026-09-26T14:30:00+03:00` exactly; repeat the same request against `ORD-7F3A22` (`RET-8842`).
4. Clock `2026-09-30T09:00:00+03:00`; same request shape against `ORD-9B4402` / `OI-2D7781-1` (`RET-8843`).
5. As vendor `779876543`, `GET /store/returns?page=1`; as unrelated customer `771234568`, `GET /returns/RET-8841`.

## Expected Result
- Step 1 → `201 { returnId: "RET-8841", subOrderId: "SUB-9C1104", state: "RETURN_REQUESTED", window: { deliveryAt: "2026-09-19T14:30:00+03:00", deadline: "2026-09-26T14:30:00+03:00", daysRemaining: 0 }, refundEstimate: { itemValue: 12500, shippingRefundable: false } }` — window = delivery confirmation + `returnPeriodDays` (`BR-RET-01`, `C-11`, `AC-FR016-01`); shipping excluded for a buyer-side reason (`BR-RET-03`).
- Step 2 → detail `200` with `policy: { isReturnable: true, returnPeriodDays: 7, windowDeadline: "2026-09-26T14:30:00+03:00" }` and a timeline entry; own feed shows the item with `decisionDueAt = openedAt + 48h` (vendor decision SLA, `returns.md` §2); buyer and vendor each get one notification in Arabic (`BR-NTF-04`).
- Step 3 → `201` — the request at the exact deadline instant is still inside the window (only an *elapsed* window is rejected, `BR-RET-01`).
- Step 4 → `201 { returnId: "RET-8843", window: { deliveryAt: "2026-09-20T12:00:00+03:00", deadline: "2026-10-04T12:00:00+03:00", daysRemaining: 4 } }` — a `COMPLETED` sub-order is an eligible origin state (`API-RET-001`) and the window follows that product's 14-day policy.
- Step 5 → vendor queue lists the three returns with `overdue: false`; the foreign customer gets `404 NOT_FOUND` (`DATA-REQ-008`, `BR-ORD-09`).
