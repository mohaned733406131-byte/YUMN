# TC-014 — Direct API bypass with forged tokens or tampered clients is denied server-side

| Field | Value |
|---|---|
| Objective | Verify that authorization is decided only by the server: forged or tampered JWTs, hand-crafted role claims and a banned client are all rejected without relying on any frontend guard. |
| Level | integration |
| Priority | P0 (merge-blocking, also runs under SEC-P-05) |
| Automation | Yes — Jest + Supertest |

## Preconditions
- A valid customer access token exists for `771234567` (baseline).
- The JWT signing key (RS256 private key) is **not** available to the test — forging must use a wrong/self-generated key.
- User `775550001` is `SUSPENDED` (banned) but still holds an unexpired access token issued before the ban.
- `GET /admin/users` is the protected target route.

## Test Data

| Field | Value |
|---|---|
| Valid customer token | issued normally for `771234567` |
| Forged token | HS256 self-signed with secret `"attacker"`, claim `roles:["ADMIN"]` |
| Tampered token | genuine token with payload edited to `roles:["ADMIN"]`, original signature kept |
| Banned user | `775550001` with pre-ban token |

## Steps
1. `GET /admin/users` with no `Authorization` header.
2. `GET /admin/users` with `Authorization: Bearer <forged HS256 token>`.
3. `GET /admin/users` with `Authorization: Bearer <tampered RS256 token, payload edited>`.
4. `GET /orders` with the tampered customer token (any authenticated route).
5. `GET /wallet` with the banned user's pre-ban but unexpired token.
6. `POST /orders` with a hand-built body adding `"roles":["ADMIN"]` as a body field instead of a claim.
7. Replay steps 2–5 while asserting no request reaches business-logic handlers (check server logs).

## Expected Result
- Step 1 returns `401 AUTH_INVALID` with `WWW-Authenticate: Bearer error="invalid_token"`.
- Step 2 returns `401 TOKEN_INVALID` (algorithm/`kid` mismatch) — an attacker-chosen algorithm never validates.
- Step 3 returns `401 TOKEN_INVALID` — signature verification fails after payload edit; the injected `ADMIN` claim is ignored.
- Step 4 returns `401 TOKEN_INVALID` — tampering invalidates the token on any route.
- Step 5 returns `403 FORBIDDEN` (account suspended) — server-side identity state is re-checked per request, not trusted from the token age alone.
- Step 6 returns `200/201` only with the caller's real role; a body field can never elevate privileges (it is not a claim).
- Steps 2–5 produce no business-logic side effects: zero rows written, zero orders created, zero ledger entries.
- Every rejection carries a `correlationId` and never echoes token material or stack traces (`SEC-REQ-008`).
