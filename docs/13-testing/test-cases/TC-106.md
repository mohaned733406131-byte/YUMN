# TC-106 — Manual alteration or deletion of an audit row fails the chain verification and raises an alert

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that tampering with the audit trail outside the application role — altering one row's snapshot or deleting one row — makes the hash-chain verification job (`J10`) fail the chain check and raise the alert required by `SEC-REQ-010`, and that restoring the original content returns the chain to PASS. | security | P1 | Yes — Jest + superuser SQL harness |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Seeded environment with an intact audit chain: running `J10` (audit hash-chain verification, `16-data/data-quality.md` §5) once reports PASS with `0` mismatches — recorded as baseline. |
| 2 | Two consecutive `b13.audit_log` rows (`seq = N`, `seq = N+1`) selected as the tamper target; their `before`, `after`, `prev_hash`, `entry_hash` values snapshotted for restoration. |
| 3 | Superuser SQL harness available (the only role able to bypass the revoked `UPDATE`/`DELETE` privileges — the tamperer under test); alert sink observable (alert count recorded as baseline). |

## Test Data

| Field | Value |
|---|---|
| tamper target | `seq = N` (snapshot all columns for byte-identical restore) |
| alteration | `UPDATE b13.audit_log SET after = after || '{"tampered":true}'::jsonb WHERE seq = N;` (superuser) |
| deletion | `DELETE FROM b13.audit_log WHERE seq = N;` (superuser — breaks the chain with a gap) |
| verification runs | `J10` run → baseline PASS; run after alteration; run after restore; run after deletion; run after re-insert |

## Steps
1. Run `J10`; record result, mismatch count and alert count (baseline PASS expected).
2. As superuser, run the `UPDATE` alteration on `seq = N`; run `J10`; capture result, mismatch/gap count and alert count.
3. Restore the original `after` value byte-identically (superuser); run `J10` again.
4. As superuser, `DELETE` the row `seq = N`; run `J10`; capture result, gap report and alert count.
5. Re-insert the snapshotted row with its original `seq`, hashes and timestamps (superuser); run `J10` again; re-read the row.

## Expected Result
- Step 1 → `J10` reports PASS, `0` mismatches, `0` new alerts — the chain is intact (`SEC-REQ-010` R4).
- Step 2 → `J10` reports **FAIL**: the recomputed `entry_hash` for `seq = N` no longer matches the stored hash (mismatch count ≥ 1) and the alert required by `SEC-REQ-010` R4 is raised (alert count increments); per the `J10` catalogue row the incident response is the alert plus the freeze on privileged writes for investigation (`audit_log.md` §Invariants App-enforced 3).
- Step 3 → `J10` returns to PASS with `0` mismatches and no further alerts — detection is content-based, not a one-shot flag.
- Step 4 → `J10` reports **FAIL** again: the missing row produces a chain gap between `seq = N−1` and `seq = N+1` (gap count ≥ 1) and a new alert is raised (`SEC-REQ-010` R4 — "modification, deletion, or gap").
- Step 5 → the restored row matches the snapshot (all columns, both hashes) and `J10` reports PASS with `0` mismatches; across all steps no application-role write succeeded — the tamper is possible only for a superuser and is always detected (`AC-SR010-02`).
