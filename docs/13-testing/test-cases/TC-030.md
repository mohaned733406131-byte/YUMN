# TC-030 — Reservation expiry, price changes and ineligible items block checkout; guest cart merges with server value winning

| Field | Value |
|---|---|
| Objective | Verify the dynamic cart rules: the 15-minute reservation releases stock and flags the line stale, price changes demand re-confirmation, ineligible items block checkout, and login merges the guest cart exactly once with server values winning. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (timer injection; merge fixtures from DOC-TST-005) |

## Preconditions
- Customer `771234567` has a cart with line `L1` (product `PRD-P1`, price snapshot 12,500 YER, reservation running).
- Product `PRD-P2` is ACTIVE; `PRD-P3` will be deactivated after being added.
- A guest cart (client-side) holds 2 items; one duplicates `L1` with quantity 3 (server has 2), one violates the 5-vendor cap.
- Clock injection available for the 15-minute boundary.

## Test Data

| Field | Value |
|---|---|
| Line | `L1` — `PRD-P1`, qty 2, snapshot `12500` YER |
| Reservation TTL | 15 min (`C-13`) |
| New price of `PRD-P1` | `13900` YER |
| Guest cart | `[{PRD-P1, qty 3}, {PRD-G1}]` |
| Merge key | `Idempotency-Key: merge-0001` |

## Steps
1. `GET /cart` and record `reservationExpiresAt` for `L1`; do **not** mutate anything for 15 minutes (clock +15:01).
2. `GET /cart` after expiry, then `PATCH /cart/items/L1` with `{"quantity":3}`.
3. Restore the reservation (re-add), change `PRD-P1` price to 13,900 YER server-side, then `GET /cart/checkout-view`.
4. Proceed: `POST /checkout/session` without re-confirming the changed price.
5. Deactivate `PRD-P2` (or zero its stock), then `GET /cart/checkout-view` and `POST /checkout/session`.
6. Log in (fresh session, empty server cart) and `POST /cart/merge` with the guest items and `Idempotency-Key: merge-0001`.
7. Repeat step 6 with the same key, then with a different key but the same payload.
8. `GET /cart` after the merge and inspect `merged` details, flags and totals.

## Expected Result
- Step 1: `reservationExpiresAt = lastActivityAt + 15 min`; a plain `GET` does **not** refresh it (reads are side-effect free).
- Step 2: after expiry the line shows `flags.stale = true`; the mutation returns `422 RESERVATION_EXPIRED` (`BR-CRT-02`) and the reserved stock was already released by the timer (`AC-FR010-03`) — re-add succeeds afterwards.
- Step 3: checkout-view returns `priceChanges: [{productId: PRD-P1, oldPrice: 12500, newPrice: 13900}]` — the cart keeps the add-time snapshot but reports divergence (`BR-CRT-04`).
- Step 4: `POST /checkout/session` (or orders) without confirmation returns `409 PRICE_CHANGED` and creates no order; after client re-confirmation the session computes totals at the **new** price (`AC-FR010-04`).
- Step 5: `blockers` contains the offending product with its reason; checkout returns `422 CART_ITEM_INELIGIBLE` until the line is removed (`BR-CRT-05`, `AC-FR010-05`).
- Step 6: `200 {"merged":{"added":…,"updated":…,"rejected":[…]}}` — the duplicate line takes the **server** quantity (2, not 3); the vendor-cap-violating guest line is rejected alone, other guest lines merge (`BR-CRT-03`).
- Step 7: same key → identical `200` response with no second mutation (`IDEMPOTENCY_CONFLICT` only when the payload differs); merge happens exactly once per login.
- Step 8: `GET /cart` reflects merged lines with fresh `reservationExpiresAt`, accurate `subtotal`/`estimatedVat` (`VAT = 15% × (subtotal − discount)`), and all responses are `no-store`.
