# TC-035 — m-Floos top-up credits exactly once on a verified callback; replayed callback is a no-op

| Field | Value |
|---|---|
| Objective | Verify that an m-Floos (or OneCash) top-up moves the wallet only after a verified provider callback or reconciled poll — never on client claim — and that a replayed or forged callback can never double-credit the wallet. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (MockPaymentAdapter scripted callbacks per DOC-INT-008) |

## Preconditions
- Customer `771234567` wallet `ACTIVE` with 10,000 YER; `MockPaymentAdapter` scripted to emit signed success callbacks and can replay them verbatim.
- Webhook signature verification active (`INT-REQ-006`); no other pending top-up exists for this buyer.

## Test Data

| Field | Value |
|---|---|
| Top-up | `{"amount":25000,"method":"MFLOOS"}`, key `top-035-01` |
| Provider reference | `MF-2026-0926-77123` |
| Balance | before `10000` → after `35000` YER |
| Forged callback | same payload, signature computed with key `"attacker"` |

## Steps
1. `POST /wallet/topups` with `Idempotency-Key: top-035-01` and the body above → record `topupId`.
2. `GET /wallet/topups/{topupId}` and `GET /wallet` before any callback.
3. Deliver the scripted **valid** provider callback for `MF-2026-0926-77123`.
4. Replay the identical callback three more times; then run the reconciled-poll job once.
5. Deliver a callback with an invalid signature for the same reference.
6. `GET /wallet`, `GET /wallet/topups/{topupId}`, `GET /wallet/transactions?type=TOPUP`; SQL-count the `TOPUP` ledger pairs and sum the ledger.

## Expected Result
- Step 1 → `201 {topupId, status:"PENDING_PROVIDER", amount:25000, method:"MFLOOS", paymentInstruction:{…}, expiresAt}`.
- Step 2 → status `PENDING_PROVIDER`, balance still `10000`, **0** ledger rows — a client claim has no credit path (`BR-PAY-03`).
- Step 3 → balance `35000`, top-up status `CREDITED` with `creditedAt` and a `ledgerReference`; exactly one balanced credit pair (`BR-PAY-06`).
- Step 4 → balance remains `35000`; still exactly **one** `TOPUP` pair (`AC-FR013-02`, `BR-PAY-08`); the poll records no second posting.
- Step 5 → `400 SIGNATURE_INVALID`, balance unchanged, top-up still `CREDITED` once (`INT-REQ-006`).
- Step 6 → `SUM(amount) = 0`, ledger rows count = 2 for the credited top-up, `GET /wallet/transactions` lists one `TOPUP` credit of `25000` with `balanceAfter 35000`.
