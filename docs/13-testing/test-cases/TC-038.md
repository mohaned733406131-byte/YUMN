# TC-038 — Wallet ledger is append-only: UPDATE/DELETE rejected, corrections are compensating entries

| Field | Value |
|---|---|
| Objective | Verify that posted ledger rows can never be modified or deleted through the API or the database, that any correction is posted as a new compensating entry, and that the ledger invariant Σ = 0 survives the attempt. |
| Level | integration |
| Priority | P1 |
| Automation | Yes — Jest + Supertest (SQL assertions on `b07.wallet_transaction`) |

## Preconditions
- Customer `771234567` wallet funded with a verified 10,000 YER top-up (two ledger rows already posted).
- The database account used by the API has no `UPDATE`/`DELETE` grant on the ledger table (append-only enforcement, `DATA-REQ-007`).
- `GET /wallet/transactions` is the only user-facing ledger view.

## Test Data

| Field | Value |
|---|---|
| Existing rows | `LT-9001` (debit 10,000), `LT-9002` (credit 10,000), balance `10000` YER |
| Tamper attempts | `PATCH /wallet/transactions/LT-9001`, `DELETE /wallet/transactions/LT-9001` |
| SQL tamper | `UPDATE b07.wallet_transaction SET amount_yer = 1 WHERE id = 'LT-9001';` / `DELETE …` |
| Correction | compensating entry of `-500` YER raised by admin adjustment |

## Steps
1. `GET /wallet/transactions` and snapshot `LT-9001`, `LT-9002` with their `amount`, `balanceAfter` and a row checksum.
2. Call `PATCH /wallet/transactions/LT-9001` with `{"amount":1}`; then `DELETE /wallet/transactions/LT-9001`.
3. Attempt the SQL `UPDATE` and `DELETE` directly against the ledger table.
4. Raise the legitimate correction: post a compensating `-500` YER entry referencing `LT-9002`.
5. Re-read `GET /wallet/transactions`, `GET /wallet` and run `SELECT SUM(amount_yer) FROM b07.wallet_transaction;`.
6. Attempt the same tamper against `GET /admin/audit-log` entries (`PATCH /admin/audit-log/{id}`).

## Expected Result
- Step 2 → `405 METHOD_NOT_ALLOWED` with `error.code = LEDGER_IMMUTABLE` (`error-model.md` §4.9); no write route exists on the ledger view.
- Step 3 → both statements are rejected by the append-only constraint/role grant; row count and values are unchanged (checksum identical).
- Step 4 → `201`-equivalent success creates **new** rows only; `LT-9002` still shows its original values with its original timestamp.
- Step 5 → original two rows byte-identical; the compensating pair references the original posting; balance `9500`; `SUM(amount_yer) = 0` (`BR-PAY-06`, `AC-FR013-05`).
- Step 6 → `405 AUDIT_LOG_IMMUTABLE` — the audit trail is equally append-only (`SEC-REQ-010`).
- `GET /wallet/transactions` lists originals **and** corrections in `createdAt` order with a consistent `balanceAfter` chain; reconciliation reports no mismatch (`AC-S-14`).
