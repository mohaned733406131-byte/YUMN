# TC-109 — Privileged and money actions record actor, action, entity, before/after, IP and timestamp — denials included

## Objective

| Objective | Level | Priority | Automation |
|---|---|---|---|
| Verify that a wallet freeze, a KYC decision and a platform-settings change each write an append-only audit entry carrying actor, action, entity, before/after state, IP and timestamp, that the settings entry records old and new values on a null platform entity, and that a denied privileged attempt is recorded with `outcome = DENIED`. | integration | P0 | Yes — Jest + Supertest |

## Preconditions

| # | Precondition |
|---|---|
| 1 | Tokens: `ADMIN`, `SUPER_ADMIN`, `MODERATOR`. Reserved-block customers `791100006` (ACTIVE wallet, will be frozen) and `791100007` (ACTIVE wallet, must stay ACTIVE). |
| 2 | KYC submission `KYC-5502` is `PENDING`; `GET /admin/settings?group=COMMISSION` shows `commission.defaultRate` = `10` at version `v0` (seed = `3`, TC-060 fixture). |
| 3 | `t0` recorded; `J10` baseline PASS; `GET /readyz` → `200`. |

## Test Data

| Field | Value |
|---|---|
| wallet freeze | `POST /admin/wallets/791100006/freeze` `ADMIN` `{"reason":"fraud probe TC-109"}` |
| KYC decision | `POST /admin/kyc/KYC-5502/reject` `ADMIN` `{"reason":"document mismatch TC-109"}` |
| settings change | `PUT /admin/settings/commission.defaultRate` `SUPER_ADMIN` `{"value":15,"expectedVersion":3}`; revert `{"value":10,"expectedVersion":4}` |
| denied attempt | `POST /admin/wallets/791100007/freeze` `MODERATOR` `{"reason":"not permitted"}` |
| correlation | capture `X-Correlation-Id` per call (one per step) |

## Steps
1. Record `t0`; read `commission.defaultRate` version (`v0 = 3`).
2. `ADMIN` freeze `791100006`; capture `auditId`, `X-Correlation-Id`.
3. `ADMIN` reject `KYC-5502` with the reason; capture `auditId`, `X-Correlation-Id`.
4. `SUPER_ADMIN` set `commission.defaultRate` to `15` with `expectedVersion: 3`; then revert to `10` with `expectedVersion: 4`; capture both `auditId`s.
5. `MODERATOR` attempt to freeze `791100007`; capture status, error code, `X-Correlation-Id`; re-read the wallet.
6. SQL by `auditId`: assert the completeness set on each row; on the settings rows assert `entity_id IS NULL` and before/after values; find the step-5 row by `correlation_id` and assert `outcome`.
7. `GET /admin/audit-log?action=wallet.freeze&actorId=<adminId>&from=<t0>&to=<now>` and `?action=settings.update&targetId=commission.defaultRate&from=<t0>&to=<now>` as `ADMIN`; re-run `J10`.

## Expected Result
- Step 2 → `200 { userId, status: "FROZEN", auditId }` (`API-ADM-033`); step 3 → `200 { status: "REJECTED", reason, decidedAt, auditId }` (`API-ADM-008`); step 4 → `200 { key, value: 15, version: 4, auditId }` then `200 { value: 10, version: 5 }` (`API-ADM-023`).
- Step 5 → `403 FORBIDDEN` (`API-ADM-033` — Moderator is denied wallet freeze, `rbac.md` matrix row 13); wallet `791100007` still `status: "ACTIVE"` — the denied attempt persisted nothing.
- Step 6 freeze row → `actor_user_id` = the admin, `actor_role = 'ADMIN'`, `action = 'wallet.freeze'`, non-null `module`/`entity_type`/`entity_id`, `before` **and** `after` snapshots present with `after` recording `FROZEN`, non-null `ip`, `created_at` in `[t0, now]`, `correlation_id` matching the captured header, `outcome = 'SUCCESS'`, non-null hashes (`BR-PLT-06`, `AC-FR020-01`).
- Step 6 KYC row → `action = 'kyc.decision'`, non-null `reason` (decisions carry a reason — `audit_log.md` field table), both snapshots present, `outcome = 'SUCCESS'`, non-null `ip` and `correlation_id` (`SEC-REQ-010` R2, `BR-VND-03` decision trail).
- Step 6 settings rows → exactly two entries (value `15`, then revert to `10`): `entity_id IS NULL` (platform-level action — `audit_log.md` field table note), `before` records the previous value and `after` the new one, `actor_role = 'SUPER_ADMIN'`, non-null `ip`/`created_at`/`correlation_id` (`AC-FR020-01`, `BR-PLT-06`).
- Step 6 denied row → `outcome = 'DENIED'`, `actor_role = 'MODERATOR'`, `action = 'wallet.freeze'`, non-null `ip` and `correlation_id`, `created_at` in window — failed authorization attempts are recorded too (`audit_log.md` outcome enum, `SEC-REQ-004`).
- Step 7 → both audit-surface queries return the matching items with the documented projection (`id`, `at`, `actorId`, `actorRole`, `action`, `targetId`, `ipHash`, `correlationId` — `API-ADM-024`); `J10` reports PASS with `0` mismatches — appends kept the chain intact.
