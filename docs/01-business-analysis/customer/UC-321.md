# UC-321 — Combine Search Filters and Compare Facet Counts

## Header Info
- **Use Case ID:** UC-321
- **Title:** Combine Search Filters and Compare Facet Counts
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer combines filters on the search page (category, store, price, rating, availability)
- **Priority:** P1
- **Goal:** Narrow results with multiple filters while the sidebar counts match exactly what the list would return.
- **Preconditions:** Search page open (`/[locale]/search`, UC-006); products indexed (FR-004); query normalized server-side (C-24).

## Main Scenario
1. Customer applies a first filter (e.g. category) → results and facet counts refresh in the same filter context (API-SRC-001/002).
2. The sidebar shows per-facet counts that match the list exactly — e.g. "Electronics (24)" (FR-009).
3. A second filter is added → counts recompute in the narrowed context; selected filters appear as removable chips.
4. The URL mirrors the state, so reload/back restore the same combination (search slice: URL wins on load).
5. Results page by cursor while every facet count reflects all applied filters (cursor pagination, NFR-004 facet caching).

## Alternative Scenarios
- **A1 — Remove one chip:** counts widen back to the previous context and the list rejoins the earlier result set.
- **A2 — Combination yields zero results:** localized empty state with per-facet "remove filter" recovery — never an error (NFR-012).
- **A3 — Facet sidebar fails independently:** block error with retry inside the sidebar; the result list keeps working (partial-data rule).

## Exception Scenarios
- **E1 — Invalid facet value:** `FACET_INVALID`/`VALIDATION_ERROR`; the previous valid results and counts stay rendered.
- **E2 — Search backend degraded:** `meta.degraded` is set and a cached replay may serve; if none exists the endpoint fails over to category browse (UC-324, NFR-007).
- **E3 — Stale cursor with new filters:** request rejected; the list restarts at the first page of the new context.

## Postconditions
- Success: filtered list plus matching counts rendered in the active locale/RTL layout; read-only — no rows written.
- Failure: the last valid result set remains; no fabricated counts.

## Business Rules Applied
- BR-CAT-06, BR-VND-04

## Related Requirements
- FR-009 (Search & Discovery — filters & facets)
- **Relation:** UC-006 is the base search; UC-322 sorts the same result set; UC-323/UC-324 handle empty and unavailable search.

## Permissions / Data / External Dependencies
- **Permissions:** Public read; only `ACTIVE` products of non-suspended stores are counted, for every caller alike (BR-CAT-06, BR-VND-04).
- **Data involved:** Elasticsearch result set, facet aggregations, filter/chip UI state, URL query string — no writes.
- **External dependencies:** Elasticsearch cluster (DEP-04); Redis aggregation cache (NFR-004); cursor pagination.

## Acceptance Criteria
- **AC-UC321-01:** Given two filters applied, when facets are fetched, then each count equals the size of the list under those same filters (FR-009).
- **AC-UC321-02:** Given a filter combination with no matches, when results return, then an empty state with remove-filter recovery shows (NFR-012).
- **AC-UC321-03:** Given an invalid facet value, when the request runs, then `FACET_INVALID`/`VALIDATION_ERROR` returns and the prior list stays.
- **AC-UC321-04:** Given the combination in the URL, when the page reloads, then the same filters, chips and counts are restored.
