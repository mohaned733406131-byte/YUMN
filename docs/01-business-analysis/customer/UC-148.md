# UC-148 — View and Edit Profile

## Header Info
- **Use Case ID:** UC-148
- **Title:** View and Edit Profile
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens Account → Profile and changes a field
- **Priority:** P1
- **Goal:** Let the customer read their own profile and edit mutable fields while the phone identifier stays immutable.
- **Preconditions:** Customer authenticated; profile row exists for the account (FR-003).

## Main Scenario
1. Client calls `GET /users/me` (API-USR-001) → `displayName`, `phoneMasked`, `email?`, `emailVerified`, `locale`, `avatarUrl?`, `roles`, `createdAt`.
2. Phone is shown masked (`7712***45`) and is immutable — the primary identifier (BR-AUTH-01); no edit path exists anywhere.
3. Customer edits displayName, locale, or the optional email → `PATCH /users/me` (API-USR-002).
4. Setting an email stores it unverified and dispatches a code to that address; verification continues in UC-149.
5. Duplicate email → `EMAIL_ALREADY_REGISTERED`; validation failures → `VALIDATION_ERROR` with field errors and no partial write (FR-003).
6. The identity-affecting change appends an audit entry (actor, before/after, timestamp — BR-PLT-06).

## Alternative Scenarios
- **A1 — Phone change:** no endpoint or UI exists; the immutable identifier cannot be altered (BR-AUTH-01).
- **A2 — Locale edit:** same stored preference the locale switcher writes (UC-152); it drives future sessions.

## Exception Scenarios
- **E1 — Concurrent edits from two devices:** last write wins; a re-read (`GET /users/me`) shows the server's current state.
- **E2 — Network error mid-PATCH:** client rolls back the optimistic UI and re-fetches to confirm what was stored.
- **E3 — Validation or rate-limit rejection:** `VALIDATION_ERROR`/`RATE_LIMITED` → stored profile unchanged (FR-003).

## Postconditions
- Success: mutable profile fields updated; phone remains masked and immutable (BR-AUTH-01); audit entry appended (BR-PLT-06).
- Failure: profile unchanged; previous values still served.

## Business Rules Applied
- BR-AUTH-01, BR-PLT-06

## Related Requirements
- FR-003 (User & Profile Management)

## Permissions / Data / External Dependencies
- **Permissions:** owner-scoped — another user's profile read returns 404 (ownership, SEC-REQ-004).
- **Data involved:** user profile row (display name, optional email, locale, avatar), audit log.
- **External dependencies:** email code dispatch for the optional email (UC-149).

## Acceptance Criteria
- **AC-UC148-01:** Given a PATCH changing displayName only, when applied, then the phone stays masked and unchanged (BR-AUTH-01).
- **AC-UC148-02:** Given an email already used by another account, when saved, then `EMAIL_ALREADY_REGISTERED` returns and nothing is stored.
- **AC-UC148-03:** Given a successful identity-affecting change, when queried, then an append-only audit entry exists (BR-PLT-06).
