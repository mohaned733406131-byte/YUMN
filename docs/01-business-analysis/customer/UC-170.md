# UC-170 — View the Return Pickup Schedule

## Header Info
- **Use Case ID:** UC-170
- **Title:** View the Return Pickup Schedule
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the Pickup section of an approved return
- **Priority:** P2
- **Goal:** Show the customer the read-only pickup status of an approved return from offer through courier pickup to receipt at the store.
- **Preconditions:** Authenticated; own return in `RETURN_APPROVED` or later (a rejected return has no pickup — A3); owner-scoped access.

## Main Scenario
1. Customer opens the approved return → Pickup section → `GET /returns/{id}/pickup` (API-RET-008).
2. System returns pickup status `OFFERED → ASSIGNED → PICKED_UP → RECEIVED` with masked courier name, `assignedAt` and `receivedAt` (BR-RET-02).
3. The view is read-only: the customer cannot schedule or reschedule — assignment reuses the courier offer flow of the same shipping engine that prices fees by zone, weight and method (BR-SHP-01).
4. The platform never requests courier location — only status and timestamps are shown.
5. On `RECEIVED` the return advances toward inspection; the customer follows it in UC-169.

## Alternative Scenarios
- **A1 — Not yet assigned:** status `OFFERED`; no courier shown, no customer action available.
- **A2 — Courier assigned:** masked name plus `assignedAt` — never a phone number or location.
- **A3 — Return rejected:** pickup lookup → `STATE_CONFLICT` (no pickup exists for a rejected return).

## Exception Scenarios
- **E1 — Unknown or foreign return:** `NOT_FOUND`.
- **E2 — Return state changed concurrently** (e.g., rejected while opening) → `STATE_CONFLICT`.
- **E3 — Invalid or expired session:** `AUTH_INVALID`; no schedule rendered.

## Postconditions
- Success: customer sees the current pickup status; read-only — no assignment, schedule or return-state change.
- Failure: no data rendered; return state unchanged.

## Business Rules Applied
- BR-RET-02, BR-SHP-01

## Related Requirements
- FR-016 (Returns & Refunds), FR-015 (Shipping & Delivery)
- **Relation:** UC-168 approved the return whose pickup is shown; the courier side reuses the delivery assignment flow.

## Permissions / Data / External Dependencies
- **Permissions:** return owner, plus vendor/admin on their scoped views; customers get read-only projection.
- **Data involved:** pickup status, courier identity (masked), timestamps — read-only.
- **External dependencies:** delivery engine (B08) for courier assignment; returns service (B09).

## Acceptance Criteria
- **AC-UC170-01:** Given an approved return, when the pickup view loads, then status `OFFERED` is returned with no courier yet (BR-RET-02).
- **AC-UC170-02:** Given an assigned pickup, when loaded, then only masked courier name and timestamps appear — no location data.
- **AC-UC170-03:** Given a rejected return, when pickup is requested, then `STATE_CONFLICT` (BR-RET-02).
- **AC-UC170-04:** Given any pickup state, when the customer looks for a reschedule control, then none exists (read-only).
