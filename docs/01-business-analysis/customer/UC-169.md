# UC-169 — Track Return Request Status

## Header Info
- **Use Case ID:** UC-169
- **Title:** Track Return Request Status
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens "My Returns" or a specific return from their order
- **Priority:** P1
- **Goal:** Show the customer where each of their return requests sits in the return state machine with decision, inspection, pickup and refund detail.
- **Preconditions:** Authenticated; at least one return request exists (or the list is empty — A1); owner-scoped access.

## Main Scenario
1. Customer opens Returns → `GET /returns` (API-RET-002), a cursor feed of own requests with state and `decisionDueAt`.
2. Customer opens one request → `GET /returns/{id}` (API-RET-003) returns items, reason/evidence, policy math (`isReturnable`, `returnPeriodDays`, `windowDeadline`), decision, inspection, refund status, pickup status and timeline.
3. System renders the machine position `RETURN_REQUESTED → RETURN_APPROVED / RETURN_REJECTED → RETURN_RECEIVED → REFUNDED` on an append-only timeline (BR-RET-02).
4. SLA markers returned by the API (`decisionDueAt`, `expectedCreditBy`) show what is pending and when it is due.
5. On `REFUNDED`, the refund block shows status and the wallet credit reference in integer YER.

## Alternative Scenarios
- **A1 — Empty list:** no returns yet → zero items, no placeholder rows.
- **A2 — Filtered view:** `?state=` narrows the feed to one state.
- **A3 — Rejected return:** detail shows the mandatory rejection reason and the final outcome; no pickup exists (E3 on UC-170).

## Exception Scenarios
- **E1 — Foreign or unknown return:** `NOT_FOUND` (owner scope).
- **E2 — Invalid cursor/filter value:** `VALIDATION_ERROR`; no data returned.
- **E3 — Invalid or expired session:** `AUTH_INVALID`; client redirects to login.

## Postconditions
- Success: customer sees their own return status and history; read-only — no state, decision or refund change.
- Failure: no data rendered; session either invalid (→ login) or intact.

## Business Rules Applied
- BR-RET-02

## Related Requirements
- FR-016 (Returns & Refunds — return state visibility)
- **Relation:** UC-168 opens the request tracked here; UC-170 shows the pickup leg of the same sequence.

## Permissions / Data / External Dependencies
- **Permissions:** return owner reads own requests; vendors/admins read their scoped views (separate roles).
- **Data involved:** return rows, policy math, decisions, inspection, refund status, timeline — read-only.
- **External dependencies:** returns service (B09) only.

## Acceptance Criteria
- **AC-UC169-01:** Given three own returns, when the feed loads, then all three appear with state and `openedAt` (BR-RET-02).
- **AC-UC169-02:** Given a return in `RETURN_APPROVED`, when detail opens, then policy, decision, pickup and refund blocks are present (BR-RET-02).
- **AC-UC169-03:** Given another user's return, when detail is requested, then `NOT_FOUND`.
- **AC-UC169-04:** Given `?state=RETURN_RECEIVED`, when applied, then only matching returns are listed.
