# UC-342 — Work With a Frozen Wallet (Pay and Top-Up Blocked, Refunds Still Received)

## Header Info
- **Use Case ID:** UC-342
- **Title:** Work With a Frozen Wallet (Pay and Top-Up Blocked, Refunds Still Received)
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the wallet (or tries to pay/top up) while the wallet status is `FROZEN`
- **Priority:** P0
- **Goal:** Explain the freeze honestly — payments and top-ups blocked, refunds still landing — with a support path.
- **Preconditions:** Wallet frozen by admin for legal/security reasons (BR-PAY-09); balance readable (API-WAL-001); support entry available (FR-020).

## Main Scenario
1. Customer opens the wallet → `GET /wallet` returns `status: "FROZEN"` (API-WAL-001).
2. A full-width warning banner shows: cannot pay or top up, refunds still received, contact support with a ticket CTA (screen-states §6).
3. Attempting to pay at checkout or start a top-up returns `WALLET_FROZEN` with the same banner (API-ORD-002, API-WAL-003).
4. A refund from a return or cancellation still credits the wallet with its ledger row (BR-PAY-09, BR-PAY-07).
5. The customer opens a support ticket from the banner with pre-filled wallet context (feedback §8).

## Alternative Scenarios
- **A1 — Freeze lifted later:** the banner clears and pay/top-up resume without re-login.
- **A2 — Refund arrives while frozen:** the credit row posts with the "to wallet only" note (screen-states §6).
- **A3 — Checkout shows the wallet first:** the shortfall/wallet step surfaces the frozen state plus support CTA (UC-330).

## Exception Scenarios
- **E1 — Pay attempt races the freeze:** the server rejects atomically — no debit and the balance never goes negative (BR-PAY-05).
- **E2 — Freeze reason not disclosed:** the banner never reveals legal/security detail — it points to support instead.
- **E3 — Session expired:** re-auth prompt, then the wallet reopens still showing the frozen state (routing §9).

## Postconditions
- Success (browse): freeze understood and support reachable; no payment or top-up succeeded.
- Failure: no partial debit, no top-up intent, balance never negative; refunds remain receivable (BR-PAY-09).

## Business Rules Applied
- BR-PAY-09, BR-PAY-05, BR-PAY-07

## Related Requirements
- FR-013 (Wallet & Payment Processing — wallet status & freeze)
- **Relation:** UC-330 hits this at checkout; UC-343 shows refunds still crediting; UC-041 starts blocked top-ups; UC-359 is the support thread used here.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER reads own wallet; freeze/unfreeze is admin-only (ACT-04) — the customer can never lift it.
- **Data involved:** wallet status, balance, blocked payment/top-up attempts, refund credits, ledger rows.
- **External dependencies:** wallet/ledger service (B07); admin freeze tooling (B13); support ticket entry (FR-020).

## Acceptance Criteria
- **AC-UC342-01:** Given a `FROZEN` wallet, when checkout confirm runs, then `WALLET_FROZEN` returns and no debit posts (BR-PAY-09).
- **AC-UC342-02:** Given a `FROZEN` wallet, when a top-up is initiated, then it is rejected with `WALLET_FROZEN` (BR-PAY-09).
- **AC-UC342-03:** Given a `FROZEN` wallet, when a refund is due, then the wallet credit still posts with a ledger row (BR-PAY-09, BR-PAY-07).
- **AC-UC342-04:** Given the freeze, when the wallet screen loads, then the banner states pay/top-up blocked, refunds received, plus a support CTA (screen-states §6).
