# UC-348 — Open the 24-Hour Code-Lockout Notice and Its Auto-Created Ticket

## Header Info
- **Use Case ID:** UC-348
- **Title:** Open the 24-Hour Code-Lockout Notice and Its Auto-Created Ticket
- **Actor:** Customer (ACT-01)
- **Trigger:** The delivery code failed 3 times, locking confirmation for 24 hours and auto-creating a support ticket
- **Priority:** P1
- **Goal:** Explain the lockout with its countdown and open the pre-filled ticket so the customer never retypes the situation.
- **Preconditions:** 3rd code failure occurred (BR-SHP-03, edge-cases EC-30); ticket auto-created with the full timeline; tracking screen open (FL-03 D3).

## Main Scenario
1. The 3rd wrong code locks confirmation for 24 hours and auto-creates a support ticket with the delivery timeline (BR-SHP-03).
2. Tracking shows the lock notice — "تم إيقاف التأكيد لمدة ٢٤ ساعة / Confirmation locked for 24 h" — with countdown and the ticket reference (screen-states §7).
3. "Contact support" opens the pre-referenced ticket thread with context attached (feedback §8 contextual escalation).
4. The thread shows the linked order/delivery and timeline — the customer adds a message instead of restating the case (UC-359).
5. When the countdown expires, code verification becomes available again (BR-SHP-03).

## Alternative Scenarios
- **A1 — Support resolves earlier:** the ticket replies arrive in-thread; verification availability follows the admin unlock path.
- **A2 — Order delivered meanwhile:** the lock notice is replaced by the proof screen (screen-states §7 already-delivered).
- **A3 — Notice reached via inbox:** the notification deep-links straight to the ticket or lock screen (FR-017).

## Exception Scenarios
- **E1 — Ticket fetch fails:** page error with retry; the lock notice itself stays visible in-app.
- **E2 — Lock expires while the screen is open:** the countdown ends and the retry affordance re-enables without reload.
- **E3 — Customer disputes the lock:** the reply appends to the same thread — no separate ticket is created (API-ADM-038).

## Postconditions
- Success: lock notice with countdown and ticket reference displayed; exactly one auto-ticket exists for the lock.
- Failure: no unlock without verification; no duplicate ticket and no state change from reading the notice.

## Business Rules Applied
- BR-SHP-03

## Related Requirements
- FR-015 (Shipping & Delivery — code attempts), FR-020 (Platform Administration — support tickets)
- **Relation:** UC-346 retrieves the code; UC-347 shows the attempts in the timeline; UC-359 appends to the thread; UC-360 rates its resolution.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own ticket and own order only — foreign tickets return `404` (admin.md thread integrity).
- **Data involved:** lock state with `lockedUntil`, attempt count, auto-created ticket, thread messages, timeline attachment.
- **External dependencies:** delivery service (B08); support ticketing (B13); notification fan-out for the lock notice (B10).

## Acceptance Criteria
- **AC-UC348-01:** Given a 3rd code failure, when the check runs, then confirmation locks for 24 h and exactly one support ticket is auto-created (BR-SHP-03).
- **AC-UC348-02:** Given the lock, when tracking renders, then the notice shows the countdown plus the ticket reference (screen-states §7).
- **AC-UC348-03:** Given the ticket link, when opened, then the thread already carries the order/delivery timeline — no retyping needed.
- **AC-UC348-04:** Given 24 hours elapsed, when verification is retried, then the lock no longer blocks the attempt (BR-SHP-03).
