# UC-351 — Open a Late-Window Return on a Completed Order

## Header Info
- **Use Case ID:** UC-351
- **Title:** Open a Late-Window Return on a Completed Order
- **Actor:** Customer (ACT-01)
- **Trigger:** The order reached `COMPLETED` (escrow released) but the return window is still open
- **Priority:** P1
- **Goal:** Let the customer open a return from `COMPLETED` inside the window — exactly one legal transition, no invented states.
- **Preconditions:** Order `COMPLETED` (BR-ORD-01); window still open from delivery confirmation (BR-RET-01); transition `COMPLETED → RETURN_REQUESTED` exists in the canonical table (state-transitions §2).

## Main Scenario
1. Customer opens the return entry on the `COMPLETED` order — the entry is offered because the window is open (FL-04).
2. Server re-validates the window from delivery confirmation + `returnPeriodDays`, not the order date (WF-007 step 2).
3. Validation passes → the sub-order transitions `COMPLETED → RETURN_REQUESTED` via the canonical transition row (BR-RET-01).
4. The return enters the standard flow: vendor decision within 48 h, then pickup and inspection (BR-RET-02).
5. The timeline gains the append-only entry and the customer sees the SLA screen (screen-states §9).

## Alternative Scenarios
- **A1 — Window also elapsed:** rejected at submission with `WINDOW_EXPIRED` — state stays `COMPLETED` (UC-350).
- **A2 — Dispute open instead:** `DISPUTE_ALREADY_OPEN` blocks the return (UC-354).
- **A3 — Order cancelled/refunded:** the return entry is not offered — that path already refunded.

## Exception Scenarios
- **E1 — Guard rejects the move (bad state):** `STATE_CONFLICT`; no history row is written (BR-ORD-01, C-09).
- **E2 — Concurrent resolution:** optimistic `version` guard — the loser gets `409` and retries on the fresh state.
- **E3 — Escrow already released:** unaffected for the customer — the refund draws escrow first, then vendor payable (BR-ESC-07).

## Postconditions
- Success: sub-order in `RETURN_REQUESTED` with one append-only history entry and a scheduled decision SLA.
- Failure: state unchanged, no return row, no pickup scheduled.

## Business Rules Applied
- BR-RET-01, BR-RET-02

## Related Requirements

- **Relation:** UC-350 gates eligibility; UC-352 covers the auto-approve branch; UC-353 explains the refund composition; UC-021 is the vendor side.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own order only — the transition runs server-side inside the order transaction.
- **Data involved:** order state, `version`, status-history row, return request row, decision SLA timestamps.
- **External dependencies:** returns service (B09); order state machine (B06); notification fan-out for SLA (B10).

## Acceptance Criteria
- **AC-UC351-01:** Given a `COMPLETED` order within the window, when the return is submitted, then the state becomes `RETURN_REQUESTED` (state-transitions §2).
- **AC-UC351-02:** Given the delivery confirmation date, when the window computes, then it starts from delivery confirmation + `returnPeriodDays` (BR-RET-01).
- **AC-UC351-03:** Given a `COMPLETED` order past the window, when submitted, then `WINDOW_EXPIRED` returns and the state stays `COMPLETED`.
- **AC-UC351-04:** Given the accepted transition, when history writes, then exactly one append-only entry with actor and timestamp exists (BR-ORD-03).
