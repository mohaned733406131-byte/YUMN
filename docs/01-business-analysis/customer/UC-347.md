# UC-347 — See Failed Delivery Attempts Reflected in Your Order Timeline

## Header Info
- **Use Case ID:** UC-347
- **Title:** See Failed Delivery Attempts Reflected in Your Order Timeline
- **Actor:** Customer (ACT-01)
- **Trigger:** A courier records a failed delivery attempt (or wrong code entries occur) on the customer's order
- **Priority:** P2
- **Goal:** Show every attempt in the customer's timeline with actor, timestamp and reason — nothing overwritten.
- **Preconditions:** Order in delivery (FR-015); append-only status history exists (BR-ORD-03); tracking screen open (FL-03).

## Main Scenario
1. The courier records a failed attempt → delivery returns to `IN_TRANSIT` with the attempt logged (API-SHP-011).
2. The attempt is appended to `order_status_history` with actor, timestamp and reason (BR-ORD-03).
3. Wrong courier code entries are recorded the same way and visible to the customer (FL-03 step 4).
4. Customer opens tracking → the timeline lists every entry newest-first under the current state badge (API-ORD-005).
5. After 3 failed attempts the escalation entry appears with a support path (BR-SHP-06).

## Alternative Scenarios
- **A1 — Attempt then success:** the next entry is `DELIVERED` via verified code (BR-ORD-08).
- **A2 — State-change notification:** push/SMS/WhatsApp per preferences deep-links back to this timeline (FR-017).
- **A3 — Third-attempt escalation:** an admin-review entry with full timeline becomes visible (BR-SHP-06).

## Exception Scenarios
- **E1 — Timeline fetch fails:** page error with retry; no client-invented entries are ever rendered.
- **E2 — Foreign order:** `404` — timeline visibility is scoped (BR-ORD-09).
- **E3 — Concurrent transitions:** optimistic locking — the losing writer gets `409` and history stays append-only (BR-ORD-03).

## Postconditions
- Success: the timeline contains every attempt with actor, timestamp and reason; the state badge matches the server.
- Failure: no history row is edited or deleted — append-only holds (BR-ORD-03).

## Business Rules Applied
- BR-ORD-03, BR-SHP-06

## Related Requirements
- FR-015 (Shipping & Delivery — failed attempts), FR-012 (Order Lifecycle Management — timeline)
- **Relation:** UC-012 opens the order; UC-349 follows progress; UC-348 handles the code lockout; UC-336 is another escalation notice.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own timeline slice only — couriers/vendors/admins see their own scoped views (BR-ORD-09).
- **Data involved:** status-history entries, attempt records, state badge, notification rows — append-only writes by system/courier.
- **External dependencies:** delivery service (B08); order service (B06); notification fan-out (B10).

## Acceptance Criteria
- **AC-UC347-01:** Given a courier failed attempt, when the customer opens the timeline, then an entry with actor, timestamp and reason appears (BR-ORD-03).
- **AC-UC347-02:** Given wrong code entries, when the timeline loads, then each attempt is recorded (BR-ORD-03).
- **AC-UC347-03:** Given existing history, when a new attempt posts, then earlier rows are byte-identical — append-only (BR-ORD-03).
- **AC-UC347-04:** Given 3 failed attempts, when the timeline updates, then an escalation entry plus support path shows (BR-SHP-06).
