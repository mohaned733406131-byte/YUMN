# UC-310 — Sit Through the 15-Minute Lockout Countdown After Five Failed Logins

## Header Info
- **Use Case ID:** UC-310
- **Title:** Sit Through the 15-Minute Lockout Countdown After Five Failed Logins
- **Actor:** Customer (ACT-01)
- **Trigger:** The fifth consecutive wrong password is submitted at login
- **Priority:** P1
- **Goal:** Lock the account for 15 minutes, show an honest countdown with a support path, and unlock automatically when the window ends.
- **Preconditions:** An account exists (UC-002); four consecutive failed logins already counted (BR-AUTH-04); login screen open (UC-003, FL-01).

## Main Scenario
1. Customer submits a wrong password for the fifth consecutive time on the login form.
2. System locks the account for 15 minutes and writes the lock event to the log (BR-AUTH-04).
3. The form is replaced by the lock screen: countdown in locale digits, support link, no password field (FL-01 step 6).
4. A mandatory lockout security notification is fanned out on all applicable channels (BR-NTF-02).
5. The countdown reaches zero → the lock expires server-side, the login form returns, and the failure counter resets (BR-AUTH-04).

## Alternative Scenarios
- **A1 — Fewer than five failures:** inline error with attempts remaining; no lock yet (BR-AUTH-04 partial path, rejoins UC-003).
- **A2 — Customer opens "forgot password":** navigates to the OTP reset flow (UC-004); the lock screen stays until its window ends.
- **A3 — Lock seen on another device:** the lock is account-wide, so any surface renders the same countdown (FL-01).

## Exception Scenarios
- **E1 — Device clock drift:** the countdown is driven by the server timestamp, so it never shows a negative or an early unlock.
- **E2 — Session/token expired during the lock (C-08):** after expiry the login form is served normally; no stale session bypasses the lock.
- **E3 — Notification channels down:** the lock still enforces server-side; the security notice retries under the platform retry policy (BR-PLT-02).

## Postconditions
- Success (expiry): account usable again; the lock event remains in the security log.
- Failure (still locked): no password check succeeds, no session issued, no partial lock state.

## Business Rules Applied
- BR-AUTH-04, BR-NTF-02, BR-PLT-02

## Related Requirements
- FR-001 (Identity, Authentication & Session Management — login & lockout)
- **Relation:** UC-003 is the login flow this interrupts; UC-004 is the reset path offered; UC-141 handles OTP resend counters.

## Permissions / Data / External Dependencies
- **Permissions:** any actor hitting login (no session yet); the lock applies to the account, not the device.
- **Data involved:** failed-login counter, lock record + lock event log, security notification, lock-screen UI state.
- **External dependencies:** auth service (B01); notification fan-out (B10); no third-party providers beyond messaging (INT-REQ-003/004).

## Acceptance Criteria
- **AC-UC310-01:** Given four consecutive failures, when a fifth wrong password is submitted, then the account locks for 15 minutes and the lock event is logged (BR-AUTH-04).
- **AC-UC310-02:** Given a locked account, when login loads, then a server-driven countdown renders in locale digits with a support link and no password field (FL-01).
- **AC-UC310-03:** Given the lock, when fan-out runs, then a lockout security notice is sent on all applicable channels and cannot be disabled (BR-NTF-02).
- **AC-UC310-04:** Given 15 minutes elapse, when the countdown ends, then login is available again with no manual intervention (BR-AUTH-04).
