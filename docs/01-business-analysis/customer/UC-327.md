# UC-327 — Re-Confirm a Price That Changed Since Add-to-Cart

## Header Info
- **Use Case ID:** UC-327
- **Title:** Re-Confirm a Price That Changed Since Add-to-Cart
- **Actor:** Customer (ACT-01)
- **Trigger:** Checkout recomputation finds a line whose current price differs from the add-to-cart snapshot
- **Priority:** P0
- **Goal:** Show the price delta and require explicit re-confirmation before any order can be created on the new price.
- **Preconditions:** Cart line holds an add-time price snapshot (FR-010); checkout session at cart-review/confirm step (FR-011); totals computed server-side (BR-CRT-04).

## Main Scenario
1. Customer enters checkout; the server recomputes the cart authoritatively (`POST /checkout/session` / cart checkout-view).
2. A line's price differs from its snapshot → `priceChanges[] { productId, oldPrice, newPrice }` is returned (BR-CRT-04).
3. UI shows the price-change panel with the per-line delta and blocks progress until the customer re-confirms (FL-02 D4).
4. Totals are recomputed server-side — items − discount + VAT 15% + shipping (BR-FIN-01, BR-FIN-02).
5. On re-confirmation the fresh price is accepted and checkout continues to wallet payment (UC-011).

## Alternative Scenarios
- **A1 — No price changes:** the panel is skipped; the authoritative totals proceed directly to payment.
- **A2 — Customer declines the new price:** leaves checkout; the cart stays intact and no order is created (BR-CRT-04).
- **A3 — Price dropped since add:** the same panel shows the lower new price — any change requires re-confirmation, not only increases.

## Exception Scenarios
- **E1 — Price changes again before confirm:** `PRICE_CHANGED` fires again on `POST /orders`; the loop repeats until the price is stable — never a silent charge.
- **E2 — Checkout session expired while reviewing:** `CHECKOUT_SESSION_EXPIRED`; the customer restarts checkout with the cart intact.
- **E3 — Vendor edits the price concurrently:** the server-side recompute always wins; no client-invented total is ever charged (state-management: money totals forbidden in client state).

## Postconditions
- Success: totals re-confirmed against current server prices; checkout advances — still no order row until confirm.
- Failure: no order row, no wallet movement, no ledger entry; cart and snapshot semantics preserved.

## Business Rules Applied
- BR-CRT-04, BR-FIN-01, BR-FIN-02

## Related Requirements
- FR-010 (Shopping Cart — server-side reconciliation), FR-011 (Checkout & Order Placement — authoritative totals)
- **Relation:** UC-161 previews the authoritative checkout totals; UC-011 completes checkout; UC-330 handles the balance gate at the same step.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner cart/session only; only the server may declare a price.
- **Data involved:** cart line price snapshots, `priceChanges[]`, recomputed totals (subtotal, discount, VAT, shipping), checkout session.
- **External dependencies:** cart/checkout service (B05); catalog price source (B02); no third-party providers.

## Acceptance Criteria
- **AC-UC327-01:** Given a line repriced after add, when checkout recomputes, then `priceChanges[]` contains its old and new price (BR-CRT-04).
- **AC-UC327-02:** Given an unconfirmed price change, when confirm is attempted, then `PRICE_CHANGED` returns and no order row exists (BR-CRT-04).
- **AC-UC327-03:** Given the re-confirmation, when totals render, then they are the server-computed breakdown including 15% VAT (BR-FIN-01).
- **AC-UC327-04:** Given the customer declines, when checkout exits, then the cart is unchanged and no debit occurred.
