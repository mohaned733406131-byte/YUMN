# UC-337 — Get the Cancel-Window Refusal After READY_FOR_PICKUP

## Header Info
- **Use Case ID:** UC-337
- **Title:** Get the Cancel-Window Refusal After READY_FOR_PICKUP
- **Actor:** Customer (ACT-01)
- **Trigger:** The customer tries to cancel an order that has reached `READY_FOR_PICKUP` or beyond
- **Priority:** P1
- **Goal:** Refuse clearly, explain the cancel window, and offer the remaining paths — never a dead button.
- **Preconditions:** Own order exists (FR-012); state at or past `READY_FOR_PICKUP` (BR-ORD-04); customer view open (FL-03).

## Main Scenario
1. On the tracking screen the cancel control is hidden with an explanatory tooltip once `READY_FOR_PICKUP` is reached (FL-03 step 2).
2. A stale screen or deep link still submits cancel → system validates the state (BR-ORD-04) and returns `CANCEL_WINDOW_CLOSED`.
3. The client maps the code to a localized message: customer cancel is allowed only while `PLACED` or `CONFIRMED`.
4. Recoveries are offered — track delivery (FL-03) or contact support — so the screen is never a dead end (NFR-012).
5. The refusal is server-side; nothing is cancelled and no refund starts.

## Alternative Scenarios
- **A1 — Still inside the window:** cancel succeeds with a reason → `CANCELLED` and the refund flow runs (BR-ORD-04).
- **A2 — Vendor/admin cancels later:** the customer sees `CANCELLED` in the timeline with the refund (BR-ORD-04).
- **A3 — Delivered instead:** the cancel path is replaced by the return entry point (UC-350).

## Exception Scenarios
- **E1 — State crosses the boundary mid-request:** optimistic guard decides — the refusal stands; no partial write (edge-cases EC-14).
- **E2 — Stale cached action:** after refetch the control is hidden; the conflict banner explains (UC-335).
- **E3 — Refund asked for anyway:** no refund row exists — cancellation never happened (BR-ORD-03).

## Postconditions
- Success (refusal): order state unchanged, no cancellation history row, no refund.
- Success (allowed): `CANCELLED` with refund pending and an append-only history entry (BR-ORD-04).

## Business Rules Applied
- BR-ORD-04, BR-ORD-01

## Related Requirements
- FR-012 (Order Lifecycle Management — customer cancel window)
- **Relation:** UC-012 shows the order detail; UC-335 handles the same 409 generically; UC-350/UC-354 are the post-delivery alternatives.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own order only; cancel permitted solely while `PLACED`/`CONFIRMED` — vendor/admin until `READY_FOR_PICKUP`.
- **Data involved:** order state, cancel attempt payload, error mapping — no writes on refusal.
- **External dependencies:** order service (B06); refund engine (B07) only when cancellation succeeds.

## Acceptance Criteria
- **AC-UC337-01:** Given an order in `READY_FOR_PICKUP`, when the customer submits cancel, then `CANCEL_WINDOW_CLOSED` returns and the state is unchanged (BR-ORD-04).
- **AC-UC337-02:** Given the refusal, when the screen renders, then a localized explanation plus track/support recoveries show (NFR-012).
- **AC-UC337-03:** Given an order still `CONFIRMED`, when cancel with a reason is submitted, then it transitions to `CANCELLED` and the refund flow starts (BR-ORD-04).
- **AC-UC337-04:** Given the refusal, when the response returns, then no cancellation history row and no refund row exist (BR-ORD-03).
