# UC-341 — Upload a Bank-Transfer Slip for Admin Verification

## Header Info
- **Use Case ID:** UC-341
- **Title:** Upload a Bank-Transfer Slip for Admin Verification
- **Actor:** Customer (ACT-01)
- **Trigger:** A bank-transfer top-up awaits proof of payment before the wallet can be credited
- **Priority:** P1
- **Goal:** Attach the transfer slip so an admin can verify it — the wallet credits only after that verification.
- **Preconditions:** Top-up created with `method = BANK_TRANSFER` at `PENDING_VERIFICATION` (BR-PAY-04); beneficiary details shown (screen-states §6).

## Main Scenario
1. Customer selects the bank-transfer rail and copies the beneficiary details; the intent is `PENDING_VERIFICATION`.
2. Customer uploads the slip via `POST /wallet/topups/{id}/proof` — image/PDF within the shared size limit, scanned, EXIF stripped (API-WAL-005).
3. Status stays `PENDING_VERIFICATION` with the submitted reference, expected SLA and edit/cancel affordance (screen-states §6).
4. An admin verifies the reference (`POST /admin/topups/{id}/verify`, admin.md) → the wallet is credited with ledger rows (BR-PAY-04, BR-PAY-06).
5. Customer sees `CREDITED` on the top-up detail and the new transaction row (API-WAL-004).

## Alternative Scenarios
- **A1 — Slip attached at initiation:** `proofFileId` rides on `POST /wallet/topups`; the same pending state follows.
- **A2 — Verification rejected:** status `REJECTED` with reason; the customer retries or picks another `C-05` rail.
- **A3 — Customer cancels before verification:** the pending intent is cancelled and no credit ever posts (screen-states §6).

## Exception Scenarios
- **E1 — File too large or wrong type:** `PAYLOAD_TOO_LARGE`/`UNSUPPORTED_MEDIA_TYPE`; no proof row is created.
- **E2 — Malware scan fails:** `FILE_SCAN_FAILED`; upload is rejected and the customer retries (api-conventions upload rules).
- **E3 — Admin backlog:** the pending status stays visible and the customer is notified of the pending state (edge-cases EC-22).

## Postconditions
- Success: proof attached; after admin verification the wallet is credited exactly once with balanced ledger rows.
- Failure: no proof row for rejected uploads; no credit and unchanged balance while unverified (BR-PAY-04).

## Business Rules Applied
- BR-PAY-04, BR-PAY-06

## Related Requirements
- FR-013 (Wallet & Payment Processing — bank-transfer top-up)
- **Relation:** UC-041 initiates top-ups; UC-340 covers the provider-rail branch; UC-339 lists the credited rows; UC-344 bounds-checks the amount.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own top-up only; verification itself is admin-only (ACT-04) — the customer can never self-credit.
- **Data involved:** top-up intent, bank reference, proof file, status transitions, ledger rows on credit.
- **External dependencies:** admin verification queue (B13, INT-REQ-002); file storage with scan validation; ledger service (B07).

## Acceptance Criteria
- **AC-UC341-01:** Given a `PENDING_VERIFICATION` top-up, when a valid slip is uploaded, then a proof id returns and status stays `PENDING_VERIFICATION` (BR-PAY-04).
- **AC-UC341-02:** Given admin verification, when credit posts, then balanced ledger rows exist exactly once (BR-PAY-06).
- **AC-UC341-03:** Given an oversized file, when uploaded, then `PAYLOAD_TOO_LARGE` returns and no proof row exists.
- **AC-UC341-04:** Given an unverified reference, when the wallet is read, then the balance is unchanged (BR-PAY-04).
