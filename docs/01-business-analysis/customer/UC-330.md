# UC-330 — Resume Checkout After Topping Up the Wallet Shortfall

## Header Info
- **Use Case ID:** UC-330
- **Title:** Resume Checkout After Topping Up the Wallet Shortfall
- **Actor:** Customer (ACT-01)
- **Trigger:** The wallet balance is below the order total at the wallet-payment/review step
- **Priority:** P0
- **Goal:** Show the exact shortfall, take the customer through a top-up, and return them to checkout with all state preserved.
- **Preconditions:** Checkout session open with computed totals (FR-011); `wallet.balance < totals.grandTotal` (BR-CRT-06); top-up rails available (C-05, FR-013).

## Main Scenario
1. Server reports `wallet.shortfall` at the wallet-payment step → a blocking panel shows the shortfall (BR-CRT-06).
2. Primary action "شحن الرصيد / Top up wallet" deep-links to `/{locale}/account/wallet/top-up` with return-to-checkout; no order row exists (screen-states §6).
3. Customer picks a rail and enters an amount within 1,000–5,000,000 YER (BR-PAY-02, UC-041).
4. Provider rail credits only on a verified callback; a bank transfer waits for admin verification (BR-PAY-03/BR-PAY-04) while the pending state is shown.
5. On credit, balanced ledger rows post (BR-PAY-06); the customer returns to checkout with cart, address and step preserved, the balance gate passes, and confirm proceeds (UC-011).

## Alternative Scenarios
- **A1 — Top-up still short:** the panel reappears with the new shortfall; the loop repeats until covered.
- **A2 — Provider pending beyond 15 minutes:** "still checking" plus a support link — never a manual "credit me" button (screen-states §6).
- **A3 — Wallet frozen:** top-up is refused (`WALLET_FROZEN`) and the frozen-wallet banner with support CTA shows (BR-PAY-09).

## Exception Scenarios
- **E1 — Provider rejects the top-up:** error with reason and "try another method"; only the three `C-05` rails are offered.
- **E2 — Checkout session expires during the top-up:** the session must restart; the cart is intact and totals recompute (BR-CRT-04).
- **E3 — Price changed while topping up:** on return the price-change re-confirmation gates confirm first (UC-327).

## Postconditions
- Success: wallet credited exactly once with ledger rows; checkout resumes at the preserved step — still no order until confirm.
- Failure: no order row, no partial debit; cart, address and shortfall panel state preserved for a retry.

## Business Rules Applied
- BR-CRT-06, BR-PAY-02, BR-PAY-03, BR-PAY-06

## Related Requirements
- FR-011 (Checkout & Order Placement — balance gate), FR-013 (Wallet & Payment Processing — top-ups)
- **Relation:** UC-041 runs the top-up; UC-161/UC-164 preview balance and totals; UC-011 completes the resumed checkout.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own wallet and own checkout session only — balance is owner-scoped.
- **Data involved:** wallet balance, top-up intent, ledger rows (append-only), checkout session, cart snapshot.
- **External dependencies:** m-Floos/OneCash providers (DEP-05, BR-PAY-03); admin verification queue (B13, BR-PAY-04); ledger service (B07).

## Acceptance Criteria
- **AC-UC330-01:** Given balance < total, when the review step loads, then the blocking panel shows the shortfall and no order row exists (BR-CRT-06).
- **AC-UC330-02:** Given a 999 YER top-up, when submitted, then it is rejected by the 1,000–5,000,000 YER bounds (BR-PAY-02).
- **AC-UC330-03:** Given a verified provider callback, when credit posts, then balanced ledger rows exist and the balance increases once (BR-PAY-06).
- **AC-UC330-04:** Given the credited balance, when the customer returns, then checkout resumes with cart, address and step preserved and confirm succeeds.
