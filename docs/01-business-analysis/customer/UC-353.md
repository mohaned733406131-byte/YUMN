# UC-353 — Read the Refund Composition (Item Value Versus Shipping)

## Header Info
- **Use Case ID:** UC-353
- **Title:** Read the Refund Composition (Item Value Versus Shipping)
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the refund detail to see exactly what is being returned to the wallet
- **Priority:** P2
- **Goal:** Explain the composition — item value always, shipping only for platform/vendor fault — with no invented numbers.
- **Preconditions:** Refund composed or pending for the order (FR-016); composition rule is fixed (BR-RET-03); refund receipt reachable (API-WAL-014, API-RET-003).

## Main Scenario
1. Customer opens the refund detail from the return or the order → composition lines render (WF-007 step 7).
2. Item value per returned line is shown; the shipping line appears only when the fault is platform/vendor-side (BR-RET-03).
3. Buyer-side returns explain that shipping was not refundable — the reason is stated, not implied (FL-04 step 2 toggle).
4. Amounts are server-composed and displayed as integer YER with locale digits (BR-FIN-05, BR-PAY-10).
5. Once credited, a deep link opens the wallet ledger row for the same amount (UC-339).

## Alternative Scenarios
- **A1 — Partial return:** only the returned lines' value appears in the composition.
- **A2 — Free-shipping coupon order:** the shipping line reads 0 — nothing to refund, composition unaffected.
- **A3 — Refund still pending:** `PENDING`/`COMPOSED` status with the expected credit date (UC-343).

## Exception Scenarios
- **E1 — Composition not yet computed:** status `PENDING` only — no amounts are fabricated on screen.
- **E2 — Detail fetch fails:** page error with retry; money views never show estimates (BR-PAY-06).
- **E3 — Customer disputes the composition:** admin is the final arbiter with an audited decision (BR-RET-06).

## Postconditions
- Success: composition displayed exactly as composed server-side; read-only — no ledger writes from viewing.
- Failure: no invented or rounded-inconsistent amounts; the ledger stays untouched.

## Business Rules Applied
- BR-RET-03, BR-RET-04

## Related Requirements
- FR-016 (Returns & Refunds — refund composition)
- **Relation:** UC-343 reports status and credit date; UC-352 triggers the refund via auto-approve; UC-350 opens the return; UC-338 is the original receipt.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own refund detail only — foreign orders return `404` (API-WAL-014).
- **Data involved:** returned lines, item values, shipping-refundable flag, composed amount, wallet credit reference.
- **External dependencies:** returns service (B09); refund engine and ledger (B07); locale formatting (BR-PLT-05).

## Acceptance Criteria
- **AC-UC353-01:** Given a platform-fault return, when composition renders, then item value and shipping appear as separate lines (BR-RET-03).
- **AC-UC353-02:** Given a buyer-side return, when composition renders, then only item value shows with a shipping-not-refunded explanation (BR-RET-03).
- **AC-UC353-03:** Given any composed amount, when displayed, then integer YER with locale digits matches the server value exactly (BR-PAY-10, BR-FIN-05).
- **AC-UC353-04:** Given a pending refund, when opened, then status plus expected credit date show with no fabricated credit (BR-RET-04).
