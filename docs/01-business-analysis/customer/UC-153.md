# UC-153 — Request Account Deletion

## Header Info
- **Use Case ID:** UC-153
- **Title:** Request Account Deletion
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens Account → Privacy → "Delete account" and confirms
- **Priority:** P1
- **Goal:** Schedule PII deletion with an explicit effective date while blocking the request until every obligation is settled.
- **Preconditions:** Customer authenticated; step-up OTP completed (UC-142, SEC-REQ-001); no deletion already pending (API-USR-012).

## Main Scenario
1. Confirmation screen explains the purge scope (profile, addresses, devices) and the retention of financial records for ≥5 years (DATA-REQ-003).
2. Client sends `POST /users/me/deletion-request { confirmation: "DELETE", otpCode }` (API-USR-012) with the step-up code.
3. System checks blocking conditions — open orders, active returns/disputes, non-zero wallet balance, pending vendor payouts, an active store → `DELETION_BLOCKED` listing `details[]` so the customer can settle them first.
4. With no blockers → `201 { requestId, status: "PENDING", effectiveAt, purgeScope, retention }` — nothing is purged yet; only the schedule exists (FR-003).
5. The privileged action appends an audit entry (BR-PLT-06) and the customer is notified; until `effectiveAt` the request can be cancelled (UC-154).

## Alternative Scenarios
- **A1 — Blocked by obligations:** `DELETION_BLOCKED` with the reason list; customer settles them and re-requests.
- **A2 — Request already pending:** `DELETION_PENDING` — no duplicate request is created.

## Exception Scenarios
- **E1 — Missing or invalid step-up code:** `OTP_NOT_VERIFIED` → no request row exists (SEC-REQ-001).
- **E2 — Network error after submit:** client retries; `DELETION_PENDING` reveals whether the first attempt already landed.
- **E3 — Request reaches `effectiveAt`:** deletion executes; cancellation is no longer possible (UC-154).

## Postconditions
- Success: PENDING deletion scheduled with a future `effectiveAt`; account still fully active; audit entry appended (BR-PLT-06).
- Failure: no request created; account untouched.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-003 (User & Profile Management)

## Permissions / Data / External Dependencies
- **Permissions:** owner-scoped action guarded by step-up OTP; nobody can request deletion for another account.
- **Data involved:** deletion request row (status, effectiveAt, purge scope), profile/addresses/devices PII, financial records retained per DATA-REQ-003, audit log.
- **External dependencies:** background purge job executing at `effectiveAt`.

## Acceptance Criteria
- **AC-UC153-01:** Given a valid OTP and no blockers, when submitted, then `201` returns a PENDING request whose `effectiveAt` is in the future.
- **AC-UC153-02:** Given an open order, when submitted, then `DELETION_BLOCKED` lists the blocker and no request is created.
- **AC-UC153-03:** Given a PENDING request, when audited, then an append-only privileged-action entry exists (BR-PLT-06).
