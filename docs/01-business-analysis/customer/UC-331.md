# UC-331 — Retry a Duplicate Confirm and Receive the Original Order

## Header Info
- **Use Case ID:** UC-331
- **Title:** Retry a Duplicate Confirm and Receive the Original Order
- **Actor:** Customer (ACT-01)
- **Trigger:** The confirm request is sent twice (double-tap, retry, flaky network) with the same idempotency key
- **Priority:** P0
- **Goal:** Return the original order on every replay — one order, one debit, one stock deduction, whatever the client does.
- **Preconditions:** Checkout session ready at confirm (FR-011); `Idempotency-Key` attached to `POST /orders` (BR-PLT-03); first attempt in flight or completed (EC-11).

## Main Scenario
1. Customer taps confirm; the client sends `POST /orders` carrying the checkout's `Idempotency-Key` (BR-PLT-03).
2. A duplicate arrives — same key (double-tap or retry after a lost response).
3. If the first call is still in flight: `IDEMPOTENCY_IN_PROGRESS`, the client waits and retries (BR-ORD-06).
4. If it completed: the server returns the **original** order with its original status code — no second row (BR-ORD-06).
5. Exactly one wallet debit, one escrow funding and one stock deduction exist (EC-11); the confirmation screen renders for that order.

## Alternative Scenarios
- **A1 — Local double-tap:** the button is disabled in-flight and the same key yields the single order (BR-ORD-06).
- **A2 — Retry after app restart:** the stored key with the checkout still maps to the original order.
- **A3 — Key reused with different payloads:** `IDEMPOTENCY_CONFLICT`; no order is created and the client re-keys a genuine new confirm.

## Exception Scenarios
- **E1 — First attempt failed mid-saga:** compensating actions rolled everything back — no order, no debit — so the retry executes the creation exactly once (BR-PLT-04).
- **E2 — Concurrent duplicates race:** one commits, the other receives `IDEMPOTENCY_IN_PROGRESS` then the original order.
- **E3 — Wallet error during the first attempt:** idempotency prevents any double charge; the ledger shows at most one debit set (BR-PAY-08).

## Postconditions
- Success: exactly one master order with its sub-orders in `PLACED`, one wallet debit, one ledger set, one confirmation notification.
- Failure: no second order/debit/stock deduction; the original order and wallet remain exactly as first written.

## Business Rules Applied
- BR-ORD-06, BR-PLT-03, BR-PAY-08, BR-PLT-04

## Related Requirements
- FR-011 (Checkout & Order Placement — idempotent order creation)
- **Relation:** UC-011 performs the first confirm; UC-327 gates price re-confirmation before it; UC-012 shows the resulting order.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner cart/session — the key is scoped to the caller's checkout; a foreign key returns 404.
- **Data involved:** idempotency key record, master/sub-orders, `order_status_history`, wallet balance, ledger rows, stock deduction.
- **External dependencies:** order service (B06); wallet/ledger service (B07); inventory deduction (B02).

## Acceptance Criteria
- **AC-UC331-01:** Given a completed confirm, when the same key is replayed, then the original order is returned with its original status code (BR-ORD-06).
- **AC-UC331-02:** Given two duplicate submissions, when both finish, then exactly one wallet debit and one stock deduction exist (EC-11).
- **AC-UC331-03:** Given the first attempt is still in flight, when the duplicate arrives, then `IDEMPOTENCY_IN_PROGRESS` returns and no second row is created.
- **AC-UC331-04:** Given a mid-saga failure rolled back, when the retry runs with the same key, then exactly one order is created (BR-PLT-04).
