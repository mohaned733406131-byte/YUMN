# UC-358 — Keep Using the App When Push Permission Is Denied

## Header Info
- **Use Case ID:** UC-358
- **Title:** Keep Using the App When Push Permission Is Denied
- **Actor:** Customer (ACT-01)
- **Trigger:** The OS push permission is denied (or never granted) and notifications must still arrive
- **Priority:** P1
- **Goal:** Keep every task and every notification working — push is convenience, never a precondition.
- **Preconditions:** Push not granted at OS level; in-app center exists (FR-017); other channels per preferences (BR-NTF-01).

## Main Scenario
1. With push denied, the app continues normally — browsing, cart, checkout and tracking all work (screen-states §5).
2. The preference center's Push column shows a "blocked at system level" state with device-level instructions; other columns stay usable (feedback §2.2-3).
3. Notifications still reach the customer: in-app inbox as the guaranteed channel, plus SMS/WhatsApp per preferences (FR-017, BR-NTF-01).
4. The push prompt is re-asked only at the next order placement or delivery event — never nag loops (feedback §3).
5. The customer reads the missed events later from the inbox with unread badge (UC-355).

## Alternative Scenarios
- **A1 — Permission granted later:** token registration succeeds and push resumes without re-login (API-NTF-008).
- **A2 — Permanently denied:** the blocked state persists in the preference center; the in-app inbox remains the documented path (feedback §3).
- **A3 — Web browser blocked:** identical treatment; the header bell and inbox are unaffected.

## Exception Scenarios
- **E1 — Token registration fails:** `DEVICE_TOKEN_INVALID` → retry; other channels continue delivering.
- **E2 — All external channels fail:** the in-app record is still written — no silent data loss (NFR-007).
- **E3 — Offline:** cached inbox reads plus the offline banner; views auto-refresh on reconnect (screen-states §5).

## Postconditions
- Success: notifications still arrive through in-app and the remaining channels; every core task completes.
- Failure: no permission error blocks a task; no dead-end prompt and no crash.

## Business Rules Applied
- BR-NTF-01

## Related Requirements
- FR-017 (Notifications & Messaging — channel resilience)
- **Relation:** UC-355 reads the inbox fallback; UC-356/UC-357 manage the other channels; UC-043-style events are never push-dependent.

## Permissions / Data / External Dependencies
- **Permissions:** Any authenticated customer — no extra permission is granted by the app when push is denied.
- **Data involved:** push token registration state, preference matrix Push column, in-app notification records — no task data depends on push.
- **External dependencies:** OS push services (Android/iOS/web); notification service (B10); device registry (API-NTF-008/010).

## Acceptance Criteria
- **AC-UC358-01:** Given denied push permission, when an order event occurs, then the in-app inbox receives it (FR-017).
- **AC-UC358-02:** Given denial, when the preference center loads, then the Push column shows the blocked-at-system-level state with instructions (feedback §2.2-3).
- **AC-UC358-03:** Given denial, when core tasks run (browse, cart, checkout, tracking), then none of them require push (NFR-012).
- **AC-UC358-04:** Given denial, when prompt logic runs, then re-asking happens only at the next order or delivery event (feedback §3).
