# UC-345 — Read Wallet Amounts Correctly as Arabic-Indic Numerals with a Screen Reader

## Header Info
- **Use Case ID:** UC-345
- **Title:** Read Wallet Amounts Correctly as Arabic-Indic Numerals with a Screen Reader
- **Actor:** Customer (ACT-01)
- **Trigger:** A screen-reader user opens the wallet (or ledger rows) in the Arabic locale
- **Priority:** P2
- **Goal:** Announce every money value as a real number — Arabic-Indic digits, no glyph-by-glyph reading, no abbreviation.
- **Preconditions:** Wallet readable (FR-013); `ar` locale active (BR-PLT-05); amounts stored as integer YER (BR-PAY-10).

## Main Scenario
1. Customer opens the wallet → balance and rows render as integer YER with Arabic-Indic digits and the `ر.ي` suffix (BR-PAY-10, screen-states §6).
2. Tabular numerals keep columns aligned; abbreviations such as "1.5M" are forbidden for money.
3. The screen reader announces the whole string as a number — e.g. "١٥٬٠٠٠ ريال يمني" — never isolated glyphs (accessibility § numerals rule).
4. Each transaction row announces type, amount and `balanceAfter` in reading order.
5. A credit updates the balance with a polite live-region announcement, without stealing focus (NFR-011).

## Alternative Scenarios
- **A1 — Locale switched to `en`:** the same values re-render in Latin digits with `YER` (NFR-013).
- **A2 — TalkBack/VoiceOver on mobile:** identical pronunciation behavior on the RN app (accessibility RN parity).
- **A3 — Balance update on screen:** announced politely once — no repeated spam.

## Exception Scenarios
- **E1 — Digits announced as isolated glyphs:** fails the WCAG AA acceptance run — copy/encoding fix required (NFR-011).
- **E2 — Partial ledger fetch:** loaded rows render; the failed section shows a block error (screen-states §1 partial data).
- **E3 — Latin digits rendered in `ar`:** a BR-PAY-10 violation that must never ship.

## Postconditions
- Success: every wallet amount is readable as a number in the active locale, on web and RN.
- Failure: no abbreviated or floating-point money string appears anywhere on the wallet.

## Business Rules Applied
- BR-PAY-10

## Related Requirements
- FR-013 (Wallet & Payment Processing — amount display)
- **Relation:** UC-339 filters the ledger read here; UC-161 previews balance; UC-343 shows refund credits — all reuse the same numeral rules.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own wallet only — accessibility behavior adds no extra privileges.
- **Data involved:** wallet balance, transaction amounts, `balanceAfter`, locale setting — display only.
- **External dependencies:** locale number formatting (BR-PLT-05, NFR-013); screen-reader engines (TalkBack/VoiceOver/browser SR).

## Acceptance Criteria
- **AC-UC345-01:** Given the `ar` locale, when the balance renders, then Arabic-Indic integer digits with the `ر.ي` suffix show (BR-PAY-10).
- **AC-UC345-02:** Given a screen reader reading the balance, when announced, then the value is pronounced as a number, not glyph-by-glyph (NFR-011).
- **AC-UC345-03:** Given any money value, when displayed, then no abbreviation or decimal float appears (BR-PAY-10).
- **AC-UC345-04:** Given the `en` locale, when the wallet renders, then Latin digits with the `YER` suffix show (NFR-013).
