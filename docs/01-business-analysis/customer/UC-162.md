# UC-162 — Apply and Validate a Coupon at Checkout

## Header Info
- **Use Case ID:** UC-162
- **Title:** Apply and Validate a Coupon at Checkout
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer enters a coupon code on the checkout payment/review step
- **Priority:** P1
- **Goal:** Validate a single coupon server-side against the current cart and fold its discount into the authoritative checkout totals before the order is created.
- **Preconditions:** Authenticated customer; cart populated (UC-009/UC-010); checkout session started; a coupon code is available to the customer.

## Main Scenario
1. Customer enters a code → client `POST /coupons/validate` (API-CNT-004) sends the code plus the cart snapshot; the server is the only judge of validity.
2. System enforces one coupon per order — codes are never merged or stacked (BR-PRM-02).
3. System evaluates the coupon constraints: optional `min_order_amount`, per-user and global usage limits, validity window; expired or fully-used codes are rejected before any order row exists (BR-PRM-04).
4. On success the response returns `valid: true` with `discountAmount` in integer YER; the checkout session `POST /checkout/session` re-applies it to per-store totals for re-confirmation.
5. A `free_shipping` coupon zeroes the shipping fee in the session response (cross-reference: UC-011 step3, free_shipping only).
6. Customer reviews the discounted breakdown (integer YER) and confirms; the code rides into `POST /orders` under the same `Idempotency-Key`.

## Alternative Scenarios
- **A1 — Under minimum order:** valid code but cart below `min_order_amount` → `COUPON_INVALID` with `details[].issue = MIN_NOT_MET`; customer sees the shortfall (BR-PRM-04).
- **A2 — Remove the coupon:** customer clears the code → totals recompute without discount; the single coupon slot is free again (BR-PRM-02).
- **A3 — Already-applied coupon view:** the checkout shows the active code and its discounted totals until replaced or removed.

## Exception Scenarios
- **E1 — Invalid/expired/used code:** `COUPON_INVALID` (`NOT_FOUND`/`EXPIRED`/`USAGE_LIMIT_REACHED`/`ALREADY_USED_BY_USER`); no order row is created (BR-PRM-06).
- **E2 — Stacking attempt:** a second code is submitted → `COUPON_STACKING_NOT_ALLOWED`; the order stays single-coupon (BR-PRM-02).
- **E3 — Limit exhausted between validate and confirm:** server re-validates at `POST /orders` → `COUPON_INVALID`, order creation aborts, no wallet debit (BR-PRM-04, BR-PRM-06).

## Postconditions
- Success: one coupon applied; per-store totals reflect the discount in integer YER; a confirmed order carries the discounted grand total.
- Failure: validation error only — no order row, no wallet movement, cart unchanged.

## Business Rules Applied
- BR-PRM-02, BR-PRM-04, BR-PRM-06

## Related Requirements
- FR-011 (Checkout & Order Placement), FR-019 (Content & Promotions — coupon engine)
- **Relation:** UC-011 step3 (free_shipping only) — shipping fee zeroing during the checkout session.

## Permissions / Data / External Dependencies
- **Permissions:** customer applies coupons only to their own checkout session; codes are never trusted from the client payload.
- **Data involved:** cart snapshot, coupon code, checkout session totals, order row (only on success).
- **External dependencies:** content/promotion service (B12 coupon engine); checkout service (B05).

## Acceptance Criteria
- **AC-UC162-01:** Given a valid coupon, when `POST /coupons/validate` runs with the cart, then `valid: true` and an integer-YER `discountAmount` are returned.
- **AC-UC162-02:** Given one coupon already applied, when a second code is submitted, then `COUPON_STACKING_NOT_ALLOWED` is returned (BR-PRM-02).
- **AC-UC162-03:** Given an expired or fully-used coupon, when validated, then `COUPON_INVALID` is returned and no order row exists (BR-PRM-06).
- **AC-UC162-04:** Given a cart below `min_order_amount`, when validated, then `MIN_NOT_MET` is reported and checkout cannot create the order (BR-PRM-04).
