# UC-346 — Retrieve the Delivery Code In-App When No SMS Arrives

## Header Info
- **Use Case ID:** UC-346
- **Title:** Retrieve the Delivery Code In-App When No SMS Arrives
- **Actor:** Customer (ACT-01)
- **Trigger:** The order is `OUT_FOR_DELIVERY` but the SMS with the 6-digit code never arrives
- **Priority:** P0
- **Goal:** Give the customer the same code in-app so the handover never depends on one channel.
- **Preconditions:** Order reached `OUT_FOR_DELIVERY` and the code was issued to the buyer (BR-SHP-02); customer owns the order (FR-015); tracking screen reachable (FL-03).

## Main Scenario
1. At `OUT_FOR_DELIVERY` the system issues the 6-digit code via SMS, WhatsApp and in-app (API-SHP-009, BR-SHP-02).
2. No SMS arrives → the customer opens tracking (`/{locale}/track/{order-id}` or order detail).
3. The code panel renders masked digits with a reveal toggle, copy action and plain-language handover copy (FL-03 step 3).
4. The panel reads the code via `GET /orders/{id}/delivery-code` — owner-only and only while `OUT_FOR_DELIVERY` (API-SHP-013).
5. The customer hands the code to the courier on receipt → verification moves the order to `DELIVERED` (BR-ORD-08).

## Alternative Scenarios
- **A1 — SMS arrives late:** identical code; the in-app panel stays the authoritative view.
- **A2 — WhatsApp delivered:** the failover channel carries the same code (BR-NTF-03, INT-REQ-003).
- **A3 — Order already delivered:** the panel is gone and the fetch returns `STATE_CONFLICT`; the proof screen shows instead.

## Exception Scenarios
- **E1 — Wrong state (not `OUT_FOR_DELIVERY`):** `NOT_FOUND`/`STATE_CONFLICT`; the code is never exposed outside its window.
- **E2 — Foreign order id:** `404` — the code is never revealed to a non-owner (BR-ORD-09).
- **E3 — In-app fetch fails:** retry with the page-error pattern; SMS/WhatsApp remain — no code is ever fabricated client-side.

## Postconditions
- Success: the customer holds the correct code and the courier verification path is unchanged.
- Failure: no code is exposed to non-owners; after `DELIVERED` the code is hidden again (API-SHP-013).

## Business Rules Applied
- BR-SHP-02, BR-NTF-03

## Related Requirements
- FR-015 (Shipping & Delivery — code confirmation), FR-017 (Notifications & Messaging — issuance channels)
- **Relation:** UC-013 covers the handoff panel; UC-349 is the tracking view around it; UC-348 handles lockout after failed entries.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, order owner only — the full code is visible to the buyer alone (BR-SHP-02).
- **Data involved:** delivery code, issue timestamp, attempts remaining, order state — read-only for the customer.
- **External dependencies:** SMS/WhatsApp providers (DEP-06, INT-REQ-003/004); delivery service (B08); in-app inbox (B10).

## Acceptance Criteria
- **AC-UC346-01:** Given an order in `OUT_FOR_DELIVERY`, when tracking opens, then the 6-digit code renders masked with a reveal toggle (BR-SHP-02).
- **AC-UC346-02:** Given SMS failure, when the in-app endpoint runs, then the same issued code returns for the order owner (API-SHP-013).
- **AC-UC346-03:** Given the order is `DELIVERED`, when the endpoint runs, then the code is hidden (`STATE_CONFLICT`).
- **AC-UC346-04:** Given another customer's order id, when the code is requested, then `404` returns and no code is revealed (BR-ORD-09).
