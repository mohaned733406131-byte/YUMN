# UC-355 — Filter the Notification Inbox by Category and Unread State

## Header Info
- **Use Case ID:** UC-355
- **Title:** Filter the Notification Inbox by Category and Unread State
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the in-app inbox and narrows it by category tab and/or unread state
- **Priority:** P2
- **Goal:** Reach the wanted notification fast without altering or deleting anything — security notices stay put.
- **Preconditions:** Authenticated customer with an in-app inbox (FR-017); notification records owner-scoped (API-NTF-001); inbox entry via bell/account (feedback §4).

## Main Scenario
1. Customer opens the inbox → the feed loads reverse-chronological with unread markers (conceptual `GET /notifications`).
2. Category tabs apply: All · Money · Orders · Store · Promotions — the Promotions tab is hidden when opted out (feedback §4, BR-NTF-05).
3. The unread-only toggle narrows further via `?unreadOnly`; unread rows carry tint, dot and bold title.
4. The unread badge (`GET /notifications/unread-count`) recomputes for the current view; per-row read stays granular.
5. Marking rows read updates the badge; SMS/WhatsApp/push deliveries are untouched — read state is in-app only.

## Alternative Scenarios
- **A1 — Empty category:** "لا إشعارات / You're all caught up" empty state with a preferences recovery (screen-states §3).
- **A2 — Mark all read:** badge clears for the scope; server records flip once (API-NTF-004).
- **A3 — Row deep link:** tapping a row opens the owning screen and keeps the read state (feedback §4 deep link).

## Exception Scenarios
- **E1 — Invalid category value:** `VALIDATION_ERROR`; the last valid list stays rendered (forms-and-validation §5).
- **E2 — Fetch fails:** block error with retry; the cached badge may show for ≤5 s (micro-cache) — rows are never invented.
- **E3 — Session expired:** re-auth prompt, then the inbox reopens with the same filters (routing §9).

## Postconditions
- Success: filtered inbox rendered in the active locale; read state persisted per record — nothing deleted.
- Failure: no notification row is removed by filtering; security notices remain dismissible only locally (BR-NTF-02).

## Business Rules Applied
- BR-NTF-01, BR-NTF-05

## Related Requirements
- FR-017 (Notifications & Messaging — in-app inbox)
- **Relation:** UC-356/UC-357 manage the preferences behind the tabs; UC-336 lands escalation notices here; UC-043-style security rows stay pinned.

## Permissions / Data / External Dependencies
- **Permissions:** Any authenticated customer, own inbox only — foreign notifications return `404` (API-NTF-003).
- **Data involved:** notification records (category, read state, deep link), unread counts, filter/tab state — no channel deliveries altered.
- **External dependencies:** notification service (B10); BullMQ fan-out records (BR-PLT-01); locale strings (BR-NTF-04).

## Acceptance Criteria
- **AC-UC355-01:** Given unread and read rows, when unread-only is applied, then only unread rows render.
- **AC-UC355-02:** Given a category tab selected, when the feed runs, then only that category renders and the badge recomputes.
- **AC-UC355-03:** Given an empty result, when rendered, then the localized empty state plus preferences recovery shows (NFR-012).
- **AC-UC355-04:** Given any filtering, when rows load, then no notification row is deleted or marked read implicitly.
