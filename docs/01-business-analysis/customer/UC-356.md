# UC-356 — Disable a Marketing Channel Without Silencing Order Alerts

## Header Info
- **Use Case ID:** UC-356
- **Title:** Disable a Marketing Channel Without Silencing Order Alerts
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer turns off a marketing/promotion channel in the preference center
- **Priority:** P1
- **Goal:** Stop promotional messages on one channel while order and delivery alerts keep flowing.
- **Preconditions:** Preference center open (`/{locale}/account/notifications`); category × channel matrix loaded (API-NTF-006); marketing categories default OFF (feedback §2.1).

## Main Scenario
1. Customer locates the marketing row (Platform & promotions) and switches a channel off — e.g. WhatsApp or SMS.
2. The toggle saves optimistically via `PUT /notifications/preferences` with the updated cell (API-NTF-007).
3. The server stores the per-category, per-channel opt-out — disabling WhatsApp marketing never touches SMS orders (feedback §2.2-1, BR-NTF-05).
4. Order, delivery and wallet categories remain ON — transactional fan-out is unaffected (feedback §2.1).
5. Later marketing fan-out skips that category+channel; order events still deliver on the opted-in channels.

## Alternative Scenarios
- **A1 — Re-enable:** the same grid turns the channel back on; it applies to the next event.
- **A2 — Several channels at once:** each cell saves independently; failures roll back per cell.
- **A3 — Email looked for:** no email column exists anywhere — v1 has four channels only (BR-NTF-01).

## Exception Scenarios
- **E1 — Save fails:** rollback toast and the previous matrix is restored (feedback §2.2-2).
- **E2 — Security category attempted:** `PREFERENCE_IMMUTABLE` — the change is refused (UC-357, BR-NTF-02).
- **E3 — Offline:** the write is blocked with an explanation; drafts are not silently dropped (screen-states §5).

## Postconditions
- Success: the marketing channel is off in stored preferences; order/delivery alerts and security notices are untouched.
- Failure: no blanket opt-out occurred; no security preference changed.

## Business Rules Applied
- BR-NTF-05, BR-NTF-02

## Related Requirements
- FR-017 (Notifications & Messaging — preferences)
- **Relation:** UC-357 shows the locked security rows; UC-355 is the inbox these preferences shape; UC-358 covers denied push alongside them.

## Permissions / Data / External Dependencies
- **Permissions:** Any authenticated customer, own preference matrix only — changes stored server-side, not just mirrored in UI.
- **Data involved:** notification preference rows (category × channel), optimistic toggle state, rollback toast.
- **External dependencies:** notification service (B10); preference API (API-NTF-007); localized copy (BR-NTF-04).

## Acceptance Criteria
- **AC-UC356-01:** Given a marketing channel disabled, when an order event fans out, then order alerts still deliver on the remaining channels (BR-NTF-05).
- **AC-UC356-02:** Given WhatsApp marketing off, when an order event occurs, then SMS order delivery still occurs (BR-NTF-05).
- **AC-UC356-03:** Given the save succeeds, when preferences reload, then the matrix reflects the disabled cell (BR-NTF-05).
- **AC-UC356-04:** Given the save fails, when rollback runs, then the prior matrix shows with a failure toast (feedback §2.2-2).
