# UC-359 — Add a Message and Attachment to an Open Support Ticket Thread

## Header Info
- **Use Case ID:** UC-359
- **Title:** Add a Message and Attachment to an Open Support Ticket Thread
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer has more to say on an already-open support ticket
- **Priority:** P2
- **Goal:** Append a reply with an optional attachment to the existing thread — never reopen or duplicate a ticket.
- **Preconditions:** Customer owns a ticket in `OPEN`/`IN_PROGRESS` (FR-020); thread readable (`GET /support/tickets/{id}`, API-ADM-037); upload rules available (api-conventions §10).

## Main Scenario
1. Customer opens the own ticket → the full message thread plus linked order/delivery entities render (API-ADM-037).
2. Customer writes a reply and optionally attaches files → `POST /support/tickets/{id}/messages` with `body` and `attachmentFileIds` (API-ADM-038).
3. Attachments pass the shared validation: type/size checked and scanned before they join the message (admin.md upload notes).
4. The message appends to the thread; once a staff member replies the status moves to `IN_PROGRESS` (API-ADM-038).
5. The customer returns to the thread later and sees their message in order with the staff replies.

## Alternative Scenarios
- **A1 — Message only:** the same endpoint with just `body` — attachments are optional.
- **A2 — Staff replies first:** status flips to `IN_PROGRESS` and the reply arrives with `unreadFromSupport` on the feed.
- **A3 — Auto-created lockout ticket:** the same thread mechanics apply (UC-348).

## Exception Scenarios
- **E1 — Ticket resolved/closed:** `TICKET_STATE_CONFLICT`; the thread is unchanged and no row is written.
- **E2 — Invalid attachment:** `PAYLOAD_TOO_LARGE`/`UNSUPPORTED_MEDIA_TYPE`/`FILE_SCAN_FAILED`; the message is not posted half-attached.
- **E3 — Foreign ticket:** `404` — another customer's thread never leaks (ownership scope).

## Postconditions
- Success: one new message row (+ attachments) in the own open thread; status consistent.
- Failure: no partial message, no duplicate ticket created, no state change beyond `IN_PROGRESS`.

## Business Rules Applied
- BR-PLT-05

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit — support tickets)
- **Relation:** UC-348 creates the lockout ticket this thread may belong to; UC-360 rates the resolution afterwards; UC-014/UC-342 open tickets.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own tickets only — visible to the opener and assigned staff; foreign tickets `404` (admin.md thread integrity).
- **Data involved:** ticket thread messages, attachment file ids, ticket status, linked entity references.
- **External dependencies:** support ticketing module (B13); file storage with scan validation; admin/support console for replies (FR-020).

## Acceptance Criteria
- **AC-UC359-01:** Given an open own ticket, when a message is appended, then `201` returns and the message appears in the thread (API-ADM-038).
- **AC-UC359-02:** Given a resolved or closed ticket, when a message is appended, then `TICKET_STATE_CONFLICT` returns and the thread is unchanged.
- **AC-UC359-03:** Given a valid attachment within limits, when the message posts, then the attachment renders in the thread after scanning.
- **AC-UC359-04:** Given another customer's ticket id, when a message is posted, then `404` returns and no row is written.
