# UC-171 — Open a Dispute on a Delivered Order

## Header Info
- **Use Case ID:** UC-171
- **Title:** Open a Dispute on a Delivered Order
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer chooses Dispute on a delivered/completed order
- **Priority:** P0
- **Goal:** Escalate a delivered sub-order into `DISPUTED`, freezing its escrow release until the admin arbiter resolves the case.
- **Preconditions:** Authenticated; order owned by the customer; sub-order `DELIVERED`/`COMPLETED`; no dispute already open on that sub-order.

## Main Scenario
1. Customer opens the order → selects the sub-order, ground, optional note and evidence images → `POST /orders/{id}/dispute` (API-RET-013).
2. System validates state and single-dispute rule → `201 { disputeId, state: "DISPUTED", escrowFrozen: true, evidenceDueBy }`.
3. The sub-order enters `DISPUTED` and escrow release is frozen for all affected sub-orders until admin resolution (BR-ORD-05).
4. Where policy and dispute conflict, the admin is the final arbiter; the decision is written to the audit log (BR-RET-06).
5. Customer proceeds to submit evidence (UC-172) and later reads the outcome (UC-173).

## Alternative Scenarios
- **A1 — Return window also open:** customer picks one path per issue; an open dispute blocks a return on the same sub-order (E3 on UC-168).
- **A2 — Vendor opens the dispute first:** the customer sees it in their dispute list (UC-173) and joins with evidence.
- **A3 — Multi-sub-order master:** the request names a single `subOrderId`; other sub-orders and their escrow are unaffected.

## Exception Scenarios
- **E1 — Dispute already open:** `DISPUTE_ALREADY_OPEN`; no second dispute row (BR-ORD-05).
- **E2 — Order not deliverable yet / not found:** `STATE_CONFLICT` or `NOT_FOUND`.
- **E3 — Missing ground or evidence:** `EVIDENCE_REQUIRED`/`VALIDATION_ERROR`; no dispute row (BR-RET-06).

## Postconditions
- Success: sub-order `DISPUTED`, escrow frozen, evidence due date set, dispute visible to buyer/vendor/admin.
- Failure: no dispute row; order and escrow unchanged.

## Business Rules Applied
- BR-ORD-05, BR-RET-06

## Related Requirements
- FR-016 (Returns & Refunds — disputes), FR-012 (Order Lifecycle Management)
- **Relation:** UC-033 (admin side) — admin reviews, arbitrates and closes the dispute opened here.

## Permissions / Data / External Dependencies
- **Permissions:** buyer disputes own order; vendor may dispute its own sub-order; only admin resolves (BR-RET-06).
- **Data involved:** sub-order state, escrow hold, dispute row (ground, note, images), audit entry.
- **External dependencies:** returns/disputes service (B09); escrow service (B07); audit log (B13).

## Acceptance Criteria
- **AC-UC171-01:** Given a `DELIVERED` sub-order with no open dispute, when submitted, then `201` with state `DISPUTED` and `escrowFrozen: true` (BR-ORD-05).
- **AC-UC171-02:** Given an already-disputed sub-order, when submitted again, then `DISPUTE_ALREADY_OPEN` (BR-ORD-05).
- **AC-UC171-03:** Given an open dispute, when the escrow view is read, then that sub-order's release is frozen (BR-ORD-05).
- **AC-UC171-04:** Given an admin resolution, when recorded, then an audit entry exists (BR-RET-06).
