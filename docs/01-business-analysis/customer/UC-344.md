# UC-344 — Reject a Top-Up Outside the 1,000-5,000,000 YER Bounds

## Header Info
- **Use Case ID:** UC-344
- **Title:** Reject a Top-Up Outside the 1,000-5,000,000 YER Bounds
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer enters a top-up amount below 1,000 YER or above 5,000,000 YER
- **Priority:** P2
- **Goal:** Reject the amount with a localized bounds message before any provider is contacted.
- **Preconditions:** Wallet exists and is usable (FR-013); top-up screen open (`/{locale}/account/wallet/top-up`); bounds are 1,000–5,000,000 YER inclusive (BR-PAY-02).

## Main Scenario
1. Customer enters an out-of-bounds amount (e.g. 999 YER or 5,000,001 YER) and submits.
2. The client hints inline, but the authoritative check runs server-side before any provider contact (API-WAL-003).
3. The request fails with `TOPUP_LIMIT` and the boundary-specific message (edge-cases EC-21).
4. The error maps to a localized inline message below the field — no raw code shown (forms-and-validation §5).
5. The customer corrects the amount into the valid range and the top-up proceeds to rail selection.

## Alternative Scenarios
- **A1 — Exact bounds:** 1,000 YER and 5,000,000 YER are accepted (inclusive bounds).
- **A2 — Valid amount, frozen wallet:** a different refusal — `WALLET_FROZEN` (UC-342).
- **A3 — Arabic-Indic digits typed:** normalized before validation; the same bounds apply (BR-PAY-10 display, i18n normalization).

## Exception Scenarios
- **E1 — Provider never contacted:** no pending top-up row and no ledger movement for the rejected attempt.
- **E2 — Network failure during submit:** retry is safe with the idempotency key — no duplicate intent (BR-PAY-08).
- **E3 — Repeated abuse:** stricter rate-limit tier applies to the top-up endpoint (screen-states §4 429 pattern).

## Postconditions
- Success: a pending top-up intent exists, exactly within bounds.
- Failure: no top-up row, no ledger movement, balance unchanged — the cart/wallet state stays intact.

## Business Rules Applied
- BR-PAY-02, BR-PAY-08

## Related Requirements
- FR-013 (Wallet & Payment Processing — top-up validation)
- **Relation:** UC-041 runs valid top-ups; UC-340 polls the provider branch; UC-341 uploads the bank slip; UC-330 tops up a checkout shortfall.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own wallet only; validation enforced server-side regardless of client checks.
- **Data involved:** top-up amount, validation errors, top-up intent row (only on success), ledger — untouched on rejection.
- **External dependencies:** wallet service (B07); localization strings for the bounds message (BR-PLT-05); rate limiter (SEC-REQ-009 tier on API-WAL-003).

## Acceptance Criteria
- **AC-UC344-01:** Given 999 YER, when submitted, then `TOPUP_LIMIT` returns and no top-up row exists (BR-PAY-02).
- **AC-UC344-02:** Given 5,000,001 YER, when submitted, then it is rejected the same way (BR-PAY-02).
- **AC-UC344-03:** Given 1,000 YER (or 5,000,000 YER), when submitted, then the top-up proceeds to rail selection (BR-PAY-02).
- **AC-UC344-04:** Given the rejection, when the form renders, then a localized bounds message shows below the field with no raw code.
