# UC-354 — Resolve a Conflict Between an Open Dispute and a New Return

## Header Info
- **Use Case ID:** UC-354
- **Title:** Resolve a Conflict Between an Open Dispute and a New Return
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer tries to open a return while a dispute is open on the same sub-order
- **Priority:** P2
- **Goal:** Refuse cleanly, explain the single-path rule, and route the customer to the active dispute.
- **Preconditions:** Dispute open on the sub-order with escrow frozen (BR-ORD-05); return precheck runs server-side (API-RET-001).

## Main Scenario
1. Customer submits a return for the disputed sub-order → server detects the open dispute (API-RET-001).
2. The request is rejected with `DISPUTE_ALREADY_OPEN`; no return row is created (returns.md error table).
3. UI explains that the dispute must resolve first and deep-links to the dispute detail with evidence panels (FL-07).
4. The admin resolves the dispute — buyer win runs the refund, vendor win returns the sub-order to `COMPLETED` (BR-RET-06).
5. Escrow unfreezes and, if the customer is still eligible, the return entry reopens (rejoins UC-350).

## Alternative Scenarios
- **A1 — Return open first, dispute attempted second:** `STATE_CONFLICT` — one path at a time; the active return continues.
- **A2 — Dispute resolved for the vendor:** the sub-order settles at `COMPLETED`; eligibility is re-evaluated from scratch (UC-350).
- **A3 — Customer still needs help:** a support ticket with the linked entities carries the case (UC-359).

## Exception Scenarios
- **E1 — Both submitted concurrently:** optimistic guard — one commits, the loser gets `409` and re-reads the state (BR-ORD-01).
- **E2 — Resolution fails:** nothing changes — the dispute stays open and escrow stays frozen (BR-ORD-05).
- **E3 — Foreign sub-order:** `404` — ownership enforced before any conflict logic (BR-ORD-09).

## Postconditions
- Success (refusal): no return row; the dispute and frozen escrow are unchanged.
- Success (after resolution): escrow unfrozen; the customer can re-check return eligibility.

## Business Rules Applied
- BR-ORD-05, BR-RET-06

## Related Requirements
- FR-016 (Returns & Refunds — dispute interaction), FR-012 (Order Lifecycle Management — `DISPUTED` state)
- **Relation:** UC-350 gates the return; UC-021 is the vendor return flow; UC-333-style recoveries keep the screen navigable; UC-360 rates support afterwards.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own sub-order only; resolution is admin-only (ACT-04) with an audit entry (BR-RET-06).
- **Data involved:** dispute record, sub-order state, escrow freeze flag, return request row (rejected — none written), timeline.
- **External dependencies:** returns/dispute service (B09); escrow ledger (B07); admin arbitration queue (B13).

## Acceptance Criteria
- **AC-UC354-01:** Given an open dispute on the sub-order, when a return is submitted, then `DISPUTE_ALREADY_OPEN` returns and no return row exists (BR-ORD-05).
- **AC-UC354-02:** Given the open dispute, when escrow evaluates, then release stays frozen until admin resolution (BR-ORD-05).
- **AC-UC354-03:** Given the rejection, when the screen renders, then an explanation plus a link to the dispute detail show (NFR-012).
- **AC-UC354-04:** Given the admin resolution, when it commits, then escrow unfreezes and the return entry can be re-evaluated (BR-RET-06).
