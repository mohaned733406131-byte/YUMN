# UC-163 — Cancel an Order Before Dispatch

## Header Info
- **Use Case ID:** UC-163
- **Title:** Cancel an Order Before Dispatch
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens a placed/confirmed order and chooses "Cancel order"
- **Priority:** P0
- **Goal:** Let the customer cancel their own order while cancellation is still permitted and always return the paid amount to their wallet.
- **Preconditions:** Authenticated; order owned by the customer (foreign orders 404); master/sub-order state is `PLACED` or `CONFIRMED` (BR-ORD-04); the order was paid from the customer's wallet.

## Main Scenario
1. Customer opens order detail (`GET /orders/{id}`) → the Cancel action is offered only while the order is `PLACED` or `CONFIRMED` (BR-ORD-04).
2. Customer enters a cancellation reason → `POST /orders/{id}/cancel` (API-ORD-012).
3. System re-validates state server-side; any later state returns `CANCEL_WINDOW_CLOSED` — vendor/admin cancellation remains possible until `READY_FOR_PICKUP` (BR-ORD-04).
4. On success the order moves to `CANCELLED` and an append-only history entry records actor, timestamp and reason.
5. Cancellation always triggers the wallet refund flow: the paid amount (integer YER) is credited back to the customer's wallet — never external cash-out (BR-PAY-07).
6. Held stock for the cancelled lines is released; the customer sees refund status on the order (conceptual `GET /orders/{id}/refund`).

## Alternative Scenarios
- **A1 — Cancel at CONFIRMED:** allowed (BR-ORD-04); identical flow, refund still runs.
- **A2 — Multi-vendor order:** affected sub-orders cancel; the master re-aggregates and each refund tracks per sub-order.
- **A3 — Cancel after dispatch prep:** customer path closed (`CANCEL_WINDOW_CLOSED`) → customer uses return (UC-168) or dispute (UC-171) instead.

## Exception Scenarios
- **E1 — Concurrent transition:** vendor advances the order between click and submit → `STATE_CONFLICT`; history unchanged, no refund started.
- **E2 — Duplicate submit/retry:** repeated cancel calls return the same `CANCELLED` result; the refund executes once for the order.
- **E3 — Missing/invalid reason:** `REASON_REQUIRED`/`VALIDATION_ERROR`; order stays in its current state (BR-ORD-04).

## Postconditions
- Success: order `CANCELLED`, append-only history entry written, wallet refund initiated in integer YER, stock released.
- Failure: state unchanged; no refund, no ledger movement.

## Business Rules Applied
- BR-ORD-04, BR-PAY-07

## Related Requirements
- FR-012 (Order Lifecycle Management)
- **Relation:** UC-033 step4 (admin cancel) — the admin holds the wider cancel window on the same lifecycle.

## Permissions / Data / External Dependencies
- **Permissions:** customer cancels only own orders (owner scope); vendor/admin cancellation runs until `READY_FOR_PICKUP` (UC-193/UC-033).
- **Data involved:** master/sub-order state, append-only status history, wallet ledger, stock reservations.
- **External dependencies:** wallet/ledger service (B07); inventory release path; notification fan-out (B10).

## Acceptance Criteria
- **AC-UC163-01:** Given an order in `PLACED`, when the customer cancels with a reason, then state becomes `CANCELLED` and a pending refund is returned (BR-ORD-04).
- **AC-UC163-02:** Given an order in `READY_FOR_PICKUP`, when cancel is attempted, then `CANCEL_WINDOW_CLOSED` is returned and state is unchanged (BR-ORD-04).
- **AC-UC163-03:** Given a successful cancellation, when the refund executes, then the wallet is credited in integer YER and no external payout is created (BR-PAY-07).
- **AC-UC163-04:** Given another customer's order, when cancel is called, then `NOT_FOUND` is returned and nothing changes.
