# UC-324 — Fall Back to Category Browse When Search Is Unavailable

## Header Info
- **Use Case ID:** UC-324
- **Title:** Fall Back to Category Browse When Search Is Unavailable
- **Actor:** Customer (ACT-01)
- **Trigger:** The search backend is unreachable while the customer runs a query
- **Priority:** P1
- **Goal:** Keep the customer shopping through category browse while search is down — cart, PDP and checkout stay unaffected.
- **Preconditions:** Search endpoint degraded or returning `503 SEARCH_UNAVAILABLE` (NFR-007); category tree available (FR-004, independent of search).

## Main Scenario
1. Customer runs a search while Elasticsearch is unreachable.
2. Gateway first attempts a cached-query replay for `relevance`/`newest` sorts and returns it with `meta.degraded = true` when possible (API-SRC-001).
3. With no cached answer the endpoint returns `503 SEARCH_UNAVAILABLE`; the client shows the localized "search temporarily unavailable" state with a browse-by-category CTA (screen-states §5).
4. Customer taps the CTA → category tree browse (`GET /categories`, `GET /categories/{slug}`) served from the database — browsing never depends on search (BR-CAT-03, BR-CAT-06).
5. Products, cart, PDP and checkout keep working throughout; the customer retries search later (EC-42).

## Alternative Scenarios
- **A1 — Degraded but cached results:** the list renders from the cached replay flagged `degraded`; the customer continues normally.
- **A2 — Outage ends:** the retry succeeds and the index catches up; normal search resumes (EC-42).
- **A3 — Arrived via deep link to `/search`:** the same fallback state renders with the URL preserved.

## Exception Scenarios
- **E1 — Category service also failing:** page error with retry plus home links; no fabricated results (screen-states §4).
- **E2 — Device offline:** persistent offline banner; safe cached reads, writes blocked with an explanation (screen-states §5).
- **E3 — Long outage:** browse continues; catalog writes keep enqueueing index jobs that sync when the index returns (BR-PLT-01).

## Postconditions
- Success (fallback): the customer browses categories with full cart/PDP capability; no search rows written.
- Failure: no search results are invented; the customer always has at least one working navigation path (NFR-012).

## Business Rules Applied
- BR-CAT-03, BR-CAT-06, BR-PLT-01

## Related Requirements
- FR-009 (Search & Discovery — graceful degradation)
- **Relation:** UC-006/UC-321/UC-322 are the search paths this substitutes for; UC-001 is the browse entry point.

## Permissions / Data / External Dependencies
- **Permissions:** Public read for both the degraded search response and category browse.
- **Data involved:** cached query replay, category tree, product listings — read-only; no customer data involved.
- **External dependencies:** Elasticsearch cluster (DEP-04, the failing dependency); PostgreSQL catalog source; `b02.catalog.index` jobs; Redis cache.

## Acceptance Criteria
- **AC-UC324-01:** Given Elasticsearch unreachable with no cached answer, when a search runs, then `503 SEARCH_UNAVAILABLE` maps to the localized unavailable state with a browse-by-category CTA (NFR-007).
- **AC-UC324-02:** Given the CTA is tapped, when categories load, then `ACTIVE` products list normally from the database (BR-CAT-06).
- **AC-UC324-03:** Given search is down, when the cart and a product page are opened, then both work unchanged.
- **AC-UC324-04:** Given a cached replay exists, when the same search runs, then results render with `meta.degraded = true` instead of an error.
