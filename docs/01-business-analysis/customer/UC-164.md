# UC-164 — View Wallet Balance and Status

## Header Info
- **Use Case ID:** UC-164
- **Title:** View Wallet Balance and Status
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the Wallet surface (web S1 or mobile S4)
- **Priority:** P0
- **Goal:** Show the customer their exact wallet balance, currency, ACTIVE/FROZEN status and money limits in integer YER.
- **Preconditions:** Authenticated with a valid session; a wallet row exists for the user; read-only access (no state change).

## Main Scenario
1. Customer opens Wallet → client `GET /wallet` (API-WAL-001).
2. System returns owner-scoped data: `balance`, `currency: "YER"`, `status: "ACTIVE"|"FROZEN"`, limits (top-up 1,000–5,000,000 YER; order 500–5,000,000 YER) and `lastTransactionAt`.
3. Balance is rendered in integer YER via `ar-YE` locale formatting with Arabic-Indic numerals; money views are exact, never estimated (BR-PAY-10).
4. The displayed balance can never be negative — the payment path's atomic check guarantees the figure is spendable (BR-PAY-05); zero is a valid balance.
5. From the same screen the customer jumps to top-up (UC-041) or the statement (UC-042).

## Alternative Scenarios
- **A1 — Frozen wallet:** `status: FROZEN` is displayed with an explanatory banner; money-out affordances are disabled on this screen while the balance stays visible.
- **A2 — Zero balance / new wallet:** `0` YER with the limits block — a valid response with no placeholder rows.
- **A3 — Stale view:** pull-to-refresh refetches after a concurrent payment so the figure re-syncs.

## Exception Scenarios
- **E1 — Invalid or expired session:** `AUTH_INVALID`; client redirects to login; no balance is rendered.
- **E2 — Wallet service read failure:** error state; no partial or estimated amount is ever shown (BR-PAY-10).
- **E3 — Concurrent debit while open:** the next fetch returns the post-transaction integer balance; the screen never sums ledger rows client-side (BR-PAY-05).

## Postconditions
- Success: customer sees their own exact balance and status; read-only — no ledger, balance or wallet-state change.
- Failure: no data rendered; session either invalid (→ login) or intact.

## Business Rules Applied
- BR-PAY-05, BR-PAY-10

## Related Requirements
- FR-013 (Wallet & Payment Processing — balance/status view)
- **Relation:** UC-041 (top-up) and UC-042 (statement) — the wallet screen is the entry point to both.

## Permissions / Data / External Dependencies
- **Permissions:** customer reads own wallet only (owner scope); no other role invokes this use case.
- **Data involved:** wallet row (balance, status, limits) — read-only.
- **External dependencies:** wallet/ledger service (B07) only.

## Acceptance Criteria
- **AC-UC164-01:** Given balance 12,345 YER, when `GET /wallet` returns, then it is displayed as integer YER in `ar-YE` format (BR-PAY-10).
- **AC-UC164-02:** Given a payment that would overdraw, when it fails, then the displayed balance is never negative (BR-PAY-05).
- **AC-UC164-03:** Given another user's wallet exists, when the customer calls `GET /wallet`, then only the owner's wallet is returned.
- **AC-UC164-04:** Given a frozen wallet, when the screen opens, then `status: FROZEN` and the limits block are shown.
