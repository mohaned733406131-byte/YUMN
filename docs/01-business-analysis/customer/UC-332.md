# UC-332 — Reject an Order Total Outside the 500-5,000,000 YER Bounds

## Header Info
- **Use Case ID:** UC-332
- **Title:** Reject an Order Total Outside the 500-5,000,000 YER Bounds
- **Actor:** Customer (ACT-01)
- **Trigger:** Confirm is attempted with a server-computed total below 500 YER or above 5,000,000 YER
- **Priority:** P1
- **Goal:** Enforce the order-value bounds before any row exists, with a message that states the allowed range.
- **Preconditions:** Totals computed server-side at review (items − discount + VAT + shipping, BR-FIN-01/BR-FIN-02); bounds are 500–5,000,000 YER inclusive (C-14, BR-CAT-04).

## Main Scenario
1. Customer reaches review; the server computes `totals.grandTotal` for the master order (BR-FIN-02).
2. On confirm the server validates the total against the bounds before any order row exists (C-14, BR-CAT-04).
3. Outside the range → `422 ORDER_VALUE_OUT_OF_RANGE` with a localized message naming 500–5,000,000 YER (BR-PLT-05).
4. No order row, no wallet debit, no ledger movement, no stock consumed (EC-08) — the cart and reservations stay intact.
5. Customer adjusts the cart (add/remove lines, change coupon — UC-162) and retries; an in-range total proceeds to placement (UC-011).

## Alternative Scenarios
- **A1 — Total exactly 500 or 5,000,000 YER:** bounds are inclusive, so the confirm proceeds (EC-08 boundary wording).
- **A2 — Coupon pushed the total under 500:** the same rejection fires; removing/adjusting the coupon restores an eligible total (UC-162).
- **A3 — Multi-vendor cart:** the bound is checked against the server-computed master total (C-10, C-14).

## Exception Scenarios
- **E1 — Price changed as well as being out of range:** whichever guard evaluates first rejects; in every case no row is created.
- **E2 — Checkout session expired:** `CHECKOUT_SESSION_EXPIRED` supersedes; the cart survives and checkout restarts.
- **E3 — Client bypass attempt (forged total):** the server recomputes `grandTotal` itself — a client-supplied number is never trusted.

## Postconditions
- Success (in-range retry): one `PLACED` order whose total lies within the bounds.
- Failure (out of range): no order row, no ledger entry, no debit; cart, snapshot totals and reservations unchanged.

## Business Rules Applied
- BR-CAT-04, BR-FIN-02, BR-PLT-05

## Related Requirements
- FR-011 (Checkout & Order Placement — order bounds)
- **Relation:** UC-011 completes an in-range confirm; UC-162 applies coupons that move the total; UC-331 governs duplicate retries of the same confirm.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner checkout session; the bound is platform-wide, not configurable per user.
- **Data involved:** computed order totals, cart lines, coupon discount, wallet balance (untouched on rejection).
- **External dependencies:** checkout/order service (B05/B06); ledger (B07, not touched on rejection); no third-party providers.

## Acceptance Criteria
- **AC-UC332-01:** Given a computed total of 499 YER, when confirm runs, then `ORDER_VALUE_OUT_OF_RANGE` returns and no order row exists (BR-CAT-04).
- **AC-UC332-02:** Given a computed total of 5,000,001 YER, when confirm runs, then the same rejection fires with no ledger movement (EC-08).
- **AC-UC332-03:** Given a total of exactly 500 YER, when confirm runs, then the order is created normally (C-14 inclusive bound).
- **AC-UC332-04:** Given the rejection, when the message renders, then it names the 500–5,000,000 YER range in the user's locale (BR-PLT-05).
