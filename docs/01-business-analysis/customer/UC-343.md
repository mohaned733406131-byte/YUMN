# UC-343 — Check Refund Status and the 3-Business-Day Wallet Credit Date

## Header Info
- **Use Case ID:** UC-343
- **Title:** Check Refund Status and the 3-Business-Day Wallet Credit Date
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer checks where a cancellation or return refund stands and when the money lands
- **Priority:** P1
- **Goal:** Report refund status per sub-order with the exact wallet-credit due date — money views are never estimated.
- **Preconditions:** Refund flow started (return or cancellation, FR-016/FR-012); wallet is the only payout rail (BR-PAY-07); receipt endpoint readable (API-WAL-014).

## Main Scenario
1. Customer opens the refund receipt for the order (conceptual `GET /orders/{id}/refund`, API-WAL-014).
2. Per sub-order the status progresses `PENDING → COMPOSED → CREDITED` with item value and the shipping-refunded flag (BR-RET-03).
3. `expectedCreditBy` shows the credit due within 3 business days of `REFUNDED` (BR-RET-04).
4. Copy states refunds go to the wallet only — no external cash-out (BR-PAY-07).
5. Once `CREDITED`, a deep link opens the matching ledger row in the wallet (UC-339).

## Alternative Scenarios
- **A1 — Cancellation refund:** same receipt and engine — `CANCELLED → REFUNDED` shares the flow (returns.md behavior notes).
- **A2 — Already credited:** `CREDITED` with `creditedAt` and the ledger reference shown.
- **A3 — Shipping not refunded:** composition shows item value only, with the policy explanation (BR-RET-03).

## Exception Scenarios
- **E1 — Not yet composed:** status `PENDING` with the expected window — no dates are invented on screen.
- **E2 — Receipt fetch fails:** page error with retry; money views never display estimated numbers (BR-PAY-06).
- **E3 — Wallet frozen at credit time:** the credit still posts (BR-PAY-09) and the receipt shows it.

## Postconditions
- Success: status, composition and expected credit date displayed; read-only — no ledger writes from viewing.
- Failure: no fabricated credit date; if uncomposed, only the pending state is shown.

## Business Rules Applied
- BR-RET-04, BR-PAY-07, BR-RET-03

## Related Requirements
- FR-016 (Returns & Refunds — refund status), FR-013 (Wallet & Payment Processing — wallet credit)
- **Relation:** UC-350 opens the return; UC-352 auto-approves it; UC-353 explains the composition; UC-339 lists the credited row.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own order's refund receipt only; foreign receipts return `404` (API-WAL-014).
- **Data involved:** refund status per sub-order, item value, shipping-refunded flag, expected credit date, ledger reference.
- **External dependencies:** refund engine (B07); order service (B06); ledger rows via the wallet module.

## Acceptance Criteria
- **AC-UC343-01:** Given a sub-order in `REFUNDED`, when the receipt opens, then the credit is shown due within 3 business days (BR-RET-04).
- **AC-UC343-02:** Given any refund, when copy renders, then it states the money returns to the wallet only (BR-PAY-07).
- **AC-UC343-03:** Given a platform-fault return, when composition renders, then item value and shipping lines appear separately (BR-RET-03).
- **AC-UC343-04:** Given the credit posted, when the receipt reloads, then status `CREDITED` appears with ledger reference and timestamp.
