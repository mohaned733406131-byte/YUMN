# UC-319 — Unfollow a Store and Stop Its Notifications

## Header Info
- **Use Case ID:** UC-319
- **Title:** Unfollow a Store and Stop Its Notifications
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer taps "unfollow" on the storefront button or in the Following list
- **Priority:** P2
- **Goal:** End the follow relationship so new-product and offer notifications from that store stop at once.
- **Preconditions:** Customer follows the store (UC-008); relationship id known (BR-VND-05); authenticated (UC-003).

## Main Scenario
1. Customer taps unfollow (storefront header or a row in `/account/following`) → conceptual `DELETE /stores/{id}/follow`.
2. Server clears the relationship → `isFollowing: false` and the follower count decrements; repeat calls return the same state (idempotent, BR-PLT-03).
3. From that moment the customer is excluded from that store's new-product/offer fan-out (BR-VND-05).
4. Notifications already delivered before the unfollow remain in the in-app history (FR-017); only future fan-out stops.
5. The vendor's follower list and count update accordingly (BR-VND-05).

## Alternative Scenarios
- **A1 — Unfollow from the Following list:** same endpoint; the row leaves the list after refresh (rejoins UC-318).
- **A2 — Already unfollowed:** idempotent `200` with `isFollowing: false`; no error is surfaced.
- **A3 — Also mute the category entirely:** the customer can turn off `STORE_FOLLOW`/`PROMOTION` per channel in preferences (UC-177, BR-NTF-05) — independent of follow state.

## Exception Scenarios
- **E1 — Store unknown, hidden or suspended:** `NOT_FOUND`; the stored follow state is left unchanged.
- **E2 — Network lost after commit:** the retry returns the idempotent same state — the count never double-decrements (BR-PLT-03).
- **E3 — Session expired:** `401`/re-auth prompt; nothing changes until the customer is authenticated again.

## Postconditions
- Success: unfollowed; future store marketing stops for this customer; in-app history preserved; vendor sees the reduced count.
- Failure: the customer still follows the store; no partial decrement, no half-sent state.

## Business Rules Applied
- BR-VND-05, BR-NTF-05, BR-PLT-03

## Related Requirements
- FR-008 (Store Management & Storefront Configuration — follower feature), FR-017 (Notifications & Messaging — preference opt-outs)
- **Relation:** UC-008 is the follow counterpart; UC-318 lists the relationships; UC-177 owns the per-channel preference switches.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner scope — a customer can only end their own follow; the vendor only reads the aggregate list.
- **Data involved:** follow row (delete), follower count, notification fan-out targeting, in-app notification history (untouched).
- **External dependencies:** store service (B03); notification fan-out (B10); no third-party providers.

## Acceptance Criteria
- **AC-UC319-01:** Given a followed store, when unfollow is tapped, then `isFollowing: false` returns and the follower count decrements by one (BR-VND-05).
- **AC-UC319-02:** Given the unfollow, when the next store promotion fans out, then this customer is not targeted (BR-VND-05).
- **AC-UC319-03:** Given a repeated unfollow, when the call is retried, then the same state returns with no further count change (BR-PLT-03).
- **AC-UC319-04:** Given notifications received before the unfollow, when the inbox opens, then those items are still present (FR-017).
