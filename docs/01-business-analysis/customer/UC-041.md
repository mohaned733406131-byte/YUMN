# UC-041 — Top Up Wallet

## Header Info
- **Use Case ID:** UC-041
- **Title:** Top Up Wallet
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer selects "Top up" from the wallet screen and chooses a funding method
- **Priority:** P0
- **Goal:** Credit the customer's own wallet through an approved rail (`C-05`: m-Floos/OneCash API or bank transfer with admin verification) with exactly-once, balanced ledger postings.
- **Preconditions:** Customer account registered and phone-verified (FR-001); a wallet row exists for the customer (FR-013 — creation timing discrepancy vs `wallet.md` tracked as `CT-30`); wallet status `ACTIVE` (BR-PAY-09); amount within 1,000–5,000,000 YER checked at intake (BR-PAY-02).

## Main Scenario
1. Customer opens Wallet → "Top up" → enters an amount in whole YER (BR-PAY-10); client `POST /wallet/topups` with `Idempotency-Key` (API-WAL-003, BR-PAY-08).
2. System validates amount bounds **before contacting any provider** (API-WAL-003; out-of-range → `TOPUP_LIMIT`, see E2).
3. System presents the available methods (`C-05`): m-Floos, OneCash, bank transfer; customer picks one.
4. **API rail (m-Floos/OneCash):** system returns the provider payment instruction; customer authorizes inside the external wallet; status stays `PENDING_PROVIDER` until a verified callback or reconciled poll confirms the transaction (BR-PAY-03, INT-REQ-001).
5. **Bank-transfer rail:** system returns beneficiary details; customer transfers and uploads proof (`POST /wallet/topups/{id}/proof`, API-WAL-005, SEC-REQ-011); status becomes `PENDING_VERIFICATION` awaiting admin verification (BR-PAY-04) — the credit leg runs in UC-034, never before.
6. On the credit event, the wallet is credited inside one ACID transaction posting balanced double-entry ledger rows (BR-PAY-06, DATA-REQ-007), exactly once (BR-PAY-08).
7. Customer polls the top-up (`GET /wallet/topups/{id}`, API-WAL-004) → `CREDITED`, and receives a confirmation notification (BR-NTF-01); balance view updates (API-WAL-001).
8. System writes an append-only audit entry for the money action (BR-PLT-06).

## Alternative Scenarios
- **A1 — Bank transfer chosen:** steps 4 and 5 swap rails — the customer's part ends at proof upload; credit occurs only after admin approval in UC-034 (BR-PAY-04, INT-REQ-002).
- **A2 — Reconciled poll instead of callback:** provider callback delayed → background poll reconciliation confirms the transaction and takes the same credit path (BR-PAY-03, INT-REQ-001).
- **A3 — Frozen wallet (BR-PAY-09):** attempt rejected at intake with `WALLET_FROZEN` (API-WAL-003); frozen wallets still receive refunds/credits but cannot initiate top-ups.

## Exception Scenarios
- **E1 — Provider outage:** top-up remains `PENDING_PROVIDER`; adapter retries per contract; no partial credit ever posts (INT-REQ-001).
- **E2 — Out-of-bounds amount:** rejected at intake with `TOPUP_LIMIT` before any provider contact (BR-PAY-02).
- **E3 — Duplicate submission or callback:** same `Idempotency-Key` / replayed callback → single credit; second call no-ops (BR-PAY-08, `IDEMPOTENCY_CONFLICT`).
- **E4 — Ledger write failure:** credit transaction rolls back; top-up stays pending; alert raised (BR-PLT-02); daily reconciliation catches any drift (BR-ESC-08).

## Postconditions
- Success: balance increased exactly once by the requested amount; balanced ledger rows exist; top-up status `CREDITED`; audit row written; customer notified.
- Failure: no balance or ledger change; status remains `PENDING_PROVIDER`/`PENDING_VERIFICATION` or `REJECTED` with reason; customer notified.

## Permissions / Data / External Dependencies
- **Permissions:** customer tops up **own** wallet only (DOC-OVR-007); ledger append-only — nobody edits rows (DATA-REQ-007); admin's only involvement is bank-transfer verification (UC-034, `rbac.md` row 14).
- **Data involved:** top-up requests, proof files (SEC-REQ-011), wallet balance, ledger entries, audit log.
- **External dependencies:** m-Floos/OneCash provider APIs (INT-REQ-001), bank statement evidence (manual, `C-05`), notification channel (BR-NTF-01).

## Acceptance Criteria
- **AC-UC041-01:** Given a 50,000 YER m-Floos top-up with a verified callback, when processed, then the balance rises by 50,000 with balanced credit/debit rows posted exactly once (BR-PAY-06, BR-PAY-08).
- **AC-UC041-02:** Given a bank-transfer request with proof, when submitted, then status is `PENDING_VERIFICATION` and no credit occurs until admin approval (BR-PAY-04, UC-034).
- **AC-UC041-03:** Given a 500 YER amount, when submitted, then it is rejected with `TOPUP_LIMIT` before any provider call (BR-PAY-02).
