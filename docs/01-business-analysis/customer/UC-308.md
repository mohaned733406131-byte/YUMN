# UC-308 — Keep Past Orders on Their Address Snapshot After Editing the Book

## Header Info
- **Use Case ID:** UC-308
- **Title:** Keep Past Orders on Their Address Snapshot After Editing the Book
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer edits or deletes an address that earlier orders were shipped to
- **Priority:** P2
- **Goal:** Change the address book going forward while historical orders keep the exact ship-to recorded at placement.
- **Preconditions:** At least one past order exists whose `shipping_address_snapshot` came from this address (FR-012); address editable in the book (UC-005, FR-003).

## Main Scenario
1. Customer opens the book and replaces an address (conceptual `PUT /addresses/{id}`) — district, street or recipient changed.
2. Server writes only the `address` row (`updated_at` bumped); no order row is mutated (FR-003).
3. Past orders keep `shipping_address_snapshot`, the immutable copy taken when the order was placed (FR-012, `08-database` invariant).
4. Order detail keeps rendering the original ship-to to the buyer — history is append-only and never overwritten (BR-ORD-03, BR-ORD-09).
5. The next checkout resolves zone and fee from the edited row (BR-SHP-01) — the change applies only going forward.

## Alternative Scenarios
- **A1 — Address deleted instead of edited:** soft delete; order→address link goes null but the snapshot still renders on past orders (UC-306).
- **A2 — Default address edited:** only future checkout defaults resolve differently; past orders unaffected.
- **A3 — Recipient phone changed:** future deliveries use the new number; delivery history still shows the snapshot values.

## Exception Scenarios
- **E1 — Address already deleted (404):** `NOT_FOUND`; the book and all orders remain as they were.
- **E2 — Invalid governorate/district pair:** `VALIDATION_ERROR` (domestic pair check, C-17); the row keeps its previous values.
- **E3 — Order detail read fails:** page/block error with retry; no order data is rewritten by a failed read.

## Postconditions
- Success: address row updated; every past order's snapshot byte-identical to before; timeline/ledger untouched; new sessions price from the edited address.
- Failure: no partial write — either the address updates wholly or not at all; orders never change.

## Business Rules Applied
- BR-ORD-03, BR-SHP-01

## Related Requirements
- FR-003 (User & Profile Management — address book), FR-012 (Order Lifecycle Management — historical order data)
- **Relation:** UC-005 edits the book; UC-306 deletes from it; UC-012 shows the order detail that renders the preserved snapshot.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner scope — only the buyer's own orders and addresses are readable/writable.
- **Data involved:** `address` rows (write), `order` rows (read-only snapshot), order timeline (read-only).
- **External dependencies:** account/address service (B01); order service (B06); no third-party providers.

## Acceptance Criteria
- **AC-UC308-01:** Given a past order placed with address X, when X is edited, then order detail still returns the original snapshot values (FR-012).
- **AC-UC308-02:** Given the same edit, when a new checkout starts, then zone and fee resolve from the edited address (BR-SHP-01).
- **AC-UC308-03:** Given the address is deleted after delivery, when the past order opens, then the ship-to still renders from the snapshot.
- **AC-UC308-04:** Given an edit rejected for an invalid district, when the response returns, then the stored address and all order rows are unchanged.
