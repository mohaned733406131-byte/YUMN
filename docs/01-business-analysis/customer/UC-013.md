# UC-013 — Confirm Receipt with Delivery Code

## Header Info
- **Use Case ID:** UC-013
- **Title:** Confirm Receipt with Delivery Code
- **Actor:** Customer (ACT-01)
- **Trigger:** Order reaches `OUT_FOR_DELIVERY` and the courier arrives at the customer's address
- **Priority:** P0
- **Goal:** Complete handover by sharing the customer-held 6-digit code with the courier, who verifies it to reach `DELIVERED` (no GPS, C-16).
- **Preconditions:** Order state is `OUT_FOR_DELIVERY`; 6-digit code issued to the buyer (BR-SHP-02); customer reachable via app/SMS/WhatsApp.

## Main Scenario
1. System transitions `IN_TRANSIT → OUT_FOR_DELIVERY` and issues a 6-digit code to the buyer (BR-SHP-02); notification sent with delivery attempt details (BR-NTF-01).
2. Customer opens the order (UC-012) and retrieves the code from the in-app delivery card (masked preview + full reveal on tap).
3. Customer verbally shares the code with the courier at the door — the platform never requests courier location (BR-SHP-05, C-16).
4. Courier submits the code (UC-030) → system `POST /deliveries/{id}/code` verifies it (3 attempts max, BR-SHP-03).
5. On success, state becomes `DELIVERED`; delivery proof = code + timestamp + courier identity, optional photo (BR-SHP-07); escrow 7-day hold starts (BR-ESC-01, C-12).
6. Customer receives a delivery-confirmation notification; the order screen shows the escrow countdown and the "Request return" window start (BR-RET-01).

## Alternative Scenarios
- **A1 — Customer not at door:** No code shared → courier records a failed attempt (UC-029); order returns to `IN_TRANSIT`, attempts counter increments.
- **A2 — Code not received:** Notification missing → customer requests resend/reveal in-app; code is retrievable from the order screen (delivery security notices cannot be disabled, BR-NTF-02).
- **A3 — Partial delivery (multi-vendor):** Code verifies the specific sub-order's delivery; other sub-orders continue independently (BR-ORD-07).

## Exception Scenarios
- **E1 — 3 wrong code entries:** Confirmation locks 24 hours and a support ticket auto-creates (BR-SHP-03); customer/support can intervene (UC-014).
- **E2 — Customer disputes receipt:** Customer raises a dispute instead (`DELIVERED → DISPUTED`, escrow frozen, BR-ORD-05) → admin resolution path (UC-033).
- **E3 — Notification channel outage:** SMS/WhatsApp down → in-app code still available; no delivery completion without a verified code (BR-ORD-08).

## Postconditions
- Success: sub-order reaches `DELIVERED`; escrow hold starts (BR-ESC-01); return window opens (BR-RET-01).
- Failure: state remains `OUT_FOR_DELIVERY` (or reverts to `IN_TRANSIT`); no escrow change.

## Business Rules Applied
- BR-ORD-05, BR-ORD-08, BR-ESC-01, BR-RET-01, BR-SHP-02, BR-SHP-03, BR-SHP-05, BR-SHP-07, BR-NTF-01, BR-NTF-02

## Related Requirements
- FR-015 (Shipping & Delivery), FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** Customer reads own delivery code only; courier submits within assigned delivery; no staff shortcut past code verification (BR-ORD-08).
- **Data involved:** Delivery code (hashed at rest), attempt counter, delivery proof, status history.
- **External dependencies:** Notification channels (B10); support ticketing (B13) on lockout.

## Acceptance Criteria
- **AC-UC013-01:** Given `OUT_FOR_DELIVERY`, when the code is issued, then the buyer can view it in-app and via notification (BR-SHP-02).
- **AC-UC013-02:** Given a correct code, when the courier submits it, then state becomes `DELIVERED` and escrow hold starts (BR-ESC-01).
- **AC-UC013-03:** Given 3 incorrect submissions, when the third fails, then confirmation locks 24 h and a support ticket exists (BR-SHP-03).
