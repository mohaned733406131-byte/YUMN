# UC-339 — Filter Wallet Transactions by Type and Date Range

## Header Info
- **Use Case ID:** UC-339
- **Title:** Filter Wallet Transactions by Type and Date Range
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer narrows the wallet ledger view by transaction type and/or date range
- **Priority:** P1
- **Goal:** Find specific movements in the append-only ledger with exact totals — money is never estimated.
- **Preconditions:** Wallet exists and belongs to the customer (FR-013); ledger rows posted (BR-PAY-06); wallet screen open (routing §4).

## Main Scenario
1. Customer opens `/{locale}/account/wallet` transactions → system fetches the own ledger feed (conceptual `GET /wallet/transactions`, API-WAL-002, cursor).
2. Customer picks a type (`TOPUP`, `ORDER_PAYMENT`, `REFUND`, `ESCROW_HOLD`, `PAYOUT`) and/or a `from`/`to` range → the request carries `?type&from&to`.
3. Server filters the owner's rows only and returns page items plus exact totals (API-WAL-002 — money views are never estimated).
4. Active filters render as removable chips and mirror into the URL for reload/back restore.
5. Clearing filters rejoins the full feed at the first page, newest-first.

## Alternative Scenarios
- **A1 — Type filter only:** date bounds stay open; the same exact-totals rule applies.
- **A2 — Date range only:** all types within the window; `balanceAfter` still proves continuity.
- **A3 — Empty result:** localized empty state with a top-up recovery (screen-states §3).

## Exception Scenarios
- **E1 — Invalid or inverted range:** `VALIDATION_ERROR`; the last valid list stays rendered (forms-and-validation §5).
- **E2 — Stale cursor after changing filters:** request rejected; the list restarts at the first page of the new context.
- **E3 — Fetch fails:** block error with retry; the balance card keeps its own freshness (NFR-004).

## Postconditions
- Success: filtered ledger view rendered in the active locale; read-only — the append-only ledger is untouched.
- Failure: no fabricated rows or estimated totals; prior valid view retained.

## Business Rules Applied
- BR-PAY-06, BR-PAY-10

- **Relation:** UC-161 previews the balance; UC-340/UC-341 create the top-ups seen here; UC-343 explains refund credits found by type.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner-scoped ledger only — no other user ever reads these rows; no endpoint edits postings.
- **Data involved:** ledger entries (type, direction, amount, `balanceAfter`, reference), filter chips, URL query — no writes.
- **External dependencies:** ledger service (B07); cursor pagination; locale number formatting (BR-PAY-10).

## Acceptance Criteria
- **AC-UC339-01:** Given rows of several types, when a type filter is applied, then only that type renders (BR-PAY-06).
- **AC-UC339-02:** Given a `from`/`to` range, when applied, then only rows inside the range show and the totals match them exactly (BR-PAY-06).
- **AC-UC339-03:** Given selected filters, when the page reloads, then the same filter set restores from the URL.
- **AC-UC339-04:** Given any filtered view, when amounts display, then they are integer YER with locale digits and no rounding drift (BR-PAY-10).
