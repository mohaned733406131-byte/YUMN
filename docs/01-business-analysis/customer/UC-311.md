# UC-311 — Collect the OTP via WhatsApp When SMS Delivery Fails

## Header Info
- **Use Case ID:** UC-311
- **Title:** Collect the OTP via WhatsApp When SMS Delivery Fails
- **Actor:** Customer (ACT-01)
- **Trigger:** The SMS provider times out or fails while delivering an OTP the customer is waiting for
- **Priority:** P1
- **Goal:** Get the 6-digit code to the customer through automatic WhatsApp failover so verification completes without extra user effort.
- **Preconditions:** An OTP request was accepted (UC-002/003/004, UC-141); 6-digit code valid 5 minutes (BR-AUTH-03); WhatsApp reachable for the user's number (INT-REQ-004).

## Main Scenario
1. Server generates the 6-digit OTP and dispatches delivery with SMS as primary channel (BR-NTF-03).
2. The OTP screen shows the channel hint naming both SMS and WhatsApp (screen-states, OTP screen).
3. SMS provider times out or errors → the same approved template is retried automatically through WhatsApp (BR-NTF-03, INT-REQ-003).
4. Customer reads the code from the WhatsApp message and enters it; the sixth digit auto-submits (FL-01 step 3).
5. Verification succeeds within 5 minutes; both attempts (SMS `FAILED`, WhatsApp `SENT`) remain in the notification's channel record (FR-017).

## Alternative Scenarios
- **A1 — SMS succeeds first:** no failover runs; the customer uses the SMS code (rejoins UC-003).
- **A2 — Code expires before use:** after 5 minutes the "code expired" state offers resend with its 60 s cooldown and ≤3 resends per 10 minutes (BR-AUTH-03, UC-141).
- **A3 — One wrong entry before success:** attempts left are shown explicitly (3 → 2 → 1) and verification continues (BR-AUTH-03).

## Exception Scenarios
- **E1 — Both SMS and WhatsApp fail:** the OTP stays queued/retried under the platform policy and the screen shows in-app guidance instead of a dead end (BR-PLT-02).
- **E2 — WhatsApp template rejected:** the retry policy re-attempts delivery; the customer is never shown a raw provider error.
- **E3 — Resend spam:** cooldown and resend counters block the abuse (BR-AUTH-03, rate limiting on OTP request).

## Postconditions
- Success: OTP verified, the protected flow continues, delivery record shows the failover trail.
- Failure: no session/verification is created; counters, cooldown and OTP state stay consistent.

## Business Rules Applied
- BR-NTF-03, BR-AUTH-03, BR-PLT-02

## Related Requirements
- FR-001 (Identity, Authentication & Session Management — OTP verification), FR-017 (Notifications & Messaging — SMS/WhatsApp channels)
- **Relation:** UC-141 is the resend entry point; UC-002/003/004 are the flows that consume this OTP.

## Permissions / Data / External Dependencies
- **Permissions:** unauthenticated applicant at the verification step; OTP bound to one phone number and one context.
- **Data involved:** OTP record (code, expiry, attempt counters), channel delivery record, notification template.
- **External dependencies:** SMS providers (DEP-06, INT-REQ-003); WhatsApp Business API (INT-REQ-004); BullMQ delivery jobs (B10).

## Acceptance Criteria
- **AC-UC311-01:** Given an SMS provider timeout, when failover runs, then the same OTP template is delivered via WhatsApp (BR-NTF-03).
- **AC-UC311-02:** Given both attempts occurred, when the delivery record is read, then SMS shows `FAILED` and WhatsApp shows `SENT`.
- **AC-UC311-03:** Given the WhatsApp-delivered code, when entered within 5 minutes, then verification succeeds (BR-AUTH-03).
- **AC-UC311-04:** Given both providers fail, when retries are exhausted, then the OTP is queued per retry policy and the screen shows in-app guidance (BR-PLT-02).
