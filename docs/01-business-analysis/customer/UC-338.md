# UC-338 — Open the Order Receipt With the Full VAT Breakdown

## Header Info
- **Use Case ID:** UC-338
- **Title:** Open the Order Receipt With the Full VAT Breakdown
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the receipt from the order confirmation or order detail
- **Priority:** P2
- **Goal:** Show every money line — subtotal, discount, VAT, shipping, total — as invoice evidence.
- **Preconditions:** Order placed and paid from wallet (FR-011); totals computed server-side (BR-FIN-02); receipt reachable from order detail (FR-012).

## Main Scenario
1. Customer opens the receipt → system returns the authoritative totals for the order (conceptual `GET /orders/{id}`).
2. The receipt renders separate lines: subtotal, coupon discount, VAT, shipping fee, grand total (compliance § displayed-price rule).
3. VAT shows as 15% × (subtotal − coupon discount) with shipping untaxed (BR-FIN-01).
4. Multi-vendor orders show per-sub-order breakdowns that sum to the master total (BR-FIN-02, C-10).
5. Amounts display as integer YER with locale digits and the `ر.ي`/`YER` suffix, never abbreviated (BR-PAY-10).

## Alternative Scenarios
- **A1 — Free-shipping coupon:** the shipping line reads 0 and VAT is unaffected (BR-SHP-01, BR-FIN-01).
- **A2 — Refund later:** the refund receipt is a separate view (UC-343); the original receipt stays immutable.
- **A3 — Locale switch:** identical numbers re-render with the other locale's digits (NFR-013).

## Exception Scenarios
- **E1 — Detail fetch fails:** page error with retry; no client-side math fabricates the breakdown (BR-FIN-05 rounding is server-side).
- **E2 — Foreign order id:** `404` — existence of another customer's order is never leaked (routing §4 IDOR hygiene).
- **E3 — Session expired:** re-auth prompt, then the receipt reopens (routing §9).

## Postconditions
- Success: full breakdown displayed in the active locale; read-only — no rows written.
- Failure: no partial or computed-invented totals appear on screen.

## Business Rules Applied
- BR-FIN-01, BR-FIN-02, BR-PAY-10

## Related Requirements
- FR-011 (Checkout & Order Placement — authoritative totals), FR-012 (Order Lifecycle Management — order detail)
- **Relation:** UC-011 confirms the totals; UC-012 shows the detail screen; UC-343 is the refund receipt; UC-334 lists the orders.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own order only; receipt read-only — vendor callers get a masked projection (API-ORD-004).
- **Data involved:** order totals, payment receipt with ledger reference, per-sub-order totals — read-only.
- **External dependencies:** order service (B06); ledger reference from the wallet module (B07); locale number formatting (BR-PLT-05).

## Acceptance Criteria
- **AC-UC338-01:** Given a placed order, when the receipt opens, then subtotal, discount, VAT, shipping and total appear as separate lines (BR-FIN-01).
- **AC-UC338-02:** Given subtotal and coupon discount, when VAT renders, then it equals 15% of (subtotal − discount) with shipping untaxed (BR-FIN-01).
- **AC-UC338-03:** Given a multi-vendor order, when totals render, then per-sub-order totals sum to the master total (BR-FIN-02, C-10).
- **AC-UC338-04:** Given the `ar` locale, when amounts render, then integer YER with Arabic-Indic digits shows with no abbreviation (BR-PAY-10).
