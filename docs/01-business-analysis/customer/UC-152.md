# UC-152 — Switch the Interface Locale (ar/en)

## Header Info
- **Use Case ID:** UC-152
- **Title:** Switch the Interface Locale (ar/en)
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer taps the ar/en language toggle in the header (or the in-app language row on mobile)
- **Priority:** P1
- **Goal:** Render the whole interface in Arabic or English with correct direction, keeping the current resource and persisting the choice.
- **Preconditions:** Exactly two locales exist — Arabic (default, canonical) and English parity (C-24); routes are locale-prefixed per `routing.md` §1.

## Main Scenario
1. Customer selects the other locale; on web the URL prefix swaps `/ar/…` ↔ `/en/…` while the path after the prefix stays identical (slugs are locale-independent, `routing.md` §1).
2. `lang` and `dir` re-render RTL ↔ LTR without a full reload; scroll position resets (`routing.md` §9 redirect policy keeps the destination).
3. Signed-in: the choice is persisted via `PATCH /users/me { locale }` so later sessions open in it (FR-003); each request carries `Accept-Language` so server-generated text (templates, errors) returns in that locale.
4. All strings come from locale catalogs — no hardcoded text, Arabic default with English parity (BR-PLT-05, C-24).

## Alternative Scenarios
- **A1 — Guest customer:** the switch applies through the URL for the visit; there is no account preference to persist.
- **A2 — Mobile app (S4):** the in-app language row reloads the message catalogs in place without restarting the app (`routing.md` §5).

## Exception Scenarios
- **E1 — Unknown or missing locale segment:** bare or invalid paths 307-redirect to `/ar/...` — never a 404 (`routing.md` §9).
- **E2 — Switch during checkout:** draft checkout state is locale-independent and preserved; labels re-render and totals re-fetch in the new locale.

## Postconditions
- Success: interface fully in the chosen locale/direction; stored locale updated when signed in (BR-PLT-05).
- Failure: request lands on the default Arabic locale; no account data changed.

## Business Rules Applied
- BR-PLT-05

## Related Requirements
- FR-003 (User & Profile Management)

## Permissions / Data / External Dependencies
- **Permissions:** any user, guest or authenticated; locale never affects authorization.
- **Data involved:** locale preference on the profile, URL locale prefix, message catalogs (ar/en).
- **External dependencies:** none — client-side rendering plus locale-aware responses via `Accept-Language`.

## Acceptance Criteria
- **AC-UC152-01:** Given the path `/ar/account`, when the toggle picks English, then the URL becomes `/en/account` showing the same resource.
- **AC-UC152-02:** Given locale = ar, when a screen renders, then Arabic strings and RTL layout are used with English parity available (BR-PLT-05, C-24).
- **AC-UC152-03:** Given an unknown locale prefix, when visited, then a 307 redirect lands on `/ar/...` (`routing.md` §9).
