# UC-325 — Add Past a Cart Guard and Leave the Cart Unchanged

## Header Info
- **Use Case ID:** UC-325
- **Title:** Add Past a Cart Guard and Leave the Cart Unchanged
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer tries an add or quantity change that would breach a cart guard
- **Priority:** P1
- **Goal:** Reject the mutation atomically with a precise code, leaving the cart byte-for-byte as it was.
- **Preconditions:** Authenticated with a server cart (UC-009/UC-010); guards are ≤50 distinct products, ≤10 units per product, ≤5 vendors (BR-CRT-01, C-15).

## Main Scenario
1. Customer submits an add/quantity change that would create the 51st product, 11th unit, or 6th vendor (conceptual `POST /cart/items` or `PATCH /cart/items/{id}`).
2. Client pre-checks the limits for instant feedback (disable + localized message) — UX only (state-management §4).
3. Server re-validates in ladder order: eligibility → unit limit → product limit → vendor limit → stock; the first violation sets the code (`UNIT_LIMIT_EXCEEDED`, `CART_LIMIT_EXCEEDED`, `MAX_VENDORS_EXCEEDED`).
4. The mutation is rejected atomically — no line added, quantity unchanged, reservation untouched (BR-CRT-01).
5. Customer adjusts within limits (UC-010/UC-160) and retries → accepted (rejoins the normal cart flow).

## Alternative Scenarios
- **A1 — Quantity PATCH breaches the unit cap:** `UNIT_LIMIT_EXCEEDED`; the stored quantity stays at its previous value.
- **A2 — Guard hit during guest-cart merge:** only the offending guest line is rejected; the rest of the merge proceeds (BR-CRT-03, UC-329).
- **A3 — Stock rather than a count guard:** the ladder's last step returns `STOCK_UNAVAILABLE` with the same atomic rejection (BR-CAT-07).

## Exception Scenarios
- **E1 — Concurrent adds push past the limit:** the count check runs inside the mutation transaction; one wins, the loser receives the guard error — never 51 lines.
- **E2 — Network lost after the rejection:** a retry re-evaluates the same guards with the same outcome; nothing accumulated.
- **E3 — Product deactivated between tap and submit:** eligibility fails first (`CART_ITEM_INELIGIBLE`/`NOT_FOUND`); the cart stays unchanged (BR-CAT-06).

## Postconditions
- Success (after correction): cart within every guard, quantities and reservations consistent.
- Failure (rejected attempt): cart identical to its pre-attempt state — no partial mutation, no orphan hold.

## Business Rules Applied
- BR-CRT-01, BR-CAT-07, BR-CAT-06

## Related Requirements
- FR-010 (Shopping Cart — multi-vendor guards)
- **Relation:** UC-009 adds items; UC-010 manages quantities; UC-329 is the merge variant of the same ladder.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, one server cart per authenticated caller — foreign cart ids return 404.
- **Data involved:** cart lines, quantities, per-store grouping, reservation timestamps — write attempt rejected atomically.
- **External dependencies:** cart service (B05); inventory availability read (B02); no third-party providers.

## Acceptance Criteria
- **AC-UC325-01:** Given a cart with 10 units of a product, when an 11th is requested, then `UNIT_LIMIT_EXCEEDED` returns and the quantity stays 10 (BR-CRT-01).
- **AC-UC325-02:** Given a cart with 50 distinct products, when a 51st is added, then `CART_LIMIT_EXCEEDED` returns and the line count stays 50 (BR-CRT-01).
- **AC-UC325-03:** Given a rejected attempt, when the cart is re-read, then it matches its pre-attempt state exactly — no orphan hold.
- **AC-UC325-04:** Given a breach caused by a merge, when merge completes, then only the offending guest line is rejected (BR-CRT-03).
