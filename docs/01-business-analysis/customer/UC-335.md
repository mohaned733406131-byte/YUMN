# UC-335 — Refresh the Order Screen After a Status Conflict

## Header Info
- **Use Case ID:** UC-335
- **Title:** Refresh the Order Screen After a Status Conflict
- **Actor:** Customer (ACT-01)
- **Trigger:** An order action or view hits `409 STATE_CONFLICT` because the state moved server-side
- **Priority:** P2
- **Goal:** Recover by refetching the authoritative state and explaining the refresh — never a dead-end error.
- **Preconditions:** Order detail or action screen open (UC-012); transitions guarded by `version` (BR-ORD-01).

## Main Scenario
1. Customer submits an order action (or reloads a stale screen) → system validates against the current `version` (BR-ORD-01, C-09).
2. The state changed since the screen loaded → `409 STATE_CONFLICT` and no status-history row is written (forms-and-validation §5).
3. Client refetches the order (`GET /orders/{id}`) and re-renders the current state badge.
4. A localized banner "الحالة تغيرت — تم التحديث / status changed, refreshed" shows from the error mapping (forms-and-validation §5).
5. The customer retries against the fresh state; if the action is no longer legal, its control is hidden with an explanation (FL-03 step 2).

## Alternative Scenarios
- **A1 — Cancel lost the race:** refetch shows `READY_FOR_PICKUP` or later; the cancel affordance is gone with a tooltip (BR-ORD-04).
- **A2 — Action still legal:** the retried action succeeds on the second attempt.
- **A3 — No action taken:** polling order detail (10–15 s while visible) corrects the stale badge on its own.

## Exception Scenarios
- **E1 — Refetch fails:** block error with retry; the conflict is never silently swallowed (screen-states §4).
- **E2 — Session expired:** re-auth prompt, then the refetch repeats (routing §9).
- **E3 — Rapid successive transitions:** each conflict triggers one refetch; history stays append-only (BR-ORD-03).

## Postconditions
- Success: screen shows the authoritative current state and the banner; server-side history unchanged by the client.
- Failure: no client-authoritative order status is cached (state-management §4 forbidden list).

## Business Rules Applied
- BR-ORD-01, BR-ORD-03

## Related Requirements
- FR-012 (Order Lifecycle Management — guarded transitions)
- **Relation:** UC-012 shows the order detail; UC-334 filters the same feed; UC-337 is the common conflict source (cancel window).

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own order only; transition guards enforced server-side regardless of client state.
- **Data involved:** order `version`, state badge, conflict banner, refetched order slice — no state written by the client.
- **External dependencies:** order service (B06); shared error mapper and locale error strings (forms-and-validation §5, BR-PLT-05).

## Acceptance Criteria
- **AC-UC335-01:** Given an order whose state changed since load, when an action is submitted, then `409 STATE_CONFLICT` returns and no status-history row is written (BR-ORD-01, BR-ORD-03).
- **AC-UC335-02:** Given the conflict, when the client handles it, then the order is refetched and the current state badge renders.
- **AC-UC335-03:** Given the refetch, when the banner shows, then it reads "status changed, refreshed" in the active locale (BR-PLT-05).
- **AC-UC335-04:** Given the fresh state forbids the action, when the screen renders, then the action control is hidden with an explanation (BR-ORD-04).
