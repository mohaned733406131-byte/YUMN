# UC-178 — Register This Device for Push Notifications

## Header Info
- **Use Case ID:** UC-178
- **Title:** Register This Device for Push Notifications
- **Actor:** Customer (ACT-01)
- **Trigger:** App launch or login on the customer mobile app (S4) after push permission is granted
- **Priority:** P1
- **Goal:** Bind this device's push token to the customer's account so opted-in notifications can be delivered to it.
- **Preconditions:** Authenticated; device push permission granted (or A1); a valid FCM/APNs token obtained by the client.

## Main Scenario
1. After login or first launch on S4, the app obtains a push token (FCM on Android, APNs on iOS).
2. Client `POST /devices` (API-NTF-008) with `{ token, platform, deviceName }` → `201 { deviceId, registeredAt }`.
3. System binds the token to the owner's account; push becomes one of the delivery channels for the customer's opted-in categories (BR-NTF-01 channel set includes push).
4. Re-registration with the same token upserts the existing entry; the same token presented by another user detaches it from the previous owner.
5. Rate limiting applies to registration attempts (10 per minute per user).

## Alternative Scenarios
- **A1 — Permission denied / no token:** registration is skipped; SMS, WhatsApp and in-app delivery still work (BR-NTF-01).
- **A2 — Token refresh after app update:** re-register upserts the row for the same device.
- **A3 — Second device:** each device registers its own token, mirroring the session cap model.

## Exception Scenarios
- **E1 — Invalid token:** `DEVICE_TOKEN_INVALID`; no device row.
- **E2 — Too many registrations:** `RATE_LIMITED`; row not written.
- **E3 — Malformed body:** `VALIDATION_ERROR`; nothing persisted.

## Postconditions
- Success: an active device token exists for the owner and will receive pushes for opted-in categories (BR-NTF-01).
- Failure: no device row; other channels unaffected.

## Business Rules Applied
- BR-NTF-01

## Related Requirements
- FR-017 (Notifications & Messaging — push channel)
- **Relation:** UC-179 manages the tokens registered here; UC-182 is a push opened by the customer.

## Permissions / Data / External Dependencies
- **Permissions:** customer registers tokens only for their own account; token ownership transfers are enforced server-side.
- **Data involved:** device token rows (token, platform, deviceName, registeredAt) — owner-scoped.
- **External dependencies:** FCM (Android) and APNs (iOS) via the push adapter; notification service (B10).

## Acceptance Criteria
- **AC-UC178-01:** Given a fresh FCM token, when `POST /devices` is called, then `201` with `deviceId` and the token is active for future pushes (BR-NTF-01).
- **AC-UC178-02:** Given the same token registered by a second user, when registered, then it is detached from the first user.
- **AC-UC178-03:** Given 11 registrations within a minute, when the 11th is sent, then `RATE_LIMITED`.
- **AC-UC178-04:** Given an empty token, when submitted, then an error is returned and no device row exists.
