# UC-352 — Watch a Return Auto-Approve After the 72-Hour Inspection Timeout

## Header Info
- **Use Case ID:** UC-352
- **Title:** Watch a Return Auto-Approve After the 72-Hour Inspection Timeout
- **Actor:** Customer (ACT-01)
- **Trigger:** The vendor does not inspect a `RETURN_RECEIVED` return within 72 hours
- **Priority:** P1
- **Goal:** Protect the buyer with automatic approval and a visible state change when the inspection SLA lapses.
- **Preconditions:** Return in `RETURN_RECEIVED` (BR-RET-02); 72 h inspection timer started (BR-RET-05); customer can read return detail (API-RET-003).

## Main Scenario
1. The return reaches `RETURN_RECEIVED`; the 72-hour inspection timer starts (WF-007 step 6).
2. No vendor inspection is recorded within 72 h → `SYSTEM` auto-approves and the state moves to `REFUNDED` (edge-cases EC-38, BR-RET-05).
3. The refund engine composes the amount (item value; shipping only on platform/vendor fault) and schedules the wallet credit (BR-RET-03).
4. The customer sees the state change in return detail and the timeline; the vendor is notified (EC-38).
5. The credit is due within 3 business days of `REFUNDED` (BR-RET-04).

## Alternative Scenarios
- **A1 — Inspection before 72 h:** normal pass/fail path runs and the timer is cleared.
- **A2 — Inspection fails before the timeout:** the return goes to admin review instead of auto-approving.
- **A3 — Customer watches the SLA:** return detail shows decision/inspection state and timestamps throughout.

## Exception Scenarios
- **E1 — Timer job delayed:** retries 3× with backoff, then DLQ alert — the auto-approve is never silently dropped (BR-PLT-02).
- **E2 — Return already refunded:** a replayed timer is a no-op — exactly one credit (BR-PAY-08).
- **E3 — Notification channel fails:** the state still advances; the in-app record is guaranteed (FR-017).

## Postconditions
- Success: state `REFUNDED` with the wallet credit scheduled within 3 business days and an append-only history entry.
- Failure: no double refund; the timer outcome is applied exactly once.

## Business Rules Applied
- BR-RET-05, BR-RET-04, BR-PAY-08

## Related Requirements
- FR-016 (Returns & Refunds — inspection SLA & auto-approval)
- **Relation:** UC-350 gates entry; UC-353 explains the refund composition; UC-343 reports the credit date; UC-021 is the vendor inspection side.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER reads own return; the auto-approve transition is executed by the system (ACT-07), never by the customer.
- **Data involved:** return state, inspection timer, refund composition, wallet credit, timeline entries, notification rows.
- **External dependencies:** returns service (B09); BullMQ timer jobs (BR-PLT-01); wallet/ledger (B07); notifications (B10).

## Acceptance Criteria
- **AC-UC352-01:** Given `RETURN_RECEIVED` untouched for 72 h, when the timer fires, then the state becomes `REFUNDED` by `SYSTEM` (BR-RET-05).
- **AC-UC352-02:** Given the auto-approval, when the customer opens the return, then the change appears with a timestamp in the timeline (BR-ORD-03).
- **AC-UC352-03:** Given a late vendor inspection, when submitted, then `INSPECTION_WINDOW_PASSED` returns (BR-RET-05).
- **AC-UC352-04:** Given the refund, when credit schedules, then it is due within 3 business days of `REFUNDED` (BR-RET-04).
