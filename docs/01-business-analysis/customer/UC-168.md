# UC-168 — Request a Return for Delivered Items

## Header Info
- **Use Case ID:** UC-168
- **Title:** Request a Return for Delivered Items
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens Return from a delivered order's detail page
- **Priority:** P0
- **Goal:** Open a return request for eligible delivered items inside the policy window and start the approval → pickup → inspection → refund sequence.
- **Preconditions:** Authenticated; order owned by the customer; state `DELIVERED`/`COMPLETED`; product `isReturnable = true` and window still open (BR-RET-01); no dispute open on the sub-order.

## Main Scenario
1. From order detail (cross-reference: UC-012 step6 — entry point) customer selects Return on an eligible order.
2. System computes the window server-side: deadline = delivery confirmation + product `returnPeriodDays`; days remaining are shown (BR-RET-01).
3. Customer picks items + quantity, reason code, note and optional evidence images → `POST /orders/{id}/returns` (API-RET-001).
4. System validates eligibility and returns `201` with `returnId`, state `RETURN_REQUESTED`, the window math and a refund estimate (item value; shipping refundable only when the fault is platform/vendor-side).
5. The request walks `RETURN_REQUESTED → RETURN_APPROVED / RETURN_REJECTED → RETURN_RECEIVED → REFUNDED` (BR-RET-02); the vendor decision is due within 48 hours.
6. Customer tracks progress in UC-169; on `REFUNDED` the wallet credit follows the refund flow.

## Alternative Scenarios
- **A1 — Multiple items:** one request covers several order items of the same sub-order.
- **A2 — Evidence images:** up to 5 files attached, scanned before acceptance.
- **A3 — Dispute already open:** the customer continues in the dispute path instead (see E3).

## Exception Scenarios
- **E1 — Return window elapsed:** `WINDOW_EXPIRED`; no return row (BR-RET-01).
- **E2 — Product not returnable:** `NOT_RETURNABLE` — a distinct rejection from E1 (BR-RET-01).
- **E3 — Dispute already open:** `DISPUTE_ALREADY_OPEN`; the return is refused while the dispute runs (BR-RET-02).

## Postconditions
- Success: a `RETURN_REQUESTED` row exists for the chosen items; window math and refund estimate recorded; order timeline appended.
- Failure: no return row; order state and escrow unchanged.

## Business Rules Applied
- BR-RET-01, BR-RET-02

## Related Requirements
- FR-016 (Returns & Refunds)
- **Relation:** UC-012 step6 (entry point) — order tracking surfaces the Return action that starts this use case.

## Permissions / Data / External Dependencies
- **Permissions:** order owner only; foreign orders and returns return `NOT_FOUND`.
- **Data involved:** order items, product return policy, return request, evidence images, refund estimate.
- **External dependencies:** returns service (B09); file scanning; notification fan-out (B10) for decision updates.

## Acceptance Criteria
- **AC-UC168-01:** Given delivery confirmed 2 days ago with `returnPeriodDays` 7, when submitted, then `201 RETURN_REQUESTED` with 5 days remaining (BR-RET-01).
- **AC-UC168-02:** Given delivery confirmed 10 days ago (period 7), when submitted, then `WINDOW_EXPIRED` and no return row (BR-RET-01).
- **AC-UC168-03:** Given `isReturnable = false`, when submitted, then `NOT_RETURNABLE` (BR-RET-01).
- **AC-UC168-04:** Given an accepted request, when states advance, then only the return states of the machine are used (BR-RET-02).
