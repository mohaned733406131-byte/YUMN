# UC-322 — Sort Results by Relevance, Price, Rating, or Newest

## Header Info
- **Use Case ID:** UC-322
- **Title:** Sort Results by Relevance, Price, Rating, or Newest
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer picks a different sort mode in the search results toolbar
- **Priority:** P2
- **Goal:** Re-order the same filtered result set under a chosen sort without losing filters, facets or page position semantics.
- **Preconditions:** Search results exist for the query (UC-006, UC-321); sort ∈ `relevance | price_asc | price_desc | newest | rating` (API-SRC-001).

## Main Scenario
1. Customer opens results with the default `sort=relevance`.
2. Chooses "price: low to high" → the client re-requests with `?sort=price_asc`.
3. Server re-orders the same filtered set on integer YER prices and restarts the cursor for the new order (FR-009).
4. Facet counts are unchanged — counts are order-independent (UC-321).
5. The sort chip and URL update, so the state is shareable and back-button correct.

## Alternative Scenarios
- **A1 — Sort by rating:** ordering uses the recomputed rating derived from visible reviews only (BR-REV-05).
- **A2 — Sort by newest:** ordering reflects index time; a just-published product appears once its `b02.catalog.index` job has run (BR-PLT-01).
- **A3 — Sort with filters applied:** filters stay in force; only the order changes (rejoins UC-321).

## Exception Scenarios
- **E1 — Invalid sort value:** `VALIDATION_ERROR`; the previous ordering stays rendered.
- **E2 — Index lag during `newest`:** results reflect the indexed set; browse-by-category stays authoritative during lag (NFR-007).
- **E3 — Search unavailable:** falls back to the degraded/`SEARCH_UNAVAILABLE` path (UC-324) rather than a broken order.

## Postconditions
- Success: results rendered in the chosen order in the active locale; read-only — no rows written, no cart impact.
- Failure: the previous valid ordering remains; no mixed or partially sorted page.

## Business Rules Applied
- BR-REV-05, BR-CAT-06, BR-PLT-01

## Related Requirements
- FR-009 (Search & Discovery — sorting modes)
- **Relation:** UC-006 searches, UC-321 filters the same set, UC-324 covers the degraded case.

## Permissions / Data / External Dependencies
- **Permissions:** Public read — every caller sees only `ACTIVE`, non-suspended-store products in any order (BR-CAT-06).
- **Data involved:** search result set, sort parameter, cursor page state, rating aggregates (read) — no writes.
- **External dependencies:** Elasticsearch cluster (DEP-04); `b02.catalog.index` BullMQ jobs for freshness; cursor pagination.

## Acceptance Criteria
- **AC-UC322-01:** Given results with mixed prices, when `sort=price_asc` is chosen, then items are ordered from lowest to highest price with filters intact (FR-009).
- **AC-UC322-02:** Given `sort=rating`, when results return, then ordering uses the visible-review rating aggregates (BR-REV-05).
- **AC-UC322-03:** Given an invalid sort value, when requested, then `VALIDATION_ERROR` returns and the previous order is kept.
- **AC-UC322-04:** Given a sort change, when facet counts render, then counts are identical to the pre-sort values.
