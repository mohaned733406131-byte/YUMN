# UC-161 — Review the Authoritative Checkout Preview

## Header Info
- **Use Case ID:** UC-161
- **Title:** Review the Authoritative Checkout Preview
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer enters checkout from the cart
- **Priority:** P1
- **Goal:** Show server-recomputed totals, price-change flags and blockers so the customer explicitly re-confirms before any order exists.
- **Preconditions:** Cart non-empty; server-side cart read (FR-010); preview endpoint `GET /cart/checkout-view` (API-CRT-007) is read-only.

## Main Scenario
1. Cart → checkout entry → client calls `GET /cart/checkout-view` (API-CRT-007).
2. Server recomputes per-store sub-carts and totals (`subtotal`, `discount`, `vat`, `shippingEstimate`, `grandTotal`); client-side numbers are display-only — totals are always recalculated server-side (BR-CRT-04).
3. Response carries `priceChanges[{ productId, oldPrice, newPrice }]` → the customer must re-confirm the new prices before continuing (BR-CRT-04).
4. `blockers[]` (inactive, out-of-stock or out-of-policy lines) must be cleared before checkout proceeds, and `wallet.shortfall` shows any balance gap to top up first (UC-041).
5. `reservationExpiresAt` is displayed; after expiry the next mutation fails with `RESERVATION_EXPIRED`.
6. Customer confirms → checkout session starts (`POST /checkout/session`) which recomputes again, and `POST /orders` revalidates one final time (FR-011).

## Alternative Scenarios
- **A1 — No price changes and no blockers:** customer proceeds straight to the address and shipping steps.
- **A2 — Wallet shortfall shown:** customer tops up (UC-041) and returns; the authoritative balance check runs again at order confirmation.

## Exception Scenarios
- **E1 — Flag appears at confirm:** `PRICE_CHANGED` / `CART_ITEM_INELIGIBLE` / `RESERVATION_EXPIRED` → preview refreshes with the new flags; customer re-confirms or edits the cart (BR-CRT-04).
- **E2 — Network error:** the preview is read-only — no order exists and no money moved; retry safely.

## Postconditions
- Success: authoritative totals seen and any price change explicitly re-confirmed; checkout session ready to start (FR-010, FR-011).
- Failure: nothing committed — the preview never creates orders, holds payment or moves stock.

## Business Rules Applied
- BR-CRT-04

## Related Requirements
- FR-010 (Shopping Cart), FR-011 (Checkout & Order Placement)

## Permissions / Data / External Dependencies
- **Permissions:** owner-scoped read of the customer's own cart; another customer's cart returns 404.
- **Data involved:** cart lines with price snapshots, per-store totals, price-change and blocker flags, wallet balance/shortfall, reservation deadline.
- **External dependencies:** none — server-side computation only.

## Acceptance Criteria
- **AC-UC161-01:** Given a price raised after add-to-cart, when the preview loads, then `priceChanges` lists old and new price and re-confirmation is required (BR-CRT-04).
- **AC-UC161-02:** Given a client-rendered total that disagrees with the server, when the preview loads, then the server-recomputed total is displayed (BR-CRT-04).
- **AC-UC161-03:** Given an out-of-stock line, when the preview loads, then it appears in `blockers` and checkout cannot continue.
