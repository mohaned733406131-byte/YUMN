# UC-357 — See Locked Security Toggles in the Preference Center

## Header Info
- **Use Case ID:** UC-357
- **Title:** See Locked Security Toggles in the Preference Center
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the preference center and inspects the Security section
- **Priority:** P1
- **Goal:** Make clear that security notifications cannot be turned off — in the UI and at the API.
- **Preconditions:** Preference center open (FR-017); security rows are ON and immutable (BR-NTF-02); matrix fetched from the server (API-NTF-006).

## Main Scenario
1. The Security section renders rows (OTP, login alerts, password change, lockout, wallet freeze) each ON with a lock icon and the explanation "إشعارات أمنية لا يمكن إيقافها / Security notifications can't be turned off" (feedback §2.1).
2. Every security toggle is disabled — tapping it does nothing and offers no off state (BR-NTF-02).
3. The API marks these rows `locked: true`, `immutable: true` — the lock is server truth, not just styling (API-NTF-006).
4. A direct `PUT` attempting to disable a security category is refused with `PREFERENCE_IMMUTABLE` (API-NTF-007).
5. Security events fan out on all applicable channels regardless of other preferences (notifications.md fan-out notes).

## Alternative Scenarios
- **A1 — Non-security rows:** ordinary toggles behave as in UC-356.
- **A2 — Screen reader:** the locked state is announced as text plus icon, never color/icon alone (NFR-011).
- **A3 — Locale switch:** the explanation renders in `ar` and `en` (BR-NTF-04).

## Exception Scenarios
- **E1 — Client tampering (direct API):** `PREFERENCE_IMMUTABLE`; stored preferences are unchanged.
- **E2 — Matrix fetch fails:** block error with retry; no unlocked illusion is ever rendered.
- **E3 — Stale cached matrix:** refetch corrects it — security rows can never render as off.

## Postconditions
- Success: security rows remain ON and locked; other rows stay per the customer's choices.
- Failure: no security preference is disabled by any path — UI or API (BR-NTF-02).

## Business Rules Applied
- BR-NTF-02

## Related Requirements
- FR-017 (Notifications & Messaging — mandatory security notices)
- **Relation:** UC-356 changes the unlocked marketing cells; UC-355 is the inbox these notices land in; UC-312/UC-336 are security/order notices delivered regardless.

## Permissions / Data / External Dependencies
- **Permissions:** Any authenticated customer may read own matrix; nobody — customer or admin UI — can disable security categories (BR-NTF-02).
- **Data involved:** preference rows with `locked`/`immutable` flags, security category definitions, fan-out channel sets.
- **External dependencies:** notification service (B10); preference API (API-NTF-006/007); localized explanation strings (BR-NTF-04).

## Acceptance Criteria
- **AC-UC357-01:** Given the preference center, when Security rows render, then each shows ON, disabled, with lock icon and explanation (BR-NTF-02).
- **AC-UC357-02:** Given a direct `PUT` disabling a security category, when it runs, then `PREFERENCE_IMMUTABLE` returns and stored preferences are unchanged (BR-NTF-02).
- **AC-UC357-03:** Given a lockout event, when fan-out runs, then the security notice goes out on all applicable channels (BR-NTF-02).
- **AC-UC357-04:** Given a screen-reader user, when the toggles are read, then the locked state is announced as text (NFR-011).
