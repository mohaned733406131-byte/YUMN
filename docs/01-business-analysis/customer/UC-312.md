# UC-312 — Hit the OTP Attempt Cap and Read the Blocked-Verification Notice

## Header Info
- **Use Case ID:** UC-312
- **Title:** Hit the OTP Attempt Cap and Read the Blocked-Verification Notice
- **Actor:** Customer (ACT-01)
- **Trigger:** The customer submits a wrong 6-digit OTP for the third time
- **Priority:** P1
- **Goal:** Stop verification at the attempt cap, tell the customer clearly what happened, and route them to recovery.
- **Preconditions:** An OTP is pending verification (BR-AUTH-03: 6 digits, 5-minute expiry, max 3 attempts); two attempts already failed; verification screen open (FL-01 D2).

## Main Scenario
1. Customer enters a wrong code for the third time; the client submits it.
2. Server rejects the attempt and consumes the OTP attempt budget (BR-AUTH-03).
3. The form is replaced by the blocked-verification notice: verification blocked, no input, explicit support entry (screen-states, OTP screen).
4. A security notification of the blocked verification is fanned out on all applicable channels (BR-NTF-02).
5. Customer recovers via resend (cooldown 60 s, ≤3 resends/10 min — UC-141) or support contact (UC-014).

## Alternative Scenarios
- **A1 — Attempts still remaining:** inline error with the remaining count shown explicitly (3 → 2 → 1); the form stays usable (BR-AUTH-03).
- **A2 — Code expired instead:** "code expired" state with resend as the primary action (BR-AUTH-03).
- **A3 — Correct code on the final attempt:** verification succeeds, the success check leads to the destination, counters are discarded (FL-01 D2).

## Exception Scenarios
- **E1 — Double submit of the correct code:** the already-verified state redirects idempotently to the destination; no second verification is recorded.
- **E2 — Notification fan-out delayed:** the block still enforces server-side; the security notice retries under platform policy (BR-PLT-02).
- **E3 — Client-side bypass attempt (direct API):** the attempt counter lives server-side, so the cap holds regardless of the UI.

## Postconditions
- Success (recovery path): a new OTP is requested under cooldown/resend limits, or support is engaged; the block notice was delivered.
- Failure: no session issued, the old OTP stays unusable, attempt counters are not reset by the blocked state.

## Business Rules Applied
- BR-AUTH-03, BR-NTF-02, BR-PLT-02

## Related Requirements
- FR-001 (Identity, Authentication & Session Management — OTP attempt limits)
- **Relation:** UC-141 governs resend counters; UC-142 covers step-up OTP for sensitive changes; UC-014 is the support entry offered here.

## Permissions / Data / External Dependencies
- **Permissions:** unauthenticated applicant bound to one OTP context; nobody can clear the counter from the client.
- **Data involved:** OTP record (expiry, attempt count, consumed flag), blocked-verification notice, security notification.
- **External dependencies:** auth/OTP service (B01); notification fan-out (B10); support entry point (B13).

## Acceptance Criteria
- **AC-UC312-01:** Given two failed attempts, when a third wrong OTP is submitted, then verification is blocked and the notice renders without an input field (BR-AUTH-03).
- **AC-UC312-02:** Given the block, when fan-out runs, then a security notification is sent on all applicable channels and cannot be disabled (BR-NTF-02).
- **AC-UC312-03:** Given the notice, when read, then it offers a support entry and no silent retry loop (BR-NTF-02).
- **AC-UC312-04:** Given attempts left above zero, when a wrong OTP is submitted, then the remaining count is displayed explicitly (3 → 2 → 1).
