# UC-142 — Complete Step-Up OTP Verification for a Sensitive Change

## Header Info
- **Use Case ID:** UC-142
- **Title:** Complete Step-Up OTP Verification for a Sensitive Change
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer starts a sensitive account change (password change or account-deletion request) while already signed in
- **Priority:** P1
- **Goal:** Prove current possession of the phone with a fresh OTP before the sensitive change is executed.
- **Preconditions:** Customer authenticated with a verified phone; target action is classified sensitive (SEC-REQ-001); API touchpoint is `POST /auth/otp/verify` with `context=SENSITIVE_CHANGE` (API-ATH-003).

## Main Scenario
1. Customer starts a sensitive change (UC-145 password change or UC-153 deletion request); the server refuses it with `OTP_NOT_VERIFIED` until a step-up exists (SEC-REQ-001).
2. Client requests the code: `POST /auth/otp/request { phone, context: "SENSITIVE_CHANGE" }` (API-ATH-002) under the same cooldown and resend caps (BR-AUTH-03).
3. System issues a 6-digit OTP with 5-minute expiry and 3 verification attempts, delivered on the SMS/WhatsApp transport.
4. Customer enters the code → `POST /auth/otp/verify` (API-ATH-003) returns `verified: true`; the correct code atomically consumes the stored OTP (BR-AUTH-03).
5. Client retries the sensitive action carrying the verified step-up; server-side role and ownership checks still apply independently (FR-002).
6. The step-up applies to this challenge only; a later sensitive change requires a new OTP.

## Alternative Scenarios
- **A1 — Resend inside the step-up:** same cooldown, quota, and attempt rules as UC-141 (BR-AUTH-03).
- **A2 — Step-up completed but action deferred:** if the customer delays past the OTP freshness window, the action is re-challenged with a new code.
- **A3 — Wrong context code:** an OTP issued for `REGISTER`/`PASSWORD_RESET` does not satisfy `SENSITIVE_CHANGE` — the correct context must be verified.

## Exception Scenarios
- **E1 — Three wrong codes:** `OTP_MAX_ATTEMPTS` blocks verification until a new code is issued (BR-AUTH-03).
- **E2 — Cooldown hit on resend:** `OTP_RESEND_COOLDOWN` with remaining seconds; counters unchanged (BR-AUTH-03).
- **E3 — Network error during verify:** client retries; the attempt counter only decrements on server receipt, so no partial state is left (BR-AUTH-03).

## Postconditions
- Success: step-up flag set for the session; the sensitive action executes on retry (FR-001, FR-002).
- Failure: no step-up granted; the sensitive action stays refused (`OTP_NOT_VERIFIED`); account state unchanged.

## Business Rules Applied
- BR-AUTH-03

## Related Requirements
- FR-001 (Identity, Authentication & Session Management), FR-002 (Roles, Permissions & Access Control)

## Permissions / Data / External Dependencies
- **Permissions:** a customer can step up only their own session; the step-up never widens roles or ownership (server-side enforcement, SEC-REQ-004).
- **Data involved:** hashed OTP, attempt counter, short-lived step-up verification flag on the session.
- **External dependencies:** SMS/WhatsApp OTP delivery (UC-040).

## Acceptance Criteria
- **AC-UC142-01:** Given a sensitive action attempted without step-up, when submitted, then `OTP_NOT_VERIFIED` returns and nothing changes.
- **AC-UC142-02:** Given a valid `SENSITIVE_CHANGE` OTP, when verified and the action retried, then the action succeeds (BR-AUTH-03).
- **AC-UC142-03:** Given three wrong codes, when the third fails, then `OTP_MAX_ATTEMPTS` blocks verification until a new code is issued (BR-AUTH-03).
