# UC-307 — Hit the 10-Address Cap and Free Up a Slot

## Header Info
- **Use Case ID:** UC-307
- **Title:** Hit the 10-Address Cap and Free Up a Slot
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer submits an 11th address while the book already holds 10 active entries
- **Priority:** P2
- **Goal:** Enforce the ≤10 address invariant with a readable rejection and show the customer how to free a slot.
- **Preconditions:** Authenticated session (UC-003); address book already holds 10 active addresses (FR-003 ≤10 invariant, checked app-side before insert).

## Main Scenario
1. Customer taps "add address" and submits the completed form (conceptual `POST /addresses`).
2. Server counts the caller's active addresses: 10 of 10 used (FR-003).
3. Insert is rejected with `MAX_ADDRESSES_REACHED`; no row is written and the form keeps its values (BR-PLT-05 localized copy).
4. The message points at the recovery: edit or delete an existing address (UC-005, UC-306) to free a slot.
5. After a delete brings the count to 9, the next valid submit succeeds → `201`, first address becomes default if it is the only one.

## Alternative Scenarios
- **A1 — Count below 10:** the address is created normally; default flag set when it is the first entry (rejoins UC-005).
- **A2 — Customer edits instead of adding:** `PUT /addresses/{id}` replaces content without consuming a slot (UC-005).
- **A3 — Default address deleted first:** slot frees and default reassignment happens in the same delete (UC-306 A3).

## Exception Scenarios
- **E1 — New address fails field validation:** `VALIDATION_ERROR` / `PHONE_INVALID` (recipient phone `^7[0-9]{8}$`, BR-AUTH-01) — the cap is not the cause; no row written.
- **E2 — Two devices add concurrently at count 9:** the count check runs inside the insert transaction; one wins, the loser gets `MAX_ADDRESSES_REACHED`; never 11 rows.
- **E3 — Response lost after a successful insert:** a retried submit is re-counted, so the book can never exceed 10 (FR-003 invariant).

## Postconditions
- Success: a row is added; active address count ≤ 10 still holds; default uniqueness preserved.
- Failure: exactly 10 rows remain, no partial row, no default flag churn.

## Business Rules Applied
- BR-AUTH-01, BR-PLT-05

## Related Requirements
- FR-003 (User & Profile Management — addresses ≤10)
- **Relation:** UC-005 manages the book; UC-306 is the delete guard used here to free a slot; UC-308 keeps past orders on their snapshot after the edit.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner scope — the count is per authenticated `sub`, never global.
- **Data involved:** address rows (insert attempt), active-address counter, default flag — read/write on the owner's own book only.
- **External dependencies:** account/address service (B01); no third-party providers.

## Acceptance Criteria
- **AC-UC307-01:** Given 10 active addresses, when an 11th is submitted, then `MAX_ADDRESSES_REACHED` returns and the book still holds 10 rows (FR-003).
- **AC-UC307-02:** Given 9 active addresses, when a valid address is submitted, then it is created and the count becomes 10.
- **AC-UC307-03:** Given the rejection, when the message renders, then it is localized in the user's locale with a delete/edit recovery path (BR-PLT-05).
- **AC-UC307-04:** Given two concurrent adds at count 9, when both commit, then at most 10 active rows exist afterwards.
