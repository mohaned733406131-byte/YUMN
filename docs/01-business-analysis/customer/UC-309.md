# UC-309 — Recover After a Refresh-Token Reuse Revokes the Session Family

## Header Info
- **Use Case ID:** UC-309
- **Title:** Recover After a Refresh-Token Reuse Revokes the Session Family
- **Actor:** Customer (ACT-01)
- **Trigger:** The app's silent refresh is refused because the session family was revoked after a consumed refresh token was replayed
- **Priority:** P1
- **Goal:** Return the customer to a working session through re-login, with the revocation alert understood and no attacker session surviving.
- **Preconditions:** A session exists whose family was revoked (BR-AUTH-05, UC-043); access token expired or expiring within the 15-minute TTL (C-08); customer knows the account.

## Main Scenario
1. Client attempts the silent refresh (~12 min into the 15-min TTL) with its httpOnly refresh cookie.
2. Server finds the family revoked by reuse detection → `401`, no new token pair is issued (BR-AUTH-05).
3. Client clears the auth slice and in-memory access token, keeps the current route, and shows the localized "session ended on another device" toast (BR-PLT-05).
4. The next guarded action prompts login (UC-003); the customer re-authenticates with phone + password.
5. A fresh session family is issued, guest cart merges if present (BR-CRT-03), and the customer resumes at the remembered route.

## Alternative Scenarios
- **A1 — Reuse alert already delivered:** the mandatory security alert reached SMS/WhatsApp/in-app before the customer retries (BR-AUTH-05, BR-NTF-02).
- **A2 — Other devices unaffected:** only the replayed family dies; the user's other sessions keep working (BR-AUTH-05, 5-device cap in UC-003).
- **A3 — App relaunched before re-login:** resume-on-launch fails the same way (UC-181) and lands on login.

## Exception Scenarios
- **E1 — Re-login itself fails (network):** error with retry; no session is created and no token pair is stored.
- **E2 — Customer suspects compromise:** password reset via OTP (UC-004) invalidates all remaining sessions (BR-AUTH-07).
- **E3 — Concurrent refreshes in several tabs:** single-flight refresh collapses them into one call; all awaiting requests receive the same 401 once, then one re-login.

## Postconditions
- Success: a new session family is active at the previous route; the revoked family stays dead; the reuse alert is on record.
- Failure: no tokens issued, app remains unauthenticated on its current route — nothing half-written.

## Business Rules Applied
- BR-AUTH-05, BR-AUTH-07, BR-CRT-03, BR-PLT-05

## Related Requirements
- FR-001 (Identity, Authentication & Session Management — token rotation & revocation)
- **Relation:** UC-043 (core) performs the rotation/revocation; UC-003 performs the re-login; UC-181 covers mobile resume.

## Permissions / Data / External Dependencies
- **Permissions:** the account owner only — revocation is scoped to the replayed family; no interactive login on the token service itself.
- **Data involved:** refresh-token records, session family, auth slice state, reuse alert, audit event.
- **External dependencies:** Redis session store; notification pipeline for the alert (B10); login endpoint (B01).

## Acceptance Criteria
- **AC-UC309-01:** Given a revoked family refresh token, when refresh is attempted, then `401` returns, no pair is issued, and the client clears auth state (BR-AUTH-05).
- **AC-UC309-02:** Given the cleared session, when the customer logs in again, then a new session family is issued and the pre-login route resumes.
- **AC-UC309-03:** Given reuse detection ran, when the customer checks notifications, then the reuse alert is present and cannot be disabled (BR-AUTH-05, BR-NTF-02).
- **AC-UC309-04:** Given a second device of the same user, when this family is revoked, then the other device's session keeps working (BR-AUTH-05).
