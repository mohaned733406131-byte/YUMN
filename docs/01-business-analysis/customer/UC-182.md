# UC-182 — Receive and Open a Deep-Linked Order Push

## Header Info
- **Use Case ID:** UC-182
- **Title:** Receive and Open a Deep-Linked Order Push
- **Actor:** Customer (ACT-01)
- **Trigger:** An order state change fires a push to the customer's registered device (S4); customer taps it
- **Priority:** P2
- **Goal:** Deliver an order-event push to an active device and land the customer on the correct, freshly fetched order detail screen.
- **Preconditions:** Customer registered a push device (UC-178); an order exists that belongs to them; push not opted out for the category.

## Main Scenario
1. An order state change triggers notification fan-out → a push is sent to the active device token through FCM/APNs (BR-NTF-01 channel set).
2. Payload carries localized title/body plus `data.deepLink` `{ surface: "CUSTOMER", route: "/orders/{orderId}", entity: { type: "ORDER", id }, action: "VIEW", locale }` — server-generated, never an external URL.
3. Customer taps the push on S4 → the app resolves the deep link `yumn://orders/{id}` to the guarded OrderStack route; an unauthenticated app goes to the auth stack first and returns after login.
4. The client re-fetches the order — a notification never embeds authoritative state — and the timeline shows only the buyer's own slice (BR-ORD-09).
5. The in-app twin of the notification reflects the open/read state in the inbox (UC-175).

## Alternative Scenarios
- **A1 — App in foreground:** an in-app banner appears; tapping navigates without a cold start.
- **A2 — Push not delivered (stale token):** the notification still lands in the in-app center (UC-175); no push retry storm.
- **A3 — Wrong-surface payload:** clients ignore notifications whose `surface` they do not serve.

## Exception Scenarios
- **E1 — FCM/APNs outage or rejection:** delivery falls back to the in-app record; queue retries follow the platform job policy with no storm.
- **E2 — Unauthenticated at open:** the auth stack shows, then the remembered deep link resumes (UC-181 A2).
- **E3 — Route not in the allowlist:** ignored — routes are validated against the server-side template; arbitrary URLs are never opened.

## Postconditions
- Success: customer lands on their own order detail with fresh data; push routing and inbox state updated; no order/escrow state changed by opening.
- Failure: notification remains available in the in-app inbox; app stays on its current screen.

## Business Rules Applied
- BR-NTF-01, BR-ORD-09

## Related Requirements
- FR-017 (Notifications & Messaging — push channel), FR-012 (Order Lifecycle Management — timeline visibility)
- **Relation:** `../../10-integrations/core/push-notifications.md` and S4 mobile routing own the token lifecycle and deep-link contract; UC-178 registered the token used here.

## Permissions / Data / External Dependencies
- **Permissions:** only the order's buyer receives and reads the push; timeline projection is buyer-scoped (BR-ORD-09).
- **Data involved:** push payload (localized text + deep link), device token, order fetch on open — no authoritative state in the payload.
- **External dependencies:** FCM/APNs push adapters; notification service (B10); order service (B06); S4 deep-link router.

## Acceptance Criteria
- **AC-UC182-01:** Given an active device token, when an order state changes, then a push arrives with a `CUSTOMER`-surface deep link to `/orders/{orderId}` (BR-NTF-01).
- **AC-UC182-02:** Given the customer taps the push, when the app opens, then the order detail is re-fetched and shows the buyer's own timeline slice (BR-ORD-09).
- **AC-UC182-03:** Given push delivery failed, when the inbox is opened, then the same notification is present in-app (BR-NTF-01).
- **AC-UC182-04:** Given an unauthenticated app, when the deep link opens, then login runs first and the order route resumes afterwards.
