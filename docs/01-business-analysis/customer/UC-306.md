# UC-306 — Delete an Address Used by an In-Flight Checkout

## Header Info
- **Use Case ID:** UC-306
- **Title:** Delete an Address Used by an In-Flight Checkout
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer taps delete on a saved address while an open checkout session still depends on it
- **Priority:** P2
- **Goal:** Remove an address from the book without breaking a checkout that already resolved its zone and fee from that address.
- **Preconditions:** Authenticated session (UC-003); address book holds the address (UC-005, ≤10 per FR-003); a checkout session is open at step 2/3 (FR-011, WF-003).

## Main Scenario
1. Customer opens `/[locale]/account/addresses` and taps delete on the address referenced by the open checkout (conceptual `DELETE /addresses/{id}`).
2. Server checks active sessions: the address is the one the in-flight checkout resolved its zone and fee from (FR-011, BR-SHP-01).
3. Deletion is refused with `VALIDATION_ERROR` — localized copy explains the address is in use by a checkout in progress (BR-PLT-05); no row is touched.
4. Customer completes or abandons the checkout; the session expires and the guard clears.
5. The retry succeeds: the address is soft-deleted and, if it was the default, the next address becomes default (UC-005).

## Alternative Scenarios
- **A1 — No open session:** delete runs immediately → `204`, soft delete, book refreshes (rejoins UC-005).
- **A2 — Different address than the one in use:** guard passes; only the selected row is soft-deleted, the checkout keeps its address.
- **A3 — Address was the checkout default:** after a successful delete the default flag moves atomically to another address (FR-003).

## Exception Scenarios
- **E1 — Unknown or foreign address id:** `404 NOT_FOUND`; nothing changes, existence of other users' rows is never revealed (FR-003).
- **E2 — Checkout opens while the delete commits:** the guard re-evaluates inside the request; the loser sees `VALIDATION_ERROR` or `404`, never a half-deleted row.
- **E3 — Delete request lost after commit:** retrying returns `404` for the already-soft-deleted row; no duplicate deletion effect.

## Postconditions
- Success: address soft-deleted (`deleted_at` set), default reassigned, open checkout sessions unaffected; past orders keep their address snapshot (UC-308).
- Failure: address row intact, checkout session intact, no orphan references created.

## Business Rules Applied
- BR-SHP-01, BR-PLT-05

## Related Requirements
- FR-003 (User & Profile Management — address book ≤10), FR-011 (Checkout & Order Placement — address step)
- **Relation:** UC-005 owns add/edit/delete of the book; UC-307 covers the 10-address cap; UC-308 covers snapshot preservation on past orders.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, owner scope only — another user's address id returns 404.
- **Data involved:** address row (soft-delete flag, `is_default`), checkout session address reference — no order rows written.
- **External dependencies:** account/address service (B01); checkout session store (B05); no third-party providers.

## Acceptance Criteria
- **AC-UC306-01:** Given a checkout session resolved from the address, when delete is requested, then `VALIDATION_ERROR` returns and the address row is unchanged (BR-SHP-01).
- **AC-UC306-02:** Given no open checkout references the address, when delete is confirmed, then the row is soft-deleted and leaves the list (FR-003).
- **AC-UC306-03:** Given the deleted address was the default, when deletion completes, then exactly one other address carries `is_default`.
- **AC-UC306-04:** Given another user's address id, when delete is requested, then `404 NOT_FOUND` returns and that row is untouched.
