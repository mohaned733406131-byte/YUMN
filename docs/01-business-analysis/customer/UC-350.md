# UC-350 — Check Return Eligibility Before Submitting a Request

## Header Info
- **Use Case ID:** UC-350
- **Title:** Check Return Eligibility Before Submitting a Request
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer taps the return entry on a delivered/completed order
- **Priority:** P0
- **Goal:** Decide eligibility up front — window and `isReturnable` — before any form, pickup or state change.
- **Preconditions:** Order `DELIVERED` or `COMPLETED` (FR-016); window = delivery confirmation + `returnPeriodDays` (BR-RET-01, C-11); return entry reachable (FL-04 D1).

## Main Scenario
1. Customer opens "طلب إرجاع / Request return" from the order → the server evaluates the policy (conceptual `POST /orders/{id}/returns` precheck).
2. Eligible: the form opens with `daysRemaining` and the refund estimate — item value plus the shipping-refundable flag (API-RET-001).
3. Not eligible: `WINDOW_EXPIRED` or `NOT_RETURNABLE` returns — distinct rejections with the policy reason and window dates (returns.md behavior notes).
4. The same policy block is visible earlier on the product page (UC-317), so the expectation is set before purchase.
5. The rejected path offers a support route — no pickup is scheduled and no return row exists (edge-cases EC-37).

## Alternative Scenarios
- **A1 — `isReturnable = false`:** `NOT_RETURNABLE` regardless of dates.
- **A2 — Inside the window:** proceed to item selection and reason (FL-04 step 2).
- **A3 — Dispute already open on the sub-order:** `DISPUTE_ALREADY_OPEN` — resolve the dispute first (UC-354).

## Exception Scenarios
- **E1 — Order not yet delivered:** the return entry is not offered at all — eligibility is never evaluated early.
- **E2 — Clock/timezone differences:** the window is computed server-side; the client never decides eligibility.
- **E3 — Eligibility check fails:** retry with the block-error pattern; the form does not open optimistically.

## Postconditions
- Success: the eligibility decision with its dates is shown; a return row exists only if the customer then submits.
- Failure: no return row, no pickup, no order-state change (BR-ORD-03).

## Business Rules Applied
- BR-RET-01

## Related Requirements
- FR-016 (Returns & Refunds — eligibility gate)
- **Relation:** UC-317 shows the policy on the PDP; UC-351 covers the late-window branch; UC-354 is the dispute conflict; UC-352 runs after submission.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own order only — eligibility decided server-side (API-RET-001 owner check).
- **Data involved:** delivery confirmation date, `returnPeriodDays`, `isReturnable`, window deadline, refund estimate — read-only precheck.
- **External dependencies:** returns service (B09); order service (B06); product policy from catalog (B02).

## Acceptance Criteria
- **AC-UC350-01:** Given a return past `returnPeriodDays`, when eligibility runs, then `WINDOW_EXPIRED` returns with window dates and no return row (BR-RET-01, C-11).
- **AC-UC350-02:** Given `isReturnable = false`, when checked, then `NOT_RETURNABLE` returns regardless of dates (BR-RET-01).
- **AC-UC350-03:** Given the order inside the window, when checked, then the form opens with `daysRemaining` (BR-RET-01).
- **AC-UC350-04:** Given an ineligible order, when the screen renders, then the policy reason plus a support path show — never a dead end (NFR-012).
