# UC-334 — Filter the Order List by Status

## Header Info
- **Use Case ID:** UC-334
- **Title:** Filter the Order List by Status
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens the orders screen and applies a lifecycle-status chip
- **Priority:** P2
- **Goal:** Narrow the own-order feed to one state with a restorable URL and never leak another customer's rows.
- **Preconditions:** Authenticated customer with ≥1 own order (FR-012); orders route `/{locale}/account/orders` available (routing §4).

## Main Scenario
1. Customer opens `/{locale}/account/orders` → system fetches the own master-order feed (conceptual `GET /orders`, API-ORD-003, cursor).
2. Customer picks a status chip (e.g. `PLACED`, `OUT_FOR_DELIVERY`, `COMPLETED`) → the client re-requests with `?status=<STATE>` (FR-012).
3. Server returns only the customer's orders in that state — buyer-scoped visibility (BR-ORD-09) over the fixed 17-state enumeration (BR-ORD-01).
4. The active chip renders as removable and mirrors into the URL, so reload/back restore the same view.
5. Removing the chip rejoins the unfiltered feed at the first page, newest-first.

## Alternative Scenarios
- **A1 — Filter with no matches:** localized empty state with a clear-filter recovery — never an error (NFR-012).
- **A2 — State changes server-side:** the next refresh shows the order under its new state only.
- **A3 — Deep link with `?status=`:** the list opens pre-filtered; the URL wins on load.

## Exception Scenarios
- **E1 — Unknown status value:** `VALIDATION_ERROR`; the last valid list stays rendered (forms-and-validation §5).
- **E2 — Feed fetch fails:** page error with retry plus home/search links; no fabricated rows (screen-states §4).
- **E3 — Session expired:** re-auth prompt on the route, then the request repeats (routing §9).

## Postconditions
- Success: filtered own-order list rendered in the active locale; read-only — no order rows written.
- Failure: the previous valid list remains; foreign orders never appear (BR-ORD-09).

## Business Rules Applied
- BR-ORD-01, BR-ORD-09

## Related Requirements
- FR-012 (Order Lifecycle Management — status feed & filtering)
- **Relation:** UC-012 is the unfiltered list and detail; UC-335 refreshes a conflicted screen; UC-337 shows the cancel refusal reachable from a list row.

## Permissions / Data / External Dependencies
- **Permissions:** CUSTOMER role, own orders only — cross-customer rows excluded server-side (ownership scope).
- **Data involved:** order headers (`masterState`, totals, thumbnail), filter chip state, URL query string — no writes.
- **External dependencies:** order service (B06); cursor pagination conventions; localized error strings (BR-PLT-05).

## Acceptance Criteria
- **AC-UC334-01:** Given orders in several states, when a status chip is selected, then only the customer's orders in that state render (BR-ORD-09).
- **AC-UC334-02:** Given a selected status filter, when the page reloads, then the same filter and result set restore from the URL.
- **AC-UC334-03:** Given a filter matching no orders, when results return, then a localized empty state with clear-filter recovery shows (NFR-012).
- **AC-UC334-04:** Given an unknown `?status` value, when the feed runs, then `VALIDATION_ERROR` returns and the prior list stays rendered.
