# UC-181 — Resume an Existing Session on App Launch (Mobile)

## Header Info
- **Use Case ID:** UC-181
- **Title:** Resume an Existing Session on App Launch (Mobile)
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer launches the customer mobile app (S4) that holds a stored refresh token
- **Priority:** P1
- **Goal:** Silently resume the customer's existing session on app launch by rotating the refresh token, without showing the login screen.
- **Preconditions:** App installed; a refresh token was stored at last login (keychain/keystore); a device session may still exist server-side (≤5 sessions, C-08).

## Main Scenario
1. Customer opens S4 → client reads the stored refresh token; no login screen is shown when one exists.
2. Client `POST /auth/refresh` (API-ATH-005) with the stored refresh credential.
3. System rotates the token: the old refresh is consumed, a new access token (15 min) and a new refresh token are issued (BR-AUTH-05).
4. The app restores its guarded route (Splash → MainTabs/OrderStack per S4 routing); an unauthenticated deep link bounces to the auth stack and returns after login.
5. The session continues within the ≤5 device-session cap (C-08); other devices keep their own sessions.

## Alternative Scenarios
- **A1 — Access token still valid:** the client skips the refresh and renders immediately from the cached session.
- **A2 — Deep link while unauthenticated:** the target route is remembered, login completes, then the route resumes.
- **A3 — No stored token:** the auth stack (Login/Register/Otp) is shown — a fresh login is out of this use case's scope (UC-003).

## Exception Scenarios
- **E1 — Expired refresh token:** `TOKEN_EXPIRED` → login screen; no authenticated data is rendered.
- **E2 — Refresh token reuse detected:** `REFRESH_TOKEN_REUSED` → the entire session family is revoked and the user is alerted (BR-AUTH-05).
- **E3 — Session revoked elsewhere:** `SESSION_NOT_FOUND`/`AUTH_INVALID` → login screen required.

## Postconditions
- Success: a fresh access/refresh pair is stored, the app resumes on the guarded route, and no other session is disturbed.
- Failure: session not resumed — the auth stack appears; the old credentials are discarded.

## Business Rules Applied
- BR-AUTH-05

## Related Requirements
- FR-001 (Identity, Authentication & Session Management — session resume/refresh rotation)
- **Relation:** UC-003 (login) establishes the stored token; UC-147 may revoke this device's session server-side.

## Permissions / Data / External Dependencies
- **Permissions:** only the token holder resumes the session; presented reuse revokes the whole family (BR-AUTH-05).
- **Data involved:** refresh token, access token, device session row — write on rotation only.
- **External dependencies:** auth service (B01); secure token storage on device (S4); route guards in S4 routing.

## Acceptance Criteria
- **AC-UC181-01:** Given a stored valid refresh token, when the app launches, then a new access+refresh pair is issued with no login screen (BR-AUTH-05).
- **AC-UC181-02:** Given a previously-used refresh token, when presented, then the session family is revoked and the user is alerted (BR-AUTH-05).
- **AC-UC181-03:** Given no stored token, when the app launches, then the auth stack is shown (C-08).
- **AC-UC181-04:** Given an expired refresh token, when refresh is attempted, then the login screen appears and no authenticated data is rendered.
