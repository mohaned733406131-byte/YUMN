# UC-206 — Update Courier Profile and Served Zones

## Header Info
- **Use Case ID:** UC-206
- **Title:** Update Courier Profile and Served Zones
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier edits their display name or served zones from the Profile tab of the courier app (S5 routing: `Tabs{Queue, Active, History, Profile}`)
- **Priority:** P2
- **Goal:** Keep the courier's profile and served zones accurate so zone-eligible delivery offers stay correct.
- **Preconditions:** Courier authenticated; profile readable; requested zones must be domestic shipping zones (C-17).

## Main Scenario
1. Courier opens Profile → client `GET /courier/profile` (API-SHP-014) returns display name, masked phone, served zones, availability and delivery stats.
2. Courier edits display name and/or served zones → submits `PUT /courier/profile` (API-SHP-015).
3. System validates each requested zone against the platform's shipping zones; non-domestic or unknown zones are rejected (`NO_SHIPPING_ZONE`).
4. On success the profile is saved and the response echoes the updated profile; delivery stats are unchanged.
5. Offer eligibility follows the saved zones: future offers are broadcast only to couriers serving that zone (BR-SHP-04); already-assigned jobs are untouched.

## Alternative Scenarios
- **A1 — Display name only:** zones untouched → offer eligibility stays exactly as before (BR-SHP-04).
- **A2 — Remove a zone while holding active jobs there:** allowed — active jobs remain assigned and completable; only new offers for that zone stop (BR-SHP-04).
- **A3 — Availability unchanged:** the online/offline switch is a separate control (UC-207); this update never flips it.

## Exception Scenarios
- **E1 — Non-domestic or unknown zone in payload:** rejected with `NO_SHIPPING_ZONE` / `VALIDATION_ERROR`; nothing is saved.
- **E2 — Profile fetch fails:** network error → last cached profile shown with retry; no local state is written.
- **E3 — Save fails mid-request:** request never applied server-side → profile keeps its previous values; courier retries with the same payload.

## Postconditions
- Success: profile and served zones reflect the edit; subsequent zone offering targets only the saved zones (BR-SHP-04).
- Failure: profile unchanged; no effect on offers or active assignments.

## Business Rules Applied
- BR-SHP-04

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** courier reads and writes only their own profile (server-side ownership check); availability is toggled only via UC-207.
- **Data involved:** courier profile row (display name, phone masked, zones, availability), delivery stats.
- **External dependencies:** shipping-zone registry (B08); offer eligibility engine (BR-SHP-04); courier app profile screen (S5).

## Acceptance Criteria
- **AC-UC206-01:** Given valid domestic zones, when the courier saves, then the profile reflects them and offers target only served zones (BR-SHP-04).
- **AC-UC206-02:** Given a non-domestic zone in the payload, when submitted, then the save is rejected and previous zones persist.
- **AC-UC206-03:** Given a zone removed while an active job there exists, when saved, then the job stays assigned and completable (BR-SHP-04).
- **AC-UC206-04:** Given only the display name is edited, when saved, then zone eligibility and availability are unchanged.
