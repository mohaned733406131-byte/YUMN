# UC-008 — Follow a Store

## Header Info
- **Use Case ID:** UC-008
- **Title:** Follow a Store
- **Actor:** Customer (ACT-01)
- **Trigger:** Authenticated customer taps "Follow" on a store page
- **Priority:** P2
- **Goal:** Let customers subscribe to a store so they receive new-product and offer notifications (BR-VND-05).
- **Preconditions:** User authenticated (UC-003); store ACTIVE and not suspended (BR-VND-04).

## Main Scenario
1. User opens a store page → system `GET /stores/{slug}` returns follower state (`is_following`) and public follower count.
2. User taps "Follow" → client `POST /stores/{id}/follow` (idempotent, BR-PLT-03).
3. System creates the follow relation, increments the follower count, and records it for the vendor's follower list (BR-VND-05).
4. Store's marketing notifications (new products/offers) are now eligible for this user, subject to channel opt-in preferences (BR-NTF-05); locale defaults to Arabic (BR-NTF-04).
5. User taps "Unfollow" → client `DELETE /stores/{id}/follow`; notifications cease from that point.

## Alternative Scenarios
- **A1 — Already following:** Repeat "Follow" → no-op returns current state (idempotent, BR-PLT-03); count unchanged.
- **A2 — Guest taps Follow:** Not authenticated → login gate (UC-003); after login the pending follow resumes.
- **A3 — Vendor views followers:** Vendor opens store dashboard → sees follower list and count scoped to own `store_id` only (BR-VND-07).

## Exception Scenarios
- **E1 — Store suspended after follow (BR-VND-04):** Follow relation is retained but no notifications are sent while suspended; storefront hidden.
- **E2 — Duplicate concurrent taps:** Two parallel requests → unique constraint on (user, store) absorbs the race; single row remains (DATA-REQ-001).
- **E3 — Notification provider outage:** Fan-out fails → BullMQ job retries 3× with backoff, then DLQ alert (BR-PLT-01, BR-PLT-02); follow state unaffected.

## Postconditions
- A follow relation exists (or was removed); follower count consistent with relation rows.
- No cart, order, or wallet change.
- Marketing notifications only go to opted-in channels (BR-NTF-05).

## Business Rules Applied
- BR-VND-04, BR-VND-05, BR-VND-07, BR-NTF-04, BR-NTF-05, BR-PLT-01, BR-PLT-02, BR-PLT-03

## Related Requirements
- FR-008 (Store Management — follower feature), FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** Customer manages own follows; vendor reads own follower list only (BR-VND-07).
- **Data involved:** Follow relation, follower count, notification preferences.
- **External dependencies:** Notification fan-out queues (B10, BullMQ per BR-PLT-01).

## Acceptance Criteria
- **AC-UC008-01:** Given an authenticated customer, when "Follow" is tapped twice, then exactly one follow row exists (idempotent).
- **AC-UC008-02:** Given a following customer, when the store publishes a new product, then an opted-in notification is delivered in the user's locale (BR-NTF-04).
- **AC-UC008-03:** Given vendor X, when querying followers, then only X's store followers are visible (BR-VND-07).
