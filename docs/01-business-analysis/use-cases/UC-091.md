# UC-091 — Suspend a User Account

## Header Info
- **Use Case ID:** UC-091
- **Title:** Suspend a User Account
- **Actor:** Admin (ACT-04) — user administration scope
- **Trigger:** Admin decides to suspend an abusive, compromised or legally challenged account
- **Priority:** P0
- **Goal:** Take an account out of service immediately — sessions revoked and dependent scopes frozen — with a recorded reason.
- **Preconditions:** Admin authenticated with suspend permission (API-ADM-003 `ADMIN`); target identified via UC-089/UC-090; a mandatory reason is supplied.

## Main Scenario
1. Admin opens the user (UC-090) → Suspend → enters a mandatory reason plus optional note.
2. Client `POST /admin/users/{id}/suspend` with `{ reason, note? }` (API-ADM-003).
3. System sets status → `SUSPENDED` and revokes every active session; the response reports affected counts (`sessionsRevoked`, `storeSuspended`, `walletFrozen`).
4. If the user is a vendor, the linked store inherits the suspension — products hidden, new orders blocked, existing orders frozen, payouts held (BR-VND-04); the platform-wide cascade across catalog, orders and payouts is owned by UC-072.
5. An append-only audit entry records actor, reason and before/after state (BR-PLT-06) and the `auditId` is returned.

## Alternative Scenarios
- **A1 — Vendor suspension:** Store-scoped effects apply per BR-VND-04; the store detail (UC-094) then shows the held state.
- **A2 — Already suspended:** Server returns `STATE_CONFLICT`; Admin reviews the existing suspension or reactivates instead (UC-092).
- **A3 — Scoped reversal:** Reactivation later targets `ACCOUNT`/`STORE`/`WALLET` scopes individually (UC-092).

## Exception Scenarios
- **E1 — Permission denied:** Moderator or non-admin → `403 FORBIDDEN`; nothing changes.
- **E2 — Final Super Admin:** Suspending the last Super Admin is refused (`LAST_SUPER_ADMIN`) — no lockout path exists.
- **E3 — Concurrent activation:** Another admin activates meanwhile → `STATE_CONFLICT`; the client re-reads and re-confirms.
- **E4 — Missing reason:** Request without `reason` → `REASON_REQUIRED` and no state change, so the audit always explains the action.

## Postconditions
- The account is `SUSPENDED`; sessions revoked; vendor scope frozen (BR-VND-04) where applicable.
- Exactly one audit entry exists for the action (BR-PLT-06); no money moved.

## Business Rules Applied
- BR-VND-04, BR-PLT-06

## Permissions / Data / External Dependencies
- **Permissions:** `ADMIN` only; Moderator forbidden; the final Super Admin cannot be targeted.
- **Data involved:** User status, sessions, linked store/wallet flags, audit entry.
- **External dependencies:** Session store (revocation); store lifecycle service; audit writer (BR-PLT-06).

## Acceptance Criteria
- **AC-UC091-01:** Given a reason, when suspend is posted, then status becomes `SUSPENDED` and active sessions drop to zero.
- **AC-UC091-02:** Given a vendor user, when suspended, then the store's products hide, orders block and payouts hold (BR-VND-04).
- **AC-UC091-03:** Given the action, when completed, then an `auditId` returns carrying before/after state (BR-PLT-06).
- **AC-UC091-04:** Given no reason, when posted, then `REASON_REQUIRED` returns and nothing changes.
- **AC-UC091-05:** Given a Moderator session, when posted, then `403 FORBIDDEN` is returned.
