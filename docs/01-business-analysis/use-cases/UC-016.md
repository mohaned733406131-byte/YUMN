# UC-016 — Manage Store Profile

## Header Info
- **Use Case ID:** UC-016
- **Title:** Manage Store Profile
- **Actor:** Vendor (ACT-02) — Owner/Manager staff
- **Trigger:** Vendor opens store settings in the seller dashboard
- **Priority:** P1
- **Goal:** Maintain the storefront's identity, branding, zones, operating settings, and follower visibility.
- **Preconditions:** Vendor authenticated with own store (BR-VND-07); KYC submitted at minimum; store not suspended (BR-VND-04).

## Main Scenario
1. Vendor opens store settings → client `GET /store` returns own profile scoped by `store_id` (BR-VND-07).
2. Vendor edits display name, description (ar/en per BR-PLT-05), logo/banner images (≤5 MB, jpg/png/webp, EXIF stripped — BR-CAT-08 patterns), contact channels, and operating settings → client `PUT /store`.
3. Vendor maintains shipping zones/fee overrides for their area and return policy defaults (`isReturnable`, `returnPeriodDays` — C-11, BR-RET-01).
4. System validates input, stores changes, and appends an audit entry for privileged/store configuration changes (BR-PLT-06).
5. Vendor views follower count/list and staff roster (BR-VND-05, BR-VND-06); Owner invites/changes Viewer/Editor/Manager staff only (BR-VND-06).
6. Changes take effect on the storefront after cache invalidation; suspended stores remain hidden (BR-VND-04).

## Alternative Scenarios
- **A1 — Staff role limits:** An Editor opens settings → allowed fields per role; role changes and staff invite/remove are Owner-only (BR-VND-06).
- **A2 — Suspension overlay:** Store suspended → profile read-only with suspension banner; payouts held, products hidden (BR-VND-04).
- **A3 — Preview:** Vendor previews the storefront as customer sees it (read-only render, BR-CAT-06 for ACTIVE products).

## Exception Scenarios
- **E1 — Concurrent edits:** Two managers save simultaneously → optimistic version conflict `409`; latest state reloaded before retry.
- **E2 — Image upload failure:** Scan/type rejection (SEC-REQ-011) → profile save proceeds without that asset; error shown.
- **E3 — Cross-store access attempt:** Vendor requests another store's ID → denied at service layer (BR-VND-07, SEC-REQ-004).

## Postconditions
- Store profile reflects approved changes; audit row appended (BR-PLT-06).
- No order, wallet, or catalog state change (except policy defaults affecting future orders).

## Business Rules Applied
- BR-VND-04, BR-VND-05, BR-VND-06, BR-VND-07, BR-RET-01, BR-PLT-05, BR-PLT-06

## Related Requirements
- FR-008 (Store Management & Storefront Configuration)

## Permissions / Data / External Dependencies
- **Permissions:** Own `store_id` only (BR-VND-07); Owner/Manager edit, Editor limited, Viewer read; Admin oversight (DOC-OVR-007).
- **Data involved:** Store profile, images, zones, return policy defaults, staff roles, follower list.
- **External dependencies:** Image storage; cache invalidation for storefront.

## Acceptance Criteria
- **AC-UC016-01:** Given vendor X, when requesting store of vendor Y, then access is denied (BR-VND-07).
- **AC-UC016-02:** Given an Editor role user, when attempting staff role change, then the action is rejected (Owner-only, BR-VND-06).
- **AC-UC016-03:** Given return period changed to 14 days, when saved, then new orders apply 14 days from delivery (BR-RET-01).
