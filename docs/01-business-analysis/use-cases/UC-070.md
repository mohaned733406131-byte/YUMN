# UC-070 — Screen and Sanitize All Uploaded Files

## Header Info
- **Use Case ID:** UC-070
- **Title:** Screen and Sanitize All Uploaded Files
- **Actor:** System (ACT-07) — shared upload validation pipeline (no interactive login)
- **Trigger:** Any upload endpoint receives a file (product images, KYC documents, bank-transfer proofs, delivery proof photos)
- **Priority:** P0
- **Goal:** Reject or sanitize every uploaded file before it becomes retrievable, so no malicious, oversized, or metadata-leaking content enters object storage.
- **Preconditions:** Object storage reachable; upload endpoints share the common validation pipeline; limits configured (BR-CAT-08, SEC-REQ-011).

## Main Scenario
1. The upload request hits type and size validation: magic-byte check against the declared type, ≤5 MB per file, images jpg/png/webp only — product images ≤10 per product (BR-CAT-08).
2. SVG/HTML payloads and type mismatches are rejected before storage; PDF is accepted only on document surfaces (KYC, bank-transfer proof).
3. For images the EXIF metadata is stripped so location/device data never leaves the platform (BR-CAT-08).
4. The file is malware-scanned; only a clean object is written to storage — PostgreSQL keeps keys and checksums, never raw bytes.
5. A rejected upload returns a validation error and persists nothing; a clean upload returns its object reference for the calling flow (UC-015 KYC, UC-017 product images).

## Alternative Scenarios
- **A1 — Oversized or malformed file (e.g., 12 MB JPEG, wrong magic bytes):** Rejected with a validation error; no object stored.
- **A2 — Document upload (KYC/bank proof):** PDF ≤5 MB accepted with the same scan/size gate; images on those surfaces obey the same image rules.
- **A3 — Attacker renames an executable to `.jpg`:** Magic-byte mismatch → rejected; declared type never trusted alone.

## Exception Scenarios
- **E1 — Scan service outage:** The file is held pending scanning and is not retrievable until cleared — the pipeline fails closed, never open.
- **E2 — Malware detected:** The object is quarantined, never served; the event is logged/alerted for security review.
- **E3 — EXIF strip fails:** The upload is rejected rather than stored with metadata intact; sanitization is mandatory before persistence.

## Postconditions
- Only sanitized, scanned, in-limit objects are retrievable; rejected uploads leave no trace in storage.
- Stored images have EXIF removed; keys/checksums recorded.
- Every accept/reject outcome is attributable to the requesting identity.

## Business Rules Applied
- BR-CAT-08

## Related Requirements
- FR-007 (Vendor Onboarding & KYC), FR-004 (Product Catalog Management), FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** Uploaders are scoped to their surfaces — Vendor (product/KYC), Customer (profile/proof), Courier (optional proof photo); System enforces validation for all.
- **Data involved:** Object storage keys, checksums, scan results, EXIF-stripped image bytes, KYC document metadata.
- **External dependencies:** MinIO-compatible object storage; malware scanner; upload endpoints across catalog, KYC, wallet, delivery modules.

## Acceptance Criteria
- **AC-UC070-01:** Given a 12 MB JPEG or any SVG file, when uploaded, then it is rejected with no stored object (BR-CAT-08).
- **AC-UC070-02:** Given a valid product image, when it is stored, then its EXIF metadata has been stripped.
- **AC-UC070-03:** Given a file renamed to `.jpg` whose bytes are an executable, when validation runs, then the magic-byte check rejects it.
- **AC-UC070-04:** Given the scan service is down, when a file is uploaded, then it is not retrievable until scanned clean (fail closed).
