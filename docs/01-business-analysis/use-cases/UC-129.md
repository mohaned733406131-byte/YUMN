# UC-129 — Triage the Refund Queue

## Header Info
- **Use Case ID:** UC-129
- **Title:** Triage the Refund Queue
- **Actor:** Admin (ACT-04)
- **Trigger:** Refunds accumulate in `PENDING`/`COMPOSED` states and some approach or breach their credit deadline
- **Priority:** P1
- **Goal:** Work the refund queue by age so no customer credit silently stalls past its deadline.
- **Preconditions:** Admin authenticated with finance-operations permission (ACT-04); refund rows exist in the queue; triage is oversight — the refund engine executes credits (UC-058).

## Main Scenario
1. Admin opens the route `/[locale]/admin/refunds` (routing.md §4) → queue sorted by age and status with `expectedCreditBy` per row.
2. Admin opens a row → per-sub-order composition (item value, shipping component, amount), current status, and wallet-credit reference when credited.
3. Admin confirms the destination rule: refunds credit the customer wallet — never external cash-out to cards or banks (BR-PAY-07).
4. Admin checks every pending credit against the 3-business-day target measured from the `REFUNDED` state (BR-RET-04).
5. Overdue items are escalated for investigation — job retry/follow-up — and annotated on the case so nothing is dropped.
6. Credied items close from the triage list once the ledger reference is confirmed present on the receipt (see UC-126 for full receipt oversight).

## Alternative Scenarios
- **A1 — Already credited:** status `CREDITED` → row closes; admin spot-checks the reference and moves on.
- **A2 — Within SLA:** pending but `expectedCreditBy` not reached → monitor only, no intervention.
- **A3 — Cancellation-origin refund:** refund rows from a cancelled order appear in the same queue and are triaged identically.
- **A4 — Bulk backlog after a promotion spike:** many rows pending → admin prioritizes oldest/overdue first and reports volume to finance.

## Exception Scenarios
- **E1 — Permission denied:** caller without finance scope → `403 FORBIDDEN`.
- **E2 — Empty queue:** no refunds pending → empty state, no error.
- **E3 — SLA breach:** credit not landed within 3 business days of `REFUNDED` → flagged overdue and escalated (BR-RET-04).
- **E4 — Duplicate-credit risk:** repeated engine triggers are idempotent → triage never hand-executes a credit, so no double credit can occur.

## Postconditions
- Queue triaged: overdue credits escalated, credited rows closed, nothing left unowned.
- No manual ledger write occurs from triage (BR-PAY-07 governs the destination).

## Business Rules Applied
- BR-PAY-07, BR-RET-04

## Related Requirements
- FR-016 (Returns & Refunds)

## Permissions / Data / External Dependencies
- **Permissions:** Admin finance-operations scope (Admin+ per routing); Moderator excluded.
- **Data involved:** Refund queue rows, statuses, deadlines, ledger references, case notes.
- **External dependencies:** Refund engine (B07); return/cancellation flows (B09, B06); ledger reads.

## Acceptance Criteria
- **AC-UC129-01:** Given a refund in the queue, when triaged, then status and `expectedCreditBy` are visible per row.
- **AC-UC129-02:** Given a case older than 3 business days from `REFUNDED` without credit, when checked, then it is flagged overdue (BR-RET-04).
- **AC-UC129-03:** Given any refund reviewed, when its destination is verified, then it resolves to the customer wallet (BR-PAY-07).
- **AC-UC129-04:** Given a non-admin caller, when the refunds route is opened, then access is denied.
