# UC-028 — Update Transit & Attempt Delivery

## Header Info
- **Use Case ID:** UC-028
- **Title:** Update Transit & Attempt Delivery
- **Actor:** Delivery Provider / Courier (ACT-03)
- **Trigger:** Courier progresses the shipment manually through transit checkpoints
- **Priority:** P1
- **Goal:** Advance `PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY` and begin the customer handover attempt — manual status updates only, no GPS (C-16).
- **Preconditions:** Delivery `PICKED_UP` (UC-027); courier is the assignee (BR-ORD-09).

## Main Scenario
1. Courier departs the pickup hub → client `POST /deliveries/{id}/transit` → system transitions `PICKED_UP → IN_TRANSIT`, appends history (BR-ORD-03), notifies customer (BR-NTF-01).
2. Courier reaches the destination zone / starts the final leg → client `POST /deliveries/{id}/out-for-delivery`.
3. System transitions `IN_TRANSIT → OUT_FOR_DELIVERY` and **issues the 6-digit delivery code to the buyer** (BR-SHP-02); the buyer gets a notification (BR-NTF-01) and sees the code in-app (UC-013).
4. Courier travels to the address using external navigation of their own (platform stores no location — BR-SHP-05, C-16) and attempts handover.
5. Courier opens the code-entry screen → continues as UC-030 (verify) or UC-029 (failed attempt).

## Alternative Scenarios
- **A1 — Multiple stops:** Courier manages several jobs; each delivery's state machine is independent (BR-ORD-07 per sub-order).
- **A2 — Return pickup route:** For `RETURN_APPROVED` jobs the same transit statuses apply, ending at vendor receipt (`RETURN_RECEIVED`, BR-RET-02).
- **A3 — Reorder checkpoints:** Skipping states is forbidden (DOC-SA-010 §2) — server rejects out-of-order transitions with `409 STATE_CONFLICT`.

## Exception Scenarios
- **E1 — Customer unreachable en route:** Courier proceeds to attempt (UC-029 records failure if no handover).
- **E2 — Duplicate status tap:** Repeat request → idempotent no-op returning current state (DOC-SA-010 §5).
- **E3 — Network dead zone:** Offline updates queue on device → synced on reconnect with server-side validation; invalid/out-of-order updates rejected (BR-ORD-03 still append-only, ordered).

## Postconditions
- Success: state = `OUT_FOR_DELIVERY`, delivery code issued to buyer, history appended.
- No location data stored at any point (BR-SHP-05); no wallet/escrow change yet.

## Business Rules Applied
- BR-ORD-03, BR-ORD-07, BR-SHP-02, BR-SHP-05, BR-NTF-01, BR-RET-02

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** Assigned courier only (BR-ORD-09); transitions validated server-side (SEC-REQ-004).
- **Data involved:** Delivery status history, issued delivery code, notifications; **no GPS/location** (C-16).
- **External dependencies:** Notification channels (B10); code generation service.

## Acceptance Criteria
- **AC-UC028-01:** Given `PICKED_UP`, when out-for-delivery is attempted directly, then the transition is rejected (`409 STATE_CONFLICT`, no state skipping).
- **AC-UC028-02:** Given `OUT_FOR_DELIVERY` reached, when the customer checks the order, then the 6-digit code is visible (BR-SHP-02).
- **AC-UC028-03:** Given the whole flow, when the API contract is audited, then no location field/endpoint exists (BR-SHP-05, C-16).
