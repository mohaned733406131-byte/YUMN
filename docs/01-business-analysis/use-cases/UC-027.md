# UC-027 — Confirm Package Pickup

## Header Info
- **Use Case ID:** UC-027
- **Title:** Confirm Package Pickup
- **Actor:** Delivery Provider / Courier (ACT-03)
- **Trigger:** Courier arrives at the vendor's store and collects the package
- **Priority:** P0
- **Goal:** Record physical possession (`ASSIGNED → PICKED_UP`) so the shipment can enter transit.
- **Preconditions:** Delivery `ASSIGNED` to this courier (UC-026); vendor marked the sub-order `READY_FOR_PICKUP` (UC-020); package present.

## Main Scenario
1. Courier arrives at the pickup point → opens the job → client `GET /deliveries/{id}/pickup` shows pickup address, package notes, expected weight band (BR-SHP-01 context).
2. Courier verifies package visually against the order lines (no GPS/location exchange, BR-SHP-05) and may take an optional photo — never required (BR-SHP-07).
3. Courier taps "Picked up" → client `POST /deliveries/{id}/pickup`.
4. System transitions `ASSIGNED → PICKED_UP`, appends history (courier, timestamp, BR-ORD-03) and notifies vendor + customer (BR-NTF-01).
5. Courier proceeds to the next state `PICKED_UP → IN_TRANSIT` on departure scan (UC-028).

## Alternative Scenarios
- **A1 — Release before pickup:** Courier releases instead → `ASSIGNED → READY_FOR_PICKUP` and offer returns to the pool (DOC-SA-010).
- **A2 — Partial package / missing line:** Package incomplete → courier does not confirm pickup; reports issue via support (UC-014) → Admin dispatch handles (UC-033).
- **A3 — Return pickup:** Job is a return pickup (`RETURN_APPROVED`) → confirming pickup advances the return flow toward `RETURN_RECEIVED` (BR-RET-02).

## Exception Scenarios
- **E1 — Vendor not ready:** Store closed / package missing → courier records a pickup issue; state stays `ASSIGNED`; vendor and admin notified.
- **E2 — Duplicate confirmation:** Double tap → idempotent: first success wins, repeat no-ops with same state (DOC-SA-010 §5).
- **E3 — Concurrent admin cancel:** Admin cancels while courier confirms → transition guards run inside the transaction; cancel wins only pre-`READY_FOR_PICKUP`, otherwise the state machine returns `409` to the loser (DOC-SA-010 §5).

## Postconditions
- Success: sub-order `PICKED_UP`; vendor/customer notified; courier bound as holder (BR-SHP-07).
- Failure: state unchanged; no notifications of possession sent.

## Business Rules Applied
- BR-ORD-03, BR-SHP-01, BR-SHP-05, BR-SHP-07, BR-RET-02, BR-NTF-01

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** Only the assigned courier may confirm own pickup (BR-ORD-09 scope); vendor/ admin observe.
- **Data involved:** Delivery record, optional photo (SEC-REQ-011 validation), status history.
- **External dependencies:** Notification channels (B10); assignment engine (INT-REQ-005).

## Acceptance Criteria
- **AC-UC027-01:** Given an `ASSIGNED` job, when pickup is confirmed, then state becomes `PICKED_UP` with courier + timestamp in history (BR-ORD-03).
- **AC-UC027-02:** Given an unassigned job, when a courier attempts pickup confirmation, then the action is denied (BR-ORD-09).
- **AC-UC027-03:** Given two rapid taps, when processed, then exactly one transition occurs (idempotent, DOC-SA-010 §5).
