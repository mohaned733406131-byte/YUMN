# UC-074 — Compensate a Failed Checkout Saga

## Header Info
- **Use Case ID:** UC-074
- **Title:** Compensate a Failed Checkout Saga
- **Actor:** System (ACT-07) — checkout saga compensator (no interactive login)
- **Trigger:** A checkout saga step fails after stock was reserved (payment failure, validation error, worker crash)
- **Priority:** P0
- **Goal:** Undo every partial effect of a failed checkout so stock, payment intent, and order state return to their pre-checkout values with no half-created order.
- **Preconditions:** Reservation created during checkout (BR-INV-01); saga with compensating actions configured (BR-PLT-04); compensation queue running.

## Main Scenario
1. The orchestrator detects a failed saga step and enqueues `b05.checkout.saga-compensate` for that checkout.
2. Compensations run in reverse order inside ACID transactions (BR-PLT-04): the stock reservation is released back to on-hand (BR-INV-01 release path).
3. Any payment intent started for the checkout is cancelled/voided — no partial charge may survive a failed order.
4. The order attempt is finalized as failed (no `PLACED` order exists) and idempotency keys are cleared so the customer may retry cleanly.
5. The customer is told the checkout failed and may restart (UC-011 step6 entry point); ledger state stays balanced throughout (BR-PLT-04).

## Alternative Scenarios
- **A1 — Failure before reservation:** Nothing to release; the saga records failure and completes compensation immediately.
- **A2 — Reservation already expiring:** Release is idempotent per reservation row — whichever of expiry/compensation lands first, stock returns exactly once (BR-INV-01).
- **A3 — Compensation itself fails once:** The compensation job retries; convergence to the pre-checkout state is guaranteed before the saga is marked done.

## Exception Scenarios
- **E1 — Database unavailable mid-compensation:** The job retries after recovery; until then stock stays reserved (temporary) rather than leaked — the TTL backstop and retry both converge to release (BR-INV-01).
- **E2 — Duplicate compensation events:** Replays are no-ops — each reservation row is released once, each payment intent cancelled once.
- **E3 — Payment provider outcome uncertain:** The saga does not guess; reconciliation determines the true provider state before any final marking — never both "charged" and "released".

## Postconditions
- Stock restored (on-hand unchanged from pre-checkout), reservations released (BR-INV-01).
- No order in `PLACED`, no orphan payment charge, ledger balanced (BR-PLT-04).
- Customer free to retry checkout with a clean idempotency scope.

## Business Rules Applied
- BR-PLT-04, BR-INV-01

## Related Requirements
- FR-011 (Checkout & Order Placement), FR-010 (Shopping Cart)
- Cross-reference (spec relation): this is the compensation path UC-011 step6 hands off to when checkout fails.

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) — writes reservations, payment intents, order attempt rows in its own flow.
- **Data involved:** Stock reservations, payment intents, order attempt/idempotency rows, ledger entries.
- **External dependencies:** BullMQ (`b05.checkout.saga-compensate`); inventory service; payment service; order service.

## Acceptance Criteria
- **AC-UC074-01:** Given a payment failure after reservation, when compensation runs, then the reservation is released and on-hand is restored (BR-INV-01).
- **AC-UC074-02:** Given a failed checkout, when the saga settles, then no order row remains in `PLACED` and no partial charge survives.
- **AC-UC074-03:** Given the compensation event is replayed, when it runs again, then no double release or double cancel occurs.
- **AC-UC074-04:** Given compensation across inventory/payment/order steps, when each step commits, then ledger state remains balanced (BR-PLT-04).
