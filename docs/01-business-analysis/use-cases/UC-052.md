# UC-052 — Execute Scheduled Vendor Payout Batches

## Header Info
- **Use Case ID:** UC-052
- **Title:** Execute Scheduled Vendor Payout Batches
- **Actor:** System (ACT-07) — payout batch job (no interactive login)
- **Trigger:** Daily business-day window scheduler enqueues `b07.payout.batch` (FR-014)
- **Priority:** P0
- **Goal:** Pay out eligible released vendor payables in batch, 3–7 business days after escrow release, honoring the 1,000 YER minimum and KYC/store gates.
- **Preconditions:** Payables were credited by escrow release (UC-039); scheduler runs in `Asia/Aden` with a Redis leader lock so only one instance registers the repeatable job.

## Main Scenario
1. The scheduler enqueues `b07.payout.batch` jobs for the current business-day window (FR-014).
2. The job selects released payables whose release is 3–7 business days old and not already paid out (BR-ESC-05).
3. It applies the eligibility gate: vendor KYC = APPROVED and store not suspended (BR-ESC-06).
4. Amounts below 1,000 YER are excluded to rollover (BR-ESC-05, see UC-053); qualifying amounts are batched per vendor (FR-014).
5. Each payout executes as one idempotent money operation — payable debited, payout record written, balanced ledger rows posted inside an ACID transaction (BR-ESC-05, FR-014).
6. The vendor sees the executed payout in Finance history; an audit entry records the batch action (FR-014).

## Alternative Scenarios
- **A1 — KYC not approved or store suspended:** the vendor's batch is skipped and held pending review; it is picked up in a later window (BR-ESC-06).
- **A2 — Eligibility pickup only:** the job reuses the eligibility computed at escrow release (UC-039 step 6) but re-verifies KYC/store state at execution time (BR-ESC-06).
- **A3 — Nothing due this window:** no eligible payables → the batch completes as an empty run; the scheduler still fires next window (BR-ESC-05).

## Exception Scenarios
- **E1 — Job fails mid-batch:** transaction rolls back for the in-flight vendor — no partial payout; the job retries with backoff, then dead-letters with an alert (FR-014).
- **E2 — Duplicate enqueue (leader failover):** idempotent payout execution keyed per batch/vendor → second run no-ops; no double payment (FR-014).
- **E3 — Payable debited concurrently (refund draw):** row-level lock serializes the debit; if the payable becomes insufficient the payout is deferred to the next window (FR-014).

## Postconditions
- Success: eligible payables debited, payout records `EXECUTED`, balanced ledger rows appended, audit entry written.
- Failure: in-flight vendor payout unchanged (still payable, batched next window); no money moved twice.

## Business Rules Applied
- BR-ESC-05, BR-ESC-06

## Related Requirements
- FR-014 (Escrow, Commission & Vendor Payouts)
- **Related:** extends UC-039 step 6 (eligibility pickup only) — release itself stays in UC-039.

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); vendors cannot trigger batch execution themselves — they request payouts, the batch executes them.
- **Data involved:** vendor payables, payout records, ledger entries, KYC/store status, audit log.
- **External dependencies:** BullMQ/Redis scheduler with leader lock (C-20), money/ledger service, notification of payout completion.

## Acceptance Criteria
- **AC-UC052-01:** Given a released payable aged 5 business days with approved KYC, when the batch runs, then the payout executes and payable is debited once (BR-ESC-05).
- **AC-UC052-02:** Given a vendor with suspended store, when the batch runs, then their payout is skipped and held (BR-ESC-06).
- **AC-UC052-03:** Given the same batch enqueued twice, when both run, then only one payout executes (BR-ESC-05).
- **AC-UC052-04:** Given a payable released 1 business day ago, when the batch runs, then it is not paid yet — the 3-day floor holds (BR-ESC-05).
