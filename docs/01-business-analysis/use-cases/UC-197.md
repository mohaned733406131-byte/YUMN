# UC-197 — Track Dispute Status

## Header Info
- **Use Case ID:** UC-197
- **Title:** Track Dispute Status
- **Actor:** Vendor (ACT-02) — any store staff role
- **Trigger:** Vendor opens the disputes screen to monitor ongoing cases
- **Priority:** P1
- **Goal:** Follow each dispute's state, evidence completeness and due date without changing anything.
- **Preconditions:** Vendor authenticated; disputes belong to the own store (BR-VND-07); at least one dispute may or may not exist.

## Main Scenario
1. Vendor opens Disputes → client `GET /disputes` returns the own-store cursor feed: `disputeId`, `state` (`OPEN`/`RESOLVED_BUYER`/`RESOLVED_VENDOR`), `openedBy`, `openedAt`, `escrowFrozen`, `dueAt` (touchpoint `API-RET-014`).
2. Vendor filters by state to prioritize open cases over resolved ones.
3. Vendor opens a dispute → client `GET /disputes/{id}` shows ground, notes, the evidence list (by/at), the full timeline and — once decided — the resolution with reason (touchpoint `API-RET-015`).
4. Vendor notes the evidence deadline and the frozen-escrow marker on the affected sub-order (BR-ORD-05).
5. After the admin decision, the view shows the arbiter outcome (BR-RET-06) and the resulting sub-order direction: refund path or completion.

## Alternative Scenarios
- **A1 — No disputes:** Empty state with a link to the returns queue (UC-194); nothing to track.
- **A2 — Resolved for the vendor:** `RESOLVED_VENDOR` → escrow unfreezes into the normal release flow; vendor expects settlement per BR-ESC rules handled elsewhere.
- **A3 — Resolved for the buyer:** `RESOLVED_BUYER` → refund path executes; the deduction appears in finances (UC-022).

## Exception Scenarios
- **E1 — Cross-store dispute id:** Direct open of a foreign dispute → `404 NOT_FOUND` (BR-VND-07).
- **E2 — Stale screen:** Dispute resolved since the last poll → refresh shows the new state; being read-only, no conflict is possible.
- **E3 — Evidence window lapsed:** `dueAt` passed with no vendor input → case proceeds on filed evidence for admin arbitration (BR-RET-06).

## Postconditions
- Read-only: no dispute state, escrow or money change originates from tracking.
- Vendor knows each case's state, deadline and whether escrow is frozen.

## Business Rules Applied
- BR-RET-06, BR-ORD-05, BR-VND-07

## Related Requirements
- FR-016 (Returns & Refunds)

## Permissions / Data / External Dependencies
- **Permissions:** Own-store disputes only (BR-VND-07); Admin/Moderator see the platform-wide list.
- **Data involved:** Dispute summaries, evidence entries, timeline, resolution, escrow freeze flag.
- **External dependencies:** Contract `API-RET-014`/`API-RET-015`; notifications (B10) on transitions.

## Acceptance Criteria
- **AC-UC197-01:** Given disputes from two stores, when the vendor lists, then only own-store disputes appear (BR-VND-07).
- **AC-UC197-02:** Given a disputed sub-order, when detail opens, then `escrowFrozen: true` and `dueAt` are shown (BR-ORD-05).
- **AC-UC197-03:** Given an admin decision, when the detail refreshes, then state is `RESOLVED_BUYER` or `RESOLVED_VENDOR` with resolution reason (BR-RET-06).
- **AC-UC197-04:** Given a foreign dispute id, when opened directly, then `404 NOT_FOUND` is returned (BR-VND-07).
