# UC-088 — Monitor Platform Health Probes

## Header Info
- **Use Case ID:** UC-088
- **Title:** Monitor Platform Health Probes
- **Actor:** Admin (ACT-04) — platform operations scope
- **Trigger:** Admin opens Ops → Health, or a probe is polled during an incident
- **Priority:** P1
- **Goal:** Confirm the platform is live and ready by reading liveness and readiness probes with their per-dependency checks.
- **Preconditions:** Admin authenticated for the health console; the probe endpoints themselves are public and unauthenticated (API-ADM-042/043).

## Main Scenario
1. Admin opens the health view → system polls `GET /healthz` (API-ADM-042) for process status, version and uptime.
2. System polls `GET /readyz` (API-ADM-043) → per-check status (`UP`/`DOWN` plus latency) for Postgres, Redis, BullMQ, Elasticsearch and external providers within budget.
3. Any `DOWN` check flips readiness to `503 SERVICE_UNAVAILABLE` and traffic is gated (BR-PLT-07); degraded search falls back to category browsing.
4. The UI renders names, status and latency only — never hostnames or connection details.
5. Read-only: no configuration change is possible from this screen (FR-020).

## Alternative Scenarios
- **A1 — External polling:** The orchestrator and monitoring poll the same two endpoints; Admin sees identical data to the automation.
- **A2 — Partial degradation:** Search provider down → readiness reports the failed check while catalog browsing still serves.

## Exception Scenarios
- **E1 — Permission denied:** The health console requires an admin session (others get `403`), even though the probe endpoints are intentionally public.
- **E2 — All checks up but slow:** Elevated latency is shown per check without failing readiness.
- **E3 — Process shutting down:** Liveness returns `SERVICE_UNAVAILABLE` during deploy/shutdown — expected transient state, retried by the orchestrator.
- **E4 — Sustained outage:** Readiness stays `503` beyond the availability target (BR-PLT-07) → incident escalation is triggered outside this use case.

## Postconditions
- Health state is displayed or returned; no platform data changed (FR-020).
- Traffic gating decisions are made by the probes (BR-PLT-07), not by this console.

## Business Rules Applied
- BR-PLT-07

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Console is `ADMIN` read; probe endpoints unauthenticated by design; no secrets may appear in responses.
- **Data involved:** Probe payloads — status, version, uptime, per-check status and latency.
- **External dependencies:** Postgres, Redis, BullMQ, Elasticsearch, payment and messaging providers.

## Acceptance Criteria
- **AC-UC088-01:** Given healthy dependencies, when `GET /readyz` is called, then `200 READY` returns with all checks `UP`.
- **AC-UC088-02:** Given a down dependency, when `GET /readyz` is called, then `503 SERVICE_UNAVAILABLE` returns naming the failing check.
- **AC-UC088-03:** Given any probe response, when inspected, then no hostname or connection string is exposed.
- **AC-UC088-04:** Given a session without admin rights, when the health console is opened, then access is denied while probes stay public.
