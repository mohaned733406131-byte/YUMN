# UC-141 — Resend an OTP (Registration, Login, or Reset)

## Header Info
- **Use Case ID:** UC-141
- **Title:** Resend an OTP (Registration, Login, or Reset)
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer is on an OTP screen (registration, login, or password reset) and the code has not arrived or has expired
- **Priority:** P1
- **Goal:** Issue a fresh 6-digit OTP for the active flow within the cooldown and resend limits without weakening verification.
- **Preconditions:** An OTP flow is in progress for a phone matching `^7[0-9]{8}$`; an earlier OTP was issued or never delivered; resend quota not exhausted (BR-AUTH-03).

## Main Scenario
1. Customer taps "Resend code" on the registration, login, or reset OTP screen.
2. Client calls `POST /auth/otp/request` (API-ATH-002) with `{ phone, context }` — context is `REGISTER`, `LOGIN`, or `PASSWORD_RESET`.
3. System enforces the 60-second resend cooldown and the cap of 3 resends per 10 minutes; both clear → a new 6-digit code is issued with 5-minute expiry and the attempt counter reset to 3 (BR-AUTH-03).
4. System dispatches the code on the OTP transport (SMS primary with automatic WhatsApp failover, UC-040) and returns `expiresAt` plus `resendAfterSeconds`.
5. Customer enters the new code; verification continues in the originating flow with at most 3 attempts (BR-AUTH-03).
6. Response is identical whether or not the account exists — anti-enumeration (FR-001).

## Alternative Scenarios
- **A1 — Cooldown not elapsed:** resend inside the 60-second window → `OTP_RESEND_COOLDOWN` with remaining seconds; nothing is sent and counters stand still (BR-AUTH-03).
- **A2 — Resend quota reached:** fourth resend inside 10 minutes → `OTP_RESEND_LIMIT`; the customer waits for the window to roll.
- **A3 — Login context:** `context=LOGIN` behaves identically — phone-only identifier, no email or alternate login path is offered.

## Exception Scenarios
- **E1 — Both delivery providers fail:** dispatch retries with backoff and WhatsApp failover; if still undelivered the flow reports delivery failure and the customer may resend within the same limits (BR-AUTH-03).
- **E2 — Network error before the server answers:** client offers retry; the cooldown is server-enforced, so a duplicate submit inside the window is rejected instead of double-sending (BR-AUTH-03).
- **E3 — Three wrong codes:** `OTP_MAX_ATTEMPTS` locks verification; a new code (resend or flow restart) is required before trying again (BR-AUTH-03).

## Postconditions
- Success: a new OTP supersedes the previous one; expiry and attempt counters restart; resend counter and cooldown advance (BR-AUTH-03).
- Failure: no new code issued; counters and the originating flow remain unchanged.

## Business Rules Applied
- BR-AUTH-03

## Permissions / Data / External Dependencies
- **Permissions:** unauthenticated endpoint keyed by phone; identical response for known and unknown numbers (anti-enumeration, SEC-REQ-001).
- **Data involved:** hashed OTP, expiry, attempt and resend counters, send log.
- **External dependencies:** SMS and WhatsApp providers behind the OTP dispatcher (UC-040, INT-REQ-003).

## Acceptance Criteria
- **AC-UC141-01:** Given a resend requested 30 seconds after the last send, when submitted, then `OTP_RESEND_COOLDOWN` returns and no message is dispatched (BR-AUTH-03).
- **AC-UC141-02:** Given three resends already used within 10 minutes, when a fourth is requested, then `OTP_RESEND_LIMIT` returns (BR-AUTH-03).
- **AC-UC141-03:** Given a successful resend, when the response returns, then `expiresAt` is now +5 minutes and `attemptsAllowed` is 3 (BR-AUTH-03).
