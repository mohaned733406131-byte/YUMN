# UC-079 — Render Notification Templates Per Locale

## Header Info
- **Use Case ID:** UC-079
- **Title:** Render Notification Templates Per Locale
- **Actor:** System (ACT-07) — template render worker (no interactive login)
- **Trigger:** Fan-out produces a recipient delivery needing message content (`b10.notification.template-render`)
- **Priority:** P1
- **Goal:** Produce every notification in the recipient's locale from bilingual templates, with no hardcoded strings leaking into messages.
- **Preconditions:** Templates exist in Arabic and English (BR-NTF-04); recipient locale preference stored (Arabic default); render queue running.

## Main Scenario
1. The fan-out enqueues `b10.notification.template-render` per recipient/notification pair.
2. The worker resolves the recipient's locale — Arabic default, English parity (BR-NTF-04, BR-PLT-05) — and selects the template variant for it.
3. Variables (order references, amounts, masked values) are substituted server-side; no user-supplied markup is interpreted.
4. The rendered message is persisted (for the in-app inbox copy) and handed to the delivery lane for the recipient's channels.
5. Render metadata (template id, version, locale) is recorded for auditability and debugging.

## Alternative Scenarios
- **A1 — Recipient locale `en`:** The English variant renders; layout/RTL concerns are irrelevant for that channel.
- **A2 — Unknown or unset locale:** Arabic is used as the default (BR-NTF-04, BR-PLT-05).
- **A3 — Template updated mid-flight:** Rendering uses the pinned template version for that job — one message never mixes versions.

## Exception Scenarios
- **E1 — Missing locale variant:** Both variants are mandatory (parity, BR-PLT-05); the job fails validation and alerts rather than shipping an untranslated message.
- **E2 — Render failure (bad/missing variables):** The job retries with backoff, then dead-letters with an alert; a malformed message is never sent.
- **E3 — Queue backlog:** Delivery lanes drain after render backlog; messages arrive late but correctly localized — freshness degrades, correctness does not.

## Postconditions
- Each delivered message exists exactly in the recipient's locale, built from a bilingual template (BR-NTF-04).
- No hardcoded/untranslated strings in user-facing output (BR-PLT-05).
- Rendered content stored with template/version/locale metadata.

## Business Rules Applied
- BR-NTF-04, BR-PLT-05

## Related Requirements
- FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) renders and stores messages; users set locale via their own settings.
- **Data involved:** Template definitions (ar/en), recipient locale, rendered message bodies, render metadata.
- **External dependencies:** BullMQ (`b10.notification.template-render`); template store; delivery lanes (SMS/WhatsApp/push/in-app).

## Acceptance Criteria
- **AC-UC079-01:** Given a recipient with locale `ar`, when a notification renders, then the Arabic variant is used (BR-NTF-04).
- **AC-UC079-02:** Given a recipient with locale `en`, when rendering runs, then the English variant with parity content is used.
- **AC-UC079-03:** Given a template missing its English variant, when validation runs, then the job fails and alerts — no untranslated message ships (BR-PLT-05).
- **AC-UC079-04:** Given a render with missing variables, when retries exhaust, then it dead-letters and nothing malformed is delivered.
