# UC-004 — Reset Password via OTP

## Header Info
- **Use Case ID:** UC-004
- **Title:** Reset Password via OTP
- **Actor:** Customer (ACT-01) — account holder
- **Trigger:** User taps "Forgot password" and enters their phone number
- **Priority:** P1
- **Goal:** Let a verified phone owner set a new password after proving possession via OTP, invalidating all prior sessions.
- **Preconditions:** Account exists for the phone (BR-AUTH-01); SMS/WhatsApp reachable (UC-040 provides failover).

## Main Scenario
1. User enters phone → system `POST /auth/password/reset/start` always responds generically (`OTP_SENT`) to avoid enumeration.
2. System issues a 6-digit OTP: 5-minute expiry, 3 verification attempts, 60 s resend cooldown, max 3 resends per 10 minutes (BR-AUTH-03); message is a mandatory security notification (BR-NTF-02).
3. User submits OTP → system `POST /auth/password/reset/verify`; on success a short-lived, single-use reset token is returned.
4. User enters a new password (≥8 chars, upper + lower + digit, different from stored hash) → system `PUT /auth/password`.
5. System stores bcrypt cost-12 hash (BR-AUTH-02), invalidates **all** existing sessions/refresh tokens (BR-AUTH-07), and sends a password-changed security notification (BR-NTF-02).
6. System writes an append-only audit entry (actor, action, IP, timestamp — BR-PLT-06) and returns the user to login (UC-003).

## Alternative Scenarios
- **A1 — Resend inside cooldown:** Requested before 60 s → cooldown error; resend counters unchanged.
- **A2 — OTP expired:** Older than 5 minutes → `OTP_EXPIRED`; user restarts the flow.
- **A3 — Password reuse attempt:** New password identical to the current one → validation error per policy; hash unchanged.

## Exception Scenarios
- **E1 — 3 wrong OTP entries:** Verification locked; user must restart the flow with a new OTP (BR-AUTH-03).
- **E2 — Provider outage:** Primary SMS fails → automatic WhatsApp failover (BR-NTF-03); both failing leaves the flow restartable, password unchanged.
- **E3 — Concurrent reset:** Two devices reset simultaneously → last write wins; all sessions are revoked either way (BR-AUTH-07), no partial state.

## Postconditions
- New password active; every pre-existing session and refresh token is revoked (BR-AUTH-07).
- No change to wallet, orders, or cart; account remains phone-identified only.
- Security audit row appended (BR-PLT-06).

## Business Rules Applied
- BR-AUTH-01, BR-AUTH-02, BR-AUTH-03, BR-AUTH-07, BR-NTF-02, BR-NTF-03, BR-NTF-04, BR-PLT-06

## Related Requirements
- FR-001 (Identity, Authentication & Session Management), FR-003 (User & Profile Management)

## Permissions / Data / External Dependencies
- **Permissions:** Self-service only; no staff can reset a password on behalf of a customer.
- **Data involved:** Password hash, OTP record, session family, audit log.
- **External dependencies:** SMS/WhatsApp providers; JWT/session store.

## Acceptance Criteria
- **AC-UC004-01:** Given a valid OTP and new password, when saved, then all prior sessions are invalidated (BR-AUTH-07).
- **AC-UC004-02:** Given an unknown phone, when reset starts, then `OTP_SENT` is still returned and no SMS is sent (no enumeration).
- **AC-UC004-03:** Given 3 wrong OTP entries, when locked, then password change is impossible until a new OTP is requested (BR-AUTH-03).
