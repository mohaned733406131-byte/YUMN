# UC-065 — Auto-Create a Support Ticket on the Third Delivery-Code Failure

## Header Info
- **Use Case ID:** UC-065
- **Title:** Auto-Create a Support Ticket on the Third Delivery-Code Failure
- **Actor:** System (ACT-07) — ticket automation (no interactive login)
- **Trigger:** Courier submits a wrong 6-digit delivery code for the third time (delivery confirmation lockout)
- **Priority:** P1
- **Goal:** Lock delivery confirmation for 24 hours and open a support ticket automatically so staff can unblock the delivery without manual detection.
- **Preconditions:** Delivery at `OUT_FOR_DELIVERY` with an issued 6-digit code; support ticket module available (FR-020).

## Main Scenario
1. Courier submits the code; failures 1 and 2 are accepted as attempts, each returning the remaining-attempt count (BR-SHP-03).
2. The third failed submission locks delivery confirmation for 24 hours (BR-SHP-03).
3. The same failure event enqueues a ticket-creation job; the support module opens a ticket with origin = delivery-code lockout, references to the order/delivery, and severity set from the lockout type.
4. The lockout and ticket are recorded append-only (actor = System) and the involved parties are notified in their locale.
5. Staff triage the new ticket with full order/timeline context (UC-014 step3 pattern) and either unblock or guide a re-attempt after the lockout.

## Alternative Scenarios
- **A1 — First or second failure:** No ticket; only the remaining-attempt warning is returned (BR-SHP-03).
- **A2 — Correct code entered before the third failure:** Delivery confirms normally; no lockout, no ticket.
- **A3 — Ticket already open for the same lockout:** The new event updates the existing ticket instead of creating a duplicate.

## Exception Scenarios
- **E1 — Ticket service unavailable:** The ticket job retries with exponential backoff and then dead-letters with a depth alert (BR-PLT-02); the 24-hour lockout still applies (BR-SHP-03) — security never depends on ticket availability.
- **E2 — Duplicate failure events (retries/replays):** Ticket creation is idempotent on lockout identity — one ticket per lockout window.
- **E3 — Notification channel failure:** The lockout and ticket are already persisted; notification retries independently and no ticket is lost.

## Postconditions
- Confirmation locked for 24 hours; delivery stays `OUT_FOR_DELIVERY`.
- Exactly one support ticket exists for the lockout, open and linked to the delivery.
- Attempt history and lockout event preserved append-only.

## Business Rules Applied
- BR-SHP-03, BR-PLT-02

## Related Requirements
- FR-015 (Shipping & Delivery), FR-020 (Platform Administration, Settings & Audit)
- Cross-reference (spec relation): automation extends the customer support entry at UC-014 step2 (ticket intake) with a system-created ticket.

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) creates tickets in its own scope; Admin/Moderator triage the queue (FR-020).
- **Data involved:** Delivery code attempt counter, lockout record, support ticket rows, order/delivery references, notifications.
- **External dependencies:** BullMQ ticket-creation job path; support module; notification fan-out.

## Acceptance Criteria
- **AC-UC065-01:** Given two prior failed code attempts, when the third attempt fails, then confirmation is locked for 24 hours (BR-SHP-03).
- **AC-UC065-02:** Given the third failure, when the event is processed, then exactly one support ticket referencing the delivery is created.
- **AC-UC065-03:** Given the ticket service is down, when failures retry and exhaust, then the job dead-letters with an alert while the lockout stays enforced (BR-PLT-02).
- **AC-UC065-04:** Given replayed failure events, when they arrive, then no duplicate ticket is created for the same lockout.
