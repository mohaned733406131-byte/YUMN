# UC-039 — Auto-Release Escrow After 7 Days

## Header Info
- **Use Case ID:** UC-039
- **Title:** Auto-Release Escrow After 7 Days
- **Actor:** System (ACT-07) — background job (no interactive login)
- **Trigger:** Scheduled escrow-release job evaluates sub-orders in `DELIVERED` (BullMQ, BR-PLT-01)
- **Priority:** P0
- **Goal:** Release escrow-held funds to vendor payable exactly 7 days after DELIVERED when all release conditions hold, moving `DELIVERED → COMPLETED`.
- **Preconditions:** Sub-order `DELIVERED` with escrow funded (BR-ESC-01); job runs at least daily with per-sub-order checks.

## Main Scenario
1. Scheduler enqueues `b07.escrow.release` jobs (queue naming `{block}.{entity}.{action}`, BR-PLT-01) for sub-orders whose 7-day hold has elapsed (C-12).
2. For each candidate the system verifies release conditions: 7 days elapsed AND no active dispute AND state ∉ {DISPUTED, RETURN_*, REFUNDED} (BR-ESC-02).
3. If eligible: compute commission = line subtotal after coupon discount × vendor tier rate 5–20% (default 10%) at release time (BR-ESC-03); credit vendor payable net of commission inside an ACID transaction with balanced ledger rows (BR-PAY-06, BR-PLT-04).
4. Transition `DELIVERED → COMPLETED` with append-only history actor=System (BR-ORD-03); master order completes when all sub-orders are COMPLETED or REFUNDED (BR-ORD-07).
5. Notify vendor ("funds released") and customer ("order completed") (BR-NTF-01); released amounts appear in UC-022 finances.
6. Payout batching picks the payable up 3–7 business days later, min 1,000 YER (BR-ESC-05), provided KYC approved and store active (BR-ESC-06).

## Alternative Scenarios
- **A1 — Dispute or return active:** Conditions fail (BR-ESC-02) → release skipped; job re-evaluates on the next run; escrow stays frozen (BR-ORD-05).
- **A2 — Return-refunded order:** State `REFUNDED` → no release; refund already drew escrow first, then payable (BR-ESC-07).
- **A3 — Late-window return after COMPLETED:** Release already happened → refund draws from escrow-held funds first and then vendor payable (BR-ESC-07); commission reversed proportionally (BR-ESC-04, BR-RET-07).

## Exception Scenarios
- **E1 — Job failure / crash:** Retry 3× with exponential backoff, then dead-letter queue; DLQ depth alert (BR-PLT-02); no funds double-released (idempotency BR-PLT-03, BR-PAY-08).
- **E2 — Concurrent dispute:** Dispute opens while release runs → transition guards evaluated inside the transaction; if dispute wins, release aborts; if release won first, dispute path handles post-completion case (DOC-SA-010).
- **E3 — Reconciliation mismatch after release:** Daily reconciliation detects imbalance → alerts finance (BR-ESC-08, BR-FIN-03); release ledger entries are append-only and never edited (DATA-REQ-007).

## Postconditions
- Eligible sub-orders: `COMPLETED`, commission booked, payable credited, ledger balanced.
- Ineligible sub-orders unchanged; escrow continues to hold until conditions are met.

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) — writes only its own domain; no interactive login; Admin observes via dashboards (FR-018).
- **Data involved:** Escrow rows, payable balances, commission records, ledger entries, status history.
- **External dependencies:** BullMQ/Redis (C-20); ledger service; notification fan-out (B10).

## Acceptance Criteria
- **AC-UC039-01:** Given a `DELIVERED` sub-order aged 6 days 23 h, when the job runs, then no release occurs (7-day rule, C-12).
- **AC-UC039-02:** Given 7 days elapsed with no dispute, when the job runs, then payable is credited net of commission and state becomes `COMPLETED` (BR-ESC-02/03).
- **AC-UC039-03:** Given an active dispute on the sub-order, when the job runs, then release is skipped and escrow stays frozen (BR-ORD-05).
