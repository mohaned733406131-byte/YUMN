# UC-020 — Mark Order Ready for Pickup

## Header Info
- **Use Case ID:** UC-020
- **Title:** Mark Order Ready for Pickup
- **Actor:** Vendor (ACT-02) — Owner/Manager staff
- **Trigger:** Vendor finished packing the confirmed sub-order
- **Priority:** P0
- **Goal:** Advance the sub-order `CONFIRMED → PROCESSING → READY_FOR_PICKUP` so the delivery engine can offer it to couriers.
- **Preconditions:** Sub-order `CONFIRMED` (UC-019); stock already deducted at `PLACED` (DOC-SA-010 guard); store active (BR-VND-04).

## Main Scenario
1. Vendor opens the sub-order → "Start fulfillment" → client `POST /store/orders/{id}/processing`; system transitions `CONFIRMED → PROCESSING` and appends history (BR-ORD-03).
2. Vendor packs items, prints/notes package details (weight/contents for shipping fee verification, BR-SHP-01) and confirms readiness → client `POST /store/orders/{id}/ready`.
3. System transitions `PROCESSING → READY_FOR_PICKUP` (last vendor-editable stage) and appends history (BR-ORD-03).
4. System enqueues the courier-assignment offer for the destination zone (BR-SHP-04, BullMQ BR-PLT-01) and notifies the customer of the readiness (BR-NTF-01).
5. The delivery pool now shows the job to eligible same-zone couriers (UC-025).

## Alternative Scenarios
- **A1 — Cancel before dispatch:** Vendor cancels while pre-`READY_FOR_PICKUP` (BR-ORD-04) → if already `READY_FOR_PICKUP`, vendor can no longer cancel; only Admin (UC-033) can release/reassign.
- **A2 — Cannot fulfil:** Vendor cancels at `CONFIRMED`/`PROCESSING` → `CANCELLED`, wallet refund flow for the sub-order (BR-PAY-07).
- **A3 — Courier releases later:** If no courier accepts, assignment returns to `READY_FOR_PICKUP` (DOC-SA-010); the offer loop repeats; admin sees backlog.

## Exception Scenarios
- **E1 — Stock discrepancy found while packing:** Physical stock < recorded → vendor opens support/admin path; order not advanced; inventory corrected per UC-018 rules (BR-CAT-07).
- **E2 — Double-click / retry:** Duplicate ready request → idempotent transition; second call no-ops with current state (BR-PLT-03).
- **E3 — Queue outage:** Assignment job fails to enqueue → alert raised (BR-PLT-02); manual admin dispatch via UC-033 possible.

## Postconditions
- Sub-order is `READY_FOR_PICKUP`; ready for courier offers; customer and delivery engine notified.
- Stock remains deducted (permanent deduction happened at payment, C-13).

## Business Rules Applied
- BR-ORD-03, BR-ORD-04, BR-SHP-01, BR-SHP-04, BR-CAT-07, BR-VND-04, BR-NTF-01, BR-PLT-01, BR-PLT-02, BR-PLT-03

## Related Requirements
- FR-012 (Order Lifecycle Management), FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** Own sub-orders only (BR-VND-07); vendor limited to own fulfillment steps (BR-ORD-07).
- **Data involved:** Sub-order state, status history, package metadata, assignment queue.
- **External dependencies:** BullMQ assignment engine (INT-REQ-005); notifications (B10).

## Acceptance Criteria
- **AC-UC020-01:** Given a `CONFIRMED` sub-order, when both steps run, then state reaches `READY_FOR_PICKUP` with two history rows (BR-ORD-03).
- **AC-UC020-02:** Given a `READY_FOR_PICKUP` sub-order, when the vendor tries to cancel, then the cancel is rejected (BR-ORD-04).
- **AC-UC020-03:** Given readiness, when enqueued, then eligible same-zone couriers see the offer (BR-SHP-04).
