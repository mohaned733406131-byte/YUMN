# UC-078 — Sweep Expired Delivery Codes

## Header Info
- **Use Case ID:** UC-078
- **Title:** Sweep Expired Delivery Codes
- **Actor:** System (ACT-07) — code TTL sweeper (no interactive login)
- **Trigger:** Scheduled sweep (`b08.shipping.code-expire`) of issued delivery codes
- **Priority:** P1
- **Goal:** Invalidate delivery codes and lockouts past their lifetime so stale secrets can never confirm a delivery and blocked couriers get re-attempted fairly.
- **Preconditions:** Codes issued at `OUT_FOR_DELIVERY` carry issue timestamps (BR-SHP-02); lockout windows recorded from the third failure (BR-SHP-03).

## Main Scenario
1. The scheduler enqueues `b08.shipping.code-expire`; the worker selects codes whose TTL has elapsed since issuance.
2. Each expired code is marked invalid — presentation and confirmation of that code now fail; the delivery stays `OUT_FOR_DELIVERY` awaiting a valid confirmation.
3. Lockout windows that have reached their 24 hours are cleared, so a courier blocked by the third failure may re-attempt (BR-SHP-03).
4. The invalidation/clear events are recorded with actor = System; the customer and courier are prompted through the normal confirmation flow.
5. Confirmation remains governed by the code rules — only a current, valid code can complete delivery (BR-SHP-02).

## Alternative Scenarios
- **A1 — Code still within TTL:** Untouched by the sweep; it remains valid until confirmed or expired.
- **A2 — Delivery already confirmed before the sweep:** Skipped — the sweep never touches completed confirmations (idempotent).
- **A3 — Lockout younger than 24 h:** Left in place; the security window is not shortened by the sweep (BR-SHP-03).

## Exception Scenarios
- **E1 — Sweep job fails:** Retried, then dead-lettered with an alert if exhausted; meanwhile confirmation already rejects expired codes at verification time — expiry is enforced where it matters even if the sweep lags.
- **E2 — Confirmation attempt races the sweep at the expiry boundary:** The expiry check runs inside the confirmation transaction — the attempt atomically either precedes expiry (accepted while valid) or follows it (rejected), never half-applied.
- **E3 — Sweep marks a code invalid twice:** Idempotent state transition — second run is a no-op with no duplicate history noise.

## Postconditions
- Expired codes invalid; stale codes can never confirm a delivery (BR-SHP-02).
- Expired 24-hour lockouts cleared; younger lockouts intact (BR-SHP-03).
- Deliveries pending confirmation remain in `OUT_FOR_DELIVERY`.

## Business Rules Applied
- BR-SHP-02, BR-SHP-03

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) invalidates codes/lockouts only; courier re-attempts through the normal delivery flow.
- **Data involved:** Delivery code rows (issuedAt, status), attempt counters, lockout windows, delivery state.
- **External dependencies:** BullMQ (`b08.shipping.code-expire`); delivery confirmation service; notifications.

## Acceptance Criteria
- **AC-UC078-01:** Given a code issued 30 minutes ago with a shorter TTL, when the sweep runs, then the code is invalid and rejected at confirmation (BR-SHP-02).
- **AC-UC078-02:** Given a 24-hour lockout that has elapsed, when the sweep runs, then the lockout is cleared (BR-SHP-03).
- **AC-UC078-03:** Given a delivery confirmed before expiry, when the sweep runs, then nothing is changed for that delivery.
- **AC-UC078-04:** Given a confirmation attempt exactly at expiry, when it commits, then the outcome is a clean accept-or-reject with no partial state.
