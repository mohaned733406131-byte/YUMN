# UC-035 — Manage Platform Settings

## Header Info
- **Use Case ID:** UC-035
- **Title:** Manage Platform Settings
- **Actor:** Admin (ACT-04) — limited settings scope (Super Admin holds full config, UC-037)
- **Trigger:** Admin opens the platform configuration console
- **Priority:** P1
- **Goal:** Operate day-to-day platform parameters (shipping zones, SLA, support, merchandising) within limits that never violate constraints.
- **Preconditions:** Admin authenticated with settings scope (DOC-OVR-007 "limited"); changes are audited (BR-PLT-06).

## Main Scenario
1. Admin opens Settings → client `GET /admin/settings` returns grouped config: shipping zones/fees (B08), vendor SLA hours, coupon/platform-promo defaults (B12), notification templates status (B10), support routing.
2. Admin edits an allowed parameter → client `PUT /admin/settings/{key}` with expected version (optimistic lock).
3. System validates the value against hard constraints — e.g., order bounds must remain 500–5,000,000 YER (C-14), cart guards 50/10/5 (C-15), escrow hold = 7 days (C-12), VAT = 15% (BR-FIN-01) — rejecting any non-compliant value (`CONSTRAINT_VIOLATION`).
4. On success, the new value takes effect (cached config invalidated; background jobs pick up new parameters), and an audit row records before/after (BR-PLT-06, SEC-REQ-010).
5. Affected parties notified via console banner where relevant (e.g., zone changes).

## Alternative Scenarios
- **A1 — Read-only keys:** Some keys are read-only for Admin (e.g., payment method set — wallet-only is fixed, C-01) → editing affordance hidden/locked.
- **A2 — Rollback:** Admin reverts to a previous value → treated as a new audited change (settings history retained).
- **A3 — Feature/ops toggles:** Toggling auto-accept orders affects the `PLACED → CONFIRMED` system actor behavior (DOC-SA-010).

## Exception Scenarios
- **E1 — Constraint violation attempt:** Attempt to disable wallet-only payments or lower VAT below policy → rejected (C-01, BR-FIN-01); logged as a security-relevant attempt.
- **E2 — Concurrent edit:** Two admins save the same key → version conflict `409`; latest reloaded.
- **E3 — Config cache failure:** Invalidation fails → change marked "pending propagation"; alert raised; system falls back to DB values (NFR-007 graceful degradation).

## Postconditions
- Settings reflect approved values with audit history; no payment-method, currency, or state-count change is possible (C-01, C-04, C-09).
- No customer money movement originates from settings changes.

## Business Rules Applied
- BR-FIN-01, BR-ORD-10, BR-PLT-05, BR-PLT-06, BR-PLT-07

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin limited scope; Super Admin full config (ACT-05, DOC-OVR-007); frontend guards are UX only (SEC-REQ-004).
- **Data involved:** Platform settings (versioned), audit log, cache entries.
- **External dependencies:** Config cache (Redis); health/readiness gating (BR-PLT-07).

## Acceptance Criteria
- **AC-UC035-01:** Given an attempt to enable a non-wallet payment method, when saved, then it is rejected (C-01, BR-PAY-01).
- **AC-UC035-02:** Given a valid zone fee change, when saved, then it applies after cache invalidation with an audit row (BR-PLT-06).
- **AC-UC035-03:** Given a settings edit, when checked, then escrow hold remains 7 days and order bounds unchanged (C-12, C-14).
