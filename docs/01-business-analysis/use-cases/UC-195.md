# UC-195 — Inspect a Received Return Within 72 Hours

## Header Info
- **Use Case ID:** UC-195
- **Title:** Inspect a Received Return Within 72 Hours
- **Actor:** Vendor (ACT-02) — Manager/Owner staff
- **Trigger:** A returned item reaches `RETURN_RECEIVED` for one of the vendor's sub-orders
- **Priority:** P0
- **Goal:** Record a pass/fail inspection of the received item within 72 hours so the refund or admin review proceeds.
- **Preconditions:** Return in `RETURN_RECEIVED` on an own-store sub-order (BR-VND-07); the approve/reject decision was already made in UC-021.

## Main Scenario
1. Vendor opens the received return → client `GET /store/returns/{id}` shows item, reason, customer evidence, pickup receipt time and the remaining inspection time (72-h countdown, BR-RET-05).
2. Vendor physically examines the item against the stated reason and the evidence images.
3. Vendor submits the inspection: client `POST /store/returns/{id}/inspection` with `outcome: PASS|FAIL`, notes and optional photo evidence (touchpoint `API-RET-009`).
4. On PASS the sub-order moves to `REFUNDED` and the refund is queued: amount = item value in integer YER, shipping refunded only when the fault is platform/vendor-side (BR-RET-03).
5. On FAIL the case leaves the vendor's hands and goes to admin review for arbitration (UC-033); the vendor files nothing further.
6. System appends the inspection to the return timeline, notifies both parties, and reports refund status as `PENDING` with expected credit date.

## Alternative Scenarios
- **A1 — Fail with photo evidence:** Vendor submits `FAIL` with images → refund path is replaced by admin review of the contested return.
- **A2 — Pass with remarks:** Vendor passes but attaches notes → notes are stored on the inspection record; refund path is unchanged.

## Exception Scenarios
- **E1 — 72-h deadline already passed:** The system auto-approved the return first → submission returns `INSPECTION_WINDOW_PASSED` and the return is already `REFUNDED` (BR-RET-05).
- **E2 — Cross-store access:** Vendor submits against a foreign store's return id → `404 NOT_FOUND` at the service layer (BR-VND-07).
- **E3 — Stale submission:** Admin concurrently resolved the case → `409 STATE_CONFLICT`; vendor reloads the timeline before any retry.

## Postconditions
- Return is `REFUNDED` (pass) or escalated to admin review (fail); wallet credit is pending within 3 business days on the pass path.
- No money moves inside the inspection call itself — it only gates the refund path.

## Business Rules Applied
- BR-RET-05, BR-RET-03, BR-VND-07

## Related Requirements
- FR-016 (Returns & Refunds)
- Cross-reference: `UC-021` step 5 covers the 72-h deadline only; this use case records the inspection itself.

## Permissions / Data / External Dependencies
- **Permissions:** Manager/Owner of the own store only (BR-VND-07); Admin may record an inspection on stalled cases.
- **Data involved:** Return record, inspection outcome/notes/images, refund status and amount (integer YER), return timeline.
- **External dependencies:** Refund execution and wallet credit (B07); notifications (B10); contract `API-RET-009`.

## Acceptance Criteria
- **AC-UC195-01:** Given a `RETURN_RECEIVED` return, when the vendor submits `PASS` within 72 h, then the state becomes `REFUNDED` with refund pending.
- **AC-UC195-02:** Given no inspection after 72 h, when the timer expires, then the return auto-approves (BR-RET-05).
- **AC-UC195-03:** Given auto-approval already ran, when a late inspection is submitted, then `INSPECTION_WINDOW_PASSED` is returned and nothing changes.
- **AC-UC195-04:** Given a foreign store's return id, when the vendor submits, then access is denied with `404` (BR-VND-07).
