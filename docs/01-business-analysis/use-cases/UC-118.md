# UC-118 — Rename, Re-Slug, or Move a Category Node

## Header Info
- **Use Case ID:** UC-118
- **Title:** Rename, Re-Slug, or Move a Category Node
- **Actor:** Admin (ACT-04)
- **Trigger:** Taxonomy naming, ordering, or hierarchy must be corrected
- **Priority:** P1
- **Goal:** Change a node's name, slug, parent, order, or active flag while depth, slug uniqueness, and canonical URLs stay valid.
- **Preconditions:** Admin authenticated with taxonomy-write permission (ACT-04); the target node exists in the tree (UC-116).

## Main Scenario
1. Admin selects the node and edits `name`, `slug`, `parentId`, `sortOrder`, and/or `isActive`.
2. Client sends `PUT /admin/categories/{id}` (API-ADM-016) with only the changed fields.
3. System revalidates the structural rules on every change (BR-CAT-03): a move re-checks the 5-level depth, and a re-slug re-checks slug uniqueness within the target level.
4. On success → `200 { …category }`; a re-slug creates slug redirects so old links keep resolving (canonical URL stability is maintained by the system slug/canonical rules — related UC-069).
5. The tree and storefront reflect the new name/position on next read.

## Alternative Scenarios
- **A1 — Rename only:** Display name changes in both locales; slug untouched, no redirect needed.
- **A2 — Move a subtree:** Node changes parent → descendants' `path`/`level` recompute and depth is revalidated (BR-CAT-03).
- **A3 — Deactivate instead of delete:** Admin sets `isActive: false` → node hidden from browsing without removal.

## Exception Scenarios
- **E1 — Permission denied:** Moderator or non-admin attempts update → 403 `FORBIDDEN`; node unchanged.
- **E2 — Validation failure:** Depth would exceed 5, or the new slug already exists at the level → `CATEGORY_DEPTH_EXCEEDED`/`SLUG_TAKEN` (BR-CAT-03); nothing written.
- **E3 — Concurrent edit:** Another admin changes the same node first → stale-write conflict (expected version mismatch) → 409; reload and reapply.

## Postconditions
- Node reflects the last accepted change; depth ≤ 5 and per-level slug uniqueness still hold (BR-CAT-03).
- Old slug URLs continue to resolve via redirects (canonical URL stability, related UC-069).

## Business Rules Applied
- BR-CAT-03

## Related Requirements
- FR-004 (Product Catalog Management)
- **Cross-reference:** UC-069 (system slug/canonical normalization) — redirect and canonical handling after a re-slug is system-owned; this use case performs the taxonomy edit.

## Permissions / Data / External Dependencies
- **Permissions:** Admin taxonomy-write scope; Moderator read-only on the tree.
- **Data involved:** Categories (name, slug, parent, order, active flag, redirects).
- **External dependencies:** Search/storefront browsing refresh after commit (indexing handled by the system catalog sync).

## Acceptance Criteria
- **AC-UC118-01:** Given a valid rename/move, when saved, then `200` returns the updated node (API-ADM-016).
- **AC-UC118-02:** Given a move that would exceed 5 levels, when saved, then `CATEGORY_DEPTH_EXCEEDED` is returned and the tree is unchanged (BR-CAT-03).
- **AC-UC118-03:** Given a re-slug, when the old URL is requested afterwards, then it still resolves via the created redirect.
- **AC-UC118-04:** Given two admins editing one node, when both save, then the second save gets 409 and no silent overwrite occurs.
