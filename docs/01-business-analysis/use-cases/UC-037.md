# UC-037 — Manage Roles & Permissions

## Header Info
- **Use Case ID:** UC-037
- **Title:** Manage Roles & Permissions
- **Actor:** Super Admin (ACT-05)
- **Trigger:** Super Admin opens Access Control to assign or modify staff roles
- **Priority:** P0
- **Goal:** Grant, modify, or revoke platform roles (Admin, Moderator, staff) safely so RBAC always matches the canonical 7-actor model.
- **Preconditions:** Super Admin authenticated; target account exists; role names restricted to canonical actors (ACT-01…ACT-07, DOC-OVR-007).

## Main Scenario
1. Super Admin opens Access Control → client `GET /admin/roles` returns staff accounts, current roles, scopes, last activity.
2. Super Admin assigns/changes a role (e.g., promote User → Admin, or Admin → Moderator) → client `POST /admin/users/{id}/role` {role, scope, reason}.
3. System validates the role against the canonical registry (no invented roles; staff-roles inside stores stay Viewer/Editor/Manager/Owner per BR-VND-06) and applies it; permission checks on every endpoint re-evaluate server-side (SEC-REQ-004).
4. System appends an audit entry with before/after (BR-PLT-06, SEC-REQ-010) and notifies the affected user (BR-NTF-02 security notice).
5. Revocation takes effect immediately; active sessions are re-scoped or revoked as appropriate.

## Alternative Scenarios
- **A1 — Vendor staff invite:** Vendor Owner invites/changes staff for own store only (BR-VND-06); Super Admin can oversee but vendor self-escalation is blocked (staff cannot self-change role — DOC-OVR-007 conceptual test 3).
- **A2 — Suspend an admin:** Super Admin suspends an Admin → permissions withdrawn instantly; audit row written.
- **A3 — Scope narrowing:** Assign Admin with a limited permission set (scoped permissions per DOC-OVR-007); defaults are least-privilege.

## Exception Scenarios
- **E1 — Self-demotion/lockout:** Attempt to remove the last Super Admin → blocked (`LAST_SUPER_ADMIN`) to avoid orphaned platform control.
- **E2 — Unknown role value:** Payload with non-canonical role → rejected (`INVALID_ROLE`); no change (no new actor names invented).
- **E3 — Concurrent modification:** Two Super Admins edit the same user → optimistic version conflict `409`; latest state reloaded.
- **E4 — Session propagation delay:** Changed permissions must apply to live sessions immediately → token claims refreshed/revoked; frontend guards are UX only (SEC-REQ-004).

## Postconditions
- Role assignments reflect the requested state with audit trail and notification.
- No permission model change beyond canonical actors; RBAC matrix in `09-security/rbac.md` remains the enforcement source.

## Business Rules Applied
- BR-VND-06, BR-VND-07, BR-NTF-02, BR-NTF-04, BR-PLT-06

## Related Requirements
- FR-002 (Roles, Permissions & Access Control), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Super Admin only (ACT-05); Admin/Moderator cannot manage roles (DOC-OVR-007); nobody self-escalates.
- **Data involved:** User roles, scopes, session state, audit log.
- **External dependencies:** Auth/session service (B01); audit store; notification channels.

## Acceptance Criteria
- **AC-UC037-01:** Given a non-Super-Admin caller, when role change is attempted, then it is denied (SEC-REQ-004).
- **AC-UC037-02:** Given a role change, when applied, then an audit row with before/after exists and the user is notified (BR-PLT-06, BR-NTF-02).
- **AC-UC037-03:** Given an attempt to demote the last Super Admin, when submitted, then `LAST_SUPER_ADMIN` blocks it.
