# UC-198 — Request a Payout

## Header Info
- **Use Case ID:** UC-198
- **Title:** Request a Payout
- **Actor:** Vendor (ACT-02) — Owner role (financial scope)
- **Trigger:** Vendor decides to withdraw the available payable balance from the Finance section
- **Priority:** P0
- **Goal:** Turn released, payable funds into a payout request that enters the batched execution cycle.
- **Preconditions:** KYC = APPROVED and store not suspended (BR-ESC-06); payout account configured; own store scope (BR-VND-07); payable balance available.

## Main Scenario
1. Vendor opens Finance → client `GET /store/finance/overview` shows `availablePayable`, `escrowHeld`, `pendingPayout`, `belowMinimumRollover` and `payoutThreshold: 1000` — all integer YER.
2. Vendor enters an amount ≤ available payable and confirms the masked destination → client `POST /store/payouts` with an idempotency key (touchpoint `API-WAL-011`).
3. System validates the request: KYC approved + store active (BR-ESC-06), amount ≥ 1,000 YER and ≤ payable (BR-ESC-05).
4. On acceptance → `201 { payoutId, status: REQUESTED, amount, destinationMasked, estimatedExecution }`; the request joins the batch executed 3–7 business days after release (BR-ESC-05).
5. Vendor reviews the request in the payout history list (`GET /store/payouts`) with status `REQUESTED`/`SCHEDULED`.
6. On batch execution, ledger entries post append-only with the payout reference, visible in the payout detail view.

## Alternative Scenarios
- **A1 — Repeat submission:** Same idempotency key replayed → the original payout is returned; no duplicate request is created.
- **A2 — Below-threshold balance:** Payable rolls over (shown as `belowMinimumRollover`); vendor waits for more releases (BR-ESC-05).
- **A3 — Destination update needed:** Vendor configures/changes the payout account first, then re-issues the request.

## Exception Scenarios
- **E1 — Payable insufficient / escrow not yet released:** `INSUFFICIENT_FUNDS` — funds still inside the 7-day escrow hold, or frozen by an active dispute (BR-ORD-05); nothing is requested.
- **E2 — Gate failed:** KYC not approved or store suspended → `KYC_NOT_APPROVED` / `STORE_SUSPENDED`; payout withheld pending review (BR-ESC-06).
- **E3 — Stale retry:** Missing or conflicting idempotency key → `IDEMPOTENCY_KEY_REQUIRED` / `IDEMPOTENCY_CONFLICT`; vendor reloads before retrying.

## Postconditions
- Payout is `REQUESTED` (awaiting batch) or rejected with a machine-readable reason; no ledger movement until execution.
- Money values remain whole integer YER end to end.

## Business Rules Applied
- BR-ESC-05, BR-ESC-06, BR-ORD-05, BR-VND-07

## Related Requirements
- FR-014 (Escrow, Commission & Vendor Payouts)
- Cross-reference: `UC-022` step 4 lists payout batches (read only); this use case creates a new request.

## Permissions / Data / External Dependencies
- **Permissions:** Owner role, own store only (BR-VND-07); no payout access for staff viewer roles.
- **Data involved:** Payable balance, payout request rows, masked destination, ledger references (integer YER).
- **External dependencies:** Payout batch job (B07); payout account store (B03); contract `API-WAL-011`.

## Acceptance Criteria
- **AC-UC198-01:** Given payable 25,000 YER and KYC approved, when requesting 25,000 YER, then `201 REQUESTED` with estimated execution is returned (BR-ESC-05).
- **AC-UC198-02:** Given an amount of 700 YER, when submitted, then `PAYOUT_BELOW_MINIMUM` is returned (BR-ESC-05).
- **AC-UC198-03:** Given a suspended store or unapproved KYC, when submitted, then the request is rejected (BR-ESC-06).
- **AC-UC198-04:** Given an active dispute freezing escrow, when payable is checked, then frozen funds are excluded (BR-ORD-05).
