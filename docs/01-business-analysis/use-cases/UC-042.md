# UC-042 — View Wallet Statement

## Header Info
- **Use Case ID:** UC-042
- **Title:** View Wallet Statement
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens Wallet → "Statement" (transaction history)
- **Priority:** P1
- **Goal:** Show the customer a complete, owner-scoped statement of every credit and debit with type, reference, timestamp and running balance, in exact figures (FR-013).
- **Preconditions:** Customer authenticated with a valid session (C-06); a wallet row exists (FR-013); ledger rows may be empty (→ A1).

## Main Scenario
1. Client `GET /wallet/transactions` with optional filters `?type&from&to&limit&cursor` (API-WAL-002).
2. System returns **only the owner's** append-only ledger entries (scoped to the owner, DATA-REQ-008): each item carries `type`, `direction` (`CREDIT`/`DEBIT`), `amount` (integer YER, BR-PAY-10), `balanceAfter`, `reference { kind, id }`, `status`, `createdAt`.
3. Customer scrolls the cursor-paginated feed and may filter by type (`TOPUP`, `ORDER_PAYMENT`, `REFUND`, `ESCROW_HOLD`, `PAYOUT` — API-WAL-002) and by date range.
4. Totals in the page envelope are exact — money views are never estimated (API-WAL-002).
5. Customer opens an entry's reference → navigates to the related order, escrow or refund detail (conceptual touchpoints; authoritative contracts in `07-api/`).

## Alternative Scenarios
- **A1 — Empty wallet:** zero entries and total value `0` are valid results; no fabricated placeholder rows.
- **A2 — Filtered view:** type/date filters return the matching subset; totals remain exact for the filtered set.
- **A3 — Escrow-linked entries:** `ESCROW_HOLD`/release postings trace to the escrow status view of the same order (API-WAL-009, C-12 seven-day hold).

## Exception Scenarios
- **E1 — Invalid or expired session:** `AUTH_INVALID`; client redirects to login (C-06); no data rendered.
- **E2 — Ledger read failure:** error response; no partial or estimated rendering is ever shown (API-WAL-002).
- **E3 — Invalid filter values:** `VALIDATION_ERROR`; no data returned.

## Postconditions
- Success: customer views their own statement; read-only — no state, balance or ledger change; no audit row (reads are not money actions, BR-PLT-06 applies to writes).
- Failure: no data rendered; session either invalid (→ login) or intact.

## Business Rules Applied
- BR-PAY-06, BR-PAY-10

## Related Requirements
- FR-013 (Wallet & Payment Processing — "transaction history" / customer-visible statement)

## Permissions / Data / External Dependencies
- **Permissions:** customer reads **own** wallet only (`rbac.md` row 16: `✔ (own)` for CUSTOMER; every other role `✖`); no other actor invokes this use case.
- **Data involved:** append-only ledger entries, wallet balance — read-only.
- **External dependencies:** none (B07 wallet/ledger service only).

## Acceptance Criteria
- **AC-UC042-01:** Given a wallet with 5 ledger entries, when the statement opens, then all 5 are listed with type, amount, `balanceAfter`, reference and timestamp (FR-013, BR-PAY-10).
- **AC-UC042-02:** Given other users' entries exist, when the customer requests the statement, then only the owner's entries are returned (DATA-REQ-008).
- **AC-UC042-03:** Given the `type=ORDER_PAYMENT` filter, when applied, then only matching entries are returned and page totals stay exact (API-WAL-002).
