# UC-015 — Register as Vendor & Submit KYC

## Header Info
- **Use Case ID:** UC-015
- **Title:** Register as Vendor & Submit KYC
- **Actor:** Vendor (ACT-02)
- **Trigger:** A registered user applies to become a vendor / opens seller onboarding
- **Priority:** P0
- **Goal:** Create a vendor profile with exactly one store and submit KYC documents for admin approval (≤48 h).
- **Preconditions:** User authenticated (UC-003); phone verified (BR-AUTH-01); no existing store (one store per vendor, BR-VND-02).

## Main Scenario
1. User opens onboarding → client `GET /vendor/onboarding/status` returns current step (NONE → PENDING_KYC → APPROVED/REJECTED).
2. User enters store legal name, trade name, category, contact info, and address → client `POST /vendor/application`; server enforces one store per vendor (BR-VND-02).
3. User uploads KYC documents (identity + commercial registration as required) → `POST /vendor/kyc/documents`; validation: type/size, malware scan, EXIF strip (SEC-REQ-011, BR-CAT-08 patterns).
4. System sets KYC status `SUBMITTED` and timestamps it; decision SLA clock starts (48 h, BR-VND-03); notification sent to applicant (BR-NTF-01).
5. Admin reviews and approves/rejects (UC-031); on approval KYC = APPROVED → vendor may publish products (BR-VND-01); on rejection, reason is returned and resubmission is allowed (BR-VND-03).
6. System writes audit entries for submission and decision (BR-PLT-06).

## Alternative Scenarios
- **A1 — Resubmit after rejection:** Rejection reason shown; user corrects documents and resubmits → SLA clock restarts (BR-VND-03).
- **A2 — Vendor already has a store:** Second application → `ONE_STORE_PER_VENDOR` rejection (BR-VND-02).
- **A3 — Pending state access:** While `SUBMITTED`, onboarding UI is read-only; user may add clarifying notes to the ticket.

## Exception Scenarios
- **E1 — SLA breach:** No decision within 48 h → system flags the case for admin escalation (BR-VND-03); applicant notified of the delay.
- **E2 — Upload failure:** Network drop mid-upload → resumable retry; document not registered until server confirms (idempotency BR-PLT-03).
- **E3 — Malware/invalid file:** Scanner or type check fails → upload rejected with localized error (SEC-REQ-011); nothing stored.

## Postconditions
- Vendor account exists with KYC `SUBMITTED`/`APPROVED`/`REJECTED`; one store maximum.
- No products are publishable until KYC = APPROVED (BR-VND-01); no payouts before approval (BR-ESC-06).
- Audit trail contains the submission/decision events (BR-PLT-06).

## Business Rules Applied
- BR-VND-01, BR-VND-02, BR-VND-03, BR-ESC-06, BR-PLT-03, BR-PLT-06, BR-NTF-01

## Related Requirements
- FR-007 (Vendor Onboarding & KYC)

## Permissions / Data / External Dependencies
- **Permissions:** Vendor submits only; approval belongs to Admin/ Super Admin (DOC-OVR-007); documents readable by admin staff only.
- **Data involved:** Vendor profile, store row, KYC documents (PII, DATA-REQ-002), audit log.
- **External dependencies:** File storage + malware scanner (SEC-REQ-011); notification channels.

## Acceptance Criteria
- **AC-UC015-01:** Given a user with an existing store, when applying again, then `ONE_STORE_PER_VENDOR` is returned (BR-VND-02).
- **AC-UC015-02:** Given documents submitted, when recorded, then KYC status is `SUBMITTED` with timestamp and applicant notified.
- **AC-UC015-03:** Given KYC = APPROVED, when the vendor tries to publish, then publishing is allowed (BR-VND-01); while `SUBMITTED` it is blocked.
