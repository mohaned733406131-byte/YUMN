# UC-019 — View & Accept Incoming Order

## Header Info
- **Use Case ID:** UC-019
- **Title:** View & Accept Incoming Order
- **Actor:** Vendor (ACT-02) — Owner/Manager staff
- **Trigger:** A sub-order reaches `PLACED` and appears in the seller dashboard
- **Priority:** P0
- **Goal:** Review a paid sub-order and move it `PLACED → CONFIRMED` within the 24-hour vendor SLA.
- **Preconditions:** Sub-order paid at master level (wallet, C-01); vendor KYC = APPROVED and store active (transition guard, DOC-SA-010); scope = own `store_id` (BR-VND-07).

## Main Scenario
1. System notifies the vendor of the new sub-order (in-app/SMS/WhatsApp, BR-NTF-01) and shows it in `PLACED`.
2. Vendor opens the sub-order → client `GET /store/orders/{id}` returns items, ship-to (masked per policy), totals (BR-FIN-02), payment confirmed, and timeline (BR-ORD-09).
3. Vendor taps "Accept" → client `POST /store/orders/{id}/confirm`.
4. System validates guard (KYC approved, store active), applies optimistic locking, and transitions `PLACED → CONFIRMED`; history row appended with actor/reason (BR-ORD-03).
5. Customer receives a confirmation notification (BR-NTF-01); the 24 h SLA clock resets at CONFIRMED for the next stage (BR-ORD-10).
6. Vendor may then proceed to fulfillment (UC-020: `CONFIRMED → PROCESSING`).

## Alternative Scenarios
- **A1 — Reject / cancel instead:** Vendor cancels while allowed (until `READY_FOR_PICKUP`, BR-ORD-04) → `CANCELLED` with reason; wallet refund flow triggers for that sub-order (BR-PAY-07).
- **A2 — Partial capacity:** Vendor cannot fulfil some lines → vendor cancels affected sub-order only; other vendors' sub-orders proceed (BR-ORD-07).
- **A3 — Auto-accept configuration:** Platform auto-accept enabled → System performs the transition; vendor still sees the history entry (DOC-SA-010).

## Exception Scenarios
- **E1 — SLA breach (24 h):** Sub-order stays unconfirmed → auto-escalates to admin review with notification; never silently auto-cancelled (BR-ORD-10).
- **E2 — Store suspended mid-flight (BR-VND-04):** Accept blocked; existing orders frozen pending admin review.
- **E3 — Concurrent state change:** Admin/customer changed state meanwhile → `409 STATE_CONFLICT`; dashboard refreshes (DOC-SA-010 §5).

## Postconditions
- Success: sub-order `CONFIRMED`, history row appended, customer notified.
- Failure: state unchanged; no refund executed unless an explicit cancel occurred (→ `CANCELLED`, refund flow).

## Business Rules Applied
- BR-ORD-03, BR-ORD-04, BR-ORD-07, BR-ORD-09, BR-ORD-10, BR-VND-01, BR-VND-04, BR-VND-07, BR-FIN-02, BR-NTF-01, BR-PAY-07

## Related Requirements
- FR-012 (Order Lifecycle Management), FR-007 (Vendor Onboarding & KYC)

## Permissions / Data / External Dependencies
- **Permissions:** Own sub-orders only (BR-VND-07); limited override rights per DOC-OVR-007; Admin has full override (UC-033).
- **Data involved:** Sub-order, status history, notification queue, refund flow on cancel.
- **External dependencies:** Notification fan-out (B10); BullMQ SLA timer (BR-PLT-01).

## Acceptance Criteria
- **AC-UC019-01:** Given a `PLACED` sub-order, when accepted, then state becomes `CONFIRMED` with an append-only history row (BR-ORD-03).
- **AC-UC019-02:** Given 24 hours without confirmation, when SLA expires, then the sub-order escalates to admin review (BR-ORD-10).
- **AC-UC019-03:** Given vendor X requesting vendor Y's sub-order, when requested, then access is denied (BR-VND-07).
