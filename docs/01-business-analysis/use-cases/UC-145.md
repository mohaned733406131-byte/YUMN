# UC-145 — Change Password While Signed In

## Header Info
- **Use Case ID:** UC-145
- **Title:** Change Password While Signed In
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens Account → Security → "Change password" and submits the form
- **Priority:** P1
- **Goal:** Replace the stored password with a policy-compliant one and invalidate every session created with the old credentials.
- **Preconditions:** Customer authenticated; current password known; step-up OTP for the sensitive change completed (UC-142, SEC-REQ-001).

## Main Scenario
1. Customer enters current password and a new password of ≥8 characters with upper case, lower case and a digit (BR-AUTH-02).
2. Client sends `PUT /auth/password { newPassword, currentPassword, otpCode }` (API-ATH-010) with the step-up code.
3. Server verifies the current password (generic `INVALID_CREDENTIALS` on mismatch, no enumeration), validates the policy, rejects a new password identical to the stored hash, and stores the new hash with bcrypt cost 12 (BR-AUTH-02).
4. Success → `204`: every existing session is invalidated, including the current one (BR-AUTH-07); the client is signed out and must log in with the new password.
5. A mandatory password-changed security notification is sent; the password itself is never logged (BR-AUTH-02).

## Alternative Scenarios
- **A1 — Reset flow instead:** a signed-out customer uses UC-004 (resetToken path of the same endpoint) — out of scope here.
- **A2 — Step-up not yet done:** request rejected with `OTP_NOT_VERIFIED`; customer completes UC-142 first.

## Exception Scenarios
- **E1 — Policy violation:** `PASSWORD_POLICY_VIOLATION` with field errors; no hash change and no session revocation (BR-AUTH-02).
- **E2 — Wrong current password:** `INVALID_CREDENTIALS`; account state untouched.
- **E3 — Network error after submit:** outcome unknown → retry; if the change landed, all sessions are already revoked (BR-AUTH-07) and the customer simply logs in with the new password.

## Postconditions
- Success: stored hash replaced (bcrypt cost 12); all pre-existing sessions revoked (BR-AUTH-07); security notification emitted.
- Failure: password and sessions unchanged; customer still signed in.

## Business Rules Applied
- BR-AUTH-02, BR-AUTH-07

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)

## Permissions / Data / External Dependencies
- **Permissions:** authenticated customer changing only their own password; requires current password plus step-up OTP (SEC-REQ-001).
- **Data involved:** password hash, session registry rows, security notification record.
- **External dependencies:** notification channels for the mandatory security notice.

## Acceptance Criteria
- **AC-UC145-01:** Given valid current password, step-up OTP and a policy-passing new password, when submitted, then `204` returns and every prior session is revoked (BR-AUTH-07).
- **AC-UC145-02:** Given a new password without a digit, when submitted, then `PASSWORD_POLICY_VIOLATION` returns and sessions stay active (BR-AUTH-02).
- **AC-UC145-03:** Given a new password equal to the stored hash, when submitted, then it is rejected per the API-ATH-010 contract.
