# UC-010 — Manage Cart

## Header Info
- **Use Case ID:** UC-010
- **Title:** Manage Cart
- **Actor:** Customer (ACT-01) — guest or authenticated
- **Trigger:** User opens the cart screen or edits quantities/items
- **Priority:** P1
- **Goal:** Review and adjust cart contents under all guards, with server-reconciled totals and blocked checkout for problem items.
- **Preconditions:** Cart exists (client-side for guests, server-side after login, BR-CRT-03).

## Main Scenario
1. User opens cart → client `GET /cart` returns lines grouped by vendor/sub-cart, quantities, line totals, and cart subtotal in integer YER (BR-PAY-10).
2. System recalculates totals server-side and refreshes the reservation countdown (BR-CRT-02, BR-CRT-04).
3. User changes a quantity → client `PATCH /cart/items/{id}`; system re-validates ≤10 units per product and ≤50 products (BR-CRT-01, C-15).
4. User removes an item → client `DELETE /cart/items/{id}`; the related reservation releases (BR-CRT-02).
5. System flags any line that became inactive, out-of-stock, or out-of-policy with a "remove to continue" marker (BR-CRT-05).
6. User taps "Checkout" → blocked while flagged lines exist; otherwise continues as UC-011.

## Alternative Scenarios
- **A1 — Price changed since add:** Server shows the new price with explicit re-confirmation prompt (BR-CRT-04); totals always recomputed server-side.
- **A2 — Coupon preview:** Applying a coupon at cart (optional) follows BR-PRM-* rules (non-stackable, ≤90%, BR-PRM-01/02); invalid coupon → validation error, no order row (BR-PRM-06).
- **A3 — Empty cart:** All items removed → empty state with continue-shopping affordance; reservation count is zero.

## Exception Scenarios
- **E1 — Stock dropped to zero:** Line flagged per BR-CRT-05; checkout blocked until removed (BR-CRT-05).
- **E2 — Concurrent modification:** Another session edits the same cart → server state wins; client shows refreshed cart (no 409 dead-ends).
- **E3 — Network failure mid-update:** Timeout → client re-fetches cart to reconcile; updates are idempotent (BR-PLT-03).

## Postconditions
- Cart reflects server truth: valid quantities, current prices, running reservations.
- No order or payment exists until checkout confirms (UC-011).

## Business Rules Applied
- BR-CRT-01, BR-CRT-02, BR-CRT-03, BR-CRT-04, BR-CRT-05, BR-PRM-01, BR-PRM-02, BR-PRM-06, BR-PAY-10, BR-PLT-03

## Related Requirements
- FR-010 (Shopping Cart)

## Permissions / Data / External Dependencies
- **Permissions:** Own cart only; guests are client-side until login gate (DOC-OVR-007).
- **Data involved:** Cart lines, reservations, price snapshots, coupon preview.
- **External dependencies:** Inventory service (stock checks), coupon engine (B12).

## Acceptance Criteria
- **AC-UC010-01:** Given a line with quantity 10, when the user increments, then the request is rejected (BR-CRT-01).
- **AC-UC010-02:** Given an out-of-stock line, when checkout is attempted, then it is blocked until the line is removed (BR-CRT-05).
- **AC-UC010-03:** Given a price change after add-to-cart, when the cart loads, then the updated price is shown with re-confirmation (BR-CRT-04).
