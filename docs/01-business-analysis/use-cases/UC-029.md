# UC-029 — Record Failed Delivery Attempt

## Header Info
- **Use Case ID:** UC-029
- **Title:** Record Failed Delivery Attempt
- **Actor:** Delivery Provider / Courier (ACT-03)
- **Trigger:** Courier cannot complete handover at the customer's address (no answer, wrong address, code not shared)
- **Priority:** P1
- **Goal:** Record the failed attempt, revert to `IN_TRANSIT`, count attempts, and escalate after 3 failures.
- **Preconditions:** Delivery in `OUT_FOR_DELIVERY`; attempt count < 3 (BR-SHP-06).

## Main Scenario
1. Courier taps "Could not deliver" → client `POST /deliveries/{id}/failed-attempt` with reason code and optional note/photo (photo never required, BR-SHP-07).
2. System transitions `OUT_FOR_DELIVERY → IN_TRANSIT`, appends history with attempt number (BR-ORD-03), and records the attempt count (BR-SHP-03 counters are separate for code-entry failures; BR-SHP-06 counts failed attempts).
3. Customer receives a failed-attempt notification with the reason and next steps (BR-NTF-01, localized BR-NTF-04); support ticket path available (UC-014).
4. Courier later re-enters the final leg: `IN_TRANSIT → OUT_FOR_DELIVERY` again; **a fresh 6-digit code is issued** for the new attempt (BR-SHP-02 semantics: code issued at OUT_FOR_DELIVERY).
5. On the 3rd failed attempt, the system escalates to admin review with the full timeline instead of looping (BR-SHP-06) — escalation is a ticket, not a 18th state (C-09).

## Alternative Scenarios
- **A1 — Customer reschedules:** Customer contacts support → admin coordinates next attempt (UC-033) within policy.
- **A2 — Wrong address confirmed:** Address issue → customer updates address where possible; admin decides on re-route or cancellation with refund (BR-ORD-04 path).
- **A3 — Attempt while code locked:** Code confirmation locked (3 wrong entries → 24 h, BR-SHP-03) → handover blocked; failure recorded or deferred per admin guidance.

## Exception Scenarios
- **E1 — Duplicate failure report:** Double tap → idempotent single history row (BR-PLT-03); counter increments once.
- **E2 — Notification outage:** Customer not informed by SMS/WhatsApp → in-app timeline updated; retries per BR-PLT-02.
- **E3 — Courier misreports (abuse):** Repeated failures on valid addresses → admin sees pattern in timeline (BR-ORD-09) and reassigns (UC-033).

## Postconditions
- State `IN_TRANSIT` (or escalated to admin review at attempt 3); attempt count incremented; customer notified.
- Escrow/wallet unchanged; delivery code for the previous attempt invalidated for the new attempt.

## Business Rules Applied
- BR-ORD-03, BR-SHP-02, BR-SHP-03, BR-SHP-06, BR-SHP-07, BR-NTF-01, BR-NTF-04, BR-PLT-02, BR-PLT-03

## Related Requirements
- FR-015 (Shipping & Delivery), FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** Assigned courier records own attempts (BR-ORD-09); Admin reads all for review.
- **Data involved:** Attempt counter, reason codes, status history, notifications, optional photo.
- **External dependencies:** Notification channels (B10); admin console/escalation ticket (B13).

## Acceptance Criteria
- **AC-UC029-01:** Given the 1st failed attempt, when recorded, then state returns to `IN_TRANSIT` and the customer is notified (BR-ORD-03).
- **AC-UC029-02:** Given 3 failed attempts, when the 3rd is recorded, then escalation to admin review occurs (BR-SHP-06).
- **AC-UC029-03:** Given a new OUT_FOR_DELIVERY after failure, when the customer checks, then a fresh 6-digit code is available (BR-SHP-02).
