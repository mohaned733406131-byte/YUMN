# UC-014 — Contact Support

## Header Info
- **Use Case ID:** UC-014
- **Title:** Contact Support
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer taps "Help / Contact support" from an order, delivery lockout, or the help center
- **Priority:** P2
- **Goal:** Open a human support ticket with order context and receive tracked responses — no AI chatbot exists (binding scope note in DOC-OVR-008, tied to FR-017).
- **Preconditions:** Customer authenticated (or ticket tied to verified phone, BR-AUTH-01); support console available to Admin/Moderator (B13).

## Main Scenario
1. Customer opens support from an order → client `POST /support/tickets` with category (order, payment, delivery, other), optional attachment, and free-text message in ar/en (BR-PLT-05).
2. System creates a ticket linked to the order/sub-order and current state snapshot; auto-attach context: delivery-code lockout, return window, or refund status when applicable.
3. Ticket enters the queue; Moderators/Admins see it in the console (UC-038 / UC-033); customer sees the ticket and status (`OPEN → IN_PROGRESS → RESOLVED`).
4. Staff replies via the console → customer receives an in-app + SMS/WhatsApp notification per preferences (BR-NTF-01, BR-NTF-04).
5. Customer replies within the thread; resolution closes the ticket; both sides see the full append-only thread.

## Alternative Scenarios
- **A1 — Lockout-triggered ticket:** Delivery code locked after 3 failures → ticket auto-created by the system with full timeline (BR-SHP-03); customer just adds description.
- **A2 — Escalation to admin:** Moderator cannot resolve → escalate to Admin (support escalation belongs to ACT-06 per DOC-OVR-007); state change written to thread.
- **A3 — Guest support:** Unauthenticated → verify by OTP to phone (BR-AUTH-03) before linking tickets to an account.

## Exception Scenarios
- **E1 — Ticket volume spike:** Queue grows → priority tagging + alerting; no silent drops; staff SLA dashboards reflect backlog (FR-018).
- **E2 — Attachment upload failure:** Malware scan/type check rejects file (SEC-REQ-011) → message still saved without attachment.
- **E3 — Notification outage:** Reply notification fails → in-app thread remains source of truth; retries per BR-PLT-02.

## Postconditions
- A ticket exists with context, thread, and status; audit trail of staff actions (BR-PLT-06).
- No order state changes directly from the ticket — state changes happen via UC-033 or the regular machine (BR-ORD-01).

## Business Rules Applied
- BR-AUTH-01, BR-AUTH-03, BR-SHP-03, BR-NTF-01, BR-NTF-04, BR-PLT-02, BR-PLT-05, BR-PLT-06

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit — support tickets)

## Permissions / Data / External Dependencies
- **Permissions:** Customer creates/reads own tickets; Moderators/Admins read and reply platform-wide; no cross-customer ticket access.
- **Data involved:** Support tickets, messages, attachments (malware-scanned), linked order snapshot.
- **External dependencies:** Notification channels (B10); file storage with scanning (SEC-REQ-011).

## Acceptance Criteria
- **AC-UC014-01:** Given an authenticated customer, when a ticket is submitted, then it appears in the staff console with the linked order context.
- **AC-UC014-02:** Given a delivery-code lockout, when the 3rd failure occurs, then a ticket is auto-created (BR-SHP-03).
- **AC-UC014-03:** Given another customer's ticket ID, when requested, then access is denied (ownership, SEC-REQ-004).
