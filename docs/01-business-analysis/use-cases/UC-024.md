# UC-024 — Respond to Customer Review

## Header Info
- **Use Case ID:** UC-024
- **Title:** Respond to Customer Review
- **Actor:** Vendor (ACT-02) — Owner/Manager staff
- **Trigger:** Vendor opens Reviews in the seller dashboard and selects a review of their product
- **Priority:** P2
- **Goal:** Publish one public response per review to address feedback and protect store reputation.
- **Preconditions:** Review exists on the vendor's product (own `store_id`, BR-VND-07); review is visible (not hidden, BR-REV-04).

## Main Scenario
1. Vendor opens Reviews → client `GET /store/reviews` returns visible reviews for own products with rating 1–5, comment, images (≤5, ≤5 MB, BR-REV-03) and order link (BR-REV-01).
2. Vendor selects a review → "Reply" → enters a localized response (ar/en, BR-PLT-05) → client `POST /store/reviews/{id}/responses`.
3. System enforces **one response per review** (BR-REV-04): subsequent submits are rejected with `RESPONSE_ALREADY_EXISTS`.
4. Response is published beneath the review; store rating recomputation is incremental via a background job (BR-REV-05, BullMQ BR-PLT-01).
5. The reviewing customer receives an in-app notification of the response (BR-NTF-01, marketing opt-out respected BR-NTF-05).

## Alternative Scenarios
- **A1 — Flag instead of reply:** Vendor flags the review as abusive → Moderator/Admin may hide it with audit entry (BR-REV-04; handled by UC-032/UC-038).
- **A2 — No reviews yet:** Empty state with tips to request reviews from delivered orders (customers review only post-delivery, BR-REV-01).
- **A3 — Edit window for customer:** Customer edits their review once within 7 days (BR-REV-02) → vendor's single response stays; version indicator refreshes.

## Exception Scenarios
- **E1 — Hidden review:** Review hidden by moderation → response form disabled; existing response hidden with it (BR-REV-04).
- **E2 — Invalid content:** Response contains prohibited content → validation/moderation pipeline rejects or queues it (FR-006 moderation, SEC-REQ-008 encoding).
- **E3 — Job failure:** Rating recomputation job fails → retried 3× then DLQ alert (BR-PLT-02); ratings self-heal on next run.

## Postconditions
- Exactly ≤1 public response exists for the review; audit trail of moderation flags preserved.
- Store rating aggregate updated incrementally (BR-REV-05).

## Business Rules Applied
- BR-REV-01, BR-REV-02, BR-REV-03, BR-REV-04, BR-REV-05, BR-VND-07, BR-NTF-01, BR-NTF-05, BR-PLT-01, BR-PLT-02, BR-PLT-05

## Related Requirements
- FR-006 (Reviews & Ratings)

## Permissions / Data / External Dependencies
- **Permissions:** Own products' reviews only (BR-VND-07); Moderator/Admin can hide (BR-REV-04); vendor cannot delete reviews.
- **Data involved:** Review, response, rating aggregates, notification preferences.
- **External dependencies:** Rating recompute job (B11/B02); notification fan-out (B10).

## Acceptance Criteria
- **AC-UC024-01:** Given a review, when the vendor replies once and tries again, then the second reply is rejected (BR-REV-04).
- **AC-UC024-02:** Given a review on another vendor's product, when queried, then it is not listed (BR-VND-07).
- **AC-UC024-03:** Given a response posted, when the job runs, then the store rating reflects the review (BR-REV-05).
