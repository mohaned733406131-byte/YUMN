# UC-021 — Respond to Return Request

## Header Info
- **Use Case ID:** UC-021
- **Title:** Respond to Return Request
- **Actor:** Vendor (ACT-02) — Owner/Manager staff
- **Trigger:** A customer's return request moves the sub-order to `RETURN_REQUESTED`
- **Priority:** P1
- **Goal:** Approve or reject the return within policy, enabling pickup (`RETURN_APPROVED`) or closure (`RETURN_REJECTED`).
- **Preconditions:** Sub-order in `RETURN_REQUESTED` (customer opened return inside window per BR-RET-01, C-11); vendor owns the sub-order (BR-VND-07).

## Main Scenario
1. Vendor opens the return → client `GET /store/returns/{id}` shows item, reason, evidence images, policy (`isReturnable`, `returnPeriodDays`) and window calculation (delivery date + returnPeriodDays, BR-RET-01).
2. Vendor reviews the request against store policy → chooses Approve or Reject.
3a. **Approve:** client `POST /store/returns/{id}/approve` → system transitions `RETURN_REQUESTED → RETURN_APPROVED`, schedules return pickup via the delivery engine (BR-SHP-04), notifies the customer (BR-NTF-01).
3b. **Reject:** client `POST /store/returns/{id}/reject` with mandatory reason → `RETURN_REQUESTED → RETURN_REJECTED`; customer notified; sub-order later settles `RETURN_REJECTED → COMPLETED` (DOC-SA-010).
4. System writes audit entries for the decision (BR-PLT-06); escrow remains frozen for this sub-order until resolution (BR-ORD-05 overlay while in return flow).
5. After `RETURN_RECEIVED`, vendor inspects within 72 h (BR-RET-05) — or the system auto-approves the refund (UC-033 handles admin edge cases).

## Alternative Scenarios
- **A1 — Vendor inaction:** No decision within the inspection SLA → admin review path (UC-033); customer may escalate (UC-014).
- **A2 — Inspection auto-approval:** Item received, 72 h pass without conclusion → return auto-approves → refund flow (BR-RET-05).
- **A3 — Policy dispute:** Vendor rejects but customer disputes → admin is final arbiter; decision written to audit log (BR-RET-06).

## Exception Scenarios
- **E1 — Window expired at review:** If return window elapsed since request → request shown as stale; only admin may override (BR-RET-01).
- **E2 — Concurrent decision:** Vendor and admin act simultaneously → optimistic lock; first valid transition wins, other gets `409 STATE_CONFLICT` (DOC-SA-010 §5).
- **E3 — Insufficient escrow at refund:** Refund draws escrow first, then vendor payable (BR-ESC-07); vendor sees liability entry in finances (UC-022).

## Postconditions
- Sub-order is `RETURN_APPROVED` (pickup scheduled) or `RETURN_REJECTED` (settles to COMPLETED).
- Escrow for the sub-order stays frozen until refund or completion (BR-ORD-05, BR-ESC-02).

## Business Rules Applied
- BR-RET-01, BR-RET-02, BR-RET-05, BR-RET-06, BR-RET-07, BR-ORD-05, BR-ESC-02, BR-ESC-07, BR-VND-07, BR-NTF-01, BR-PLT-06

## Related Requirements
- FR-016 (Returns & Refunds), FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** Own sub-orders/returns only; Admin overrides (UC-033); customer may only open/track (DOC-OVR-007).
- **Data involved:** Return record, evidence images, policy snapshot, status history, audit log.
- **External dependencies:** Delivery engine for return pickup (B08); notifications (B10).

## Acceptance Criteria
- **AC-UC021-01:** Given a valid `RETURN_REQUESTED`, when approved, then state becomes `RETURN_APPROVED` and pickup is scheduled (BR-RET-02).
- **AC-UC021-02:** Given rejection, when submitted without a reason, then validation fails (reason required, DOC-SA-010).
- **AC-UC021-03:** Given received item and 72 h elapsed, when inspection is open, then the return auto-approves (BR-RET-05).
