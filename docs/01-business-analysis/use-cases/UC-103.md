# UC-103 — Resolve a Support Ticket with a Resolution Note

## Header Info
- **Use Case ID:** UC-103
- **Title:** Resolve a Support Ticket with a Resolution Note
- **Actor:** Admin (ACT-04) — support operations scope
- **Trigger:** Admin finishes handling a ticket
- **Priority:** P1
- **Goal:** Close the loop with a mandatory resolution note so the outcome is traceable.
- **Preconditions:** Admin or Moderator authenticated (API-ADM-041); ticket is `OPEN` or `IN_PROGRESS`; a resolution note has been written.

## Main Scenario
1. Admin opens the ticket (UC-100) → Resolve → enters the mandatory resolution text.
2. Client `POST /admin/tickets/{id}/resolve` with `{ resolution }` (API-ADM-041).
3. System transitions → `RESOLVED`, stores `resolvedAt` and returns an `auditId`.
4. The resolution writes an append-only audit entry with actor, entity and before/after state (BR-PLT-06).
5. The customer is notified and may reopen the ticket once from their ticket view before it is closed for good.

## Alternative Scenarios
- **A1 — Moderator resolve:** Moderator resolves within scope (API-ADM-041 roles) with the same mandatory note.
- **A2 — Customer reopens:** The single reopen returns the ticket to active work; the next close is final.

## Exception Scenarios
- **E1 — Permission denied:** Non-staff session → `403 FORBIDDEN`.
- **E2 — Missing resolution:** Empty note → `VALIDATION_ERROR`; the ticket stays open, so no anonymous closes exist.
- **E3 — Already resolved or closed:** `TICKET_STATE_CONFLICT`; no duplicate audit entries.
- **E4 — Repeat reopen attempts:** Only one reopen is allowed — the ticket reaches `CLOSED` and stays there (guaranteed terminal state).

## Postconditions
- The ticket is `RESOLVED`, then `CLOSED` after the reopen window, with a resolution note on record.
- One audit entry exists for the resolution (BR-PLT-06); no order or money state changed.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** `ADMIN`/`MODERATOR` resolve; the customer may reopen exactly once.
- **Data involved:** Ticket status, resolution note, audit entry.
- **External dependencies:** Customer notification channels; audit writer (BR-PLT-06).

## Acceptance Criteria
- **AC-UC103-01:** Given an in-progress ticket, when resolve is posted with a note, then status becomes `RESOLVED` with `resolvedAt` and an `auditId`.
- **AC-UC103-02:** Given an empty resolution, when posted, then `VALIDATION_ERROR` returns and status is unchanged.
- **AC-UC103-03:** Given an already-resolved ticket, when resolved again, then `TICKET_STATE_CONFLICT` is returned.
- **AC-UC103-04:** Given the customer reopens once, when reopened, then the ticket returns to active work and the second close is terminal.
