# UC-126 — Oversee Refund Receipts and Statuses

## Header Info
- **Use Case ID:** UC-126
- **Title:** Oversee Refund Receipts and Statuses
- **Actor:** Admin (ACT-04)
- **Trigger:** An admin needs to verify where a refund stands — pending, composed, or credited — for an order under review
- **Priority:** P1
- **Goal:** Confirm every refund's status, composition, and wallet-credit reference without mutating any ledger data.
- **Preconditions:** Admin authenticated with finance-read permission (ACT-04); the target order exists and may hold refund rows; the ledger is append-only and never writable from this screen.

## Main Scenario
1. Admin requests the refund receipt for an order → client `GET /orders/{id}/refund` (API-WAL-014, admin-scoped read).
2. System returns per-sub-order refund rows: status (`PENDING` → `COMPOSED` → `CREDITED`), amount, item value, shipping component, `expectedCreditBy`, and the wallet-credit reference once credited.
3. Admin verifies every credited amount is backed by balanced double-entry ledger rows — debit plus credit, append-only (BR-PAY-06).
4. Admin confirms the money path is wallet-only: refunds credit the customer wallet and never cash out externally to cards or banks (BR-PAY-07).
5. Admin traces the wallet-credit reference into the ledger view, ensuring the reference exists and matches the refund amount for that sub-order.
6. Anything stalled is handed to refund triage (UC-129); execution of the credit itself stays with the refund engine (UC-058) — this UC performs no writes.

## Alternative Scenarios
- **A1 — Refund pending:** status `PENDING` → admin monitors engine progress only; no intervention required.
- **A2 — Refund credited:** status `CREDITED` with `creditedAt` and ledger reference → oversight for that sub-order closes.
- **A3 — Cancellation-origin refund:** the order was cancelled rather than returned → the same receipt endpoint reports those refund rows.
- **A4 — Mixed composition:** some sub-orders refunded, others not → admin reviews row by row; totals come from the ledger, never estimated by the UI.

## Exception Scenarios
- **E1 — Permission denied:** caller without finance-read scope → `403 FORBIDDEN`; the ledger has no write path here.
- **E2 — No refund yet:** the order never entered a refund flow → empty rows / no-record state rather than an error.
- **E3 — Credit overdue:** `expectedCreditBy` passed while status is not `CREDITED` → flagged and escalated to refund triage (UC-129).
- **E4 — Duplicate execution risk:** repeated refund triggers are idempotent → no double credit ever appears in the receipt.

## Postconditions
- Refund status per sub-order is observable and each credit maps to balanced ledger rows (BR-PAY-06).
- Refunds credit wallets only — no external cash-out path exists (BR-PAY-07).

## Business Rules Applied
- BR-PAY-07, BR-PAY-06

## Related Requirements

## Permissions / Data / External Dependencies
- **Permissions:** Admin finance-read scope; strictly read-only — no ledger or balance writes (DOC-OVR-007).
- **Data involved:** Refund rows, ledger entries, wallet credits, sub-order states, order receipts.
- **External dependencies:** Refund engine (B07); return and cancellation flows (B09, B06); ledger/statement reads.

## Acceptance Criteria
- **AC-UC126-01:** Given a credited refund, when the admin reads the receipt, then status is `CREDITED` with wallet-credit reference and timestamp.
- **AC-UC126-02:** Given any credited amount, when inspected, then balanced double-entry ledger rows exist behind it (BR-PAY-06).
- **AC-UC126-03:** Given a refund under review, when checked, then it resolves to a wallet credit with no external cash-out option (BR-PAY-07).
- **AC-UC126-04:** Given a non-admin caller, when the receipt is requested, then access is denied.
