# UC-003 — Login with Phone & Password

## Header Info
- **Use Case ID:** UC-003
- **Title:** Login with Phone & Password
- **Actor:** Customer (ACT-01) — registered user
- **Trigger:** User submits phone and password on the login screen
- **Priority:** P0
- **Goal:** Establish an authenticated session for a registered account using the phone identifier only (no email/social login).
- **Preconditions:** Account exists and is not locked; phone matches `^7[0-9]{8}$` (BR-AUTH-01); device not exceeding session limits.

## Main Scenario
1. User enters phone + password → client `POST /auth/login`.
2. System validates format, looks up the account, and verifies the bcrypt hash (cost 12, BR-AUTH-02); failures return a generic `INVALID_CREDENTIALS` (no user enumeration).
3. On success, system resets the failed-attempt counter, issues JWT pair (access 15 min / refresh 7 days single-use rotation, BR-AUTH-05, C-08) and records the device session.
4. If active sessions exceed 5, system evicts the oldest session (BR-AUTH-06).
5. System merges any client-side guest cart into the server cart, server values winning on quantity conflict (BR-CRT-03).
6. Client redirects to the authenticated home; a mandatory security notification about the new login is sent (BR-NTF-02) in the user's locale (BR-NTF-04).

## Alternative Scenarios
- **A1 — Password reset path:** User taps "forgot password" → flow continues as UC-004.
- **A2 — OTP-only entry point:** Login screen offers "verify with OTP" → server issues OTP per BR-AUTH-03 and completes login after verification (still phone-only, C-06).
- **A3 — Frozen/banned account:** Account status prevents login → generic denial; frozen-wallet users may still log in but cannot pay or top up (BR-PAY-09).

## Exception Scenarios
- **E1 — Brute-force lockout:** 5 consecutive failed logins → account locked 15 minutes, lock event logged, user notified (BR-AUTH-04).
- **E2 — Refresh token reuse:** An already-used refresh token is presented → entire session family revoked, user alerted (BR-AUTH-05).
- **E3 — Network failure:** Response lost after server success → client retry with the same request is safe; token issuance is per-session, no duplicate accounts.

## Postconditions
- An active session exists for the user (≤5 devices), or login failed with no session.
- No order, payment, or ledger change occurs during login.
- Guest cart (if any) is now server-owned (BR-CRT-03).

## Business Rules Applied
- BR-AUTH-01, BR-AUTH-02, BR-AUTH-04, BR-AUTH-05, BR-AUTH-06, BR-CRT-03, BR-NTF-02, BR-NTF-04, BR-PAY-09

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)

## Permissions / Data / External Dependencies
- **Permissions:** Grants Customer (ACT-01) scope only; server-side RBAC applies to every endpoint (SEC-REQ-004).
- **Data involved:** Credentials, session/device records, refresh-token family, cart.
- **External dependencies:** SMS/WhatsApp for security notices (BR-NTF-03); JWT issuer.

## Acceptance Criteria
- **AC-UC003-01:** Given correct phone and password, when submitted, then a 15-minute access token and rotating refresh token are returned.
- **AC-UC003-02:** Given 5 consecutive wrong passwords, when the fifth fails, then the account is locked for 15 minutes (BR-AUTH-04).
- **AC-UC003-03:** Given a reused refresh token, when presented, then all sessions of the family are revoked and the user is alerted (BR-AUTH-05).
