# UC-107 — Publish a CMS Page

## Header Info
- **Use Case ID:** UC-107
- **Title:** Publish a CMS Page
- **Actor:** Admin (ACT-04)
- **Trigger:** An admin approves a reviewed draft for public display
- **Priority:** P1
- **Goal:** Move a page DRAFT → PUBLISHED atomically so the public route resolves with the audited content.
- **Preconditions:** Admin authenticated with content-write permission (ACT-04); target page exists in DRAFT state with parity-complete content.

## Main Scenario
1. Admin opens the page detail (API-CNT-007), previews the content and confirms both localized titles are complete before publishing.
2. Admin clicks Publish → client `POST /admin/pages/{id}/publish` (API-CNT-009).
3. System transitions `DRAFT → PUBLISHED` atomically; the public read `GET /pages/{slug}` switches from 404 to `200 { slug, title, bodyBlocks, publishedAt }` in the same commit → response `200 { status: "PUBLISHED", publishedAt, auditId }`.
4. System appends an audit entry with actor, action, entity and before/after (BR-PLT-06) and returns its `auditId`.
5. Refresh of cached/derived public reads is performed by the adjacent system cache-purge path, not by the admin action itself.

## Alternative Scenarios
- **A1 — Republish after edits:** Page already PUBLISHED and edited (UC-106) → a new publish pushes the revised content live with a fresh audit entry.
- **A2 — Preview first:** Admin previews the draft, returns to editing (UC-106), publishes later — no state change until publish.
- **A3 — Publish conflict resolved:** Concurrent publish by a colleague → first wins; this admin sees `STATE_CONFLICT` and reloads.

## Exception Scenarios
- **E1 — Already published:** Page is PUBLISHED → 409 `STATE_CONFLICT`; no duplicate audit row.
- **E2 — Permission denied:** Moderator or non-admin attempts publish → 403 `FORBIDDEN`; status unchanged.
- **E3 — Concurrent publish:** Two admins publish the same draft → only one transition commits; the other gets `STATE_CONFLICT` (BR-PLT-06 audit exists once).

## Postconditions
- Page is PUBLISHED and publicly resolvable; one audit row records the transition (BR-PLT-06).
- Draft content not published remains invisible.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-019 (Content & Promotions (CMS + Coupons))
- **Cross-reference:** UC-067 (system search-index/cache synchronization) — the adjacent cache purge after publish is system-owned; this use case covers only the state transition.

## Permissions / Data / External Dependencies
- **Permissions:** Admin content-write scope; Moderator cannot publish.
- **Data involved:** CMS pages (status, publishedAt), audit log, public content cache.
- **External dependencies:** Public page route and cached content reads (`GET /pages/{slug}`) switching atomically on publish.

## Acceptance Criteria
- **AC-UC107-01:** Given a DRAFT page, when publish is called, then the response is `200 { status: "PUBLISHED", publishedAt, auditId }` (API-CNT-009).
- **AC-UC107-02:** Given a published page, when the public route is read, then it returns `200` with the published content and never a partial state.
- **AC-UC107-03:** Given a successful publish, when the audit log is read, then exactly one publish entry exists (BR-PLT-06).
- **AC-UC107-04:** Given an already PUBLISHED page, when publish is repeated, then 409 `STATE_CONFLICT` is returned.
