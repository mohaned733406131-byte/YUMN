# UC-082 — Deliver Signed Outbound Webhooks with Retry

## Header Info
- **Use Case ID:** UC-082
- **Title:** Deliver Signed Outbound Webhooks with Retry
- **Actor:** System (ACT-07) — outbound webhook dispatcher (no interactive login)
- **Trigger:** A subscribed domain event occurs (order state change, payout, refund, etc.)
- **Priority:** P1
- **Goal:** Deliver every subscribed event to external endpoints with a verifiable signature and a bounded retry policy, losing nothing on failure.
- **Preconditions:** Subscriber endpoints registered with secrets; events carry stable ids; delivery queue running (INT-REQ-006).

## Main Scenario
1. The event is enqueued as `b13.platform.webhook.send`, following the `{block}.{entity}.{action}` naming (BR-PLT-01).
2. The worker builds the payload and signs the raw body HMAC-SHA256 with the endpoint's secret, including a timestamp header (INT-REQ-006).
3. It POSTs to the subscriber endpoint with a timeout; a `2xx` response marks the delivery `DELIVERED` with the correlation id logged.
4. A non-`2xx` or timeout triggers retry with exponential backoff (e.g. 1 m / 5 m / 25 m), 3 attempts total, then the job dead-letters with a depth alert (BR-PLT-02).
5. Attempt history is retained; DLQ entries stay re-drivable so an admin can replay a payload after the receiver is fixed (FR-020 console).

## Alternative Scenarios
- **A1 — Slow receiver:** Timeout counts as a failed attempt and enters the backoff schedule; slowness never blocks other deliveries.
- **A2 — Receiver recovers before retries exhaust:** The next attempt succeeds and delivery completes normally.
- **A3 — Duplicate delivery to an idempotent receiver:** Event ids let the receiver dedupe — at-least-once delivery stays safe (INT-REQ-006 idempotent handlers).

## Exception Scenarios
- **E1 — All attempts fail:** The job lands in the DLQ with an alert (BR-PLT-02); the event is preserved for replay, never dropped.
- **E2 — Queue outage:** Events persist upstream and drain on recovery — no silent loss (platform retry/DLQ policy).
- **E3 — Signature rejected by receiver (clock skew / wrong secret):** The attempt fails like any non-2xx; repeated failures dead-letter and surface for secret/endpoint configuration review.

## Postconditions
- Every emitted event reaches exactly one terminal state: DELIVERED or DLQ'd-with-alert — none lost.
- Delivered payloads are HMAC-signed and timestamped (INT-REQ-006); attempts and outcomes are logged.
- Replay from DLQ produces the same idempotent outcome.

## Business Rules Applied
- BR-PLT-01, BR-PLT-02

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) signs and sends; admins manage subscriptions/replays via the platform console (FR-020).
- **Data involved:** Event payloads, endpoint secrets, delivery attempts, DLQ entries, correlation ids.
- **External dependencies:** BullMQ (`b13.platform.webhook.send`); subscriber HTTPS endpoints; HMAC secrets custody.

## Acceptance Criteria
- **AC-UC082-01:** Given a subscribed event, when it is delivered, then the receiver can verify the HMAC signature over the raw body (INT-REQ-006).
- **AC-UC082-02:** Given a receiver returning 500, when attempts proceed, then it retries 3× with backoff and then dead-letters with an alert (BR-PLT-02).
- **AC-UC082-03:** Given a DLQ entry replayed after a fix, when re-driven, then the receiver gets the same payload with idempotent effect.
- **AC-UC082-04:** Given a queue outage, when events accumulate, then none is lost once the queue drains.
