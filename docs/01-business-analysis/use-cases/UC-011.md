# UC-011 — Checkout with Wallet Payment

## Header Info
- **Use Case ID:** UC-011
- **Title:** Checkout with Wallet Payment
- **Actor:** Customer (ACT-01) — authenticated
- **Trigger:** User proceeds from cart to checkout and confirms the order
- **Priority:** P0
- **Goal:** Convert a valid cart into a paid master order (one sub-order per vendor) funded exclusively from the customer's wallet.
- **Preconditions:** Authenticated; cart valid (UC-010); address selected (UC-005); wallet balance ≥ order total (BR-CRT-06, C-01).

## Main Scenario
1. User enters checkout → system `POST /checkout/session` snapshots the cart, applies shipping fee = f(zone, weight, method) (BR-SHP-01) and computes VAT 15% × (subtotal − coupon discount), shipping untaxed (BR-FIN-01).
2. User selects delivery address (≤10, UC-005) → system validates shipping zone eligibility (C-17).
3. User selects shipping method → fee updates; `free_shipping` coupon zeroes it (BR-SHP-01).
4. System shows the payment step with **wallet only** — any other method is rejected with `PAYMENT_METHOD_NOT_ALLOWED` (BR-PAY-01, C-01); balance and order total displayed in integer YER (BR-PAY-10).
5. User reviews the full breakdown (items − discount + VAT + shipping per sub-order, BR-FIN-02) and confirms → client `POST /orders` with idempotency key (BR-ORD-06, BR-PLT-03).
6. System runs the saga (BR-PLT-04): validates order bounds 500–5,000,000 YER (C-14, BR-CAT-04), atomically debits the wallet with row locking so balance never goes negative (BR-PAY-05), posts balanced double-entry ledger rows (BR-PAY-06), permanently deducts stock (C-13, BR-CAT-07), creates master order + one sub-order per vendor (BR-ORD-02, C-10).
7. Order enters `PLACED`; escrow funded at master level (BR-ESC-01 context); confirmation + payment notifications sent (BR-NTF-01, BR-NTF-04); user sees order confirmation (UC-012).

## Alternative Scenarios
- **A1 — Insufficient balance:** Balance < total → checkout blocked with top-up CTA (bounds 1,000–5,000,000 YER, BR-PAY-02); no order row created.
- **A2 — Coupon applied:** One coupon only (non-stackable, BR-PRM-02), ≤90% discount, ≤90-day validity (BR-PRM-01); invalid coupon → error, no order row (BR-PRM-06).
- **A3 — Price/stock drift at confirm:** Server recalculation surfaces changed price for re-confirmation (BR-CRT-04); reservation refresh keeps stock held.

## Exception Scenarios
- **E1 — Duplicate submission / retry:** Same idempotency key → original order returned, wallet debited once (BR-ORD-06, BR-PAY-08).
- **E2 — Stock conflict at payment:** Atomic deduction fails on last unit → saga compensates (releases reservation, no debit persisted) and user gets a stock error (BR-PLT-04).
- **E3 — Wallet frozen:** Frozen wallet (BR-PAY-09) → payment rejected; refunds remain permitted.
- **E4 — Provider/DB outage mid-saga:** Compensating actions unwind the partial steps; ledger stays balanced (BR-ESC-08, DATA-REQ-007); user may retry safely.

## Postconditions
- Success: master order `PLACED`, one sub-order per vendor, wallet debited once, ledger balanced, stock deducted, escrow funded.
- Failure: no order row, no persistent debit (compensated), reservation released.

## Permissions / Data / External Dependencies
- **Permissions:** Customer may pay only from own wallet (DATA-REQ-008); no COD/cards exist anywhere (C-01, C-02).
- **Data involved:** Cart, wallet, ledger, stock, master/sub-orders, coupon, address, shipping zone.
- **External dependencies:** Wallet/ledger service (B07); BullMQ jobs (BR-PLT-01); notification fan-out (B10).

## Acceptance Criteria
- **AC-UC011-01:** Given a cart totalling 300 YER, when confirmed, then the order is rejected (min 500 YER, C-14).
- **AC-UC011-02:** Given `payment_method=cod`, when order creation is attempted, then `PAYMENT_METHOD_NOT_ALLOWED` is returned (BR-PAY-01).
- **AC-UC011-03:** Given balance 10,000 YER and total 12,000 YER, when confirmed, then no order is created and balance is unchanged (BR-CRT-06).
- **AC-UC011-04:** Given a multi-vendor cart, when payment succeeds, then one master order and one sub-order per vendor exist (BR-ORD-02).
