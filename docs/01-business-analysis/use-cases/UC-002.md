# UC-002 — Register with Phone + OTP

## Header Info
- **Use Case ID:** UC-002
- **Title:** Register with Phone + OTP
- **Actor:** Customer (ACT-01) — guest
- **Trigger:** Guest taps "Create account" and submits a phone number
- **Priority:** P0
- **Goal:** Create a verified Customer account whose primary identifier is a unique, OTP-verified phone number.
- **Preconditions:** Phone is not already registered; SMS/WhatsApp provider reachable (fallback per UC-040); guest has set a password meeting complexity rules.

## Main Scenario
1. Guest enters phone matching `^7[0-9]{8}$` and a password (≥8 chars, upper + lower + digit, BR-AUTH-02) → client `POST /auth/register/start`.
2. System validates format, checks uniqueness (BR-AUTH-01), rejects duplicates with `PHONE_ALREADY_REGISTERED`, else creates a pending account and requests an OTP (conceptually `POST /auth/otp` → delivered by UC-040).
3. System sends a 6-digit OTP valid 5 minutes with 60 s resend cooldown and max 3 resends per 10 minutes (BR-AUTH-03); security notifications cannot be disabled (BR-NTF-02).
4. User enters the OTP → system `POST /auth/otp/verify` allows max 3 verification attempts (BR-AUTH-03); on success the phone is marked VERIFIED and the account becomes ACTIVE.
5. System issues JWT pair: access 15 min, refresh 7 days single-use rotation (BR-AUTH-05, C-08); guest cart merges server-side (BR-CRT-03).
6. System writes an append-only audit entry for the identity event (BR-PLT-06) and logs the user in.

## Alternative Scenarios
- **A1 — Resend within cooldown:** User requests OTP inside 60 s → system rejects with cooldown message; counter unchanged.
- **A2 — OTP expired:** 5 minutes elapsed → verification fails with `OTP_EXPIRED`; user requests a fresh OTP (resend limits still apply).
- **A3 — Email (optional):** User optionally adds an email → stored unverified; it is never used for login or OTP delivery (BR-AUTH-08).

## Exception Scenarios
- **E1 — OTP lockout:** 3 wrong attempts → verification locked until a new OTP is issued; lock event logged (BR-AUTH-03).
- **E2 — SMS provider outage:** Primary provider times out → automatic failover to WhatsApp within the OTP flow (BR-NTF-03, INT-REQ-003); if both fail, user may retry after cooldown.
- **E3 — Duplicate concurrent registration:** Two submissions race → unique constraint on phone wins; loser receives `PHONE_ALREADY_REGISTERED` (DATA-REQ-001).

## Postconditions
- Account exists with VERIFIED phone; no login without OTP success.
- No wallet balance is created beyond 0 YER; no order or ledger entry exists.
- Failed attempts leave security logs only (no partial profiles).

## Business Rules Applied
- BR-AUTH-01, BR-AUTH-02, BR-AUTH-03, BR-AUTH-05, BR-AUTH-08, BR-CRT-03, BR-NTF-02, BR-NTF-03, BR-PLT-06

## Related Requirements
- FR-001 (Identity, Authentication & Session Management), FR-003 (User & Profile Management)

## Permissions / Data / External Dependencies
- **Permissions:** Public; becomes Customer (ACT-01) on success; no privileged access granted.
- **Data involved:** User (phone, password hash bcrypt cost 12, optional email), OTP records, audit log.
- **External dependencies:** SMS/WhatsApp providers (BR-NTF-03); JWT signing keys (SEC-REQ-003).

## Acceptance Criteria
- **AC-UC002-01:** Given phone `771234567` and correct OTP, when verified, then the account activates and an access token of 15 min is issued.
- **AC-UC002-02:** Given an already-registered phone, when registration starts, then `PHONE_ALREADY_REGISTERED` is returned and no OTP is sent.
- **AC-UC002-03:** Given 3 wrong OTP entries, when the third fails, then verification is locked and the attempt is logged (BR-AUTH-03).
