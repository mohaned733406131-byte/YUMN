# UC-026 — Accept Delivery Assignment

## Header Info
- **Use Case ID:** UC-026
- **Title:** Accept Delivery Assignment
- **Actor:** Delivery Provider / Courier (ACT-03)
- **Trigger:** Courier taps "Accept" on an available delivery offer (UC-025)
- **Priority:** P0
- **Goal:** Claim a `READY_FOR_PICKUP` job, moving it to `ASSIGNED` under first-accept-wins optimistic locking.
- **Preconditions:** Offer still open; courier eligible for the zone (BR-SHP-04); sub-order not cancelled/disputed.

## Main Scenario
1. Courier taps "Accept" → client `POST /deliveries/{id}/accept` with the offer version.
2. System validates eligibility (zone, courier enabled) and executes the `READY_FOR_PICKUP → ASSIGNED` transition with optimistic locking on the assignment row — the first accept wins; the loser receives `ASSIGNED_ELSEWHERE` (BR-SHP-04).
3. System appends history (actor = courier, timestamp, BR-ORD-03) and marks the offer as taken for all other couriers.
4. Vendor sees the assignment; customer receives "courier assigned" notification (BR-NTF-01); pickup instructions become available (UC-027).
5. Courier identity is bound to the delivery for later proof (BR-SHP-07).

## Alternative Scenarios
- **A1 — Release assignment:** Courier releases before pickup → `ASSIGNED → READY_FOR_PICKUP` (DOC-SA-010) and the offer re-enters the pool; history recorded.
- **A2 — Multiple offers:** Courier accepts job B while job A active → allowed if capacity rules permit; each job tracked independently (BR-ORD-07 per sub-order).
- **A3 — Admin reassign:** Admin overrides assignment (UC-033) → courier notified; state history shows admin actor.

## Exception Scenarios
- **E1 — Double accept race:** Two couriers accept concurrently → optimistic lock: exactly one succeeds; other gets `409/ASSIGNED_ELSEWHERE` (DOC-SA-010 §5).
- **E2 — Job cancelled between view and accept:** Sub-order `CANCELLED` → accept rejected; courier sees cancellation notice; no state change.
- **E3 — Network timeout after commit:** Retry with same idempotency key returns the accepted result once (BR-PLT-03); no double assignment.

## Postconditions
- Success: sub-order `ASSIGNED` to this courier; offer removed from pool; history appended.
- Failure: state remains `READY_FOR_PICKUP`; no courier bound.

## Business Rules Applied
- BR-SHP-04, BR-SHP-07, BR-ORD-03, BR-ORD-07, BR-NTF-01, BR-PLT-03

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** Courier may accept only open, zone-eligible offers; cannot assign to others (Admin can, UC-033).
- **Data involved:** Assignment row (version), status history, courier identity, notifications.
- **External dependencies:** Assignment engine (INT-REQ-005); push notifications (B10).

## Acceptance Criteria
- **AC-UC026-01:** Given two concurrent accepts, when both submit, then exactly one wins and state is `ASSIGNED` once (BR-SHP-04).
- **AC-UC026-02:** Given a released assignment, when released pre-pickup, then state returns to `READY_FOR_PICKUP` (DOC-SA-010).
- **AC-UC026-03:** Given an accepted job, when history is read, then courier identity + timestamp are recorded (BR-ORD-03, BR-SHP-07).
