# UC-030 — Confirm Delivery with 6-Digit Code

## Header Info
- **Use Case ID:** UC-030
- **Title:** Confirm Delivery with 6-Digit Code
- **Actor:** Delivery Provider / Courier (ACT-03)
- **Trigger:** Courier is at the customer's door and requests the code (customer shares per UC-013)
- **Priority:** P0
- **Goal:** Verify the customer-held 6-digit code to transition `OUT_FOR_DELIVERY → DELIVERED` — the only permitted path to DELIVERED (BR-ORD-08, C-16).
- **Preconditions:** Delivery `OUT_FOR_DELIVERY` with code issued (BR-SHP-02); code confirmation not locked (BR-SHP-03).

## Main Scenario
1. Courier opens the job → client renders the code-entry form (6 digits) → courier submits `POST /deliveries/{id}/code` {code}.
2. System compares against the issued code (hashed at rest), enforcing attempts < 3 (BR-SHP-03).
3. **Success:** system transitions `OUT_FOR_DELIVERY → DELIVERED`, records delivery proof = code + timestamp + courier identity (+optional photo, BR-SHP-07), appends history (BR-ORD-03).
4. Escrow hold starts for the sub-order: funds held 7 days from DELIVERED (BR-ESC-01, C-12); return window opens (BR-RET-01).
5. Customer and vendor receive delivery notifications (BR-NTF-01); customer is prompted to review (BR-REV-01) and can request returns if eligible.
6. The courier's job leaves "active deliveries" (UC-025).

## Alternative Scenarios
- **A1 — Wrong code, attempts remain (1–2):** System rejects and shows remaining attempts (BR-SHP-03); state stays `OUT_FOR_DELIVERY`.
- **A2 — Customer refuses to share code:** Courier records a failed attempt (UC-029); state reverts to `IN_TRANSIT`, attempt counted.
- **A3 — Duplicate submission after success:** Repeat with same/similar request → idempotent no-op returning DELIVERED result (DOC-SA-010 §5).

## Exception Scenarios
- **E1 — 3rd wrong code:** Confirmation locks for 24 hours and a support ticket auto-creates (BR-SHP-03); admin/support resolves (UC-033/UC-014).
- **E2 — Concurrent admin action:** Admin cancels/disputes simultaneously → transition guards decide within the transaction; conflict returns `409` (DOC-SA-010 §5).
- **E3 — Payment/escrow engine error post-transition:** State becomes DELIVERED but escrow job fails → BullMQ retry 3× then DLQ alert (BR-PLT-02); reconciliation catches drift (BR-ESC-08).

## Postconditions
- Success: sub-order `DELIVERED`; proof stored; escrow 7-day timer running (BR-ESC-01); return window open (BR-RET-01).
- Failure: state remains `OUT_FOR_DELIVERY` (or reverts per A2); escrow untouched.

## Business Rules Applied
- BR-ORD-03, BR-ORD-08, BR-ESC-01, BR-RET-01, BR-REV-01, BR-SHP-02, BR-SHP-03, BR-SHP-07, BR-NTF-01, BR-PLT-02, BR-ESC-08

## Related Requirements
- FR-015 (Shipping & Delivery), FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** Assigned courier submits code; customers hold the code (UC-013); no one can force DELIVERED without verification (BR-ORD-08).
- **Data involved:** Delivery code (hashed), attempt counter, proof record, status history, escrow timer.
- **External dependencies:** Escrow engine (B07); notifications (B10); support ticketing (B13).

## Acceptance Criteria
- **AC-UC030-01:** Given the correct code, when submitted, then state becomes `DELIVERED` and escrow hold starts (BR-ESC-01).
- **AC-UC030-02:** Given 3 wrong codes, when the 3rd fails, then confirmation locks 24 h and a ticket exists (BR-SHP-03).
- **AC-UC030-03:** Given any direct state-set attempt bypassing the code, when requested, then DELIVERED cannot be reached (BR-ORD-08, C-16).
