# UC-012 — Track Order

## Header Info
- **Use Case ID:** UC-012
- **Title:** Track Order
- **Actor:** Customer (ACT-01)
- **Trigger:** Customer opens "My Orders" or a specific order
- **Priority:** P1
- **Goal:** Show the buyer the live state, timeline, and money breakdown of their own master order across the 17-state machine.
- **Preconditions:** Customer authenticated; order exists and is owned by the customer (BR-ORD-09).

## Main Scenario
1. Customer opens order list → client `GET /orders` returns own orders only (ownership/IDOR enforced, DOC-OVR-007).
2. Customer opens an order → system `GET /orders/{id}` returns master order with per-vendor sub-orders, current state (one of the 17, C-09/BR-ORD-01), totals (items − discount + VAT + shipping, BR-FIN-02) and wallet payment receipt.
3. System renders the timeline from append-only `order_status_history` (actor, timestamp, reason — BR-ORD-03), including courier assignment stage (no GPS/location data — C-16, BR-SHP-05).
4. At `OUT_FOR_DELIVERY` the customer sees the 6-digit delivery code to share with the courier (BR-SHP-02, UC-013).
5. State-change notifications arrive via in-app/SMS/WhatsApp/push per preferences (BR-NTF-01, BR-NTF-04).
6. When `DELIVERED`, the screen shows the 7-day escrow countdown and, if within policy, "Request return" (UC-021 entry point, BR-RET-01).

## Alternative Scenarios
- **A1 — Multi-vendor order:** Master shows sub-orders with independent states (BR-ORD-07); master completes only when all sub-orders are COMPLETED or REFUNDED.
- **A2 — Cancelled order:** State `CANCELLED` → refund flow entry shown; refund status visible until `REFUNDED` (BR-ORD-04).
- **A3 — Disputed order:** State `DISPUTED` → escrow frozen notice and admin-resolution status displayed (BR-ORD-05).

## Exception Scenarios
- **E1 — Another customer's order ID:** Request denied (ownership check, SEC-REQ-004); no data leakage.
- **E2 — Notification outage:** Push/SMS fails → in-app timeline remains authoritative; jobs retry per BR-PLT-02.
- **E3 — Concurrent transition:** State changes while viewing → next poll/refresh shows the new state; history rows are never overwritten (BR-ORD-03).

## Postconditions
- Read-only: no state, wallet, or stock change.
- Buyer, vendor (own sub-orders), assigned courier and admin see consistent scoped timelines (BR-ORD-09).

## Business Rules Applied
- BR-ORD-01, BR-ORD-03, BR-ORD-04, BR-ORD-05, BR-ORD-07, BR-ORD-09, BR-ESC-01, BR-FIN-02, BR-NTF-01, BR-NTF-04, BR-SHP-02, BR-SHP-05, BR-RET-01

## Related Requirements
- FR-012 (Order Lifecycle Management), FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** Buyer reads own orders only; vendor reads own sub-orders; courier reads assigned delivery (BR-ORD-09).
- **Data involved:** Master/sub-orders, status history, payment receipt, delivery code (masked until stage).
- **External dependencies:** Notification channels (B10); polling/websocket updates.

## Acceptance Criteria
- **AC-UC012-01:** Given order in `PICKED_UP`, when opened, then the timeline shows every prior transition with actor and timestamp (BR-ORD-03).
- **AC-UC012-02:** Given another customer's order ID, when requested, then access is denied (SEC-REQ-004).
- **AC-UC012-03:** Given a multi-vendor order, when one sub-order is `DELIVERED` and another `PROCESSING`, then both states render independently (BR-ORD-07).
