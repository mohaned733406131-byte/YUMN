# UC-046 — Expire Unpaid Stock Reservations After 15 Minutes

## Header Info
- **Use Case ID:** UC-046
- **Title:** Expire Unpaid Stock Reservations After 15 Minutes
- **Actor:** System (ACT-07) — TTL sweeper job (no interactive login)
- **Trigger:** Repeatable queue job `b02.inventory.expire` runs every 60 seconds (C-13)
- **Priority:** P0
- **Goal:** Release every unpaid stock reservation whose 15-minute hold has elapsed so held quantity returns to sellable stock exactly once.
- **Preconditions:** Reservations exist with `expires_at = created_at + 15 min` and status `HELD`; payment has not completed for them.

## Main Scenario
1. The repeatable sweeper selects rows where `expires_at <= now` and `status = HELD` on queue `b02.inventory.expire` (FR-005).
2. For each row the system opens a transaction and re-checks the status guard `status = HELD` (BR-INV-04).
3. It decrements `qty_reserved` by the held quantity and flips the reservation to `RELEASED` (BR-INV-04, BR-CRT-02).
4. It appends a `RELEASE_TLP` ledger row with actor `SYSTEM` and a timestamp — append-only, corrections are new rows (BR-INV-04).
5. A `StockReleased` event is emitted so cart countdowns and availability views refresh (FR-005, C-13).
6. A re-run of the sweep over already-`RELEASED` rows is a no-op — the status guard prevents double release (BR-INV-04).

## Alternative Scenarios
- **A1 — Payment won the race:** the reservation is already `CONSUMED` by the payment transaction → the sweeper skips it; the permanent deduction stands (BR-INV-04, C-13).
- **A2 — Cart activity refreshed the hold:** `expires_at` was pushed forward by a cart change → the row is not selected until the new deadline (BR-CRT-02).
- **A3 — Batch with mixed states:** one sweep covers many rows → each row is guarded individually; held rows release, consumed ones are left alone (BR-INV-04).

## Exception Scenarios
- **E1 — Sweep job fails:** the job is retried with backoff and alerted if it keeps failing; overdue rows release on the next tick once the queue recovers (FR-005).
- **E2 — Failure mid-release:** the transaction rolls back → the row stays `HELD` with its old `expires_at`, and the next sweep releases it — never a partial release (BR-INV-04).
- **E3 — Sweeper delayed (downtime):** release happens later than the 60-second budget after recovery; the UI countdown always uses the server timestamp, so displayed expiry stays truthful (C-13).

## Postconditions
- Success: expired reservations are `RELEASED`, `qty_reserved` decreased once per row, `RELEASE_TLP` ledger rows appended with actor `SYSTEM`.
- Failure: no reservation state or stock quantity changes; the offending row remains `HELD` and is retried on the next sweep.

## Business Rules Applied
- BR-INV-04, BR-CRT-02

## Related Requirements
- FR-005 (Inventory Management)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); vendors never release reservations manually — the sweeper owns the TTL path (FR-005).
- **Data involved:** `stock_reservation` rows, inventory `qty_reserved`, inventory ledger, `StockReleased` events.
- **External dependencies:** BullMQ/Redis repeatable job (C-20); cart and storefront cache invalidation.

## Acceptance Criteria
- **AC-UC046-01:** Given a `HELD` reservation aged 15 minutes, when the sweep runs, then status becomes `RELEASED` and `qty_reserved` drops by the held quantity (BR-INV-04).
- **AC-UC046-02:** Given a `RELEASED` reservation, when the sweep runs again, then no further quantity is released (BR-INV-04).
- **AC-UC046-03:** Given a reservation consumed by payment, when the sweep runs, then it is skipped and stock stays deducted (C-13).
- **AC-UC046-04:** Given a release, when it posts, then a `RELEASE_TLP` ledger row with actor `SYSTEM` and timestamp exists (BR-INV-04).
