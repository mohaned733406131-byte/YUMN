# UC-068 — Gate Traffic on Liveness and Readiness Probes

## Header Info
- **Use Case ID:** UC-068
- **Title:** Gate Traffic on Liveness and Readiness Probes
- **Actor:** System (ACT-07) — health endpoints under orchestrator/load-balancer probing (no interactive login)
- **Trigger:** Continuous probe calls from the orchestrator, load balancer, and monitoring stack
- **Priority:** P0
- **Goal:** Route traffic only to ready instances and restart unresponsive ones, holding availability at the 99.99% target.
- **Preconditions:** Every service exposes liveness and readiness endpoints; probes wired in deployment config; C-26 availability target active.

## Main Scenario
1. The orchestrator calls the liveness probe at short intervals; a healthy process answers `200` and is left running.
2. The load balancer calls the readiness probe before routing traffic; `ready` instances receive requests, `not ready` instances are drained from rotation.
3. Readiness reports dependency state (database, Redis/queue); when dependencies are reachable the instance flips back to ready and rejoins rotation.
4. Probe results and availability metrics are exported to monitoring (C-26 target 99.99%, BR-PLT-07).
5. Operations observe probe status through the admin health views (FR-020).

## Alternative Scenarios
- **A1 — Dependency degraded, process healthy:** Liveness passes but readiness fails → traffic drains while the instance heals; no user requests hit a broken worker.
- **A2 — Rolling deploy / cold start:** New instances stay unready until warm-up completes, then enter rotation — zero-downtime cutover.
- **A3 — Recovery:** Dependencies return → readiness passes → instance re-enters rotation without restart.

## Exception Scenarios
- **E1 — Liveness failures persist:** The orchestrator restarts the instance; repeated restarts surface as an alert rather than an infinite crash loop serving errors.
- **E2 — Probe flapping:** Consecutive-failure thresholds (hysteresis) prevent traffic churn; the instance changes state only on sustained results.
- **E3 — All instances unready:** Rotation empties → platform unavailability triggers a page; the availability objective (C-26/BR-PLT-07) is breached visibly, never silently.

## Postconditions
- Only ready instances serve traffic; unresponsive instances are restarted or replaced.
- Probe state and availability are observable (metrics/alerts).
- No request is routed to an instance that cannot reach its dependencies.

## Business Rules Applied
- BR-PLT-07

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Probes are unauthenticated operational endpoints exposing status only (no business data); admin reads health views (FR-020).
- **Data involved:** Health status flags, probe counters, availability metrics — no business entities.
- **External dependencies:** Orchestrator/load balancer probe configuration; Prometheus/Grafana-style monitoring (conceptual observability stack).

## Acceptance Criteria
- **AC-UC068-01:** Given an instance that cannot reach the database, when readiness is probed, then it fails and the instance is removed from traffic.
- **AC-UC068-02:** Given a hung process, when liveness fails repeatedly, then the orchestrator restarts it.
- **AC-UC068-03:** Given dependencies recover, when readiness passes, then the instance rejoins rotation without manual action.
- **AC-UC068-04:** Given sustained healthy probes, when measured over the window, then availability tracks the 99.99% target (BR-PLT-07, C-26).
