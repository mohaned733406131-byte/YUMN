# UC-246 — Record SMS and WhatsApp Delivery Receipts per Message

## Header Info
- **Use Case ID:** UC-246
- **Title:** Record SMS and WhatsApp Delivery Receipts per Message
- **Actor:** System (ACT-07) — receipt ingestion webhook handler (no interactive login)
- **Trigger:** A provider posts a delivery receipt (DLR) or WhatsApp status webhook for a sent message
- **Priority:** P1
- **Goal:** Record delivery status per message so send quality is observable and failures are attributable.
- **Preconditions:** The message was dispatched via `b10.notification.delivery`; the provider webhook is configured with signature verification; receipts are best-effort (recorded when the provider delivers them).

## Main Scenario
1. The provider webhook fires with a message status (sent / delivered / failed).
2. Signature, allowlist and replay-window verification runs first — invalid calls are rejected before touching records.
3. A valid receipt is matched to its message via correlation ID and the per-message status row is updated.
4. Duplicate receipts short-circuit — the message keeps one status record, no duplicate rows.
5. The handler acknowledges quickly; persisted payload processing continues asynchronously.
6. Receipt outcomes and latency feed provider-quality metrics (NFR-014).

## Alternative Scenarios
- **A1 — Receipt for an unknown message:** it is logged as unmatched and never attached to another message.
- **A2 — WhatsApp status update instead of an SMS DLR:** the same pipeline records it; the per-message status is updated either way.
- **A3 — No receipt ever arrives:** the message keeps its last known status — a missing receipt alone is not a send failure (best-effort semantics).

## Exception Scenarios
- **E1 — Signature invalid:** the call is rejected outright and nothing is recorded; repeated invalid calls are a security signal.
- **E2 — Handler crashes after receipt:** the raw payload was durably persisted before acknowledgement → processing resumes from it; no receipt is lost.
- **E3 — Provider outage with no receipts:** sends continue; status rows stay at their last known value; the gap shows in metrics (NFR-014).

## Postconditions
- Success: every received receipt leaves the message with its latest provider status and correlation ID; metrics are updated.
- Failure: invalid or unprocessable receipts change nothing — the original send record stays untouched.

## Business Rules Applied
- None — receipt recording is provider-integration behavior (FR-017); no BR in DOC-BA-005 governs delivery receipts.

## Related Requirements
- FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — writes message-status rows from verified provider calls; providers have no other write path.
- **Data involved:** message records, per-message status rows, correlation IDs, raw receipt payloads, metrics.
- **External dependencies:** SMS provider DLR webhook; WhatsApp status webhook; Prometheus metrics.

## Acceptance Criteria
- **AC-UC246-01:** Given a signed receipt for a sent message, when it is processed, then that message's status updates with its correlation ID (FR-017).
- **AC-UC246-02:** Given an invalid signature, when the webhook arrives, then it is rejected and no status row changes.
- **AC-UC246-03:** Given the same receipt delivered twice, when both arrive, then exactly one status record exists for the message.
- **AC-UC246-04:** Given a receipt for an unknown message, when it arrives, then it is never attached to an existing message.
