# UC-249 — Purge CDN and ISR Caches When Content Is Published

## Header Info
- **Use Case ID:** UC-249
- **Title:** Purge CDN and ISR Caches When Content Is Published
- **Actor:** System (ACT-07) — content publish cache-invalidation job (no interactive login)
- **Trigger:** CMS content is published or a banner changes and the commit lands
- **Priority:** P1
- **Goal:** Readers see new content immediately — edge HTML and cached pages are purged in the same publish flow.
- **Preconditions:** The publish is committed in the database; the CDN fronts catalog/CMS routes; `b12.content.publish` owns revalidation (ISR ping + cache purge).

## Main Scenario
1. Publish commits → the service layer emits invalidation (after commit, never from controllers — job-driven updates invalidate too).
2. `cms:page:*` and `banner:*` keys are purged from Redis.
3. The `b12.content.publish` job sends the ISR revalidation ping and the CDN purge for affected routes.
4. The next edge request re-renders from committed source and repopulates the cache with the new version.
5. The job outcome is observable; a failure alerts instead of leaving stale edge content unexplained (BR-PLT-02).
6. The reader never chooses between versions — the database is the only source of truth.

## Alternative Scenarios
- **A1 — Purge partially applied:** remaining keys expire at their TTL (CMS pages 10 min, banners 5 min) — staleness stays bounded even on failure.
- **A2 — Publish with no cached copy:** the purge is a no-op; the next read simply caches the fresh content.
- **A3 — Job-driven update rather than an admin click:** invalidation still fires — the emit point is the service layer, so background updates purge too.

## Exception Scenarios
- **E1 — Revalidation ping fails:** retry with backoff then dead-letter with an alert (BR-PLT-02); TTL bounds stale edge content meanwhile.
- **E2 — CDN unreachable:** Redis keys are already purged; the CDN serves until the retry succeeds or its own TTL elapses.
- **E3 — Concurrent publishes:** each emits its own purge; the next render reads whatever last committed — no split-brain versioning.

## Postconditions
- Success: no cached or edge copy of the previous version survives — the next read renders committed content.
- Failure: bounded staleness only — Redis TTL (5–10 min) plus job retry; never a permanently stale page presented as current.

## Business Rules Applied
- BR-PLT-02 — job retry/DLQ discipline for the purge job; publish-time invalidation itself is cache behavior under FR-019 (no dedicated BR).

## Related Requirements
- FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — invalidates cache and edge copies; the publish itself belongs to an admin/CMS author (ACT-04).
- **Data involved:** CMS page and banner cache keys, ISR route copies, CDN edge HTML, publish events.
- **External dependencies:** Redis cache; CDN/ISR revalidation endpoint; BullMQ `b12.content.publish` queue.

## Acceptance Criteria
- **AC-UC249-01:** Given a committed publish, when invalidation runs, then cms/banner keys are purged and an ISR revalidation ping is issued (FR-019).
- **AC-UC249-02:** Given a failing purge job, when retries exhaust, then it dead-letters with an alert (BR-PLT-02).
- **AC-UC249-03:** Given a failed purge, when the TTL lapses, then readers get fresh content within the TTL bound.
- **AC-UC249-04:** Given a job-driven content update, when it commits, then the same invalidation path runs (no controller-only emit).
