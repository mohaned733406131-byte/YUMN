# UC-250 — Invalidate the Coupon Validation Cache on Admin Disable

## Header Info
- **Use Case ID:** UC-250
- **Title:** Invalidate the Coupon Validation Cache on Admin Disable
- **Actor:** System (ACT-07) — cache invalidation hook (no interactive login)
- **Trigger:** An admin disables a coupon and the disable commits
- **Priority:** P2
- **Goal:** A disabled coupon stops validating immediately — not whenever its cache entry happens to expire.
- **Preconditions:** The coupon is cacheable (`coupon:{code}`, 60 s TTL); the admin holds coupon-management permission; the disable commits in the database first.

## Main Scenario
1. The admin disables the coupon → the disable commits in the database.
2. The service layer emits invalidation after commit — explicit bump/purge of the `coupon:{code}` entry.
3. The next validation read misses the cache, loads the definition, sees disabled and rejects before order creation (BR-PRM-04).
4. The rejection is a validation error with no order row created (BR-PRM-06).
5. The admin action is recorded in the append-only audit trail with before/after state (BR-PLT-06).
6. A later re-enable simply repopulates from source on the next read — the cache never decides state.

## Alternative Scenarios
- **A1 — Entry already expired:** the 60 s TTL would have caught it anyway; the explicit bump just makes the effect immediate.
- **A2 — Validation racing the disable:** an in-flight read may complete against the pre-disable value; the very next validation observes the disable — staleness is bounded to that race, never open-ended.
- **A3 — Disable of a never-cached coupon:** nothing to purge; the source state already governs all reads.

## Exception Scenarios
- **E1 — Invalidation emission fails:** the 60 s TTL bounds staleness — the coupon can validate for at most one TTL window, never longer (BR-PRM-04).
- **E2 — Read during the disable transaction:** the uncommitted change is invisible under isolation; after commit the cache is bumped.
- **E3 — The disable itself fails:** no commit → no invalidation → the coupon stays valid — consistent, never half-applied.

## Postconditions
- Success: the coupon is disabled in the database, its cache entry is invalidated, and the next validation rejects it before any order row (BR-PRM-04, BR-PRM-06).
- Failure: nothing is half-applied — the coupon is either fully valid or fully disabled; no stale validation outlives one TTL.

## Business Rules Applied
- BR-PRM-04, BR-PRM-06, BR-PLT-06

## Related Requirements
- FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — invalidates cache and writes audit; the disable action itself belongs to admin (ACT-04).
- **Data involved:** coupon definition row, `coupon:{code}` cache entry, checkout validation reads, audit entry.
- **External dependencies:** Redis coupon cache; admin console; audit pipeline.

## Acceptance Criteria
- **AC-UC250-01:** Given a cached enabled coupon, when the admin disables it, then its cache entry is invalidated in the same flow (FR-019).
- **AC-UC250-02:** Given a disabled coupon, when checkout validates it, then it is rejected before any order row is created (BR-PRM-04, BR-PRM-06).
- **AC-UC250-03:** Given the disable action, when it commits, then an audit entry records actor, action and before/after state (BR-PLT-06).
- **AC-UC250-04:** Given an invalidation failure, when the TTL lapses, then validation observes the disable within 60 seconds.
