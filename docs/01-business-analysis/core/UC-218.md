# UC-218 — Resolve the Reservation-Expiry Race at Checkout Confirmation

## Header Info
- **Use Case ID:** UC-218
- **Title:** Resolve the Reservation-Expiry Race at Checkout Confirmation
- **Actor:** System (ACT-07) — checkout/inventory service (no interactive login)
- **Trigger:** Checkout confirmation arrives at the same moment the reservation's 15-minute TTL expires
- **Priority:** P0
- **Goal:** Resolve the race deterministically — exactly one of commit or release wins, never both, and stock never goes negative.
- **Preconditions:** A reservation exists with a 15-minute TTL (BR-CRT-02, C-13); the TTL sweeper may fire concurrently; confirmation re-checks validity (BR-INV-01).

## Main Scenario
1. Checkout confirmation arrives while the reservation's TTL may be expiring.
2. The race resolves deterministically: an expiry that wins releases first, and confirmation re-checks reservation validity before committing.
3. Reservation still valid → commit: permanent atomic deduction, reservation moves to committed (BR-INV-01).
4. Reservation already released → confirmation re-reserves if stock is available, otherwise fails with a stock conflict; no order row survives a conflict (BR-CRT-02).
5. A release is status-guarded — re-running the sweeper never releases the same hold twice (BR-INV-04).
6. Stock never goes negative at any point in either ordering (BR-CAT-07).

## Alternative Scenarios
- **A1 — Confirmation wins:** the expiry job later finds a committed reservation and releases nothing.
- **A2 — Expiry wins, stock still free:** the confirmation re-reserves with a fresh 15-minute hold and checkout proceeds.
- **A3 — Expiry wins, stock taken:** checkout returns a stock conflict; the cart item is flagged until removed (BR-CRT-05).

## Exception Scenarios
- **E1 — Sweeper crashed mid-release:** the retry is idempotent — the guarded status yields exactly one release outcome.
- **E2 — Confirmation transaction fails:** rollback leaves the reservation exactly as it was — committed or still held, never half-released.
- **E3 — Duplicate confirmation replay:** idempotency on the checkout key returns the original outcome instead of re-running the race (BR-PLT-03).

## Postconditions
- Success: the reservation commits to a permanent deduction and checkout continues.
- Failure: exactly one release outcome exists — no double release, no negative stock, no orphan hold.

## Business Rules Applied
- BR-INV-01, BR-CRT-02

## Related Requirements
- FR-005 (Inventory Management)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — commits/releases on behalf of checkout; no human override of the race outcome.
- **Data involved:** stock reservations, inventory quantities, order rows (only on success), release ledger events.
- **External dependencies:** PostgreSQL transactions; BullMQ TTL sweeper job.

## Acceptance Criteria
- **AC-UC218-01:** Given a reservation expiring as confirmation arrives, when both run, then the outcome is commit or release — never both (BR-INV-01).
- **AC-UC218-02:** Given a released reservation, when confirmation runs, then it re-reserves or fails with conflict — no half state (BR-CRT-02).
- **AC-UC218-03:** Given the expiry job runs twice, when it completes, then stock is released exactly once (BR-INV-04).
