# UC-222 — Rebuild the Search Index From Source After an Outage

## Header Info
- **Use Case ID:** UC-222
- **Title:** Rebuild the Search Index From Source After an Outage
- **Actor:** System (ACT-07) — index rebuild job (no interactive login)
- **Trigger:** Elasticsearch health recovers after an outage and the index is stale or lost
- **Priority:** P1
- **Goal:** Repopulate the search index from the database so search is trustworthy again without restoring a backup (the index has none).
- **Preconditions:** Cluster health check passes; PostgreSQL is the source of truth; index is rebuildable, not backed up; browse fallback available meanwhile (FR-009).

## Main Scenario
1. Cluster health recovers → the full rebuild job is triggered — rebuild is the documented recovery path for a non-backed-up index.
2. The job walks PostgreSQL in idempotent batches by ID range and reindexes documents.
3. Only ACTIVE products with available stock are written; inactive or soft-deleted products stay out (BR-CAT-06).
4. While the rebuild runs, search stays degraded and category browse keeps serving from database/cache (FR-009).
5. Batch failures retry with backoff and land in the dead-letter queue with an alert if persistent (BR-PLT-02).
6. Rebuild completes → the backlog drains, search recovers, and the degraded-mode flag clears without a restart.

## Alternative Scenarios
- **A1 — Catalog changes during rebuild:** incremental index events flow alongside the backfill; the database always wins and the final state converges.
- **A2 — Incremental sync already healthy:** no rebuild needed — this use case covers the outage-recovery path only.
- **A3 — Scheduled rebuild cadence:** absent an outage the periodic full rebuild still guarantees no orphan documents survive bulk purges.

## Exception Scenarios
- **E1 — Rebuild crashes:** it resumes from the last completed batch; batches are idempotent, so no document is duplicated.
- **E2 — Outage not actually over:** health checks fail → the rebuild waits; search stays degraded rather than half-populated.
- **E3 — Persistent batch failure:** retries exhaust → dead-letter + alert (BR-PLT-02); operators replay after fixing the cause.

## Postconditions
- Success: the index matches the source; only ACTIVE products are discoverable; search is available again.
- Failure: the index stays in degraded mode with browse intact — never a partially trusted index presented as healthy.

## Business Rules Applied
- BR-CAT-06

## Related Requirements

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — index write rights; no human role writes documents directly.
- **Data involved:** product/category source rows, search index documents, batch checkpoints, DLQ entries.
- **External dependencies:** Elasticsearch (DEP-04); BullMQ rebuild queue.

## Acceptance Criteria
- **AC-UC222-01:** Given a restored cluster, when the rebuild runs, then every ACTIVE product is searchable again (FR-009).
- **AC-UC222-02:** Given a soft-deleted product, when the rebuild indexes its category, then no document is created for it (BR-CAT-06).
- **AC-UC222-03:** Given a crash mid-rebuild, when the job resumes, then documents are not duplicated and the index converges to source.
