# UC-077 — Broadcast Delivery Offers to Eligible Couriers

## Header Info
- **Use Case ID:** UC-077
- **Title:** Broadcast Delivery Offers to Eligible Couriers
- **Actor:** System (ACT-07) — assignment broadcaster (no interactive login)
- **Trigger:** Sub-order reaches `READY_FOR_PICKUP` and awaits courier assignment
- **Priority:** P0
- **Goal:** Offer each ready delivery to all eligible couriers in the zone simultaneously and assign it to exactly the first acceptor.
- **Preconditions:** Sub-order `READY_FOR_PICKUP` with zone set; couriers online with served zones; assignment queue running.

## Main Scenario
1. The state change enqueues `b08.shipping.assign-offer`; the worker selects couriers whose served zone matches and who are online.
2. An offer row is created and broadcast — the same delivery is visible to multiple eligible couriers at once.
3. Couriers see it in their available-deliveries list (UC-025 step1–2) and may accept.
4. The first accept wins via optimistic locking: state moves to `ASSIGNED`, courier set, history appended; every later accept for the same delivery is rejected.
5. Losing/late offers are withdrawn so no stale accept can succeed after assignment.

## Alternative Scenarios
- **A1 — No eligible courier online:** The offer stays pending and is re-broadcast on the next cycle; the delivery is never force-assigned.
- **A2 — Courier accepts then releases (UC-205):** State returns to `READY_FOR_PICKUP` and a fresh broadcast goes out.
- **A3 — Multiple accepts arrive concurrently:** Optimistic locking admits exactly one; the others get a conflict rejection — no double assignment.

## Exception Scenarios
- **E1 — Broadcast job crashes:** Retry is idempotent — offer rows are keyed by delivery, so replays update rather than duplicate; assignment rules unchanged.
- **E2 — Accept arrives while the job re-runs:** The accept path re-checks state (`READY_FOR_PICKUP` only) inside the transaction — a stale broadcast can never re-assign an assigned delivery.
- **E3 — Zone has no couriers at all:** The delivery remains pending with an operational signal so staff can intervene through the platform console.

## Postconditions
- Exactly one courier assigned per delivery (or none, still pending); state `ASSIGNED` with history row.
- All non-winners' offers withdrawn; no double assignment possible (BR-SHP-04).
- Re-broadcasts continue until an assignment exists.

## Business Rules Applied
- BR-SHP-04

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) creates offers; couriers (ACT-03) accept within their zone scope.
- **Data involved:** Offer rows, courier availability/zone records, sub-order state, assignment history.
- **External dependencies:** BullMQ (`b08.shipping.assign-offer`); courier availability store; optimistic-lock state updates.

## Acceptance Criteria
- **AC-UC077-01:** Given three online couriers in the zone, when a delivery becomes ready, then all three receive the offer (BR-SHP-04).
- **AC-UC077-02:** Given two simultaneous accepts, when both commit, then exactly one wins and the other is rejected — no double assignment.
- **AC-UC077-03:** Given no online courier in the zone, when the job runs, then the delivery stays pending and re-broadcasts later.
- **AC-UC077-04:** Given an assigned delivery, when a late accept arrives, then it is rejected.
