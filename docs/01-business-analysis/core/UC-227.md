# UC-227 — Expire Idempotency-Key Records After 24 Hours

## Header Info
- **Use Case ID:** UC-227
- **Title:** Expire Idempotency-Key Records After 24 Hours
- **Actor:** System (ACT-07) — idempotency store (no interactive login)
- **Trigger:** A stored idempotency-key record reaches its 24-hour TTL
- **Priority:** P2
- **Goal:** Keep replay records bounded: keys replay their original response for 24 hours, then age out automatically.
- **Preconditions:** Key records written write-through with 24-hour TTL (BR-PLT-03); database uniqueness backstops remain after expiry.

## Main Scenario
1. The first request stores its key record with a 24-hour TTL.
2. Any replay inside the window returns the stored response snapshot unchanged.
3. At 24 hours the store expires the record automatically — no cron, no manual cleanup.
4. After expiry the key string is treated as brand new; a fresh execution is allowed (BR-PLT-03 governs which operations must carry keys, not how long records live).
5. Durable database uniqueness constraints outlive the record, so money effects stay single even after the window.
6. Storage stays bounded: records age out continuously instead of accumulating.

## Alternative Scenarios
- **A1 — Reuse before expiry:** normal replay of the original response.
- **A2 — Error responses:** non-2xx results are not cached, so a failed attempt occupies no window.
- **A3 — Cache eviction under memory pressure:** early loss behaves like expiry; the database backstop still prevents duplicates.

## Exception Scenarios
- **E1 — Record lost before 24 hours:** a retry re-executes, but database constraints stop a second order or payment row from being created.
- **E2 — 5xx result not cached:** retries execute; ledger and order uniqueness keep side effects idempotent (BR-PLT-03).
- **E3 — Key reused across users:** keys are scoped to the request payload; a mismatched payload is rejected as a conflict, not replayed.

## Postconditions
- Success: key records disappear within 24 hours; in-window replays are exact; storage stays bounded.
- Failure: no duplicate order or payment is created by an expired or lost key.

## Business Rules Applied
- BR-PLT-03

## Related Requirements
- FR-011 (Checkout & Order Placement)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — owns key records; callers only present their own keys.
- **Data involved:** idempotency key records (request hash + response snapshot), database uniqueness constraints.
- **External dependencies:** Redis TTL store for key records; PostgreSQL as durable backstop.

## Acceptance Criteria
- **AC-UC227-01:** Given a key stored at time T, when it is replayed before T+24h, then the original response is returned (BR-PLT-03).
- **AC-UC227-02:** Given the same key after T+24h, when submitted, then the record is gone and the request executes as new.
- **AC-UC227-03:** Given expired keys, when the store is inspected, then no key record older than 24 hours remains.
