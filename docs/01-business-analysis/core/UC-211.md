# UC-211 — Enforce OTP and Login Rate-Limit Budgets With 429 and Retry-After

## Header Info
- **Use Case ID:** UC-211
- **Title:** Enforce OTP and Login Rate-Limit Budgets With 429 and Retry-After
- **Actor:** System (ACT-07) — rate-limit middleware (no interactive login)
- **Trigger:** A login or OTP request reaches an authentication endpoint and consumes a per-account, per-phone or per-IP budget
- **Priority:** P1
- **Goal:** Throttle abusive authentication bursts with `429` + `Retry-After` before any credential or OTP work runs, without throttling legitimate traffic.
- **Preconditions:** Redis counters reachable; budgets active (login 5 per 15 min per account + IP; OTP resend cooldown 60 s, max 3 per 10 min); lockout at 5 consecutive failures (BR-AUTH-03, BR-AUTH-04).

## Main Scenario
1. Request hits the auth middleware → counters are incremented and checked in Redis, keyed by account/phone and by source IP, before business logic.
2. Budget not exceeded → the request proceeds to the auth service for normal processing.
3. Budget exceeded → system answers `429` with `Retry-After` and stops before any credential check or OTP dispatch (BR-AUTH-03).
4. OTP resend inside budget but within the 60 s cooldown → rejected with the cooldown remaining (BR-AUTH-03).
5. Successful login resets the consecutive-failure counter; five consecutive failures still escalate to the 15-minute lock (BR-AUTH-04).
6. `429` bursts are exported as security metrics and alerted as abuse signals.

## Alternative Scenarios
- **A1 — Within budget:** request processed normally; counters decay with their window; no user-visible delay.
- **A2 — Legitimate heavy load:** budgets are sized so the baseline load profile passes untouched; counters are shared across replicas, so no replica bypasses a limit.
- **A3 — Lockout takes over:** at five consecutive failures the 15-minute lock rejects the attempt with the lock message rather than a generic throttle.

## Exception Scenarios
- **E1 — Counter store unavailable:** authentication fails closed with an explicit dependency error; no credential check, OTP issue or session happens without counters — never a silent bypass.
- **E2 — Distributed password spraying:** per-IP budgets catch spread attempts while the per-account counter still reaches the lockout threshold (BR-AUTH-04).
- **E3 — Client ignores Retry-After:** every request inside the window is answered `429` until it resets; nothing is processed in between.

## Postconditions
- Success: the request is either processed normally or rejected with `429` + `Retry-After`; counters reflect the outcome.
- Failure (counter store down): no session, OTP or password change occurs — authentication stays fail-closed.

## Business Rules Applied
- BR-AUTH-03, BR-AUTH-04

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)

## Permissions / Data / External Dependencies
- **Permissions:** pre-authentication middleware — applies to anonymous callers; no role required, no privileged data touched.
- **Data involved:** rate-limit counters, OTP attempt/resend counters, lockout state and lock events (phone masked in metrics).
- **External dependencies:** Redis counter store shared across API replicas.

## Acceptance Criteria
- **AC-UC211-01:** Given an exhausted OTP resend budget, when a resend is requested, then `429` with `Retry-After` is returned and no OTP is issued (BR-AUTH-03).
- **AC-UC211-02:** Given five consecutive failed logins, when the next attempt arrives, then the account is locked for 15 minutes and the lock event is logged (BR-AUTH-04).
- **AC-UC211-03:** Given a request inside its budget, when it reaches the middleware, then it is processed without a `429`.
