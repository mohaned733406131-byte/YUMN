# UC-072 — Cascade a Store Suspension Across Catalog, Orders, and Payouts

## Header Info
- **Use Case ID:** UC-072
- **Title:** Cascade a Store Suspension Across Catalog, Orders, and Payouts
- **Actor:** System (ACT-07) — suspension cascade worker (no interactive login)
- **Trigger:** Admin records a store/user suspension decision; the cascade job applies its four effects
- **Priority:** P0
- **Goal:** Apply one suspension decision consistently everywhere — storefront, checkout, live orders, and payouts — so nothing keeps selling or paying out.
- **Preconditions:** Suspension decision recorded with actor and reason; store-scoped enforcement in place (BR-VND-07).

## Main Scenario
1. The suspension decision is recorded (privileged action, actor + reason, append-only history).
2. Effect 1 — catalog: the store's products are hidden from storefront and search; only previously visible states existed before suspension.
3. Effect 2 — new orders: checkout against this store's items is blocked; carts referencing it fail server-side validation.
4. Effect 3 — existing orders: the store's live sub-orders are frozen pending review — no state advances while frozen.
5. Effect 4 — payouts: the store's payable is held; payout batch eligibility skips it (BR-VND-04 defines all four effects).
6. Every store-scoped query continues to be enforced at the service layer — cross-store access stays denied (BR-VND-07).

## Alternative Scenarios
- **A1 — Suspension lifted (re-activation):** The cascade is reversed: products become visible again, orders resume, payouts un-hold — gated by the admin re-activation decision.
- **A2 — Order already in delivery:** The freeze applies to state advancement as defined by BR-VND-04; history is append-only — frozen means "held pending review", never rewritten.
- **A3 — Cascade re-run (retry/replay):** The cascade is idempotent — a second run converges to the same end state with no duplicate effects.

## Exception Scenarios
- **E1 — Cascade step fails midway (e.g., payouts hold times out):** The job retries the failed effect until all four hold; the platform errs toward holding money and blocking sales rather than partially applying.
- **E2 — Concurrent new order racing the flag:** Once the block flag is set inside the transaction, the racing checkout fails validation; an order committed before the flag is part of effect 3's freeze.
- **E3 — Cascade job dead-letters:** Depth alert fires; the suspension decision itself is already recorded, so staff can see the incomplete cascade and re-drive it.

## Postconditions
- All four effects hold: products hidden, new orders blocked, existing orders frozen, payouts held (BR-VND-04).
- Suspension is observable and auditable; store scoping unchanged (BR-VND-07).
- No revenue flows out while the store is suspended.

## Business Rules Applied
- BR-VND-04, BR-VND-07

## Permissions / Data / External Dependencies
- **Permissions:** Admin records the decision; System applies it automatically; vendor staff lose effective write scope while suspended.
- **Data involved:** Store status, product visibility, sub-order states, payable/payout eligibility, audit rows.
- **External dependencies:** Suspension cascade queue; catalog/checkout/payout services; notification of affected vendor (conceptual).

## Acceptance Criteria
- **AC-UC072-01:** Given a suspended store, when a customer browses, then its products are not shown (BR-VND-04).
- **AC-UC072-02:** Given a suspended store, when checkout references its items, then the order is blocked.
- **AC-UC072-03:** Given live sub-orders of a suspended store, when the cascade runs, then they are frozen pending review (BR-VND-04).
- **AC-UC072-04:** Given a suspended store with payable balance, when payout batching runs, then its payout is held.
