# UC-255 — Cascade Primary-Data Deletion to Search, Cache, Queues, and Objects

## Header Info
- **Use Case ID:** UC-255
- **Title:** Cascade Primary-Data Deletion to Search, Cache, Queues, and Objects
- **Actor:** System (ACT-07) — deletion cascade job (no interactive login)
- **Trigger:** A primary record is deleted (account deletion, scheduled purge, or store closure)
- **Priority:** P1
- **Goal:** Derived stores never outlive their source — search, cache, queues and object storage are updated in the same operation.
- **Preconditions:** The primary deletion committed in the database (source of truth); the entity's derived stores are identified; the index-lag SLO is 5 minutes.

## Main Scenario
1. The primary deletion commits in PostgreSQL.
2. Search: index documents for the entity are removed or updated within the 5-minute index-lag SLO.
3. Cache: entity keys are purged explicitly — never left to expire naturally.
4. Queues: pending jobs parameterized by the entity are cancelled or drained before the run completes.
5. Objects: MinIO hard delete plus version purge plus orphan-key sweep.
6. Verification queries confirm no derived copy still serves the record; the nightly full index rebuild is the backstop.

## Alternative Scenarios
- **A1 — Product soft-deleted only:** documents drop from search and only ACTIVE products show (BR-CAT-06); objects stay while orders reference them — hard purge waits for the product row itself.
- **A2 — A derived store briefly unreachable:** the step is retried within the SLO and tracked to completion — never dropped as "done".
- **A3 — Bulk purge:** queues are drained first so no job re-serves deleted state; the full rebuild covers any index residue.

## Exception Scenarios
- **E1 — Index delete fails:** retries persist; if unresolved, the nightly rebuild removes the orphan and an alert fires (BR-PLT-02).
- **E2 — Object store unreachable:** the orphan sweep picks the keys up later; keys are non-guessable, so a lingering key is never served.
- **E3 — Open queue jobs for the record:** they are cancelled or drained before the cascade completes — no job recreates or serves stale state.

## Postconditions
- Success: the primary row is gone and its search documents, cache keys, queued jobs and objects are gone with it — no derived copy serves the record.
- Failure: nothing is left silently stale — failures are retried, alerted and covered by the nightly rebuild; deletion is never reported done while a store still serves the entity.

## Business Rules Applied
- BR-CAT-06 (soft-delete semantics and search visibility during partial deletion), BR-PLT-02 (cascade retries and dead-letter alerting)

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — touches only the deleted entity's derived rows; ownership scoping still applies per store.
- **Data involved:** primary rows, search index documents, Redis keys, queued jobs, MinIO objects and versions, purge counts.
- **External dependencies:** Elasticsearch index; Redis cache; BullMQ queues; MinIO object store; nightly rebuild job.

## Acceptance Criteria
- **AC-UC255-01:** Given a deleted primary record, when the cascade runs, then its search documents, cache keys and queued jobs are removed (FR-020).
- **AC-UC255-02:** Given a product soft-delete, when search serves results, then the product is absent while order-referenced objects are kept (BR-CAT-06).
- **AC-UC255-03:** Given a failing cascade step, when retries exhaust, then it dead-letters with an alert and the nightly rebuild backstops the index (BR-PLT-02).
- **AC-UC255-04:** Given orphaned objects after the purge, when the sweep runs, then they are removed.
