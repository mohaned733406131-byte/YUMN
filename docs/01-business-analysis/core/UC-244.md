# UC-244 — Deduplicate Notification Fan-Out by Event, Recipient, and Channel

## Header Info
- **Use Case ID:** UC-244
- **Title:** Deduplicate Notification Fan-Out by Event, Recipient, and Channel
- **Actor:** System (ACT-07) — notification fan-out orchestrator (no interactive login)
- **Trigger:** A domain event reaches the fan-out queue, possibly more than once (at-least-once delivery)
- **Priority:** P1
- **Goal:** Each recipient receives each notification exactly once per channel, even when the event or a job repeats.
- **Preconditions:** The domain event carries an event ID (no message bodies in the payload); recipient resolution and preferences are available (FR-017); queues reachable.

## Main Scenario
1. `b10.notification.fanout` receives the domain event and resolves recipients and locale.
2. Preference check runs — security notices are non-disableable (BR-NTF-02).
3. Child jobs are created per channel with `jobId = hash(eventId, recipient, channel)` — the dedup key.
4. A duplicate enqueue of the same event/recipient/channel collides on that job ID and collapses to one job; retries of the job stay idempotent (BR-PLT-03 discipline applied to fan-out).
5. Distinct channels are separate jobs — SMS, WhatsApp, push and in-app each send their own copy.
6. Delivery lanes dispatch and receipts are logged per message.

## Alternative Scenarios
- **A1 — Same event, different recipients:** distinct job IDs → each recipient receives their copy once.
- **A2 — Same event, same recipient, different channels:** one job per channel → each channel delivers exactly once.
- **A3 — Retry of a failed delivery job:** the same job ID → no second message; the retry completes the original send.

## Exception Scenarios
- **E1 — Producer publishes the event twice:** the fan-out collapses to one set of sends on the dedup key (BR-PLT-03).
- **E2 — Preference or recipient resolution fails:** retries then dead-letter with an alert — no partial fan-out is presented as complete (BR-PLT-02).
- **E3 — One channel's send fails:** other channels are unaffected; the failed lane retries under its own job — recipients never get duplicates from the retry (BR-PLT-02).

## Postconditions
- Success: exactly one message per (event, recipient, channel); security notices still went out; receipts logged.
- Failure: no duplicate messages are produced; failed sends sit in the dead-letter queue with an alert — no silent loss (NFR-007).

## Business Rules Applied
- BR-PLT-03, BR-NTF-02, BR-PLT-02

## Related Requirements
- FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — writes job and message records; preference data is read, never edited here.
- **Data involved:** domain event IDs, recipient resolution, preference rows, child jobs, message records, receipts.
- **External dependencies:** BullMQ fan-out and delivery lanes; SMS/WhatsApp/push providers; in-app inbox.

## Acceptance Criteria
- **AC-UC244-01:** Given the same event delivered twice, when fan-out runs, then each recipient gets one message per channel (BR-PLT-03).
- **AC-UC244-02:** Given one event with two recipients, when fan-out runs, then each recipient's sends are independent and single.
- **AC-UC244-03:** Given a security notice, when preferences are checked, then it is still sent (BR-NTF-02).
- **AC-UC244-04:** Given a failing channel job, when retries exhaust, then it dead-letters with an alert and produces no duplicates (BR-PLT-02).
