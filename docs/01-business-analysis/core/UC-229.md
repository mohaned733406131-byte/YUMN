# UC-229 — Roll the Master Order Up to COMPLETED When Every Sub-Order Settles

## Header Info
- **Use Case ID:** UC-229
- **Title:** Roll the Master Order Up to COMPLETED When Every Sub-Order Settles
- **Actor:** System (ACT-07) — master aggregation job (no interactive login)
- **Trigger:** A sub-order reaches a terminal state and aggregation re-evaluates the master order
- **Priority:** P1
- **Goal:** Complete the master exactly when every sub-order has settled — never earlier, never twice.
- **Preconditions:** Master with sub-orders (C-10); terminal sub-order states are COMPLETED or REFUNDED (BR-ORD-07); history append-only (BR-ORD-03).

## Main Scenario
1. A sub-order reaches a terminal state — escrow released to `COMPLETED`, or refunded.
2. After the transition, aggregation checks the master: is every sub-order terminal and allowed?
3. All settled → the master transitions to `COMPLETED` with an append-only history row (actor System) (BR-ORD-07).
4. Any sub-order still active → the master stays where it is; the check re-runs on the next transition.
5. Mixed terminal outcomes (COMPLETED + REFUNDED) qualify — both are allowed settle states (BR-ORD-07).
6. Parties see the rolled-up state on the order timeline.

## Alternative Scenarios
- **A1 — Last sub-order completes after escrow release:** triggers the roll-up (the main path).
- **A2 — A sub-order was cancelled and refunded:** it counts as settled; the master can still complete.
- **A3 — Return rejection completes a sub-order:** `RETURN_REJECTED → COMPLETED` is itself terminal and feeds the same check.

## Exception Scenarios
- **E1 — Aggregation interrupted:** the check is idempotent and re-evaluated on the next event or a recovery sweep; the master completes later, never early.
- **E2 — Duplicate trigger:** the master is already `COMPLETED` → guarded no-op; no second history row for the same move (BR-ORD-03).
- **E3 — Sub-order stuck non-terminal:** no roll-up occurs — the guard is the protection, not a timeout (BR-ORD-07).

## Postconditions
- Success: the master is `COMPLETED` exactly when every sub-order settled; history appended once.
- Failure: the master remains in its pre-roll-up state; no premature completion exists.

## Business Rules Applied
- BR-ORD-07

## Related Requirements
- FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** automated order-state action permitted to System (ACT-07); actor recorded as System on the roll-up row.
- **Data involved:** master/sub-order states, order status history, escrow/payable outcomes feeding the terminal states.
- **External dependencies:** BullMQ aggregation sweep; escrow release job (upstream).

## Acceptance Criteria
- **AC-UC229-01:** Given sub-orders in mixed terminal states, when the last one settles, then the master becomes `COMPLETED` (BR-ORD-07).
- **AC-UC229-02:** Given one sub-order still active, when the others settle, then the master does not complete.
- **AC-UC229-03:** Given the roll-up, when it commits, then exactly one history row records the master's move (BR-ORD-03).
