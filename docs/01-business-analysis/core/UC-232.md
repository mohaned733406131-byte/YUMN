# UC-232 — Open a Circuit Breaker on a Failing Top-Up Provider and Degrade to Bank Transfer

## Header Info
- **Use Case ID:** UC-232
- **Title:** Open a Circuit Breaker on a Failing Top-Up Provider and Degrade to Bank Transfer
- **Actor:** System (ACT-07) — provider adapter / breaker (no interactive login)
- **Trigger:** Repeated timeouts or provider-down results on top-up initiations
- **Priority:** P1
- **Goal:** Fail fast instead of hanging users, and degrade top-ups to the rail that still works — bank transfer with admin verification.
- **Preconditions:** Provider adapter with 10 s call timeout; breaker thresholds configured; bank-transfer rail available (BR-PAY-04); wallet payments from existing balance unaffected.

## Main Scenario
1. Repeated provider-down or timeout results trip the breaker for that provider into open state.
2. While open, new top-up initiations fail fast with a provider-down result — no workers tied up, no user hang.
3. The top-up UI degrades: the failing provider's option is disabled; if both providers are open, only bank transfer remains, with a bilingual explanation (BR-PAY-04).
4. In-flight `PENDING` top-ups keep being watched by poll and reconciliation — they are not abandoned.
5. After the cooldown a half-open probe tests the provider; success closes the breaker, failure re-opens it.
6. The state change alerts operations; recovery drains the backlog and reconciliation confirms no double credit.

## Alternative Scenarios
- **A1 — One provider down:** the other provider plus bank transfer remain available.
- **A2 — Both providers down:** degrade to bank transfer only; wallet payments from existing balance are unaffected.
- **A3 — Provider recovers:** the breaker closes via probe and instant top-ups resume without a redeploy.

## Exception Scenarios
- **E1 — Probe keeps failing:** the breaker re-opens for another cooldown; degradation persists with alerts rather than error storms.
- **E2 — Callback arrives while open:** processed normally on the webhook path — the breaker only gates outbound initiation.
- **E3 — Bank fallback credit:** credits only after admin verification of the reference — never automatic (BR-PAY-04).

## Postconditions
- Success: top-ups degrade safely to available rails; no worker pile-up; no wallet credit without verification.
- Failure: pending items remain reconcilable; balances are untouched by the degradation itself.

## Business Rules Applied
- BR-PAY-04

## Related Requirements
- FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — adapter configuration and breaker state are runtime config; admin owns bank verification.
- **Data involved:** breaker state, top-up intents, provider health metrics, degradation banner text (ar/en).
- **External dependencies:** m-Floos/OneCash providers (INT-REQ-001); bank-transfer verification path (INT-REQ-002).

## Acceptance Criteria
- **AC-UC232-01:** Given repeated provider failures, when the breaker opens, then new initiations fail fast and the option is disabled.
- **AC-UC232-02:** Given both providers open, when a customer opens top-up, then bank transfer is offered with an ar/en explanation.
- **AC-UC232-03:** Given provider recovery, when the half-open probe succeeds, then instant top-ups resume automatically (BR-PAY-04).
