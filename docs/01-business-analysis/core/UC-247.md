# UC-247 — Publish the Weekly Retention Purge Report

## Header Info
- **Use Case ID:** UC-247
- **Title:** Publish the Weekly Retention Purge Report
- **Actor:** System (ACT-07) — retention report job (no interactive login)
- **Trigger:** The weekly schedule fires after seven days of purge runs
- **Priority:** P2
- **Goal:** Give admins an evidence-backed weekly view of what was purged, what guards blocked, and how old the backlog is.
- **Preconditions:** Daily purge runs wrote evidence (actor, scope, row counts, timestamp); retention classes are configured; the admin reporting surface exists (FR-018).

## Main Scenario
1. The weekly trigger aggregates evidence entries from the past week's purge runs.
2. The report computes rows purged per retention class, rows skipped by guard, and backlog age.
3. Guard alerts are reconciled — a skip is reported as a skip, never counted as a purge.
4. The report is published to the admin analytics surface (dashboards and export lanes of B11).
5. Each figure links back to its purge-run evidence so the numbers are auditable.
6. The published report becomes the record for that week; prior weeks are immutable.

## Alternative Scenarios
- **A1 — Week with no purges:** a zero-count report is still published — silence is not mistaken for success.
- **A2 — A guard blocked deletions:** the blocked classes appear in the skipped-by-guard column with their alert counts.
- **A3 — Admin needs a copy:** the report is exported as CSV/XLSX through the analytics export lane.

## Exception Scenarios
- **E1 — Evidence missing for a run:** the gap is reported as incomplete rather than assumed zero — no false clean run.
- **E2 — Report job fails:** retries then dead-letter with an alert; prior weeks' reports are unaffected (BR-PLT-02).
- **E3 — Backlog is old:** the backlog-age column highlights it; the operational path for that is alerting, not a silent report (NFR-014).

## Postconditions
- Success: a weekly report exists with per-class purged counts, skips and backlog age — every figure traceable to run evidence.
- Failure: no partial report is published; the previous report remains the latest complete one.

## Business Rules Applied
- BR-PLT-02 — report job retry/DLQ discipline only; report content is evidence aggregation under FR-018 (no BR governs report publication).

## Related Requirements
- FR-018 (Analytics & Reporting)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — reads purge evidence and writes the report; admins (ACT-04/ACT-05) are the readers.
- **Data involved:** purge-run evidence entries, class-level counts, guard alerts, backlog metrics, report rows.
- **External dependencies:** BullMQ report/export queues; analytics dashboards; alert history.

## Acceptance Criteria
- **AC-UC247-01:** Given purge evidence from the week, when the report runs, then per-class purged and skipped-by-guard counts match the evidence (FR-018).
- **AC-UC247-02:** Given a class blocked by a guard, when the report runs, then it appears as skipped, not as purged (NFR-019).
- **AC-UC247-03:** Given a zero-purge week, when the schedule fires, then a zero-count report is still published.
- **AC-UC247-04:** Given a failing report job, when retries exhaust, then it dead-letters with an alert (BR-PLT-02).
