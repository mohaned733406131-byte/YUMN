# UC-050 — Recompute Store Ratings Incrementally

## Header Info
- **Use Case ID:** UC-050
- **Title:** Recompute Store Ratings Incrementally
- **Actor:** System (ACT-07) — rating recompute job (no interactive login)
- **Trigger:** A review is created, edited, or hidden; the review service enqueues `b02.review.rating-recompute` (FR-006)
- **Priority:** P2
- **Goal:** Keep each store's displayed rating current by recomputing it incrementally from visible product ratings instead of rescanning the whole catalog.
- **Preconditions:** Reviews exist with integer ratings 1–5; only visible reviews count (BR-REV-05).

## Main Scenario
1. A review mutation event (create/edit/hide) enqueues a job on `b02.review.rating-recompute` carrying the product and store IDs only (FR-006).
2. The consumer reads the current reviews for the affected products from the database — the payload never carries aggregates (FR-006).
3. It computes the store rating as the average of visible product ratings with the review count shown (BR-REV-05).
4. The updated rating and count are written to the store's rating fields (FR-006).
5. Storefront and product views pick up the new value on their next read (FR-006).
6. The job records completion; an identical enqueued job is deduplicated by job ID (FR-006).

## Alternative Scenarios
- **A1 — Review hidden by moderation:** the hidden review drops out of the visible set → the average is recomputed without it (BR-REV-05).
- **A2 — Burst of reviews:** several events for one store coalesce — each run re-reads current state, so the last write reflects all reviews (FR-006).
- **A3 — Store with zero visible ratings:** no visible ratings remain → the rating is cleared and no rating is displayed (BR-REV-05).

## Exception Scenarios
- **E1 — Job fails:** retried with backoff and alerted if it keeps failing; the store keeps serving the last computed rating until the retry succeeds (FR-006).
- **E2 — Stale payload applied late:** the consumer reads fresh DB state rather than trusting the payload, so an out-of-order job still converges to the correct value (FR-006).
- **E3 — Concurrent edits to the same review:** last write wins in the DB; the follow-up recompute event recalculates from that final state (FR-006).

## Postconditions
- Success: store rating fields equal the average of currently visible product ratings, with the correct review count.
- Failure: store rating unchanged (stale but consistent); the job retries; no review data is altered.

## Business Rules Applied
- BR-REV-05

## Related Requirements
- FR-006 (Reviews & Ratings)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); vendors and customers cannot write rating aggregates — only the job does.
- **Data involved:** reviews, product rating fields, store rating aggregates.
- **External dependencies:** BullMQ/Redis queue `b02.review.rating-recompute` (C-20); read models serving storefront.

## Acceptance Criteria
- **AC-UC050-01:** Given a store with visible product ratings 5 and 3, when the job runs, then the store rating is 4 with the review count shown (BR-REV-05).
- **AC-UC050-02:** Given a 1-star review hidden by moderation, when the job runs, then the store rating excludes it (BR-REV-05).
- **AC-UC050-03:** Given a failed recompute, when retried, then the store rating converges to the value derived from current reviews (FR-006).
