# UC-230 — Append the State-History Backstop Row on Every Order Transition

## Header Info
- **Use Case ID:** UC-230
- **Title:** Append the State-History Backstop Row on Every Order Transition
- **Actor:** System (ACT-07) — database trigger + history writer (no interactive login)
- **Trigger:** An order or sub-order state column is updated inside a transaction
- **Priority:** P1
- **Goal:** Make it impossible to change state without leaving a history row — the app writes it, the database backstops it.
- **Preconditions:** Guarded transition updates `b06.order` / `b06.sub_order` state in a transaction; history table append-only (BR-ORD-03); exactly 17 states (C-09).

## Main Scenario
1. The application performs a guarded state transition and writes its enriched history row (actor, timestamp, reason) in the same transaction.
2. The `AFTER UPDATE OF state` trigger fires for the order or sub-order.
3. The trigger checks whether a history row for this transition already exists (application rows are marked in metadata).
4. App row present → the trigger does nothing (idempotent); app row missing → it appends a backstop row with from-state, to-state, actor and reason.
5. Either way the invariant holds: no state change commits without a history row (BR-ORD-03).
6. `UPDATE` and `DELETE` on the history table are revoked — states and history are never overwritten.

## Alternative Scenarios
- **A1 — Normal path:** the application row is present, the trigger no-ops; one enriched row remains.
- **A2 — Transition path that forgot its row:** the trigger supplies the backstop row before commit.
- **A3 — Timeline reads:** consumers read the append-only partition; nothing can mutate a past row (BR-ORD-03).

## Exception Scenarios
- **E1 — Attempted UPDATE/DELETE on history:** denied by revoked privileges; the write never lands.
- **E2 — Trigger or history write fails:** the transition transaction fails; state only changes together with its history — never without it.
- **E3 — Attempt to write an 18th state:** impossible — the state enum is constrained to the 17 canonical values (C-09).

## Postconditions
- Success: every committed transition has at least one history row; history is immutable.
- Failure: no state change without history; the canonical state set is untouched (C-09).

## Business Rules Applied
- BR-ORD-03

## Related Requirements
- FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** application roles hold read/insert on history only; DDL and mutation rights belong to the migration role alone.
- **Data involved:** order/sub-order state columns, `order_status_history` rows, actor/reason metadata.
- **External dependencies:** PostgreSQL triggers and revoked table privileges.

## Acceptance Criteria
- **AC-UC230-01:** Given a transition whose application row is missing, when the update commits, then the trigger appends a backstop history row (BR-ORD-03).
- **AC-UC230-02:** Given a normal transition, when it commits, then exactly one enriched history row exists and the trigger adds nothing.
- **AC-UC230-03:** Given a request to edit a history row, when issued by an application role, then it is denied.
