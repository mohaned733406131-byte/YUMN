# UC-040 — Send OTP with Provider Failover

## Header Info
- **Use Case ID:** UC-040
- **Title:** Send OTP with Provider Failover
- **Actor:** System (ACT-07) — notification pipeline (no interactive login)
- **Trigger:** Any flow requests an OTP (UC-002 register, UC-003 login-OTP, UC-004 password reset, UC-014 guest verification)
- **Priority:** P0
- **Goal:** Deliver a 6-digit OTP reliably via SMS with automatic WhatsApp failover, respecting resend limits and mandatory security delivery.
- **Preconditions:** OTP requested for a valid phone (`^7[0-9]{8}$`, BR-AUTH-01); request within resend limits (60 s cooldown, max 3 per 10 min, BR-AUTH-03).

## Main Scenario
1. Auth service generates a 6-digit OTP, stores it hashed with 5-minute expiry, attempt counter = 3 (BR-AUTH-03), and requests delivery.
2. System renders the template in the user's locale — Arabic default, English parity (BR-NTF-04, C-24) — and sends via **primary SMS provider** (INT-REQ-003).
3. System waits for the provider response/delivery receipt; on success logs the receipt and marks the OTP `SENT` (delivery receipts logged, INT-REQ-003).
4. The message is a security notification: it **cannot be opted out of by the user** (BR-NTF-02); no email channel exists (BR-NTF-01).
5. User receives the code and completes verification in the requesting flow (3 attempts max, 5-min expiry, BR-AUTH-03).

## Alternative Scenarios
- **A1 — Primary provider timeout/failure:** No ack or error within the timeout → **automatic failover to WhatsApp Business** template message (BR-NTF-03, INT-REQ-004); outcome logged.
- **A2 — Both providers fail:** Attempt retried with backoff (BR-PLT-02); if still failing, the requesting flow reports delivery failure after cooldown — user may retry within resend limits (BR-AUTH-03).
- **A3 — Resend requested:** Within 60 s → cooldown suppresses sending; counters unchanged (BR-AUTH-03).

## Exception Scenarios
- **E1 — Template not approved (WhatsApp):** Template rejection → logged and alerted; fallback stays on SMS; no OTP silently lost (INT-REQ-004 approval-gated).
- **E2 — Message queue outage:** BullMQ down → requests retried; dead-letter alert on exhaustion (BR-PLT-01, BR-PLT-02); auth flow reports temporary failure (graceful degradation NFR-007).
- **E3 — Abuse / SMS pumping:** Per-IP/per-user rate limits on OTP endpoints (SEC-REQ-009) plus resend caps (BR-AUTH-03) stop flooding; suspicious bursts alerted.

## Postconditions
- OTP delivered through at least one channel (or explicit failure reported); delivery attempt logged with channel used.
- OTP state machine unchanged until user verification; no account/session change from delivery itself.
- Security notification obligations satisfied (BR-NTF-02).

## Business Rules Applied
- BR-AUTH-01, BR-AUTH-03, BR-NTF-01, BR-NTF-02, BR-NTF-03, BR-NTF-04, BR-PLT-01, BR-PLT-02, BR-PLT-05

## Related Requirements
- FR-001 (Identity, Authentication & Session Management), FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** System service identity (ACT-07), write-only in its scope; no human login (DOC-OVR-007).
- **Data involved:** OTP records (hashed code, expiry, attempts, channel), delivery receipts, rate-limit counters.
- **External dependencies:** Primary SMS provider + secondary provider, WhatsApp Business API (INT-REQ-003, INT-REQ-004); BullMQ queues (C-20).

## Acceptance Criteria
- **AC-UC040-01:** Given a primary SMS timeout, when failover triggers, then WhatsApp delivers the OTP and the channel is logged (BR-NTF-03).
- **AC-UC040-02:** Given a user who disabled marketing messages, when an OTP is requested, then it is still delivered (BR-NTF-02).
- **AC-UC040-03:** Given a resend inside 60 seconds, when requested, then no message is sent and cooldown is enforced (BR-AUTH-03).
