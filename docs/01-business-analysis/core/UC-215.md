# UC-215 — Lift the Account Lock Automatically After the 15-Minute Timeout

## Header Info
- **Use Case ID:** UC-215
- **Title:** Lift the Account Lock Automatically After the 15-Minute Timeout
- **Actor:** System (ACT-07) — auth lockout service (no interactive login)
- **Trigger:** A login attempt arrives for an account whose 15-minute lock window has or has not yet elapsed
- **Priority:** P1
- **Goal:** Release lockouts by time alone — never by operator action — while the lock holds for the full window and every lock event stays logged.
- **Preconditions:** Lock applied at 5 consecutive failures with 15-minute expiry; lock state held with its expiry timestamp; no manual unlock exists (BR-AUTH-04).

## Main Scenario
1. The fifth consecutive failure locks the account for 15 minutes and the lock event is logged (BR-AUTH-04).
2. Lock state is read with its expiry; support tooling can see remaining time but cannot unlock.
3. A login attempt inside the window → `ACCOUNT_LOCKED` with remaining seconds; credentials are not evaluated.
4. A correct password inside the window is still rejected for the whole window.
5. When the 15 minutes elapse the lock clears automatically — the expiry passes, no operator action.
6. The next attempt is evaluated normally; success resets the failure counter and issues the session (C-08).

## Alternative Scenarios
- **A1 — Failures below five:** no lock is applied; counters keep their normal window.
- **A2 — Lock expires and login succeeds:** the account is usable immediately; the earlier lock event remains in the log (BR-AUTH-04).
- **A3 — Support lookup:** staff see lock state and remaining attempts to assist the user without unlocking manually.

## Exception Scenarios
- **E1 — Counter store outage:** authentication fails closed with an explicit error rather than silently unlocking (BR-AUTH-04 stays enforced).
- **E2 — Repeated offenders:** each new run of five failures re-applies a fresh 15-minute lock; lock events accumulate for review.
- **E3 — Attempt landing at expiry:** evaluated against the expiry timestamp — after the window it proceeds normally, before it returns the lock error.

## Postconditions
- Success: the account is usable again after exactly 15 minutes with no operator involvement; lock events remain logged.
- Failure: the account stays locked until the timeout; no manual override ever exists.

## Business Rules Applied
- BR-AUTH-04

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — reads and expires its own lock state; support roles get read-only visibility.
- **Data involved:** failure counters, lock state with expiry, lock events (audit-relevant).
- **External dependencies:** Redis lock/counter store.

## Acceptance Criteria
- **AC-UC215-01:** Given a locked account, when login is attempted before 15 minutes, then `ACCOUNT_LOCKED` with remaining time is returned and no session issued (BR-AUTH-04).
- **AC-UC215-02:** Given the 15 minutes have elapsed, when login is attempted with correct credentials, then it succeeds and the failure counter is reset.
- **AC-UC215-03:** Given any lock, when it is inspected, then a corresponding lock event exists in the log (BR-AUTH-04).
