# UC-226 — Reject Order Totals Outside the 500–5,000,000 YER Bounds

## Header Info
- **Use Case ID:** UC-226
- **Title:** Reject Order Totals Outside the 500–5,000,000 YER Bounds
- **Actor:** System (ACT-07) — checkout validation (no interactive login)
- **Trigger:** Checkout computes a server-side order total and validates it against the platform bounds
- **Priority:** P0
- **Goal:** Refuse any order whose total falls outside 500–5,000,000 YER before an order row or ledger movement exists.
- **Preconditions:** Totals recomputed server-side; bounds inclusive (BR-CAT-04, C-14); database CHECK mirrors the same bound.

## Main Scenario
1. Checkout computes the authoritative server-side total (items − discount + VAT + shipping).
2. The total is validated: ≥ 500 and ≤ 5,000,000 YER (BR-CAT-04).
3. Outside bounds → rejected at validation with a boundary-specific message; no order row, no payment, no ledger movement.
4. Inside bounds → validation passes and checkout proceeds to payment and creation.
5. The same bound exists as a database CHECK, so a bypassed application layer still cannot persist an out-of-range total (C-14).
6. The cart is preserved so the buyer can adjust quantities and retry.

## Alternative Scenarios
- **A1 — Exact boundaries:** 500 and 5,000,000 YER are accepted (inclusive); 499 and 5,000,001 YER are rejected.
- **A2 — Coupon moves the total:** totals are recalculated server-side; a total now under the floor is rejected again at confirm.
- **A3 — Client-side bypass attempt:** server validation and the CHECK both reject; the UI is never the boundary.

## Exception Scenarios
- **E1 — Price change during checkout:** recompute then revalidate — the bound applies to the final computed total.
- **E2 — Concurrent duplicate confirm:** idempotency governs replays; the bound is validated before any order row exists.
- **E3 — Invalid intermediate total (NaN/float):** amounts are integer YER end-to-end; a non-integer total cannot pass validation (BR-PAY-10).

## Postconditions
- Success: only in-bounds orders exist; each carries a validated integer-YER total.
- Failure: no order row, no ledger entry — only the cart's existing reservation is unaffected by the rejection.

## Business Rules Applied
- BR-CAT-04

## Related Requirements
- FR-011 (Checkout & Order Placement)

## Permissions / Data / External Dependencies
- **Permissions:** Any authenticated buyer for their own checkout; validation runs server-side regardless of role.
- **Data involved:** computed order totals, order rows (only on success), ledger entries (only on success), cart/reservation.
- **External dependencies:** PostgreSQL CHECK constraint as second enforcement layer.

## Acceptance Criteria
- **AC-UC226-01:** Given a computed total of 499 YER, when checkout confirms, then it is rejected and no order row exists (BR-CAT-04).
- **AC-UC226-02:** Given a computed total of 5,000,001 YER, when checkout confirms, then it is rejected with the boundary message (C-14).
- **AC-UC226-03:** Given totals of 500 and 5,000,000 YER, when submitted, then both are accepted.
