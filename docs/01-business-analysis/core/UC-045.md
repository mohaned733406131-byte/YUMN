# UC-045 — Sweep Expired Sessions and Orphaned Refresh Tokens

## Header Info
- **Use Case ID:** UC-045
- **Title:** Sweep Expired Sessions and Orphaned Refresh Tokens
- **Actor:** System (ACT-07) — background worker (no interactive login)
- **Trigger:** The repeatable sweep job `b01.auth.session.sweep` fires on its schedule
- **Priority:** P2
- **Goal:** Periodically delete expired JWT sessions and orphaned refresh-token rows so the 5-active-session limit (BR-AUTH-06) and session-family integrity (BR-AUTH-05) hold outside login.
- **Preconditions:** Session registry (Redis) reachable; sweep queue registered (`../../06-backend/core/background-processing.md` §1 register: `b01.auth.session.sweep`, producer auth service).

## Main Scenario
1. Scheduler enqueues `b01.auth.session.sweep` on its repeatable cadence; a single worker claims the job.
2. Worker scans the session registry for sessions past their token lifetime (refresh window per UC-003/UC-043) and marks them for removal.
3. Expired sessions are deleted from the registry, so any lingering access token of that session fails the per-request `sid` check and is rejected.
4. Orphaned refresh-token rows — tokens whose session family no longer exists (family revoked by UC-043 reuse handling, logout, or password reset) — are deleted so no detached lineage can ever be revived (BR-AUTH-05).
5. The registry now holds only live sessions: the 5-active-session cap (BR-AUTH-06) is evaluated against true active sessions, complementing login-time eviction (UC-003).
6. Family integrity stays intact (BR-AUTH-05): dead lineages are purged, never resurrected; live families of the same user are untouched.
7. The job logs its deletion counts; failures follow the platform's standard retry-then-dead-letter path.

## Alternative Scenarios
- **A1 — Nothing to sweep:** job completes as a no-op with zero deletions; registry unchanged.
- **A2 — Mixed live and expired sessions for one user:** only expired entries and orphaned rows go; the user's live sessions keep working.
- **A3 — Sweep overlaps a fresh login/refresh:** sessions created after the scan point survive — the sweep only removes entries already past expiry when scanned.

## Exception Scenarios
- **E1 — Registry unreachable:** the sweep aborts without deleting; request-time checks already fail closed while the registry is down (UC-043 exception path).
- **E2 — Worker crashes mid-scan:** the job is retried and re-scans current state — the sweep is idempotent, nothing is double-counted.
- **E3 — No worker picks the queue up:** sessions linger until a worker runs; correctness is preserved because expiry is still enforced per request by the auth guard.

## Postconditions
- Success: expired sessions and orphaned refresh-token rows removed; registry contains only live sessions/families — BR-AUTH-05 and BR-AUTH-06 hold outside login.
- Failure: registry unchanged; per-request enforcement remains active, so no stale session gains access.

## Business Rules Applied
- BR-AUTH-05

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)
- **Related:** complementary to UC-043 (rotation / reuse-revoke) and UC-003 (login-time eviction) — this is the background sweep only; it neither rotates tokens nor evicts at login.

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — no interactive login; the worker writes only session and refresh-token records.
- **Data involved:** session registry entries, refresh-token rows, sweep job log with deletion counts.
- **External dependencies:** Redis session store; BullMQ queue `b01.auth.session.sweep` (`../../06-backend/core/background-processing.md` §1).

## Acceptance Criteria
- **AC-UC045-01:** Given sessions past their token lifetime, when the sweep runs, then they are removed from the registry.
- **AC-UC045-02:** Given a refresh-token row whose session family is gone, when swept, then the row is deleted (BR-AUTH-05).
- **AC-UC045-03:** Given a user with live and expired sessions, when swept, then only the expired entries are removed and the 5-active-session cap counts true live sessions (BR-AUTH-06).
- **AC-UC045-04:** Given an active session created after the scan started, when the sweep finishes, then that session remains valid.
