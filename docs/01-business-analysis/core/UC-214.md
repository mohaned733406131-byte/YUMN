# UC-214 — Expire OTP Challenges After Five Minutes and Reset Attempt Counters

## Header Info
- **Use Case ID:** UC-214
- **Title:** Expire OTP Challenges After Five Minutes and Reset Attempt Counters
- **Actor:** System (ACT-07) — OTP service (no interactive login)
- **Trigger:** An OTP challenge's five-minute lifetime elapses, or a verification attempt arrives after it
- **Priority:** P1
- **Goal:** Make every OTP single-use and short-lived: expired codes can never verify, and each fresh challenge starts with a full attempt counter.
- **Preconditions:** OTP stored in Redis with a 5-minute TTL and attempt counter 3 (BR-AUTH-03); a requesting flow awaits verification.

## Main Scenario
1. OTP issued → stored under its context key with TTL 300 s, attempt counter 3, resend counters attached (BR-AUTH-03).
2. Five minutes elapse → Redis expires the key; the code becomes unverifiable.
3. A verification attempt after expiry → `OTP_EXPIRED`; no session, reset token or step-up is issued.
4. Expiry clears the attempt counters with the key; a fresh OTP request is allowed within the 60 s cooldown and 3-resends-per-10-minute limits (BR-AUTH-03).
5. The new challenge overwrites the context key with a fresh counter set; the previous code stays permanently unusable.
6. Before expiry each verification decrements the counter atomically; the third wrong code deletes the key (`OTP_MAX_ATTEMPTS`).

## Alternative Scenarios
- **A1 — Verified in window:** the correct code consumes the key and the flow continues; counters disappear with it.
- **A2 — Resend inside cooldown:** rejected with the remaining cooldown — expiry is never a way around resend limits (BR-AUTH-03).
- **A3 — Abandoned challenge:** the key simply expires with no residue and no user action required (Redis is authoritative and write-through).

## Exception Scenarios
- **E1 — Redis unavailable:** authentication endpoints return an explicit dependency error; codes are never accepted without live counters — fail closed.
- **E2 — Expiry extended by reads:** impossible — the TTL is set once at write and reads never refresh it.
- **E3 — Wrong codes until expiry:** counters reach zero → key deleted at the third attempt → `OTP_MAX_ATTEMPTS`; expiry then only concerns a fresh challenge (BR-AUTH-03).

## Postconditions
- Success: within the window the code verifies exactly once; after five minutes it can never verify (BR-AUTH-03).
- Failure: no session or token is issued for an expired code; counters reset with the next challenge.

## Business Rules Applied
- BR-AUTH-03

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — owns OTP records; verification is invoked by the requesting public flow.
- **Data involved:** OTP keys, attempt counters, resend counters, verification outcome events.
- **External dependencies:** Redis (TTL-native authoritative store for OTP state).

## Acceptance Criteria
- **AC-UC214-01:** Given an OTP older than five minutes, when it is submitted, then it is rejected as expired and no token is issued (BR-AUTH-03).
- **AC-UC214-02:** Given an expired challenge, when a new OTP is requested within limits, then a fresh code with a full attempt counter is issued (BR-AUTH-03).
- **AC-UC214-03:** Given a live challenge, when three wrong codes are submitted, then the key is deleted and `OTP_MAX_ATTEMPTS` returned (BR-AUTH-03).
