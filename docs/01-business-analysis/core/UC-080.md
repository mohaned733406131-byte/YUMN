# UC-080 — Aggregate Dashboard Analytics Rollups

## Header Info
- **Use Case ID:** UC-080
- **Title:** Aggregate Dashboard Analytics Rollups
- **Actor:** System (ACT-07) — analytics aggregator (no interactive login)
- **Trigger:** Scheduled aggregation cycle (`b11.analytics.rollup`)
- **Priority:** P1
- **Goal:** Maintain pre-aggregated metric snapshots so dashboards answer fast without scanning transactional tables live.
- **Preconditions:** Source data in orders/finance/delivery tables; dashboards (admin, vendor) consume rollups; queue running.

## Main Scenario
1. The scheduler enqueues `b11.analytics.rollup` on its cadence, following the platform `{block}.{entity}.{action}` naming (BR-PLT-01).
2. The worker aggregates sales, finance, and operations metrics for each scope — platform-wide for admins, store-scoped for vendors.
3. Results are written to rollup read tables/structures serving dashboard queries (UC-084 admin dashboard, UC-199 vendor dashboard).
4. Aggregates derive from append-only sources; a window may be recomputed at any time and converges to the same numbers.
5. Dashboards read only pre-aggregated values — interactive queries never hammer base tables.

## Alternative Scenarios
- **A1 — Late-arriving data (events after the window closed):** The next cycle refreshes the affected window; numbers converge with bounded lag.
- **A2 — New period first run:** The period is seeded from prior aggregates plus the current delta.
- **A3 — Recompute on demand:** Re-running a window is idempotent — same input state yields identical aggregates.

## Exception Scenarios
- **E1 — Aggregation job fails:** Retried, then dead-lettered with an alert if exhausted; dashboards keep serving the last good rollup rather than errors.
- **E2 — Rollup backlog during a spike:** Freshness degrades (stale-but-valid numbers) until the queue drains; no dashboard outage.
- **E3 — Inconsistent window detected:** The affected window is recomputed from source; aggregates are derived data, so repair never edits sources.

## Postconditions
- Rollup tables hold current aggregates for every dashboard scope.
- Dashboards serve pre-aggregated values with known freshness.
- Failed cycles leave the previous rollup intact — no half-written metrics.

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) reads base tables, writes rollups; dashboards are read-only per role scope.
- **Data involved:** Order/finance/delivery aggregates (counts, sums, rates), rollup timestamps, scope keys.
- **External dependencies:** BullMQ (`b11.analytics.rollup`); scheduled triggers; dashboard read APIs.

## Acceptance Criteria
- **AC-UC080-01:** Given the scheduled cycle, when the job runs, then it is named `b11.analytics.rollup` per the queue convention (BR-PLT-01).
- **AC-UC080-02:** Given new orders in the window, when the rollup completes, then dashboards show updated aggregates.
- **AC-UC080-03:** Given a failed aggregation cycle, when dashboards are queried, then the last good rollup is served.
- **AC-UC080-04:** Given the same window recomputed twice, when both runs finish, then the aggregate values are identical.
