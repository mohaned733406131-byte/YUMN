# UC-067 — Synchronize the Search Index on Catalog Changes

## Header Info
- **Use Case ID:** UC-067
- **Title:** Synchronize the Search Index on Catalog Changes
- **Actor:** System (ACT-07) — index worker (no interactive login)
- **Trigger:** Catalog mutation event (product create/update/publish/unpublish/soft-delete, price or stock change, category change)
- **Priority:** P1
- **Goal:** Keep the search index in sync with the catalog so search and category browse only ever return ACTIVE, visible products.
- **Preconditions:** Search index deployed; catalog change events emitted transactionally with the write; search consumers (UC-006) depend on the index.

## Main Scenario
1. A catalog write commits and emits an event; the outbox enqueues `b02.catalog.index` with the product/category identifier and operation.
2. The worker resolves the product's current state and upserts the index document (Arabic-aware text fields, price, stock, store, category path).
3. Soft-deleted or non-ACTIVE products are removed from the index — only ACTIVE products appear in search/storefront (BR-CAT-06).
4. Category changes re-index the affected subtree so browse paths and slugs match the tree.
5. Search queries (UC-006) and typeahead read the index; the index tolerates short lag but converges to catalog state after the queue drains.

## Alternative Scenarios
- **A1 — Unpublish or soft-delete:** The document is deleted from the index (BR-CAT-06); the product immediately stops appearing in search results.
- **A2 — Bulk category move:** One job re-indexes all products under the moved node instead of firing per-product jobs.
- **A3 — Duplicate events for the same product:** The worker upserts by product id — later events win, no duplicate documents.

## Exception Scenarios
- **E1 — Index job failure:** Retries with exponential backoff, then dead-letter with a depth alert (platform queue policy); queries keep serving the last consistent index — degraded freshness, never wrong visibility.
- **E2 — Index/database divergence detected:** A scheduled reconciliation triggers a full re-index of the catalog until parity is restored.
- **E3 — Index unavailable:** Catalog writes continue and events accumulate; indexing resumes when the index recovers — no catalog write is rolled back by search.

## Postconditions
- Index converges to catalog state: ACTIVE visible products present, soft-deleted/inactive ones absent (BR-CAT-06).
- Failed jobs are retried or dead-lettered with alerting; no event silently dropped.
- Search results reflect the last synchronized catalog state.

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) — reads catalog, writes index; no human login.
- **Data involved:** Product/category records, index documents, outbox events, job status.
- **External dependencies:** BullMQ (`b02.catalog.index`); search engine (Arabic stemming); PostgreSQL outbox.

## Acceptance Criteria
- **AC-UC067-01:** Given a product is soft-deleted, when its index job runs, then the document is removed and search no longer returns it (BR-CAT-06).
- **AC-UC067-02:** Given a price change commits, when `b02.catalog.index` drains, then search shows the new price.
- **AC-UC067-03:** Given the index job fails repeatedly, when retries exhaust, then it dead-letters with an alert while queries serve the last consistent index.
- **AC-UC067-04:** Given duplicate events for one product, when both are processed, then exactly one current document exists.
