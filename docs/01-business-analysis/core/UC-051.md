# UC-051 — Release Unused Wallet Authorization Holds

## Header Info
- **Use Case ID:** UC-051
- **Title:** Release Unused Wallet Authorization Holds
- **Actor:** System (ACT-07) — hold-release path of the wallet payment lifecycle (no interactive login)
- **Trigger:** A checkout session expires or is abandoned while its authorization hold is still `AUTHORIZED` (FR-013)
- **Priority:** P1
- **Goal:** Return every uncaptured authorization hold to available balance exactly once so customers are never stranded with frozen funds.
- **Preconditions:** A hold exists from `POST /wallet/payments/authorize` (hold ≤ available balance, BR-PAY-05); the order saga did not capture it.

## Main Scenario
1. The checkout session reaches its 15-minute expiry without a confirmed order (C-13 hold window).
2. The system identifies the hold as uncaptured and calls the internal release touchpoint `POST /wallet/payments/{id}/release` with a reason (FR-013).
3. The release is executed only from state `AUTHORIZED` — the state guard rejects any other status (BR-PLT-03 idempotency).
4. The held amount returns to available balance under row-level locking with an atomic balance check — balance never goes negative (BR-PAY-05).
5. The payment record moves to `RELEASED` and the customer's wallet view reflects the freed amount (FR-013).
6. The release is idempotent — replaying it is a `STATE_CONFLICT` no-op, never a double credit (BR-PLT-03).

## Alternative Scenarios
- **A1 — Order confirmed instead:** the saga captured the hold → release is not attempted; funds flow through escrow as normal (FR-013).
- **A2 — Manual release:** an operator triggers the same internal endpoint with a reason for a stuck hold; identical state guard and audit apply (FR-013).
- **A3 — Customer restarts checkout:** a new authorize creates a fresh hold; the old one still releases on its own expiry (BR-PAY-05).

## Exception Scenarios
- **E1 — Release job fails:** retried with backoff and alerted if it keeps failing; the hold stays `AUTHORIZED` until released — funds are never silently consumed (FR-013).
- **E2 — Concurrent capture and release:** both run in guarded transactions; exactly one wins — capture ⇒ release is rejected, release ⇒ capture is rejected (BR-PLT-03, BR-PAY-05).
- **E3 — Release against unknown payment:** `NOT_FOUND` returned; no balance change; the anomaly is logged (FR-013).

## Postconditions
- Success: hold `RELEASED`, available balance restored exactly once, payment history shows the release reason.
- Failure: hold remains `AUTHORIZED` with funds still held; balance unchanged; the case is retried or reported.

## Business Rules Applied
- BR-PAY-05, BR-PLT-03

## Related Requirements
- FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** internal `SYSTEM` endpoint plus admin manual trigger — never callable by customers; money movement writes are append-only (FR-013).
- **Data involved:** payment/hold records, wallet balance, ledger entries, audit entry.
- **External dependencies:** order saga (capture side), wallet service, BullMQ (C-20).

## Acceptance Criteria
- **AC-UC051-01:** Given an `AUTHORIZED` hold on an abandoned checkout, when release runs, then status is `RELEASED` and available balance rises by the held amount once (BR-PAY-05).
- **AC-UC051-02:** Given a released hold, when release is replayed, then it returns `STATE_CONFLICT` with no balance change (BR-PLT-03).
- **AC-UC051-03:** Given a captured payment, when release is attempted, then it is rejected and escrow flow is unaffected (BR-PLT-03).
- **AC-UC051-04:** Given concurrent capture and release, when both commit, then exactly one succeeds and balance stays correct (BR-PAY-05).
