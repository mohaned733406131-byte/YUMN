# UC-049 — Reconcile the Inventory Ledger Against On-Hand Stock

## Header Info
- **Use Case ID:** UC-049
- **Title:** Reconcile the Inventory Ledger Against On-Hand Stock
- **Actor:** System (ACT-07) — scheduled reconciliation job (no interactive login)
- **Trigger:** Scheduled reconciliation run over the append-only inventory ledger (FR-005)
- **Priority:** P1
- **Goal:** Detect any drift between summed inventory-ledger deltas and `qty_on_hand` per product, and flag mismatches instead of silently patching stock.
- **Preconditions:** Every mutation (reserve, consume, release, manual adjustment, cancellation restoration) has appended a ledger row (BR-INV-05).

## Main Scenario
1. The scheduled job opens a consistent read window over the inventory ledger (conceptual `b02` reconciliation job, FR-005).
2. It sums signed deltas per inventory row across all ledger events in the window (BR-INV-05).
3. It compares each sum against the recorded `qty_on_hand` change for the same window and checks the invariant `qty_on_hand ≥ qty_reserved ≥ 0` (BR-INV-05).
4. Matching rows are marked reconciled; the run writes a reconciliation result record (FR-005).
5. A mismatch is reported as a discrepancy with product, expected vs actual value and timestamp — the stock row itself is never edited to "fix" it (BR-INV-05).
6. The result is retained for audit so operators can trace the offending event chain (FR-005).

## Alternative Scenarios
- **A1 — Clean run:** every row matches → result `BALANCED`; no operator action (BR-INV-05).
- **A2 — Manual adjustment in window:** vendor adjustment has a ledger row of its own → it participates in the sum and stays balanced (BR-INV-05).
- **A3 — Window with only TTL releases:** `RELEASE_TLP` events sum against quantity changes → balanced (BR-INV-05).

## Exception Scenarios
- **E1 — Mismatch found:** discrepancy recorded and flagged for investigation; corrections are appended as new ledger rows, never edits (BR-INV-05).
- **E2 — Job fails mid-run:** the run is retried with backoff and alerted if it keeps failing; partial results are discarded (FR-005).
- **E3 — Ledger gap (missing row):** the sum diverges → reported as a missing-event discrepancy, pointing at the mutation window for review (BR-INV-05).

## Postconditions
- Success: a reconciliation result exists for the window — `BALANCED` or `MISMATCH` with details; stock rows are untouched by the job.
- Failure: no trusted result for the window; the job retries; no stock data changed either way.

## Business Rules Applied
- BR-INV-05

## Related Requirements
- FR-005 (Inventory Management)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); the job appends result rows only — it has no stock-editing permission (BR-INV-05).
- **Data involved:** inventory ledger, inventory rows, reconciliation result records.
- **External dependencies:** scheduled BullMQ job (C-20); alerting channel for mismatches.

## Acceptance Criteria
- **AC-UC049-01:** Given ledger deltas summing to +3 units for a product, when the window's `qty_on_hand` moved by +3, then the row reconciles `BALANCED` (BR-INV-05).
- **AC-UC049-02:** Given a summed delta that does not match `qty_on_hand`, when the job runs, then a `MISMATCH` discrepancy is recorded with details (BR-INV-05).
- **AC-UC049-03:** Given a detected mismatch, when the run completes, then the stock row is unchanged — correction requires a new ledger row (BR-INV-05).
