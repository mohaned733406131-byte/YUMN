# UC-233 — Serialize Concurrent Wallet Debits to Keep Balances Non-Negative

## Header Info
- **Use Case ID:** UC-233
- **Title:** Serialize Concurrent Wallet Debits to Keep Balances Non-Negative
- **Actor:** System (ACT-07) — wallet payment service (no interactive login)
- **Trigger:** Two or more debits contend on the same wallet row in the same instant
- **Priority:** P0
- **Goal:** Serialize debits on one row with an atomic balance check so a balance can never go negative under any interleaving.
- **Preconditions:** Wallet row exists; debits run in ACID transactions with row-level locking (BR-PAY-05); every balance change posts balanced ledger rows (BR-PAY-06).

## Main Scenario
1. A debit opens a transaction and takes a row-level lock on the wallet row.
2. Under the lock, the atomic check evaluates `balance ≥ amount` (BR-PAY-05).
3. Sufficient → balance decremented and balanced double-entry ledger rows posted in the same transaction (BR-PAY-06).
4. Insufficient → the debit fails; balance and ledger untouched; the caller is told to top up.
5. The lock releases; the next queued debit re-reads the updated balance — debits serialize on one row.
6. The invariant holds: the balance can never go negative under any interleaving (BR-PAY-05).

## Alternative Scenarios
- **A1 — No contention:** the lock is acquired immediately; check and post happen in one pass.
- **A2 — Mixed credits and debits:** each operation serializes on the same row; ordering never yields a negative read.
- **A3 — Concurrent duplicates:** idempotency keys short-circuit replays so a retried debit cannot double-charge (BR-PLT-03).

## Exception Scenarios
- **E1 — Lock wait timeout or deadlock:** one transaction aborts and retries; neither posts a partial ledger set.
- **E2 — Crash while holding the lock:** rollback restores the balance; no ledger rows survive without the balance change.
- **E3 — Attempted overdraft:** rejected at the check — there is no code path that writes a negative balance (BR-PAY-05).

## Postconditions
- Success: the balance is reduced atomically with balanced ledger rows.
- Failure: the balance is unchanged, no ledger rows exist, and no negative balance is ever observed.

## Business Rules Applied
- BR-PAY-05

## Related Requirements

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — wallet writes confined to the payment service; nobody edits balances directly.
- **Data involved:** wallet rows, ledger entries, payment records, idempotency keys.
- **External dependencies:** PostgreSQL row-level locking; double-entry ledger table.

## Acceptance Criteria
- **AC-UC233-01:** Given a balance of 10,000 YER and two concurrent debits of 7,000, when both run, then exactly one succeeds (BR-PAY-05).
- **AC-UC233-02:** Given a successful debit, when it commits, then balanced double-entry rows exist for the change (BR-PAY-06).
- **AC-UC233-03:** Given any interleaving, when balances are read afterward, then none is negative (BR-PAY-05).
