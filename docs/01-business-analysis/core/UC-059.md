# UC-059 — Fan Out Notifications Across Channels by Preference

## Header Info
- **Use Case ID:** UC-059
- **Title:** Fan Out Notifications Across Channels by Preference
- **Actor:** System (ACT-07) — notification fan-out pipeline (no interactive login)
- **Trigger:** A domain event occurs (OrderConfirmed, WalletCredited, OtpRequested, …) and enqueues `b10.notification.fanout` (FR-017)
- **Priority:** P0
- **Goal:** Deliver every platform notification to each recipient on the channels the platform supports and the recipient uses, exactly once per channel.
- **Preconditions:** Recipients and their locales are resolvable; the event carries an event ID — no message bodies in the queue (FR-017).

## Main Scenario
1. A domain event enqueues one fan-out job on `b10.notification.fanout` containing the event ID (FR-017).
2. The consumer resolves recipients and locale (Arabic default, English parity) (FR-017).
3. It runs the preference check per recipient and category before dispatch (FR-017).
4. In-app messages write directly to the notification inbox — always (FR-017).
5. Per-channel child jobs render the template then dispatch through the delivery lanes: SMS, WhatsApp, push — no email channel in v1 (BR-NTF-01).
6. Each child job's ID is a hash of event, recipient and channel, so retries never duplicate a message; delivery receipts are logged (FR-017).

## Alternative Scenarios
- **A1 — Push disabled for the recipient:** the push lane is skipped while SMS/WhatsApp/in-app still deliver (FR-017).
- **A2 — Locale English:** the template renders in English; Arabic remains the default for all other recipients (FR-017).
- **A3 — No push device registered:** only the applicable lanes dispatch; the in-app copy always exists (BR-NTF-01).

## Exception Scenarios
- **E1 — Channel provider fails:** the delivery lane job retries with backoff; the in-app copy is already durable meanwhile (FR-017).
- **E2 — Fan-out job crashes:** retried with backoff, then dead-letter with alert; the dedup job ID keeps re-runs idempotent (FR-017).
- **E3 — Recipient missing or deleted:** resolution yields no target → the job completes without dispatch; no message body was ever in the payload (FR-017).

## Postconditions
- Success: in-app inbox row exists per recipient; channel messages dispatched once per channel; receipts logged.
- Failure: the affected channel's send is retried or dead-lettered with alert; no duplicate messages; event data unchanged.

## Business Rules Applied
- BR-NTF-01

## Related Requirements
- FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); the pipeline writes notification rows and dispatches — it does not alter domain data.
- **Data involved:** notification events, recipient preferences, inbox rows, delivery receipts.
- **External dependencies:** SMS/WhatsApp/push providers, BullMQ/Redis queues `b10.notification.fanout` and delivery lanes (C-20).

## Acceptance Criteria
- **AC-UC059-01:** Given a domain event with two recipients, when fan-out runs, then each recipient gets an in-app row and per-channel dispatches (FR-017).
- **AC-UC059-02:** Given a retried channel job with the same event/recipient/channel, when it re-runs, then only one message is delivered (FR-017).
- **AC-UC059-03:** Given the pipeline, when any channel dispatches, then only SMS, WhatsApp, in-app, push are used — no email (BR-NTF-01).
- **AC-UC059-04:** Given a queue payload, when inspected, then it contains the event ID only — no message body (FR-017).
