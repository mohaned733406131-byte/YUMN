# UC-239 — Award a Delivery Offer to the First Courier Acceptance Only

## Header Info
- **Use Case ID:** UC-239
- **Title:** Award a Delivery Offer to the First Courier Acceptance Only
- **Actor:** System (ACT-07) — courier assignment engine (no interactive login)
- **Trigger:** An order becomes ready and the assignment job offers the delivery to couriers
- **Priority:** P0
- **Goal:** Exactly one courier owns each delivery — concurrent acceptances resolve to a single winner, never a double assignment.
- **Preconditions:** Order at READY_FOR_PICKUP; eligible couriers exist in the shipping zone (BR-SHP-04); the offer is published by `b08.shipping.assign-offer`.

## Main Scenario
1. The order is ready → `b08.shipping.assign-offer` offers the delivery to every eligible courier in the zone (BR-SHP-04).
2. Offers sit pending; each courier sees them in their own delivery scope.
3. Two couriers accept simultaneously → the acceptance goes through optimistic locking on the assignment record (BR-SHP-04).
4. The first accept commits: the delivery is assigned, and the offer is withdrawn from every other courier.
5. The second acceptance finds the offer taken → rejected as "no longer available"; no assignment row is written for it.
6. The assignment lands on the delivery timeline and pending offers are closed.

## Alternative Scenarios
- **A1 — Single courier accepts:** straightforward award; no contention, one assignment row.
- **A2 — Acceptance after the award:** any later acceptance of the same offer is rejected as unavailable; the courier continues with their other offers.
- **A3 — Nobody accepts yet:** the offer stays open to eligible same-zone couriers until one accepts (BR-SHP-04).

## Exception Scenarios
- **E1 — Lock contention at award:** the losing write is rejected, never partially applied — exactly one assignment exists (BR-SHP-04).
- **E2 — Assignment job crashes:** the re-run reads current assignment state and skips already-awarded deliveries — never a second award.
- **E3 — Acceptance races the withdrawal:** the withdrawal check wins → the acceptance is rejected; no half-assigned state survives (BR-SHP-04).

## Postconditions
- Success: exactly one courier is assigned; all other offers are closed; no second assignment row exists.
- Failure: no assignment is written — the delivery returns to pending offers with its zone eligibility intact.

## Business Rules Applied
- BR-SHP-04

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — writes assignment records; the acceptance itself belongs to the courier (ACT-03, own deliveries).
- **Data involved:** delivery offers, assignment row, offer state, delivery timeline entry.
- **External dependencies:** BullMQ `b08.shipping.assign-offer` queue; courier app (acceptance surface).

## Acceptance Criteria
- **AC-UC239-01:** Given two concurrent acceptances of one offer, when both are processed, then exactly one assignment exists (BR-SHP-04).
- **AC-UC239-02:** Given the losing courier, when their acceptance is processed, then it is rejected as no longer available and no assignment row is written (BR-SHP-04).
- **AC-UC239-03:** Given an offer, when it is published, then only eligible couriers of the same zone receive it (BR-SHP-04).
