# UC-228 — Auto-Accept PLACED Orders for Stores With Auto-Accept Enabled

## Header Info
- **Use Case ID:** UC-228
- **Title:** Auto-Accept PLACED Orders for Stores With Auto-Accept Enabled
- **Actor:** System (ACT-07) — order auto-accept job (no interactive login)
- **Trigger:** A vendor sub-order enters `PLACED` for a store with auto-accept enabled
- **Priority:** P2
- **Goal:** Confirm eligible orders without waiting for a vendor click, using the System actor on the canonical transition.
- **Preconditions:** Sub-order in `PLACED` within the 17-state machine (BR-ORD-01, C-09); store auto-accept setting on and platform gate on; vendor KYC approved, store active.

## Main Scenario
1. Order placement leaves the vendor sub-order in `PLACED` (BR-ORD-01, C-09).
2. The auto-accept check runs: store setting on, platform gate on, vendor KYC approved and store active.
3. All conditions hold → transition `PLACED → CONFIRMED` executed by the System actor (auto-accept config).
4. The transition is written append-only to status history with actor System and a reason (BR-ORD-03).
5. Buyer and vendor see the confirmation on the order timeline as with a manual accept.
6. Conditions not met → the sub-order waits for the vendor's manual acceptance; nothing auto-fires.

## Alternative Scenarios
- **A1 — Setting off:** no auto-accept; the vendor accepts manually and the flow rejoins the normal lifecycle.
- **A2 — Store suspended or KYC not approved:** auto-accept is skipped — an ineligible store never confirms itself (BR-VND-01, BR-VND-04).
- **A3 — Vendor accepts simultaneously:** optimistic locking serializes; one transition commits and the loser gets `409` — never two rows for one move.

## Exception Scenarios
- **E1 — Job failure:** the sub-order remains `PLACED`; retries run with backoff then dead-letter alert (BR-PLT-02); the vendor can still accept manually.
- **E2 — Invalid target state:** the transition guard refuses any move outside the canonical table; no 18th state can be produced (C-09).
- **E3 — Setting toggled mid-flight:** the check re-reads the setting at execution; a just-disabled store is not auto-accepted.

## Postconditions
- Success: eligible sub-orders are `CONFIRMED` with an append-only history row (actor System).
- Failure: nothing changes; sub-orders stay `PLACED` and no history row is written.

## Business Rules Applied
- BR-ORD-01

## Related Requirements
- FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** automated order-state action permitted to System (ACT-07); no human impersonation — actor recorded as System.
- **Data involved:** sub-order state, store settings, KYC/store status, order status history.
- **External dependencies:** BullMQ job queue; store-settings lookup.

## Acceptance Criteria
- **AC-UC228-01:** Given a store with auto-accept enabled and approved KYC, when a new order arrives, then the sub-order moves `PLACED → CONFIRMED` (BR-ORD-01).
- **AC-UC228-02:** Given the transition, when it commits, then history carries actor System with a reason (BR-ORD-03).
- **AC-UC228-03:** Given auto-accept disabled, when an order arrives, then the sub-order stays `PLACED` until the vendor accepts.
