# UC-236 — Post Ledger Corrections as Compensating Entries Only

## Header Info
- **Use Case ID:** UC-236
- **Title:** Post Ledger Corrections as Compensating Entries Only
- **Actor:** System (ACT-07) — ledger service (no interactive login)
- **Trigger:** An erroneous or disputed ledger posting requires correction
- **Priority:** P1
- **Goal:** Correct money history without ever rewriting it — reversal is a new balanced pair that references the original.
- **Preconditions:** Ledger is append-only for application roles; every balance change posts balanced debit+credit rows (BR-PAY-06); corrections are privileged money actions.

## Main Scenario
1. A discrepancy is detected (reconciliation or manual review) requiring correction of a posted entry.
2. The system never updates or deletes the original row — application roles hold read/insert rights on the ledger only.
3. A compensating pair is posted: debit and credit referencing the original transaction and reversing its effect (BR-PAY-06).
4. The pair balances on its own; the sum of all ledger entries remains zero.
5. The original row stays byte-identical, preserving the audit trail of what happened.
6. The correction is recorded as a privileged money action with an audit entry.

## Alternative Scenarios
- **A1 — Refund or commission reversal:** the same compensating pattern applies — effects are reversed, never edited.
- **A2 — Rounding adjustment:** residuals post to the platform rounding account as ordinary entries (BR-FIN-05).
- **A3 — Read path:** statements and reconciliation read the original plus its compensations — history is complete.

## Exception Scenarios
- **E1 — Attempted UPDATE/DELETE by an application role:** denied by revoked privileges; the correction must be a new posting.
- **E2 — Compensating pair itself unbalanced:** rejected at posting — balanced double-entry is enforced (BR-PAY-06).
- **E3 — Duplicate correction attempt:** idempotency on money operations prevents a second reversal for the same reference (BR-PLT-03).

## Postconditions
- Success: the net effect is corrected with both original and compensating rows intact; the ledger still balances.
- Failure: no row was mutated and no unbalanced state exists.

## Business Rules Applied
- BR-PAY-06

## Related Requirements
- FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** privileged money path only — application roles cannot mutate ledger rows; DDL belongs to the migration role.
- **Data involved:** ledger entries (originals + compensating pairs), references to source transactions, audit entries.
- **External dependencies:** PostgreSQL revoked UPDATE/DELETE privileges; daily reconciliation as the detector.

## Acceptance Criteria
- **AC-UC236-01:** Given an erroneous posting, when it is corrected, then the original row is byte-identical and a compensating pair references it (BR-PAY-06).
- **AC-UC236-02:** Given the correction, when it posts, then the sum of ledger entries remains zero.
- **AC-UC236-03:** Given an application role, when it tries to update a ledger row, then the operation is denied.
