# UC-220 — Delete Superseded KYC Document Sets When a Resubmission Is Accepted

## Header Info
- **Use Case ID:** UC-220
- **Title:** Delete Superseded KYC Document Sets When a Resubmission Is Accepted
- **Actor:** System (ACT-07) — retention job (no interactive login)
- **Trigger:** An admin accepts a vendor's resubmitted KYC set, making the previous set superseded
- **Priority:** P2
- **Goal:** Keep exactly one active KYC set — superseded document bytes and metadata are deleted at acceptance, never before.
- **Preconditions:** A prior set was rejected and resubmission allowed (BR-VND-03); acceptance decision recorded within the 48-hour SLA (BR-VND-03); object store reachable.

## Main Scenario
1. The vendor resubmits KYC documents after a rejection (resubmission is allowed, BR-VND-03).
2. The admin reviews and accepts the new set — decision recorded inside the 48-hour SLA (BR-VND-03).
3. On acceptance the previous set is marked superseded; exactly one active set remains.
4. Superseded objects are deleted from the store and their metadata rows purged in the same run.
5. The decision and the purge are written to the append-only audit trail — workflow history lives there.
6. The accepted set continues under the KYC retention schedule (five years after account closure).

## Alternative Scenarios
- **A1 — First submission:** no prior set → nothing to delete; acceptance simply activates the set.
- **A2 — More documents requested:** the case returns to submitted state; no deletion happens until a decision accepts a set.
- **A3 — Rejection again:** the rejected set becomes superseded at the next acceptance — not at rejection time.

## Exception Scenarios
- **E1 — Object delete fails:** retried; the superseded set is unusable for review regardless, and repeated failures alert operations (BR-PLT-02).
- **E2 — Metadata purge fails after object delete:** the job retries; the active set and decision are unaffected either way.
- **E3 — Acceptance transaction fails:** nothing is marked superseded and nothing is deleted — the active set is never left empty.

## Postconditions
- Success: exactly one active KYC set exists; superseded bytes and metadata are gone; the decision is audited.
- Failure: no deletion occurs; the current active set is untouched.

## Business Rules Applied
- BR-VND-03

## Related Requirements
- FR-007 (Vendor Onboarding & KYC)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — deletes only sets marked superseded by an admin decision; admin owns the acceptance itself.
- **Data involved:** KYC document objects, KYC metadata rows, decision record, audit entry.
- **External dependencies:** MinIO object store (KYC documents); audit pipeline.

## Acceptance Criteria
- **AC-UC220-01:** Given a rejected set and an accepted resubmission, when acceptance commits, then the superseded objects are deleted (BR-VND-03).
- **AC-UC220-02:** Given an accepted KYC set, when the run completes, then exactly one active set remains.
- **AC-UC220-03:** Given the acceptance, when it completes, then an audit entry records the decision.
