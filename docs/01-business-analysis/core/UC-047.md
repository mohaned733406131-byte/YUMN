# UC-047 — Commit Stock Reservations on Payment Success

## Header Info
- **Use Case ID:** UC-047
- **Title:** Commit Stock Reservations on Payment Success
- **Actor:** System (ACT-07) — checkout saga stock leg (no interactive login)
- **Trigger:** Wallet payment capture succeeds during order creation (FR-005)
- **Priority:** P0
- **Goal:** Convert each held reservation into a permanent stock deduction atomically when payment succeeds, so stock is never oversold and never leaked.
- **Preconditions:** Reservations exist in `HELD` state for the cart lines; payment capture runs inside the order-creation saga with an idempotency key (BR-PLT-03).

## Main Scenario
1. Payment capture succeeds inside the checkout saga (conceptual `POST /wallet/payments/{id}/capture`).
2. In the same ACID transaction the system flips each matching reservation `HELD → CONSUMED` and decrements `qty_on_hand` by the reserved quantity (BR-INV-01 reserve→commit).
3. The commit is keyed by idempotency so a replayed capture never deducts twice (BR-PLT-03).
4. An append-only inventory ledger row records the consumption with actor, reason and delta (BR-INV-01).
5. The order advances in the saga; stock availability views and any storefront caches refresh from committed state (FR-005).
6. A later TTL sweep skips the row because it is no longer `HELD` (BR-INV-01).

## Alternative Scenarios
- **A1 — Payment pending:** capture not yet confirmed → reservations stay `HELD` and the 15-minute countdown continues (BR-INV-01).
- **A2 — Multi-vendor cart:** one sub-order per vendor → each vendor's lines commit independently within the saga (BR-INV-01).
- **A3 — Capture arrives near expiry:** commit wins the race inside its transaction; the sweeper's `status = HELD` guard skips the consumed row (BR-INV-01).

## Exception Scenarios
- **E1 — Stock conflict at commit:** the invariant would break → the transaction rolls back, the saga reports a stock conflict, no order row is created (BR-INV-01, BR-PLT-03).
- **E2 — Saga leg fails after commit:** the saga compensating path restores stock by releasing the committed reservation — the reserve→commit/release lifecycle always terminates (BR-INV-01).
- **E3 — Duplicate capture event:** same idempotency key → second execution no-ops; exactly one deduction and one ledger row exist (BR-PLT-03, BR-INV-01).

## Postconditions
- Success: reservations `CONSUMED`, `qty_on_hand` permanently reduced, ledger rows appended, order creation continues.
- Failure: no reservation or quantity change; reservations remain `HELD` (and may expire via UC-046); no partial deduction.

## Business Rules Applied
- BR-INV-01, BR-PLT-03

## Related Requirements
- FR-005 (Inventory Management)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); stock commits are never triggered directly by a client call — only through the payment saga.
- **Data involved:** `stock_reservation` rows, inventory quantities, inventory ledger, payment/capture record.
- **External dependencies:** wallet capture service, checkout saga coordinator, BullMQ (C-20).

## Acceptance Criteria
- **AC-UC047-01:** Given a `HELD` reservation and a successful capture, when the commit runs, then status is `CONSUMED` and `qty_on_hand` decreased atomically (BR-INV-01).
- **AC-UC047-02:** Given the capture event is replayed, when processed again, then no second deduction or ledger row is produced (BR-PLT-03).
- **AC-UC047-03:** Given a commit transaction fails, when it rolls back, then reservation and quantity are unchanged (BR-INV-01).
- **AC-UC047-04:** Given a committed reservation, when the TTL sweeper runs, then the row is skipped (BR-INV-01).
