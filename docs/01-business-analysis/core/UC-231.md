# UC-231 — Auto-Cancel Top-Ups Left Pending Beyond the Confirmation Window

## Header Info
- **Use Case ID:** UC-231
- **Title:** Auto-Cancel Top-Ups Left Pending Beyond the Confirmation Window
- **Actor:** System (ACT-07) — top-up poll/cancel job (no interactive login)
- **Trigger:** A mobile-wallet top-up is still `PENDING` past the confirmation window with no verified callback
- **Priority:** P1
- **Goal:** Close stale pending top-ups honestly — cancel them, notify the customer, and never credit without a verified provider signal.
- **Preconditions:** Top-up created `PENDING`; confirmation window (design: > 15 minutes) elapsed; poll returns pending; credit only on verified callback or reconciled poll (BR-PAY-03).

## Main Scenario
1. The poll job finds a top-up still `PENDING` beyond the confirmation window.
2. System cancels the top-up: state → cancelled, any hold released, wallet untouched — no credit without a verified callback (BR-PAY-03).
3. The customer is notified with an honest status and retry guidance.
4. The cancellation is recorded; the pending list no longer shows it as awaiting the provider.
5. If a valid callback arrives later, it is matched against the cancelled record: if the provider did charge, the case routes to reconciliation for a manual credit decision — never a silent credit (BR-PAY-03).
6. Reconciliation confirms no double credit across wallets and provider statements.

## Alternative Scenarios
- **A1 — Callback arrives in window:** normal credit path; no cancellation (BR-PAY-03).
- **A2 — Poll reports provider failure:** the top-up fails per provider status; no credit occurs.
- **A3 — Bank-transfer top-ups:** never auto-cancelled — they wait for admin verification with no timeout conversion to credit (BR-PAY-04).

## Exception Scenarios
- **E1 — Late callback after cancellation:** evaluated against the cancelled record → reconciliation/manual decision, never automatic credit (BR-PAY-03).
- **E2 — Cancel job crashes:** rerun is status-guarded — a top-up is cancelled exactly once.
- **E3 — Notification send fails:** retried through the queue with dead-letter alerting; the cancellation itself stands (BR-PLT-02).

## Postconditions
- Success: no top-up lingers `PENDING` past the window; the wallet balance is unchanged by cancellation.
- Failure: no wallet credit occurred without a verified callback; nothing is left half-cancelled.

## Business Rules Applied
- BR-PAY-03

## Related Requirements
- FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — cancels its own pending intents; never credits a wallet.
- **Data involved:** top-up intents, wallet balance (untouched), cancellation record, customer notification, reconciliation entries.
- **External dependencies:** m-Floos/OneCash provider callbacks and poll (INT-REQ-001); notification pipeline.

## Acceptance Criteria
- **AC-UC231-01:** Given a top-up pending beyond the window with no verified callback, when the job runs, then it is cancelled and no wallet credit occurs (BR-PAY-03).
- **AC-UC231-02:** Given a cancelled top-up, when a late provider callback arrives, then it routes to reconciliation instead of crediting (BR-PAY-03).
- **AC-UC231-03:** Given a bank-transfer request awaiting verification, when the job runs, then it is not cancelled (BR-PAY-04).
