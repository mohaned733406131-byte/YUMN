# UC-225 — Return the Original Order on Idempotent Checkout Replay

## Header Info
- **Use Case ID:** UC-225
- **Title:** Return the Original Order on Idempotent Checkout Replay
- **Actor:** System (ACT-07) — checkout idempotency middleware (no interactive login)
- **Trigger:** An order-creation request arrives carrying an `Idempotency-Key` that may already have been executed
- **Priority:** P0
- **Goal:** Guarantee exactly one order and one wallet debit per key — a replay returns the original order instead of creating another.
- **Preconditions:** Key mandatory for order creation (BR-ORD-06, BR-PLT-03); key store reachable with 24-hour snapshot TTL; prior response may exist.

## Main Scenario
1. Order creation arrives with an idempotency key; middleware looks up the key record (request hash + response snapshot).
2. Same key, same payload → the stored response is replayed: no second order, no second wallet movement (BR-ORD-06).
3. Same key, different payload → `409 IDEMPOTENCY_KEY_CONFLICT`; nothing executes.
4. First-seen key → checkout executes: server-side totals, wallet payment, master/sub-order creation — then the response is stored write-through with a 24-hour TTL (BR-PLT-03).
5. Concurrent duplicates serialize on the key: one executes, the other replays the stored original.
6. A database unique constraint on the idempotency key backstops the cache, so cache loss cannot double-create (BR-ORD-06).

## Alternative Scenarios
- **A1 — Replay past 24 hours:** the key record has expired; the request is treated as new (fresh order).
- **A2 — Client retry after a network drop:** same key → the original order is returned; the buyer sees one order.
- **A3 — Failure response:** non-2xx responses are not cached, so a retry may execute; business idempotency keeps money effects single.

## Exception Scenarios
- **E1 — Key store down:** the unique database constraint prevents a duplicate order; the request fails safely instead of double-charging (BR-PLT-03).
- **E2 — Payment succeeded, response lost:** the retry returns the original order; the wallet is debited exactly once.
- **E3 — Key reused for a different cart:** payload mismatch → `409`, no execution (BR-ORD-06).

## Postconditions
- Success: exactly one order row and one wallet debit per key; a replaying client receives the original order.
- Failure: no half-written order, no duplicate charge — the conflict is explicit.

## Business Rules Applied
- BR-ORD-06, BR-PLT-03

## Related Requirements
- FR-011 (Checkout & Order Placement)

## Permissions / Data / External Dependencies
- **Permissions:** Any authenticated buyer for their own checkout; the middleware itself is service-scoped.
- **Data involved:** idempotency key records, order/master/sub-order rows, wallet payment, response snapshots.
- **External dependencies:** Redis key store; PostgreSQL unique constraints as durable backstop.

## Acceptance Criteria
- **AC-UC225-01:** Given a completed checkout, when the same key and payload are resubmitted, then the original order is returned with no new order row (BR-ORD-06).
- **AC-UC225-02:** Given the same key with a different payload, when submitted, then `409` is returned and nothing executes.
- **AC-UC225-03:** Given two concurrent submissions with one key, when both complete, then exactly one order and one wallet debit exist (BR-PLT-03).
