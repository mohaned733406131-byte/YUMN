# UC-252 — Page On-Call When Backup Freshness Breaches Its Window

## Header Info
- **Use Case ID:** UC-252
- **Title:** Page On-Call When Backup Freshness Breaches Its Window
- **Actor:** System (ACT-07) — backup freshness monitor (no interactive login)
- **Trigger:** The freshness check detects WAL age over 15 minutes or snapshot age over 24 hours
- **Priority:** P0
- **Goal:** A stale backup is a paging incident — on-call knows within a minute, not at the next restore attempt.
- **Preconditions:** Freshness runs every 15 minutes; thresholds configured (WAL 15 min, snapshot 24 h); the P1 page route to on-call exists (NFR-006).

## Main Scenario
1. The freshness check runs against WAL age and snapshot age.
2. Either threshold is breached → severity `backup_failed` is raised as P1.
3. The route sends the ops owner a notice plus a page to on-call — page within 1 minute, ack within 15 minutes.
4. The page links the backup runbook section so the responder starts with steps, not guesswork.
5. The responder repairs the job and a fresh backup lands → the next 15-minute check clears the alert.
6. A periodic failure-injection drill proves the alert path actually fires — tested, not assumed.

## Alternative Scenarios
- **A1 — Freshness within bounds:** no alert; the monitor records a pass.
- **A2 — WAL fresh but snapshot stale (or either alone):** each threshold pages independently — partial staleness still pages.
- **A3 — Alert channel uncertainty:** the weekly dead-man's-switch watchdog proves the paging path itself still works.

## Exception Scenarios
- **E1 — Backup job failing repeatedly:** pages repeat until freshness is restored; nothing self-clears without a fresh backup (NFR-006).
- **E2 — Staleness found during a restore drill:** the drill confirms the gap and the RPO breach is recorded — the monitor and drill corroborate each other (NFR-006).
- **E3 — Page unacknowledged for 15 minutes:** routing escalates the severity per alert rules — silence is not an outcome.

## Postconditions
- Success: freshness restored — WAL within 15 minutes, snapshot within 24 hours — and the alert is cleared.
- Failure: staleness never passes unnoticed — a page is already out or fires at the next 15-minute tick; no silent stale state (NFR-006).

## Business Rules Applied
- None — backup freshness is recoverability monitoring (FR-020, NFR-006); no BR in DOC-BA-005 governs it.

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — reads backup metadata and raises alerts; on-call receives and acknowledges pages.
- **Data involved:** WAL segment ages, snapshot timestamps, alert records, acknowledgement state.
- **External dependencies:** CI/ops freshness check; Prometheus/Alertmanager routes; pager channel; backup jobs.

## Acceptance Criteria
- **AC-UC252-01:** Given WAL age above 15 minutes, when the monitor runs, then a P1 page reaches on-call within 1 minute (NFR-006).
- **AC-UC252-02:** Given fresh WAL and a fresh snapshot, when the monitor runs, then no page is raised.
- **AC-UC252-03:** Given an unacknowledged page, when 15 minutes pass, then the alert escalates per routing rules.
- **AC-UC252-04:** Given a failed backup job, when freshness breaches again after a fix, then a new page fires — staleness is never cached away.
