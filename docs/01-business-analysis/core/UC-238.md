# UC-238 — Issue a Fresh 6-Digit Delivery Code at OUT_FOR_DELIVERY

## Header Info
- **Use Case ID:** UC-238
- **Title:** Issue a Fresh 6-Digit Delivery Code at OUT_FOR_DELIVERY
- **Actor:** System (ACT-07) — delivery code issuance job (no interactive login)
- **Trigger:** A shipment transitions to OUT_FOR_DELIVERY and the buyer needs the confirmation code
- **Priority:** P0
- **Goal:** Give the buyer a fresh 6-digit code on every OUT_FOR_DELIVERY entry so delivery can be confirmed only by code entry.
- **Preconditions:** Order reached OUT_FOR_DELIVERY in the 17-state machine (C-09); a courier is assigned (BR-SHP-04); the buyer is reachable on at least one notification channel (FR-017).

## Main Scenario
1. The shipment enters OUT_FOR_DELIVERY → the `b08.shipping.code-issue` job is enqueued.
2. The job generates a fresh 6-digit code for this delivery — never a code left over from a previous attempt (BR-SHP-02).
3. The code is delivered to the buyer through the notification lanes; the buyer shares it with the courier out-of-band (BR-SHP-02, C-16).
4. The code stays bound to the shipment server-side; courier entry is verified against it and only successful verification reaches DELIVERED (BR-ORD-08).
5. Concurrent entries are serialized: the first success wins and duplicate successes no-op (BR-SHP-03).
6. The `b08.shipping.code-expire` job clears the code once its TTL lapses (BR-SHP-02).

## Alternative Scenarios
- **A1 — Delivery fails before confirmation:** the shipment leaves and later re-enters OUT_FOR_DELIVERY → the job runs again and a new code replaces the old one.
- **A2 — Code notification channel fails:** the send retries over the next channel in the pipeline; the code itself is unchanged (FR-017).
- **A3 — Wrong code entered once or twice:** attempts 1–2 return remaining-attempt feedback and the flow continues (BR-SHP-03).

## Exception Scenarios
- **E1 — Third wrong entry:** confirmation locks for 24 hours and a support ticket is auto-created; entries are rejected for the duration (BR-SHP-03, C-16).
- **E2 — Issuance job fails:** retry with backoff, then dead-letter with an alert; the order stays OUT_FOR_DELIVERY and no code reaches the buyer (BR-PLT-02).
- **E3 — Stale code from an earlier attempt presented:** verification checks the current code only → rejected; the previous code died when the new one was issued (BR-SHP-02).

## Postconditions
- Success: exactly one active 6-digit code exists for the delivery; the buyer holds it; verified entry completes delivery (BR-ORD-08).
- Failure: no code is issued or the lock is active — the order remains OUT_FOR_DELIVERY; delivery never completes without code verification.

## Business Rules Applied
- BR-SHP-02, BR-SHP-03, BR-ORD-08, BR-PLT-02

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — writes code, attempt and TTL records; no interactive login.
- **Data involved:** shipment delivery-code field, attempt counters, code TTL record, notification message, support ticket on lock.
- **External dependencies:** notification pipeline for code delivery (B10); BullMQ delivery queues.

## Acceptance Criteria
- **AC-UC238-01:** Given an order at OUT_FOR_DELIVERY, when the issuance job runs, then a fresh 6-digit code is stored and delivered to the buyer (BR-SHP-02).
- **AC-UC238-02:** Given a code from a previous attempt, when the shipment re-enters OUT_FOR_DELIVERY, then a new code is issued and the old one no longer verifies (BR-SHP-02).
- **AC-UC238-03:** Given three wrong entries, when the third fails, then confirmation locks for 24 hours and a support ticket exists (BR-SHP-03, C-16).
- **AC-UC238-04:** Given successful code verification, when the transition runs, then the order reaches DELIVERED (BR-ORD-08).
