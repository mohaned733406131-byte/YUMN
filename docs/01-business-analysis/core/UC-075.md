# UC-075 — Rebuild the Order Timeline Read Model

## Header Info
- **Use Case ID:** UC-075
- **Title:** Rebuild the Order Timeline Read Model
- **Actor:** System (ACT-07) — timeline projector (no interactive login)
- **Trigger:** Order state change commits, or a full read-model rebuild is requested
- **Priority:** P2
- **Goal:** Keep a role-aware, query-friendly order timeline projection derived from append-only history, rebuildable at any time without touching source data.
- **Preconditions:** `order_status_history` append-only with actor/timestamp/reason (BR-ORD-03); timeline projection queue running.

## Main Scenario
1. Every state change appends a history row (BR-ORD-03) and emits an event; the outbox enqueues `b06.order.timeline-project`.
2. The projector consumes the event in order and upserts the read model entry (order ref, state, actor, timestamp, reason, visible-to roles).
3. Timeline queries serve the read model — visibility filtered per role: buyer (own), vendor (own sub-orders), assigned courier (own delivery), admin/moderator scoped (BR-ORD-09).
4. On divergence (backfill, migration, corruption) an operator triggers a full rebuild: history is replayed into an empty projection and the result replaces the old read model atomically.
5. The rebuilt timeline is identical to the incremental one because both derive from the same append-only source.

## Alternative Scenarios
- **A1 — Out-of-order events:** Projection orders entries by history sequence/timestamp — source history, not arrival order, decides the timeline.
- **A2 — Full rebuild requested:** Replay from `order_status_history` until parity, then swap — reads continue on the old model during the swap.
- **A3 — Role-scoped read:** Same projection, different filter — courier sees only its delivery leg (BR-ORD-09).

## Exception Scenarios
- **E1 — Projector crash:** Retry from the last checkpoint; the read model is temporarily stale while source history stays authoritative and intact.
- **E2 — Duplicate events:** Upsert by (order, history entry) identity — replays never create duplicate timeline rows.
- **E3 — History gap detected during rebuild:** The rebuild aborts rather than inventing missing entries; the gap is alerted for investigation (history is append-only, BR-ORD-03).

## Postconditions
- Read model converges to history; every projected row traceable to an append-only history entry (BR-ORD-03).
- Role visibility rules hold on read (BR-ORD-09); source history never modified by projection.
- Rebuild produces a projection equal to the incremental one.

## Business Rules Applied
- BR-ORD-03, BR-ORD-09

## Related Requirements
- FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) writes the read model only; humans read through role-scoped APIs (BR-ORD-09).
- **Data involved:** `order_status_history`, timeline projection rows, projection checkpoints.
- **External dependencies:** BullMQ (`b06.order.timeline-project`); PostgreSQL source + read tables; order event outbox.

## Acceptance Criteria
- **AC-UC075-01:** Given a committed state change, when the projector runs, then the timeline shows the new entry with actor, timestamp and reason (BR-ORD-03).
- **AC-UC075-02:** Given a courier reading a timeline, when the projection is served, then only its own delivery leg is visible (BR-ORD-09).
- **AC-UC075-03:** Given a full rebuild, when history is replayed, then the resulting timeline equals the incrementally built one.
- **AC-UC075-04:** Given a duplicated event, when processed twice, then exactly one timeline entry exists.
