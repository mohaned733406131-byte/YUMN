# UC-061 — Deliver Mandatory Security Notifications

## Header Info
- **Use Case ID:** UC-061
- **Title:** Deliver Mandatory Security Notifications
- **Actor:** System (ACT-07) — security-class notification path (no interactive login)
- **Trigger:** A security event occurs (OTP issued, login, password change, account lockout) (FR-001, FR-017)
- **Priority:** P0
- **Goal:** Guarantee that security notifications reach the user regardless of any preference the user has set — they can never be disabled.
- **Preconditions:** The event is classified as security class before the preference gate; the security category is exempt from opt-out evaluation (FR-017).

## Main Scenario
1. A security domain event (OTP, login, password change, lockout) is emitted by the auth domain (FR-001).
2. The fan-out consumer classifies it as security → the per-category opt-out gate is bypassed (FR-017).
3. The template renders in the user's locale — Arabic default (FR-017).
4. For OTP transport specifically, delivery runs through the OTP path with SMS primary and automatic WhatsApp failover (FR-001, see UC-040).
5. Non-OTP security notices dispatch through the standard lanes (SMS/WhatsApp/push/in-app) without preference filtering (FR-017).
6. Delivery receipts are logged and the notification is visible in the in-app inbox (FR-017).

## Alternative Scenarios
- **A1 — OTP event:** transport details (6-digit code, resend cooldowns, provider failover) belong to UC-040 — this UC only guarantees the mandatory-delivery classification (FR-001).
- **A2 — User previously opted out of everything:** irrelevant for security class — the message still dispatches on configured channels (FR-017).
- **A3 — Lockout notice:** triggered by the account lockout flow; delivered as a security-class message with the same bypass (FR-001).

## Exception Scenarios
- **E1 — Primary channel fails:** provider retry/failover logic of the delivery lanes applies (for OTP: WhatsApp failover per UC-040); the message is not dropped (FR-001).
- **E2 — Fan-out job fails:** retried with backoff, then dead-letter with alert; a security notice failing is never silently swallowed (FR-017).
- **E3 — Recipient has no reachable channel:** the in-app inbox copy still persists so the record exists when the user signs in (FR-017).

## Postconditions
- Success: security notification dispatched on all configured channels (or OTP path completed) and present in the in-app inbox, regardless of user preferences.
- Failure: dispatch retried/dead-lettered with alert; the security event itself is unaffected; no preference can have suppressed it.

## Business Rules Applied
- BR-NTF-02

## Related Requirements
- FR-017 (Notifications & Messaging), FR-001 (Identity, Authentication & Session Management)
- **Related:** complements UC-040 (OTP transport only) — this UC guarantees the mandatory classification; UC-040 owns channel failover.

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); users cannot write opt-out flags for the security category.
- **Data involved:** security events, notification preferences (bypassed), inbox rows, delivery receipts.
- **External dependencies:** OTP transport path (UC-040), notification lanes, auth domain events.

## Acceptance Criteria
- **AC-UC061-01:** Given a user who disabled all notification categories, when an OTP is issued, then it is still delivered (BR-NTF-02).
- **AC-UC061-02:** Given a password-change security event, when fan-out runs, then the preference gate does not suppress it (BR-NTF-02).
- **AC-UC061-03:** Given an OTP event, when transport runs, then it follows the UC-040 path (SMS primary, WhatsApp failover) (FR-001).
- **AC-UC061-04:** Given all external channels down, when the job completes, then the in-app inbox copy exists (FR-017).
