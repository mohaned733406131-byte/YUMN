# UC-212 — Evict the Oldest Device Session on the Sixth Concurrent Login

## Header Info
- **Use Case ID:** UC-212
- **Title:** Evict the Oldest Device Session on the Sixth Concurrent Login
- **Actor:** System (ACT-07) — session service (no interactive login)
- **Trigger:** A successful login would register a sixth concurrent device session for a user who already has five active
- **Priority:** P1
- **Goal:** Hold the five-device cap by evicting the oldest session the moment a sixth login succeeds.
- **Preconditions:** Five-session cap in force (BR-AUTH-06, C-08); session registry reachable; login issues single-use rotating refresh tokens.

## Main Scenario
1. Client authenticates (`POST /auth/login`) → the service counts the user's active device sessions.
2. Fewer than five active → the new session is registered and the token pair issued (C-08).
3. Exactly five active → the oldest session (earliest registration) is revoked before the new one is registered (BR-AUTH-06).
4. The evicted device's refresh token fails on its next use; that device returns to login.
5. The new session is recorded with device name and last-seen metadata; exactly ≤5 sessions remain active (BR-AUTH-06).
6. A mandatory login security notification is queued for the user (BR-NTF-02).

## Alternative Scenarios
- **A1 — Below the cap:** registration proceeds with no eviction; existing sessions are untouched.
- **A2 — Same device re-login:** the device's own session is replaced rather than added — the cap is never approached.
- **A3 — User-managed revocation:** the user may revoke sessions individually from the session list; a later login then fits without eviction (FR-003).

## Exception Scenarios
- **E1 — Registry outage:** login fails closed with a dependency error; no session is registered, so the cap cannot be silently exceeded.
- **E2 — Evicted device still holds an access token:** it keeps working until that 15-minute token expires (C-08), but refresh is rejected from the first renewal onward.
- **E3 — Two logins racing:** registrations serialize on the registry; the count never exceeds five — the loser evicts the oldest (BR-AUTH-06).

## Postconditions
- Success: a new session is active and the user has at most five concurrent sessions; the oldest session family is revoked.
- Failure: no new session exists and the previous sessions are untouched.

## Business Rules Applied
- BR-AUTH-06

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)
- **Related:** complements UC-043 (rotation/family revocation) — the 5-device cap is enforced here.

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — writes its own session records; no interactive login.
- **Data involved:** session registry entries, refresh-token records, login security notification, session metadata.
- **External dependencies:** Redis session registry; notification pipeline for the login notice.

## Acceptance Criteria
- **AC-UC212-01:** Given five active sessions, when a sixth login succeeds, then the oldest session is revoked and exactly five remain (BR-AUTH-06).
- **AC-UC212-02:** Given an evicted device, when it attempts a refresh, then the request is rejected and it must log in again (C-08).
- **AC-UC212-03:** Given fewer than five sessions, when a login succeeds, then no existing session is evicted.
