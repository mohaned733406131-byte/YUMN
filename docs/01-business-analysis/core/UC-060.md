# UC-060 — Honor Per-Category Notification Opt-Outs

## Header Info
- **Use Case ID:** UC-060
- **Title:** Honor Per-Category Notification Opt-Outs
- **Actor:** System (ACT-07) — preference gate inside the fan-out pipeline (no interactive login)
- **Trigger:** The fan-out consumer reaches the preference check before dispatch (FR-017)
- **Priority:** P1
- **Goal:** Suppress marketing-category messages on exactly the channels a user opted out of, while never touching security notifications.
- **Preconditions:** User preferences store per-category, per-channel opt-out flags (FR-017); the event's category is classified before dispatch.

## Main Scenario
1. The fan-out consumer classifies the event's notification category (FR-017).
2. It reads the recipient's opt-out flags for that category, per channel (FR-017).
3. For each opted-out channel, the corresponding dispatch job is skipped — no render, no provider call (FR-017).
4. Channels not opted out for the category proceed normally through render and delivery (FR-017).
5. In-app inbox behavior follows the stored preference for the category (FR-017).
6. The decision is logged per recipient so suppressed sends are traceable (FR-017).

## Alternative Scenarios
- **A1 — Opt-out on SMS only:** SMS dispatch is skipped while WhatsApp and push still deliver for the same message (FR-017).
- **A2 — Category fully opted out on all channels:** nothing dispatches for that category; the recipient sees no message of it (FR-017).
- **A3 — Security notification (e.g. OTP, lockout):** classified as security → the opt-out gate does not apply; delivery proceeds on all configured channels (FR-017).

## Exception Scenarios
- **E1 — Preferences unreadable:** the check fails closed for marketing categories — dispatch is deferred and retried rather than guessed; security notices are exempt (FR-017).
- **E2 — Preference changed mid-flight:** the check reads current state at dispatch time; a last-second change affects only the subsequent run (FR-017).
- **E3 — Unknown category:** an unclassified category does not bypass preferences — it is treated conservatively as suppressible and flagged for review (FR-017).

## Postconditions
- Success: only opted-in channel dispatches occur for the category; suppression decisions are logged.
- Failure: no message is sent on a channel whose opt-out could not be evaluated; the job retries.

## Business Rules Applied
- BR-NTF-05

## Related Requirements
- FR-017 (Notifications & Messaging)

## Permissions / Data / External Dependencies
- **Permissions:** service identity reads preferences and dispatches; only the user (via preference management) writes opt-out flags.
- **Data involved:** user notification preferences (category × channel), dispatch logs, suppression decisions.
- **External dependencies:** fan-out pipeline (`b10.notification.fanout`), notification inbox store.

## Acceptance Criteria
- **AC-UC060-01:** Given a user opted out of marketing on SMS, when a marketing event fans out, then no SMS dispatch job runs for them (BR-NTF-05).
- **AC-UC060-02:** Given the same user with push still enabled, when the event fans out, then push still delivers (BR-NTF-05).
- **AC-UC060-03:** Given a security notification and any opt-out flags, when fan-out runs, then it is not suppressed (FR-017).
- **AC-UC060-04:** Given a suppressed send, when logged, then the suppression decision is traceable per recipient (FR-017).
