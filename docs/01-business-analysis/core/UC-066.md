# UC-066 — Auto-Close Stale Support Tickets

## Header Info
- **Use Case ID:** UC-066
- **Title:** Auto-Close Stale Support Tickets
- **Actor:** System (ACT-07) — ticket housekeeping job (no interactive login)
- **Trigger:** Scheduled sweep of the ticket queue (`b13.ticket.auto-close`)
- **Priority:** P2
- **Goal:** Close support tickets that have been idle past the configured inactivity window so the queue reflects real work and does not accumulate stale items.
- **Preconditions:** Tickets exist with status OPEN/PENDING; inactivity window configured in platform settings; ticket module available (FR-020).

## Main Scenario
1. The scheduler enqueues `b13.ticket.auto-close` jobs on its cadence; the queue follows the platform `{block}.{entity}.{action}` convention.
2. The worker selects tickets with no customer or staff activity for longer than the inactivity window and skipping any flagged as escalation or dispute-linked.
3. For each candidate the system sends a pending-close notice to the ticket's requester in their locale, then closes the ticket with an auto-close resolution code.
4. The closure writes an append-only record (actor = System, reason = auto-close) so UC-036 audit reads can distinguish it from staff closure.
5. Queue/DLQ health for the sweep is exported to the observability stack (INT-REQ-007).

## Alternative Scenarios
- **A1 — Staff activity within the window:** Ticket skipped; the inactivity timer restarts from the latest activity.
- **A2 — Customer replies during the grace period:** The pending-close notice is withdrawn and the ticket reopens into the normal queue.
- **A3 — Ticket already closed or resolved:** Skipped — the sweep is idempotent and never re-closes or reopens anything.

## Exception Scenarios
- **E1 — Sweep job crash:** The job retries with backoff and then dead-letters with a depth alert (BR-PLT-02); stale tickets linger one more cycle — the failure direction is "stay open", never "wrongly closed".
- **E2 — Close notice delivery fails:** The notice is retried; a ticket is only closed after the notice succeeds, so requesters are never silently dropped.
- **E3 — DLQ depth grows (broken sweep):** Depth alert fires through the observability export (INT-REQ-007) so operators re-drive or fix the job.

## Postconditions
- Stale tickets are closed with resolution code `AUTO_CLOSED`; active tickets untouched.
- Closure history is append-only and auditable; requester informed.
- No ticket is lost — closure is a status transition, not a deletion.

## Business Rules Applied
- BR-PLT-02

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) — ticket status writes only; staff visibility unchanged (UC-014, UC-100).
- **Data involved:** Support ticket rows (status, last-activity timestamp, resolution code), notification records, queue metrics.
- **External dependencies:** BullMQ/Redis (`b13.ticket.auto-close`); ticket module; notification channels; Prometheus/Grafana export (INT-REQ-007).

## Acceptance Criteria
- **AC-UC066-01:** Given a ticket idle beyond the inactivity window, when the sweep runs, then it is closed with an auto-close resolution code.
- **AC-UC066-02:** Given a ticket with activity inside the window, when the sweep runs, then it remains open and its timer restarts.
- **AC-UC066-03:** Given the sweep job keeps failing, when retries exhaust, then the job dead-letters with an alert and stale tickets stay open (BR-PLT-02).
- **AC-UC066-04:** Given an auto-closed ticket, when an admin inspects it, then the closure is distinguishable from a staff closure in history.
