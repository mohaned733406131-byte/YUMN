# UC-076 — Reconcile Wallet Top-Ups Against Provider Polls and Callbacks

## Header Info
- **Use Case ID:** UC-076
- **Title:** Reconcile Wallet Top-Ups Against Provider Polls and Callbacks
- **Actor:** System (ACT-07) — top-up reconciliation worker (no interactive login)
- **Trigger:** Scheduled reconcile job (`b07.wallet.topup.reconcile`), every cycle for pending top-ups
- **Priority:** P1
- **Goal:** Credit wallet top-ups only from verified provider evidence — callback or reconciled poll — so no top-up is credited twice or on a client claim.
- **Preconditions:** Pending top-up rows carry provider references; provider APIs reachable (INT-REQ-001); wallet ledger available.

## Main Scenario
1. The scheduler enqueues `b07.wallet.topup.reconcile`; the worker selects top-ups still pending credit.
2. For each candidate it matches evidence: a verified provider callback already persisted, or a poll response from the provider API confirming the transaction (INT-REQ-001).
3. Crediting happens only on a verified callback or a reconciled poll — never on the client's claim (BR-PAY-03).
4. Bank-transfer top-ups are held for admin verification of the reference — no automatic credit (BR-PAY-04); reconciliation marks them awaiting the UC-034 check.
5. On a match the credit is written atomically with balanced ledger rows; the top-up moves to CREDITED; already-credited references are skipped idempotently.
6. The cycle repeats every few minutes until pending items resolve; the customer's balance/status reflects credits (UC-041/UC-164).

## Alternative Scenarios
- **A1 — Callback and poll both report success:** Single credit; the second piece of evidence is deduplicated by provider reference (idempotent).
- **A2 — Callback never arrived but provider shows success:** The poll reconciles the transaction and credits per BR-PAY-03.
- **A3 — Bank-transfer top-up:** Stays pending until admin verifies the reference (BR-PAY-04, UC-034); reconciliation never auto-credits it.

## Exception Scenarios
- **E1 — Provider outage:** Polls fail → top-ups remain pending and are retried next cycle; nothing is credited on absent evidence and nothing is lost.
- **E2 — Forged callback:** Signature verification rejects unauthenticated payloads — only verified evidence reaches the credit path.
- **E3 — Amount/reference mismatch:** No credit; the top-up is flagged for admin review with both values recorded.

## Postconditions
- Verified top-ups credited exactly once with balanced ledger rows; unverified ones stay pending.
- Bank-transfer top-ups await admin verification (BR-PAY-04); client claims never credited (BR-PAY-03).
- Reconciliation outcome stored per reference for audit.

## Business Rules Applied
- BR-PAY-03, BR-PAY-04

## Related Requirements
- FR-013 (Wallet & Payment Processing)
- Cross-reference (spec relation): reconciliation closes the loop UC-041 starts (customer top-up) and feeds UC-034 (admin bank-transfer verification).

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) writes credits in its flow; Admin performs only the bank-transfer verification leg (UC-034).
- **Data involved:** Top-up rows (provider ref, amount, status), wallet ledger entries, provider responses, admin verification records.
- **External dependencies:** Wallet provider APIs (m-Floos/OneCash, INT-REQ-001); signed callbacks; BullMQ (`b07.wallet.topup.reconcile`).

## Acceptance Criteria
- **AC-UC076-01:** Given a top-up with only a client claim, when reconciliation runs, then no credit occurs (BR-PAY-03).
- **AC-UC076-02:** Given a verified provider callback, when reconciliation runs, then the wallet is credited exactly once.
- **AC-UC076-03:** Given a bank-transfer reference, when reconciliation runs, then it stays pending until admin verification (BR-PAY-04).
- **AC-UC076-04:** Given a provider outage, when polls fail, then top-ups stay pending and are retried next cycle without loss.
