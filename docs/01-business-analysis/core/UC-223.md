# UC-223 — Serve Category Browse From Cache While Search Is Degraded

## Header Info
- **Use Case ID:** UC-223
- **Title:** Serve Category Browse From Cache While Search Is Degraded
- **Actor:** System (ACT-07) — discovery/degradation handler (no interactive login)
- **Trigger:** Search cluster health fails and requests arrive for search-dependent browsing
- **Priority:** P1
- **Goal:** Keep category browsing fully usable from cache/database while search is degraded — graceful degradation, never an error page.
- **Preconditions:** Search flagged degraded; cache warm or warming with version invalidation; browse data available in database/cache (FR-009, NFR-007).

## Main Scenario
1. Health probes detect the search failure → the platform enters degraded search mode.
2. Search endpoints return a graceful fallback instead of an error; no user-facing 5xx from the search path (NFR-007).
3. Category browse requests are served from the cache (cache-aside with version invalidation), falling through to the database on a miss.
4. Product detail pages keep serving from database/cache; catalog correctness is unaffected.
5. The degraded state is alerted as an urgent-but-not-outage incident and logged for the availability math.
6. When the cluster returns, search recovers automatically within a minute — no restart, and the fallback flag clears.

## Alternative Scenarios
- **A1 — Search healthy:** normal search; browse still uses cache to hold the hit-ratio target.
- **A2 — Cache also unavailable:** reads bypass to the database — slower but correct; writes are unaffected.
- **A3 — Load shedding:** suggestion traffic is shed first while explicit search and browse keep working.

## Exception Scenarios
- **E1 — Degradation persists:** the alert escalates on the degraded-time threshold instead of staying silent.
- **E2 — Cache stampede on recovery:** soft-TTL warm-up with a short lock lets only the first requester query the database.
- **E3 — Cached price/data must not lie:** stale-priced checkout confirmations are impossible — checkout always recomputes server-side; the cache only serves browse reads.

## Postconditions
- Success: category browse remains correct and available throughout; recovery is automatic.
- Failure: no corrupted or wrong-price data is served — correctness wins over availability for money-relevant reads.

## Business Rules Applied
- None — graceful degradation flows from FR-009 (no BR applies directly).

## Related Requirements
- FR-009 (Search & Discovery)

## Permissions / Data / External Dependencies
- **Permissions:** Public browse — anonymous read access; no writes through this path.
- **Data involved:** category tree, product browse documents, cache keys/versions, degradation flag.
- **External dependencies:** Elasticsearch (DEP-04) in degraded state; Redis cache; PostgreSQL fallback.

## Acceptance Criteria
- **AC-UC223-01:** Given Elasticsearch down, when a customer browses a category, then products are served from cache/database without error (FR-009).
- **AC-UC223-02:** Given search degraded, when a user searches, then a graceful fallback is shown — no 500 (NFR-007).
- **AC-UC223-03:** Given the cluster recovers, when health returns, then search resumes automatically and the degraded flag clears.
