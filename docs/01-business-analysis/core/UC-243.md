# UC-243 — Advance the Order to COMPLETED After a Rejected Return

## Header Info
- **Use Case ID:** UC-243
- **Title:** Advance the Order to COMPLETED After a Rejected Return
- **Actor:** System (ACT-07) — order state automation (no interactive login)
- **Trigger:** A return request is rejected by vendor or admin with a reason
- **Priority:** P1
- **Goal:** Close the loop — a final rejection returns the order to COMPLETED so obligations resume and the customer is told.
- **Preconditions:** Order in the return flow at RETURN_REQUESTED; rejection carries a reason (transition guard); the 17-state machine allows RETURN_REJECTED → COMPLETED by System (BR-RET-02).

## Main Scenario
1. Vendor or admin rejects the return with a reason → RETURN_REQUESTED → RETURN_REJECTED (BR-RET-02).
2. The rejection is final → System advances RETURN_REJECTED → COMPLETED (actor System, state machine).
3. The customer receives the rejection notification as part of the transition's guard.
4. A history row is appended with actor, timestamp and reason — never overwritten (BR-ORD-03).
5. The master order re-evaluates: it completes only when every sub-order is COMPLETED or REFUNDED (BR-ORD-07).
6. No refund is created — a rejected return leaves the completed order's settlement untouched.

## Alternative Scenarios
- **A1 — Return approved instead:** the flow diverges to RETURN_RECEIVED → REFUNDED with wallet credit (BR-RET-02) — not this path.
- **A2 — Another return attempt:** a new request is only possible inside the return window (BR-RET-01); outside it, validation rejects it.
- **A3 — Sibling sub-orders still in flight:** this sub-order rests at COMPLETED while the master waits for the others (BR-ORD-07).

## Exception Scenarios
- **E1 — Concurrent transitions:** optimistic locking — one transition commits and the loser gets a state conflict; no double transition (BR-RET-02).
- **E2 — Notification delivery fails:** the decision is already recorded in history; the notification retries through the pipeline (FR-017).
- **E3 — Automation crashes after rejection:** the re-run sees RETURN_REJECTED already reached and applies only the missing COMPLETED step — one history row per transition (BR-ORD-03).

## Postconditions
- Success: the order is back at COMPLETED; rejection and reason sit in append-only history; the customer was notified; no refund exists.
- Failure: the transition is not applied — the order stays in the return state and the step is retried; never COMPLETED without history.

## Business Rules Applied
- BR-RET-02, BR-RET-01, BR-ORD-03, BR-ORD-07

## Related Requirements
- FR-016 (Returns & Refunds)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — performs the guarded transition; the rejection decision itself belongs to vendor/admin (human).
- **Data involved:** order and sub-order state, order status history, return record, notification message.
- **External dependencies:** state-transition automation; notification pipeline; order timeline read model.

## Acceptance Criteria
- **AC-UC243-01:** Given a rejected return, when the automation runs, then RETURN_REJECTED → COMPLETED executes with actor System (BR-RET-02).
- **AC-UC243-02:** Given the transition, when it commits, then an append-only history row carries actor, timestamp and reason (BR-ORD-03).
- **AC-UC243-03:** Given the final rejection, when it is recorded, then a notification reaches the customer and no refund is created (BR-RET-02).
- **AC-UC243-04:** Given sibling sub-orders not yet terminal, when this sub-order completes, then the master order stays non-terminal (BR-ORD-07).
