# UC-054 — Run Daily Ledger and Escrow Reconciliation

## Header Info
- **Use Case ID:** UC-054
- **Title:** Run Daily Ledger and Escrow Reconciliation
- **Actor:** System (ACT-07) — daily reconciliation job (no interactive login)
- **Trigger:** Daily scheduler enqueues `b07.ledger.daily-reconcile` (FR-013, FR-014)
- **Priority:** P0
- **Goal:** Prove once per day that the books balance — Σ ledger entries net to zero and wallet + escrow + payable totals equal provider statements.
- **Preconditions:** All money movements have posted append-only ledger rows; provider statements for the window are obtainable.

## Main Scenario
1. The scheduler enqueues the daily reconcile job after the business day closes (FR-013, FR-014).
2. The job sums all ledger entries in the window and verifies the double-entry balance (Σ = 0) (BR-ESC-08).
3. It totalizes wallet balances, escrow holdings and vendor payables from current state (BR-ESC-08).
4. It compares those totals against the provider statements (m-Floos/OneCash/bank references) for the same window (BR-ESC-08, BR-FIN-03).
5. A match writes a `BALANCED` reconciliation result retained for audit; a mismatch writes the discrepancy details and raises the alert path (BR-ESC-08, see UC-055).
6. The result is queryable by admin review the next morning (FR-013, FR-014).

## Alternative Scenarios
- **A1 — Clean reconciliation:** all checks pass → `BALANCED` result stored; no alert (BR-ESC-08).
- **A2 — Weekend/holiday window:** reduced activity → same checks run; empty windows still produce a stored result (BR-FIN-03).
- **A3 — Pending provider statement:** statement not yet available → the job waits within its window and re-runs; no false `BALANCED` is recorded (BR-ESC-08).

## Exception Scenarios
- **E1 — Mismatch detected:** discrepancy recorded with breakdown; the finance alert path fires (UC-055); no ledger data is modified (BR-ESC-08).
- **E2 — Job fails mid-run:** retried with backoff, then dead-letter with alert; a partial result is discarded — only complete runs are stored (FR-013).
- **E3 — Provider outage (statement unreachable):** the run is incomplete, not balanced; it retries until statements are retrievable (BR-ESC-08).

## Postconditions
- Success: a complete reconciliation result (`BALANCED` or `MISMATCH`) exists for the window; ledger and balances untouched by the job.
- Failure: no trusted result for the window; retry scheduled; no book data changed.

## Business Rules Applied
- BR-ESC-08, BR-FIN-03

## Related Requirements
- FR-013 (Wallet & Payment Processing), FR-014 (Escrow, Commission & Vendor Payouts)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); the job reads money data and appends results — it cannot post ledger entries.
- **Data involved:** ledger entries, wallet/escrow/payable totals, provider statements, reconciliation results.
- **External dependencies:** wallet provider APIs (statements), BullMQ/Redis job (C-20), alerting channel.

## Acceptance Criteria
- **AC-UC054-01:** Given ledger entries summing to zero and totals matching provider statements, when the job runs, then a `BALANCED` result is stored (BR-ESC-08).
- **AC-UC054-02:** Given a 5,000 YER drift between totals and statements, when the job runs, then a `MISMATCH` result with breakdown is stored (BR-ESC-08).
- **AC-UC054-03:** Given the job fails halfway, when retried, then only a complete result is ever stored (FR-013).
- **AC-UC054-04:** Given any reconciliation run, when it completes, then no ledger or balance row was modified by the job (BR-FIN-03).
