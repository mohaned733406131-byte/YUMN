# UC-235 — Drain the Escrow Release Backlog After Scheduler Recovery

## Header Info
- **Use Case ID:** UC-235
- **Title:** Drain the Escrow Release Backlog After Scheduler Recovery
- **Actor:** System (ACT-07) — escrow release scheduler (no interactive login)
- **Trigger:** The release job, previously down, restarts and finds unprocessed matured holds
- **Priority:** P1
- **Goal:** Process the accumulated releases exactly once each — escrow simply stayed held during the outage (fail-safe), never released early.
- **Preconditions:** Sub-orders `DELIVERED` with escrow funded (BR-ESC-01); 7-day maturity measured from delivery (C-12); release conditions evaluable (BR-ESC-02).

## Main Scenario
1. Scheduler recovery is detected → the release job resumes and scans for matured holds.
2. Each candidate's conditions are verified: 7 days elapsed AND no active dispute AND state not in the disputed/return/refunded set (BR-ESC-02).
3. Eligible → commission computed at release and vendor payable credited net of it inside an ACID transaction with balanced ledger rows (BR-PAY-06).
4. Transition `DELIVERED → COMPLETED` with append-only history, actor System (BR-ORD-03).
5. The backlog drains in order; each release is idempotent, so a replay never double-releases (BR-PLT-03).
6. Vendors are notified of the delayed releases; daily reconciliation confirms totals.

## Alternative Scenarios
- **A1 — Dispute or return active:** release skipped; escrow stays held; the item re-evaluates on the next run (BR-ESC-02).
- **A2 — Partial backlog failure:** failed items retry with backoff then dead-letter while the rest of the backlog continues (BR-PLT-02).
- **A3 — Maturity during the outage:** items that matured while the job was down are simply older candidates — no state was lost.

## Exception Scenarios
- **E1 — Job crash mid-drain:** restart is idempotent — released items are skipped by their state, unreleased items are processed.
- **E2 — Release racing a new dispute:** the condition check is re-read under lock — a dispute opening at the same moment blocks the release (BR-ESC-02).
- **E3 — Reconciliation mismatch after catch-up:** the mismatch alerts finance; no silent pass (BR-ESC-01 conditions already gate each release).

## Postconditions
- Success: the backlog is drained; eligible escrows released exactly once; payables credited with balanced rows.
- Failure: money stays held — never released early, never twice.

## Business Rules Applied
- BR-ESC-01, BR-ESC-02

## Related Requirements
- FR-014 (Escrow, Commission & Vendor Payouts)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — releases its own escrow rows; actor System recorded on history.
- **Data involved:** escrow holds, vendor payable balances, commission records, order status history, ledger entries.
- **External dependencies:** BullMQ scheduled job; notification pipeline for delay notices.

## Acceptance Criteria
- **AC-UC235-01:** Given a backlog of matured, dispute-free holds, when the job recovers, then each is released exactly once (BR-ESC-02).
- **AC-UC235-02:** Given a hold with an active dispute in the backlog, when the job runs, then it is skipped and remains held (BR-ESC-01).
- **AC-UC235-03:** Given the release, when it commits, then `DELIVERED → COMPLETED` history exists with actor System (BR-ORD-03).
