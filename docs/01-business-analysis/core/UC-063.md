# UC-063 — Escalate Orders Stuck at CONFIRMED After 24 Hours

## Header Info
- **Use Case ID:** UC-063
- **Title:** Escalate Orders Stuck at CONFIRMED After 24 Hours
- **Actor:** System (ACT-07) — order SLA check job (no interactive login)
- **Trigger:** Hourly repeatable job `b06.order.sla.check` scans orders still in `CONFIRMED` (FR-012)
- **Priority:** P1
- **Goal:** Detect orders that have sat at `CONFIRMED` for 24 hours and escalate them for admin review with a customer notification — never silently auto-cancel.
- **Preconditions:** Order status history records the `CONFIRMED` timestamp; the job runs at least hourly (FR-012).

## Main Scenario
1. The repeatable job enqueues `b06.order.sla.check` on its hourly schedule (FR-012).
2. It selects orders whose state is `CONFIRMED` and whose confirmation timestamp is at least 24 hours old (FR-012).
3. For each stuck order it creates an admin review escalation with the full order context (FR-012).
4. It sends the customer a notification that the order is under review — the order is never silently auto-cancelled (FR-012).
5. The escalation appears in the admin orders queue for handling (FR-012).
6. The escalation action is recorded in order history with actor `SYSTEM` (FR-012).

## Alternative Scenarios
- **A1 — Order progressed before the check:** state moved past `CONFIRMED` → not selected; no escalation (FR-012).
- **A2 — Order confirmed 23 hours ago:** below the threshold → not yet selected; the next hourly run catches it after 24 hours (FR-012).
- **A3 — Multiple stuck orders in one run:** each is escalated independently with its own review item and customer notification (FR-012).

## Exception Scenarios
- **E1 — Job fails:** retried with backoff then dead-letter with alert; the next successful run still selects all past-due orders by timestamp (FR-012).
- **E2 — Notification delivery fails:** the escalation itself is created; notification retries — the no-silent-cancel guarantee does not depend on message delivery (FR-012).
- **E3 — Admin review delayed:** the order remains `CONFIRMED` under escalation; the job does not cancel it — human review owns the outcome (FR-012).

## Postconditions
- Success: every order ≥24 h at `CONFIRMED` has an admin escalation, a customer notification, and a history entry with actor `SYSTEM`.
- Failure: no escalation created for the run; the job retries; order states unchanged.

## Business Rules Applied
- BR-ORD-10

## Related Requirements
- FR-012 (Order Lifecycle Management)
- **Related:** raises the escalation for admin handling — UC-135 (reciprocal: rel UC-063, system raises); UC-137 offers moderator read-only visibility.

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); the job escalates and notifies but never cancels orders — the decision belongs to the admin reviewer.
- **Data involved:** orders, status history, escalation records, customer notifications.
- **External dependencies:** BullMQ/Redis repeatable job (C-20), notification fan-out (B10), admin orders queue.

## Acceptance Criteria
- **AC-UC063-01:** Given an order `CONFIRMED` for 25 hours, when the job runs, then an admin escalation is created (BR-ORD-10).
- **AC-UC063-02:** Given an escalated order, when the run completes, then the customer received a review notification (BR-ORD-10).
- **AC-UC063-03:** Given an order `CONFIRMED` for 23 hours, when the job runs, then no escalation is created (BR-ORD-10).
- **AC-UC063-04:** Given any escalated order, when inspected after the run, then its state is still `CONFIRMED` — never auto-cancelled (BR-ORD-10).
