# UC-240 — Lift the Delivery-Code Confirmation Lock After 24 Hours

## Header Info
- **Use Case ID:** UC-240
- **Title:** Lift the Delivery-Code Confirmation Lock After 24 Hours
- **Actor:** System (ACT-07) — lock-expiry sweeper (no interactive login)
- **Trigger:** 24 hours elapse since the delivery-code confirmation lock was applied
- **Priority:** P1
- **Goal:** Return the courier to a working confirmation path automatically after the penalty window, with no manual unlock.
- **Preconditions:** A third wrong entry locked confirmation and auto-created a support ticket (BR-SHP-03); the lock lives server-side; the shipment's current code is unchanged (BR-SHP-02).

## Main Scenario
1. The lock timer reaches 24 hours → the sweeper detects the expired lock.
2. The server-side lock flag is cleared and confirmation accepts entries again (BR-SHP-03).
3. The lock event and its expiry remain visible in the trail so support can see the unlock was automatic.
4. The courier retries with the current 6-digit code; verification proceeds against the shipment's bound code (BR-SHP-02).
5. Attempt handling resumes under the server-side rules — feedback shows remaining attempts before any new lock (BR-SHP-03).
6. A courier app restart never lifted the lock early; only this expiry does.

## Alternative Scenarios
- **A1 — Still inside the window:** entries are rejected with the lock message; nothing changes.
- **A2 — Resolution before 24 hours:** v1 has no admin bypass — early resolution is ticket-driven manual handling only.
- **A3 — Shipment leaves delivery while locked:** the lock becomes moot; a later OUT_FOR_DELIVERY entry issues a fresh code (BR-SHP-02).

## Exception Scenarios
- **E1 — Sweeper tick missed:** the missed window is processed on the next tick with re-derived state; the courier stays locked in the meantime.
- **E2 — Entry racing the unlock:** the server-side check decides — either locked-reject or verified; never a partially unlocked state.
- **E3 — Third failure right after unlock:** a new 24-hour lock and a new support ticket are created (BR-SHP-03).

## Postconditions
- Success: the lock is lifted at 24 hours; the courier can attempt again; attempt history and timeline are intact.
- Failure: the lock persists; delivery waits — no bypass occurred and nothing was reset manually.

## Business Rules Applied
- BR-SHP-03, BR-SHP-02

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — clears its own lock flags; courier (ACT-03) submits entries against own delivery.
- **Data involved:** delivery-code lock flag and timestamp, attempt counters, support ticket, verification record.
- **External dependencies:** BullMQ SLA sweep; support-ticket pipeline.

## Acceptance Criteria
- **AC-UC240-01:** Given a lock applied at time T, when 24 hours elapse, then the lock is lifted and entries are accepted again (BR-SHP-03).
- **AC-UC240-02:** Given a locked confirmation before 24 hours, when the courier submits the code, then the entry is rejected (BR-SHP-03).
- **AC-UC240-03:** Given an app restart during the lock, when the courier retries, then the lock is still enforced (server-side).
- **AC-UC240-04:** Given the unlock, when the courier enters the current code correctly, then verification succeeds against the shipment's bound code (BR-SHP-02).
