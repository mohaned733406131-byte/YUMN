# UC-055 — Alert Finance on Reconciliation Mismatch

## Header Info
- **Use Case ID:** UC-055
- **Title:** Alert Finance on Reconciliation Mismatch
- **Actor:** System (ACT-07) — mismatch alert path of the reconciliation job (no interactive login)
- **Trigger:** The daily reconciliation run records a `MISMATCH` result (FR-013)
- **Priority:** P0
- **Goal:** Get a verified money discrepancy in front of finance within the alerting window, with enough detail to investigate, instead of letting drift compound silently.
- **Preconditions:** Reconciliation (UC-054) completed with a mismatch breakdown; a notification channel is configured for finance recipients.

## Main Scenario
1. UC-054's run detects that Σ ledger entries or wallet+escrow+payable totals diverge from provider statements (BR-ESC-08).
2. The mismatch record captures scope (ledger vs statement), amount delta, affected window and references (FR-013).
3. The system raises the alert through the notification pipeline to the finance recipient set (BR-NTF-01 channels: SMS, WhatsApp, in-app, push — no email in v1).
4. The alert carries the discrepancy summary and points at the stored reconciliation result (FR-013).
5. The mismatch also becomes visible in admin reconciliation review so operators can cross-check (FR-013).
6. The alert and result are retained as audit evidence; the ledger itself is never edited to force a balance (BR-ESC-08).

## Alternative Scenarios
- **A1 — Clean run:** no mismatch → no alert is raised; only the `BALANCED` result is stored (BR-ESC-08).
- **A2 — Repeat mismatch across days:** each run raises its own alert; none is suppressed — consecutive drift stays visible (BR-ESC-08).
- **A3 — Finance prefers dashboard:** the admin reconciliation view shows the same mismatch; the alert remains the time-critical channel (FR-013).

## Exception Scenarios
- **E1 — Notification channel fails:** the pipeline retries delivery per platform job policy; the stored mismatch is never lost (BR-NTF-01).
- **E2 — Reconciliation job crashed before comparing:** no mismatch record exists → no alert; the job retry path of UC-054 must complete first (FR-013).
- **E3 — Alert delivered but investigation stalls:** the mismatch stays open in review; subsequent daily runs keep re-flagging the unresolved drift (BR-ESC-08).

## Postconditions
- Success: mismatch recorded, finance notified, admin review shows the open discrepancy; ledger and balances unchanged.
- Failure: alert not delivered (retried); the mismatch record still exists and is re-surfaced on subsequent runs.

## Business Rules Applied
- BR-ESC-08, BR-NTF-01

## Related Requirements
- FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); alerts target finance recipients; no role can amend ledger entries through this path.
- **Data involved:** reconciliation mismatch records, alert messages, audit trail.
- **External dependencies:** notification fan-out (B10, BR-NTF-01 channels), admin reconciliation view.

## Acceptance Criteria
- **AC-UC055-01:** Given a reconciliation run with a detected delta, when the run completes, then a finance alert with the discrepancy summary is sent (BR-ESC-08, BR-NTF-01).
- **AC-UC055-02:** Given a `BALANCED` run, when it completes, then no mismatch alert is sent (BR-ESC-08).
- **AC-UC055-03:** Given the alert channel rejects delivery, when the pipeline retries, then the mismatch record persists regardless (BR-NTF-01).
- **AC-UC055-04:** Given an unresolved mismatch, when the next day's run executes, then the discrepancy is flagged again (BR-ESC-08).
