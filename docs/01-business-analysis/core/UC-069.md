# UC-069 — Normalize Slugs and Preserve Canonical URLs

## Header Info
- **Use Case ID:** UC-069
- **Title:** Normalize Slugs and Preserve Canonical URLs
- **Actor:** System (ACT-07) — slug/canonical URL service (no interactive login)
- **Trigger:** Entity creation or rename (category, product, store, CMS page), or any request to a legacy slug
- **Priority:** P2
- **Goal:** Generate stable, RTL-safe slugs once and keep every old URL resolving to its canonical address so links and SEO never break.
- **Preconditions:** Entities have localized display names (ar/en); routing rules define locale prefixes and canonical policy (`routing.md` §8).

## Main Scenario
1. On entity creation the service derives a slug by Latin transliteration of the display name — Arabic names are never raw URL segments.
2. Uniqueness is enforced: category slugs unique per tree level (BR-CAT-03); product/store slugs unique platform-wide, collisions resolved by appending a short opaque suffix.
3. The slug is persisted once at creation and never silently rewritten; the page declares `<link rel="canonical">` and `hreflang` for ar/en.
4. The slug is locale-independent — the same path serves `/ar/…` and `/en/…` (names are translated in the UI, not in the path).
5. Requests resolve `/{locale}/c/{category-slug}`, `/p/{product-slug}`, `/store/{store-slug}` against published slugs; unpublished or soft-deleted targets 404.

## Alternative Scenarios
- **A1 — Slug collision at creation:** A short opaque suffix is appended (`-x7k2`) until the slug is unique (BR-CAT-03 for categories).
- **A2 — Entity renamed:** A redirect row is created from the old slug to the canonical one; the live URL is never changed in place.
- **A3 — Legacy/renamed slug request:** The router answers a 308 permanent redirect to the canonical slug, preserving SEO.

## Exception Scenarios
- **E1 — Redirect chain growth:** Intermediate slugs are collapsed to a single hop to the current canonical so chains never deepen.
- **E2 — Unknown slug:** No entity and no redirect match → clean 404, no redirect loop.
- **E3 — Rename racing a request:** Resolution reads the redirect table inside the same consistency boundary as the slug lookup — a request gets either the old canonical (redirected) or the new one, never a dead link.

## Postconditions
- Every entity has exactly one canonical slug; older slugs 308-redirect to it.
- URLs are locale-independent and RTL-safe; canonical/hreflang tags present.
- Soft-deleted or inactive targets are not resolvable.

## Business Rules Applied
- BR-CAT-03

## Related Requirements
- FR-009 (Search & Discovery), FR-004 (Product Catalog Management)

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) writes slug/redirect rows; Admin edits category nodes (renames route through this service).
- **Data involved:** Slug columns, redirect rows, canonical metadata, entity publish state.
- **External dependencies:** Next.js-style router with locale prefixes (conceptual frontend routing); ISR/published-slug path generation.

## Acceptance Criteria
- **AC-UC069-01:** Given a category created with an Arabic name, when the slug is generated, then it is a Latin transliteration unique within its level (BR-CAT-03).
- **AC-UC069-02:** Given a renamed entity, when its old URL is opened, then a 308 redirect serves the canonical slug.
- **AC-UC069-03:** Given two products whose names transliterate identically, when both are created, then their slugs differ by an opaque suffix.
- **AC-UC069-04:** Given a soft-deleted product, when its slug is requested, then the response is 404.
