# UC-064 — Guard Escrow Release While a Dispute Is Open

## Header Info
- **Use Case ID:** UC-064
- **Title:** Guard Escrow Release While a Dispute Is Open
- **Actor:** System (ACT-07) — escrow release guard (no interactive login)
- **Trigger:** Scheduled escrow-release job evaluates a candidate sub-order, or a dispute opens on a held sub-order
- **Priority:** P0
- **Goal:** Prevent any escrow release to vendor payable while a dispute or return is active, so disputed funds stay frozen until resolution.
- **Preconditions:** Sub-order past its 7-day hold with funded escrow; dispute intake (customer/admin) available; release queue running.

## Main Scenario
1. Scheduler enqueues escrow-release jobs for sub-orders whose 7-day hold has elapsed; the guard is evaluated before any money movement.
2. For each candidate the system tests the guard: no active dispute AND state ∉ {DISPUTED, RETURN_*, REFUNDED} (BR-ESC-02).
3. When a dispute opens on a delivered sub-order, that sub-order enters `DISPUTED` and escrow release for it is frozen until resolution (BR-ORD-05).
4. Guard passes → release proceeds as in UC-039 (commission booked, payable credited, `DELIVERED → COMPLETED`); guard fails → release skipped, escrow stays held, no ledger row written.
5. On admin resolution the sub-order leaves `DISPUTED`; the next job run re-tests the guard and releases once eligible.

## Alternative Scenarios
- **A1 — Return in progress:** State is `RETURN_*` → guard fails (BR-ESC-02) → release skipped; the job re-evaluates on its next run.
- **A2 — Dispute resolved before the job runs:** Next run passes the guard → normal release; the freeze only delays release, never cancels it.
- **A3 — Refunded order:** State `REFUNDED` → guard fails permanently; the refund already drew on escrow, so there is nothing left to release.

## Exception Scenarios
- **E1 — Race: dispute opens while release commits:** The guard is tested inside the release transaction; if the dispute wins the row lock the release aborts and rolls back — a release never coexists with an active dispute; if release won first, the dispute path handles the post-completion case.
- **E2 — Release job crash mid-run:** The job is retried and, on exhaustion, dead-lettered with a depth alert; guard evaluation is idempotent so no sub-order releases twice or releases unguarded.
- **E3 — Dispute on one sub-order only:** The freeze is scoped to affected sub-orders (BR-ORD-05); sibling sub-orders without disputes may still release.

## Postconditions
- Disputed or returning sub-orders: escrow still held, state unchanged, zero ledger movement.
- Unaffected eligible sub-orders: released per UC-039 — `COMPLETED`, payable credited.
- Every guard decision is logged with the run (actor = System).

## Business Rules Applied
- BR-ESC-02, BR-ORD-05

## Related Requirements
- FR-014 (Escrow, Commission & Vendor Payouts), FR-012 (Order Lifecycle Management)
- Cross-reference (spec relation): this guard is the check UC-039 step2 relies on and the freeze UC-033 step3a leaves in place until resolution.

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07), no interactive login; Admin arbitrates disputes and observes releases through dashboards.
- **Data involved:** Escrow rows, dispute records, sub-order state, order status history, ledger entries.
- **External dependencies:** BullMQ escrow-release queue (`b07.escrow.release`); dispute service; ledger service.

## Acceptance Criteria
- **AC-UC064-01:** Given a sub-order with an open dispute, when the release job runs, then no release occurs and escrow stays frozen (BR-ESC-02).
- **AC-UC064-02:** Given a dispute opens on a delivered sub-order, when the dispute is recorded, then release for that sub-order is frozen (BR-ORD-05).
- **AC-UC064-03:** Given the dispute is resolved and the hold has elapsed, when the job runs again, then release proceeds normally.
- **AC-UC064-04:** Given a dispute opening racing the release transaction, when both commit, then exactly one wins — never a release plus an active dispute.
