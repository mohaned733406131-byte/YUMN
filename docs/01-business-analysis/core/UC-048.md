# UC-048 — Restore Stock When an Order Is Cancelled

## Header Info
- **Use Case ID:** UC-048
- **Title:** Restore Stock When an Order Is Cancelled
- **Actor:** System (ACT-07) — cancellation stock-release leg (no interactive login)
- **Trigger:** An order or sub-order reaches `CANCELLED` through a permitted cancellation (FR-012)
- **Priority:** P1
- **Goal:** Return every quantity the cancelled order held or consumed to sellable stock exactly once, keeping the inventory invariant intact.
- **Preconditions:** Cancellation is allowed in the current state (customer while `PLACED`/`CONFIRMED`, vendor/admin until `READY_FOR_PICKUP`, BR-ORD-04); the order's reservations are `HELD` or `CONSUMED`.

## Main Scenario
1. A permitted cancellation transitions the order/sub-order to `CANCELLED` (conceptual `POST /orders/{id}/cancel`, FR-012).
2. The system locates the reservation rows belonging to the cancelled lines (FR-005).
3. For `HELD` rows: release → `qty_reserved` decreased, status `RELEASED`; for `CONSUMED` rows: restore → `qty_on_hand` increased back (BR-INV-01 release path).
4. Each mutation appends an inventory ledger row with actor `SYSTEM`, reason `CANCELLATION`, delta and timestamp — append-only (BR-INV-01).
5. The cancellation triggers the wallet refund flow (BR-ORD-04) — refund credit itself runs in UC-058.
6. Availability views refresh; the restored quantity becomes immediately sellable (FR-005).

## Alternative Scenarios
- **A1 — Cancel before payment:** reservations are `HELD` only → release path, nothing to restore on `qty_on_hand` (BR-INV-01).
- **A2 — Cancel after payment:** reservations are `CONSUMED` → restore path increments `qty_on_hand` (BR-INV-01).
- **A3 — Multi-vendor order:** only the cancelled sub-order's lines restore; other vendors' sub-orders keep their stock (BR-ORD-04).

## Exception Scenarios
- **E1 — Cancellation not permitted:** state is past `READY_FOR_PICKUP` → rejected; no stock change occurs (BR-ORD-04).
- **E2 — Reservation already released by TTL:** re-running the restore finds no `HELD` row → no-op, quantity is never restored twice (BR-INV-01).
- **E3 — Restore fails mid-transaction:** rollback → order stays in its pre-cancel transition with stock untouched; the cancellation is retried (FR-012).

## Postconditions
- Success: order/sub-order `CANCELLED`; stock restored or released exactly once; ledger rows appended; refund flow triggered (BR-ORD-04).
- Failure: order state and stock unchanged; cancellation retried or reported to the actor.

## Business Rules Applied
- BR-INV-01, BR-ORD-04

## Related Requirements
- FR-005 (Inventory Management), FR-012 (Order Lifecycle Management)

## Permissions / Data / External Dependencies
- **Permissions:** the cancel request must come from an actor permitted by BR-ORD-04 (customer/vendor/admin); the stock leg itself runs under service identity (ACT-07).
- **Data involved:** order status history, `stock_reservation` rows, inventory quantities, inventory ledger, refund record.
- **External dependencies:** order service, wallet refund flow (UC-058), BullMQ (C-20).

## Acceptance Criteria
- **AC-UC048-01:** Given a `CONSUMED` reservation on a cancelled order, when restore runs, then `qty_on_hand` increases by the quantity once (BR-INV-01).
- **AC-UC048-02:** Given a `HELD` reservation on a cancelled order, when release runs, then `qty_reserved` decreases and status is `RELEASED` (BR-INV-01).
- **AC-UC048-03:** Given an order in `READY_FOR_PICKUP`, when customer cancellation is attempted, then it is rejected with no stock change (BR-ORD-04).
- **AC-UC048-04:** Given a successful cancellation, when stock is restored, then a `CANCELLATION` ledger row with actor `SYSTEM` exists (BR-INV-01).
