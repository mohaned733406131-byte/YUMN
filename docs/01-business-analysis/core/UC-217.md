# UC-217 — Serialize Contended Stock Reservations to Prevent Oversell

## Header Info
- **Use Case ID:** UC-217
- **Title:** Serialize Contended Stock Reservations to Prevent Oversell
- **Actor:** System (ACT-07) — inventory service (no interactive login)
- **Trigger:** A reservation request (cart add or checkout) contends with another for the same product's inventory row
- **Priority:** P0
- **Goal:** Serialize contended reservations on one row so stock can never be oversold and the invariant `on-hand ≥ reserved ≥ 0` always holds.
- **Preconditions:** Inventory row exists; reservation carries a 15-minute TTL (BR-CRT-02, C-13); row-level locking available (BR-INV-02).

## Main Scenario
1. A reservation request arrives → the transaction opens and takes a row-level lock on that product's inventory row.
2. Under the lock, availability is evaluated: requested ≤ available, keeping `on-hand ≥ reserved ≥ 0` (BR-INV-02).
3. Sufficient → insert one reservation row with a 15-minute expiry and increment reserved quantity, then commit (BR-CAT-07).
4. Insufficient → reject with a stock conflict; no reservation row is written — oversell is prohibited (BR-CAT-07).
5. The lock releases at commit or rollback; the next waiter re-reads the row and repeats — requests serialize on one row.
6. The invariant holds after every operation: reserved never exceeds on-hand and never goes negative (BR-INV-02).

## Alternative Scenarios
- **A1 — No contention:** the lock is acquired immediately; grant or reject happens in one pass.
- **A2 — Expiry interleaved:** the TTL sweeper releases expired holds on the same row — release is status-guarded, so a re-run never double-releases (BR-INV-04).
- **A3 — Lock wait timeout:** the transaction aborts cleanly and the client retries; no partial hold exists.

## Exception Scenarios
- **E1 — Deadlock between rows:** one transaction aborts and retries while the other proceeds; stock stays consistent either way.
- **E2 — Crash while holding the lock:** the dropped connection rolls the transaction back; the reservation is not created.
- **E3 — Request for a missing product or variant:** validation fails before locking; no inventory row is touched.

## Postconditions
- Success: exactly one reservation row per granted line; reserved ≤ on-hand at all times.
- Failure: no row written, stock untouched, the caller sees a conflict — never negative stock (BR-CAT-07).

## Business Rules Applied
- BR-CAT-07, BR-INV-02

## Related Requirements
- FR-005 (Inventory Management)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — inventory writes on behalf of cart/checkout flows; no human role touches reservations.
- **Data involved:** inventory rows, stock reservation rows, stock conflict outcomes.
- **External dependencies:** PostgreSQL row-level locking (single transactional store).

## Acceptance Criteria
- **AC-UC217-01:** Given two concurrent reservations for the last unit, when both run, then one is granted and the other rejected — never oversold (BR-INV-02).
- **AC-UC217-02:** Given a granted reservation, when it commits, then a single reservation row exists with a 15-minute expiry (BR-CAT-07).
- **AC-UC217-03:** Given an aborted request, when it fails, then no reservation row exists and quantities are unchanged.
