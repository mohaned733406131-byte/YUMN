# UC-044 — Lock an Account After Five Consecutive Failed Logins

## Header Info
- **Use Case ID:** UC-044
- **Title:** Lock an Account After Five Consecutive Failed Logins
- **Actor:** System (ACT-07) — auth service failure counter (no interactive login)
- **Trigger:** The fifth consecutive failed password login for the same phone number
- **Priority:** P0
- **Goal:** Freeze the account for 15 minutes after five consecutive failed logins so credential stuffing cannot continue, then unlock automatically.
- **Preconditions:** Login attempts reach the auth service (UC-003 step 2/3); per-phone failure counter maintained in Redis (`lock:fail:{phone}`).

## Main Scenario
1. Each failed password login increments the per-phone failure counter (`INCR`) inside the login path (FR-001).
2. On the fifth consecutive failure the counter reaches 5 and a 15-minute expiry is set on it — the account is now locked (BR-AUTH-04).
3. The lock event is logged and an audit entry is written for the privileged security action (FR-001).
4. Further login attempts check the lock **before** verifying credentials and are refused with `ACCOUNT_LOCKED` plus a retry-after hint (BR-AUTH-04).
5. A lockout notice is sent to the user through the notification pipeline (FR-001).
6. A successful login after the window deletes the counter, resetting it for the next cycle (BR-AUTH-04).

## Alternative Scenarios
- **A1 — Fewer than five failures:** counter below 5 → normal credential verification continues; a successful login deletes the counter and the streak resets (BR-AUTH-04).
- **A2 — Lock expires by TTL:** the 15-minute expiry elapses → the counter is gone, login is accepted again; a new failure restarts the count (BR-AUTH-04).
- **A3 — Mixed failure sources:** failures counted per phone account, not per IP — distributed attempts against one account still accumulate toward the same limit (BR-AUTH-04).

## Exception Scenarios
- **E1 — Counter store unavailable:** the lock state cannot be read or incremented → login fails with a temporary authentication error; no lock is bypassed and no session is created (FR-001).
- **E2 — Attempts race at the boundary:** concurrent requests hitting the fifth failure → atomic `INCR` serializes them; the lock applies once, later attempts see `ACCOUNT_LOCKED` (BR-AUTH-04).
- **E3 — User locked out and unable to receive notices:** the lock still enforces server-side; the user learns of it from the retry-after response on the next attempt (BR-AUTH-04).

## Postconditions
- Success: either a session is issued with the counter cleared, or the account is locked for 15 minutes with the lock event logged.
- Failure: no session exists; the account lock state (locked/unlocked) and failure counter reflect the last attempt.

## Business Rules Applied
- BR-AUTH-04

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)
- **Related:** complements UC-003 step 2 and step 3 (failed-attempt counting and counter reset only) — login itself stays in UC-003.

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07); no human role can trigger or bypass the lock — only time expiry or a successful login clears it.
- **Data involved:** per-phone failure counter, lock events, audit entry, lockout notification.
- **External dependencies:** Redis counter store; notification pipeline for the lockout notice.

## Acceptance Criteria
- **AC-UC044-01:** Given four consecutive failed logins, when the fifth fails, then the account is locked for 15 minutes (BR-AUTH-04).
- **AC-UC044-02:** Given a locked account, when login is attempted, then `ACCOUNT_LOCKED` with retry-after is returned before credential verification (BR-AUTH-04).
- **AC-UC044-03:** Given a lock is active, when 15 minutes elapse, then login succeeds again with a fresh counter (BR-AUTH-04).
- **AC-UC044-04:** Given the fifth failure, when the lock is applied, then a lock event and audit entry are recorded (BR-AUTH-04).
