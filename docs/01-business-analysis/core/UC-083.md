# UC-083 — Enforce Audit Log Retention and Redaction

## Header Info
- **Use Case ID:** UC-083
- **Title:** Enforce Audit Log Retention and Redaction
- **Actor:** System (ACT-07) — retention housekeeping job (no interactive login)
- **Trigger:** Scheduled retention cycle (`b13.platform.audit.retention`)
- **Priority:** P1
- **Goal:** Keep audit history within retention policy — long enough for accountability, redacted where sensitive — while never violating append-only integrity.
- **Preconditions:** Audit rows written append-only with actor/action/before-after (BR-PLT-06); retention policy configured (financial records ≥5 years, DATA-REQ-003).

## Main Scenario
1. The scheduler enqueues `b13.platform.audit.retention`; the worker evaluates partitions/rows against the configured retention windows.
2. Records inside the retention window are never deleted — financial and audit data is retained at least 5 years (DATA-REQ-003).
3. Beyond the window, old partitions are archived, not row-deleted inside the window; purge attempts against protected young rows are blocked and alerted instead of executed.
4. Redaction masks secrets, tokens, OTP bodies and PII payloads from log/export views while the stored append-only entry itself is left untouched (BR-PLT-06).
5. Admin audit reads (UC-036) continue against the retained, redacted view — accountability survives, sensitive values do not leak.

## Alternative Scenarios
- **A1 — Account deletion:** Related rows are anonymized, not dropped — retention and deletion obligations reconcile (DATA-REQ-003).
- **A2 — Record within window:** Skipped by the purge path — the job's default direction is retention.
- **A3 — Archive access needed:** Archived partitions remain retrievable through the controlled audit path, not through live tables.

## Exception Scenarios
- **E1 — Retention job fails:** Retried, then dead-lettered with an alert; a failed job leaves data retained — the failure mode can over-retain, never under-retain.
- **E2 — Purge targets a young financial/audit row:** The action is blocked and alerted; data inside the ≥5-year window survives any misconfiguration (DATA-REQ-003).
- **E3 — Redaction would alter history:** Redaction is applied at view/export time only — stored entries stay append-only and unedited (BR-PLT-06).

## Postconditions
- Retention windows honored: in-window data intact, beyond-window data archived per policy (DATA-REQ-003).
- Views/exports expose no secrets or raw PII; stored audit entries unmodified (BR-PLT-06).
- UC-036 audit reads keep working on retained, redacted data.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)
- Cross-reference (spec relation): this job curates the data UC-036 reads.

## Permissions / Data / External Dependencies
- **Permissions:** Service identity (System, ACT-07) archives/redacts views only; Admin reads audit via UC-036 — no human edits audit rows.
- **Data involved:** Audit log rows/partitions, redaction masks, retention metadata, archive storage.
- **External dependencies:** BullMQ (`b13.platform.audit.retention`); partitioned audit tables; archive/object storage; alerting pipeline.

## Acceptance Criteria
- **AC-UC083-01:** Given an audit row inside its retention window, when the job runs, then it is not deleted (DATA-REQ-003).
- **AC-UC083-02:** Given a purge attempt on a young financial row, when it is attempted, then it is blocked and alerted.
- **AC-UC083-03:** Given an audit view containing a secret, when it is rendered, then the secret is redacted while the stored entry stays unedited (BR-PLT-06).
- **AC-UC083-04:** Given the retention job crashes, when retries exhaust, then data remains retained and the failure alerts.
