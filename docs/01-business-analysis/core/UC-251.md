# UC-251 — Verify the Audit Hash Chain Nightly and Alert on Tamper

## Header Info
- **Use Case ID:** UC-251
- **Title:** Verify the Audit Hash Chain Nightly and Alert on Tamper
- **Actor:** System (ACT-07) — audit chain verifier (no interactive login)
- **Trigger:** The nightly verification schedule fires
- **Priority:** P0
- **Goal:** Prove the append-only audit trail has not been altered — any tampering surfaces within a day.
- **Preconditions:** Audit entries were written with `seq`, `prev_hash` and `entry_hash` (SHA-256 over canonical fields); the chain head serializes appends; the verifier has read-only access (BR-PLT-06).

## Main Scenario
1. The nightly job recomputes `entry_hash` across entries in `seq` order.
2. Each recomputed hash is compared with the stored value; every match extends the verified prefix.
3. A full pass records the verification result (last verified seq, timestamp) and modifies no rows.
4. A mismatch at any `seq` is tamper evidence → a high-severity alert pages security/on-call immediately (BR-PLT-06).
5. The alert names the offending `seq` and entity so responders can investigate without scanning the whole trail.
6. Nothing is auto-repaired — the trail is append-only and edits are never the answer (BR-PLT-06).

## Alternative Scenarios
- **A1 — Chain intact:** the pass is recorded and no alert fires — the normal night.
- **A2 — New entries since last run:** verification always covers the whole chain to date, including them.
- **A3 — Verification job itself fails:** its failure alerts (BR-PLT-02) — a dark verifier is treated as loudly as a failed check.

## Exception Scenarios
- **E1 — Tamper detected:** mismatch → page security; no automatic repair or row deletion — investigation is manual (BR-PLT-06).
- **E2 — Appends during verification:** reads are non-blocking snapshots — verification never locks out ongoing audit writes.
- **E3 — Retention purge due the same night:** the segment being removed is verified intact before any purge — verification and purge never race the same rows.

## Postconditions
- Success: every audit row's hash matches its predecessor — the trail is proven intact and the result is timestamped.
- Failure: a mismatch means an alert is out and the tamper location is identified; the verifier modified nothing either way.

## Business Rules Applied
- BR-PLT-06, BR-PLT-02

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — read-only over audit rows; no role, human or service, updates or deletes them.
- **Data involved:** audit_log entries (`seq`, `prev_hash`, `entry_hash`), chain head row, verification result, alert.
- **External dependencies:** BullMQ nightly job; alert routing to on-call; audit append path (concurrent writer).

## Acceptance Criteria
- **AC-UC251-01:** Given an intact chain, when the nightly job runs, then it completes with a pass and modifies no rows (BR-PLT-06).
- **AC-UC251-02:** Given one altered audit row, when the chain is recomputed, then a tamper alert fires naming that `seq` (BR-PLT-06).
- **AC-UC251-03:** Given a crashing verifier, when retries exhaust, then an alert fires — verification never fails silently (BR-PLT-02).
- **AC-UC251-04:** Given audit appends in flight, when verification runs, then writes are not blocked and the pass reflects a consistent snapshot.
