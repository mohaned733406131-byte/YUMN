# UC-213 — Invalidate Every Session When a Password Reset Succeeds

## Header Info
- **Use Case ID:** UC-213
- **Title:** Invalidate Every Session When a Password Reset Succeeds
- **Actor:** System (ACT-07) — auth service (no interactive login)
- **Trigger:** A new password is submitted with a verified, single-use reset token and the reset commits
- **Priority:** P1
- **Goal:** Replace the password and kill every pre-existing session so a stolen session cannot survive a reset.
- **Preconditions:** Reset OTP verified and a single-use reset token issued; sessions exist for the account; password policy in force (BR-AUTH-02, BR-AUTH-07).

## Main Scenario
1. Client submits the new password with the reset token (`PUT /auth/password`).
2. System validates token authenticity, single use and expiry, then validates the password policy (BR-AUTH-02).
3. The new bcrypt hash is stored and the reset token is consumed.
4. Every existing session of the account is invalidated — refresh tokens die and active devices are signed out (BR-AUTH-07).
5. A mandatory security notification about the password change is queued (BR-NTF-02).
6. `204` is returned; the user re-authenticates with the new password, other devices land back on login.

## Alternative Scenarios
- **A1 — Authenticated change path:** a change made with current password + OTP step-up revokes all sessions by the same rule.
- **A2 — Expired or unknown token:** rejected with `TOKEN_EXPIRED`; password unchanged, sessions untouched; the user restarts at reset start.
- **A3 — No active sessions:** revocation is a no-op; the password still changes and the notification still goes out.

## Exception Scenarios
- **E1 — Reset token replay:** a second use of the same token is rejected; no password change occurs.
- **E2 — Notification provider down:** password change and revocation still commit; the notice retries through the queue with dead-letter alerting (BR-PLT-02).
- **E3 — Session store unreachable during revocation:** the operation fails closed — either password change + full revocation commit together, or nothing changes.

## Postconditions
- Success: the old password is invalid, the new one is active, zero pre-existing sessions survive, and the security notification is queued.
- Failure: the password is unchanged and existing sessions remain valid.

## Business Rules Applied
- BR-AUTH-07

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)

## Permissions / Data / External Dependencies
- **Permissions:** public endpoint gated by the single-use reset token (or authenticated step-up) — no session reuse after success.
- **Data involved:** password hash, reset-token record, session registry entries, security notification, audit entry.
- **External dependencies:** Redis session registry; notification pipeline for the security notice.

## Acceptance Criteria
- **AC-UC213-01:** Given an account with active sessions, when a reset completes, then every prior session is rejected at next use (BR-AUTH-07).
- **AC-UC213-02:** Given a consumed reset token, when it is replayed, then it is rejected and no password change occurs.
- **AC-UC213-03:** Given a successful reset, when it commits, then a mandatory security notification is queued (BR-NTF-02).
