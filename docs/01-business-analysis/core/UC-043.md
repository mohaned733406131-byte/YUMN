# UC-043 — Rotate Refresh Tokens and Revoke Session Families on Reuse

## Header Info
- **Use Case ID:** UC-043
- **Title:** Rotate Refresh Tokens and Revoke Session Families on Reuse
- **Actor:** System (ACT-07) — auth token service (no interactive login)
- **Trigger:** A client presents a refresh token at the token endpoint to renew an expired access token
- **Priority:** P0
- **Goal:** Renew sessions with single-use rotating refresh tokens and revoke an entire session family the moment a consumed token is replayed.
- **Preconditions:** A session exists (issued by UC-003); refresh token within its 7-day lifetime (C-08); session registry (Redis) reachable.

## Main Scenario
1. Client sends a refresh request with its stored token (conceptual `POST /auth/refresh`).
2. System looks the token up in the session registry, checks lifetime (7 days, C-08) and consumption flag.
3. If unused: mark it consumed (single-use), issue a new access/refresh pair, and invalidate the old cookie — rotation on every use (BR-AUTH-05).
4. The renewed pair drives further access; other sessions of the same user are untouched (5-device cap handled in UC-003).
5. If the token is already consumed (reuse detected): revoke the whole session family — every refresh token and access token descending from that lineage dies (BR-AUTH-05).
6. System sends the user a reuse alert (mandatory security notification) and records the event (BR-AUTH-05, FR-001).

## Alternative Scenarios
- **A1 — Access token still valid:** client keeps using it; no refresh call is made, rotation waits until expiry (C-08).
- **A2 — Session already ended:** token family was removed by logout or password reset → refresh rejected; client returns to login (UC-003).
- **A3 — Two devices of one user:** each device owns its own family; rotation or revocation in one family never affects the other (BR-AUTH-05).

## Exception Scenarios
- **E1 — Stolen/replayed refresh token:** consumed token presented again → family revoked, user alerted; no attacker session survives (BR-AUTH-05).
- **E2 — Session store outage:** registry unreachable → refresh fails closed with a temporary error; no pair is issued, client retries (FR-001).
- **E3 — Renewal response lost:** client retries with the just-consumed token → treated as reuse → family revoked; user re-authenticates via UC-003 (BR-AUTH-05).
- **E4 — Token older than 7 days:** lifetime check fails → rejected; full re-login required (C-08).

## Postconditions
- Success: old token consumed, new pair active, session family continues with a new lineage.
- Reuse detected: entire session family revoked, user alerted, no active session remains for that family; audit trail records the event.

## Business Rules Applied
- BR-AUTH-05

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)
- **Related:** complements UC-003 step 3 (token issue only) — rotation and family revocation live here.

## Permissions / Data / External Dependencies
- **Permissions:** service identity only (ACT-07) — no interactive login; the token service writes only its own session/token records.
- **Data involved:** refresh-token records, session families, session registry entries, security alert, audit entry.
- **External dependencies:** Redis session store; notification pipeline for the reuse alert (B10).

## Acceptance Criteria
- **AC-UC043-01:** Given an unused refresh token, when presented, then a new pair is issued and the old token is unusable afterward (BR-AUTH-05).
- **AC-UC043-02:** Given a previously consumed refresh token, when replayed, then the entire session family is revoked.
- **AC-UC043-03:** Given a replay is detected, when revocation runs, then the user receives a reuse alert.
- **AC-UC043-04:** Given a refresh token older than 7 days, when presented, then it is rejected and no pair is issued (C-08).
