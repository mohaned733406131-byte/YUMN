# UC-033 — Manage Orders & Disputes

## Header Info
- **Use Case ID:** UC-033
- **Title:** Manage Orders & Disputes
- **Actor:** Admin (ACT-04)
- **Trigger:** An order escalation reaches the admin queue: SLA breach (BR-ORD-10), 3rd failed delivery (BR-SHP-06), dispute opened, or return-policy conflict
- **Priority:** P0
- **Goal:** Resolve order exceptions and disputes fairly, with escrow frozen/unfrozen and every action audited.
- **Preconditions:** Admin authenticated with order/dispute scope; target order/sub-order exists (any state, per override rights DOC-OVR-007).

## Main Scenario
1. Admin opens the operations queue → client `GET /admin/orders` (filters: state, SLA age, dispute, escalation) with full timelines (BR-ORD-09 platform scope).
2. Admin opens a case → sees master/sub-order states, history (BR-ORD-03), payments/ledger refs, delivery attempts, return policy snapshot.
3a. **Dispute raised:** `DELIVERED/COMPLETED → DISPUTED` freezes escrow for affected sub-orders (BR-ORD-05); admin gathers evidence from both sides (support threads UC-014).
3b. Admin resolves: "for buyer" → `DISPUTED → REFUNDED` (refund flow: escrow first, then vendor payable, BR-ESC-07; wallet credit ≤3 business days BR-RET-04); "for vendor" → `DISPUTED → COMPLETED` (escrow releases per BR-ESC-02). Audit entry required (DOC-SA-010, BR-PLT-06).
4. Admin may cancel pre-dispatch orders (BR-ORD-04), release/reassign courier jobs, or force state corrections — always via guarded transitions (never editing history, BR-ORD-03).
5. Return-policy conflicts: admin is final arbiter; decision written to audit log (BR-RET-06).
6. Notifications to affected parties on every resolution (BR-NTF-01, BR-NTF-04).

## Alternative Scenarios
- **A1 — SLA escalation:** Unconfirmed 24 h order → admin contacts vendor, confirms or cancels+refunds (BR-ORD-10; never silent auto-cancel).
- **A2 — Failed-attempt escalation (3rd):** Admin coordinates redelivery or customer contact (BR-SHP-06).
- **A3 — Frozen/suspended vendor orders:** Vendor suspended mid-order → orders frozen pending review (BR-VND-04); admin decides continuation or refund.

## Exception Scenarios
- **E1 — Concurrent transitions:** Vendor/customer act simultaneously → optimistic locking; loser gets `409 STATE_CONFLICT` (DOC-SA-010 §5).
- **E2 — Refund engine failure:** Resolution queued but refund job fails → BullMQ retry 3× then DLQ alert (BR-PLT-02); reconciliation flags drift (BR-ESC-08); no double refund (BR-PAY-08).
- **E3 — Insufficient escrow at buyer-win refund:** Draw from vendor payable (BR-ESC-07); record liability; vendor sees it in UC-022.

## Postconditions
- Dispute resolved (`COMPLETED` or `REFUNDED`) with audit trail; escrow unfrozen accordingly (BR-ORD-05).
- History rows appended, never overwritten (BR-ORD-03); parties notified.

## Permissions / Data / External Dependencies
- **Permissions:** Admin order-override scope; no direct wallet ledger writes (append-only, DOC-OVR-007); Super Admin supersedes (UC-037).
- **Data involved:** Orders, disputes, escrow, ledger references, status history, audit log.
- **External dependencies:** Escrow/refund engines (B07); support ticketing (B13); notifications (B10).

## Acceptance Criteria
- **AC-UC033-01:** Given an open dispute, when raised, then escrow release freezes for affected sub-orders (BR-ORD-05).
- **AC-UC033-02:** Given a buyer-win resolution, when executed, then state becomes `REFUNDED` with balanced ledger entries (BR-PAY-06, BR-ESC-07).
- **AC-UC033-03:** Given any admin override, when applied, then history is appended (not edited) and an audit row exists (BR-ORD-03, BR-PLT-06).
