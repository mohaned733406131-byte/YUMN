# UC-286 — Verify Refund Credits Within the 3-Business-Day SLA

## Header Info
- **Use Case ID:** UC-286
- **Title:** Verify Refund Credits Within the 3-Business-Day SLA
- **Actor:** Admin (ACT-04)
- **Trigger:** A customer or support case claims a refund has not landed, or finance runs the standing SLA check on recent `REFUNDED` orders
- **Priority:** P1
- **Goal:** Prove, per refund, whether the wallet credit happened within 3 business days of `REFUNDED` — and act when it did not.
- **Preconditions:** Orders have reached `REFUNDED` (return or cancellation path); refund receipt endpoint reachable (API-WAL-014); credit rule in force (BR-RET-04).

## Main Scenario
1. Admin locates the order (`GET /orders/{id}/refund`, API-WAL-014) — owner customer or Admin may read it.
2. System returns per sub-order refund rows: `status` (`PENDING`/`COMPOSED`/`CREDITED`), amounts, `walletCredit: { reference, creditedAt? }` and `expectedCreditBy`.
3. Admin compares `creditedAt` (or today, if still pending) against `expectedCreditBy` — the 3-business-day bound from `REFUNDED` (BR-RET-04).
4. Admin confirms the credit target is the wallet, never an external cash-out (BR-PAY-07), and that `commissionReversed` reflects the proportional reversal when applicable.
5. On-SLA refunds are closed out; breached ones are escalated to finance with the receipt as evidence.

## Alternative Scenarios
- **A1 — Credit already posted:** `status: CREDITED` with `creditedAt` inside the window → verification passes, no action.
- **A2 — Refund still pending inside the window:** `expectedCreditBy` not yet reached → marked "on track", re-checked at the next SLA run.
- **A3 — Partial composition:** shipping refunded or not per fault rules shows in the amounts; Admin verifies the composition before judging the SLA (BR-RET-04 applies from `REFUNDED` regardless of composition).

## Exception Scenarios
- **E1 — Credit past `expectedCreditBy`:** SLA breach confirmed → Admin opens a finance escalation; the wallet credit is still owed to the customer (BR-RET-04).
- **E2 — Order not found / not readable:** `NOT_FOUND` / `TIMELINE_ACCESS_DENIED` (API-WAL-014) → no figures shown, nothing changed.
- **E3 — Refund marked credited but ledger disagrees:** flagged as a ledger-integrity alarm rather than closed — money data is never auto-corrected; finance resolves via compensating entries.

## Postconditions
- Success: each inspected refund carries a verified SLA verdict with the receipt as evidence; no balance was modified by the check.
- Failure/breach: the credit obligation stands unchanged and is escalated — no half-posted wallet row, no phantom credit.

## Business Rules Applied
- BR-RET-04, BR-PAY-07

## Related Requirements
- FR-013 (Wallet & Payment Processing)
- FR-016 (Returns & Refunds)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) read on refund receipts; customer reads only their own order (API-WAL-014).
- **Data involved:** refund rows, wallet credit references, order refund status, ledger entries (read).
- **External dependencies:** wallet/ledger engine (block B07); return and cancellation flows that trigger refunds.

## Acceptance Criteria
- **AC-UC286-01:** Given a `REFUNDED` order, when the receipt is read, then per sub-order status, amounts and `expectedCreditBy` are returned (API-WAL-014).
- **AC-UC286-02:** Given a credit posted within 3 business days of `REFUNDED`, when verified, then the refund passes the SLA check (BR-RET-04).
- **AC-UC286-03:** Given a credit still missing after the bound, when verified, then the refund is reported as breached and escalated (BR-RET-04).
- **AC-UC286-04:** Given any refund, when the credit target is inspected, then it is the customer's wallet and never an external cash-out (BR-PAY-07).
