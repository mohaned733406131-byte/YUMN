# UC-285 — Track Open Disputes and Their Frozen Escrow Exposure

## Header Info
- **Use Case ID:** UC-285
- **Title:** Track Open Disputes and Their Frozen Escrow Exposure
- **Actor:** Admin (ACT-04)
- **Trigger:** Operations or finance needs the current backlog of open disputes and how much escrow is held out of circulation because of them
- **Priority:** P1
- **Goal:** See every open dispute with its frozen-escrow flag and due date so exposure is quantified and aged cases are worked before they breach.
- **Preconditions:** Disputes exist in open states; Admin holds platform-wide dispute read (API-RET-014); escrow freezes follow the dispute rule (BR-ORD-05).

## Main Scenario
1. Admin opens the dispute list (`GET /disputes`, API-RET-014, offset mode via `?page` for the admin surface).
2. System returns each case with `orderId`, `subOrderId`, `state`, `openedBy`, `openedAt`, `escrowFrozen` and `dueAt`.
3. Admin filters to open states and sorts by `dueAt` to find cases nearest their evidence deadline.
4. Admin cross-checks the dispute queue depth against the platform dashboard (`GET /admin/dashboard`, API-ANL-006) so backlog and exposure agree.
5. Admin drives follow-up — evidence request (UC-284) or arbitration (UC-283) — for each aged case.

## Alternative Scenarios
- **A1 — Exposure drill for finance:** the same list is read to total the frozen sub-orders before a payout batch is approved — frozen cases never release (BR-ORD-05).
- **A2 — Resolved cases only:** Admin filters to resolved states to confirm escrow has unfrozen and the refund or release path started (API-RET-017).
- **A3 — Moderator watching the queue:** Moderator may read the list within scope; arbitration and evidence actions stay with Admin (BR-ORD-09).

## Exception Scenarios
- **E1 — Invalid filter/page input:** `VALIDATION_ERROR` → no data returned, no state touched (API-RET-014).
- **E2 — Case not found after the list was cached:** `NOT_FOUND` on detail → Admin refreshes the list; the backlog figures come from the live store, never a stale copy.
- **E3 — Dispute store unavailable:** the list read fails with a temporary error → exposure is reported as unavailable rather than estimated; retries follow the standard read path.

## Postconditions
- Success: Admin holds an accurate, current picture of open disputes and the escrow frozen behind them; no case state changed by reading.
- Failure: no view is produced and nothing is written — exposure is never guessed from partial data.

## Business Rules Applied
- BR-ORD-05, BR-ORD-09

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) platform-wide dispute read; parties see only their own cases (API-RET-014).
- **Data involved:** dispute records, escrow freeze flags, due dates, sub-order states, dashboard aggregates.
- **External dependencies:** escrow ledger (block B07); platform dashboard rollups (API-ANL-006).

## Acceptance Criteria
- **AC-UC285-01:** Given open disputes, when Admin lists them, then every item shows `escrowFrozen` and `dueAt` (API-RET-014).
- **AC-UC285-02:** Given a disputed sub-order, when its escrow is inspected, then release is frozen until admin resolution (BR-ORD-05).
- **AC-UC285-03:** Given an invalid filter, when the list is requested, then `VALIDATION_ERROR` is returned and no data leaks.
- **AC-UC285-04:** Given the tracking view, when it is refreshed, then dispute counts match the dashboard queue depth (API-ANL-006).
