# UC-272 — Trace a Master Order to Its Sub-Orders During an Investigation

## Header Info
- **Use Case ID:** UC-272
- **Title:** Trace a Master Order to Its Sub-Orders During an Investigation
- **Actor:** Admin (ACT-04)
- **Trigger:** An investigation starts from a master order — finance discrepancy, dispute, or customer complaint spanning several vendors
- **Priority:** P2
- **Goal:** Walk master → sub-orders → money and state per vendor, proving totals reconcile and each sub-order's state is explainable.
- **Preconditions:** Master order exists (one master per checkout, one sub-order per vendor, BR-ORD-02); Admin authenticated with scoped order read (BR-ORD-09); ledger rows readable in aggregate (Admin has no raw balance write, ever).

## Main Scenario
1. Admin opens the master (`GET /orders/{id}`, API-ORD-004 with Admin projection) → sub-orders with `storeId`, state, items, totals, and escrow status.
2. Admin checks the structural invariant: master total equals the sum of sub-order totals (BR-ORD-02, C-10) — payment and escrow sit at master level, fulfilment per sub-order.
3. Admin expands each sub-order's timeline (API-ORD-005) to explain its current state with append-only history (BR-ORD-03).
4. Admin traces money: wallet receipt and `ledgerReference` at master level, escrow hold/release eligibility per sub-order (BR-ESC-01, BR-ESC-02).
5. Admin confirms the aggregation rule: master `COMPLETED` requires every sub-order `COMPLETED` or `REFUNDED` (BR-ORD-07), and the investigation note records any sub-order that breaks expectation.

## Alternative Scenarios
- **A1 — Single-vendor order:** exactly one sub-order → the same trace collapses to one branch; totals must still match (BR-ORD-02).
- **A2 — Vendor suspended mid-order:** that sub-order is frozen pending review (BR-VND-04) while siblings continue; the trace records the freeze as the explanation.
- **A3 — Dispute on one branch:** escrow is frozen only for the affected sub-order (BR-ORD-05) — unaffected branches keep their release schedule (BR-ESC-02).

## Exception Scenarios
- **E1 — Totals do not reconcile:** master/Σ mismatch is a data-quality event → flagged for reconciliation (J5, DQ-18) rather than corrected by hand; no ledger row is edited (BR-PAY-06).
- **E2 — Foreign or unknown order:** `404 NOT_FOUND` / `403` → the trace ends without disclosing existence (rbac.md P7).
- **E3 — Partial projection for another party:** a vendor or moderator view masks what their scope excludes (BR-ORD-09) → Admin uses the platform-scope projection for the full trace.

## Postconditions
- A trace record exists: master totals verified against Σ sub-order totals, each sub-order state explained by its history (BR-ORD-02, BR-ORD-03).
- Nothing was mutated — the investigation is read-only; discrepancies are flagged for their own corrective flows.

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) platform-scope order read (rbac.md row 3); ownership still excludes cross-customer peeking by non-admins (DATA-REQ-008).
- **Data involved:** master order, sub-orders, totals breakdown, payment receipt, ledger references, escrow rows, status history.
- **External dependencies:** wallet/escrow reads (API-WAL-009); reconciliation job J5 for total verification (data-quality.md §5).

## Acceptance Criteria
- **AC-UC272-01:** Given a multi-vendor order, when the master is opened, then one sub-order per vendor is listed with state, totals, and escrow status (BR-ORD-02, C-10).
- **AC-UC272-02:** Given the trace, when totals are compared, then master total equals Σ sub-order totals (BR-ORD-02).
- **AC-UC272-03:** Given each sub-order, when its history is read, then the current state is explained by append-only entries (BR-ORD-03).
- **AC-UC272-04:** Given an unknown order id, when the trace is requested, then `404 NOT_FOUND` is returned with no data disclosure.
