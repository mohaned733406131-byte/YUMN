# UC-282 — Pull Delivery Proof for a Dispute Review

## Header Info
- **Use Case ID:** UC-282
- **Title:** Pull Delivery Proof for a Dispute Review
- **Actor:** Admin (ACT-04)
- **Trigger:** A dispute review needs the delivery-side proof (code verification, timestamp, courier identity, optional photo) for a delivered sub-order
- **Priority:** P2
- **Goal:** Retrieve the complete, read-only delivery proof and attempt history so the dispute can be judged on verified facts.
- **Preconditions:** Dispute open on a `DELIVERED`/`COMPLETED` sub-order (BR-ORD-05); delivery record exists for the sub-order; Admin holds scoped timeline read (BR-ORD-09); evidence window still open (API-RET-016).

## Main Scenario
1. Admin opens the dispute case (`GET /disputes/{id}`, API-RET-015) and notes the `orderId`/`subOrderId` it freezes (BR-ORD-05).
2. Admin reads the delivery detail for that sub-order (`GET /deliveries/{id}`, API-SHP-003).
3. System returns addresses, attempt log, code status and `proof: { photoUrl?, verifiedAt? }` — proof = code + timestamp + courier identity, photo optional (BR-SHP-07).
4. Admin cross-checks `verifiedAt` and each attempt outcome against the dispute ground; recipient contact is masked in the payload.
5. Admin records the finding for arbitration (UC-283) or attaches it as case evidence (UC-284); the delivery record itself is never modified.

## Alternative Scenarios
- **A1 — No photo attached:** proof remains complete — the photo is stored but never required and never gates `DELIVERED` (BR-SHP-07).
- **A2 — Delivery ended by admin transition (no code scan):** attempt history and order status history show the override; Admin notes the missing `verifiedAt` instead of inventing proof.
- **A3 — Escalated delivery (3 failed attempts):** the attempt log carries the escalation to admin review with the full timeline, which the dispute review consumes directly (BR-SHP-06).

## Exception Scenarios
- **E1 — Delivery not found or out of scope:** `NOT_FOUND` / `TIMELINE_ACCESS_DENIED` (API-SHP-003) → nothing read beyond scope, nothing written (BR-ORD-09).
- **E2 — Proof photo unreachable:** photo fetch fails while metadata loads → code/timestamp/courier proof is still returned; review continues on code proof (BR-SHP-07).
- **E3 — Dispute already resolved:** detail stays readable for the record, but attaching the pull as evidence returns `STATE_CONFLICT` (API-RET-016).

## Postconditions
- The delivery proof and attempt history are in the Admin's hands; the delivery state, `version` and status history are untouched — the pull is read-only.
- The dispute case can be judged on verified proof; escrow stays frozen until Admin resolves it (BR-ORD-05).

## Business Rules Applied
- BR-SHP-07, BR-ORD-09, BR-ORD-05, BR-SHP-06

## Related Requirements
- FR-015 (Shipping & Delivery)
- FR-016 (Returns & Refunds)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) delivery-detail read (API-SHP-003 roles: assignee courier, Admin); Moderator has no delivery-detail scope.
- **Data involved:** delivery record, code attempts, proof photo reference, dispute case, order status history (read).
- **External dependencies:** MinIO object store for the optional proof photo (DEP-07); dispute store.

## Acceptance Criteria
- **AC-UC282-01:** Given a dispute on a delivered sub-order, when Admin opens the delivery detail, then code, timestamp, courier identity and the attempt log are returned (BR-SHP-07).
- **AC-UC282-02:** Given no photo was ever attached, when the proof is pulled, then the proof is complete and no photo is demanded (BR-SHP-07).
- **AC-UC282-03:** Given a delivery outside Admin scope, when the call is made, then access is denied and no data is disclosed (BR-ORD-09).
- **AC-UC282-04:** Given the proof is retrieved, when the review ends, then delivery state and `version` are unchanged.
