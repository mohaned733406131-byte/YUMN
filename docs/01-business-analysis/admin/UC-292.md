# UC-292 — Disable a Store Coupon for Promotion Abuse

## Header Info
- **Use Case ID:** UC-292
- **Title:** Disable a Store Coupon for Promotion Abuse
- **Actor:** Admin (ACT-04)
- **Trigger:** A vendor-created coupon is being abused (stacking attempts, discount farming, refund gaming) and must stop taking effect immediately
- **Priority:** P1
- **Goal:** Disable the offending store coupon platform-wide with a reason, so no further order can redeem it.
- **Preconditions:** Coupon exists and is `ACTIVE`; the coupon is store-scoped or platform-scoped — Admin may disable either (BR-PRM-03); abuse evidence is available; a reason is ready.

## Main Scenario
1. Admin locates the coupon in the platform-wide list (`GET /admin/coupons`, API-CNT-015) filtered by `scope`/`status`.
2. Admin confirms current usage: `usageCount`, `usageLimit`, validity window and discount percent (BR-PRM-01).
3. Admin disables it (`POST /admin/coupons/{id}/disable` with `{ reason }`, API-CNT-017).
4. System flips status to `DISABLED` with `disabledAt` and writes the audit entry (BR-PLT-06).
5. In-flight carts holding the code get `COUPON_INVALID` on their next validation — no order redeems it after the disable.

## Alternative Scenarios
- **A1 — Already expired or fully used:** disable is unnecessary; Admin records the finding without a status change (`STATE_CONFLICT` handled as "no action").
- **A2 — Platform coupon instead of store coupon:** same endpoint and reason flow — Admin owns both scopes (BR-PRM-03).
- **A3 — Follow-up enforcement:** the pattern is escalated into the wider abuse investigation (UC-293) and, if warranted, the vendor is notified.

## Exception Scenarios
- **E1 — Missing reason:** `REASON_REQUIRED` → coupon stays active; every disable is reasoned (API-CNT-017).
- **E2 — Coupon not found:** `NOT_FOUND` → nothing changed (API-CNT-017).
- **E3 — Moderator attempts the disable:** `FORBIDDEN` → status untouched; moderation of coupons is Admin-scoped (API-CNT-017).

## Postconditions
- Success: the coupon is `DISABLED` with timestamp and one audit entry; no subsequent order can apply it.
- Failure: the coupon remains `ACTIVE` exactly as before — no partial state, no cart orphaned.

## Business Rules Applied
- BR-PRM-03, BR-PRM-01, BR-PLT-06

## Related Requirements
- FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) coupon write (API-CNT-017); Moderator read-only; vendor manages only its own coupons outside this endpoint.
- **Data involved:** coupon records (status, usage counters, window), audit entries, in-flight cart validations.
- **External dependencies:** coupon validation path in checkout (block B05); append-only audit log (API-ADM-024).

## Acceptance Criteria
- **AC-UC292-01:** Given an active coupon, when Admin disables it with a reason, then status becomes `DISABLED` with `disabledAt` (API-CNT-017).
- **AC-UC292-02:** Given a disabled coupon, when an in-flight cart validates it, then the cart receives `COUPON_INVALID`.
- **AC-UC292-03:** Given a disable without a reason, when submitted, then `REASON_REQUIRED` is returned and the coupon stays active.
- **AC-UC292-04:** Given any disable, when it completes, then exactly one audit entry records Admin, coupon and reason (BR-PLT-06).
