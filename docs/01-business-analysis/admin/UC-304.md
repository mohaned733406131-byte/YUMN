# UC-304 — Audit the Evidence Entry of a Completed Purge Run

## Header Info
- **Use Case ID:** UC-304
- **Title:** Audit the Evidence Entry of a Completed Purge Run
- **Actor:** Admin (ACT-04)
- **Trigger:** A purge run completes and its evidence entry must be checked for completeness (retention §6 step 7, principle R4)
- **Priority:** P2
- **Goal:** Verify each completed run produced the full evidence record — actor, class, scope, counts, duration, timestamp — so deletions are provable after the fact.
- **Preconditions:** Purge run finished; evidence entry written by System; the backup residual window is stated alongside deletions (retention §5.7); Admin holds audit read.

## Main Scenario
1. Admin opens the audit log filtered to purge-run actions (`GET /admin/audit-log` with action/`from`/`to`, API-ADM-024).
2. Admin inspects the run's evidence entry for the required fields: actor (`System`), retention class, scope, row/object counts, duration, timestamp.
3. Admin cross-checks the row count against the weekly report's per-class figure for the same run (UC-300).
4. Admin confirms the entry states the backup residual window, so downstream consumers know purge is not yet visible in backups.
5. Gaps are raised to the job owner; complete entries are signed off as the period's deletion evidence.

## Alternative Scenarios
- **A1 — Counts reconcile:** report and evidence agree → sign-off recorded for the run.
- **A2 — Count mismatch:** evidence says N, report says M → treated as an integrity issue and investigated before sign-off — figures are never adjusted to match.
- **A3 — Multiple runs in one day:** each run carries its own entry; Admin audits them individually rather than sampling one.

## Exception Scenarios
- **E1 — Missing fields in the evidence entry:** incomplete evidence → the run is flagged unproven; the purge result is not accepted as evidenced (retention §6 step 7).
- **E2 — Evidence entry absent entirely:** escalated as a control failure — a run without evidence violates the runbook, and no "assumed clean" status is recorded.
- **E3 — Audit log read denied/unavailable:** `FORBIDDEN`/temporary failure → audit paused; evidence is never gathered from an out-of-scope path.

## Postconditions
- Success: the purge run carries complete, verified deletion evidence tied to its counts; the audit trail gained only the read activity, no new writes by Admin.
- Failure: the run is marked unevidenced and escalated — no fabricated evidence, no edited history.

## Business Rules Applied
- BR-PLT-06 (the evidence entry is an append-only audit record — read, never rewritten)

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) audit read; System alone writes the purge evidence entry; no role edits audit rows.
- **Data involved:** purge evidence entries, weekly report figures, retention class definitions (read).
- **External dependencies:** daily purge job (BR-PLT-01); append-only audit store (API-ADM-024); backup window statement (retention §5.7).

## Acceptance Criteria
- **AC-UC304-01:** Given a completed purge run, when its evidence entry is read, then actor, class, scope, counts, duration and timestamp are all present.
- **AC-UC304-02:** Given the weekly report figure for the run, when compared to the evidence count, then the two agree exactly.
- **AC-UC304-03:** Given a run missing its evidence entry, when the audit is performed, then it is flagged as unproven and escalated.
- **AC-UC304-04:** Given the audit completes, when the log is re-read, then no entry was modified by the review (BR-PLT-06).
