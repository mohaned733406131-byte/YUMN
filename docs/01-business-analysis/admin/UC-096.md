# UC-096 — Suspend a Store

## Header Info
- **Use Case ID:** UC-096
- **Title:** Suspend a Store
- **Actor:** Admin (ACT-04) — vendor operations scope
- **Trigger:** Admin suspends a store for policy, fraud or legal reasons
- **Priority:** P0
- **Goal:** Stop a store trading immediately with the full suspension cascade while keeping the action reversible and audited.
- **Preconditions:** Admin authenticated with suspend permission (API-ADM-012 `ADMIN`); target store exists and is not already suspended; a mandatory reason is supplied.

## Main Scenario
1. Admin opens the store (UC-094) → Suspend → mandatory reason plus optional note.
2. Client `POST /admin/stores/{id}/suspend` (API-ADM-012).
3. System applies the suspension cascade (BR-VND-04): products delisted from the storefront, new orders blocked, existing orders frozen, payouts held — the response reports `productsDelisted` and `ordersBlocked`.
4. An append-only audit entry records reason and before/after state (BR-PLT-06) and `auditId` returns; the platform-wide follow-through across catalog, orders and payouts is owned by UC-072.
5. A moderation-level content hide stays a separate reversible action (UC-032) — it is not a store suspension.

## Alternative Scenarios
- **A1 — Content-only violation:** Admin hides the offending content instead (UC-032) and leaves the store trading.
- **A2 — Already suspended:** `STATE_CONFLICT`; Admin reviews the existing suspension rather than duplicating it.

## Exception Scenarios
- **E1 — Permission denied:** Moderator → `403 FORBIDDEN`; nothing changes.
- **E2 — Missing reason:** `REASON_REQUIRED`; no state change and no audit row.
- **E3 — Concurrent re-activation:** Another admin activates meanwhile → `STATE_CONFLICT`, refetch and re-decide.
- **E4 — Open orders and disputes:** Existing orders freeze and payouts hold rather than cancel — customers keep fulfillment of in-flight orders (BR-VND-04).

## Postconditions
- The store is `SUSPENDED` with all four BR-VND-04 effects applied; existing orders frozen, not cancelled.
- One audit entry exists (BR-PLT-06); no refund is triggered directly by this action.

## Business Rules Applied
- BR-VND-04, BR-PLT-06

## Related Requirements
- FR-007 (Vendor Onboarding & KYC)
- FR-020 (Platform Administration, Settings & Audit)
- Cross-reference: rel UC-072 (cascade across catalog, orders and payouts).

## Permissions / Data / External Dependencies
- **Permissions:** `ADMIN` only; moderation hide is separately scoped (UC-032).
- **Data involved:** Store status, product listings, order flags, payout holds, audit entry.
- **External dependencies:** Storefront and search surfaces (delisting propagates); audit writer (BR-PLT-06).

## Acceptance Criteria
- **AC-UC096-01:** Given an active store, when suspend is posted with a reason, then status becomes `SUSPENDED` and products are delisted (BR-VND-04).
- **AC-UC096-02:** Given in-flight orders, when suspended, then existing orders freeze and payouts hold — nothing is cancelled.
- **AC-UC096-03:** Given the action, when completed, then an `auditId` returns with before/after state (BR-PLT-06).
- **AC-UC096-04:** Given no reason, when posted, then `REASON_REQUIRED` returns and nothing changes.
