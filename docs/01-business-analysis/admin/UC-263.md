# UC-263 — Confirm Rating Recomputation After a Review Is Hidden

## Header Info
- **Use Case ID:** UC-263
- **Title:** Confirm Rating Recomputation After a Review Is Hidden
- **Actor:** Admin (ACT-04)
- **Trigger:** A review was hidden for abuse or inappropriateness and the operator must confirm the affected averages were actually recomputed (BR-REV-04)
- **Priority:** P2
- **Goal:** Prove that the hidden review is excluded from product and store rating summaries, with the count shown alongside the new average.
- **Preconditions:** The review is already hidden with an audit entry (`POST /admin/moderation/{type}/{id}/hide`, API-ADM-028); the incremental recompute job is scheduled (BR-REV-05); product/store exist.

## Main Scenario
1. Admin confirms the hide landed: response `hidden: true`, `hiddenBy`, and `auditId` for the reason supplied (API-ADM-028, BR-REV-04).
2. System enqueues the incremental rating recompute for the affected product (BR-REV-05).
3. Admin reads the public review feed (`GET /products/{slug}/reviews`, API-CAT-019) → the hidden review is absent from items and `ratingSummary` (average, count, distribution).
4. Admin reads the store projection (API-VND-012 / API-VND-006) → store rating reflects the recomputed average of visible ratings with the review count shown (BR-REV-05).
5. Admin records the confirmation against the moderation action; if the job has not landed yet, the check repeats rather than being marked passed.

## Alternative Scenarios
- **A1 — Restore later:** unhide (`POST /admin/moderation/{type}/{id}/restore`, API-ADM-029) → the same recompute path re-includes the review and averages return to the prior basis (BR-REV-04).
- **A2 — Hidden product, not review:** the delisting path applies instead and rating recompute is out of scope (UC-264).
- **A3 — Several reviews hidden:** each hide enqueues its own recompute; Admin verifies the final summary once the queue drains.

## Exception Scenarios
- **E1 — Recompute job fails:** BullMQ retries 3× with backoff, then dead-letters and alerts (BR-PLT-02) → Admin does not sign off until the summary matches visible reviews.
- **E2 — Already hidden:** second hide returns `STATE_CONFLICT`; the existing audit entry stands (API-ADM-028).
- **E3 — Hide without reason:** `REASON_REQUIRED` → nothing is hidden and no recompute is needed (BR-REV-04 requires the audited reason).

## Postconditions
- Product and store summaries exclude the hidden review; counts match the visible set (BR-REV-05).
- The moderation action retains exactly one audit entry with its reason; no review content was deleted.

## Business Rules Applied
- BR-REV-04, BR-REV-05, BR-PLT-02

## Related Requirements
- FR-006 (Reviews & Ratings)

## Permissions / Data / External Dependencies
- **Permissions:** Admin/Moderator moderation scope (API-ADM-027/028); this UC only verifies — hide/restore already happened.
- **Data involved:** review rows (`hidden` flag), product rating summary, store rating projection, moderation audit entries.
- **External dependencies:** incremental recompute job (BullMQ, BR-PLT-02); cached store rating (NFR-004).

## Acceptance Criteria
- **AC-UC263-01:** Given a hidden review, when the public review feed is read, then that review is absent from items and `ratingSummary` (BR-REV-05).
- **AC-UC263-02:** Given the recompute ran, when the store projection is read, then the average covers only visible ratings with the count shown (BR-REV-05).
- **AC-UC263-03:** Given the recompute job fails three times, when the DLQ alert fires, then no sign-off is recorded (BR-PLT-02).
- **AC-UC263-04:** Given the hide action, when it completes, then one audit entry with the reason exists (BR-REV-04).
