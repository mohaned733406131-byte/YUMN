# UC-260 — Review a Target's Recent Administrative Actions Before Enforcement

## Header Info
- **Use Case ID:** UC-260
- **Title:** Review a Target's Recent Administrative Actions Before Enforcement
- **Actor:** Admin (ACT-04)
- **Trigger:** An enforcement action (suspend, revoke role, freeze, moderation) is proposed against a user and the operator wants the target's recent footprint first
- **Priority:** P2
- **Goal:** Give the operator a quick, audited view of what the target has recently done and who else is implicated, so enforcement is proportionate and evidence-backed.
- **Preconditions:** Admin authenticated with user-directory and audit read (API-ADM-001/002/024); target account exists; enforcement itself is a separate, reason-bearing use case.

## Main Scenario
1. Admin opens the target (`GET /admin/users/{id}`, API-ADM-002) from the user directory.
2. System returns the profile projection plus `recentActions: [ { at, action, actorId } ]` and the active-session count for that user.
3. Admin cross-reads the audit stream filtered by `targetId`/`actorId` (API-ADM-024) to see privileged and money actions with before/after status (BR-PLT-06).
4. Admin checks the target's role catalog (`assignableRoles`) and store/KYC projection so the decision accounts for what the account could have touched (FR-002).
5. Admin records the review outcome as the evidence basis for enforcement; this UC only reads — no suspend, revoke, or freeze happens here.

## Alternative Scenarios
- **A1 — Target is the final Super Admin:** `LAST_SUPER_ADMIN` protections apply → enforcement is refused downstream; the review flags the identity as protected (rbac.md §3, UC-037).
- **A2 — Target is a department bundle holder:** actions are scoped to their ORG/ROLE bundle (rbac.md §11) → review focuses on that scope rather than platform-wide activity.
- **A3 — No recent actions:** empty `recentActions` → review completes with a clean footprint; enforcement proceeds on external evidence only.

## Exception Scenarios
- **E1 — Target not found:** `404 NOT_FOUND` → nothing is displayed and no enforcement reference is created.
- **E2 — Caller lacks read scope:** `403 FORBIDDEN` → the review cannot start; Moderator sees only its permitted slices (rbac.md §4).
- **E3 — Target suspended concurrently:** another operator acted first → the projection shows `SUSPENDED`; a duplicate enforcement attempt would fail `STATE_CONFLICT`.

## Postconditions
- A review record exists linking the target, the `recentActions` window, and the audit range consulted.
- No state of the target account, roles, or wallet was changed by this use case.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-002 (Roles, Permissions & Access Control), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) directory + platform-scope audit read; ownership/role checks apply to every projection (rbac.md §3, P3).
- **Data involved:** user profile projection, `recentActions`, active sessions, audit entries, role catalog.
- **External dependencies:** audit cursor stream (API-ADM-024); user directory offset pagination (API-ADM-001).

## Acceptance Criteria
- **AC-UC260-01:** Given an existing target, when the Admin opens the profile, then `recentActions` and active-session count are returned (API-ADM-002).
- **AC-UC260-02:** Given privileged actions by the target, when the audit filter runs, then each entry shows actor, action, before/after, and `ipHash` (BR-PLT-06).
- **AC-UC260-03:** Given the review completes, when it is recorded, then the target's account, roles, and wallet are unchanged.
- **AC-UC260-04:** Given an unknown target id, when the profile is requested, then `404 NOT_FOUND` is returned and no record is created.
