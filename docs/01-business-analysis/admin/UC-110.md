# UC-110 — Create a Home Banner

## Header Info
- **Use Case ID:** UC-110
- **Title:** Create a Home Banner
- **Actor:** Admin (ACT-04)
- **Trigger:** A campaign or announcement needs a banner on a home surface
- **Priority:** P1
- **Goal:** Create a banner with localized label, surface, role targeting, and optional schedule that goes live automatically inside its window.
- **Preconditions:** Admin authenticated with content-write permission (ACT-04); banner image already uploaded via the shared upload endpoint.

## Main Scenario
1. Admin opens Content → Banners → "New banner" and enters the localized label (ar default, en parity — BR-PLT-05), `surface`, `visibleTo` roles and optional `startsAt`/`endsAt`.
2. Client sends `POST /admin/banners` (API-CNT-012) with the uploaded `imageUrl`.
3. System validates the payload (schema, surface/role values — `VALIDATION_ERROR`) and the upload limits (`PAYLOAD_TOO_LARGE`).
4. On success → `201 { …banner, active }` where `active` is computed from the schedule window; the banner appears only on the targeted surfaces for the targeted roles once in-window.

## Alternative Scenarios
- **A1 — No schedule:** Admin omits `startsAt`/`endsAt` → the banner becomes active immediately per its computed flag.
- **A2 — Future campaign:** Admin sets a future `startsAt` → created but inactive until the window opens.
- **A3 — Narrow targeting:** Admin targets one role list (e.g. CUSTOMER only) → vendors/guests never receive it.

## Exception Scenarios
- **E1 — Permission denied:** Moderator or non-admin attempts create → 403 `FORBIDDEN`; no banner persisted.
- **E2 — Validation failure:** Empty label or unsupported surface → 400 `VALIDATION_ERROR`; oversized image → 413 `PAYLOAD_TOO_LARGE` at upload; nothing created.
- **E3 — Concurrent duplicate creation:** Two admins create the same campaign banner → both persist (no uniqueness rule); the extra copy is removed via UC-112.

## Postconditions
- A banner record exists with the given targeting/schedule; its display follows the window (BR-PLT-05 localized label on render).
- No page, coupon, or order change originates from banner creation.

## Business Rules Applied
- BR-PLT-05

## Related Requirements
- FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Admin content-write scope; Moderator read-only on banners.
- **Data involved:** Banners (label, surface, visibleTo, schedule, imageUrl).
- **External dependencies:** Shared file upload endpoint (image screening/size limits); home surface rendering.

## Acceptance Criteria
- **AC-UC110-01:** Given a valid banner payload, when `POST /admin/banners` is called, then `201` returns the banner with a computed `active` flag (API-CNT-012).
- **AC-UC110-02:** Given a future `startsAt`, when the home surface is read before the window, then the banner is absent.
- **AC-UC110-03:** Given an unsupported surface value, when the create is attempted, then 400 `VALIDATION_ERROR` and no record exists.
- **AC-UC110-04:** Given a Moderator, when create is attempted, then 403 `FORBIDDEN` and no banner is created.
