# UC-139 — Review a Dispute as Moderator (Advisory Input)

## Header Info
- **Use Case ID:** UC-139
- **Title:** Review a Dispute as Moderator (Advisory Input)
- **Actor:** Moderator (ACT-06)
- **Trigger:** A dispute is open with escrow frozen and both sides' evidence in place; Moderator is asked to review and advise
- **Priority:** P1
- **Goal:** Read the dispute fully and deliver an advisory recommendation to Admin — never a binding resolution.
- **Preconditions:** Moderator authenticated with READ-ONLY/advisory scope (ACT-06); dispute exists in `OPEN` state with evidence; binding arbitration is Admin-only — the admin is the final arbiter and the decision is audited (BR-RET-06).

## Main Scenario
1. Moderator opens the dispute list → `GET /disputes` (API-RET-014, roles include MODERATOR) filtered by state; escrow-frozen flags visible per row.
2. Moderator opens a dispute → `GET /disputes/{id}` (API-RET-015): ground, notes, evidence files from both sides, timeline, and the `escrowFrozen` indicator.
3. Moderator reviews the evidence against the grounds and forms a recommendation — buyer-favor, vendor-favor, or request more evidence.
4. Moderator passes the recommendation to Admin through the escalation/support path; Admin executes `POST /disputes/{id}/resolve`, the final arbiter decision with audit (BR-RET-06).
5. Escrow stays frozen until the Admin resolution — Moderator cannot unfreeze or otherwise move money.
6. Moderator follows up by re-reading the dispute to confirm the resolution outcome landed.

## Alternative Scenarios
- **A1 — Evidence incomplete:** key proof missing → recommendation asks Admin to request more evidence before the due date.
- **A2 — Clear-cut case:** evidence aligns with one side → recommendation delivered with rationale; Admin still decides (BR-RET-06).
- **A3 — Read-only outcome check:** dispute already resolved by Admin → Moderator reads `RESOLVED_BUYER`/`RESOLVED_VENDOR` outcome for closure.

## Exception Scenarios
- **E1 — Permission denied:** Moderator attempts `POST /disputes/{id}/resolve` → `403`/`ARBITRATION_FORBIDDEN`; arbitration stays Admin-only (BR-RET-06).
- **E2 — Already-resolved case:** dispute closed → `STATE_CONFLICT` on any input; only the recorded outcome is readable.
- **E3 — Escrow still frozen:** open dispute keeps escrow frozen → informational state for Moderator, no action available (Admin resolves to unfreeze).
- **E4 — SLA breach / evidence deadline:** evidence due date approaching → Moderator escalates urgency to Admin before the window closes.

## Postconditions
- No dispute state change by Moderator; recommendation delivered; escrow untouched.
- Admin's eventual resolution is written with an audit entry (BR-RET-06); escrow unfreezes into the chosen path.

## Business Rules Applied
- BR-RET-06

## Related Requirements
- FR-016 (Returns & Refunds), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Moderator READ-ONLY/advisory on disputes — no resolve, no escrow effect; Admin is final arbiter (UC-033).
- **Data involved:** Disputes, evidence files, timelines, escrow-freeze flags, resolution records.
- **External dependencies:** Escrow/refund engines driven only by Admin resolution (B07); support escalation path (B13).

## Acceptance Criteria
- **AC-UC139-01:** Given a Moderator, when the dispute list opens, then all disputes are readable (API-RET-014 roles=MODERATOR).
- **AC-UC139-02:** Given a Moderator resolve attempt, when submitted, then arbitration is refused (BR-RET-06).
- **AC-UC139-03:** Given an Admin resolution, when executed, then the outcome and audit entry are recorded (BR-RET-06).
- **AC-UC139-04:** Given an open dispute, when the Moderator reviews it, then `escrowFrozen` remains `true` until Admin resolves.
