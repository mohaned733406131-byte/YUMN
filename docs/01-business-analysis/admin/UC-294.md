# UC-294 — Hide Reported Content With a Reason as Moderator

## Header Info
- **Use Case ID:** UC-294
- **Title:** Hide Reported Content With a Reason as Moderator
- **Actor:** Moderator (ACT-06)
- **Trigger:** Reported or auto-flagged content sits in the moderation queue and must come off public surfaces before it spreads
- **Priority:** P1
- **Goal:** Hide the offending review/product/media from every public surface with a mandatory reason and an audit trail.
- **Preconditions:** Item is queued as `PENDING` (`GET /admin/moderation`, API-ADM-027); Moderator holds moderation write (API-ADM-028); a reason is available; hiding is reversible (restore is a separate Admin action).

## Main Scenario
1. Moderator opens the moderation queue (`GET /admin/moderation?type=…&status=PENDING`, API-ADM-027) and sorts by `reportedAt`.
2. Moderator inspects the item — reports count, reason, current status — and checks the underlying review/product context.
3. Moderator hides it (`POST /admin/moderation/{type}/{id}/hide` with `{ reason }`, API-ADM-028).
4. System marks `hidden: true` with `hiddenBy` and returns an `auditId` (BR-REV-04, BR-PLT-06).
5. The effect applies everywhere: a hidden review leaves rating averages after recompute; a hidden product is delisted from search and storefront.

## Alternative Scenarios
- **A1 — Report cleared instead:** evidence shows the content is fine → Moderator leaves it visible and closes the queue item without a hide.
- **A2 — Admin acting on the same queue:** Admin may hide or restore with identical semantics (API-ADM-028) — moderation is shared, reason still mandatory.
- **A3 — Vendor responds first:** the vendor's one permitted response does not remove the hide decision — the moderator verdict stands until restored (BR-REV-04).

## Exception Scenarios
- **E1 — Missing reason:** `REASON_REQUIRED` → nothing hidden, queue item unchanged (API-ADM-028).
- **E2 — Already hidden:** `STATE_CONFLICT` → no second hide, no duplicate audit entry.
- **E3 — Item deleted/unknown meanwhile:** `NOT_FOUND` → queue refreshed, no state written.

## Postconditions
- Success: the content is off all public surfaces, `hiddenBy` is set, and one audit entry carries Moderator, item and reason (BR-REV-04, BR-PLT-06).
- Failure: the content stays exactly as it was — nothing hidden, nothing audited, no rating recomputed.

## Business Rules Applied
- BR-REV-04, BR-PLT-06

## Related Requirements

- FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Moderator (ACT-06) moderation write (API-ADM-028); vendor may respond but never hide; customer reports only.
- **Data involved:** moderation queue items, review/product visibility flags, rating aggregates, audit entries.
- **External dependencies:** rating recompute job; search index update for delisted products (block B02); append-only audit log (API-ADM-024).

## Acceptance Criteria
- **AC-UC294-01:** Given a queued item, when Moderator hides it with a reason, then `hidden: true` and an `auditId` are returned (API-ADM-028).
- **AC-UC294-02:** Given a hidden review, when ratings recompute, then it is excluded from the average (BR-REV-04).
- **AC-UC294-03:** Given a hide without a reason, when submitted, then `REASON_REQUIRED` is returned and nothing changes.
- **AC-UC294-04:** Given a completed hide, when the audit log is read, then one entry names Moderator, item and reason (BR-PLT-06).
