# UC-293 — Investigate Coupon-Abuse Patterns Across Orders and Refunds

## Header Info
- **Use Case ID:** UC-293
- **Title:** Investigate Coupon-Abuse Patterns Across Orders and Refunds
- **Actor:** Admin (ACT-04)
- **Trigger:** Early-warning indicators fire — coupon-attempt rejection spikes, usage-limit hits, a rising refund-with-coupon rate, or discount share of GMV drifting upward (risk register, coupon/promotion abuse entry)
- **Priority:** P2
- **Goal:** Establish whether coupon rules are being gamed across orders and refunds, and stop the pattern with an audited action.
- **Preconditions:** Orders, refunds and coupon usage records are queryable; coupon bounds are enforced (BR-PRM-01, BR-PRM-02); Admin holds analytics and coupon rights (FR-011, FR-019).

## Main Scenario
1. Admin pulls the orders and returns reports for the suspect period (`GET /admin/reports/{family}`, API-ANL-007, families `orders`/`returns`).
2. Admin isolates orders carrying coupons and cross-references their refund outcomes — buy-with-coupon-then-refund sequences are the primary signal.
3. Admin checks rule compliance: one coupon per order (BR-PRM-02), discount ≤ 90% and window ≤ 90 days (BR-PRM-01).
4. Admin verifies the commission consequence of refunded coupon orders — commission reverses proportionally with the refund (BR-ESC-04).
5. Admin records the finding and, where an offending coupon is identified, disables it with a reason (UC-292).

## Alternative Scenarios
- **A1 — Stacking attempts only:** rejections show the engine already blocks stacking (BR-PRM-02) → no enforcement action, monitoring continues.
- **A2 — Single-account concentration:** one account dominates refund-with-coupon rows → the account's coupon eligibility is flagged for enforcement per the risk contingency, with audit (BR-PLT-06).
- **A3 — Legitimate promotion:** patterns match a planned campaign with expected discount share → closed as false positive with a note.

## Exception Scenarios
- **E1 — Report data incomplete or unlabelled:** totals arrive without exact/estimate labels → the investigation pauses rather than concluding on unlabelled money.
- **E2 — Evidence points at a ledger discrepancy:** the case is handed to reconciliation, not resolved here — money data is never adjusted to fit a narrative.
- **E3 — Coupon already disabled/expired mid-investigation:** further disable attempts return `STATE_CONFLICT` (API-CNT-017); the analysis continues on historical usage.

## Postconditions
- Success: an evidenced verdict exists — abuse confirmed (with an enforced disable) or cleared — and any enforcement action carries an audit entry (BR-PLT-06).
- Failure: no conclusion is recorded and no coupon status changed; the signals stay open for the next run.

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) analytics read + coupon write; vendor sees only its own store's coupons (API-CNT-015).
- **Data involved:** coupon usage records, orders, refunds, commission reversals, audit entries.
- **External dependencies:** analytics rollups (API-ANL-007); escrow/commission engine (block B07); risk register (`17-risk-management/risk-register.md`).

## Acceptance Criteria
- **AC-UC293-01:** Given a suspect period, when orders and returns reports are run, then coupon-bearing orders and their refund outcomes are enumerable (API-ANL-007).
- **AC-UC293-02:** Given coupon rows, when rules are checked, then violations of the no-stacking or bound rules are identified (BR-PRM-01, BR-PRM-02).
- **AC-UC293-03:** Given a refunded coupon order, when commission is inspected, then reversal is proportional to the refund (BR-ESC-04).
- **AC-UC293-04:** Given an offending coupon, when it is disabled, then one audit entry records Admin and the reason (BR-PLT-06).
