# UC-274 — Second-Approve a Large Bank-Transfer Top-Up

## Header Info
- **Use Case ID:** UC-274
- **Title:** Second-Approve a Large Bank-Transfer Top-Up
- **Actor:** Super Admin (ACT-05)
- **Trigger:** A bank-transfer top-up above the configured two-person threshold has a first approval and needs a distinct second approver before crediting
- **Priority:** P1
- **Goal:** Apply four-eyes control to high-value manual credits so one insider can never mint wallet balance alone (BR-PAY-04: credit only after admin verification).
- **Preconditions:** Top-up exists in `PENDING_VERIFICATION` (`GET /admin/topups`, API-ADM-030); evidence (amount, unique reference, receipt) matches (bank-transfer-topup.md §2/§6); first approver is recorded and differs from the second; threshold set with finance (design note, INFERENCE).

## Main Scenario
1. Admin (first approver) checks the request against evidence: amount matches the transfer, reference is normalized and platform-unique, receipt passes upload rules (bank-transfer-topup.md §6).
2. The large-amount rule requires a second, distinct approver → the request is routed to Super Admin with the first approver's record attached (two-person control, §6).
3. Super Admin independently re-checks amount and reference against the bank evidence, then approves (conceptual `POST /admin/topups/{id}/verify`, API-ADM-031).
4. On approval one ACID transaction runs: balanced ledger credit (BR-PAY-06), wallet balance update, status `CREDITED`, idempotency guard (BR-PAY-08), and an audit entry naming both approvers (BR-PLT-06).
5. The customer's request shows `CREDITED` with `ledgerReference` (API-WAL-004); the decision trail retains initiator and approver for the four-eyes audit (UC-259).

## Alternative Scenarios
- **A1 — Below the threshold:** one Admin decision suffices; the second-approval gate is skipped by configuration, never by code exception (BR-PAY-04).
- **A2 — Same person attempts both roles:** the four-eyes guardrail refuses — ORG-01 initiator ≠ approver on money actions (rbac.md §11).
- **A3 — Decline instead:** second approver declines with reason → `DECLINED`, zero ledger effect, customer notified with the localized reason (BR-NTF-04).

## Exception Scenarios
- **E1 — Duplicate reference:** the reference was already used → the request is rejected at uniqueness check; no credit path exists (bank-transfer-topup.md §4).
- **E2 — Wallet frozen:** credit precondition fails — a frozen wallet cannot be topped up (BR-PAY-09) → approval is held, freeze reviewed first.
- **E3 — Outage during decide:** retry is idempotent — exactly one ledger credit ever lands for the request (BR-PAY-08).

## Postconditions
- A large top-up is credited only after two distinct approvals, with balanced ledger rows and one audit entry per decision (BR-PAY-06, BR-PLT-06).
- Declined requests leave the wallet untouched; no code path credits before approval (BR-PAY-04).

## Business Rules Applied
- BR-PAY-04, BR-PAY-06, BR-PAY-08, BR-PAY-09, BR-PLT-06

## Related Requirements
- FR-013 (Wallet & Payment Processing), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin and Super Admin only — finance scope (ACT-05 signs the second approval); Moderator explicitly denied (rbac.md row 14).
- **Data involved:** top-up request (amount, bank, reference, receipt), ledger rows, wallet balance, audit entries.
- **External dependencies:** bank statement/portal for evidence check (S-10, ops-held); upload scanning for receipts (SEC-REQ-011).

## Acceptance Criteria
- **AC-UC274-01:** Given a top-up above the threshold, when only one approver has acted, then the wallet is not credited (BR-PAY-04).
- **AC-UC274-02:** Given two distinct approvers, when approval completes, then balanced ledger rows, `CREDITED` status, and an `auditId` result (BR-PAY-06, BR-PLT-06).
- **AC-UC274-03:** Given the same identity attempts both roles, when checked, then the operation is refused (rbac.md §11).
- **AC-UC274-04:** Given a retried approval after an outage, when it runs, then exactly one credit exists (BR-PAY-08).
