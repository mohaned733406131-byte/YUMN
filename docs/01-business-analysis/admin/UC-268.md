# UC-268 — Set the Platform Commission Tier Within the 5-20% Bound

## Header Info
- **Use Case ID:** UC-268
- **Title:** Set the Platform Commission Tier Within the 5-20% Bound
- **Actor:** Super Admin (ACT-05) — platform configuration is Super Admin's sole right (rbac.md §3)
- **Trigger:** A commission-tier change is approved and must be written to platform settings without violating the 5–20% bound
- **Priority:** P1
- **Goal:** Update the commission tier atomically and auditably, with optimistic locking, so future escrow releases compute at the new rate and past releases stay untouched.
- **Preconditions:** Settings read available (`GET /admin/settings`, API-ADM-022, group `COMMISSION`); commission rule fixed at 5–20% per vendor tier, default 10% (BR-ESC-03); caller is Super Admin (Admin gets `403`).

## Main Scenario
1. Super Admin reads the commission group (`GET /admin/settings?group=COMMISSION`, API-ADM-022) → current `value`, `schema`, `defaultValue`, and `version`.
2. Super Admin writes the new tier (`PUT /admin/settings/{key}` with `{ value, expectedVersion }`, API-ADM-023).
3. System validates the value against the setting schema — the tier must stay inside 5–20 (BR-ESC-03); out-of-bounds values are rejected before any change.
4. On success the response returns the new `value`, incremented `version`, and `auditId` (BR-PLT-06); the write is guarded by optimistic locking.
5. The new rate applies to commissions computed at future escrow releases (BR-ESC-03, BR-ESC-02) — releases already computed are never restated.

## Alternative Scenarios
- **A1 — No-op validation:** Super Admin submits the current value → version increments or the write is acknowledged; the bound still holds either way.
- **A2 — Stale `expectedVersion`:** another Super Admin wrote first → `409 SETTINGS_VERSION_CONFLICT`; the caller re-reads and re-applies deliberately (API-ADM-023).
- **A3 — Read-only check:** Admin/Moderator may read the tier (API-ADM-022 read grants) but only Super Admin may write it (rbac.md §2 row 24).

## Exception Scenarios
- **E1 — Value outside 5–20:** `VALIDATION_ERROR` → settings unchanged, no audit entry for a write that never happened (BR-ESC-03).
- **E2 — Caller is Admin, not Super Admin:** `403 FORBIDDEN` → no change (rbac.md §3).
- **E3 — Settings store unavailable:** the write fails before commit → old tier remains authoritative; no partial version bump.

## Postconditions
- The commission setting holds the new value with a new version and exactly one audit entry (BR-PLT-06).
- Future releases compute commission at the new tier within 5–20%; past commission rows are unchanged (append-only).

## Business Rules Applied
- BR-ESC-03, BR-PLT-06

## Related Requirements
- FR-014 (Escrow, Commission & Vendor Payouts), FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Super Admin (ACT-05) sole writer of platform settings; Admin operational read; Moderator read-only.
- **Data involved:** platform settings rows (key, value, schema, version, updatedBy), commission tier, audit entries.
- **External dependencies:** escrow release engine consuming the tier (FR-014); settings optimistic-locking path (admin.md §1.5).

## Acceptance Criteria
- **AC-UC268-01:** Given a value inside 5–20, when the Super Admin writes it, then the setting updates with a new `version` and an `auditId` (BR-ESC-03, BR-PLT-06).
- **AC-UC268-02:** Given a value of 4.9 or 20.1, when validation runs, then the write is rejected and the stored tier is unchanged (BR-ESC-03).
- **AC-UC268-03:** Given a stale `expectedVersion`, when the write is attempted, then `SETTINGS_VERSION_CONFLICT` is returned with no change (API-ADM-023).
- **AC-UC268-04:** Given an Admin (not Super Admin) caller, when the write is attempted, then it is denied (rbac.md §3).
