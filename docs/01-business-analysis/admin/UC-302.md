# UC-302 — Resolve a Settings Version Conflict After a Concurrent Edit

## Header Info
- **Use Case ID:** UC-302
- **Title:** Resolve a Settings Version Conflict After a Concurrent Edit
- **Actor:** Super Admin (ACT-05)
- **Trigger:** A settings write returns `SETTINGS_VERSION_CONFLICT` because another admin changed the key between read and save
- **Priority:** P2
- **Goal:** Re-read the current setting, reconcile the two intended values deliberately, and reapply one authoritative version — never a blind overwrite.
- **Preconditions:** Settings use optimistic locking via `expectedVersion` (API-ADM-023); Super Admin holds settings write; both editors' intents are known (audit log readable).

## Main Scenario
1. Super Admin's save fails with `SETTINGS_VERSION_CONFLICT` (409) on a stale `expectedVersion`.
2. Super Admin re-reads the key to get the current `{ value, version }` and opens the audit log (`GET /admin/audit-log`, API-ADM-024) to see who changed it and why.
3. Super Admin compares the concurrent change against the intended one — e.g. whether a value still sits inside its validated bound (commission tier must stay within 5–20).
4. Super Admin reapplies with the fresh `expectedVersion` (`PUT /admin/settings/{key}`, API-ADM-023).
5. System validates the value against the setting's schema, increments `version`, and returns an `auditId`.

## Alternative Scenarios
- **A1 — Concurrent change already correct:** the other editor's value matches intent → no rewrite needed; the conflict is closed with a note.
- **A2 — Non–Super Admin caller:** the endpoint returns `FORBIDDEN` — settings writes are Super Admin only; the conflict path never opens (API-ADM-023).
- **A3 — Value fails schema/BR bounds on reapply:** `VALIDATION_ERROR` → nothing written; the intended value is corrected first.

## Exception Scenarios
- **E1 — Second conflict (another edit during reconciliation):** 409 again → reread and reapply; optimistic locking guarantees the last deliberate write wins, never a silent merge.
- **E2 — Malformed value:** `VALIDATION_ERROR` → stored setting untouched, no version bump.
- **E3 — Key not found:** `NOT_FOUND` → nothing written; the key list is re-checked before retrying.

## Postconditions
- Success: the key holds one coherent value at a new `version`, with one audit entry naming Super Admin, before/after and reason (BR-PLT-06).
- Failure: the stored value stays at its previous version — a conflict never half-applies or merges two values.

## Permissions / Data / External Dependencies
- **Permissions:** Super Admin (ACT-05) settings write (API-ADM-023); Admin/Moderator read-only; deny-by-default elsewhere.
- **Data involved:** platform setting records (`value`, `version`), audit entries (read/write).
- **External dependencies:** append-only audit log (API-ADM-024); setting schema validation (e.g. commission-tier bounds, BR-ESC-03).

## Acceptance Criteria
- **AC-UC302-01:** Given a stale `expectedVersion`, when the save is attempted, then `SETTINGS_VERSION_CONFLICT` is returned and the stored value is unchanged.
- **AC-UC302-02:** Given the conflict, when Super Admin reapplies with the fresh version, then the value saves with an incremented `version` and an `auditId`.
- **AC-UC302-03:** Given an out-of-bound value (e.g. commission tier outside 5–20), when it is submitted, then `VALIDATION_ERROR` is returned and nothing changes (BR-ESC-03).
- **AC-UC302-04:** Given a non–Super Admin caller, when settings write is attempted, then `FORBIDDEN` is returned (API-ADM-023).
