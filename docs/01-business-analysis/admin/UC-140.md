# UC-140 — Handle a Support Ticket as Moderator

## Header Info
- **Use Case ID:** UC-140
- **Title:** Handle a Support Ticket as Moderator
- **Actor:** Moderator (ACT-06)
- **Trigger:** A support ticket needs a reply or resolution and a Moderator picks it up from the shared queue
- **Priority:** P1
- **Goal:** Reply to and resolve support tickets within the Moderator's support scope, escalating platform-action cases to Admin.
- **Preconditions:** Moderator authenticated with support scope (ACT-06) — may read tickets, append messages, and resolve; may NOT reassign others' tickets (Admin-only assign); resolution writes an audit entry (BR-PLT-06).

## Main Scenario
1. Moderator opens the support queue → `GET /admin/tickets` (API-ADM-039, roles include MODERATOR) filtered by status/category/source (`AUTO` delivery-code tickets included).
2. Moderator opens ticket detail → `GET /support/tickets/{id}` (API-ADM-037): full message thread, linked order/delivery, and timeline.
3. Moderator replies → `POST /support/tickets/{id}/messages` (API-ADM-038) with body/attachments; the ticket moves to `IN_PROGRESS` once a staff member replies.
4. Moderator resolves when handled → `POST /admin/tickets/{id}/resolve` (API-ADM-041) with a mandatory resolution → status `RESOLVED` plus `auditId` (BR-PLT-06).
5. Cases needing platform action (order, wallet, vendor) are escalated to Admin (UC-102 staff side) — content-flag triage remains UC-038 territory.
6. The customer may reopen once before final close; a reopen returns the ticket to the queue for further handling.

## Alternative Scenarios
- **A1 — Escalate instead of resolve:** Moderator cannot act (needs Admin) → hand off with context; ticket stays open/in progress.
- **A2 — Auto-created ticket:** delivery-code lock created it with timeline attached → Moderator handles with the linked order context.
- **A3 — Relation notes:** UC-038 routes flagged-content threads needing platform action here; UC-102 is the Admin reply side of the same thread endpoint.

## Exception Scenarios
- **E1 — Permission denied:** Moderator attempts to reassign another's ticket → `403 FORBIDDEN` (assign is Admin-only).
- **E2 — Already-resolved case:** ticket resolved/closed → `TICKET_STATE_CONFLICT` on further messages; read the recorded resolution.
- **E3 — SLA breach:** ticket marked overdue in the queue → prioritized/escalated so it is not silently stalled.
- **E4 — Missing resolution note:** resolve submitted without a resolution → `VALIDATION_ERROR` (resolution required); status unchanged.

## Postconditions
- Ticket ends `RESOLVED` with a resolution note and audit row (BR-PLT-06), or is escalated to Admin with context intact.
- Thread messages are appended, never edited; the customer sees the reply/resolution in their own feed.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)
- **Cross-reference:** UC-038 (flagged content triage hand-off) · UC-102 (Admin reply side of the thread).

## Permissions / Data / External Dependencies
- **Permissions:** Moderator support scope — reply and resolve allowed; reassignment, settings, roles, finance, and order actions remain Admin-only.
- **Data involved:** Support tickets, message threads, linked entities, audit log.
- **External dependencies:** Support queue (B13); linked order/timeline reads (B06); notifications to the ticket owner.

## Acceptance Criteria
- **AC-UC140-01:** Given a Moderator, when replying to a ticket, then the message is appended and status becomes `IN_PROGRESS` (API-ADM-038).
- **AC-UC140-02:** Given a resolve without a resolution note, when submitted, then validation fails and status is unchanged.
- **AC-UC140-03:** Given a Moderator resolution, when executed, then status is `RESOLVED` with an `auditId` (BR-PLT-06).
- **AC-UC140-04:** Given a Moderator reassign attempt, when submitted, then access is denied (`403 FORBIDDEN`).
