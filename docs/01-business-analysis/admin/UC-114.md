# UC-114 — Create a Platform Coupon

## Header Info
- **Use Case ID:** UC-114
- **Title:** Create a Platform Coupon
- **Actor:** Admin (ACT-04)
- **Trigger:** The platform launches a discount campaign
- **Priority:** P1
- **Goal:** Issue an ACTIVE platform coupon whose code, discount type, and window satisfy all coupon constraints server-side.
- **Preconditions:** Admin authenticated with content-write permission (ACT-04); the chosen code is not yet used.

## Main Scenario
1. Admin opens Promotions → Coupons → "New coupon" and enters `code`, `scope: "PLATFORM"`, a type (percentage, fixed amount, free shipping, or buy-X-get-Y — BR-PRM-05), `discountPercent`/value, `startsAt`/`endsAt` and optional caps.
2. Client sends `POST /admin/coupons` (API-CNT-016).
3. System validates bounds server-side: discount ≤ 90% and validity window ≤ 90 days (BR-PRM-01) → otherwise `COUPON_BOUNDS_EXCEEDED`; code uniqueness → `DUPLICATE_RESOURCE`.
4. On success → `201 { …coupon, status: "ACTIVE" }`; the coupon never stacks with another coupon on an order (BR-PRM-02) and applies only inside its window.

## Alternative Scenarios
- **A1 — Fixed/free-shipping campaign:** Admin picks a non-percentage type from the type set (BR-PRM-05); bounds checks still apply.
- **A2 — Future launch:** Admin sets `startsAt` in the future → coupon is ACTIVE but only valid from the window start.
- **A3 — Capped discount:** Admin sets `maxDiscount` to bound large carts; validation accepts it within the ≤90% rule (BR-PRM-01).

## Exception Scenarios
- **E1 — Bounds violation (validation failure):** 91% discount or 91-day window → 422 `COUPON_BOUNDS_EXCEEDED`; no coupon created (BR-PRM-01).
- **E2 — Duplicate code:** Code already exists → `DUPLICATE_RESOURCE`; admin picks another code.
- **E3 — Permission denied:** Moderator or non-admin attempts create → 403 `FORBIDDEN`; no coupon created.
- **E4 — Concurrent creation:** Two admins submit the same code → exactly one `201`; the other gets `DUPLICATE_RESOURCE`.

## Postconditions
- One ACTIVE coupon exists within all bounds; it is non-stackable (BR-PRM-02) and listed for oversight (UC-113).
- No money moves at creation time.

## Business Rules Applied
- BR-PRM-01, BR-PRM-02, BR-PRM-05

## Related Requirements
- FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Admin content-write scope; Moderator cannot create coupons.
- **Data involved:** Coupons (code, scope, type, window, caps, status).
- **External dependencies:** Cart/checkout coupon validation enforces non-stacking and bounds at order time.

## Acceptance Criteria
- **AC-UC114-01:** Given a 91% discount or a 91-day window, when the coupon is submitted, then `COUPON_BOUNDS_EXCEEDED` is returned and nothing is created (BR-PRM-01).
- **AC-UC114-02:** Given a valid payload, when `POST /admin/coupons` succeeds, then `201` returns `status: "ACTIVE"` (API-CNT-016).
- **AC-UC114-03:** Given a second coupon offered on the same order, when both are supplied, then only one applies (BR-PRM-02).
- **AC-UC114-04:** Given an already-used code, when create is attempted, then `DUPLICATE_RESOURCE` is returned.
