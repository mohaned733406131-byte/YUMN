# UC-269 — Cancel an Order as the Platform of Last Resort

## Header Info
- **Use Case ID:** UC-269
- **Title:** Cancel an Order as the Platform of Last Resort
- **Actor:** Admin (ACT-04)
- **Trigger:** Neither buyer nor vendor will act (unresponsive vendor, blocked fulfilment, escalation deadlocked) and the platform must cancel to release the buyer's money
- **Priority:** P1
- **Goal:** Cancel a sub-order inside the allowed window with a mandatory reason, so the refund flow runs and no funds stay stuck in escrow.
- **Preconditions:** Target sub-order exists and is still before `READY_FOR_PICKUP` (BR-ORD-04 admin cancellation window); Admin authenticated with order-override rights (rbac.md row 18); buyer/vendor cancellation already unavailable or refused.

## Main Scenario
1. Admin opens the operations queue (`GET /admin/orders`, API-ORD-013) and reads the order detail with per-sub-order states (API-ORD-004).
2. Admin confirms the target sub-order has not reached `READY_FOR_PICKUP` — the last state in which cancellation is possible (BR-ORD-04, API-ORD-010 note).
3. Admin cancels with a mandatory reason (`POST /store/orders/{id}/cancel` with Admin role, API-ORD-011) → sub-order `CANCELLED`, response includes `refund: { status: "PENDING" }`.
4. The refund flow runs to the buyer's wallet — cancellation always triggers the refund path, never an external cash-out (BR-ORD-04, BR-PAY-07).
5. Status history gains an append-only entry with actor, timestamp, and reason (BR-ORD-03), and the forced action returns an `auditId` (BR-PLT-06); the master is re-evaluated (BR-ORD-07).

## Alternative Scenarios
- **A1 — Window already closed:** sub-order is at/past `READY_FOR_PICKUP` → `CANCEL_WINDOW_CLOSED`; the operator uses a guarded state correction instead (UC-270) — this UC never overrides the window silently.
- **A2 — Multi-vendor order:** only affected sub-orders are cancelled; unaffected ones continue, and the master aggregates what remains (BR-ORD-02, BR-ORD-07).
- **A3 — Vendor already cancelled:** the entry is already `CANCELLED` → no duplicate action; Admin verifies the refund progress instead (UC-126).

## Exception Scenarios
- **E1 — Concurrent vendor/customer action:** optimistic locking returns `409 STATE_CONFLICT`; history is unchanged and the queue is re-read.
- **E2 — Missing reason:** `REASON_REQUIRED` blocks the cancellation — no state change without a recorded reason (API-ORD-011).
- **E3 — Refund job fails after cancellation:** BullMQ retries 3× then dead-letters with an alert (BR-PLT-02); reconciliation flags the drift (BR-ESC-08) and no double refund occurs (BR-PAY-08).

## Postconditions
- The sub-order is `CANCELLED` with an append-only history row and an audit entry naming the Admin and reason (BR-ORD-03, BR-PLT-06).
- A refund is pending to the buyer's wallet — wallet-only, never external (BR-PAY-07); escrow for that sub-order is released into the refund path.

## Business Rules Applied
- BR-ORD-03, BR-ORD-04, BR-ORD-07, BR-PAY-06, BR-PAY-07, BR-PAY-08, BR-ESC-08, BR-PLT-02, BR-PLT-06

## Related Requirements
- FR-012 (Order Lifecycle Management), FR-014 (Escrow, Commission & Vendor Payouts)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) order-override (rbac.md row 18); Moderator read-only; buyer/vendor windows unchanged for them (BR-ORD-04).
- **Data involved:** sub-order state, status history, refund rows, escrow hold, audit entries.
- **External dependencies:** refund engine (B07); escrow release logic (BR-ESC-02/BR-ESC-07); notifications to both parties (BR-NTF-04).

## Acceptance Criteria
- **AC-UC269-01:** Given a sub-order before `READY_FOR_PICKUP`, when the Admin cancels with a reason, then it becomes `CANCELLED` with `refund: PENDING` (BR-ORD-04).
- **AC-UC269-02:** Given a sub-order at or past `READY_FOR_PICKUP`, when cancellation is attempted, then `CANCEL_WINDOW_CLOSED` is returned with no state change.
- **AC-UC269-03:** Given the cancellation completes, when history is read, then a new entry carries actor, timestamp, and reason — appended, never overwritten (BR-ORD-03).
- **AC-UC269-04:** Given the refund runs, when it credits, then the buyer's wallet is credited with balanced ledger rows, never an external payout (BR-PAY-07, BR-PAY-06).
