# UC-301 — Investigate a Guard-Blocked Retention Purge Attempt

## Header Info
- **Use Case ID:** UC-301
- **Title:** Investigate a Guard-Blocked Retention Purge Attempt
- **Actor:** Admin (ACT-04)
- **Trigger:** The purge job's guard skips and alerts on a financial/audit/KYC class sitting below its retention floor (`16-data/core/retention-and-archival.md` §6 step 3)
- **Priority:** P1
- **Goal:** Establish why a protected class was eligible for purge at all — bad config, clock, or partition — and close the cause without ever deleting protected rows.
- **Preconditions:** Guard fired (skip + alert, never delete); class is RC-05/RC-06/RC-07; retention periods are configuration consumed by the job; Admin owns the investigation.

## Main Scenario
1. Admin opens the guard alert: class, scope, counts, timestamp of the skipped run.
2. Admin reads the configured period for that class against the schedule — financial/audit floor is never below the legal minimum.
3. Admin inspects the job input: which rows the job believed were eligible, and whether partition dating or a clock skew produced the wrong set.
4. Admin corrects the configuration or the job's eligibility query — a config fix, not a code release, where the period is at fault.
5. Admin re-runs the guard check for the class: it must skip again while below floor, and the disposition is recorded (BR-PLT-06).

## Alternative Scenarios
- **A1 — Config drift (period set too low):** the period is restored to schedule value; the guard's refusal is confirmed as the control that caught it.
- **A2 — Eligibility bug (wrong partition read):** the fix targets the job's selection logic; a seeded-below-floor test proves the guard still refuses.
- **A3 — Alert with no actual eligibility (false positive):** documented and closed; the guard stays armed — it is never disabled to quiet an alert.

## Exception Scenarios
- **E1 — Pressure to bypass the guard:** impossible by design — the guard skips and alerts, deletion of below-floor rows cannot be forced (retention §6 step 3).
- **E2 — Protected rows found already deleted:** immediate incident (UC-296/UC-304 territory) — evidence preserved, escalation to Super Admin; not resolved by editing records.
- **E3 — Investigation cannot determine cause:** the class stays guarded with monitoring tightened; no purge resumes on an unexplained eligibility.

## Postconditions
- Success: root cause identified and fixed (config or job), guard proven still effective for the class, one audit entry records Admin's actions (BR-PLT-06).
- Failure: zero protected rows deleted in every outcome — a failed investigation leaves data intact and the alert active.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) investigation + config correction; System runs the purge; deletion of protected classes stays impossible while below floor.
- **Data involved:** retention configuration, purge job eligibility sets, guard alerts, protected class rows (read), audit entries.
- **External dependencies:** daily purge job `system.retention.purge` (BR-PLT-01); alert route for the guard skip (INT-REQ-007).

## Acceptance Criteria
- **AC-UC301-01:** Given a class below its floor, when the purge runs, then the run skips the class and raises an alert — zero rows deleted.
- **AC-UC301-02:** Given the investigation closes, when the fix is applied, then a re-run of the guard still refuses below-floor deletion.
- **AC-UC301-03:** Given any Admin action in the investigation, when it completes, then one audit entry records actor, class and reason (BR-PLT-06).
- **AC-UC301-04:** Given an attempted forced deletion of protected rows, when it is made, then it is refused — no bypass path exists.
