# UC-135 — Handle the 24-Hour Confirmation Escalation

## Header Info
- **Use Case ID:** UC-135
- **Title:** Handle the 24-Hour Confirmation Escalation
- **Actor:** Admin (ACT-04)
- **Trigger:** A sub-order still sits at `CONFIRMED` 24 hours after confirmation and the system raises an escalation with notification (UC-063)
- **Priority:** P1
- **Goal:** Resolve the stalled order with a recorded decision so it is never left silently stuck.
- **Preconditions:** Admin authenticated with order-override scope (ACT-04); escalation exists with `SLA_24H` flag on the queue; the sub-order is still at `CONFIRMED`.

## Main Scenario
1. System raises the escalation at the 24-hour mark with a notification and never silently auto-cancels (BR-ORD-10; raised by UC-063).
2. Admin opens the operations queue → `GET /admin/orders` (API-ORD-013) filtered to the `SLA_24H` flag, sorted by SLA age.
3. Admin opens the order → sub-order states, append-only timeline, vendor contact history, and payment/escrow references.
4. Admin contacts the vendor or checks store status, then decides: resume fulfillment, or cancel with a mandatory reason.
5. Any forced move uses `POST /admin/orders/{id}/transition` (API-ORD-014) inside the canonical 17-state table, with a reason — and writes an append-only audit entry (BR-PLT-06).
6. Cancellation triggers the standard refund path; the escalation clears only after a recorded decision and notification (BR-ORD-10).

## Alternative Scenarios
- **A1 — Vendor responds:** vendor resumes fulfillment → escalation flag clears on the next queue refresh, no override needed.
- **A2 — Admin cancels:** vendor unresponsive → cancel with reason → refund flow runs; decision and notification recorded (BR-ORD-10).
- **A3 — Order already advanced:** vendor confirmed/processed before admin looked → flag clears on refresh; no action required.
- **A4 — Store-level issue found:** underlying store problem → hand off to store review while keeping the escalation owned until closed.

## Exception Scenarios
- **E1 — Concurrent transition:** vendor/customer act at the same time → `409 STATE_CONFLICT`; admin refreshes the timeline before retrying.
- **E2 — Missing reason:** forced transition without reason → `422 REASON_REQUIRED`; no state change, no audit row.
- **E3 — Permission denied:** Moderator attempts the transition → `403 FORBIDDEN`; Moderator escalates instead (UC-137 is read-only).
- **E4 — SLA breach persists:** order remains past 24 hours undecided → notification and `SLA_24H` flag persist until a recorded decision lands (BR-ORD-10).

## Postconditions
- Escalation resolved with a recorded decision; order rests in a valid canonical state.
- Audit row exists for any forced transition (BR-PLT-06); vendor/customer notified (BR-ORD-10).

## Business Rules Applied
- BR-ORD-10, BR-PLT-06

## Related Requirements
- FR-012 (Order Lifecycle Management)
- **Cross-reference:** UC-063 (system raises the 24-hour escalation).

## Permissions / Data / External Dependencies
- **Permissions:** Admin order-override scope; Moderator read-only (UC-137); Super Admin supersedes (UC-037).
- **Data involved:** Orders/sub-orders, status timeline, escalation flags, audit log, notifications.
- **External dependencies:** Escalation watcher job (B06); notification service (B10); refund engine on cancellation (B07).

## Acceptance Criteria
- **AC-UC135-01:** Given a sub-order `CONFIRMED` for 24 hours, when the check runs, then `SLA_24H` appears on the admin queue (BR-ORD-10).
- **AC-UC135-02:** Given an admin forced transition, when executed, then a reason and `auditId` are recorded (BR-PLT-06).
- **AC-UC135-03:** Given an escalation, when it is closed, then a decision plus notification exist — never a silent drop (BR-ORD-10).
- **AC-UC135-04:** Given a Moderator account, when a transition is attempted, then access is denied (`403 FORBIDDEN`).
