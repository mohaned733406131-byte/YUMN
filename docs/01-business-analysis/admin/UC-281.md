# UC-281 — Reassign a Stalled Delivery Back to the Offer Pool

## Header Info
- **Use Case ID:** UC-281
- **Title:** Reassign a Stalled Delivery Back to the Offer Pool
- **Actor:** Admin (ACT-04) — dispatch override (rbac.md row 9)
- **Trigger:** An assigned delivery has stalled — courier went offline, missed pickup, or abandoned the job — and the shipment must return to the zone's offer pool
- **Priority:** P1
- **Goal:** Release the stalled assignment so eligible couriers in the same zone can accept it under first-accept-wins, without double assignment.
- **Preconditions:** Delivery exists in `ASSIGNED` (state table, DOC-SA-010); Admin holds dispatch override (rbac.md row 9); assignment rule = offered to eligible couriers in the same zone, first accept wins (BR-SHP-04).

## Main Scenario
1. Admin spots the stall in dispatch view and opens the delivery (`GET /deliveries/{id}`, API-SHP-003) — state, attempt history, code status, and assignee.
2. Admin confirms it is genuinely stalled: still `ASSIGNED` with no pickup scan and no courier progress (a picked-up job is not released this way).
3. Admin releases it with a mandatory reason (`POST /deliveries/{id}/release`, API-SHP-005, ADMIN allowed alongside the courier's own release) → `ASSIGNED → READY_FOR_PICKUP` with a `historyEntry`.
4. The delivery re-enters the offer feed for its zone (`GET /deliveries/available`, API-SHP-001) and is offered to eligible couriers; the first accept wins under optimistic locking (BR-SHP-04).
5. The previous courier's access to that shipment is revoked — release returns the job to the pool and ends their view of it (rbac.md §5); the state history keeps both legs (BR-ORD-03).

## Alternative Scenarios
- **A1 — Courier released it themselves:** the same endpoint with the courier role produces the identical transition; Admin only verifies it landed.
- **A2 — Repeated stalls on the order:** after 3 failed delivery attempts the order escalates to admin review with full timeline (BR-SHP-06) — release alone is no longer sufficient.
- **A3 — No eligible courier free:** the offer simply stays open in the zone feed; nothing is auto-assigned and no location data is collected (BR-SHP-05, C-16).

## Exception Scenarios
- **E1 — Missing reason:** `REASON_REQUIRED` blocks the release (API-SHP-005).
- **E2 — Concurrent accept during release:** optimistic locking on `offerVersion` prevents double assignment — one caller wins, the other gets a conflict (BR-SHP-04).
- **E3 — Delivery not in `ASSIGNED`:** `STATE_CONFLICT` (already picked up, delivered, or released) → Admin re-reads state and handles via the escalation path, never by forcing history (BR-ORD-03).

## Postconditions
- The delivery sits at `READY_FOR_PICKUP`, re-offered in its zone, with an appended history entry naming Admin and reason (BR-ORD-03, BR-SHP-04).
- The prior assignment is void; exactly one courier can hold the job after the next accept — no double assignment is possible (BR-SHP-04).

## Business Rules Applied
- BR-SHP-04, BR-SHP-05, BR-SHP-06, BR-ORD-03

## Related Requirements
- FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) dispatch override (rbac.md row 9); courier may release only their own assignment; Moderator denied.
- **Data involved:** delivery/assignment rows, offer version, status history, attempt records, zone offer feed.
- **External dependencies:** offer/acceptance feed (API-SHP-001/004); courier availability state (API-SHP-016); state machine (DOC-SA-010).

## Acceptance Criteria
- **AC-UC281-01:** Given a stalled `ASSIGNED` delivery, when the Admin releases it with a reason, then state becomes `READY_FOR_PICKUP` with a `historyEntry` (API-SHP-005, BR-ORD-03).
- **AC-UC281-02:** Given the release, when the zone feed is read, then the delivery appears among available offers (BR-SHP-04).
- **AC-UC281-03:** Given two couriers accept concurrently, when locking runs, then exactly one wins and the other gets a conflict (BR-SHP-04).
- **AC-UC281-04:** Given the release completes, when the previous courier reads the delivery, then their access to it is revoked (rbac.md §5).
