# UC-299 — Dispose of Aged Data-Quality Quarantine Records

## Header Info
- **Use Case ID:** UC-299
- **Title:** Dispose of Aged Data-Quality Quarantine Records
- **Actor:** Admin (ACT-04)
- **Trigger:** Quarantine entries age past 72 hours and escalate to Admin review with the daily report (`16-data/core/data-quality.md` §6)
- **Priority:** P1
- **Goal:** Clear aged quarantine rows with an explicit, audited disposition — reprocess, accept, void, or purge — so the backlog never rots silently.
- **Preconditions:** Rows sit in `dq_quarantine` with source table, row key, rule ID, error and attempt counts; original rows untouched until disposition; a reason is available.

## Main Scenario
1. Admin opens the aged-quarantine view (escalated >72 h) with entries grouped by rule ID.
2. Admin inspects an entry: the failing rule, error, first/last seen and the untouched original row.
3. Admin chooses a disposition path: (a) fix source and reprocess, (b) accept/void the record, or (c) purge if the record is beyond its retention period.
4. The disposition is written to the audit trail naming Admin, entry and choice (BR-PLT-06).
5. Admin confirms the quarantine depth falls and the standing quarantine panel reflects the change.

## Alternative Scenarios
- **A1 — Reprocess path:** source defect fixed → the row is reprocessed; a clean result clears the quarantine entry with its own evidence.
- **A2 — Money data involved:** mismatches are never auto-corrected — disposition records the decision while Finance resolves the underlying figure via compensating entries.
- **A3 — Entry younger than the threshold:** ≤24 h entries stay in normal alerting; Admin only works the escalated backlog.

## Exception Scenarios
- **E1 — Disposition without a reason:** blocked — every quarantine disposition is reasoned and auditable (BR-PLT-06); entry stays queued.
- **E2 — Original row already changed upstream:** the entry is voided with a note rather than reprocessed onto stale data; no orphan is created.
- **E3 — Purge chosen on a retained class:** retention guard refuses the delete — quarantine disposal never overrides retention (UC-301).

## Postconditions
- Success: each aged entry carries an audited disposition and the quarantine backlog shrinks; original data was changed only by the chosen, deliberate path.
- Failure: the entry stays in quarantine untouched — no silent delete, no auto-correction of money data.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) quarantine disposition; System writes quarantine rows; Finance owns money-data outcomes.
- **Data involved:** `dq_quarantine` entries, source rows, rule register references, audit entries.
- **External dependencies:** reconciliation jobs and their monitors (`16-data/core/data-quality.md` §5); Grafana quarantine panel (INT-REQ-007).

## Acceptance Criteria
- **AC-UC299-01:** Given an entry older than 72 h, when it is reviewed, then it appears in the Admin escalation view with rule ID and error.
- **AC-UC299-02:** Given a disposition is chosen, when it is recorded, then one audit entry names Admin, entry and choice (BR-PLT-06).
- **AC-UC299-03:** Given a money-data entry, when disposition runs, then no automatic correction of the underlying amount occurs.
- **AC-UC299-04:** Given a retained-class record, when purge is attempted, then the guard refuses and the entry survives (UC-301).
