# UC-134 — Restore Previously Hidden Content

## Header Info
- **Use Case ID:** UC-134
- **Title:** Restore Previously Hidden Content
- **Actor:** Admin (ACT-04)
- **Trigger:** Previously hidden content (review, product, or media) is re-reviewed — via appeal, corrected evidence, or a false-positive finding — and should become visible again
- **Priority:** P1
- **Goal:** Un-hide content with a recorded reason and audit trail so the marketplace sees it again.
- **Preconditions:** Admin authenticated with moderation scope (ACT-04); target content exists in hidden state with its original hide reason and audit entry; hiding itself belongs to UC-032 (hide/dismiss only).

## Main Scenario
1. Admin opens the moderation queue → `GET /admin/moderation` filtered to hidden items (conceptual touchpoint for API-ADM-027).
2. Admin opens the item → original content, hide reason, reporter count, author history, and the audit entry recorded at hide time (BR-PLT-06).
3. Admin evaluates the policy basis: content now complies, or the abuse/report grounds no longer hold (BR-REV-04 governs moderation hides with audit).
4. Admin restores → `POST /admin/moderation/{type}/{id}/restore` (API-ADM-029) with a mandatory reason.
5. System returns `hidden: false` plus an `auditId` — the restore is appended to the audit trail, never overwriting the original hide entry (BR-PLT-06).
6. The content returns to all public surfaces it was removed from, and the moderation record stays intact for history.

## Alternative Scenarios
- **A1 — Review restored:** the review reappears in product review lists and is counted again in ratings displays.
- **A2 — Product restored:** the listing is re-listed and becomes browsable/searchable again.
- **A3 — Appeal path:** author or vendor appealed through support (UC-014) → admin reviews the appeal and restores if upheld.
- **A4 — Relation to UC-032:** UC-032 performs hide/dismiss only; this UC is the audited reversal.

## Exception Scenarios
- **E1 — Not hidden:** restore attempted on visible content → `409 STATE_CONFLICT`; nothing changes.
- **E2 — Missing reason:** restore submitted without a reason → `422 REASON_REQUIRED`; nothing is written.
- **E3 — Permission denied:** caller without moderation scope → `403 FORBIDDEN`.
- **E4 — Concurrent decision:** another moderator/admin hides or restores the same item first → optimistic lock; refresh and re-evaluate before retrying.

## Postconditions
- Content is publicly visible again with an append-only audit row for the restore (BR-REV-04, BR-PLT-06).
- The original hide record remains; no history is edited or deleted.

## Business Rules Applied
- BR-REV-04, BR-PLT-06

## Related Requirements
- FR-006 (Reviews & Ratings), FR-019 (Content & Promotions (CMS + Coupons))
- **Cross-reference:** UC-032 (hide/dismiss only — restore is its reversal).

## Permissions / Data / External Dependencies
- **Permissions:** Admin moderation scope; Super Admin supersedes (UC-037).
- **Data involved:** Moderation queue items, content records, reasons, audit log.
- **External dependencies:** Moderation queue (B13); public catalog/review surfaces; support appeals (B13).

## Acceptance Criteria
- **AC-UC134-01:** Given hidden content, when restored with a reason, then `hidden: false` and an `auditId` are returned (BR-REV-04, BR-PLT-06).
- **AC-UC134-02:** Given content that is not hidden, when restore is attempted, then `STATE_CONFLICT` is returned and visibility is unchanged.
- **AC-UC134-03:** Given a restore without a reason, when submitted, then `REASON_REQUIRED` is returned and nothing is written.
- **AC-UC134-04:** Given a restored review, when a product page renders, then the review displays again (BR-REV-04).
