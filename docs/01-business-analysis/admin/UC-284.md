# UC-284 — Attach Platform Evidence to a Dispute Case

## Header Info
- **Use Case ID:** UC-284
- **Title:** Attach Platform Evidence to a Dispute Case
- **Actor:** Admin (ACT-04)
- **Trigger:** The platform holds material (delivery proof, reconciliation output, audit excerpt) that a disputed case needs before arbitration
- **Priority:** P1
- **Goal:** Add platform-side evidence to the open dispute so the arbitration decision rests on a complete record.
- **Preconditions:** Dispute open and escrow frozen (BR-ORD-05); evidence files pass the upload rules (≤5 files, scanned); Admin holds dispute evidence rights (API-RET-016).

## Main Scenario
1. Admin opens the dispute (`GET /disputes/{id}`, API-RET-015) and confirms it is still open.
2. Admin gathers the platform evidence — delivery proof (UC-282), timeline excerpt, reconciliation line.
3. Admin submits it (`POST /disputes/{id}/evidence` with `multipart { note?, file? }` or JSON `{ note, imageFileIds? }`, API-RET-016).
4. System scans the files, enforces the ≤5-item payload limit, and returns `{ evidenceId, at }`.
5. The new item appears in the case evidence list visible to both parties and to the arbitrator.

## Alternative Scenarios
- **A1 — Text-only note:** Admin submits a `note` without files (e.g. a reconciliation summary); the same `evidenceId` is issued and the case timeline grows.
- **A2 — Evidence gathered after submission:** Admin attaches further material before the due date — each submission is a new `evidenceId`, the case stays open (BR-ORD-05).
- **A3 — Arbitration follows:** the assembled record feeds the verdict (UC-283); nothing else in this case changes here.

## Exception Scenarios
- **E1 — Empty payload:** `EVIDENCE_REQUIRED` → no evidence row, case unchanged (API-RET-016).
- **E2 — File rejected by the pipeline:** oversized, wrong media type or failed malware scan (`PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `FILE_SCAN_FAILED`) → the file is dropped, note-only submission still possible, nothing partial is stored.
- **E3 — Dispute already resolved:** `STATE_CONFLICT` → evidence is never appended to a closed case (API-RET-016).

## Postconditions
- Success: the dispute carries one more evidence item with submitter and timestamp; escrow remains frozen until arbitration (BR-ORD-05).
- Failure: the evidence list is byte-for-byte what it was — no partial upload, no orphan file object.

## Business Rules Applied
- BR-ORD-05

## Related Requirements
- FR-016 (Returns & Refunds)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) plus the case parties within their own scope (API-RET-016); ownership enforced per dispute.
- **Data involved:** dispute record, evidence rows, uploaded file objects, case timeline.
- **External dependencies:** MinIO object storage with scan pipeline (DEP-07); dispute store.

## Acceptance Criteria
- **AC-UC284-01:** Given an open dispute, when Admin submits evidence with a note, then an `evidenceId` is returned and the item is listed on the case.
- **AC-UC284-02:** Given a file that fails the scan, when submission is made, then the file is rejected and no partial evidence row exists.
- **AC-UC284-03:** Given a resolved dispute, when evidence is submitted, then `STATE_CONFLICT` is returned and the record is unchanged.
- **AC-UC284-04:** Given evidence is attached, when the case is inspected, then escrow is still frozen pending arbitration (BR-ORD-05).
