# UC-276 — Release an Unused Authorization Hold Manually

## Header Info
- **Use Case ID:** UC-276
- **Title:** Release an Unused Authorization Hold Manually
- **Actor:** Admin (ACT-04)
- **Trigger:** An authorization hold from a checkout session was never captured and did not return to available balance, tying up customer funds
- **Priority:** P1
- **Goal:** Release the orphaned hold exactly once so available balance is restored, with a reason and audit trail — never by editing a balance.
- **Preconditions:** A payment hold exists in `AUTHORIZED` (API-WAL-006) whose checkout session is expired (holds expire with the session, C-13); Admin holds the manual-release right on `POST /wallet/payments/{id}/release` (API-WAL-008, ADMIN alongside the SYSTEM internal path).

## Main Scenario
1. Admin identifies the stuck hold: authorized but not captured, checkout session expired, hold still reported as held (wallet read surfaces).
2. Admin confirms it is genuinely unused — no capture inside the `POST /orders` saga, no active order referencing the payment (authorization/capture split, wallet.md §2).
3. Admin releases with a mandatory reason (`POST /wallet/payments/{id}/release`, API-WAL-008) → status `RELEASED`, held funds return to available balance.
4. The release is a balance-affecting money operation: it posts balanced double-entry ledger rows and an audit entry (BR-PAY-06, BR-PLT-06) — the balance is never hand-edited (rbac.md rows 15/16 are absolute).
5. Admin re-reads the wallet projection to confirm available balance rose by exactly the released hold and no duplicate release exists (BR-PAY-08).

## Alternative Scenarios
- **A1 — Hold still active and checkout live:** do not release — the normal expiry/capture path owns it (C-13); premature release would break checkout integrity.
- **A2 — Already released:** second call returns `STATE_CONFLICT`; the original result stands (API-WAL-008).
- **A3 — SYSTEM already released it:** the internal path won the race → Admin's confirmation step observes `RELEASED` and closes without a second write.

## Exception Scenarios
- **E1 — Payment not found:** `404 NOT_FOUND` → nothing changes; the investigation continues with UC-272/ledger reads.
- **E2 — Missing reason:** `REASON_REQUIRED` blocks the release (API-WAL-008).
- **E3 — Balance/ledger inconsistency suspected:** halt and run reconciliation first — releasing against a drifted balance would compound a RISK-001 defect; no compensating row is invented by hand (BR-ESC-08).

## Postconditions
- The hold is `RELEASED` exactly once; available balance increased by the held amount through balanced ledger rows (BR-PAY-06, BR-PAY-08).
- An audit entry records Admin, reason, payment id, and before/after amounts (BR-PLT-06); no row was UPDATEd or DELETEd.

## Business Rules Applied
- BR-PAY-06, BR-PAY-08, BR-ESC-08, BR-PLT-06

## Related Requirements
- FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) manual release; SYSTEM runs the automatic expiry release; no role may adjust balances directly (rbac.md rows 15/16).
- **Data involved:** payment/hold records, wallet balance, ledger rows, audit entries, checkout session references.
- **External dependencies:** checkout session TTL (C-13); order saga capture path (API-WAL-007, SYSTEM-only); reconciliation job for drift checks (BR-ESC-08).

## Acceptance Criteria
- **AC-UC276-01:** Given an unused hold past session expiry, when the Admin releases it with a reason, then status becomes `RELEASED` and available balance increases by the held amount (API-WAL-008).
- **AC-UC276-02:** Given the release runs, when the ledger is read, then balanced double-entry rows exist behind the balance change (BR-PAY-06).
- **AC-UC276-03:** Given a repeat release attempt, when the call is made, then `STATE_CONFLICT` is returned and only one release exists (BR-PAY-08).
- **AC-UC276-04:** Given a release without a reason, when submitted, then `REASON_REQUIRED` blocks it (API-WAL-008).
