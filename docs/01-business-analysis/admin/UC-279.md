# UC-279 — Freeze Payouts and Top-Up Crediting on a Ledger-Integrity Alarm

## Header Info
- **Use Case ID:** UC-279
- **Title:** Freeze Payouts and Top-Up Crediting on a Ledger-Integrity Alarm
- **Actor:** Admin (ACT-04) — Finance (Admin) is the operational authority for the RISK-001 contingency (risk-register.md)
- **Trigger:** A ledger-integrity alarm fires — balance-vs-ledger (J1) or global-invariant (J2) mismatch, even 1 YER, is a CRITICAL page (RISK-001, DQ-08)
- **Priority:** P0
- **Goal:** Contain money movement the moment the append-only ledger stops agreeing with balances, so exposure stops growing while state is reconstructed.
- **Preconditions:** Alarm received from reconciliation (BR-ESC-08/BR-FIN-03) or the invariant job (DQ-08); Admin holds finance controls (wallet freeze row 13, payout ops row 25); ledger remains append-only (BR-PAY-06).

## Main Scenario
1. Admin acknowledges the page and confirms the mismatch: run status, delta, and affected source on the Data Quality / reconciliation dashboards (data-quality.md §7).
2. Admin executes the RISK-001 contingency in order: freeze payouts (stop release/payout jobs) and suspend top-up crediting (risk-register.md RISK-001 contingency plan).
3. For affected accounts, Admin applies the wallet-freeze path: frozen wallets cannot pay or top up but still receive refunds (BR-PAY-09) — refunds are deliberately not blocked.
4. Admin pages on-call and preserves all evidence: postings stay append-only, nothing is edited to "balance" the books (BR-PAY-06).
5. Every containment action writes an audit entry (BR-PLT-06); the incident record tracks resume criteria — reconstruction from postings + audit chain, Finance-approved compensating entries only.
6. Admin verifies recovery: J1/J2 re-run to zero delta before lifting the freeze (BR-ESC-08, BR-FIN-03).

## Alternative Scenarios
- **A1 — Single-account anomaly:** scope the freeze to the affected wallets instead of a platform-wide halt (BR-PAY-09 account-level path).
- **A2 — Provider-statement-only drift:** no ledger imbalance → targeted hold on that source's crediting (J6 hold) rather than a full freeze.
- **A3 — Fraud-driven imbalance:** freeze implicated wallets, then hand to the dispute/abuse flow with the incident record (FR-020).

## Exception Scenarios
- **E1 — Refund during freeze:** refunds must still credit wallets — a freeze that blocks refunds violates the rule and is corrected immediately (BR-PAY-09).
- **E2 — False alarm:** once J1/J2 re-run clean, the freeze is lifted with an audit entry naming the reason and the verifying run (BR-PLT-06).
- **E3 — Pressure to edit ledger rows:** refused — no role can UPDATE/DELETE ledger or audit rows; reconstruction uses append-only postings and compensating entries only (BR-PAY-06).

## Postconditions
- Payouts and top-up crediting are frozen (platform-wide or scoped), with audit entries and an incident record; exposure is bounded.
- The ledger is byte-for-byte unchanged by containment; refunds continue to credit (BR-PAY-06, BR-PAY-09).

## Business Rules Applied
- BR-PAY-06, BR-PAY-09, BR-ESC-08, BR-FIN-03, BR-PLT-06

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) finance freeze controls (rbac.md rows 13, 25); Super Admin supersedes; Moderator denied finance entirely (§4).
- **Data involved:** ledger rows (read-only), wallet statuses, payout/top-up queues, reconciliation runs, audit entries, incident record.
- **External dependencies:** reconciliation jobs J1/J2/J6 (data-quality.md §5); payout executor (haltable); wallet freeze API (API-ADM-033/034).

## Acceptance Criteria
- **AC-UC279-01:** Given a J1/J2 mismatch of even 1 YER, when the alarm fires, then payouts and top-up crediting are frozen before further money movement (RISK-001).
- **AC-UC279-02:** Given a frozen scope, when a refund is due, then the refund still credits the wallet (BR-PAY-09).
- **AC-UC279-03:** Given containment runs, when the ledger is inspected, then no row was updated or deleted (BR-PAY-06).
- **AC-UC279-04:** Given recovery, when J1/J2 re-run, then the freeze is lifted only after a zero-delta result with an audit entry (BR-ESC-08, BR-PLT-06).
