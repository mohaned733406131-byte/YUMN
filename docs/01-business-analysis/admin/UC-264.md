# UC-264 — Confirm a Hidden Product Is Delisted From Search and Storefront

## Header Info
- **Use Case ID:** UC-264
- **Title:** Confirm a Hidden Product Is Delisted From Search and Storefront
- **Actor:** Admin (ACT-04)
- **Trigger:** A product was hidden through moderation and the operator must verify it vanished from every public surface, not just the admin console
- **Priority:** P2
- **Goal:** Prove the hidden product is delisted from search, storefront, and detail reads while its history and stock records stay intact.
- **Preconditions:** Hide executed with reason (`POST /admin/moderation/{type}/{id}/hide`, API-ADM-028 → `hidden: true`, `auditId`); only ACTIVE, non-deleted products may appear publicly (BR-CAT-06); search index and query-time checks both active.

## Main Scenario
1. Admin confirms the hide response for the product (`hidden: true`, reason recorded, audit entry written, BR-REV-04 discipline applied to the product type).
2. Admin queries public search (`GET /search/products`, API-SRC-001) → the product is absent: exclusion is enforced at index time **and** re-checked at query time (belt-and-braces, search.md).
3. Admin queries the storefront (`GET /stores/{slug}`, API-VND-012) → the product is not in the store's ACTIVE product list (BR-CAT-06).
4. Admin requests the product detail (`GET /products/{slug}`, API-CAT-004) → inactive/hidden reads return `404 NOT_FOUND`.
5. Admin verifies the record still exists internally with stock and history untouched, so restore remains possible (soft-hide, never deletion).

## Alternative Scenarios
- **A1 — Review hidden instead of product:** rating recompute path applies (UC-263); delisting is irrelevant.
- **A2 — Restore:** `POST /admin/moderation/{type}/{id}/restore` (API-ADM-029) returns the product to ACTIVE surfaces after reindex (BR-REV-04).
- **A3 — Suspended store:** store suspension delists products as its own cascade (BR-VND-04) — the moderation hide stays separately reversible (admin.md API-ADM-012 note).

## Exception Scenarios
- **E1 — Reindex lag:** the search index has not caught up → the query-time re-check still excludes the product; if a residual hit appears, Admin re-verifies before signing off (search.md).
- **E2 — Already hidden:** second hide returns `STATE_CONFLICT`; the first audit entry stands (API-ADM-028).
- **E3 — Caller outside moderation scope:** `403 FORBIDDEN` → no hide, no verification session (rbac.md row 20).

## Postconditions
- The product is absent from search, storefront, and detail reads, and still exists internally for restore (BR-CAT-06).
- One audit entry records the hide with its reason; no product row was deleted.

## Business Rules Applied
- BR-CAT-06, BR-REV-04, BR-VND-04

## Related Requirements
- FR-004 (Product Catalog Management), FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Admin/Moderator moderation hide/restore (rbac.md row 20); this UC verifies the effect of an executed hide.
- **Data involved:** product rows (`status`/hidden flag), search index documents, storefront projections, moderation audit entries.
- **External dependencies:** Elasticsearch search index and its query-time re-check (FR-009); storefront product feed (API-VND-012).

## Acceptance Criteria
- **AC-UC264-01:** Given a hidden product, when public search is queried, then the product is absent from results (BR-CAT-06).
- **AC-UC264-02:** Given the hidden product, when the storefront feed is read, then it is not listed among ACTIVE products (BR-CAT-06).
- **AC-UC264-03:** Given the hidden product, when its detail slug is requested, then `404 NOT_FOUND` is returned while the row still exists internally.
- **AC-UC264-04:** Given the hide executed, when the response is read, then `hidden: true`, the reason, and an `auditId` are present (BR-REV-04).
