# UC-125 — Decide a Stalled or Disputed Return Case

## Header Info
- **Use Case ID:** UC-125
- **Title:** Decide a Stalled or Disputed Return Case
- **Actor:** Admin (ACT-04)
- **Trigger:** A vendor misses the 48-hour return decision SLA, or buyer and vendor disagree, so the case surfaces in the platform return queue
- **Priority:** P0
- **Goal:** Issue a final, audited approve/reject decision that clears a stalled or disputed return from the queue.
- **Preconditions:** Admin authenticated with return-arbitration permission (ACT-04); the target return exists in `RETURN_REQUESTED` (or escalated) state with policy snapshot, evidence, and vendor decision history attached.

## Main Scenario
1. Admin opens the platform return queue → client `GET /admin/returns` (conceptual touchpoint for API-RET-010) filtered to `overdue`/`escalated`, sorted by `decisionDueAt`.
2. Admin opens the case → items, reason, evidence images, policy-window calculation, vendor decision history, and inspection notes.
3. Admin reconciles both positions — customer support thread (UC-014), vendor rationale, and any dispute evidence linked to the order.
4. Admin decides: **approve** via `POST /admin/returns/{id}/approve` (API-RET-011) or **reject** via `POST /admin/returns/{id}/reject` (API-RET-012), always with a mandatory reason; the call is version-guarded.
5. System treats the admin decision as final authority (BR-RET-06) and appends an immutable audit entry — actor, action, reason, timestamp — returning its `auditId` (BR-PLT-06).
6. System advances the case along the canonical 17-state machine (DOC-SA-010), notifies both parties, and clears the escalation flag so the queue shrinks.

## Alternative Scenarios
- **A1 — Vendor SLA stall, no dispute:** 48 hours elapsed with no vendor decision → admin decides straight from the escalation queue.
- **A2 — Policy vs dispute conflict:** policy text and dispute grounds disagree → admin is the final arbiter and the reasoning is captured with the decision (BR-RET-06).
- **A3 — Approval path:** approve → return pickup is scheduled through the courier offer flow and the case moves toward received/refunded states.
- **A4 — Rejection path:** reject with reason → the case settles toward its terminal state and the customer sees the recorded reason.

## Exception Scenarios
- **E1 — Permission denied:** caller lacks return-arbitration scope (e.g., Moderator) → `403 FORBIDDEN`, no state change.
- **E2 — Already-resolved case:** another admin decided first → `409 STATE_CONFLICT`; this admin refreshes and reads the recorded outcome.
- **E3 — Missing reason:** approve/reject submitted without a reason → `422 REASON_REQUIRED`; nothing is written.
- **E4 — SLA breach:** case age keeps growing while unreviewed → the queue highlights `overdue` and keeps the escalation flag until a decision lands.

## Postconditions
- The return leaves `RETURN_REQUESTED` as `RETURN_APPROVED` or `RETURN_REJECTED`, with an audit row for the decision (BR-RET-06, BR-PLT-06).
- Both parties are notified, the escalation flag is cleared, and history is appended rather than edited.

## Business Rules Applied
- BR-RET-06, BR-PLT-06

## Permissions / Data / External Dependencies
- **Permissions:** Admin return-arbitration scope; Moderator is read-only on returns (UC-138); Super Admin supersedes (UC-037).
- **Data involved:** Returns, evidence files, policy snapshots, status history, audit log, notifications.
- **External dependencies:** Return pickup/delivery flow (B08); refund engine after approval (B07); support ticketing (B13).

## Acceptance Criteria
- **AC-UC125-01:** Given an escalated return, when the admin approves it, then state becomes `RETURN_APPROVED` and an `auditId` is returned (BR-RET-06, BR-PLT-06).
- **AC-UC125-02:** Given a decision submitted without a reason, when sent, then `REASON_REQUIRED` is returned and no state changes.
- **AC-UC125-03:** Given a case already decided by another admin, when this admin submits, then `STATE_CONFLICT` is returned and the recorded outcome stays intact.
- **AC-UC125-04:** Given a Moderator account, when approve/reject is attempted, then access is denied (`403 FORBIDDEN`).
