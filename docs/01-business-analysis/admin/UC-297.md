# UC-297 — Extract Audit Evidence for a Security Incident

## Header Info
- **Use Case ID:** UC-297
- **Title:** Extract Audit Evidence for a Security Incident
- **Actor:** Admin (ACT-04)
- **Trigger:** A security incident (secret leak, OTP abuse, suspicious admin action) opens and the response runbook requires the audit trail for the implicated window
- **Priority:** P1
- **Goal:** Pull the scoped, immutable audit entries for the incident so the response is built on evidence, not recollection.
- **Preconditions:** Incident recorded and its window/actors known; audit log queryable with filters (API-ADM-024); log is append-only (BR-PLT-06); extraction follows runbook #10 (security incident → rotate, lockout review, audit extraction).

## Main Scenario
1. Admin defines the slice: `actorId`/`targetId`/`action` and `from`–`to` covering the incident window (`GET /admin/audit-log`, API-ADM-024).
2. System pages the result with the sole cursor-paginated admin table — entries carry `at`, `actorRole`, `action`, `targetType`, `targetId`, `reason`, `ipHash`, `correlationId`.
3. Admin walks the pages until the window is complete, noting gaps (an absence of entries is itself evidence).
4. Admin correlates entries via `correlationId` to the related logs/traces in the incident record.
5. The extracted set is attached to the incident with its filters documented, so the extraction itself is reproducible.

## Alternative Scenarios
- **A1 — Narrow actor scope:** the incident implicates one actor → filter by `actorId` for a compact, reviewable sequence.
- **A2 — Cross-entity action sweep:** the incident concerns one entity (e.g. a wallet) → filter by `targetId`/`action` to reconstruct every touch on it.
- **A3 — Follow-on actions:** findings feed remediation (UC-303) or, for chain doubt, the chain-break investigation (UC-296).

## Exception Scenarios
- **E1 — Read outside permission scope:** `FORBIDDEN` → nothing disclosed; scoping is enforced server-side (API-ADM-024).
- **E2 — Malformed filter values:** `VALIDATION_ERROR` → no partial window returned — an incomplete extraction is never presented as complete.
- **E3 — Log store unavailable:** the read fails → extraction is reported incomplete and retried; the incident record marks the gap rather than filling it.

## Postconditions
- Success: the incident holds a complete, filter-documented set of immutable audit entries for its window; no audit row was created or changed by the extraction.
- Failure: no extraction is attached, nothing is written, and the audit trail remains untouched.

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) platform-scope audit read; Super Admin full scope; nobody edits audit rows (append-only, write-only by System).
- **Data involved:** audit entries (actor, action, entity, before/after, IP hash, correlation ID), incident record.
- **External dependencies:** structured log store and trace backend for correlation (`12-non-functional/core/observability.md` runbook #10).

## Acceptance Criteria
- **AC-UC297-01:** Given an incident window, when the filtered audit query runs, then entries covering that window are returned with their correlation IDs (API-ADM-024).
- **AC-UC297-02:** Given the extraction, when it is attached to the incident, then the exact filters used are recorded so it can be reproduced.
- **AC-UC297-03:** Given an out-of-scope query, when it is made, then `FORBIDDEN` is returned and no entries are disclosed.
- **AC-UC297-04:** Given the extraction completes, when the audit log is re-read, then no entry was added, edited or removed by the process (BR-PLT-06).
