# UC-305 — Review the Monthly Security Severity Report

## Header Info
- **Use Case ID:** UC-305
- **Title:** Review the Monthly Security Severity Report
- **Actor:** Admin (ACT-04)
- **Trigger:** The month closes and the recurring severity report of the findings register is due (SEC-REQ-012; `09-security/core/security-controls.md` §6)
- **Priority:** P2
- **Goal:** Review findings by severity for the month with zero silent suppressions, and confirm remediation health going into the next cycle.
- **Preconditions:** Findings registry current for the month; severities assigned and only reclassified with evidence; report must show every finding by severity without unjustified suppressions.

## Main Scenario
1. Admin generates the month's report from the findings registry — counts by severity (CRITICAL/HIGH/MEDIUM/LOW), open vs closed.
2. Admin checks suppression hygiene: every excluded or deferred item carries a written justification; silence is not an option.
3. Admin reviews the CRITICAL/HIGH rows against their SLA outcomes for the month (UC-303), noting breaches carried forward.
4. Admin verifies closure quality: each closed row has fix/accepted-risk, evidence and severity re-check — findings are never deleted.
5. Admin distributes the report to the stakeholders and files it as the month's control evidence.

## Alternative Scenarios
- **A1 — Clean month:** no CRITICAL findings, all HIGH within window → report records the absence explicitly rather than omitting the section.
- **A2 — Justified suppression:** a deferred finding appears with its rationale and owner → accepted as a disclosed suppression, not a hidden one.
- **A3 — Severity reclassified during the month:** the reclassification is shown with its evidence so severity trend stays interpretable.

## Exception Scenarios
- **E1 — Registry inconsistent (closed row without evidence):** report generation flags the row instead of counting it as remediated.
- **E2 — Report omits a severity band:** treated as a generation defect — the report is regenerated until all bands are present.
- **E3 — Registry unavailable:** the report is late and recorded as late; a fabricated "no findings" month is never issued.

## Postconditions
- Success: a complete monthly severity report exists — every finding by severity, suppressions justified, SLA outcomes visible — and is filed as evidence.
- Failure: no report (or an incomplete one) is issued; findings data itself is untouched by the reporting step.

## Business Rules Applied
- No DOC-BA-005 rule governs severity reporting — rule of record is SEC-REQ-012 (recurring reporting by severity, no silent suppressions, `09-security/core/security-findings.md`)

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) registry review and reporting; security owner signs severity decisions; Super Admin receives escalations.
- **Data involved:** findings registry (severity, status, dates, evidence, suppressions), SLA outcomes (read).
- **External dependencies:** CI/CD scan output feeding the registry; distribution channel for stakeholders.

## Acceptance Criteria
- **AC-UC305-01:** Given the month's registry, when the report is generated, then findings appear grouped by every severity band.
- **AC-UC305-02:** Given any suppressed or deferred finding, when the report is read, then a written justification is attached.
- **AC-UC305-03:** Given a closed finding, when it is counted as remediated, then evidence and severity re-check are present on its row.
- **AC-UC305-04:** Given the report completes, when it is filed, then no registry row was deleted or altered by the reporting step.
