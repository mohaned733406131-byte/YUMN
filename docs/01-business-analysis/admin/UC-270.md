# UC-270 — Force a Sub-Order State Correction Within the 17-State Table

## Header Info
- **Use Case ID:** UC-270
- **Title:** Force a Sub-Order State Correction Within the 17-State Table
- **Actor:** Admin (ACT-04)
- **Trigger:** A sub-order is stuck or mis-stated and normal party transitions cannot reach the correct state (stalled vendor, lost scan, reconciliation finding)
- **Priority:** P0
- **Goal:** Apply an audited admin override that lands the sub-order on a legal state — never an invented one — with history appended and the master re-evaluated.
- **Preconditions:** Sub-order exists with a current `version`; the transition table has exactly 17 states (C-09, BR-ORD-01); Admin holds order-override rights (rbac.md row 18); a reason is available for the record.

## Main Scenario
1. Admin locates the sub-order via the operations queue (API-ORD-013) and reads its state, version, and full timeline (API-ORD-005).
2. Admin chooses the target state from the canonical 17-state list only (`POST /admin/orders/{id}/transition` with `{ subOrderId, toState, reason }`, API-ORD-014).
3. System validates `toState` against the transition table (C-09, BR-ORD-01) — an unknown or illegal move is rejected outright; no 18th state can ever be produced.
4. On success the response returns the new state, incremented `version`, a `historyEntry` (actor, timestamp, reason — append-only, BR-ORD-03), and an `auditId` (BR-PLT-06).
5. The master order is re-evaluated: it reaches `COMPLETED` only when every sub-order is `COMPLETED` or `REFUNDED` (BR-ORD-07); any escrow-bearing state change follows the escrow rules (BR-ESC-02).

## Alternative Scenarios
- **A1 — Correction that starts a dispute-freeze path:** landing on a state that freezes escrow applies the freeze for the affected sub-order only (BR-ORD-05).
- **A2 — Correction resolves a stuck SLA escalation:** the 24-hour flag clears once the sub-order moves past `CONFIRMED` (BR-ORD-10).
- **A3 — Moderator viewing:** Moderator may read the queue and timeline but every transition call returns `FORBIDDEN` (API-ORD-014).

## Exception Scenarios
- **E1 — Illegal or unknown target state:** validation fails (`STATE_CONFLICT`/`VALIDATION_ERROR`) → no history entry, no audit entry, state unchanged (BR-ORD-01, C-09).
- **E2 — Stale `version`:** another actor moved it first → `409 STATE_CONFLICT`; history unchanged (BR-ORD-03, optimistic locking).
- **E3 — Missing reason:** `REASON_REQUIRED` blocks the override — every forced transition is reasoned (API-ORD-014).

## Postconditions
- The sub-order sits on a legal canonical state with a new append-only history row and one audit entry naming Admin, reason, before/after (BR-ORD-03, BR-PLT-06).
- The master reflects the aggregate of sub-order states (BR-ORD-07); escrow effects, if any, follow the rules — never a side-channel edit.

## Business Rules Applied
- BR-ORD-01, BR-ORD-03, BR-ORD-05, BR-ORD-07, BR-ORD-10, BR-PLT-06

## Related Requirements
- FR-012 (Order Lifecycle Management), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) order override (rbac.md row 18); Moderator denied (read-only); SYSTEM performs automated transitions separately.
- **Data involved:** sub-order state and `version`, order status history, escrow holds, master projection, audit entries.
- **External dependencies:** state machine in `03-system-analysis/core/state-transitions.md` (C-09); escrow/refund engines (B07).

## Acceptance Criteria
- **AC-UC270-01:** Given a canonical target state, when the Admin forces the transition, then the sub-order lands on it with `version` incremented and a `historyEntry` (BR-ORD-01, BR-ORD-03).
- **AC-UC270-02:** Given a state outside the 17-state table, when the call is made, then it is rejected and nothing changes (C-09, BR-ORD-01).
- **AC-UC270-03:** Given any forced transition, when it completes, then one append-only audit entry exists with reason and before/after (BR-PLT-06).
- **AC-UC270-04:** Given all sub-orders are `COMPLETED` or `REFUNDED`, when the master is re-evaluated, then it reaches `COMPLETED` (BR-ORD-07).
