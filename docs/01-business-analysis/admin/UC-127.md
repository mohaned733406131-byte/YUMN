# UC-127 — Review Vendor Payout Runs

## Header Info
- **Use Case ID:** UC-127
- **Title:** Review Vendor Payout Runs
- **Actor:** Admin (ACT-04)
- **Trigger:** Payout batches are scheduled or executed, or a daily reconciliation result flags a finance anomaly
- **Priority:** P1
- **Goal:** Review payout runs against escrow eligibility and reconciliation results so money leaves the platform only when it should.
- **Preconditions:** Admin authenticated with finance-operations permission (ACT-04); payout runs and reconciliation results exist for the selected period; run execution itself belongs to the system batch (UC-052).

## Main Scenario
1. Admin opens the finance console route `/[locale]/admin/finance/payouts` (routing.md §4) → payout run list with batch status, scheduled date, and totals.
2. System groups payouts per escrow release: execution runs 3–7 business days after release, and amounts below the 1,000 YER minimum roll over (BR-ESC-05).
3. Admin opens a run → per-vendor payout rows with eligibility flags, rollover entries, masked destinations, and provider references.
4. Admin cross-checks the daily reconciliation result for the same date — ledger vs wallet vs escrow vs payable vs provider statements (BR-ESC-08).
5. On a mismatch the platform has already alerted finance (BR-ESC-08); admin tracks the delta to resolution inside the reconciliation view.
6. Admin confirms the run's execution status or lets it wait for the next batch; below-minimum balances stay queued for rollover (BR-ESC-05).

## Alternative Scenarios
- **A1 — Below-minimum rollover:** payout under 1,000 YER → shown as rolled over, not paid (BR-ESC-05).
- **A2 — Mismatch day:** reconciliation status `MISMATCH` → admin investigates the delta with the finance alert as the trigger (BR-ESC-08).
- **A3 — Empty period:** no runs in the selected range → empty state with filter reset; no error.
- **A4 — Execution is system-owned:** admin reviews and annotates only — batch execution belongs to UC-052, never a manual admin payout.

## Exception Scenarios
- **E1 — Permission denied:** caller without finance scope (or Moderator) → `403 FORBIDDEN`, route blocked.
- **E2 — Empty queue:** zero payout runs or zero reconciliation rows → friendly empty state, not a failure.
- **E3 — Already-executed run:** run finished → rows are read-only; no admin action can re-trigger it (UC-052 owns execution).
- **E4 — SLA breach:** a run ages past its scheduled execution window → flagged for investigation until executed or rolled over (BR-ESC-05).

## Postconditions
- Payout runs are reviewed against eligibility (BR-ESC-05) and reconciliation (BR-ESC-08); mismatches stay tracked until resolved.
- Review itself mutates no ledger, escrow, or payable figures.

## Business Rules Applied
- BR-ESC-05, BR-ESC-08

## Related Requirements
- FR-014 (Escrow, Commission & Vendor Payouts), FR-020 (Platform Administration, Settings & Audit)
- **Cross-reference:** UC-052 (system executes the payout batches).

## Permissions / Data / External Dependencies
- **Permissions:** Admin finance-operations scope; Moderator excluded from finance ops (routing.md §4).
- **Data involved:** Payout runs, payout rows, escrow release refs, reconciliation results, provider statements.
- **External dependencies:** Payout batch queue (B07); reconciliation job (B07); payment providers (statement feeds).

## Acceptance Criteria
- **AC-UC127-01:** Given a payout run, when opened, then batches show scheduled execution 3–7 business days after release (BR-ESC-05).
- **AC-UC127-02:** Given a payout below 1,000 YER, when the run is reviewed, then it appears as rolled over rather than executed (BR-ESC-05).
- **AC-UC127-03:** Given a reconciliation mismatch, when the date is selected, then status `MISMATCH` with the delta is visible (BR-ESC-08).
- **AC-UC127-04:** Given a Moderator account, when the payouts route is opened, then access is denied (Admin+ per routing).
