# UC-259 — Audit Four-Eyes Compliance on Money Operations

## Header Info
- **Use Case ID:** UC-259
- **Title:** Audit Four-Eyes Compliance on Money Operations
- **Actor:** Admin (ACT-04) — Trust & Safety / Finance oversight bundle (rbac.md §11)
- **Trigger:** A periodic (or incident-driven) review asks whether money operations honoured the four-eyes rule — initiator ≠ approver
- **Priority:** P1
- **Goal:** Prove that every money action was approved by someone other than its initiator, and surface any self-approved operation as a compliance exception.
- **Preconditions:** Admin authenticated with platform-scope audit read (rbac.md row 22); money operations in scope: top-up verify/reject, wallet freeze/unfreeze, refund approval, payout batch approval (rbac.md §11 guardrail); audit log append-only (BR-PLT-06).

## Main Scenario
1. Admin opens the audit log (API-ADM-024, cursor stream) filtered to the money actions in scope and the review period.
2. System returns each entry with actor, action, target entity, before/after status, `ipHash`, and `correlationId` — exactly the fields a four-eyes attestation needs (BR-PLT-06).
3. Admin pairs records per operation: the initiator (who raised or first touched the request) and the approver (who returned the final `auditId`-bearing decision).
4. Admin verifies the two identities differ — the guardrail requires ORG-01 initiator ≠ approver on verify/freeze/refund/payout actions (rbac.md §11).
5. Exceptions (same identity on both sides, or a missing approver record) are written to the compliance log with evidence pointers; compliant periods are attested with the entry range used.
6. The audit is read-only: no money state, role grant, or setting is changed by this use case.

## Alternative Scenarios
- **A1 — System-scheduled execution:** the payout execution step has no human approver (SYSTEM, rbac.md row 25) → evaluated against the batch approval record that authorised it, not as a violation.
- **A2 — Moderator appears in a money log:** impossible by matrix (Moderator denied rows 12–14/25, rbac.md §4) → any such row is itself a critical finding requiring immediate escalation.
- **A3 — Sampled review:** full-range enumeration is too large → a bounded window is attested and the range recorded; the cursor position is preserved for the next window.

## Exception Scenarios
- **E1 — Audit hash-chain verification failed:** chain break detected (J10) → stop the attestation, page per CRITICAL severity, and freeze privileged writes for investigation (data-quality.md §5).
- **E2 — Entry missing its approver record:** operation exists without a second identity → flagged as a four-eyes violation with entity reference; remediation is assigned, not auto-fixed.
- **E3 — Caller lacks audit read:** `403 FORBIDDEN` → no partial attestation is issued; Moderator and non-admin roles never reach the data (rbac.md §4).

## Postconditions
- A compliance result exists for the reviewed window: pass with evidence range, or exceptions with entity references and owners.
- No money, role, or settings state was mutated; the audit trail itself is unchanged.

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) platform-scope audit read; Super Admin full read; Moderator denied (rbac.md §4); strictly read-only.
- **Data involved:** audit entries (money actions), approver/initiator pairs, compliance exception log.
- **External dependencies:** audit hash-chain verification job J10 (data-quality.md §5); cursor pagination exception (pagination.md §1).

## Acceptance Criteria
- **AC-UC259-01:** Given a money operation in the review window, when its entries are paired, then initiator and approver are two distinct identities (rbac.md §11).
- **AC-UC259-02:** Given an operation approved by its own initiator, when the review runs, then it is recorded as an exception with entity reference (BR-PLT-06).
- **AC-UC259-03:** Given the audit chain fails verification, when J10 reports it, then the attestation stops and privileged writes are frozen (data-quality.md §5).
- **AC-UC259-04:** Given a Moderator account requests the audit stream, when the call is made, then it is denied (rbac.md §4).
