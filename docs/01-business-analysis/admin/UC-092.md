# UC-092 — Reactivate a Suspended User Account

## Header Info
- **Use Case ID:** UC-092
- **Title:** Reactivate a Suspended User Account
- **Actor:** Admin (ACT-04) — user administration scope
- **Trigger:** Admin lifts a suspension after review
- **Priority:** P1
- **Goal:** Return a suspended account — and optionally its store and wallet scopes — to active service with a recorded reason.
- **Preconditions:** Admin authenticated with activate permission (API-ADM-004 `ADMIN`); target status is `SUSPENDED`; a reason is supplied.

## Main Scenario
1. Admin opens the suspended user (UC-090) → Reactivate → selects scopes `ACCOUNT`, `STORE`, `WALLET` and a mandatory reason.
2. Client `POST /admin/users/{id}/activate` with `{ scopes, reason }` (API-ADM-004).
3. System flips the selected scopes back to `ACTIVE` and returns the new status with an `auditId`.
4. The store scope is granted only while KYC remains valid — otherwise that scope is refused (`KYC_NOT_APPROVED`) and the store stays suspended pending a KYC decision (UC-031).
5. The reversal writes an append-only audit entry with actor, reason and before/after state (BR-PLT-06).

## Alternative Scenarios
- **A1 — Partial reactivation:** Only `ACCOUNT` is restored while store and wallet remain held (e.g. payout review still open).
- **A2 — Full reactivation:** All scopes active; the suspended-store effects of BR-VND-04 are lifted together.

## Exception Scenarios
- **E1 — Permission denied:** Moderator → `403 FORBIDDEN`; nothing changes.
- **E2 — Not suspended:** Server returns `STATE_CONFLICT`; the call is a no-op for an already-active account.
- **E3 — Concurrent suspension:** Another admin re-suspends meanwhile → conflict returned; the client re-reads state before retrying.
- **E4 — KYC lapsed:** `STORE` scope blocked until the KYC decision lands while the account scope still restores (decision SLA handled in UC-031).

## Postconditions
- Selected scopes are `ACTIVE`; unselected scopes keep their prior state.
- One audit entry exists per state change (BR-PLT-06); no money moved.

## Business Rules Applied
- BR-PLT-06

## Related Requirements
- FR-002 (Roles, Permissions & Access Control)

## Permissions / Data / External Dependencies
- **Permissions:** `ADMIN` only; scopes are explicit per request, never implicit.
- **Data involved:** User status flags, linked store/KYC projection, audit entry.
- **External dependencies:** KYC service (validity gate); audit writer (BR-PLT-06).

## Acceptance Criteria
- **AC-UC092-01:** Given a suspended user, when activate is posted with `ACCOUNT`, then status becomes `ACTIVE` and an `auditId` returns.
- **AC-UC092-02:** Given an already-active user, when posted, then `STATE_CONFLICT` returns with no change.
- **AC-UC092-03:** Given invalid KYC, when `STORE` scope is requested, then `KYC_NOT_APPROVED` returns for that scope.
- **AC-UC092-04:** Given no reason, when posted, then `REASON_REQUIRED` returns and no state changes.
