# UC-034 — Verify Bank-Transfer Top-Up

## Header Info
- **Use Case ID:** UC-034
- **Title:** Verify Bank-Transfer Top-Up
- **Actor:** Admin (ACT-04) — finance scope
- **Trigger:** A customer submits a bank-transfer top-up request awaiting manual verification
- **Priority:** P1
- **Goal:** Credit the customer's wallet only after verifying the transfer reference (manual admin verification rail, C-05/BR-PAY-04).
- **Preconditions:** Customer initiated a top-up within bounds 1,000–5,000,000 YER (BR-PAY-02) with upload/reference of the bank transfer; Admin has finance permission.

## Main Scenario
1. Admin opens the top-up verification queue → client `GET /admin/topups?status=pending` lists requests: user, amount (integer YER, BR-PAY-10), reference, submitted proof image/PDF, timestamp.
2. Admin opens a case → compares the reference/amount against the bank statement evidence provided (INT-REQ-002 manual flow).
3. Admin approves → client `POST /admin/topups/{id}/verify`; system credits the wallet inside an ACID transaction posting **balanced double-entry ledger rows** (BR-PAY-06, DATA-REQ-007) with idempotency key (BR-PAY-08, BR-PLT-03).
4. Customer receives a top-up confirmation notification (BR-NTF-01); balance updates (never negative, BR-PAY-05).
5. Admin rejects with reason (mismatch/invalid proof) → no credit; customer notified and may resubmit.
6. System writes an append-only audit entry for the money action (BR-PLT-06, SEC-REQ-010).

## Alternative Scenarios
- **A1 — Mobile wallet top-ups (m-Floos/OneCash):** Not this UC — credited only after verified provider callback/reconciled poll (BR-PAY-03, INT-REQ-001); admin does not hand-credit those.
- **A2 — Partial mismatch:** Amount differs from reference → reject with reason; never credit a mismatched amount (BR-PAY-04).
- **A3 — Frozen wallet (BR-PAY-09):** Credit is still posted (frozen wallets receive refunds/credits) but remains unusable for payment/top-up until unfrozen.

## Exception Scenarios
- **E1 — Duplicate verification:** Same request verified twice → idempotency key ensures single credit (BR-PAY-08); second call no-ops.
- **E2 — Out-of-bounds amount:** Request outside 1,000–5,000,000 YER → rejected at intake (BR-PAY-02); never reaches queue.
- **E3 — Ledger write failure:** Credit fails mid-transaction → transaction rolls back; queue item stays pending; alert raised (BR-PLT-02, BR-ESC-08 reconciliation).

## Postconditions
- Approved: wallet credited exactly once with balanced ledger rows; request `VERIFIED`; audit row exists.
- Rejected: no balance/ledger change; customer notified with reason.

## Business Rules Applied
- BR-PAY-02, BR-PAY-04, BR-PAY-05, BR-PAY-06, BR-PAY-08, BR-PAY-09, BR-PAY-10, BR-PLT-03, BR-PLT-06, BR-ESC-08

## Related Requirements
- FR-013 (Wallet & Payment Processing), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin finance scope; customers can only submit requests; ledger append-only — nobody edits rows (DOC-OVR-007, DATA-REQ-007).
- **Data involved:** Top-up requests, proof files (SEC-REQ-011), wallet balance, ledger entries, audit log.
- **External dependencies:** Bank statement evidence (manual, C-05); wallet/ledger service (B07).

## Acceptance Criteria
- **AC-UC034-01:** Given a verified 50,000 YER transfer, when approved, then balance increases by 50,000 with balanced debit+credit rows (BR-PAY-06).
- **AC-UC034-02:** Given double approval clicks, when processed, then the wallet is credited once (BR-PAY-08).
- **AC-UC034-03:** Given a 500 YER request, when submitted, then it is rejected (min 1,000 YER, BR-PAY-02).
