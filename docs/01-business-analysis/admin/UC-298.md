# UC-298 — Re-Drive a Failed Job From the Dead-Letter Queue

## Header Info
- **Use Case ID:** UC-298
- **Title:** Re-Drive a Failed Job From the Dead-Letter Queue
- **Actor:** Admin (ACT-04)
- **Trigger:** A queue's DLQ depth alert fires and the underlying defect has been fixed, so the parked payloads must be processed again
- **Priority:** P1
- **Goal:** Re-drive dead-lettered jobs after a fix with identical idempotency guarantees, so the events land exactly once — not zero, not twice.
- **Preconditions:** Entries sit in a DLQ after 3 retries with exponential backoff (BR-PLT-02); the defect is fixed and verified; Admin holds DLQ console access (admin-only, FR-020); queue naming follows `{block}.{entity}.{action}` (BR-PLT-01).

## Main Scenario
1. Admin opens the DLQ console for the alerted queue and reads each entry: payload, error, correlation ID.
2. Admin confirms the root cause is fixed (deploy/config) before touching any payload.
3. Admin re-drives a stored entry — the payload is re-enqueued with its original idempotency key (webhook-reliability §1.4).
4. System processes it idempotently: the provider/event ID short-circuits duplicates, so N deliveries still yield exactly one domain effect.
5. Admin confirms the entry drained, DLQ depth returned to zero, and the replay is written as an audited privileged action.

## Alternative Scenarios
- **A1 — Partial re-drive:** only poison-adjacent entries are replayed first; the rest follow after verification — depth decreases incrementally.
- **A2 — Payload now stale by state:** the domain handler rejects it with a state conflict no-op rather than corrupting state — reprocessing is always state-guarded.
- **A3 — Alert clears without re-drive:** root cause fixed and provider re-delivered → the entry is dropped as an idempotent no-op; depth still returns to zero.

## Exception Scenarios
- **E1 — Re-drive attempted before the fix:** handler fails again → entry re-enters DLQ after retries, alert persists; no partial state is written (BR-PLT-02).
- **E2 — Payload unreadable (deserialization failure):** it never reaches the domain handler → quarantined for inspection, never force-processed.
- **E3 — Non-admin access to the console:** denied by default — the DLQ console is admin-only (FR-020); nothing re-enqueued.

## Postconditions
- Success: the DLQ is empty, each replayed event produced exactly one domain effect, and one audit entry records Admin's replay action (BR-PLT-06).
- Failure: entries remain parked with the alert active — never half-processed, never duplicated.

## Business Rules Applied
- BR-PLT-01, BR-PLT-02, BR-PLT-06

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) DLQ console (deny-by-default RBAC); operators observe, only Admin re-drives.
- **Data involved:** DLQ entries (payload, error, correlation ID), idempotency keys, domain rows written by the replay, audit entries.
- **External dependencies:** BullMQ queues/Redis (DEP-03); webhook ingress persistence; alert route on DLQ depth (`10-integrations/core/webhook-reliability.md` §4).

## Acceptance Criteria
- **AC-UC298-01:** Given a dead-lettered entry after a fix, when Admin re-drives it, then it processes and DLQ depth decreases.
- **AC-UC298-02:** Given the same entry re-driven twice, when it completes, then exactly one domain effect exists (idempotency preserved).
- **AC-UC298-03:** Given a still-broken handler, when re-drive runs, then the entry returns to the DLQ and the alert persists (BR-PLT-02).
- **AC-UC298-04:** Given any successful re-drive, when it completes, then one audit entry records Admin as the actor (BR-PLT-06).
