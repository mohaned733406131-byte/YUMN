# UC-296 — Investigate an Audit Hash-Chain Verification Failure

## Header Info
- **Use Case ID:** UC-296
- **Title:** Investigate an Audit Hash-Chain Verification Failure
- **Actor:** Admin (ACT-04)
- **Trigger:** The hourly audit hash-chain verification job reports a broken link and privileged writes are frozen pending investigation
- **Priority:** P0
- **Goal:** Determine whether the chain break is tampering, a migration/restore artifact, or a job defect — and restore confidence in the audit trail before the freeze lifts.
- **Preconditions:** Audit log is append-only with a hash chain; the verification job runs hourly and alerts on mismatch; privileged-write freeze is active; Admin verifies the chain (data-quality §9 stewardship).

## Main Scenario
1. Admin receives the chain-break alert and confirms the failing partition and row range from the job output.
2. Admin reads the surrounding audit entries (`GET /admin/audit-log`, API-ADM-024) filtered to the suspect window — the log is never editable (`AUDIT_LOG_IMMUTABLE`).
3. Admin compares chain links around the break: identify the first entry whose stored hash does not match its predecessor's.
4. Admin reconstructs the cause from correlated signals — deployments, restores, or direct DB access — using the entry's `correlationId` and `ipHash`.
5. Findings and disposition are recorded (append-only, BR-PLT-06); only after the chain is explained does the privileged-write freeze lift, escalated to Super Admin if unresolved.

## Alternative Scenarios
- **A1 — Job/infra defect:** the break traces to a failed migration or restore artifact → chain segment re-verified from the backup window, freeze lifted with a documented explanation.
- **A2 — Confirmed tamper indication:** evidence of out-of-band modification → freeze stays on, escalated to Super Admin and the security incident path (UC-297).
- **A3 — Alert resolves on re-run:** transient read error → job re-run passes, first failure documented as a false positive.

## Exception Scenarios
- **E1 — Audit log read fails:** temporary error → investigation paused with the freeze still active; nothing is cleared on an unreadable log.
- **E2 — Attempt to "repair" an entry directly:** impossible by design — no `UPDATE`/`DELETE` path exists; any such attempt itself fails and is recorded (BR-PLT-06).
- **E3 — Break spans multiple partitions:** scope widens; resolution is not partial — the freeze covers all affected privileged writes until every segment is explained.

## Postconditions
- Success: the break has a documented cause and evidence, the chain is verified, and the freeze is lifted deliberately — with one audit entry per action taken (BR-PLT-06).
- Failure: freeze remains active, the trail stays unreadable-as-trusted, and no audit row was altered — integrity is never "fixed" by editing history.

## Related Requirements

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) audit read + investigation; the application role holds no audit write (write-only by System); escalation to Super Admin.
- **Data involved:** audit log partitions, hash chain links, job output/alerts, deployment and access records (read).
- **External dependencies:** hourly verification job and its alert route (`16-data/core/data-quality.md` §5); audit store.

## Acceptance Criteria
- **AC-UC296-01:** Given a chain-break alert, when Admin reads the audit log around the break, then the first mismatching entry is identified without any edit to the log (API-ADM-024).
- **AC-UC296-02:** Given a resolved cause, when the investigation closes, then exactly one audit entry records the disposition (BR-PLT-06).
- **AC-UC296-03:** Given an unresolved break, when it is investigated, then the privileged-write freeze stays active until explained.
- **AC-UC296-04:** Given any repair attempt, when it is made, then direct modification of audit rows is impossible.
