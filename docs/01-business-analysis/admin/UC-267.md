# UC-267 — Verify the Cascade Effects of a Store Suspension

## Header Info
- **Use Case ID:** UC-267
- **Title:** Verify the Cascade Effects of a Store Suspension
- **Actor:** Admin (ACT-04)
- **Trigger:** A store was just suspended (or is under review) and the operator must confirm every declared cascade effect actually took hold
- **Priority:** P2
- **Goal:** Prove that suspension hid the products, blocked new orders, froze existing orders, and held payouts — exactly the four effects the rule declares, with nothing extra broken.
- **Preconditions:** Store suspended with reason (`POST /admin/stores/{id}/suspend`, API-ADM-012) or inherited from a suspended owner (API-ADM-003); suspension cascade defined by BR-VND-04.

## Main Scenario
1. Admin reads the suspension response → `affected: { productsDelisted, ordersBlocked }` plus `auditId` (API-ADM-012).
2. Admin checks the store projection (`GET /admin/stores/{id}`, API-ADM-010) → `status = SUSPENDED` with `counts: { products, ordersOpen, returnsOpen }` for open exposure.
3. Admin verifies public surfaces: storefront reads 404 and product writes return `STORE_SUSPENDED` (admin.md §2 suspension behaviour, BR-VND-04).
4. Admin verifies money effects: new orders are blocked at checkout and payouts are held pending review (BR-VND-04) — payout eligibility also requires a non-suspended store (BR-ESC-06).
5. Admin confirms open orders are frozen, not cancelled, and open returns/disputes remain resolvable (BR-ORD-05 keeps escrow frozen for disputed sub-orders regardless).
6. The verification is recorded with the response snapshot; reactivation happens only in a separate, reason-bearing action.

## Alternative Scenarios
- **A1 — Moderation-only concern:** use content hide instead of suspension — the moderation hide stays separately reversible (admin.md API-ADM-012 note, UC-264).
- **A2 — Suspension inherited from the owner:** suspending the user suspends the store (API-ADM-003) → same cascade, same verification steps.
- **A3 — Reactivation later:** `POST /admin/stores/{id}/activate` restores state unless KYC is invalid (UC-266); effects unwind in reverse.

## Exception Scenarios
- **E1 — Already suspended:** repeat suspension returns `STATE_CONFLICT`; the original audit entry stands (API-ADM-012).
- **E2 — Missing reason:** `REASON_REQUIRED` blocks the suspension — no cascade starts without a recorded reason.
- **E3 — Effect missing after suspension:** a product still visible or an order still accepted → treated as a defect, escalated with the `auditId` evidence; no manual patching of rows.

## Postconditions
- All four declared effects are confirmed present: products delisted, new orders blocked, existing orders frozen, payouts held (BR-VND-04).
- Store remains `SUSPENDED` with exactly one audit entry; no order, escrow, or ledger row was rewritten.

## Business Rules Applied
- BR-VND-04, BR-ESC-06, BR-ORD-05, BR-PLT-06

## Related Requirements
- FR-007 (Vendor Onboarding & KYC), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) store lifecycle; Moderator read-only (rbac.md §4); verification is read-only.
- **Data involved:** store status, product visibility flags, order queue state, payout eligibility, open returns/disputes, audit entries.
- **External dependencies:** storefront/search surfaces that must reflect the delist; payout scheduler that must hold batches (BR-ESC-05).

## Acceptance Criteria
- **AC-UC267-01:** Given a suspended store, when its storefront is read, then it 404s and its products are not listed (BR-VND-04).
- **AC-UC267-02:** Given a suspended store, when a customer attempts a new order, then the order is blocked (BR-VND-04).
- **AC-UC267-03:** Given existing orders on the suspended store, when checked, then they are frozen, not cancelled, and payouts are held (BR-VND-04, BR-ESC-06).
- **AC-UC267-04:** Given the suspension completes, when the response returns, then `affected` reports `productsDelisted` and `ordersBlocked` with an `auditId` (API-ADM-012).
