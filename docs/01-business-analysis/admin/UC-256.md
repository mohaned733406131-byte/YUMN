# UC-256 — Investigate Account-Lockout and OTP-Abuse Signals

## Header Info
- **Use Case ID:** UC-256
- **Title:** Investigate Account-Lockout and OTP-Abuse Signals
- **Actor:** Admin (ACT-04) — security on-call duties are mapped to Admin
- **Trigger:** The security/auth dashboard shows a cluster of account lockouts, OTP verification failures, or 429 rate-limit spikes for one or more accounts
- **Priority:** P1
- **Goal:** Determine whether the cluster is credential abuse, OTP abuse, or a provider fault, and hand a substantiated finding to enforcement without mutating any account state.
- **Preconditions:** Admin authenticated with platform-scope audit read (rbac.md row 22); observability stack live (dashboards #11 and #8); audit log append-only and readable (`GET /admin/audit-log`, API-ADM-024).

## Main Scenario
1. Admin opens the security/auth panel (OTP send/verify/fail rates, lockouts, 429s, anomalous logins) and selects the offending account or phone range.
2. Admin filters the audit log by actor, action, and time window (API-ADM-024, the sole cursor-paginated admin table) → system returns lock events with actor, action, target, `ipHash`, and `correlationId`.
3. System shows the lock evidence: 5 consecutive failed logins locked the account for 15 minutes and the lock event was logged (BR-AUTH-04).
4. Admin cross-checks OTP behaviour against the OTP contract — 3 verification attempts max, 60 s resend cooldown, max 3 resends per 10 minutes (BR-AUTH-03) — to separate abuse from user error or delivery failure.
5. Admin opens the target profile (`GET /admin/users/{id}`, API-ADM-002) for active-session count and `recentActions` so legitimate owner activity is not mistaken for attacker activity.
6. Admin records the conclusion (abuse confirmed / benign / provider fault) with correlation IDs; any enforcement is executed through the existing reason-bearing audited endpoints — this UC performs no writes.

## Alternative Scenarios
- **A1 — Benign lockout:** attempts are the legitimate owner mistyping → cluster marked benign, no enforcement, monitoring continues.
- **A2 — Provider fault:** OTP delivery failures line up with integrations dashboard #8 → treated as a provider incident (BR-NTF-03 failover), not an attack.
- **A3 — Target is a staff account:** the actor holds ADMIN/MODERATOR/SUPER_ADMIN roles → finding escalates to Super Admin before any enforcement (rbac.md §3).

## Exception Scenarios
- **E1 — Audit range unavailable:** log store or cursor stream unreachable → investigation is paused and flagged incomplete; no enforcement runs on partial evidence (FR-020).
- **E2 — Target already suspended:** subsequent enforcement would return `STATE_CONFLICT` → investigation continues read-only against historical entries.
- **E3 — Alert storm:** 429 flood outruns manual triage → severity routing pages on-call (P1 page ≤1 min) and the investigation resumes from the alert's trace deep-link.

## Postconditions
- A documented finding exists for the cluster (abuse / benign / provider) with correlation IDs; no account, session, or wallet state was changed by this UC.
- Audit evidence is read-only and hash-chained; nothing in it was edited or deleted.

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04), platform-scope audit read; Moderator is explicitly denied audit-log access (rbac.md §4); read-only investigation.
- **Data involved:** audit entries, lock events, OTP attempt counters, user profile projection, session count.
- **External dependencies:** Prometheus/Grafana observability stack and structured log store (INT-REQ-007, NFR-014); notification pipeline for lockout notices (BR-NTF-02).

## Acceptance Criteria
- **AC-UC256-01:** Given a lockout cluster on the security dashboard, when the Admin filters the audit log for that actor, then every lock event is returned with timestamp, action, and `ipHash` (BR-AUTH-04).
- **AC-UC256-02:** Given OTP-abuse signals, when the Admin reviews the attempt history, then the 3-attempt cap and 60 s resend cooldown limits are evidenced per session (BR-AUTH-03).
- **AC-UC256-03:** Given the investigation completes, when the finding is recorded, then no account, session, or wallet state was mutated by this use case.
- **AC-UC256-04:** Given a Moderator account calls the audit endpoint, when the request is made, then access is denied (rbac.md §4).
