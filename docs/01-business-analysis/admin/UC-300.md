# UC-300 — Review the Weekly Retention Purge Report

## Header Info
- **Use Case ID:** UC-300
- **Title:** Review the Weekly Retention Purge Report
- **Actor:** Admin (ACT-04)
- **Trigger:** The weekly retention report lands (`16-data/core/retention-and-archival.md` §6 step 8) and must be reviewed before the next purge cycle
- **Priority:** P2
- **Goal:** Confirm every retention class behaved as scheduled — rows purged, guards skipped correctly, backlog within bounds.
- **Preconditions:** Daily purge job `system.retention.purge` has run for the week; the report lists rows per class purged, skipped-by-guard and backlog age; retention periods are configuration (not code).

## Main Scenario
1. Admin opens the weekly report for the completed period.
2. Admin reads per-class purge counts against the retention schedule — classes with zero activity are checked for a reason (no data vs blocked run).
3. Admin reviews `skipped-by-guard` counts: financial, audit and KYC classes below their floor must appear here, never in the deleted column.
4. Admin checks backlog age against the target and flags any class where the purge job retried into the DLQ.
5. Admin signs off (or raises an issue) — the review itself is the week's control evidence.

## Alternative Scenarios
- **A1 — Quiet week:** low volumes → small counts with an explainable pattern; sign-off records the low volume rather than an anomaly.
- **A2 — Guard skip spike:** many skips → Admin traces the misconfigured period candidate before it can cause a breach (config change, not code).
- **A3 — Backlog age breach:** age over target → Admin escalates to the job owner and checks DLQ depth for the purge queue (BR-PLT-02).

## Exception Scenarios
- **E1 — Report missing or late:** the review cannot complete → flagged as a control gap for the period; no assumed-clean status is recorded.
- **E2 — Purge job dead-lettered mid-week:** the report shows a gap for affected classes → Admin opens the DLQ path (UC-298) instead of signing off.
- **E3 — Deleted rows in a guarded class:** contradiction with the schedule → treated as an incident (UC-301), not a reporting error to wave through.

## Postconditions
- Success: the week's purge behaviour is reviewed and recorded — either sign-off or a raised issue; no data was changed by the review.
- Failure: no sign-off exists and nothing was silently assumed; underlying purge results are untouched.

## Business Rules Applied
- BR-PLT-01, BR-PLT-02 (the scheduled purge job the report measures)

## Related Requirements
- FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) report read; System produces the report; no role edits report figures.
- **Data involved:** purge run evidence (per-class counts, guard skips, backlog age), retention configuration (read).
- **External dependencies:** daily purge job on BullMQ (BR-PLT-01); alerting/metrics pipeline (INT-REQ-007).

## Acceptance Criteria
- **AC-UC300-01:** Given a completed week, when the report is opened, then per-class purged counts, guard skips and backlog age are present.
- **AC-UC300-02:** Given classes below their retention floor, when the report is read, then they appear as skipped, not deleted.
- **AC-UC300-03:** Given a purge job that exhausted retries, when the report is reviewed, then the gap is visible and DLQ follow-up is opened (BR-PLT-02).
- **AC-UC300-04:** Given the review completes, when it is recorded, then either sign-off or a raised issue exists for the period.
