# UC-265 — Prioritize the Overdue KYC Queue Before the 48-Hour SLA

## Header Info
- **Use Case ID:** UC-265
- **Title:** Prioritize the Overdue KYC Queue Before the 48-Hour SLA
- **Actor:** Admin (ACT-04) — KYC approval scope (rbac.md row 8)
- **Trigger:** The KYC queue contains submissions nearing or past the 48-hour decision deadline
- **Priority:** P1
- **Goal:** Work the queue oldest-deadline-first and decide every submission inside the 48-hour SLA so vendors are not blocked and no decision lands late.
- **Preconditions:** Admin authenticated with KYC decision rights (Moderator read-only); submissions exist in `PENDING`/`IN_REVIEW`; SLA clock starts at submission (BR-VND-03).

## Main Scenario
1. Admin opens the queue sorted by deadline (`GET /admin/kyc?sort=slaDueAt_asc`, API-ADM-005) — each row carries `slaDueAt` and an `overdue` flag (BR-VND-03).
2. Admin opens the top submission (`GET /admin/kyc/{id}`, API-ADM-006): documents with `scanStatus`, extracted fields, and the decision timeline.
3. Admin decides — approve (`POST /admin/kyc/{id}/approve`, API-ADM-007) or reject with mandatory reason (`POST /admin/kyc/{id}/reject`, API-ADM-008); both return `decidedAt`, `by`, and `auditId` (BR-PLT-06).
4. Approval lands before SLA auto-escalation; publishing and payouts unlock for the vendor (BR-VND-01, and payout eligibility per BR-ESC-06).
5. Admin re-reads the queue to confirm the entry left the pending set and the next `slaDueAt_asc` row is selected — the loop continues until the overdue set is clear.

## Alternative Scenarios
- **A1 — SLA already breached:** the decision is still recorded but flagged `KYC_DECISION_LATE`; the late reason is noted for the SLA report (API-ADM-007).
- **A2 — Reject:** reason is mandatory; the vendor may resubmit without limit (BR-VND-03) and the new submission re-enters the queue with a fresh SLA clock.
- **A3 — Moderator reviewing:** Moderator may read queue and documents but every decide call returns `FORBIDDEN` (rbac.md §4).

## Exception Scenarios
- **E1 — Document scan failed/quarantined:** decision is held until the scan resolves or the vendor resubmits the file (API-ADM-006 `scanStatus`).
- **E2 — Concurrent decision:** another Admin decided first → `STATE_CONFLICT`; the queue is re-read and the next item taken.
- **E3 — Missing reject reason:** `REASON_REQUIRED` → no state change; the reason is supplied and the call repeated (API-ADM-008).

## Postconditions
- Every decided submission is `APPROVED` or `REJECTED` with actor, timestamp, reason, and audit entry; pending items are deadline-ordered.
- Approvals inside SLA unlock publishing/payout gates (BR-VND-01, BR-ESC-06); no submission is silently dropped or auto-decided.

## Business Rules Applied
- BR-VND-01, BR-VND-03, BR-ESC-06, BR-PLT-06

## Related Requirements
- FR-007 (Vendor Onboarding & KYC), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) KYC decide; Moderator read-only; Super Admin supersedes (rbac.md rows 8, 3).
- **Data involved:** KYC submissions, documents (RESTRICTED class, named reviewers), extracted fields, decision timeline, audit entries.
- **External dependencies:** object storage + malware-scan pipeline for documents (SEC-REQ-011); SLA escalation job feeding `KYC_DECISION_LATE` (admin.md §2).

## Acceptance Criteria
- **AC-UC265-01:** Given pending submissions, when the Admin opens the queue, then rows arrive sorted by `slaDueAt` ascending with `overdue` flags (BR-VND-03).
- **AC-UC265-02:** Given an in-SLA decision, when approve/reject runs, then `decidedAt`, `by`, and `auditId` are returned (BR-PLT-06).
- **AC-UC265-03:** Given a rejection, when it is submitted without a reason, then `REASON_REQUIRED` blocks the change (API-ADM-008).
- **AC-UC265-04:** Given an approval, when it completes, then the vendor's publishing gate opens (BR-VND-01).
