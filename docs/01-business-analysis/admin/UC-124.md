# UC-124 — Monitor the Platform Return Queue

## Header Info
- **Use Case ID:** UC-124
- **Title:** Monitor the Platform Return Queue
- **Actor:** Admin (ACT-04)
- **Trigger:** An admin reviews platform-wide return flow and SLA escalations
- **Priority:** P1
- **Goal:** See every return with its state and escalation flags so stalled cases are spotted before SLAs breach.
- **Preconditions:** Admin authenticated with platform-operations permission (ACT-04); returns exist or the queue is empty.

## Main Scenario
1. Admin opens Returns → Queue → client `GET /admin/returns` (API-RET-010) with `?page&pageSize&state&overdue&sort=decisionDueAt_asc`.
2. System returns offset rows: return summary plus `escalated` and `vendorDecisionOverdue` flags for cases auto-escalated after the 48-hour vendor decision window.
3. Each row's state follows the return state sequence `RETURN_REQUESTED → RETURN_APPROVED / RETURN_REJECTED → RETURN_RECEIVED → REFUNDED` (BR-RET-02).
4. Admin filters overdue/escalated rows and opens a case detail for inspection; monitoring itself changes no state — decisions are a separate action (UC-125 counterpart).

## Alternative Scenarios
- **A1 — SLA-first view:** Admin keeps `sort=decisionDueAt_asc` to work the oldest due dates first.
- **A2 — State drill-down:** Admin filters a single state (e.g. `RETURN_REQUESTED`) to review pending vendor decisions.
- **A3 — Moderator read:** A Moderator reads a scoped projection of the same queue (read-only).

## Exception Scenarios
- **E1 — Permission denied:** A caller outside admin/moderator read scope → 403 `FORBIDDEN`; no rows returned.
- **E2 — Validation failure:** Unknown `state` value or non-numeric paging → 400 `VALIDATION_ERROR`; no rows returned.
- **E3 — Concurrent transition:** A vendor decides (approve/reject) while the queue is open → the row is stale; reload shows the new state per BR-RET-02 and cleared escalation flag.

## Postconditions
- Queue reviewed read-only; no return state changed by monitoring (BR-RET-02 sequence intact).
- Escalated and overdue cases are visible for follow-up action.

## Business Rules Applied
- BR-RET-02

## Related Requirements
- FR-016 (Returns & Refunds), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin operations scope; Moderator read-only on the queue; state transitions require the admin decision action.
- **Data involved:** Returns (state, decision due date, escalation flags), no audit entries from reads.
- **External dependencies:** Vendor return decisions and the 48-hour SLA escalation feed that populates the queue.

## Acceptance Criteria
- **AC-UC124-01:** Given returns in different states, when the queue is read, then each row shows its BR-RET-02 state plus escalation/overdue flags (API-RET-010).
- **AC-UC124-02:** Given a vendor decision made 48 hours late, when the queue is read, then the row carries `escalated`/`vendorDecisionOverdue`.
- **AC-UC124-03:** Given `sort=decisionDueAt_asc`, when the queue is read, then the nearest decision due date appears first.
- **AC-UC124-04:** Given a Moderator session, when the queue is read, then 200 is returned with a read-only scoped projection.
