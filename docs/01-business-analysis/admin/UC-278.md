# UC-278 — Approve the Vendor Payout Batch for Execution

## Header Info
- **Use Case ID:** UC-278
- **Title:** Approve the Vendor Payout Batch for Execution
- **Actor:** Admin (ACT-04) — payout batch approval is ADMIN/SUPER_ADMIN (rbac.md row 25)
- **Trigger:** A payout batch has accumulated and awaits human approval before the scheduled executor releases funds to vendors
- **Priority:** P0
- **Goal:** Approve only eligible, verified payouts so vendors are paid on the 3–7 business-day cycle with four-eyes accountability and a full audit trail.
- **Preconditions:** Payout requests exist in `REQUESTED`/`SCHEDULED` (API-WAL-011/012); batch executed 3–7 business days after release with a 1,000 YER floor (BR-ESC-05); eligibility = KYC `APPROVED` and non-suspended store (BR-ESC-06); approver differs from initiator (rbac.md §11).

## Main Scenario
1. Admin opens the payout batch view → requests with amount, masked destination, status, and rollover flags (API-WAL-012, payout threshold 1,000 YER).
2. Admin screens each request: KYC = `APPROVED` and store not suspended (BR-ESC-06), payable balance sufficient, no frozen escrow on the underlying sub-orders (BR-ORD-05, BR-ESC-02).
3. Admin screens the batch math: amounts ≥ 1,000 YER, sub-threshold requests marked `ROLLED_OVER` rather than paid (BR-ESC-05).
4. Admin approves the batch as the second pair of eyes (initiator ≠ approver, rbac.md §11) → approval returns an `auditId` (BR-PLT-06) and marks the batch for scheduled execution.
5. The SYSTEM executor runs the batch on schedule (rbac.md row 25); Admin verifies execution results against the approved list and ledger references.

## Alternative Scenarios
- **A1 — Super Admin approves instead:** equally valid (row 25) — the four-eyes rule still requires a different identity from the initiator.
- **A2 — Sub-threshold or ineligible entries:** held back (`ROLLED_OVER`, `KYC_NOT_APPROVED`, `STORE_SUSPENDED`) while the clean remainder of the batch proceeds (BR-ESC-05, BR-ESC-06).
- **A3 — Batch on hold due to dispute:** affected sub-orders keep escrow frozen (BR-ORD-05) → their payouts are excluded until resolution.

## Exception Scenarios
- **E1 — Insufficient payable balance:** `PAYOUT_NOT_ELIGIBLE`/`INSUFFICIENT_FUNDS` → the request stays pending; no partial approval is faked (API-WAL-011).
- **E2 — Same identity initiated and approved:** the four-eyes guardrail refuses → a second approver is required before execution (rbac.md §11).
- **E3 — Execution failure mid-batch:** failed transfers are retried per the idempotent money rules (BR-PAY-08) and surfaced by reconciliation (BR-ESC-08); no double payment occurs.

## Postconditions
- The approved batch is scheduled with exactly one audit entry naming the approver (BR-PLT-06); ineligible entries were excluded with reasons.
- Execution pays each vendor once, to a masked destination, with ledger references; nothing pays below the 1,000 YER floor (BR-ESC-05).

## Business Rules Applied
- BR-ESC-05, BR-ESC-06, BR-ORD-05, BR-PAY-08, BR-ESC-08, BR-PLT-06

## Related Requirements
- FR-014 (Escrow, Commission & Vendor Payouts), FR-020 (Platform Administration, Settings & Audit)

## Permissions / Data / External Dependencies
- **Permissions:** Admin/Super Admin payout approval (rbac.md row 25); Moderator explicitly denied (§4); SYSTEM executes the approved batch only.
- **Data involved:** payout requests, payable balances, store/KYC status, escrow holds, destinations (masked), audit entries.
- **External dependencies:** payout executor job (BR-ESC-05 schedule); bank/wallet transfer rails; reconciliation (BR-ESC-08) post-execution.

## Acceptance Criteria
- **AC-UC278-01:** Given a batch with eligible requests, when the Admin approves it with a distinct approver identity, then an `auditId` is returned and the batch is scheduled (BR-PLT-06, rbac.md §11).
- **AC-UC278-02:** Given a request below 1,000 YER, when the batch is built, then it rolls over instead of paying (BR-ESC-05).
- **AC-UC278-03:** Given a store that is suspended or KYC-invalid, when screening runs, then its payout is excluded (BR-ESC-06).
- **AC-UC278-04:** Given execution runs, when a transfer fails and is retried, then the vendor is never paid twice (BR-PAY-08).
