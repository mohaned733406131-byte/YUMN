# UC-261 — Sample-Verify Completed Data-Deletion Requests

## Header Info
- **Use Case ID:** UC-261
- **Title:** Sample-Verify Completed Data-Deletion Requests
- **Actor:** Admin (ACT-04) — Trust & Safety / Compliance oversight (rbac.md §11)
- **Trigger:** The monthly sampling-QA window opens for completed account-deletion requests
- **Priority:** P1
- **Goal:** Re-check a random sample of completed deletions against the zero-hit rule so residual PII is proven absent — or raised as a HIGH incident the moment it is found.
- **Preconditions:** Requests in the sample are `COMPLETED` (execution finished within the published SLA, data-deletion-and-privacy.md §2); verification queries available (§6); financial/audit rows are expected to survive as records, not as PII (§3 matrix).

## Main Scenario
1. Admin draws the standing sample: 5 random completed deletion requests for the month (data-deletion-and-privacy.md §6, sampling QA).
2. For each sampled request, Admin runs the §6 verification queries over the subject's scoped PII columns — profile, addresses, session/login rows.
3. System reports per-query hit counts; the rule is zero-hit: any surviving value is a hit (data-deletion-and-privacy.md §6).
4. Zero-hit requests are marked verified with the query set and timestamp recorded against the request's evidence entry (DATA-REQ-003 evidence trail).
5. Any hit escalates immediately: a HIGH-severity incident is logged in the security findings and validation records — no silent fix, no data edit by hand (data-deletion-and-privacy.md §6).
6. The monthly sampling result (verified count, exceptions, incident references) is published to the compliance record.

## Alternative Scenarios
- **A1 — All five verify clean:** sample passes; the attestation cites the request IDs and query set used.
- **A2 — Vendor/store closure in scope:** deletion with open financial exposure runs two-person control (requester + Admin oversight) before inclusion in the sample (data-deletion-and-privacy.md §2).
- **A3 — Residual backup window:** rows still present in the rolling backup window are assessed against the documented retention window, not counted as a PII hit (data-deletion-and-privacy.md §6 / retention doc).

## Exception Scenarios
- **E1 — A verification query returns a hit:** HIGH incident raised immediately in security findings; further purges on that path are held pending investigation (zero-hit rule).
- **E2 — Verification tooling unavailable:** the sample is deferred and explicitly not marked passed — no attestation on partial evidence (FR-020).
- **E3 — Request not yet complete:** outside the sample frame; only completed requests are eligible (SLA still running).

## Postconditions
- A sampling record exists for the month: 5 sampled requests, per-request results, and any incident references.
- No deletion record, audit row, or financial record was mutated by this use case; hits are escalated, never patched in place.

## Business Rules Applied

## Related Requirements

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) compliance read + verification-query execution; Super Admin escalation target; read-only against user data.
- **Data involved:** deletion request records, PII verification queries (profile, addresses, sessions), evidence entries, security findings.
- **External dependencies:** deletion/anonymization jobs and their §6 queries (16-data); security-findings register (09-security).

## Acceptance Criteria
- **AC-UC261-01:** Given the monthly window, when sampling runs, then exactly 5 random completed requests are drawn (data-deletion-and-privacy.md §6).
- **AC-UC261-02:** Given a clean request, when verification queries run, then every scoped PII query returns zero rows.
- **AC-UC261-03:** Given any surviving PII value, when detected, then a HIGH-severity incident is logged in security findings (zero-hit rule).
- **AC-UC261-04:** Given verification tooling is down, when the window closes, then the sample is deferred, never recorded as passed (FR-020).
