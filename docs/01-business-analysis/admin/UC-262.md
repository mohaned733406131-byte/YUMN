# UC-262 — Deactivate a Category Node from the Storefront

## Header Info
- **Use Case ID:** UC-262
- **Title:** Deactivate a Category Node from the Storefront
- **Actor:** Admin (ACT-04) — taxonomy edits are Admin-scoped (admin.md §1.4)
- **Trigger:** A category is seasonal, empty, mis-scoped, or otherwise should stop appearing in public browse while keeping its history and product links
- **Priority:** P2
- **Goal:** Take a category node out of the public storefront reversibly, without breaking the 5-level tree, slugs, or product references.
- **Preconditions:** Admin authenticated with taxonomy write; target node exists in the platform category tree (`GET /admin/categories`, API-ADM-014, `?includeHidden`); depth and slug constraints known (BR-CAT-03).

## Main Scenario
1. Admin opens the full category tree including hidden nodes (API-ADM-014) and selects the node, noting `level`, `path`, and `productCount`.
2. Admin issues the update (conceptual `PUT /admin/categories/{id}` with `isActive: false`, API-ADM-016).
3. System validates the change against the tree rules — depth ≤ 5 levels and slug uniqueness per level hold unchanged (BR-CAT-03) — and applies it.
4. System returns the updated node and writes an append-only audit entry for the taxonomy edit (BR-PLT-06).
5. The node stops appearing in public category browse and merchandising surfaces; admin views still list it with `includeHidden` for later reversal.

## Alternative Scenarios
- **A1 — Node with products or children:** deactivation remains allowed (it is reversible and touches no product rows) — unlike deletion, which refuses while children or products exist (`STATE_CONFLICT`, API-ADM-017).
- **A2 — Reactivation:** the same endpoint with `isActive: true` restores the node; slugs and product references were never rewritten.
- **A3 — Rename instead of deactivate:** a re-slug creates redirects so old links keep resolving (API-ADM-016) — deactivation does not need this path.

## Exception Scenarios
- **E1 — Concurrent move/rename:** another operator changed the tree mid-request → stale node version returns `STATE_CONFLICT`; history is unchanged and the Admin re-reads the tree.
- **E2 — Caller without taxonomy write:** `403 FORBIDDEN` → nothing changes (Moderator is read-only here, admin.md §1.4).
- **E3 — Unknown node:** `404 NOT_FOUND` → no partial update, no audit entry.

## Postconditions
- The category node is inactive: absent from public browse, retained in admin views with history and product links intact.
- Tree depth and slug constraints still hold; one audit entry records the taxonomy change.

## Business Rules Applied
- BR-CAT-03, BR-PLT-06

## Related Requirements
- FR-004 (Product Catalog Management)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) taxonomy write; Moderator read-only (API-ADM-014); no vendor input — this is a platform taxonomy action.
- **Data involved:** category nodes (name, slug, level, path, sortOrder, `isActive`), product counts, audit entries.
- **External dependencies:** category browse and search index surfaces (FR-004/FR-009 render the tree); audit log (API-ADM-024).

## Acceptance Criteria
- **AC-UC262-01:** Given an active category node, when the Admin sets `isActive: false`, then the node no longer appears in public category browse (API-ADM-014/016).
- **AC-UC262-02:** Given the deactivation, when validation runs, then tree depth ≤ 5 and per-level slug uniqueness still hold (BR-CAT-03).
- **AC-UC262-03:** Given the change applies, when the response returns, then an audit entry exists for the taxonomy edit (BR-PLT-06).
- **AC-UC262-04:** Given a Moderator caller, when the update is attempted, then it is denied with `403 FORBIDDEN`.
