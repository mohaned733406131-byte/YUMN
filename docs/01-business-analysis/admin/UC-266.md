# UC-266 — Clear a KYC Blocker That Prevents Store Reactivation

## Header Info
- **Use Case ID:** UC-266
- **Title:** Clear a KYC Blocker That Prevents Store Reactivation
- **Actor:** Admin (ACT-04)
- **Trigger:** An attempt to re-activate a suspended store fails with `KYC_NOT_APPROVED` and the operator must clear the KYC blocker first
- **Priority:** P1
- **Goal:** Resolve the KYC state that blocks reactivation, then re-activate the store, so a suspended vendor returns to trading through the guarded path rather than around it.
- **Preconditions:** Store exists in `SUSPENDED` with a linked KYC record (API-ADM-010); publishing and payouts require KYC = `APPROVED` (BR-VND-01); Admin holds both KYC decide and store lifecycle rights (rbac.md rows 8, 5).

## Main Scenario
1. Admin attempts reactivation (`POST /admin/stores/{id}/activate`, API-ADM-013) → system refuses with `KYC_NOT_APPROVED`, listing the blocker (admin.md §1.3).
2. Admin inspects the store projection (`GET /admin/stores/{id}`, API-ADM-010) → `kycStatus` shows the blocking value (e.g. `PENDING`, `IN_REVIEW`, `REJECTED`).
3. Admin opens the linked submission from the KYC queue (API-ADM-005/006) and decides it — approve (`API-ADM-007`) or reject with reason (`API-ADM-008`) — inside the 48-hour SLA (BR-VND-03).
4. With KYC = `APPROVED`, Admin repeats activation with a reason → store `ACTIVE`, `auditId` returned (API-ADM-013).
5. Admin verifies the cascade cleared: product writes accept again, storefront reads resolve, and payout eligibility is restored (BR-VND-01, BR-ESC-06).

## Alternative Scenarios
- **A1 — KYC already approved:** the blocker was a stale projection or another scope flag → activation is retried and succeeds with reason (API-ADM-013).
- **A2 — KYC rejected:** rejection stands; the vendor resubmits (BR-VND-03) and activation waits for the new decision — no bypass exists.
- **A3 — Account-level suspension too:** the user carries `ACCOUNT`/`STORE`/`WALLET` scopes (API-ADM-004) → the store scope is cleared per scope, wallet freeze stays a separate decision (BR-PAY-09).

## Exception Scenarios
- **E1 — Store not suspended:** activation returns `STATE_CONFLICT`; nothing changes (API-ADM-013).
- **E2 — Decision lands after escalation:** the approve call returns `KYC_DECISION_LATE` → decision still recorded, SLA exception logged (API-ADM-007).
- **E3 — Moderator attempts either call:** `FORBIDDEN` — neither KYC decide nor store lifecycle is in Moderator scope (rbac.md §4).

## Postconditions
- KYC status is terminal and approved where activation proceeded; store is `ACTIVE` with an audit entry, or remains suspended with the recorded blocker.
- No bypass path exists: activation never succeeds while KYC ≠ `APPROVED` (BR-VND-01).

## Business Rules Applied
- BR-VND-01, BR-VND-03, BR-ESC-06, BR-PAY-09, BR-PLT-06

## Related Requirements
- FR-007 (Vendor Onboarding & KYC), FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) — KYC decide (row 8) and store lifecycle (row 5); Moderator denied both.
- **Data involved:** store status, KYC submission and decision fields, document vault references, audit entries.
- **External dependencies:** KYC queue and document scanner (SEC-REQ-011); storefront/product surfaces that reappear after activation.

## Acceptance Criteria
- **AC-UC266-01:** Given a store with KYC ≠ `APPROVED`, when activation is attempted, then `KYC_NOT_APPROVED` is returned and the store stays suspended.
- **AC-UC266-02:** Given KYC approved, when activation is repeated with a reason, then the store becomes `ACTIVE` with an `auditId` (API-ADM-013).
- **AC-UC266-03:** Given a rejected KYC, when the vendor resubmits, then activation stays blocked until the new submission is approved (BR-VND-01, BR-VND-03).
- **AC-UC266-04:** Given the store is active again, when payout eligibility is checked, then it requires KYC = `APPROVED` and a non-suspended store (BR-ESC-06).
