# UC-275 — Cross-Check Pending Top-Ups Against the Bank Statement

## Header Info
- **Use Case ID:** UC-275
- **Title:** Cross-Check Pending Top-Ups Against the Bank Statement
- **Actor:** Admin (ACT-04) — Finance & Payments bundle (rbac.md §11, ORG-01)
- **Trigger:** Bank-transfer requests are pending verification and the operator must confirm the money actually arrived before crediting anyone's wallet
- **Priority:** P1
- **Goal:** Match each pending request's amount and reference against the platform's bank statement so only real, unique transfers are credited (BR-PAY-04).
- **Preconditions:** Requests are `PENDING_VERIFICATION` and sorted by age (API-ADM-030); Admin holds finance verification rights (row 14, Moderator denied); bank-portal credentials are ops-held and human-used (S-10, secrets-management.md §5).

## Main Scenario
1. Admin opens the verification queue (`GET /admin/topups?status=PENDING_VERIFICATION`, API-ADM-030) — oldest first with amount, method, and proof file id.
2. Admin opens the platform bank account statement via the ops-held portal credentials (statement verification path, bank-transfer-topup.md §6 — S-10, never pasted into tickets or chat).
3. Admin matches per request: transferred amount equals `amountYER`, and the normalized reference matches one statement row not already used (§2 evidence fields, §6 checks).
4. Match confirmed → Admin approves (`POST /admin/topups/{id}/verify`, API-ADM-031): one transaction posts balanced ledger rows (BR-PAY-06), sets `CREDITED`, guards idempotently (BR-PAY-08), and writes an audit entry (BR-PLT-06).
5. No match / ambiguity → Admin declines with reason (`API-ADM-032`): zero ledger effect, customer notified with the localized reason (BR-NTF-04).

## Alternative Scenarios
- **A1 — Evidence unclear before the statement check:** the statement is the tie-breaker — ops cross-checks the platform account and decides on that basis (bank-transfer-topup.md §6).
- **A2 — Suspected fraud:** hold plus support/dispute path instead of approve/decline; possible wallet freeze for the account (BR-PAY-09).
- **A3 — Statement unavailable (portal outage):** requests simply remain `PENDING` — never auto-approved, no timeout converts pending into credited (BR-PAY-04).

## Exception Scenarios
- **E1 — Duplicate reference:** a second request reusing a reference is rejected at uniqueness; the first claim stands (§4).
- **E2 — Receipt fails scanning:** the request may still be submitted without a receipt; the statement remains the source of truth (upload rules, SEC-REQ-011).
- **E3 — Credentials incident:** portal credential suspected exposed → rotate per the incident runbook (UC-257) before continuing decisions; values never leave the ops channel.

## Postconditions
- Each checked request is either `CREDITED` with balanced ledger rows and an audit entry, or `DECLINED` with reason — never both, never half (BR-PAY-06, BR-PLT-06).
- Unmatched requests stay pending until evidence resolves them; the wallet balance changed only for verified transfers (BR-PAY-04).

## Business Rules Applied
- BR-PAY-04, BR-PAY-06, BR-PAY-08, BR-PAY-09, BR-NTF-04, BR-PLT-06

## Related Requirements
- FR-013 (Wallet & Payment Processing), FR-014 (Escrow, Commission & Vendor Payouts)

## Permissions / Data / External Dependencies
- **Permissions:** Admin/Super Admin finance verification (rbac.md row 14); Moderator denied (§4); four-eyes applies on large amounts (UC-274).
- **Data involved:** top-up requests, receipts, bank statement rows, ledger entries, wallet balances, audit entries.
- **External dependencies:** bank web portal (S-10 credentials, INT-REQ-002 manual rail); upload scan pipeline (SEC-REQ-011).

## Acceptance Criteria
- **AC-UC275-01:** Given a pending request whose amount and reference match the statement, when verified, then the wallet is credited with balanced ledger rows (BR-PAY-04, BR-PAY-06).
- **AC-UC275-02:** Given a request with no statement match, when decided, then it is declined with reason and the ledger is untouched.
- **AC-UC275-03:** Given the statement is unreachable, when the queue ages, then requests stay `PENDING` — none becomes `CREDITED` (BR-PAY-04).
- **AC-UC275-04:** Given a Moderator calls verify, when the request is made, then it is denied (rbac.md row 14).
