# UC-277 — Record the Disposition of a Reconciliation Mismatch

## Header Info
- **Use Case ID:** UC-277
- **Title:** Record the Disposition of a Reconciliation Mismatch
- **Actor:** Admin (ACT-04) — Finance & Payments bundle (rbac.md §11, ORG-01)
- **Trigger:** The daily reconciliation reports a `MISMATCH` row between ledger totals and a provider/bank statement and someone must own its disposition
- **Priority:** P0
- **Goal:** Investigate each mismatch and record who resolved it and how, so `unresolvedYER` trends to zero without ever touching an append-only ledger row.
- **Preconditions:** Reconciliation ran (BR-ESC-08, BR-FIN-03: ledger vs wallet vs escrow vs payable vs provider statements); `GET /admin/reconciliation` available to Admin (API-ANL-009); ledger is append-only (BR-PAY-06).

## Main Scenario
1. Admin opens the reconciliation view filtered to mismatches (`GET /admin/reconciliation?status=MISMATCH`, API-ANL-009) → per-source rows with `ledgerTotal`, `providerTotal`, `deltaYER`, and totals of mismatches/unresolved amounts.
2. Admin investigates the delta's source per row source (`MFLOOS`/`ONECASH`/`BANK`/`INTERNAL`): late callback, statement lag, missed posting, or genuine imbalance.
3. Admin records the disposition on the row — `resolvedBy` plus a `note` — so the mismatch moves from unresolved to explained (API-ANL-009 write-back, audited per BR-PLT-06).
4. If the delta is a real imbalance, the RISK-001 contingency applies: freeze payouts and top-up crediting, page on-call, and reconstruct from append-only postings — never by editing rows (BR-PAY-06).
5. Admin re-reads `totals.unresolvedYER` to confirm the disposition landed and hands systemic fixes to the owning block with the row as evidence.

## Alternative Scenarios
- **A1 — Row already `MATCHED`:** no disposition needed; the view is used as evidence that the source reconciles (BR-ESC-08).
- **A2 — Provider lag explains it:** disposition = explained-by-lag with the confirming next cycle cited; the row closes when the following run matches.
- **A3 — Imbalance confirmed:** escalation to the freeze path (UC-279) with this disposition as the triggering record.

## Exception Scenarios
- **E1 — Imbalance persists across runs:** repeated mismatch alerts finance (BR-ESC-08) and the contingency escalation escalates severity (RISK-001 trigger).
- **E2 — Attempt to "correct" the ledger directly:** impossible — ledger rows are append-only; only compensating entries through the Finance-approved procedure exist (BR-PAY-06).
- **E3 — Moderator or unauthorized caller:** `403 FORBIDDEN` — reconciliation is Admin/finance scope (API-ANL-009, rbac.md §4).

## Postconditions
- Every mismatch row carries a disposition (`resolvedBy`, `note`) or an active escalation; `unresolvedYER` reflects reality (BR-ESC-08, BR-FIN-03).
- No ledger, wallet, escrow, or payable row was modified; the disposition itself is audited (BR-PLT-06).

## Business Rules Applied
- BR-ESC-08, BR-FIN-03, BR-PAY-06, BR-PAY-09, BR-PLT-06

## Related Requirements
- FR-013 (Wallet & Payment Processing), FR-014 (Escrow, Commission & Vendor Payouts)

## Permissions / Data / External Dependencies
- **Permissions:** Admin (ACT-04) finance/reconciliation read + disposition write; Super Admin supersedes; Moderator denied (rbac.md §4); no ledger write for anyone.
- **Data involved:** reconciliation rows (ledger/provider totals, deltas, status), disposition notes, audit entries, ledger/escrow/payable aggregates.
- **External dependencies:** daily reconciliation jobs (BR-ESC-08/BR-FIN-03); provider statement feeds (INT-REQ-001, INT-REQ-002); wallet freeze path (BR-PAY-09).

## Acceptance Criteria
- **AC-UC277-01:** Given a `MISMATCH` row, when the Admin records a disposition, then `resolvedBy` and `note` are stored and the row leaves the unresolved set (API-ANL-009).
- **AC-UC277-02:** Given a confirmed imbalance, when the contingency runs, then payouts and top-up crediting are frozen before any further money movement (BR-PAY-09).
- **AC-UC277-03:** Given the disposition is recorded, when the ledger is inspected, then no row was updated or deleted (BR-PAY-06).
- **AC-UC277-04:** Given any disposition write, when it completes, then an audit entry exists with actor and before/after status (BR-PLT-06).
