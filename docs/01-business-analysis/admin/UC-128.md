# UC-128 — Monitor Frozen Wallets

## Header Info
- **Use Case ID:** UC-128
- **Title:** Monitor Frozen Wallets
- **Actor:** Admin (ACT-04)
- **Trigger:** An admin audits wallets frozen for legal/security reasons or reviews freeze activity over a period
- **Priority:** P2
- **Goal:** Keep oversight of every frozen wallet and confirm freeze semantics hold without changing any balance.
- **Preconditions:** Admin authenticated with finance-read permission (ACT-04); at least the possibility of frozen wallets in the period; this use case is monitoring only — freeze/unfreeze actions live in their own admin flows (UC-098, UC-099).

## Main Scenario
1. Admin opens the route `/[locale]/admin/finance/wallet-freezes` (routing.md §4) → list of frozen wallets with reason, freeze date (sourced from the audit trail), and user reference.
2. Admin filters by reason, date range, or user role to scope the review.
3. Admin opens a wallet entry → balance, freeze status, recent activity projection, and linked store when the owner is a vendor.
4. System enforces freeze semantics throughout: a frozen wallet cannot pay or top up, but it still receives refunds (BR-PAY-09).
5. Admin confirms the freeze reason still stands; if it no longer applies, the case is flagged for the dedicated unfreeze action rather than changed here.
6. Admin records findings for follow-up — the monitor path itself performs no state or balance change.

## Alternative Scenarios
- **A1 — Refund lands on a frozen wallet:** credit is accepted while frozen (BR-PAY-09) → visible as an incoming credit on the frozen entry.
- **A2 — Frozen vendor wallet:** owner has a store → admin cross-checks store exposure before deciding on follow-up.
- **A3 — Unfreeze justified:** review concludes the reason lapsed → admin routes to the unfreeze action (UC-099) with a reason.
- **A4 — Empty list:** no frozen wallets in the period → empty state with filters intact.

## Exception Scenarios
- **E1 — Permission denied:** caller without finance scope → `403 FORBIDDEN`.
- **E2 — Empty queue:** zero frozen wallets → empty state, no error.
- **E3 — Concurrent unfreeze:** another admin lifted the freeze while this one reviews → stale row; admin refreshes to see `ACTIVE` status.
- **E4 — SLA breach / long-held freeze:** freeze held far beyond its review window → flagged for re-evaluation so it is never silently indefinite.

## Postconditions
- Frozen-wallet population is reviewed; freeze semantics confirmed (BR-PAY-09).
- No balance, ledger, or status change originates from monitoring.

## Business Rules Applied
- BR-PAY-09

## Related Requirements
- FR-013 (Wallet & Payment Processing)

## Permissions / Data / External Dependencies
- **Permissions:** Admin finance-read scope; freeze/unfreeze writes belong to dedicated admin actions, not this UC.
- **Data involved:** Wallet statuses, freeze reasons/dates, balances (read), audit-trail freeze entries.
- **External dependencies:** Audit log for freeze provenance; refund engine (credits still land).

## Acceptance Criteria
- **AC-UC128-01:** Given a frozen wallet, when the route is opened, then it appears with its reason and freeze date.
- **AC-UC128-02:** Given a frozen wallet, when its owner attempts to pay or top up, then the action is rejected (BR-PAY-09).
- **AC-UC128-03:** Given a refund owed to a frozen wallet, when the refund executes, then the credit still lands (BR-PAY-09).
- **AC-UC128-04:** Given the monitor view, when Admin reviews it, then no balance or ledger row is created or modified.
