# UC-115 — Disable a Platform Coupon

## Header Info
- **Use Case ID:** UC-115
- **Title:** Disable a Platform Coupon
- **Actor:** Admin (ACT-04)
- **Trigger:** A campaign must stop early (abuse, budget, or mistake)
- **Priority:** P1
- **Goal:** Stop an active coupon from being validated at cart/checkout immediately, with a mandatory reason.
- **Preconditions:** Admin authenticated with content-write permission (ACT-04); the target coupon exists and is ACTIVE.

## Main Scenario
1. Admin locates the coupon in the list (UC-113) and chooses "Disable", entering a reason.
2. Client sends `POST /admin/coupons/{id}/disable` (API-CNT-017) with `{ reason }`.
3. System enforces the reason (`REASON_REQUIRED`) and rejects already disabled/expired coupons (`STATE_CONFLICT`) → `200 { status: "DISABLED", disabledAt }`.
4. In-flight carts receive `COUPON_INVALID` on their next validation, and expired/fully-used coupons are rejected before order creation (BR-PRM-04).
5. Admin oversight scope covers vendor store coupons as well: platform coupons are admin-created, store coupons vendor-created, admin may list and disable both (BR-PRM-03).

## Alternative Scenarios
- **A1 — Disable a store coupon:** Admin disables a vendor-created coupon (`scope=STORE`) under the same list/disable right (BR-PRM-03).
- **A2 — Let it expire:** Admin takes no action → the window closes and the coupon moves to EXPIRED, rejected at validation (BR-PRM-04).
- **A3 — Disable and reissue:** Admin disables the flawed coupon and creates a corrected one (UC-114).

## Exception Scenarios
- **E1 — Validation failure (missing reason):** No reason supplied → `REASON_REQUIRED`; status unchanged.
- **E2 — Already inactive:** Coupon already DISABLED or EXPIRED → `STATE_CONFLICT`; no second transition.
- **E3 — Permission denied:** Moderator or non-admin attempts disable → 403 `FORBIDDEN`; coupon stays ACTIVE.
- **E4 — Concurrent disable:** Two admins disable the same coupon → one `200`, the other `STATE_CONFLICT`; a single disablement stands.

## Postconditions
- Coupon status is DISABLED with `disabledAt`; validation rejects it from the next check onward (BR-PRM-04).
- No refund or ledger change originates from a disablement.

## Business Rules Applied
- BR-PRM-03, BR-PRM-04

## Related Requirements
- FR-019 (Content & Promotions (CMS + Coupons))

## Permissions / Data / External Dependencies
- **Permissions:** Admin content-write scope; Moderator cannot disable coupons.
- **Data involved:** Coupons (status, disabledAt, reason), in-flight carts' validation results.
- **External dependencies:** Cart/checkout coupon validation (`POST /coupons/validate`) rejects the disabled code at next use.

## Acceptance Criteria
- **AC-UC115-01:** Given an ACTIVE coupon, when disable is called with a reason, then `200` returns `status: "DISABLED"` and `disabledAt` (API-CNT-017).
- **AC-UC115-02:** Given a disabled coupon, when a cart validates it next, then it is rejected as invalid before order creation (BR-PRM-04).
- **AC-UC115-03:** Given no reason, when disable is attempted, then `REASON_REQUIRED` is returned and the coupon stays ACTIVE.
- **AC-UC115-04:** Given a vendor store coupon, when the admin disables it, then it succeeds under the admin list/disable right (BR-PRM-03).
