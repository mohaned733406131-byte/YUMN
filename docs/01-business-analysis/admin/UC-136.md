# UC-136 — Handle the Three-Failed-Attempt Delivery Escalation

## Header Info
- **Use Case ID:** UC-136
- **Title:** Handle the Three-Failed-Attempt Delivery Escalation
- **Actor:** Admin (ACT-04)
- **Trigger:** A third failed delivery-code attempt escalates the order to admin review with the full timeline (recorded at UC-029 step5) and an auto-created support ticket (UC-065)
- **Priority:** P1
- **Goal:** Resolve the failed-delivery escalation with a recorded outcome so the delivery reaches a terminal state.
- **Preconditions:** Admin authenticated with order-override scope (ACT-04); escalation exists with the full attempt timeline; linked auto-ticket may exist in the support queue.

## Main Scenario
1. After the 3rd failed attempt the system escalates the order to admin review with the full timeline (BR-SHP-06) alongside the auto-created ticket (UC-065).
2. Admin opens the queue → order flagged `DELIVERY_ESCALATION` on `GET /admin/orders` (API-ORD-013) and/or the `AUTO` ticket on `GET /admin/tickets`.
3. Admin reviews the timeline: attempts, timestamps, courier identity, and code evidence recorded without GPS.
4. Admin decides and coordinates: redelivery, customer contact, or reassignment — capturing the decision on the case.
5. Any order state correction uses the guarded admin transition with a mandatory reason → append-only audit entry (BR-PLT-06).
6. Admin resolves the linked ticket with a resolution note; the escalation clears only with a recorded outcome (BR-SHP-06 requires admin review with the full timeline).

## Alternative Scenarios
- **A1 — Redelivery succeeds:** next attempt confirms → ticket resolved, escalation cleared, order continues to completion.
- **A2 — Customer unreachable:** contact fails → cancellation and refund path runs; outcome and notification recorded.
- **A3 — Courier problem:** assignment returned to the pool → reassign delivery, escalation stays open until delivery resolves.
- **A4 — Relation notes:** UC-029 step5 records the third attempt; UC-065 auto-created the support ticket with the timeline attached.

## Exception Scenarios
- **E1 — Already-resolved ticket:** linked ticket resolved by another admin → `TICKET_STATE_CONFLICT`; this admin reads the recorded resolution instead.
- **E2 — Permission denied:** Moderator attempts a state change → `403 FORBIDDEN`; Moderator advises only (UC-137).
- **E3 — Concurrent handling:** two admins work the same escalation → optimistic lock on the transition; one wins, the other refreshes.
- **E4 — SLA breach:** escalation stays open past expectations → it remains flagged and prioritized until a recorded decision lands (BR-SHP-06).

## Postconditions
- Escalation closed with a recorded decision; linked ticket `RESOLVED` with a resolution note.
- Audit row exists for any forced transition (BR-PLT-06); timeline history is appended, never edited.

## Business Rules Applied
- BR-SHP-06, BR-PLT-06

## Related Requirements
- FR-015 (Shipping & Delivery), FR-012 (Order Lifecycle Management)
- **Cross-reference:** UC-029 step5 (third attempt recorded) · UC-065 (auto-created ticket).

## Permissions / Data / External Dependencies
- **Permissions:** Admin order-override scope; Moderator read-only (UC-137); Super Admin supersedes (UC-037).
- **Data involved:** Orders/deliveries, attempt timelines, support tickets, audit log, notifications.
- **External dependencies:** Delivery engine (B08); support ticketing (B13); refund engine if cancelled (B07).

## Acceptance Criteria
- **AC-UC136-01:** Given a third failed delivery-code attempt, when it is recorded, then an escalation with full timeline and an auto ticket exist (BR-SHP-06).
- **AC-UC136-02:** Given an admin state correction, when executed, then a reason and `auditId` are recorded (BR-PLT-06).
- **AC-UC136-03:** Given a resolved escalation, when checked, then the linked ticket is `RESOLVED` with a resolution note.
- **AC-UC136-04:** Given the escalation, when handled, then the outcome is recorded — never silently dropped (BR-SHP-06).
