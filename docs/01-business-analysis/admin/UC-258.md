# UC-258 — Force Session Revalidation After a Signing-Key Rotation

## Header Info
- **Use Case ID:** UC-258
- **Title:** Force Session Revalidation After a Signing-Key Rotation
- **Actor:** Super Admin (ACT-05) — platform configuration authority (rbac.md §3)
- **Trigger:** The JWT signing key (S-01) has been rotated or retired (UC-257) and sessions minted under the old key must be revalidated
- **Priority:** P1
- **Goal:** Invalidate every session signed with the retired key so users re-authenticate under the new key, without exceeding the 5-device cap or leaving any orphan session.
- **Preconditions:** New signing key deployed and serving (health-gated, BR-PLT-07); session registry reachable; Super Admin authenticated (role change/config = Super Admin only, FR-002); revalidation scope decided (single key retirement vs full wipe).

## Main Scenario
1. Super Admin triggers session revalidation for the retired key → system marks all session families signed with that key as requiring re-login (assess step of secrets-management.md §7).
2. Each client presents its refresh token (conceptual `POST /auth/refresh`) → the family is rejected because its lineage was minted under the retired key → the client returns to login (BR-AUTH-05).
3. Users re-authenticate (UC-003) and receive a fresh access/refresh pair signed with the new key; single-use rotation continues from the first renewed token (BR-AUTH-05).
4. Re-issued sessions are re-checked against the device cap: at most 5 active device sessions per user, the oldest evicted beyond the limit (BR-AUTH-06).
5. A mandatory security notification informs affected users their sessions were reset (BR-NTF-02); the revalidation itself writes an append-only audit entry with actor and scope (BR-PLT-06).

## Alternative Scenarios
- **A1 — Key rotated but not retired:** the old key still verifies until natural expiry → no forced revalidation; sessions die by lifetime (C-08) and rotation.
- **A2 — Access token still valid:** a user mid-window keeps working for at most 15 minutes before the first refresh attempt forces re-login (C-08).
- **A3 — Compromise-driven wipe:** the key was leaked, not scheduled → all families revoked immediately rather than at refresh time; users are alerted (BR-AUTH-05, BR-NTF-02).

## Exception Scenarios
- **E1 — Session registry unreachable:** revalidation fails closed — no partial wipe, no pair is issued, and the attempt is retried once the registry returns (FR-001).
- **E2 — Device over the cap after re-login:** a user attempts a 6th device → oldest session evicted, never a 6th concurrent session (BR-AUTH-06).
- **E3 — Non–Super Admin caller:** role/config surface is Super Admin-only → `403 FORBIDDEN`; revalidation does not start (FR-002).

## Postconditions
- No session signed with the retired key remains usable; every active user is either re-authenticated under the new key or logged out.
- Device cap still holds (≤5 per user); revalidation is audited and users received a security notice.

## Business Rules Applied
- BR-AUTH-05, BR-AUTH-06, BR-NTF-02, BR-PLT-06

## Related Requirements
- FR-001 (Identity, Authentication & Session Management), FR-002 (Roles, Permissions & Access Control)

## Permissions / Data / External Dependencies
- **Permissions:** Super Admin (ACT-05) for the revalidation trigger; Admin holds read-only visibility of the audit entry; affected users only re-authenticate, never approve.
- **Data involved:** session registry entries, refresh-token families, JWT signing material (never logged), security notifications, audit entries.
- **External dependencies:** Redis session store; notification pipeline for the mandatory security notice (BR-NTF-02); health probes gating the restart (BR-PLT-07).

## Acceptance Criteria
- **AC-UC258-01:** Given a retired signing key, when any client presents a session minted under it, then the session cannot be renewed and the client must re-login (BR-AUTH-05).
- **AC-UC258-02:** Given users re-authenticate, when a user reaches 6 concurrent devices, then the oldest session is evicted (BR-AUTH-06).
- **AC-UC258-03:** Given revalidation runs, when it completes, then affected users hold a security notification and one audit entry exists (BR-NTF-02, BR-PLT-06).
- **AC-UC258-04:** Given an Admin (not Super Admin) calls the trigger, when the request is made, then it is denied (FR-002).
