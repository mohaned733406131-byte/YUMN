# UC-208 — Handle the 24-Hour Code Lockout After Third Failure

## Header Info
- **Use Case ID:** UC-208
- **Title:** Handle the 24-Hour Code Lockout After Third Failure
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** The courier's third wrong 6-digit code entry locks delivery-code confirmation for 24 hours
- **Priority:** P1
- **Goal:** Surface and handle the lockout so the courier sees why confirmation is blocked, cannot burn attempts during the lock, and can retry once it expires.
- **Preconditions:** Delivery `OUT_FOR_DELIVERY` with code issued; two failed code attempts already recorded (UC-030 step 2).

## Main Scenario
1. Courier submits a third wrong code (conceptual `POST /deliveries/{id}/code`) → system rejects it as attempt-limit exceeded.
2. System locks code confirmation for 24 hours and auto-creates a support ticket carrying the full delivery timeline (BR-SHP-03; ticket creation owned by UC-065).
3. Courier opens job detail → code status shows `lockedUntil`, attempts used and the linked ticket reference (conceptual `GET /deliveries/{id}`).
4. Any submission while the lock is active is refused as locked — the attempt counter does not advance and state stays `OUT_FOR_DELIVERY`.
5. After 24 hours elapse, confirmation is enabled again; the courier retries with the customer's code (UC-030) or records a failed attempt (UC-029).
6. Support answers through the auto-created ticket; the courier can add context to it (UC-210).

## Alternative Scenarios
- **A1 — Lock already active on open:** the code-entry screen is disabled with a countdown; job detail shows the lock and ticket reference.
- **A2 — Customer re-shares the correct code during the lock:** still refused until the lock expires; no attempt is consumed (BR-SHP-03).
- **A3 — Lock expires while the app is open:** refresh re-enables the code screen; the normal confirmation flow resumes (UC-030).

## Exception Scenarios
- **E1 — Ticket creation fails:** the lock still applies (security first); the platform's standard job retry path re-attempts ticket creation in the background.
- **E2 — Network failure on the third submit:** outcome unknown → courier refreshes job detail to read the authoritative attempt and lock state before retrying.
- **E3 — Repeated lockouts:** each 24-hour lock behaves the same; the recurring pattern is visible to support through the auto-created tickets (BR-SHP-03).

## Postconditions
- Lock active: confirmation blocked for 24 hours, ticket exists, sub-order stays `OUT_FOR_DELIVERY`, escrow untouched.
- Lock expired: confirmation enabled again; state changes only through a valid code entry (UC-030).

## Business Rules Applied
- BR-SHP-03

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** complements UC-030 step 2 (attempt counting) and UC-065 (auto-created ticket on the third failure).

## Permissions / Data / External Dependencies
- **Permissions:** only the assigned courier submits codes; the lock is server-enforced and cannot be dismissed by the client (BR-SHP-03).
- **Data involved:** attempt counter, `lockedUntil`, delivery-code status, auto-created support ticket with timeline.
- **External dependencies:** support ticketing (B13); delivery detail feed (B08); notifications for ticket updates (B10).

## Acceptance Criteria
- **AC-UC208-01:** Given two failed attempts, when the third code fails, then confirmation locks for 24 hours and a support ticket exists (BR-SHP-03).
- **AC-UC208-02:** Given an active lock, when a code is submitted, then it is refused and the attempt counter does not increase.
- **AC-UC208-03:** Given the lock expires, when the courier submits the correct code, then delivery confirms normally (UC-030).
- **AC-UC208-04:** Given a locked job, when job detail loads, then remaining lock time and the ticket reference are visible to the courier.
