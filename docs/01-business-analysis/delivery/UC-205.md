# UC-205 — Release an Accepted Assignment Back to the Pool

## Header Info
- **Use Case ID:** UC-205
- **Title:** Release an Accepted Assignment Back to the Pool
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier decides they cannot carry out a job they already accepted
- **Priority:** P1
- **Goal:** Return an accepted-but-not-picked-up assignment to the zone offer pool so another eligible courier can take it.
- **Preconditions:** Courier is the current assignee of a job in `ASSIGNED` state (accepted via UC-026); physical pickup not yet confirmed.

## Main Scenario
1. Courier opens the assigned job, chooses "release", enters a reason → submits `POST /deliveries/{id}/release` (conceptual touchpoint, API-SHP-005).
2. System verifies the caller is the assignee and state is `ASSIGNED`; a reason is mandatory (`REASON_REQUIRED` when absent).
3. System transitions `ASSIGNED → READY_FOR_PICKUP`, appends a history entry (actor, reason, timestamp) and returns a fresh version for optimistic locking.
4. The delivery re-enters the zone offer pool — offered to eligible couriers in the same zone again, first accept wins (BR-SHP-04).
5. The job leaves the courier's active list (conceptual `GET /deliveries/mine`) and shows up again for zone peers (UC-025).

## Alternative Scenarios
- **A1 — Job already picked up:** state is `PICKED_UP` or later → release refused with `STATE_CONFLICT`; the courier keeps the job and continues the pickup/transit flow (UC-027).
- **A2 — Courier wants to stop working:** releasing the last active job clears the precondition for going offline (UC-207), then the assignment pool is untouched.
- **A3 — Admin releases instead:** the same conceptual endpoint accepts the `ADMIN` role; the courier sees the job vanish from "my deliveries" with a history entry naming the admin actor.

## Exception Scenarios
- **E1 — Concurrent modification:** another actor changes the job at the same moment → optimistic-lock check fails with `STATE_CONFLICT`; nothing changes, courier refreshes and re-decides.
- **E2 — Job already gone (cancelled or completed):** request returns `NOT_FOUND` → "no longer available" notice; pool and history untouched.
- **E3 — Network failure after submit:** outcome unknown → courier reopens the job detail to read the authoritative state before retrying; no local mutation.

## Postconditions
- Success: sub-order back to `READY_FOR_PICKUP`, assignment cleared, offer re-broadcast to the zone, history row appended.
- Failure: state stays `ASSIGNED`, the courier keeps the job, no pool or money change.

## Business Rules Applied
- BR-SHP-04

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** reverse of UC-026 (accept) — release undoes the accept transition and restores first-accept-wins offering (BR-SHP-04).

## Permissions / Data / External Dependencies
- **Permissions:** only the assignee courier (or an admin on the same endpoint) can release; other couriers cannot touch the job (BR-SHP-04 scoping).
- **Data involved:** assignment row, release reason, status-history entry, offer row (addresses PII masked).
- **External dependencies:** offer broadcast queue `b08.shipping.assign-offer` (`../../06-backend/core/background-processing.md` §1); no location data exchanged (C-16).

## Acceptance Criteria
- **AC-UC205-01:** Given an `ASSIGNED` job, when the assignee submits release with a reason, then state becomes `READY_FOR_PICKUP` and the job reappears in the zone offer pool (BR-SHP-04).
- **AC-UC205-02:** Given a release request without a reason, when submitted, then it is rejected and state stays `ASSIGNED`.
- **AC-UC205-03:** Given a job already `PICKED_UP`, when release is attempted, then it fails with a state conflict and nothing changes.
- **AC-UC205-04:** Given a successful release, when a zone peer lists offers, then the released job is offerable again (first accept wins, BR-SHP-04).
