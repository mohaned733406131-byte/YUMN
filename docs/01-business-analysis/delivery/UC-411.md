# UC-411 — Re-Authenticate When the Session Expires Mid-Job

## Header Info
- **Use Case ID:** UC-411
- **Title:** Re-Authenticate When the Session Expires Mid-Job
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** The access token expires while the courier is acting on a delivery (code entry, pickup confirmation)
- **Priority:** P1
- **Goal:** Recover the interrupted action in place after re-authentication — without losing job context or resetting counters.
- **Preconditions:** Access token older than 15 minutes (C-08); courier mid-action on an owned job; session registry reachable.

## Main Scenario
1. The pending request fails with `AUTH_INVALID` because the access token expired (C-08).
2. The client shows a re-authentication prompt on the current route — never a hard redirect home (screen-states §4 global, routing §9).
3. Courier re-authenticates with password or OTP (FR-001); with a valid refresh token the client renews silently and rotation applies (BR-AUTH-05).
4. On success the interrupted action is re-validated and re-submitted — the courier stays exactly where they were.
5. Counters, lock and job state are read fresh from the server after re-authentication (UC-402).

## Alternative Scenarios
- **A1 — Refresh token still valid:** silent renewal, no visible prompt, and the action simply completes.
- **A2 — Refresh token expired (>7 days) or revoked:** full login is required before the action resumes (C-08).
- **A3 — OTP route:** 6-digit OTP with three attempts and a 60-second resend cooldown (BR-AUTH-03).

## Exception Scenarios
- **E1 — Consumed refresh token replayed:** the whole session family is revoked (BR-AUTH-05) → full re-login, then the action is re-validated.
- **E2 — Five failed re-authentication attempts:** 15-minute lockout plus a mandatory security notification (BR-AUTH-04, BR-NTF-02).
- **E3 — Job released or reassigned during re-auth:** the re-submitted action returns a conflict/not-found and the courier is taken back to Queue (BR-SHP-04).

## Postconditions
- Success: session renewed, interrupted action completed, courier remains on the same screen.
- Failure: no partial action is applied — job state is whatever the server holds, with nothing half-written.

## Business Rules Applied
- BR-AUTH-05, BR-AUTH-04, BR-AUTH-03, BR-NTF-02

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)
- FR-015 (Shipping & Delivery)
- **Related:** B01 gate over the B08 job flow — pairs with UC-410 (cold-start deep link) and UC-402 (state survives restart).

## Permissions / Data / External Dependencies
- **Permissions:** only the logged-in courier resumes; re-authentication never widens scope — the server re-checks ownership.
- **Data involved:** session tokens, pending request payload, shipment state (re-read after login).
- **External dependencies:** session registry (Redis, DEP-03); OTP channels (BR-NTF-03); security notification fan-out (B10).

## Acceptance Criteria
- **AC-UC411-01:** Given an expired access token mid-action, when re-authentication succeeds, then the pending action completes on the same screen.
- **AC-UC411-02:** Given a valid refresh token, when renewal runs, then a new pair is issued and the old refresh token becomes unusable (BR-AUTH-05).
- **AC-UC411-03:** Given five failed re-authentication attempts, when the fifth fails, then the account locks for 15 minutes (BR-AUTH-04).
- **AC-UC411-04:** Given a job released during re-authentication, when the action resumes, then it is refused and the courier returns to Queue (BR-SHP-04).
