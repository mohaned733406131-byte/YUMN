# UC-408 — Fall Back to the In-App Inbox When Push Delivery Fails

## Header Info
- **Use Case ID:** UC-408
- **Title:** Fall Back to the In-App Inbox When Push Delivery Fails
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** A push send fails (provider outage, reject, invalid token) for a courier notification
- **Priority:** P2
- **Goal:** Guarantee the courier still receives job messages through the in-app center whenever push cannot deliver them.
- **Preconditions:** Notification queued on `b10.notification.delivery` (BR-PLT-01); every push is mirrored into the in-app center (FR-017).

## Main Scenario
1. A delivery event is queued and mirrored into the in-app center alongside the push fan-out.
2. The push send fails → the adapter classifies it and retries per policy (3× backoff, BR-PLT-02) or marks the token stale.
3. Despite the failure the message is readable in the in-app inbox (`GET /notifications`, API-NTF-001) with its deep link intact.
4. Courier opens the inbox, reads the message, and the unread badge reconciles against `GET /notifications/unread-count`.
5. Stale tokens are pruned so later fan-outs skip them — no push retry storm is created (push fallback chain §7).

## Alternative Scenarios
- **A1 — Invalid token:** silent skip and prune; the courier finds the message on the next app open.
- **A2 — Transient provider failure:** up to three retries, then dead-letter with an alert (BR-PLT-02); the inbox copy already exists.
- **A3 — Push permission never granted:** the inbox is the only channel and the app keeps working (screen-states §5).

## Exception Scenarios
- **E1 — FCM/APNs outage:** messages accumulate in-app while orders and deliveries continue unaffected (NFR-007 graceful degradation).
- **E2 — In-app fetch fails:** block error with retry; the message persists server-side, so nothing is lost.
- **E3 — Duplicate events:** the same entity and category collapse into one entry within the dedupe window; the badge is not double-counted.

## Postconditions
- Success: the message is readable in-app regardless of the push outcome and the badge matches the server unread count.
- Failure: no message is lost — worst case the push is absent while the in-app record survives.

## Business Rules Applied
- BR-NTF-01, BR-PLT-01, BR-PLT-02

## Permissions / Data / External Dependencies
- **Permissions:** courier reads the own inbox only; notification rows are owner-scoped.
- **Data involved:** notification rows (category, channel delivery record, read state), device tokens, badge counts.
- **External dependencies:** FCM/APNs (INT-REQ-008); BullMQ queue (BR-PLT-01); Redis (DEP-03).

## Acceptance Criteria
- **AC-UC408-01:** Given a failed push send, when the courier opens the inbox, then the message is present and readable.
- **AC-UC408-02:** Given a provider outage, when events fire, then messages accumulate in-app and no retry storm occurs (BR-PLT-02).
- **AC-UC408-03:** Given an invalid token, when fan-out runs, then the token is marked stale and skipped while the inbox copy survives.
- **AC-UC408-04:** Given the inbox read completes, when the unread badge is checked, then it equals the server unread count.
