# UC-407 — Open a Delivery Job from a Push Deep Link

## Header Info
- **Use Case ID:** UC-407
- **Title:** Open a Delivery Job from a Push Deep Link
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** A job push notification arrives and the courier taps it
- **Priority:** P1
- **Goal:** Land the courier on the exact, freshly fetched delivery screen — never on a stale or foreign target.
- **Preconditions:** Device registered (UC-406); payload carries a server-generated `deepLink` with `surface: "COURIER"`, route, entity and action.

## Main Scenario
1. A delivery event fans out a push whose `data.deepLink` carries `surface: "COURIER"`, an app-relative `route`, the entity reference and an action (API-NTF contract, `07-api/core/notifications.md` §2).
2. Courier taps the notification → the OS opens the courier app, cold or warm.
3. Client checks `surface` and ignores notifications whose surface it does not serve.
4. The route is validated against the allowlist and resolved to a guarded courier screen (`05-frontend/core/routing.md` §5); unauthenticated targets bounce to the auth stack and resume after login (UC-410).
5. Client re-fetches the delivery by entity id — the payload never embeds authoritative business state (stale-state safe) — then renders the job, or falls back to Queue when the job no longer belongs to this courier.

## Alternative Scenarios
- **A1 — App backgrounded:** the same resolution path runs and the app foregrounds on the target screen.
- **A2 — Logged out:** authentication completes first, then the deep link resumes (UC-410).
- **A3 — Already read in-app:** tapping still navigates; read state is independent of routing.

## Exception Scenarios
- **E1 — Unknown or absolute URL route:** rejected by the allowlist → the app opens Queue instead (arbitrary URLs are never accepted).
- **E2 — Entity gone or reassigned:** re-fetch yields not-found → localized "not available" and return to Queue (BR-ORD-09).
- **E3 — Arrives while offline:** the app opens from cache and refreshes on reconnection; no job data is fabricated.

## Postconditions
- Success: courier lands on the correct, freshly fetched job screen holding own-scope data only.
- Failure: no navigation to a foreign or arbitrary target — the fallback is always the courier Queue.

## Business Rules Applied
- BR-ORD-09, BR-SHP-04

## Related Requirements
- FR-017 (Notifications & Messaging)
- FR-015 (Shipping & Delivery)
- **Related:** delivery half of the deep-link contract — UC-406 registers the device, UC-410 handles the logged-out bounce.

## Permissions / Data / External Dependencies
- **Permissions:** only the assignee's device receives the job link; the API independently re-checks ownership (guards are UX only, `05-frontend/core/routing.md` §6).
- **Data involved:** push payload (deepLink, entity ref, category), route/session state, delivery record (re-fetched).
- **External dependencies:** FCM/APNs via `PushPort` (INT-REQ-008); notification queue `b10.notification.delivery` (BR-PLT-01); app route allowlist.

## Acceptance Criteria
- **AC-UC407-01:** Given a `COURIER`-surface push, when tapped from cold start, then the app opens on the target delivery screen.
- **AC-UC407-02:** Given a stale payload whose job was reassigned, when the client re-fetches, then the courier sees "not available" and returns to Queue (BR-ORD-09).
- **AC-UC407-03:** Given a route outside the allowlist, when the payload arrives, then navigation is refused and Queue opens.
- **AC-UC407-04:** Given an unauthenticated courier tapping the link, when login completes, then the original deep link resumes (UC-410).
