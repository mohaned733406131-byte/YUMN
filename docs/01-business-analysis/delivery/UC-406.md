# UC-406 — Register This Courier Device for Job Push Notifications

## Header Info
- **Use Case ID:** UC-406
- **Title:** Register This Courier Device for Job Push Notifications
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier logs in or launches the app and grants the OS push-permission prompt
- **Priority:** P1
- **Goal:** Bind this device's push token to the courier's account so job events reach the phone while keeping the in-app inbox as the guaranteed channel.
- **Preconditions:** Courier authenticated; OS push permission granted; platform token available (android/ios).

## Main Scenario
1. On login or first launch the client obtains the platform push token after the OS permission grant.
2. Client calls `POST /devices` with token, platform and device name (API-NTF-008).
3. System validates token format (`DEVICE_TOKEN_INVALID` when malformed) and applies the registration rate tier (SEC-REQ-009).
4. System stores the device bound to this courier, enforcing the ≤5 device cap that mirrors the 5-session limit (BR-AUTH-06).
5. `201 { deviceId, token, registeredAt }` returns; job events (offers, assignment changes, return pickups) now fan out to this token alongside SMS, WhatsApp and in-app (BR-NTF-01).
6. A token previously bound to another user is detached from that owner and rebound to this courier.

## Alternative Scenarios
- **A1 — Permission denied:** the app keeps working and the in-app inbox remains the guaranteed channel (screen-states §5).
- **A2 — Token refresh:** the new token upserts the old entry for the same device; no duplicate rows are created.
- **A3 — Logout on this device:** `DELETE /devices/{token}` unregisters only this device's token (API-NTF-009).

## Exception Scenarios
- **E1 — Malformed or invalid token:** `DEVICE_TOKEN_INVALID` → no row created; the courier retries after a fresh grant.
- **E2 — Burst re-registration:** `RATE_LIMITED` with a countdown; the earlier successful registration still stands (SEC-REQ-009).
- **E3 — Push provider outage at send time:** registration is unaffected and the message stays readable in-app (push fallback chain §7).

## Postconditions
- Success: one active device token bound to this courier and eligible for job push fan-out.
- Failure: no device row is created (or the previous valid row is kept) and notification behaviour does not change.

## Business Rules Applied
- BR-NTF-01, BR-AUTH-06

## Related Requirements
- FR-017 (Notifications & Messaging)
- **Related:** device-token lifecycle owned by `10-integrations/core/push-notifications.md` §2 — pairs with UC-407 (deep link) and UC-408 (fallback).

## Permissions / Data / External Dependencies
- **Permissions:** any authenticated courier registers own devices only; tokens are owner-bound and never shared.
- **Data involved:** device token row (token, platform, device name, registered_at, owner), unread badge counts.
- **External dependencies:** FCM/APNs behind the `PushPort` abstraction (INT-REQ-008); BullMQ `b10.notification.delivery` (BR-PLT-01).

## Acceptance Criteria
- **AC-UC406-01:** Given a granted push permission, when the client registers, then `201` with a `deviceId` bound to the courier is returned.
- **AC-UC406-02:** Given a token previously bound to another user, when it is re-registered, then it detaches from the old owner and binds to this courier.
- **AC-UC406-03:** Given five existing device entries, when a sixth is registered, then the cap mirroring the 5-session limit is enforced (BR-AUTH-06).
- **AC-UC406-04:** Given a malformed token, when registration is attempted, then `DEVICE_TOKEN_INVALID` is returned and no row is created.
