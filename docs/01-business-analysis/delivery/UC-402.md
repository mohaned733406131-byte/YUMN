# UC-402 — Keep Attempt and Lock Progress Across an App Restart

## Header Info
- **Use Case ID:** UC-402
- **Title:** Keep Attempt and Lock Progress Across an App Restart
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** The courier app is killed or restarted mid-job (OS reclaim, crash, manual close)
- **Priority:** P2
- **Goal:** Rehydrate the job exactly as the server knows it — attempts, lock countdown and state survive a restart untouched.
- **Preconditions:** At least one active or recent job; server-side attempt/lock storage is authoritative (FM-08, §2.5).

## Main Scenario
1. The app terminates while the courier is working a job.
2. On relaunch the client re-authenticates (session/refresh per C-08) and re-fetches job state (`GET /deliveries/{id}`).
3. Attempt counters, `code_locked_until`, escalation position and shipment state are rendered from the server response — never from local storage.
4. The 24-hour lock countdown continues from the server timestamp: a restart neither resets nor extends it (BR-SHP-03).
5. Courier resumes at the last authoritative screen — Queue, Active, or a locked CodeEntry showing the live countdown.

## Alternative Scenarios
- **A1 — Offline at restart:** cached views render behind the offline banner, labelled as the last known server read (screen-states §5).
- **A2 — Session expired at restart:** re-auth prompt, then the courier returns to the same job (UC-411) rather than to home.
- **A3 — No active job:** the Queue tab opens with the empty state and its recovery actions.

## Exception Scenarios
- **E1 — State fetch fails:** page error with retry; the app never displays zeroed or fabricated counters.
- **E2 — Local cache disagrees with the server:** server wins; the cache is replaced on the successful read.
- **E3 — Re-authentication fails repeatedly:** the fifth failure locks the account for 15 minutes (BR-AUTH-04) and the restart resumes only after the lock.

## Postconditions
- Success: attempts, lock and job state are identical to their pre-restart values (server-authoritative).
- Failure: nothing is written — no counter, lock or state is mutated by a restart.

## Business Rules Applied
- BR-SHP-03, BR-AUTH-04

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** read-back half of UC-411 (session expiry) — the guarantee is owned by failure mode FM-08 §2.5.

## Permissions / Data / External Dependencies
- **Permissions:** assignee courier only; the server restores own jobs (BR-ORD-09).
- **Data involved:** shipment counters, code lock fields, session tokens, non-authoritative local cache.
- **External dependencies:** auth/session store (Redis, DEP-03); delivery API.

## Acceptance Criteria
- **AC-UC402-01:** Given `code_attempts = 2` before a restart, when the app relaunches, then the UI shows 2 and the server value remains 2.
- **AC-UC402-02:** Given an active 24-hour lock, when the app restarts, then the countdown is recomputed from the server `lockUntil` (BR-SHP-03).
- **AC-UC402-03:** Given a local cache holding stale zeroed counters, when the server read completes, then server values replace the cache.
- **AC-UC402-04:** Given five failed re-authentication attempts after restart, when the fifth fails, then the account locks for 15 minutes (BR-AUTH-04).
