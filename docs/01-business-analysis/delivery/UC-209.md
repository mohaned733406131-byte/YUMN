# UC-209 — Follow the Order Timeline During a Delivery

## Header Info
- **Use Case ID:** UC-209
- **Title:** Follow the Order Timeline During a Delivery
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier opens the order history/timeline view for a delivery they are assigned to
- **Priority:** P2
- **Goal:** Let the courier watch the append-only order timeline scoped to their own delivery while the job progresses.
- **Preconditions:** Courier is the assigned courier on the order (BR-ORD-09); order exists with status history.

## Main Scenario
1. Courier opens the job and selects "history" → client `GET /orders/{id}/timeline` (API-ORD-005, roles include `COURIER`).
2. System returns append-only entries (from → to, actor, timestamp, reason), filtered to the courier's own delivery slice (BR-ORD-09).
3. Courier sees the progression that concerns them: assignment, pickup, transit, out-for-delivery, delivery confirmation (UC-027, UC-028, UC-030).
4. Each courier action (pickup scan, transit scan, code entry) appends a new entry with courier identity and timestamp; existing entries are never edited.
5. The view contains no location/GPS data at any point (BR-SHP-05); a refresh always re-reads the same authoritative history.

## Alternative Scenarios
- **A1 — Sub-order granularity:** orders with several sub-orders return only the rows belonging to the courier's assigned slice (BR-ORD-09).
- **A2 — Timeline as evidence:** when opening a support ticket about the delivery (UC-210), the courier references entries from this view in the ticket body.
- **A3 — Refresh after own action:** after a scan or code entry, the reload shows the just-appended entry for that action.

## Exception Scenarios
- **E1 — Not the assigned courier (or order unknown):** access is denied / `NOT_FOUND`; nothing is rendered (BR-ORD-09 scoping).
- **E2 — Read failure or timeout:** retry with the last known entries and a retry affordance; the operation is read-only, no local state changes.
- **E3 — Concurrent state change during the read:** the refreshed view simply shows the newly appended row; prior rows stay byte-identical (append-only).

## Postconditions
- Read-only: no order state, assignment, or money change; the courier's picture of the delivery matches the server history (BR-ORD-09).

## Business Rules Applied
- BR-ORD-09, BR-SHP-05

## Related Requirements
- FR-012 (Order Lifecycle Management), FR-015 (Shipping & Delivery)

## Permissions / Data / External Dependencies
- **Permissions:** assigned courier reads only own delivery rows; buyer, vendor, admin and moderator read their own scoped slices (BR-ORD-09).
- **Data involved:** append-only order status history (actor, timestamp, reason), sub-order rows.
- **External dependencies:** order read model / timeline projection (`b06.order.timeline-project`, background-processing.md §1); courier app Active/History tabs (S5).

## Acceptance Criteria
- **AC-UC209-01:** Given the assigned courier, when the timeline is requested, then own-delivery entries are returned (BR-ORD-09).
- **AC-UC209-02:** Given an order assigned to another courier, when requested, then access is denied and no entries are shown.
- **AC-UC209-03:** Given the rendered timeline, when inspected, then no GPS or location field appears anywhere (BR-SHP-05).
- **AC-UC209-04:** Given a courier state-change action, when the timeline is reloaded, then a new entry with actor and timestamp is present and earlier entries are unchanged.
