# UC-409 — Configure Delivery Notification Channels as a Courier

## Header Info
- **Use Case ID:** UC-409
- **Title:** Configure Delivery Notification Channels as a Courier
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier wants to choose which channels carry which notification categories
- **Priority:** P2
- **Goal:** Persist a per-category, per-channel opt-in matrix for the courier while security notices stay non-disableable.
- **Preconditions:** Courier authenticated; preferences endpoint reachable; four channels exist in v1 — SMS, WhatsApp, in-app, push (BR-NTF-01).

## Main Scenario
1. Courier opens Profile → notification settings → client calls `GET /notifications/preferences` (API-NTF-006).
2. The response is the per-category, per-channel opt-in matrix with `emailSupported: false` (BR-NTF-01).
3. Security rows arrive `locked` and immutable — rendered but not toggleable (BR-NTF-02).
4. Courier toggles delivery, order and promo channels and saves via `PUT /notifications/preferences` (API-NTF-007).
5. System applies the updates, returns the refreshed matrix, and later fan-outs honour the new channel set (BR-NTF-05).

## Alternative Scenarios
- **A1 — Security category touched:** rejected with `PREFERENCE_IMMUTABLE`; the matrix is unchanged (BR-NTF-02).
- **A2 — Email channel requested:** rejected with `CHANNEL_NOT_SUPPORTED` — no email exists in v1 (BR-NTF-01).
- **A3 — Restore defaults:** a bulk update resets every non-security row to the platform default.

## Exception Scenarios
- **E1 — Concurrent edit from another device:** last successful write wins after a fresh read; no partial matrix is stored.
- **E2 — Save fails on the network:** pending toggles stay on screen with retry; the server matrix is untouched.
- **E3 — Unknown category or channel pair:** `VALIDATION_ERROR` → nothing is written.

## Postconditions
- Success: the persisted matrix matches the courier's choices and security categories are untouched.
- Failure: no partial preference write — the prior matrix remains intact.

## Business Rules Applied
- BR-NTF-05, BR-NTF-02, BR-NTF-01

## Related Requirements
- FR-017 (Notifications & Messaging)
- **Related:** courier-portal twin of the customer preference screen — same endpoints, courier-scoped account.

## Permissions / Data / External Dependencies
- **Permissions:** any authenticated courier edits own preferences; security rows are never user-editable (BR-NTF-02).
- **Data involved:** notification preference matrix (category × channel), profile notification settings.
- **External dependencies:** fan-out engine reads preferences at send time (B10); templates localized per BR-NTF-04.

## Acceptance Criteria
- **AC-UC409-01:** Given a courier toggling a non-security category channel, when saved, then the new matrix is returned and stored (BR-NTF-05).
- **AC-UC409-02:** Given a security category, when a change is attempted, then `PREFERENCE_IMMUTABLE` is returned and nothing changes (BR-NTF-02).
- **AC-UC409-03:** Given an `EMAIL` channel in the payload, when submitted, then `CHANNEL_NOT_SUPPORTED` is returned with no change (BR-NTF-01).
- **AC-UC409-04:** Given the saved matrix, when the next delivery event fans out, then only the enabled channels are used.
