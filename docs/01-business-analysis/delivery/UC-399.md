# UC-399 — Finish on the Proof Success Screen and Continue to the Next Job

## Header Info
- **Use Case ID:** UC-399
- **Title:** Finish on the Proof Success Screen and Continue to the Next Job
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Code verification succeeds and the delivery reaches `DELIVERED`
- **Priority:** P2
- **Goal:** Close the completed job on a clear proof confirmation and return the courier to a workable Queue with one tap.
- **Preconditions:** Delivery just verified (UC-030); courier authenticated; Queue feed reachable.

## Main Scenario
1. Verified code moves the sub-order to `DELIVERED`; the client renders the proof screen — code status, timestamp, courier identity and the optional photo slot (BR-SHP-07).
2. A full-screen success confirmation appears with the "next job" call to action (screen-states §9).
3. Courier may attach the optional photo (UC-398) without leaving the proof state.
4. Courier taps "next job" → returns to the Queue tab (S5) and the offer feed refreshes (`GET /deliveries/available`).
5. If an offer is waiting it opens the accept path (UC-026); the completed delivery's 7-day escrow hold has started (BR-ESC-01).

## Alternative Scenarios
- **A1 — No jobs available:** queue shows the courier empty state with Refresh and History recovery actions.
- **A2 — Review the finished job:** the History tab keeps the record with proof visible (UC-415).
- **A3 — Reopening the proof screen:** idempotent "already delivered" notice — no second transition (screen-states §7).

## Exception Scenarios
- **E1 — Next-job refresh fails:** block error with retry inside the success screen; the completed delivery stays confirmed.
- **E2 — Session expires on the success screen:** re-auth prompt then return to the action — never a hard redirect home (screen-states §4 global).
- **E3 — Offline after success:** the confirmed response keeps the success screen usable; writes stay blocked until reconnection.

## Postconditions
- Success: proof complete, courier back at Queue, next offer flow reachable, escrow clock running.
- Failure: the committed `DELIVERED` transition is never rolled back and no second transition is written.

## Business Rules Applied
- BR-SHP-07, BR-ESC-01

## Related Requirements

- **Related:** terminal UI of UC-030 (code verification); confirmation pattern owned by `DOC-UX-005` §9.

## Permissions / Data / External Dependencies
- **Permissions:** assigned courier sees own proof; customer sees the same delivery only through own order timeline (BR-ORD-09).
- **Data involved:** delivery proof record, success-screen state, refreshed offer feed.
- **External dependencies:** offer feed (API-SHP-001); notification fan-out to customer and vendor (B10).

## Acceptance Criteria
- **AC-UC399-01:** Given a verified code, when the proof screen opens, then timestamp, courier identity and the photo slot are shown (BR-SHP-07).
- **AC-UC399-02:** Given the success screen, when "next job" is tapped, then the Queue tab loads with a refreshed offer feed.
- **AC-UC399-03:** Given no open offers, when the queue loads, then the empty state with recovery actions is displayed.
- **AC-UC399-04:** Given an expired session on the success screen, when re-authentication completes, then the courier returns to the same action, not to home.
