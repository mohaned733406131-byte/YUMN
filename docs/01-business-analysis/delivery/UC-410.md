# UC-410 — Resume a Delivery Deep Link After Signing In

## Header Info
- **Use Case ID:** UC-410
- **Title:** Resume a Delivery Deep Link After Signing In
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier follows a delivery deep link while logged out or holding an expired session
- **Priority:** P2
- **Goal:** Authenticate and return the courier to the exact delivery they asked for — never to an arbitrary or foreign target.
- **Preconditions:** Deep link resolves to a guarded courier route; login carries the encoded target as `next` (`05-frontend/core/routing.md` §9).

## Main Scenario
1. Courier opens a delivery deep link (push, saved route) without a valid session.
2. The guard bounces to the courier auth stack with the intended target encoded in `next` (307 to `/{locale}/login?next=…`).
3. Courier authenticates with phone plus password or OTP (FR-001, C-06).
4. On success the client returns to the encoded `next` target rather than the default landing (ACT-03 lands back on the deep link).
5. The target delivery is re-fetched under the new session; if it is still this courier's, the job opens (UC-407).

## Alternative Scenarios
- **A1 — Session merely expired:** an in-place re-auth prompt continues the action — never a hard redirect home (routing §9).
- **A2 — Role mismatch after login:** a non-courier account is redirected to its own role landing; the delivery link is not honoured.
- **A3 — Target no longer assigned:** after login the fetch yields not-found → Queue with an explanation (BR-ORD-09).

## Exception Scenarios
- **E1 — Tampered or absolute `next`:** ignored — the courier falls back to their landing page and no foreign URL is opened.
- **E2 — Login fails:** the error stays on the login screen and `next` is preserved for the retry.
- **E3 — Five consecutive failed logins:** 15-minute lockout applies (BR-AUTH-04) with `next` still preserved for after the lock.

## Postconditions
- Success: courier is authenticated and looking at the intended delivery, or an honest fallback.
- Failure: no unauthorized screen opens and `next` survives until a successful login.

## Business Rules Applied
- BR-AUTH-04, BR-ORD-09

## Related Requirements
- FR-001 (Identity, Authentication & Session Management)
- FR-015 (Shipping & Delivery)
- **Related:** courier instance of the deep-link auth bounce — complements UC-407 (tap while logged in) and UC-411 (expiry mid-job).

## Permissions / Data / External Dependencies
- **Permissions:** authentication is public; delivery access is re-checked server-side after login (guards are UX only, routing §6).
- **Data involved:** session tokens, `next` parameter (encoded, non-secret), delivery record (read after login).
- **External dependencies:** auth/session store (Redis, DEP-03); OTP delivery via SMS with WhatsApp failover (BR-NTF-03).

## Acceptance Criteria
- **AC-UC410-01:** Given a logged-out courier opening a delivery deep link, when login succeeds, then the courier lands on that delivery screen.
- **AC-UC410-02:** Given an invalid or absolute `next` value, when login succeeds, then the courier lands on their default and no foreign URL is opened.
- **AC-UC410-03:** Given five failed login attempts, when the fifth fails, then login is locked for 15 minutes with `next` preserved (BR-AUTH-04).
- **AC-UC410-04:** Given a resumed link to a job not owned by the courier, when fetched, then it is not found and Queue opens (BR-ORD-09).
