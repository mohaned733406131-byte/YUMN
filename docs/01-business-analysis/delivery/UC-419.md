# UC-419 — Work Only with a Masked Buyer Code at the Door

## Header Info
- **Use Case ID:** UC-419
- **Title:** Work Only with a Masked Buyer Code at the Door
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Job reaches `OUT_FOR_DELIVERY` and the courier prepares to confirm delivery at the door
- **Priority:** P1
- **Goal:** Verify with a customer-read code while the courier never receives or stores the full 6-digit value.
- **Preconditions:** Shipment `OUT_FOR_DELIVERY`; 6-digit code issued to the buyer only (BR-SHP-02); courier is the assignee.

## Main Scenario
1. At `OUT_FOR_DELIVERY` the code is issued to the buyer via SMS, WhatsApp and in-app; the courier is never sent the full value (BR-SHP-02).
2. Courier opens the job → the detail carries only `buyerCodeMasked` (e.g. `**4821`) as a last-digits hint (API-SHP-009 response).
3. Courier asks the customer to read the code aloud and types it into the six-slot input, masked against shoulder-surfing with a reveal toggle (screen-states §7).
4. Submission is verified server-side against the stored hash; the full code is never returned to the courier on any endpoint.
5. The customer-only endpoint that returns the full code (`GET /orders/{id}/delivery-code`, API-SHP-013) denies courier calls (BR-ORD-09 scope).

## Alternative Scenarios
- **A1 — No masked hint present:** the code was not issued or was already verified → the courier relies on the customer reading it out.
- **A2 — Customer unavailable:** the courier waits and retries later without guessing (UC-418).
- **A3 — Wrong entry:** remaining attempts are shown after a failed submission (BR-SHP-03).

## Exception Scenarios
- **E1 — Courier calls the customer-only code endpoint:** denied (BR-ORD-09); the courier UI never offers it.
- **E2 — Masked value stale after reissue:** a refresh of the job detail updates the hint; verification still uses the server-side hash.
- **E3 — Shoulder-surfing risk:** slots stay masked by default and require the explicit reveal toggle (screen-states §7).

## Postconditions
- Success: delivery verified from the customer-provided code and the courier holds no stored full code.
- Failure: the full 6-digit code never appears in any courier-facing response, log or cache.

## Business Rules Applied
- BR-SHP-02, BR-SHP-03, BR-ORD-09

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** visibility split between API-SHP-009 (masked) and API-SHP-013 (customer-only) — pairs with UC-420 (Latin digit slots).

## Permissions / Data / External Dependencies
- **Permissions:** courier submits codes but never reads them; only the buyer can read the full code (`CUSTOMER` role); only a hash is stored.
- **Data involved:** masked code hint, `delivery_code_hash` (server-side), attempt counters, input buffer.
- **External dependencies:** code issuance fan-out through B10 (BR-NTF-03); no location data exchanged (C-16).

## Acceptance Criteria
- **AC-UC419-01:** Given an `OUT_FOR_DELIVERY` job, when the courier opens it, then only a masked code hint with last digits is shown (API-SHP-009).
- **AC-UC419-02:** Given a courier request to the customer-only code endpoint, when sent, then it is denied and no code is returned (BR-ORD-09).
- **AC-UC419-03:** Given the correct code read by the customer, when entered, then the delivery verifies and reaches `DELIVERED` (BR-SHP-02).
- **AC-UC419-04:** Given any courier-facing response for the job, when inspected, then the full 6-digit code never appears in it.
