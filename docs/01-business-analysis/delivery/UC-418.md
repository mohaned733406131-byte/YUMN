# UC-418 — Wait and Retry Later When the Customer Is Unavailable

## Header Info
- **Use Case ID:** UC-418
- **Title:** Wait and Retry Later When the Customer Is Unavailable
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier is at the drop-off but the customer is absent and has not shared the 6-digit code
- **Priority:** P1
- **Goal:** Leave the delivery deliverable on a later visit without burning a code attempt or applying a lock.
- **Preconditions:** Shipment `OUT_FOR_DELIVERY`; code issued to the buyer (BR-SHP-02); no code in hand.

## Main Scenario
1. Courier is at the door with the job `OUT_FOR_DELIVERY` while the customer is absent and no code has been shared (WF-005 step 6).
2. Courier does not guess a code — entry happens only with a code in hand, and waiting consumes nothing.
3. Courier marks the visit "customer unavailable / retry later" → the job hands back to transit awaiting the next attempt (API-SHP-008) with no code attempt consumed (BR-SHP-03).
4. The visit outcome is recorded for context while `code_attempts` stays unchanged and `code_locked_until` stays null.
5. Courier moves to other jobs and returns later; the code issued at `OUT_FOR_DELIVERY` still verifies on the next visit (BR-SHP-02).

## Alternative Scenarios
- **A1 — Customer returns and shares the code:** normal verification proceeds (UC-030) and attempts count from that point.
- **A2 — A wrong code is entered during the visit:** that entry consumes exactly one attempt and shows remaining counts (BR-SHP-03) — the contrast defining this use case.
- **A3 — Repeated absence over several visits:** visits without entry stay free; escalation follows recorded failed delivery attempts (BR-SHP-06), not code attempts.

## Exception Scenarios
- **E1 — 24-hour code lock already active:** entry is refused regardless and the courier waits out the countdown (BR-SHP-03).
- **E2 — App restart during the wait:** counters and lock are preserved server-side (UC-402).
- **E3 — Job reassigned while waiting:** the next attempt belongs to the new assignee and this courier's screen disables (UC-400).

## Postconditions
- Success: no code attempt consumed, no lock applied, and the job remains deliverable on a later visit.
- Failure: if a code was actually entered wrongly, the attempt counter increases honestly — it is never faked back to zero.

## Business Rules Applied
- BR-SHP-03, BR-SHP-02, BR-SHP-06

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** WF-005 step 6 — complements UC-030 (code entry) and UC-417 (pickup-side wait).

## Permissions / Data / External Dependencies
- **Permissions:** assignee courier only; customer absence never triggers a system-side state jump.
- **Data involved:** shipment state, code attempt counters (unchanged), attempt log visit record, delivery code.
- **External dependencies:** no location check is permitted at the door (BR-SHP-05, C-16); notification channels if the customer is messaged (B10).

## Acceptance Criteria
- **AC-UC418-01:** Given a visit with no code entered, when the courier marks the customer unavailable, then `code_attempts` does not increase (BR-SHP-03).
- **AC-UC418-02:** Given no attempt consumed, when the lock fields are read, then `code_locked_until` is null and verification remains possible (BR-SHP-02).
- **AC-UC418-03:** Given a wrong code entered during the visit, when counted, then exactly one attempt is consumed (BR-SHP-03).
- **AC-UC418-04:** Given the later retry, when the customer shares the code, then verification succeeds under the normal attempt rules.
