# UC-396 — Decline a Delivery Offer Without Claiming It

## Header Info
- **Use Case ID:** UC-396
- **Title:** Decline a Delivery Offer Without Claiming It
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier reviews an open offer in the Queue tab and decides not to take the job
- **Priority:** P1
- **Goal:** Reject a personal offer so the courier is not blocked by it, while the shipment stays available to every other eligible courier.
- **Preconditions:** Offer row exists for this courier (`b08.shipment_offer`, `UNIQUE(shipment_id, courier_id)`); shipment `READY_FOR_PICKUP`; courier online (BR-SHP-04).

## Main Scenario
1. Courier opens an offer from the Queue feed (`GET /deliveries/available`, API-SHP-001) showing zone, pickup point, drop-off district, weight band and offered fee.
2. Courier taps "decline" → the offer row addressed to this courier moves `OFFERED → DECLINED` with a response timestamp.
3. The shipment itself is untouched: it stays `READY_FOR_PICKUP` and keeps being offered to other eligible same-zone couriers (BR-SHP-04).
4. The offer disappears from this courier's Queue; peers still see it until one accepts first (first accept wins via optimistic locking, BR-SHP-04).
5. No shipment or order state transition occurs, so no `order_status_history` row is appended — decline is a response, not a lifecycle event (BR-ORD-03).

## Alternative Scenarios
- **A1 — Offer already claimed:** another courier accepted first → decline is refused with a conflict/not-found; the courier refreshes the feed and picks another offer (BR-SHP-04).
- **A2 — Offer expired:** `expires_at` passed → status is `EXPIRED`; a late decline is a no-op against an already-closed row.
- **A3 — Nothing left to decline:** the feed returns the courier empty state with Refresh and History recovery actions.

## Exception Scenarios
- **E1 — Concurrent accept/decline race:** version check fails → nothing changes for the shipment; the courier re-reads the feed (BR-SHP-04).
- **E2 — Network failure after tapping decline:** outcome unknown → courier reloads the offer list and confirms the offer is gone before assuming success; no local-only mutation.
- **E3 — Job already held by this courier:** accepted earlier or reassigned → decline rejected (`STATE_CONFLICT`); the job stays in Active.

## Postconditions
- Success: exactly this courier's offer row is `DECLINED`; the shipment remains `READY_FOR_PICKUP` and offerable to peers.
- Failure: the offer row is unchanged (`OFFERED` or already `ACCEPTED`); no shipment, order or history change exists.

## Business Rules Applied
- BR-SHP-04, BR-ORD-03

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** non-committing third response to an offer — pairs with UC-026 (accept) and UC-205 (release).

## Permissions / Data / External Dependencies
- **Permissions:** courier responds only to offers addressed to them (`UNIQUE(shipment_id, courier_id)`, BR-ORD-09 scope); admin dispatch observes.
- **Data involved:** `shipment_offer` row (status, responded_at), shipment state (read-only), queue feed.
- **External dependencies:** offer broadcast queue `b08.shipping.assign-offer` (BR-PLT-01); no location data exchanged (C-16).

## Acceptance Criteria
- **AC-UC396-01:** Given an `OFFERED` row for this courier, when decline is submitted, then the row becomes `DECLINED` and the shipment stays `READY_FOR_PICKUP` (BR-SHP-04).
- **AC-UC396-02:** Given a declined offer, when a zone peer lists offers, then the shipment is still offerable and first accept still wins (BR-SHP-04).
- **AC-UC396-03:** Given an offer already `ACCEPTED` by another courier, when decline is submitted, then it is refused and no row changes.
- **AC-UC396-04:** Given a declined offer, when the order history is read, then no state transition was appended (BR-ORD-03).
