# UC-420 — Type the Delivery Code with Latin Digits in the Arabic Interface

## Header Info
- **Use Case ID:** UC-420
- **Title:** Type the Delivery Code with Latin Digits in the Arabic Interface
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier enters the 6-digit delivery code while the app is in the default Arabic locale
- **Priority:** P2
- **Goal:** Keep verification identical in both locales — Latin digits in the slots, fully localized labels around them.
- **Preconditions:** Arabic locale active (C-24, Arabic-first); job `OUT_FOR_DELIVERY`; code slots render an LTR island.

## Main Scenario
1. Courier works in Arabic (default) and opens CodeEntry with its six-slot input.
2. The slots are a Latin-digit island (`dir="ltr"`) with localized labels around them — digits match the SMS the customer received (`11-ui-ux/core/localization.md` §3).
3. The numeric keypad yields Latin digits and the courier types the code exactly as the customer reads it.
4. On failure the localized Arabic message and attempts counter are announced around the Latin slots (UC-404).
5. Verification runs on the canonical Latin value while the surrounding screen stays fully localized with no hardcoded strings (BR-PLT-05).

## Alternative Scenarios
- **A1 — English locale:** identical slot behaviour; only the labels change (NFR-013 parity).
- **A2 — Mixed digit input (Arabic-Indic keystrokes or paste):** normalized or rejected so a single canonical form is validated (localization §3 input normalization).
- **A3 — Locale switched mid-entry:** labels re-localize while slot values and direction are untouched (UC-412).

## Exception Scenarios
- **E1 — Wrong length or non-digit content:** `VALIDATION_ERROR` before any attempt is consumed (BR-SHP-03 untouched).
- **E2 — Correct length but wrong code:** normal attempt feedback with localized copy around the Latin slots (BR-SHP-03).
- **E3 — Missing localized string:** Arabic copy is used as fallback and the parity gap is logged as a release defect (NFR-013).

## Postconditions
- Success: the code verifies from Latin-digit input inside a fully localized Arabic screen.
- Failure: no locale-dependent verification bug — the canonical value checked is identical under `ar` and `en`.

## Business Rules Applied
- BR-PLT-05, BR-SHP-02, BR-SHP-03

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** numeral policy in `11-ui-ux/core/localization.md` §3 — code slots are the documented Latin-digit exception inside the Arabic UI.

## Permissions / Data / External Dependencies
- **Permissions:** same assignee-only verification; locale is a display concern with no effect on authorization.
- **Data involved:** code input buffer, localized string catalogs, server-side hash comparison.
- **External dependencies:** locale bundles in the app; code content produced by the notification pipeline (BR-NTF-04).

## Acceptance Criteria
- **AC-UC420-01:** Given the Arabic UI, when the customer's Latin-digit code is entered, then verification succeeds exactly as in English (BR-SHP-02).
- **AC-UC420-02:** Given mixed or invalid digits, when submitted, then `VALIDATION_ERROR` is returned and no attempt is consumed (BR-SHP-03).
- **AC-UC420-03:** Given the Arabic locale, when the slots render, then digits are Latin inside an LTR island with localized labels (BR-PLT-05).
- **AC-UC420-04:** Given a wrong code, when feedback renders, then message and counter are localized while the digits stay Latin (NFR-013).
