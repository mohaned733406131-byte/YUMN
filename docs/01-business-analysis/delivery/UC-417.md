# UC-417 — Record a Failed Pickup Attempt When the Store Is Not Ready

## Header Info
- **Use Case ID:** UC-417
- **Title:** Record a Failed Pickup Attempt When the Store Is Not Ready
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier reaches the pickup point and the package or store is not ready
- **Priority:** P1
- **Goal:** Capture pickup-side evidence with a reason while the shipment stays assigned and no possession is claimed.
- **Preconditions:** Shipment `ASSIGNED` to this courier; pickup not yet confirmed; attempt storage enforces unique attempt numbers per shipment.

## Main Scenario
1. Courier arrives at the pickup point and the package is missing, incomplete or the store is closed (UC-027 E1).
2. Courier records a pickup failure with a reason and optional note → a `shipment_attempt` row is appended with outcome `PICKUP_FAILED`.
3. The shipment stays `ASSIGNED` — no pickup transition occurs and possession is never claimed (BR-ORD-03: history appended, state unchanged).
4. Vendor and admin are notified of the failed pickup (BR-NTF-01) and the job remains in the courier's Active list.
5. Failures accumulate in the same attempt log; at the third failed attempt the delivery escalates to admin review with the full timeline (BR-SHP-06).

## Alternative Scenarios
- **A1 — Package becomes ready later:** the courier confirms pickup normally (UC-027) and the failure rows remain as history.
- **A2 — Admin reacts to repeated failures:** the job can be released or reassigned; the offer returns to the zone pool (BR-SHP-04).
- **A3 — Bad address or wrong door:** the same recording path applies and a support ticket route is available (UC-210).

## Exception Scenarios
- **E1 — Reason omitted:** `REASON_REQUIRED` → nothing is written.
- **E2 — Concurrent state change (cancelled by admin):** `STATE_CONFLICT` → no attempt row is added to a cancelled shipment.
- **E3 — Notification failure:** the attempt row still commits; parties read status from their own scoped views.

## Postconditions
- Success: one `PICKUP_FAILED` attempt row with reason, courier and timestamp; shipment still `ASSIGNED`.
- Failure: no attempt row, no state change and no possession recorded.

## Business Rules Applied
- BR-SHP-06, BR-ORD-03, BR-SHP-04, BR-NTF-01

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** pickup-side sibling of UC-029 (failed delivery attempt) — same attempt log, different leg of the job.

## Permissions / Data / External Dependencies
- **Permissions:** only the assignee courier records attempts for the own job (BR-ORD-09); vendor and admin observe.
- **Data involved:** `shipment_attempt` rows, shipment counters, order history, notifications.
- **External dependencies:** notification fan-out (B10); admin dispatch view (B13).

## Acceptance Criteria
- **AC-UC417-01:** Given an `ASSIGNED` job with the store not ready, when the courier records the failure, then a `PICKUP_FAILED` attempt row exists with reason and timestamp.
- **AC-UC417-02:** Given the recorded failure, when the shipment state is read, then it remains `ASSIGNED` (BR-ORD-03).
- **AC-UC417-03:** Given a submission without a reason, when sent, then `REASON_REQUIRED` is returned and no row is written.
- **AC-UC417-04:** Given three recorded failures, when the threshold is evaluated, then the case escalates to admin review with the full timeline (BR-SHP-06).
