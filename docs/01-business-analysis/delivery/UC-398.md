# UC-398 — Upload an Optional Delivery Photo as Extra Proof

## Header Info
- **Use Case ID:** UC-398
- **Title:** Upload an Optional Delivery Photo as Extra Proof
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier wants to attach a photo to a delivery as supplementary evidence
- **Priority:** P2
- **Goal:** Store one optional delivery photo linked to the shipment without ever making the photo a condition of delivery.
- **Preconditions:** Job assigned to this courier; proof upload endpoint reachable; photo ≤5 MB in jpg/png/webp.

## Main Scenario
1. Courier finishes code verification (UC-030) and stays on the proof screen (UC-399), then chooses "add photo".
2. Client sends `POST /deliveries/{id}/proof-photo` as multipart (API-SHP-012).
3. System enforces size and media type, strips EXIF and runs the file scan (SEC-REQ-011) before writing the object to MinIO (DEP-07).
4. On success `201 { photoUrl, uploadedAt }` returns and `proof_photo_key` is set on the shipment.
5. Proof remains code + timestamp + courier identity; the photo is stored but never required and never gates `DELIVERED` (BR-SHP-07).

## Alternative Scenarios
- **A1 — Courier skips the photo:** proof is already complete after code verification; nothing else is needed (BR-SHP-07).
- **A2 — Photo already present:** a second upload replaces the stored key for the same shipment; one photo is retained per delivery.
- **A3 — Offline:** the upload is blocked with an explanation and the file stays local until connectivity returns (screen-states §5).

## Exception Scenarios
- **E1 — File over 5 MB:** `PAYLOAD_TOO_LARGE` → nothing stored; the courier picks a smaller file.
- **E2 — Unsupported media type:** `UNSUPPORTED_MEDIA_TYPE` → nothing stored; jpg/png/webp only.
- **E3 — Scan fails:** `FILE_SCAN_FAILED` → the object is rejected and no key is written (SEC-REQ-011).

## Postconditions
- Success: `proof_photo_key` set and `photoUrl` returned; delivery state and code verification unchanged.
- Failure: no object stored and no partial key — proof from code verification remains intact.

## Business Rules Applied
- BR-SHP-07

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** the optional artifact displayed on the UC-399 proof success screen; never a precondition for `DELIVERED`.

## Permissions / Data / External Dependencies
- **Permissions:** only the assignee courier uploads for the own delivery (BR-ORD-09); other parties read the proof through their own scoped views.
- **Data involved:** shipment proof fields, MinIO object, scan result.
- **External dependencies:** MinIO object storage (DEP-07); file-scanning service; delivery API.

## Acceptance Criteria
- **AC-UC398-01:** Given an assignee courier uploading a ≤5 MB jpg, when processed, then `201` with `photoUrl` is returned and `proof_photo_key` is set (BR-SHP-07).
- **AC-UC398-02:** Given no photo uploaded, when the code verifies, then the delivery still reaches `DELIVERED` with complete proof (BR-SHP-07).
- **AC-UC398-03:** Given a 6 MB file, when uploaded, then `PAYLOAD_TOO_LARGE` is returned and no object is stored.
- **AC-UC398-04:** Given a file that fails the scan, when uploaded, then `FILE_SCAN_FAILED` is returned and no key is written (SEC-REQ-011).
