# UC-400 — Disable Code Entry When the Job Is Reassigned or Released

## Header Info
- **Use Case ID:** UC-400
- **Title:** Disable Code Entry When the Job Is Reassigned or Released
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** While the courier sits on CodeEntry, the assignment changes under them (release, admin override, reassignment)
- **Priority:** P1
- **Goal:** Kill code entry on a job the courier no longer owns, explain why, and return them to the Queue without consuming attempts.
- **Preconditions:** CodeEntry screen open for an `OUT_FOR_DELIVERY` job; assignment can change concurrently (BR-SHP-04).

## Main Scenario
1. Courier is on CodeEntry (S5) for an `OUT_FOR_DELIVERY` job they hold.
2. Assignment changes elsewhere: courier releases (UC-205), admin releases/overrides, or the job is reassigned (BR-SHP-04).
3. Client re-reads job state on refresh/focus and finds the caller is no longer the assignee.
4. Code input is disabled with a text explanation ("أعيد توزيع الطلب / Order reassigned") and the app returns to the Queue tab — the documented "Order reassigned/released" state (screen-states §7).
5. Any in-flight code submission is rejected server-side; `code_attempts` is not incremented.

## Alternative Scenarios
- **A1 — Admin released it:** same disabled treatment; the history entry names the admin actor (UC-205 A3).
- **A2 — Code already verified before the change:** success no-op "already delivered"; no entry is possible (screen-states §7).
- **A3 — Courier reclaims it later:** if the job returns to the zone pool and this courier accepts again, CodeEntry re-enables on the fresh assignment (BR-SHP-04).

## Exception Scenarios
- **E1 — Submission races the reassignment:** server returns not-found/state-conflict; the attempt counter stays unchanged.
- **E2 — Change notice never reaches the device:** the next authoritative read still disables input — local state never wins.
- **E3 — Offline while the change happens:** the disabled state is applied on reconnect, before any entry is accepted.

## Postconditions
- Success: no code entry is possible on a job this courier no longer owns; the courier is back at Queue.
- Failure: if the assignment was in fact unchanged, input stays enabled and the job proceeds normally.

## Business Rules Applied
- BR-SHP-04, BR-ORD-09

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** consequence of UC-205 (release) under first-accept assignment — contrast with UC-411, where the session dies but the job stays.

## Permissions / Data / External Dependencies
- **Permissions:** assignee-only code entry; the server enforces ownership (BR-ORD-09) regardless of the disabled control.
- **Data involved:** assignment (`courier_id`, `version`), code attempt counters (untouched), screen state.
- **External dependencies:** job state feed; assignment-change notifications (B10).

## Acceptance Criteria
- **AC-UC400-01:** Given an open CodeEntry screen for a released job, when the state refreshes, then input is disabled and a return-to-queue action is offered.
- **AC-UC400-02:** Given a code submitted for a job reassigned away, when the server processes it, then it is rejected and `code_attempts` does not increase.
- **AC-UC400-03:** Given the same courier accepts the job again, when the screen reopens, then code entry is enabled for the new assignment (BR-SHP-04).
- **AC-UC400-04:** Given a job still assigned to this courier, when the screen refreshes, then code entry remains enabled.
