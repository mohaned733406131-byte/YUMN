# UC-414 — Escalate a Failed Return Pickup to Operations

## Header Info
- **Use Case ID:** UC-414
- **Title:** Escalate a Failed Return Pickup to Operations
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier cannot complete a return pickup or vendor handover (store closed, customer absent, package not ready, refusal)
- **Priority:** P2
- **Goal:** Hand a stuck return to operations with evidence, leaving the return in a legal state instead of an invented one.
- **Preconditions:** Return `RETURN_APPROVED` (or `RETURN_RECEIVED`) with an assigned return shipment; ops queue reachable (FR-020).

## Main Scenario
1. Courier arrives and the counterpart is unavailable → the courier records the failure against the return shipment with a reason.
2. A pickup-side attempt row is written with outcome `PICKUP_FAILED`, courier identity and timestamp.
3. The return remains `RETURN_APPROVED` pending operations handling — WF-007 explicitly leaves failed pickups there.
4. Courier escalates to operations: a ticket is raised carrying the return id, reason and timestamp (FR-020), filed from the courier support entry (UC-210).
5. Operations picks the case from the admin return queue (`GET /admin/returns`, API-RET-010) and decides to reschedule, reassign or resolve.

## Alternative Scenarios
- **A1 — Transient absence:** the courier retries the visit first; escalation follows only after the attempt fails.
- **A2 — Vendor refuses receipt:** the same escalation path records the refusal reason and inspection never starts.
- **A3 — Admin resolves the case:** the return re-enters the normal pickup and receipt flow (UC-413).

## Exception Scenarios
- **E1 — Escalation submission fails:** no partial ticket exists; the courier retries with the same payload.
- **E2 — State changed meanwhile (customer cancelled, dispute opened):** the escalation attaches to the current state or is refused as stale.
- **E3 — Notification to operations unavailable:** the ticket still exists in the admin queue — escalation does not depend on a single channel.

## Postconditions
- Success: an operations-visible ticket exists and the return stays in a legal state awaiting ops (no new state invented, BR-RET-02).
- Failure: no ticket and no state change; the courier can retry the escalation.

## Business Rules Applied
- BR-RET-02, BR-ORD-03

## Related Requirements
- FR-016 (Returns & Refunds)
- FR-020 (Platform Administration, Settings & Audit)
- **Related:** WF-007 Exceptions — the operations-handling branch for failed return pickups.

## Permissions / Data / External Dependencies
- **Permissions:** courier records own return attempts and opens tickets; only Admin/Moderator act on the ops queue (FR-020 scope).
- **Data involved:** `return_request` state, `shipment_attempt` (`PICKUP_FAILED`), support ticket, return/order history.
- **External dependencies:** support ticketing (B13); admin return queue (API-RET-010); notification fan-out (B10).

## Acceptance Criteria
- **AC-UC414-01:** Given a return pickup that cannot complete, when the courier records it, then a `PICKUP_FAILED` attempt row exists with reason and timestamp.
- **AC-UC414-02:** Given the failed pickup, when the state is checked, then the return remains `RETURN_APPROVED` with no invented state (BR-RET-02).
- **AC-UC414-03:** Given the escalation, when operations opens the admin return queue, then the case is present with its reference (FR-020).
- **AC-UC414-04:** Given a duplicate escalation attempt, when it is retried, then no second ticket is created.
