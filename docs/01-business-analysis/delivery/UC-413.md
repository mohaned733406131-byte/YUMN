# UC-413 — Record Vendor Receipt of an Approved Return Package

## Header Info
- **Use Case ID:** UC-413
- **Title:** Record Vendor Receipt of an Approved Return Package
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier hands the collected return package back to the vendor's store
- **Priority:** P0
- **Goal:** Record custody transfer at the vendor so the return advances to `RETURN_RECEIVED` and the inspection clock can start.
- **Preconditions:** Return `RETURN_APPROVED` (API-RET-006); a `kind='RETURN'` shipment assigned to this courier; package in courier custody.

## Main Scenario
1. Approval schedules the return pickup through the delivery engine; a `kind='RETURN'` shipment is offered in the zone (BR-SHP-04, WF-007 step 4).
2. Courier accepts and collects the package from the customer — custody is courier identity plus timestamp, never GPS (C-16).
3. Courier delivers it to the vendor's store and confirms handover → the return advances `RETURN_APPROVED → RETURN_RECEIVED` (BR-RET-02, WF-007 step 5).
4. System records custody with courier identity and timestamp, appends history (BR-ORD-03) and notifies customer and vendor (BR-NTF-04).
5. The vendor's 72-hour inspection window starts on `RETURN_RECEIVED` (BR-RET-05) and the return becomes available for inspection (API-RET-009).

## Alternative Scenarios
- **A1 — Pickup never completed:** the flow never reaches receipt; the return stays `RETURN_APPROVED` and escalation belongs to UC-414.
- **A2 — Vendor refuses the package:** receipt is not recorded; courier opens the failed-receipt path (UC-414) with the state unchanged.
- **A3 — Customer absent at pickup:** the pickup retries; receipt is impossible until the package is in courier custody.

## Exception Scenarios
- **E1 — Concurrent state change (admin resolves, dispute opens):** the guarded transition returns a conflict; receipt is never double-applied (DOC-SA-010 §5).
- **E2 — Duplicate confirmation:** idempotent — first success wins and the repeat returns the same `RETURN_RECEIVED`.
- **E3 — Notification failure:** the receipt still commits; parties read status from their own scoped views.

## Postconditions
- Success: return is `RETURN_RECEIVED`, custody is logged with courier identity and timestamp, and the 72-hour inspection clock is running (BR-RET-05).
- Failure: state stays `RETURN_APPROVED` with no custody row and no inspection clock — nothing half-written.

## Business Rules Applied
- BR-RET-02, BR-RET-05, BR-SHP-04, BR-ORD-03

## Related Requirements
- FR-016 (Returns & Refunds)
- **Related:** WF-007 step 5 — the courier-side custody handover inside the return workflow.

## Permissions / Data / External Dependencies
- **Permissions:** the assigned return courier records receipt for the own return shipment only; the vendor inspects afterwards (API-RET-009) and admin arbitrates.
- **Data involved:** `return_request` state, `kind='RETURN'` shipment, return/order history, inspection clock, notifications.
- **External dependencies:** delivery assignment offer queue (BR-SHP-04); notification fan-out (B10); refund engine downstream (B07).

## Acceptance Criteria
- **AC-UC413-01:** Given an approved return in courier custody, when handover at the vendor is confirmed, then state becomes `RETURN_RECEIVED` with courier identity and timestamp (BR-RET-02).
- **AC-UC413-02:** Given `RETURN_RECEIVED`, when the clock is checked, then the 72-hour inspection window is running (BR-RET-05).
- **AC-UC413-03:** Given a duplicate confirmation, when it is processed, then only one receipt transition occurs (idempotent).
- **AC-UC413-04:** Given a concurrent admin or dispute action, when receipt is submitted, then it applies once or returns a conflict — never a partial state.
