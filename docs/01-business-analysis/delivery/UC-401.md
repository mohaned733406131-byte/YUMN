# UC-401 — Recover from Delivery-Code Entry Rate Limiting

## Header Info
- **Use Case ID:** UC-401
- **Title:** Recover from Delivery-Code Entry Rate Limiting
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier submits the 6-digit code faster than the per-courier verification tier allows
- **Priority:** P2
- **Goal:** Recover cleanly from a transient 429 so the courier waits out the window instead of burning code attempts.
- **Preconditions:** Job `OUT_FOR_DELIVERY`; the stricter courier code limiter (5 submissions/minute) applies to `POST /deliveries/{id}/code` (SEC-REQ-009).

## Main Scenario
1. Courier submits the code; the per-courier limiter counts the call before verification runs.
2. The tier is exceeded → `429` and the client renders a countdown until entry is allowed again plus a support link (screen-states §4 rate-limited pattern).
3. Rate limiting is transport-level: it consumes no `BR-SHP-03` code attempt and applies no confirmation lock.
4. When the countdown ends the courier resubmits; a correct code verifies and the delivery reaches `DELIVERED` (BR-SHP-02).
5. Refused calls are logged for abuse detection only — no attempt row, counter or state change is written.

## Alternative Scenarios
- **A1 — Ordinary wrong code (not rate limited):** attempts remaining 2 then 1 are shown and one attempt is consumed (BR-SHP-03).
- **A2 — 24 h lock already active:** submissions return `CODE_LOCKED` regardless of the limiter; the lock countdown is authoritative (BR-SHP-03).
- **A3 — Correct code inside the tier:** verification succeeds on the first allowed call; the limiter is never visible.

## Exception Scenarios
- **E1 — Retry before the countdown ends:** another `429`; the window restarts and no attempt is consumed.
- **E2 — Limiter still refusing after the window:** the support link opens a ticket (UC-210) so the job is not stranded.
- **E3 — Outcome unknown (timeout):** courier re-reads job state before retrying; no blind resubmissions.

## Postconditions
- Success: courier resumes verification after the window; attempt and lock counters were never touched by the rate limiting.
- Failure: state, `code_attempts` and `code_locked_until` are exactly as they were before the refused calls.

## Business Rules Applied
- BR-SHP-03, BR-SHP-02

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** transient sibling of UC-403 (frozen for review) and UC-418 (waiting without consuming attempts).

## Permissions / Data / External Dependencies
- **Permissions:** every assignee courier is subject to the same per-courier tier (SEC-REQ-009).
- **Data involved:** rate-limit counters (per courier), code attempt fields (unchanged), support ticket if raised.
- **External dependencies:** Redis-backed limiter (DEP-03); support ticketing (B13).

## Acceptance Criteria
- **AC-UC401-01:** Given five code submissions in one minute, when a sixth is sent, then `429` with a countdown is returned and `code_attempts` is unchanged (SEC-REQ-009, BR-SHP-03).
- **AC-UC401-02:** Given the countdown has elapsed, when a correct code is submitted, then verification succeeds and the state becomes `DELIVERED` (BR-SHP-02).
- **AC-UC401-03:** Given a rate-limited response, when the UI renders it, then a countdown and a support link are shown.
- **AC-UC401-04:** Given an active 24-hour lock, when any code is submitted, then `CODE_LOCKED` is returned independently of the rate window (BR-SHP-03).
