# UC-403 — Work a Delivery Whose Attempts Are Frozen for Admin Review

## Header Info
- **Use Case ID:** UC-403
- **Title:** Work a Delivery Whose Attempts Are Frozen for Admin Review
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** The third failed attempt escalates the delivery and further attempts are refused
- **Priority:** P1
- **Goal:** Let the courier understand, read and work around the frozen state instead of hammering a blocked endpoint.
- **Preconditions:** Delivery carries three recorded failures; escalation to admin review exists with the full timeline (BR-SHP-06).

## Main Scenario
1. After the third failed delivery attempt the system escalates to admin review; further attempts return `DELIVERY_ATTEMPTS_EXCEEDED`.
2. Courier opens the job → API-SHP-003 shows the attempt log, the escalation notice and the auto-created support ticket reference (BR-SHP-03, BR-SHP-06).
3. The courier cannot record further failed attempts or push the delivery; the job stays in its current state pending admin intervention.
4. Courier reads the timeline, adds context to the auto-created ticket (UC-210) and moves on to other jobs.
5. Admin reviews on the dispatch side and either clears the block or reassigns; the courier sees the block lifted on the next refresh.

## Alternative Scenarios
- **A1 — 24-hour code lock also active:** the lock countdown is displayed alongside the escalation; both must clear (BR-SHP-03, BR-SHP-06).
- **A2 — Admin resolves quickly:** the block clears and the normal attempt flow resumes on refresh.
- **A3 — Job reassigned during review:** it leaves the courier's Active list; the courier keeps read-only history (BR-ORD-09).

## Exception Scenarios
- **E1 — Courier forces a submission:** refused with `DELIVERY_ATTEMPTS_EXCEEDED`; no state or counter changes.
- **E2 — State changed concurrently (delivered or cancelled by admin):** refresh shows the new state and the banner disappears.
- **E3 — Ticket reference unreadable (network error):** the block message still renders from the error code; the courier retries the read.

## Postconditions
- Success: courier continues other work with a readable block and a trackable ticket reference.
- Failure: no attempt bypasses the escalation; reading changes neither state nor counters.

## Business Rules Applied
- BR-SHP-06, BR-SHP-03, BR-ORD-09

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** successor state of UC-029 (third attempt recorded) and UC-397 (attempt log reviewed beforehand).

## Permissions / Data / External Dependencies
- **Permissions:** assigned courier reads the own blocked job; only Admin can lift the escalation (B13 dispatch).
- **Data involved:** `shipment_attempt` rows, `failed_attempt_count`, escalation record, auto-created support ticket.
- **External dependencies:** support ticketing (B13); admin notification fan-out (B10).

## Acceptance Criteria
- **AC-UC403-01:** Given three recorded failures, when the courier tries to record another, then `DELIVERY_ATTEMPTS_EXCEEDED` is returned and the counter stays at 3 (BR-SHP-06).
- **AC-UC403-02:** Given an escalated job, when the detail is opened, then the escalation notice and the auto-ticket reference are visible.
- **AC-UC403-03:** Given admin intervention clearing the block, when the courier refreshes, then attempts are accepted again.
- **AC-UC403-04:** Given a job not assigned to the courier, when opened, then it is not found and no escalation detail is exposed (BR-ORD-09).
