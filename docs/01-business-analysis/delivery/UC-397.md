# UC-397 — Review the Shipment Attempt Log Before a Retry

## Header Info
- **Use Case ID:** UC-397
- **Title:** Review the Shipment Attempt Log Before a Retry
- **Actor:** Delivery Provider (ACT-03)
- **Trigger:** Courier reopens a job that previously failed and must decide whether to try again now
- **Priority:** P1
- **Goal:** Read the authoritative attempt history and escalation position so the retry decision is informed, not guessed.
- **Preconditions:** Job assigned to this courier; at least one attempt may exist in `b08.shipment_attempt`; delivery detail endpoint reachable.

## Main Scenario
1. Courier opens the job detail → `GET /deliveries/{id}` (API-SHP-003) returns `attempts: [{ at, outcome, reason? }]`, current state and code status.
2. Courier reads each recorded attempt (`DELIVERY_FAILED`, `CODE_FAILED`, `PICKUP_FAILED`) with courier identity, timestamp and reason — the log is append-only evidence (BR-ORD-03).
3. The response carries the escalation position (`remainingBeforeEscalation`) so the courier knows how many failures remain before admin review (BR-SHP-06).
4. Courier decides: retry now (UC-029 record-failed-attempt, UC-030 code entry) or hand the job back to transit and wait (UC-418).
5. Nothing is written by this use case — it is a read that informs the next action.

## Alternative Scenarios
- **A1 — First visit, no attempts yet:** empty attempt list and zero counter; the courier proceeds with the normal flow.
- **A2 — Already escalated:** the log shows the third failure and its escalation record; further attempts are refused until an admin intervenes (BR-SHP-06).
- **A3 — Mixed history:** code failures and courier-recorded failures appear side by side; only recorded failures drive the escalation threshold.

## Exception Scenarios
- **E1 — Foreign or unassigned job:** request returns `NOT_FOUND` (visibility scoping, BR-ORD-09); no attempt data leaks.
- **E2 — New attempt appended while reading:** courier refreshes to see the latest entry — the log is never overwritten (BR-ORD-03).
- **E3 — Detail fetch fails:** page/block error with retry; the courier does not act on counters the client cannot prove (screen-states §4).

## Postconditions
- Success: courier holds an accurate server-side view of attempts, code lock state and escalation position.
- Failure: nothing written — counters, lock and shipment state are untouched.

## Business Rules Applied
- BR-SHP-06, BR-ORD-03, BR-ORD-09

## Related Requirements
- FR-015 (Shipping & Delivery)
- **Related:** read-only companion of UC-029 (records the failed attempt); UC-403 covers the frozen post-escalation state.

## Permissions / Data / External Dependencies
- **Permissions:** assignee courier reads own delivery only; Admin sees the same log on the dispatch view (BR-ORD-09).
- **Data involved:** `shipment_attempt` rows, `failed_attempt_count`, `code_attempts`, `code_locked_until` (all read).
- **External dependencies:** delivery API only; no location data is requested or stored (C-16).

## Acceptance Criteria
- **AC-UC397-01:** Given a job with recorded failures, when the detail is opened, then every attempt appears with time, outcome and reason (BR-ORD-03).
- **AC-UC397-02:** Given two recorded failures, when the log is read, then remaining-before-escalation is reported as 1 (BR-SHP-06).
- **AC-UC397-03:** Given a job not assigned to the courier, when detail is requested, then it returns not-found with no attempt data (BR-ORD-09).
- **AC-UC397-04:** Given the log is read, when the shipment state is checked afterwards, then no counter or state changed.
