# Validation — DTOs, Business Validation, Idempotency & Payload Limits

Validation happens in **two distinct layers**: *schema validation* at the controller boundary (class-validator DTOs + global `ValidationPipe`) and *business validation* inside services/domain (rules, state, funds, limits). Schema validation rejects malformed input; business validation rejects well-formed but illegal input. Both are server-side; clients mirror schemas for UX only (`../../05-frontend/core/forms-and-validation.md`).

---

## 1. Schema Validation (Controller Boundary)

| Aspect | Decision |
|---|---|
| Library | **class-validator** DTOs + NestJS global `ValidationPipe` (matches NestJS 10 stack) |
| Pipe config | `whitelist: true` (strip unknown properties), `forbidNonWhitelisted: true` in non-prod+prod for write endpoints, `transform: true`, `validateError` → `VALIDATION_ERROR` |
| Placement | every `@Body`, `@Query`, `@Param` typed with a DTO class; controllers never accept `any` |
| Output | `400 VALIDATION_ERROR` with `fields: { fieldName: errorCode }` (error model, `DOC-BE-008` §2) |
| Shared constraints | `shared/validation` — phone regex, integer-money, locale enum, cursor format |
| Error mapping | class-validator violations → stable field codes (not English messages) for i18n |

### Canonical DTO constraints (mirrors)

| DTO field | Constraint | Rule source |
|---|---|---|
| `phone` | `Matches(/^7\d{8}$/)` | BR-AUTH-01 |
| `password` | `MinLength(8)` + complexity custom validator | BR-AUTH-02 |
| `otpCode` | `Length(6)`, digits only | BR-AUTH-03 |
| `amountYER` | `@IsInt()`, min/max per operation | BR-PAY-02, C-14 |
| `quantity` | `@IsInt()`, min 1 (max via business layer) | BR-CRT-01, C-15 |
| `priceYER` | `@IsInt()`, `Min(1)` | BR-CAT-04 |
| `rating` | `@IsInt()` 1–5 | BR-REV-03 |
| `deliveryCode` | `Length(6)` digits | BR-SHP-02, C-16 |
| `couponCode` | string, normalized upper-case trim | BR-PRM-01 |
| `locale` | enum `ar` \| `en` only | C-24 |

## 2. Business Validation (Service / Domain)

| Check type | Lives in | Examples |
|---|---|---|
| Uniqueness | service (DB constraint is the backstop) | phone unique (BR-AUTH-01), SKU per store (BR-CAT-02) |
| Limits | service/domain | cart ≤50/≤10/≤5 (C-15), addresses ≤10 (FR-003), top-up bounds (BR-PAY-02) |
| Money sufficiency | domain inside transaction | wallet ≥ order total, no negative (BR-PAY-05, BR-CRT-06) |
| Stock | domain (atomic) | reserve/deduct guards (BR-CAT-07, C-13) |
| State | domain state machine | legal transition else `409 STATE_CONFLICT` (C-09) |
| Policy/window | domain | return window (BR-RET-01), review window (BR-REV-01), cancel window (BR-ORD-04) |
| Ownership | repository/service scope | DATA-REQ-008, BR-VND-07 |
| Eligibility | service | KYC approved before publish (BR-VND-01), coupon validity (BR-PRM-04) |

**Split rule:** if the rule needs DB state or another entity, it is *business* validation (service/domain); if it is purely syntactic, it is *schema* validation (DTO). Nothing belongs to both — DTOs never query the database.

## 3. Validation Failure Semantics

| Failure | Response | Never |
|---|---|---|
| Schema violation | `400 VALIDATION_ERROR` + field map | create any row |
| Business rule violation | domain code (`STOCK_UNAVAILABLE`, `LIMIT_EXCEEDED`, `COUPON_INVALID`, `RETURN_WINDOW_CLOSED`, …) | partially apply (transactions roll back) |
| Coupon invalid | `COUPON_INVALID` **before** order row creation | BR-PRM-06: no order row on invalid coupon |
| Unknown fields | rejected (`forbidNonWhitelisted`) | silently accept tampered payloads |
| Multiple failures | full field map returned at once (better UX) | stop at first error |

## 4. Payload & Upload Limits

| Limit | Value | Enforcement |
|---|---|---|
| JSON body | ≤ 1 MB standard endpoints | NestJS body parser + reverse proxy |
| Multipart file | ≤ 5 MB per image (`SEC-REQ-011`, `BR-CAT-08`) | multer limits → `413` |
| Images per product | ≤ 10 | business validation (BR-CAT-08) |
| Images per review | ≤ 5 | business validation (BR-REV-03) |
| Allowed image types | jpg/png/webp only; **no SVG execution** (`SEC-REQ-011`) | MIME sniffing + extension allow-list |
| EXIF | stripped on upload | processing pipeline (BR-CAT-08) |
| Array depth (variants) | ≤5 dimensions, ≤50 combinations | DTO + business check (BR-CAT-02) |
| String lengths | per-field `MaxLength` in DTO (names, addresses, reasons) | DTO |
| Batch/export sizes | paginated; export size capped, generated by job | `DOC-BE-006` §1 |

Malware scanning of uploads happens in the storage pipeline (`SEC-REQ-011`, `09-security/` details) — validation here only gates type/size/structure.

## 5. Idempotency-Key Handling (BR-PAY-08, BR-PLT-03)

| Aspect | Implementation |
|---|---|
| Mandatory for | payment, order creation, stock reservation, coupon application, refund (BR-PLT-03) |
| Transport | `Idempotency-Key` header (UUIDv4) on POST/PUT money/order endpoints |
| Storage | Redis `idem:{key}` → request hash + response snapshot, TTL 24 h (`shared/idempotency`, `DOC-BE-007` §1) |
| First request | claims key via `SET NX`; executes; stores response (status + body) |
| Replay (same key + same hash) | return stored response **verbatim** — no re-execution |
| Same key + different hash | `409 IDEMPOTENCY_KEY_CONFLICT` |
| Concurrent same key | second caller waits on lock or receives `409` retry hint — never double-executes |
| Failure handling | non-2xx not cached (client may retry); 5xx not cached but execution side effects guarded by business idempotency (ledger unique constraints) |
| DB backstop | unique constraints (e.g. `idempotency_key` on orders, ledger reference uniqueness) — Redis loss cannot cause double spend (`NFR-008`) |

## 6. Money Typing & Decimal Handling

| Rule | Implementation | Source |
|---|---|---|
| Store/transport as **integer YER** | DTO fields `*YER: number` validated `@IsInt()`; DB columns `BIGINT` | BR-PAY-10 |
| No floats for money | ESLint rule bans arithmetic on `*YER` with non-integer literals; no `parseFloat` on money | BR-PAY-10 |
| No decimal places | input masks strip separators client-side; server rejects non-integers | BR-PAY-10 |
| VAT math | `vat = roundHalfUp((subtotal − discount) × 15 / 100)` in integer space | BR-FIN-01 |
| Rounding | half-up to whole YER **per sub-order**; residual → platform rounding account | BR-FIN-05 |
| Percentages (commission/coupons) | basis points (integers) internally: 1000 bp = 10% | BR-ESC-03, BR-PRM-01 |
| Display formatting | client-side only (`Intl.NumberFormat`), never re-sent | 05 frontend docs |
| Cross-checks | reconciliation job verifies Σ ledger = 0 at all times | BR-ESC-08, DATA-REQ-006 |

## 7. Validation Testing

| Level | Cases |
|---|---|
| Unit (`NFR-010`) | every DTO constraint; business validators with fakes (no network) |
| Golden fixtures | shared payload sets rejected identically by client Zod and server DTO (`../../05-frontend/core/forms-and-validation.md` §7) |
| Boundary | 499/500 and 5,000,000/5,000,001 YER (C-14); 1,000/999 top-up (BR-PAY-02); 50/51 products, 10/11 units, 5/6 vendors (C-15) |
| Idempotency | concurrent double-submit produces one order (BR-ORD-06) |
| Security | oversized body → 413; SVG upload rejected; unknown field rejected (SEC-REQ-008/011) |
