# FR-011 — Checkout & Order Placement

**Block:** B05 Cart & Checkout · **Priority:** Critical · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-011 runs the seven-step checkout — cart revalidation, address, shipping, wallet payment, review, confirm, confirmation — following the canonical sequence address → shipping → wallet payment → review → confirm (`DOC-REQ-001` §1). It enforces order bounds (500–5,000,000 YER), wallet-only payment, server-side totals (items − discount + VAT + shipping, half-up rounding per sub-order), one coupon per order, idempotent order creation, and the master/sub-order split (one master per checkout, one sub-order per vendor).

## Rationale

- Traces `OBJ-01` (block B05), `OBJ-02` (100% of orders paid from wallet, escrow funded at placement) and `OBJ-12` (`C-01`, `C-10`, `C-13`, `C-14` validation tests).
- Idempotency and the saga design (`BR-ORD-06`, `BR-PLT-03`, `BR-PLT-04`) exist because order creation spans stock, wallet, escrow and notifications — a partial failure must never double-charge or lose an order (`NFR-008`).
- Master/sub splitting at this point is what makes per-vendor fulfillment, commission and payout (`FR-014`, `FR-015`) possible.

## Requirements Detail

- Seven-step guided session: (1) cart revalidation/reservation, (2) address, (3) shipping method/fee, (4) wallet payment, (5) review, (6) confirm, (7) order confirmation — canonical order address → shipping → wallet payment → review → confirm.
- Order value bounds: minimum 500 YER, maximum 5,000,000 YER; both boundaries rejected with clear errors (`C-14`).
- Wallet-only payment: any other method rejected with `PAYMENT_METHOD_NOT_ALLOWED` (`BR-PAY-01`, `C-01`, `C-02`, `C-03`).
- Wallet balance must be ≥ order total at confirmation (`BR-CRT-06`); debit is atomic and never drives balance negative (`BR-PAY-05`).
- Server-side totals: sub-order = (items − item discount) + VAT + shipping; master total = Σ sub-order totals (`BR-FIN-02`, `BR-ORD-02`).
- VAT = 15% × (subtotal − coupon discount); shipping is not taxed (`BR-FIN-01`).
- Rounding half-up to whole YER per sub-order; differences post to the platform rounding account (`BR-FIN-05`).
- Coupon: exactly one per order (`BR-PRM-02`), validated before any order row exists; invalid → error, no order created (`BR-PRM-06`).
- Idempotency key required on order creation; duplicate submissions return the original order (`BR-ORD-06`, `BR-PLT-03`).
- Stock reserved for 15 minutes from cart activity; released on expiry (`C-13`, FR-005).
- Ineligible cart items block checkout until removed (`BR-CRT-05`); price changes require re-confirmation (`BR-CRT-04`).
- Payment posts balanced double-entry ledger rows (`BR-PAY-06`); multi-step creation runs as a saga with compensating actions (`BR-PLT-04`).
- On successful payment the master order enters PLACED with escrow funded, and one sub-order per vendor is created (`BR-ORD-02`, `C-10`).
- Order summary breakdown displayed ar-YE formatted with Arabic-Indic numerals (`BR-PAY-10`, `C-24`).

## Preconditions

- An authenticated customer with a valid cart (FR-010), a chosen address (≤10, FR-003) and wallet balance ≥ total (FR-013).
- Shipping zone/method resolvable for the address (FR-015) and products active with reserved stock (FR-004/FR-005).
- Coupon (if any) is valid: active, in window ≤ 90 days, usage remaining, discount ≤ 90% (FR-019).

## Expected Result

A valid checkout produces exactly one master order plus one sub-order per vendor, debits the wallet once, funds escrow, locks stock and emits PLACED — deterministically under retries and duplicates — while every invalid input (bounds, method, balance, coupon, price change) stops before any order row exists.

## Acceptance Criteria

- **AC-FR011-01** — Given an order total of 499 YER, when confirm is attempted, then validation rejects it (minimum 500 YER, `C-14`).
- **AC-FR011-02** — Given a duplicate confirm with the same idempotency key, when processed, then the original order is returned with no second order or wallet debit.
- **AC-FR011-03** — Given insufficient wallet balance at confirmation, when processed, then no order is created and no ledger entry posts.
- **AC-FR011-04** — Given a cart spanning 3 vendors, when the order is placed, then 1 master + 3 sub-orders exist and the master total equals the sum of sub-order totals.
- **AC-FR011-05** — Given `payment_method != wallet` (COD, card, anything), when order creation is processed, then `PAYMENT_METHOD_NOT_ALLOWED` is returned and no order row exists (`C-01`, `BR-PAY-01`).

## Business Rules Applied

- `BR-ORD-02` master/sub structure; `BR-ORD-06` idempotency key; `BR-PAY-01` wallet-only; `BR-PAY-05` never-negative balance.
- `BR-CRT-04`/`BR-CRT-05`/`BR-CRT-06` re-confirmation, eligibility and balance gates; `BR-PRM-02`/`BR-PRM-06` single valid coupon.
- `BR-FIN-01`/`BR-FIN-02`/`BR-FIN-05` VAT, sub-order math and rounding; `BR-PLT-03`/`BR-PLT-04` idempotency and ACID saga.

## Constraints Honored

- `C-01`, `C-02`, `C-03` wallet-only — no COD, cards or credit anywhere in the flow.
- `C-10` one master order per checkout, one sub-order per vendor.
- `C-13` 15-minute stock reservation before payment.
- `C-14` 500–5,000,000 YER order bounds.

## Dependencies

- **FR:** FR-010 (cart input), FR-012 (resulting lifecycle), FR-013 (payment), FR-015 (shipping fee), FR-019 (coupon), FR-017 (order confirmations).
- **NFR/SEC:** NFR-008, SEC-REQ-009 (rate limiting on order creation), NFR-001.

## Verification Method

- Boundary tests at 500 and 5,000,000 YER and one unit outside each; negative tests for non-wallet methods.
- Idempotency/concurrency tests: double-submit, network retry, saga compensation after simulated failure at each step.
- Math unit tests for VAT/rounding/master-total; E2E checkout happy path in ar and en.

## Out of Scope Notes

- COD, cards, BNPL, crypto and multi-currency (`C-01`–`C-04`); split/partial payments and payment plans.
- Guest checkout without an account, scheduled delivery slots, and post-placement order editing (see FR-012).
- Gift cards, store credit instruments and loyalty redemption (`GAP-04`, FUTURE SCOPE).
