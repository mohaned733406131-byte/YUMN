# FR-013 — Wallet & Payment Processing

**Block:** B07 Payment & Wallet · **Priority:** Critical · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-013 is the money core: a YER-only per-user wallet with balance view and transaction history, top-ups via m-Floos/OneCash (credited only on verified provider callback or reconciled poll) and bank transfer (credited only after admin verification), wallet-only order payment with never-negative atomic debits, double-entry append-only ledger postings for every balance change, refunds credited strictly to the wallet, idempotent money operations, and admin wallet freezes.

## Rationale

- Traces `OBJ-02` (trust-safe payments: 100% wallet-funded, zero ledger imbalance) and `OBJ-12` (`C-01`–`C-05` payment constraint tests).
- The escrow model (`C-12`) is only credible if funds are pre-funded and ledgered — this requirement is the precondition of `FR-014` and of `DEP-10`'s closed-loop wallet rationale.
- Callback-only crediting (`BR-PAY-03`) and admin-verified bank transfers (`BR-PAY-04`) close the classic "client claims payment" fraud hole.

## Requirements Detail

- One wallet per user holding integer YER amounts; display formatted for `ar-YE` with Arabic-Indic numerals (`BR-PAY-10`, `C-04`).
- Top-up bounds: minimum 1,000 YER, maximum 5,000,000 YER per transaction (`BR-PAY-02`).
- m-Floos/OneCash: initiate → callback/poll → credit only after verified provider response, never on client claim (`BR-PAY-03`, `INT-REQ-001`).
- Bank transfer: credit only after admin verification of the payment reference (`BR-PAY-04`, `INT-REQ-002`, FR-020).
- Order payment accepts only the wallet; other methods return `PAYMENT_METHOD_NOT_ALLOWED` (`BR-PAY-01`, `C-01`).
- Balance never goes negative; payment uses row-level locking with an atomic balance check (`BR-PAY-05`).
- Every balance change posts balanced double-entry ledger rows (debit + credit); the ledger is append-only — corrections are compensating entries (`BR-PAY-06`, `DATA-REQ-007`).
- Refunds always credit the wallet — never external cash-out to cards/banks for customers (`BR-PAY-07`, `C-01`).
- Payments, top-ups and refunds are idempotent via idempotency keys (`BR-PAY-08`, `BR-PLT-03`).
- Admin can freeze a wallet: frozen wallets cannot pay or top up but still receive refunds (`BR-PAY-09`, FR-020).
- Provider reconciliation job matches ledger/wallet totals against provider statements and alerts on mismatch (`BR-ESC-08`, `BR-FIN-03`).
- Customer-visible transaction history lists every credit/debit with type, reference and timestamp, scoped to the owner (`DATA-REQ-008`).
- Stricter rate limits apply to top-up and payment endpoints (`SEC-REQ-009`); no card/BNPL/crypto fields or endpoints exist (`C-02`, `C-03`).

## Preconditions

- User account exists (FR-001) with a wallet row created at registration.
- Provider credentials/sandbox available for m-Floos/OneCash (`DEP-05`); admin queue available for bank-transfer verification (FR-020).
- Order exists with a wallet balance ≥ total for payment (FR-011); wallet not frozen (`BR-PAY-09`).

## Expected Result

Money enters only through verified channels, leaves only to approved order payments/refunds, and is always reflected by balanced ledger postings: balances are exact and never negative, replays produce no double effects, and every operator can reconcile wallet totals against provider statements daily.

## Acceptance Criteria

- **AC-FR013-01** — Given a top-up request of 999 YER, when submitted, then it is rejected (minimum 1,000 YER, `BR-PAY-02`).
- **AC-FR013-02** — Given a replayed m-Floos callback for an already-credited transaction, when processed, then the wallet is credited exactly once.
- **AC-FR013-03** — Given a balance of 10,000 YER and a 12,000 YER payment, when attempted, then the payment fails and the balance remains 10,000 YER.
- **AC-FR013-04** — Given an order submission with a non-wallet payment method, when processed, then `PAYMENT_METHOD_NOT_ALLOWED` is returned and no ledger entry posts.
- **AC-FR013-05** — Given any successful balance change (top-up, payment, refund, freeze effect), when the ledger is inspected, then balanced debit + credit rows exist in one ACID transaction and are append-only (`BR-PAY-06`, `DATA-REQ-007`).

## Business Rules Applied

- `BR-PAY-01` wallet-only; `BR-PAY-02` top-up bounds; `BR-PAY-03` callback-verified credit; `BR-PAY-04` admin-verified bank transfer.
- `BR-PAY-05` never-negative atomic debit; `BR-PAY-06` balanced double-entry append-only ledger; `BR-PAY-07` refunds to wallet.
- `BR-PAY-08` idempotent money ops; `BR-PAY-09` wallet freeze; `BR-PAY-10` integer YER + `ar-YE` formatting.

## Constraints Honored

- `C-01` wallet-only payments; `C-02` no card processing; `C-03` no BNPL/credit; `C-04` YER only, no crypto/multi-currency; `C-05` top-up methods limited to m-Floos, OneCash and bank transfer.

## Dependencies

- **FR:** FR-011 (order payment), FR-014 (escrow/payout interplay), FR-016 (refunds), FR-020 (verification/freeze console).
- **NFR/SEC/DATA/INT:** NFR-008, SEC-REQ-006, SEC-REQ-009, DATA-REQ-007, DATA-REQ-008, INT-REQ-001, INT-REQ-002, INT-REQ-006, INT-REQ-008.
- **DEP:** DEP-05 (provider merchant APIs — production blocker), DEP-10 (regulatory position on closed-loop wallets), DEP-02, DEP-03.

## Verification Method

- Integration tests per top-up method (success, timeout, replay, wrong amount) and negative tests for prohibited methods/amounts.
- Ledger invariants: Σ debits == Σ credits under randomized operation sequences; append-only enforcement (no UPDATE/DELETE).
- Concurrency tests on balance debit; reconciliation test against fixture provider statements; rate-limit tests (`SEC-REQ-009`).

## Out of Scope Notes

- Card payments, COD, BNPL/installments, cryptocurrency and non-YER wallets (`C-01`–`C-04`).
- Customer cash-out to bank/cards (`BR-PAY-07`); vendor payout execution mechanics live in FR-014 (`GAP-06` for vendor cash-out).
- Interest/yield on balances, payment plans, stored-value gift cards and third-party payment pages.
