# FR-017 — Notifications & Messaging

**Block:** B10 Notifications · **Priority:** High · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-017 fans transactional and marketing messages across four channels — SMS, WhatsApp, in-app and push (no email in v1) — using bilingual templates (Arabic default, English parity) that follow the user's locale, per-channel preference opt-outs for marketing categories, mandatory delivery of security notifications (OTP, login, password change, lockout), SMS-primary OTP with automatic WhatsApp failover, an in-app notification center, and reliable background delivery via BullMQ with retries and a dead-letter queue.

## Rationale

- Traces `OBJ-01` (block B10), `OBJ-03` (localized messaging) and `OBJ-07` (delivery reliability — the 6-digit code must actually reach the buyer).
- `DEP-06` (SMS/WhatsApp contracts) is the Phase 0 gate; explicit failover (`BR-NTF-03`, `INT-REQ-003`) is what keeps registration and delivery flows alive during provider outages.
- Security notices that cannot be disabled (`BR-NTF-02`) protect lockout/OTP semantics from being nullified by user preference.

## Requirements Detail

- Channels: SMS, WhatsApp, in-app, push — email is not a channel in v1 (`BR-NTF-01`, `GAP-03`).
- Security notifications (OTP, login, password change, lockout) cannot be disabled by the user (`BR-NTF-02`).
- OTP delivery: SMS primary with automatic failover to WhatsApp on provider timeout/failure; delivery receipts logged (`BR-NTF-03`, `INT-REQ-003`).
- Every template exists in Arabic and English; language follows user locale with Arabic default (`BR-NTF-04`, `C-24`).
- Users may opt out of marketing/notification categories independently per channel (`BR-NTF-05`).
- WhatsApp templates are approval-gated Business API templates (`INT-REQ-004`).
- Event-driven fan-out from order, delivery, return, escrow/payout, KYC and store events (FR-007/012/014/015/016/008).
- In-app notification center with read/unread state, scoped per user (`DATA-REQ-008`).
- Push token registration/deregistration per device; notifications target only active tokens.
- Delivery runs on BullMQ queues `{block}.{entity}.{action}` with 3 retries + exponential backoff + DLQ, DLQ depth alerting (`BR-PLT-01`, `BR-PLT-02`, `C-20`).
- Rate limiting applies to notification-triggering endpoints (OTP/top-up) (`SEC-REQ-009`).
- Follower notifications for new products/offers respect store-follow state (`BR-VND-05`).

## Preconditions

- User exists with locale and channel preferences (FR-003); `DEP-06` SMS/WhatsApp providers configured (`INT-REQ-003`, `INT-REQ-004`).
- A triggering event has occurred (e.g., order state change in FR-012, code issuance in FR-015).
- Queue infrastructure (`DEP-03`) is running; templates are registered in ar/en.

## Expected Result

Each qualifying event produces the correct localized messages on the permitted channels — security messages always, marketing messages only when opted in — with retries, visible delivery receipts, an in-app record, and no email sent anywhere.

## Acceptance Criteria

- **AC-FR017-01** — Given a user who disabled all marketing channels, when an OTP is requested, then it is still delivered (security notices are mandatory).
- **AC-FR017-02** — Given an SMS provider timeout during OTP delivery, when the failover path runs, then WhatsApp delivery is attempted automatically.
- **AC-FR017-03** — Given a user with locale `en`, when an order update is sent, then the English template is used; Arabic is used for the default locale.
- **AC-FR017-04** — When notification records for any event are inspected, then only SMS/WhatsApp/in-app/push channels appear — never email.
- **AC-FR017-05** — Given a user opting out of marketing per channel, when a campaign notification is triggered, then the opted-out channel receives nothing while other channels/categories remain unaffected (`BR-NTF-05`).

## Business Rules Applied

- `BR-NTF-01` channel set (no email); `BR-NTF-02` mandatory security notices; `BR-NTF-03` OTP channel failover.
- `BR-NTF-04` bilingual templates; `BR-NTF-05` per-channel marketing opt-out.
- `BR-PLT-01`/`BR-PLT-02` queue naming, retries and DLQ.

## Constraints Honored

- `C-06` OTP verification via SMS or WhatsApp only.
- `C-24` Arabic-first bilingual templates and message text.

## Dependencies

- **FR:** FR-001 (OTP/security events), FR-007 (KYC decisions), FR-008 (follower alerts), FR-012/FR-015/FR-016 (order/delivery/return events), FR-019 (marketing content).
- **NFR/INT/SEC/DEP:** NFR-013, NFR-007 (degrade behavior), INT-REQ-003, INT-REQ-004, INT-REQ-008, SEC-REQ-009, DEP-06, DEP-12 (SIM-based OTP testing).

## Verification Method

- Integration tests: fan-out per event type and channel set; failover on simulated provider failure; opt-out enforcement matrix.
- Unit tests: template selection by locale, security-vs-marketing classification.
- Reliability tests: retry/backoff/DLQ behavior; E2E OTP on real SIMs (`DEP-12`); snapshot tests for ar/en template rendering.

## Out of Scope Notes

- Email as a notification channel (`GAP-03` pending product-owner confirmation; excluded in v1).
- AI chatbot / generative-AI support messaging — human ticketing only (project scope decision).
- Inbound two-way conversations, marketing automation journeys, SMS to non-Yemeni numbers and websocket real-time chat.
