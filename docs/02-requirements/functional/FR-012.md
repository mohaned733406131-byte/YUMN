# FR-012 — Order Lifecycle Management

**Block:** B06 Order Management · **Priority:** Critical · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-012 owns the order state machine: exactly the 17 canonical states from `03-system-analysis/state-transitions.md`, executed **per sub-order**, with guarded transitions (optimistic locking, `409 STATE_CONFLICT` on invalid moves), append-only status history (actor, timestamp, reason), master aggregation rules, and role-specific actions and timeline visibility for Customer, Vendor, Delivery Provider, Admin/Moderator and System.

## Rationale

- Traces `OBJ-01` (block B06), `OBJ-02` (escrow moves strictly with state) and `OBJ-12` (`C-09`, `C-10` constraint tests) — the 17-state vocabulary is shared across 4 surfaces.
- Append-only history (`BR-ORD-03`) is the audit substrate for disputes (`BR-RET-06`) and admin accountability (`OBJ-08`).
- Explicit cancellation and SLA rules (`BR-ORD-04`, `BR-ORD-10`) prevent silent order loss — a top trust risk in marketplace operations.

## Requirements Detail

- Exactly 17 states: PLACED, CONFIRMED, PROCESSING, READY_FOR_PICKUP, ASSIGNED, PICKED_UP, IN_TRANSIT, OUT_FOR_DELIVERY, DELIVERED, COMPLETED, CANCELLED, RETURN_REQUESTED, RETURN_APPROVED, RETURN_REJECTED, RETURN_RECEIVED, REFUNDED, DISPUTED — no others exist in code (`BR-ORD-01`, `C-09`).
- The machine runs per sub-order; the master enters PLACED on payment and reaches COMPLETED only when every sub-order is COMPLETED or REFUNDED (`BR-ORD-07`, `C-10`).
- Payment, escrow funding and the buyer timeline operate at master level; fulfillment, commission and payout at sub-order level (`C-10`).
- Every transition is append-only in `order_status_history` with actor, timestamp and reason; rows are never overwritten (`BR-ORD-03`).
- Customer may cancel only at PLACED or CONFIRMED; vendor/admin until READY_FOR_PICKUP; cancellation always triggers the wallet refund flow (`BR-ORD-04`).
- DISPUTED freezes escrow release for the affected sub-orders until admin resolution (`BR-ORD-05`).
- Order creation requires an idempotency key; duplicates return the original order (`BR-ORD-06`).
- DELIVERED is reachable only through successful 6-digit delivery-code verification (`BR-ORD-08`, `C-16`).
- Timeline visibility: buyer (own), vendor (own sub-orders), assigned courier (own delivery), admin/moderator (scoped) (`BR-ORD-09`).
- Orders not paid/completed within the 24-hour vendor SLA at CONFIRMED auto-escalate to admin review — never silent auto-cancel without notification (`BR-ORD-10`).
- Transitions are guarded inside the order transaction with optimistic locking on `version`; invalid transitions return `409 STATE_CONFLICT`.
- Forbidden: skipping states, returning from DELIVERED to pre-delivery states, editing history rows, REFUNDED without ledger entries (`state-transitions.md` §2).
- Customer/vendor/admin/courier action sets follow the canonical transition table (actor + guard per row).

## Preconditions

- FR-011 created a master order with sub-orders in PLACED and escrow funded.
- Actors are authenticated and authorized for the requested transition (FR-002).
- The canonical transition table in `03-system-analysis/state-transitions.md` is the only allowed-move source.

## Expected Result

Orders advance strictly along the documented paths with full, immutable history; illegal or concurrent transitions are refused deterministically; each actor sees only their slice of the timeline; and money movements (refund, escrow, completion) stay synchronized with state.

## Acceptance Criteria

- **AC-FR012-01** — Given the state enumeration in code, when enumerated, then exactly 17 states exist and no others (constraint test `TST-CON-09`).
- **AC-FR012-02** — Given an order in PLACED, when a transition to DELIVERED is attempted, then it is rejected with `409 STATE_CONFLICT` and history is unchanged.
- **AC-FR012-03** — Given an order in READY_FOR_PICKUP, when the customer attempts cancellation, then it is denied per `BR-ORD-04`.
- **AC-FR012-04** — Given all sub-orders are COMPLETED or REFUNDED, when the master is evaluated, then the master becomes COMPLETED.
- **AC-FR012-05** — Given any state change by any actor, when the order history is queried, then `order_status_history` is append-only with actor, timestamp and reason — states are never overwritten (`BR-ORD-03`).

## Business Rules Applied

- `BR-ORD-01`…`BR-ORD-10` (17 states, master/sub, append-only history, cancel window, dispute freeze, idempotency, sub-order independence, code-gated DELIVERED, timeline visibility, 24-hour escalation SLA).

## Constraints Honored

- `C-09` exactly 17 canonical states.
- `C-10` master/sub-order architecture with level-specific responsibilities.
- `C-16` DELIVERED only via 6-digit code verification.

## Dependencies

- **FR:** FR-011 (creation), FR-013 (payment/refund), FR-014 (escrow release), FR-015 (delivery transitions), FR-016 (return transitions), FR-017 (state notifications), FR-020 (overrides/disputes).
- **NFR/DATA:** NFR-008, DATA-REQ-001, DATA-REQ-006.

## Verification Method

- State-machine unit tests: ≥1 test per row of the canonical transition table plus forbidden-transition negatives.
- Integration/E2E: full happy path PLACED → COMPLETED; cancel path; dispute path; return path.
- Constraint tests: `TST-CON-09` (state count == 17) and concurrency tests for optimistic locking/duplicate code entry.

## Out of Scope Notes

- Adding, renaming or removing states — any change requires updating `state-transitions.md` and `C-09` via change management.
- Editing or amending an order after placement (line items, address changes) — not specified in v1.
- Partial shipment/split fulfillment within one sub-order, backorders and scheduled/recurring orders.
