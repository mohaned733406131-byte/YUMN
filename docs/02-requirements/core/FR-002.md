# FR-002 — Roles, Permissions & Access Control

**Block:** B01 Identity & Access · **Priority:** Critical · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-002 defines a single role-based access control model for the seven canonical actors (Customer, Vendor, Delivery Provider, Admin, Super Admin, Moderator, System) and enforces it **server-side on every endpoint**, together with resource-ownership checks (wallet, orders, store/products, deliveries, audit logs). Vendor staff hold Viewer/Editor/Manager roles under an Owner; front-end route guards are UX conveniences only and are never the security boundary. Every privileged action writes an append-only audit entry.

## Rationale

- Traces `OBJ-01` (13-block marketplace) and `OBJ-12` (zero constraint violations); four surfaces sharing one permission model prevents divergent, insecure behavior.
- Directly answers the IDOR/cross-tenant threats documented as authorization tests 1–4 in `00-project-overview/actors-and-roles.md` — without this requirement those tests have nothing to assert against.
- Supports `SEC-REQ-004` (server-side authorization) and `SEC-REQ-010` (audit integrity), which are meaningless if roles are enforced only in the UI.

## Requirements Detail

- Exactly the 7 canonical actors (`ACT-01…ACT-07`) with one centrally defined permission matrix reused by customer web, vendor panel, admin console and mobile apps.
- Deny-by-default: an endpoint without an explicit grant returns a localized `403` (`BR-PLT-05`, `C-24`).
- Server-side enforcement of RBAC **and** ownership on every endpoint; client-side guards are UX only (`SEC-REQ-004`).
- Resource ownership: wallet = Customer only (Admin may flag, never write); orders = buyer + vendor (own sub-orders); store/products = own `store_id`; deliveries = assigned courier; audit logs = append-only, read per role scope.
- Vendor staff roles Viewer / Editor / Manager; only the Owner invites, removes or changes staff roles; self-role-escalation is blocked (`BR-VND-06`).
- Vendor-facing queries are scoped to `store_id` at the service layer; cross-store access is denied (`BR-VND-07`, `DATA-REQ-008`).
- Admin permissions are scoped to day-to-day operations; Super Admin alone manages roles/permissions and platform configuration; Moderator is limited to content/support moderation.
- System (ACT-07) acts through service identities with no interactive login.
- Order, delivery and dispute timelines are visible only per the actor matrix (`BR-ORD-09`).
- Every privileged or state-changing action writes an append-only audit entry: actor, action, entity, before/after, IP, timestamp (`BR-PLT-06`, `SEC-REQ-010`).
- Permission failures and errors are localized ar/en (`BR-PLT-05`).

## Preconditions

- FR-001 provides an authenticated principal (session/token) for every request.
- Role and permission data exist for all actors; ownership keys (`user_id`, `store_id`) are present on tenant-scoped rows (`DATA-REQ-008`).
- The canonical actor register and permission summary in `00-project-overview/actors-and-roles.md` are approved.

## Expected Result

Every request is authorized against role + ownership before any business logic runs: legitimate actors act only within their scope, all cross-user/cross-store attempts are denied without data leakage, and each privileged change leaves a tamper-evident audit record.

## Acceptance Criteria

- **AC-FR002-01** — Given Customer A requests Customer B's order by ID, when the API call is processed, then `403` is returned and no order data is disclosed.
- **AC-FR002-02** — Given Vendor X's staff submits an edit for Vendor Y's product, when the request is processed, then it is denied by `store_id` scoping.
- **AC-FR002-03** — Given a vendor staff member attempts to change their own role to Owner, when processed, then the change is rejected.
- **AC-FR002-04** — Given an Admin performs a state-changing privileged action, when it completes, then an append-only audit entry with actor, action, entity and timestamp exists.
- **AC-FR002-05** — Given a vendor staff member with role Viewer, when they call a vendor write endpoint directly via API, then the server responds `403` — frontend guards are bypassed but authorization still holds (`SEC-REQ-004`).

## Business Rules Applied

- `BR-VND-06` vendor staff roles and Owner-only role management; `BR-VND-07` `store_id` scoping at the service layer.
- `BR-ORD-09` timeline visibility per actor; `BR-PLT-06` append-only audit entries for privileged and money actions.

## Constraints Honored

- `C-21` enforcement lives inside the modular monolith's service/module boundaries — no out-of-process policy call is required for correctness.
- `C-24` authorization outcomes (errors, denials) are localized ar (default) / en.

## Dependencies

- **FR:** FR-001 (authentication), FR-003 (user/role data), FR-020 (role management console), FR-012 (actor-scoped order actions).
- **NFR/SEC/DATA:** SEC-REQ-004, SEC-REQ-010, DATA-REQ-008, NFR-009 (module boundaries), NFR-010 (unit-testable policy logic).

## Verification Method

- Unit tests: one positive and one negative case per (role, permission) pair; ownership predicate tests.
- Integration/negative tests: the IDOR suite (Customer A vs B, Vendor X vs Y, staff self-escalation, banned user calling the API directly — `TC-011…TC-014` concept cases in `actors-and-roles.md`).
- Static/contract checks: no endpoint registered without an authorization declaration; audit rows asserted after privileged operations (`SEC-REQ-010`).

## Out of Scope Notes

- Attribute-based/expression policy languages and external IAM/SSO providers — not required for 7 actors in v1.
- Customer-session impersonation ("view as customer") tooling — not specified anywhere in the canon.
- Permission customization beyond the defined matrix (custom roles per tenant) — roles are fixed by the canon register.
