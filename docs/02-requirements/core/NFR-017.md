# NFR-017 — Storage growth

## Description

Schema, indexes and infrastructure must sustain the platform's five-year data horizon: **10,000,000 products, 100,000,000 order-line records, and 5-year retention** of financial and operational data. High-volume tables (order lines, ledger entries, order status history, notifications, audit log) ship with a **partitioning plan** so that writes, queries and retention jobs stay within the latency budgets as volume grows.

## Metric / Target

- Capacity targets: **10,000,000 products** and **100,000,000 order-line records** loaded and queryable with p95 still within NFR-001 (read < 200 ms on indexed queries).
- **Partitioning implemented** for the three highest-volume tables (order lines, ledger, order history) — monthly or quarterly partitions; retention deletes/drops partitions instead of row-by-row deletes.
- **Retention: 5 years** for financial records (`NFR-019`, `DATA-REQ-003`) with a retention job that provably deletes nothing inside the window (dry-run report) and archives before dropping.
- Volume test loads the full 10M/100M synthetic dataset (bulk COPY) and validates: index bloat within limits, query plans use indexes (0 seq scans on hot paths), `EXPLAIN` regressions = 0.
- Storage forecast maintained with **≤ 10% variance** between projected and actual disk usage per quarter; disk alert at 70% capacity.

## Rationale

Marketplace growth is the business case (`OBJ-11`); retrofitting partitioning on 100M rows in production is a high-risk outage. `AC-S-05` latency commitments only hold if query cost is bounded by indexes/partitions rather than table size; 5-year retention is a compliance obligation (`NFR-019`).

## Measurement Method

- Synthetic **volume test** in staging: bulk-load 10M products + 100M order lines, run the k6 read/write profiles, capture p95 and `EXPLAIN (ANALYZE, BUFFERS)` for the 20 hottest queries.
- Partition presence and maintenance verified by SQL inspection in a dedicated test; retention job run in dry-run mode with a diff report.
- Quarterly capacity review of actual vs forecast disk growth in Grafana.

## Verification / Acceptance

`AC-NFR-017-01` — volume test at 10M/100M scale meets NFR-001 p95 budgets with all hot-path queries index-backed (0 unexpected seq scans). `AC-NFR-017-02` — partitioning live on the three high-volume tables, retention job proves 5-year protection with dry-run evidence, forecast variance ≤ 10%. Both PASS.

## Dependencies

- NFR-001 (latency holds at volume), NFR-018 (scale-out path includes storage), NFR-019 (retention obligation), FR-018 (reporting queries on large data).
- DATA-REQ-003 (retention/deletion), DATA-REQ-005 (expand-contract schema evolution), DEP-02 (PostgreSQL 16 native partitioning), DEP-07 (object storage for media).

## Failure Consequences

Tables outgrow the design: queries slow past NFR-001, VACUUM/partition maintenance causes outages, retention jobs lock tables for minutes (availability breach), and 5-year financial retention becomes either impossible or ruinously expensive.
