# NFR-008 — Data Integrity

## Description

Money, orders and stock must never be corrupted, duplicated or lost. Integrity is enforced in layers: PostgreSQL ACID transactions and constraints (`C-19`, `DATA-REQ-001`), idempotency keys on every money/order/stock operation (`BR-PLT-03`), append-only double-entry ledger (`DATA-REQ-007`), and automated daily reconciliation across wallets, escrow, payables and provider statements (`BR-ESC-08`, `BR-FIN-03`).

## Metric / Target

- **Ledger invariant: Σ of all ledger entries = 0 at every reconciliation point** — 0 mismatches tolerated (`AC-S-14`); mismatch alerts finance within 15 minutes of detection.
- **Idempotency coverage: 100%** of payment, order-creation, stock-reservation, coupon-application and refund operations (mandatory set per `BR-PLT-03`); replaying any of them with the same key yields the original result, never a duplicate side effect.
- **Double-entry**: every balance change posts balanced debit + credit rows in one ACID transaction; 0 unbalanced postings found by daily audit.
- **Referential integrity**: 0 orphan rows — FK violations rejected at the database, not only in application code (`DATA-REQ-001`).
- **Wallet balance never negative** (`BR-PAY-05`); **stock never negative** (`BR-CAT-07`) under concurrent load — 0 occurrences in the concurrency suite.
- **Ledger immutability**: 0 UPDATE/DELETE statements against ledger postings (`DATA-REQ-007`; corrections only via compensating entries).

## Rationale

`OBJ-02` (trust-safe payments: zero ledger imbalance), `AC-S-14` and `AC-S-15` make integrity a launch gate. Escrow (`C-12`), wallet-only payment (`C-01`) and commission math (`BR-ESC-03`) all rest on balances being exactly right — a single imbalance disputes real Yemeni rials with vendors.

## Measurement Method

- Daily automated **reconciliation job** (`BR-ESC-03`/`BR-FIN-03`) asserting wallet + escrow + payable totals against ledger and provider statements; report reviewed each morning (`OBJ-08`).
- **Integration test suite** for idempotent replays, concurrent wallet debits, concurrent stock deductions; PostgreSQL constraint tests for FK/NOT NULL/CHECK.
- CI check (e.g. `squawk`/custom rule) scanning migrations and code for writes to ledger tables.

## Verification / Acceptance

`AC-NFR-008-01` — daily reconciliation reports Σ ledger = 0 across 30 consecutive simulated days and the payment suite proves balanced double-entry with 0 unbalanced postings. `AC-NFR-008-02` — idempotent-replay and concurrency tests show 0 duplicates, 0 negative balances, 0 negative stock, 0 orphan rows. Both PASS (`AC-S-14`, `AC-S-15`).

## Dependencies

- NFR-010 (tests that prove the invariants), NFR-019 (5-year audit retention), NFR-020 (reconciliation runs as an operable job).
- FR-011, FR-012, FR-013, FR-014, DATA-REQ-001, DATA-REQ-006, DATA-REQ-007, DEP-02.

## Failure Consequences

Money appears from nowhere or vanishes: customer wallets, vendor payables and escrow no longer reconcile; refunds cannot be trusted; vendors must be paid manually; `OBJ-02`, `AC-S-14`, `AC-S-15` fail — an existential credibility and legal problem for a payment-holding platform.
