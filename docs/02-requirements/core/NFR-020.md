# NFR-020 — Supportability

## Description

Running and fixing the platform must be routine work for an on-call engineer: documented runbooks for the top incidents, configuration delivered entirely through the environment, health endpoints gating traffic, schema changes deployed without downtime (expand-contract, `DATA-REQ-005`), and a rehearsed rollback. Support staff must be able to resolve common customer issues (`FR-020`) using admin tooling and runbooks, not code changes.

## Metric / Target

- **Runbooks: 100% of the top 10 operational incidents** documented (symptom → diagnosis → mitigation → escalation) and each rehearsed at least once (`AC-S-19`).
- **Health endpoints**: `/healthz` and `/readyz` respond in **< 1 s**, wired to load-balancer target checks; an unhealthy instance is removed from rotation in **≤ 30 s** (`BR-PLT-07`).
- **Configuration: 100% via environment/secrets** — 0 secrets or environment-specific values in code, images or the repo (`SEC-REQ-007`, `AC-S-16`).
- **Zero-downtime deploys**: expand-contract migrations only; a staging deploy produces **0 failed customer requests** (5xx spike < 0.1% over a 5-minute window) and never requires downtime for schema change.
- **Rollback ≤ 15 minutes**, executed successfully in a staging rehearsal (`AC-S-20`).
- Support readiness: ticket flow, dispute flow and code-lockout escalation operable by support staff (`AC-S-23`).

## Rationale

`AC-S-19`, `AC-S-20`, `AC-S-23` are explicit operational-readiness gates; `AC-S-06` (99.99%) is unreachable without fast recovery paths. `C-21`/`C-22` chose a simple stack precisely so a small team can operate it — that only works if the operating knowledge exists outside people's heads.

## Measurement Method

- Runbook review + timed tabletop/chaos rehearsal per incident class; on-call acknowledgement of clarity.
- Health-endpoint probe timing in staging; deploy and rollback drills with request-error monitoring during the window.
- CI secret scan + config audit (values found in repo = failure); migration dry-run checking expand-contract compliance.

## Verification / Acceptance

`AC-NFR-020-01` — top-10 runbooks exist and rehearsed; health endpoints meet timing and LB gating; config/secret audit clean. `AC-NFR-020-02` — staging deploy with 0 failed requests and rehearsed rollback ≤ 15 minutes with evidence (`AC-S-19`, `AC-S-20`). Both PASS before launch.

## Dependencies

- NFR-005, NFR-006 (availability and recovery depend on these mechanics), NFR-014 (signals the runbooks act on), NFR-009 (CI/docs standards).
- DATA-REQ-005 (expand-contract), SEC-REQ-007 (secrets), INT-REQ-007 (alert routing), FR-020 (support tooling).

## Failure Consequences

Incidents stretch from minutes to hours (RTO and 99.99% breach); deploys cause outages and failed orders; secrets leak into the repo (`AC-S-16` fails); support cannot resolve escalations without engineers, so every issue becomes a code change and on-call burns out.
