# FR-001 — Identity, Authentication & Session Management

**Block:** B01 Identity & Access · **Priority:** Critical · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-001 provides registration, login, OTP verification and session lifecycle for every human actor on yumn. The Yemeni mobile number (`^7[0-9]{8}$`) is the sole primary identifier; passwords are strong, bcrypt-hashed and never logged; 6-digit OTP verification (5-minute expiry) is delivered by SMS with automatic WhatsApp failover and guards registration, password reset and other sensitive changes. JWT access tokens (15 minutes) and single-use rotating refresh tokens (7 days, maximum 5 device sessions) make sessions both usable across the four surfaces and immediately revocable.

## Rationale

- Traces `OBJ-01` (all 13 blocks production-ready) and `OBJ-12` (zero violations of `C-01…C-26`); identity is the entry point of every other FR.
- Encodes the market reality behind `C-06` (phone universal, email is not) and the security baseline `C-08` (token lifetimes) rather than leaving them to implementation chance.
- Blocks the entire critical path: `DEP-06` (SMS/WhatsApp) gates registration, so this requirement must be explicit about failover, throttling and lockout behavior.

## Requirements Detail

- Register with phone `^7[0-9]{8}$` + password (≥8 chars, upper, lower, digit); stored bcrypt cost 12, never logged (`BR-AUTH-01`, `BR-AUTH-02`).
- Phone number is unique platform-wide; duplicate registration is rejected with a clear conflict error (`BR-AUTH-01`).
- OTP: 6 digits, 5-minute expiry, max 3 verification attempts, 60-second resend cooldown, max 3 resends per 10 minutes (`BR-AUTH-03`).
- OTP delivery: SMS primary, automatic failover to WhatsApp on provider timeout/failure (`BR-NTF-03`, `INT-REQ-003`).
- Login by phone + password; 5 consecutive failures lock the account for 15 minutes and the lock event is logged (`BR-AUTH-04`).
- Password reset via OTP invalidates **all** existing sessions (`BR-AUTH-07`).
- JWT access 15 min / refresh 7 days with single-use rotation; presenting a used refresh token revokes the whole session family and alerts the user (`BR-AUTH-05`, `C-08`).
- Maximum 5 active device sessions per user; the 6th login evicts the oldest session (`BR-AUTH-06`).
- Email is optional, must be verified if provided, and is never used for login or OTP delivery (`BR-AUTH-08`).
- Security notifications (OTP, login, password change, lockout) cannot be disabled by the user (`BR-NTF-02`).
- All authentication messages and screens are localized ar (default) / en (`BR-NTF-04`, `BR-PLT-05`, `C-24`).
- Session revocation on logout, password change and lockout propagates to all tokens on the next request.

## Preconditions

- `DEP-06` (SMS provider + WhatsApp Business API approval) is available in the target environment; `DEP-02` (PostgreSQL) and `DEP-03` (Redis for OTP/rate counters) are running.
- The client renders Arabic-default localized auth screens (`NFR-013`).
- A user record exists (or is created at registration) before any login, reset or session operation.

## Expected Result

A user can register, verify by OTP, log in, refresh sessions and log out across all four surfaces; credentials and tokens are stored/transmitted only in protected forms; brute-force paths are throttled and locked per rule; every failure is explicit, localized and logged; no session outlives its token lifetime or the 5-device cap.

## Acceptance Criteria

- **AC-FR001-01** — Given a phone matching `^7[0-9]{8}$` and a compliant password, when registration is submitted, then the account is created and a 6-digit OTP valid for 5 minutes is dispatched by SMS.
- **AC-FR001-02** — Given 5 consecutive failed logins, when a 6th attempt is made, then login is refused, the account is locked for 15 minutes, and a lock event is recorded.
- **AC-FR001-03** — Given a refresh token used once, when the same token is presented again, then it is rejected, the entire session family is revoked, and the user is alerted.
- **AC-FR001-04** — Given a user with 5 active device sessions, when a new device logs in, then a new session exists and the oldest session fails on its next request.
- **AC-FR001-05** — Given the correct OTP within 5 minutes (or a wrong/expired one), when the OTP is submitted, then a correct OTP verifies the phone and issues a session; after 3 failed attempts verification is rejected (`BR-AUTH-03`).

## Business Rules Applied

- `BR-AUTH-01` phone as unique primary identifier; `BR-AUTH-02` password complexity + bcrypt 12 + never logged; `BR-AUTH-03` OTP parameters.
- `BR-AUTH-04` 5 failures → 15-minute lock; `BR-AUTH-05` single-use refresh rotation; `BR-AUTH-06` 5-session cap with oldest eviction.
- `BR-AUTH-07` reset invalidates all sessions; `BR-AUTH-08` optional verified email; `BR-NTF-02` mandatory security notices; `BR-NTF-03` OTP channel failover; `BR-NTF-04` bilingual templates.

## Constraints Honored

- `C-06` phone + OTP only — no email-primary auth and no social login.
- `C-07` no biometrics as server-side authentication.
- `C-08` access token 15 minutes, refresh token 7 days with single-use rotation.
- `C-24` Arabic-first localization of all authentication text.

## Dependencies

- **FR:** FR-002 (authorization applied to authenticated sessions), FR-003 (profile created at registration), FR-017 (OTP and security notification delivery).
- **NFR/SEC/DATA:** SEC-REQ-001, SEC-REQ-002, SEC-REQ-003, SEC-REQ-005, NFR-013, NFR-014 (auth event logging).
- **DEP:** DEP-06 (SMS/WhatsApp — Phase 0 gate), DEP-01 (Node/TS runtime), DEP-02 (PostgreSQL), DEP-03 (Redis), DEP-12 (carrier SIMs for OTP testing).

## Verification Method

- Unit tests: password policy, OTP generation/expiry/attempt counters, lockout counter, token rotation logic (no network required, `NFR-010`).
- Integration tests: register → OTP → login → refresh → logout; WhatsApp failover on simulated SMS timeout; 6th-device eviction.
- Security/constraint tests: brute-force lockout (`SEC-REQ-005`), token lifetimes (`C-08`), no email/social login paths exist (`C-06`); E2E OTP on real SIMs per `DEP-12`.

## Out of Scope Notes

- Email-primary authentication, social login (Google/Facebook/Apple) and SSO/OIDC federation — excluded by `C-06`.
- Biometric and device-credential authentication as server-side factors — excluded by `C-07`.
- Changing or transferring a phone number (identity is immutable in v1); passwordless/link-based login; email OTP delivery (`GAP-03` concerns notifications only).
