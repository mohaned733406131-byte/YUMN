# NFR-018 — Scale-out path

## Description

Beyond the `C-25` baseline of 10,000 concurrent users there must be a **documented, tested path to scale out** without re-architecture: stateless API replicas behind the load balancer, PostgreSQL read replicas for reporting/search offload, and known scaling knobs for Redis and Elasticsearch. The modular monolith (`C-21`) scales horizontally at the process level; the path from 10k to higher load is written down and rehearsed, not improvised during an incident.

## Metric / Target

- API tier statelessness: **0 in-process session/state** — any replica can serve any request (verified by killing a replica mid-load with 0 failed user sessions).
- Horizontal scaling efficiency **≥ 80%**: throughput at 4 API replicas ≥ 3.2× throughput at 1 replica on the read-heavy profile (scaling curve measured in staging).
- Database read path: PostgreSQL read replica demonstrated with **replication lag < 5 seconds** under load; reporting/analytics queries (`FR-018`) routed to the replica so they add 0 p95 cost to checkout.
- **Scale-out runbook published** covering the path from 10,000 to **50,000** concurrent users: named steps (add API replicas, tune pool sizes, enable replicas, shard/adjust ES, Redis capacity), with estimated capacity per step.
- Scale test repeated **before each major release** and whenever traffic grows > 30% over baseline.

## Rationale

`C-25` fixes today's target; `OBJ-11` (liquidity/growth) means traffic will not stay at today's level. `NFR-017` handles data growth, this NFR handles load growth — together they keep `AC-S-05` achievable as the marketplace succeeds. `C-21`/`C-22` deliberately avoid Kubernetes, so process-level scaling must be simple and documented.

## Measurement Method

- Staging **scaling-curve test**: k6 at fixed VUs against 1, 2 and 4 API replicas; throughput and p95 recorded per tier to compute efficiency.
- Replica-kill test during load (session continuity, error rate).
- PostgreSQL replication-lag metric in Prometheus; reporting queries timed on primary vs replica.
- Runbook tabletop review with the on-call team (`NFR-020`).

## Verification / Acceptance

`AC-NFR-018-01` — measured scaling efficiency ≥ 80% from 1→4 replicas with 0 errors on replica kill, and read-replica lag < 5 s under load. `AC-NFR-018-02` — scale-out runbook published, reviewed, and its 10k→50k steps validated at least to the 25k step in staging. Both PASS.

## Dependencies

- NFR-003 (baseline concurrency), NFR-004 (cache absorbs read load), NFR-016 (stateless containers), NFR-017 (storage growth plan), NFR-009 (statelessness enforced by module design).
- DEP-02 (PostgreSQL streaming replication), DEP-03, DEP-04.

## Failure Consequences

Growth hits an invisible ceiling: adding traffic means outages instead of replicas; reporting queries starve checkout; scaling decisions become ad-hoc during incidents; `C-25` compliance degrades as soon as the marketplace succeeds beyond plan.
