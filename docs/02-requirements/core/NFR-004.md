# NFR-004 — Caching

## Description

Read-heavy catalog and discovery traffic (product detail, category listing, store pages, banners, search suggestions) is served from **Redis 7** (`DEP-03`) so PostgreSQL and Elasticsearch are not saturated by repeated identical reads. Caching must never compromise correctness: prices, stock and checkout totals are always re-validated server-side (`BR-CRT-04`, `BR-CAT-07`), so cached copies are short-lived and evicted on write.

## Metric / Target

- Cache hit ratio **≥ 80%** over a 24-hour window on catalog read endpoints (product detail, category browse, store page).
- Cache-hit p95 **< 50 ms**; cache-miss p95 still within NFR-001 read budget (< 200 ms).
- Write-to-visibility propagation: evicted/updated keys reflect the new value in **≤ 5 seconds** everywhere.
- Checkout, cart totals, wallet balance and payment paths: **0 requests served from a cache older than 5 s** (server-side revalidation mandatory).
- Cache memory stays < 75% of the Redis maxmemory policy limit; zero evictions of non-TTL keys during the NFR-003 load run.

## Rationale

`OBJ-04` (performance) and `C-25` (10,000 users) — catalog browsing dominates traffic and must not scale linearly with database load. Consistency rules `BR-CRT-04`/`BR-CAT-07` require that any speedup never serves a stale price or oversells stock, so hit ratio is paired with a staleness ceiling.

## Measurement Method

- Custom Prometheus metric `cache_requests_total{route,result=hit|miss}` → hit ratio per route in Grafana (15 s scrape, 24 h window).
- **Redis `INFO stats`** (`keyspace_hits`/`keyspace_misses`) cross-checked as a sanity number.
- Staleness probed by an integration test: mutate a product/price, assert all reads reflect it within 5 s; load test during NFR-003 confirms hit ratio under concurrency.

## Verification / Acceptance

`AC-NFR-004-01` — 24-hour hit ratio ≥ 80% on catalog read routes in staging with production-like traffic replay. `AC-NFR-004-02` — staleness ≤ 5 s after write and 0 stale-priced checkout confirmations in the checkout integration suite. Both PASS required.

## Dependencies

- NFR-001, NFR-003 (performance outcomes it supports), NFR-007 (behavior when Redis is down).
- FR-004, FR-008, FR-009, FR-019 (catalog/banner reads), DEP-03 (Redis 7), DEP-04 (ES for search suggestions).

## Failure Consequences

Every catalog read hits PostgreSQL/Elasticsearch directly; database CPU becomes the bottleneck long before 10,000 users (NFR-003 fails); alternatively, careless caching serves stale prices or stock, breaking `BR-CRT-04`/`BR-CAT-07` and causing financial or oversell incidents.
