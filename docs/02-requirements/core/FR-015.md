# FR-015 — Shipping & Delivery

**Block:** B08 Shipping & Delivery · **Priority:** Critical · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-015 configures domestic shipping zones and fee calculation (zone × package weight × method, waived by free-shipping coupons), assigns deliveries to eligible same-zone couriers with first-accept wins, drives the physical flow READY_FOR_PICKUP → ASSIGNED → PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED, and gates DELIVERED on a **6-digit code** issued at OUT_FOR_DELIVERY: 3 failed attempts lock confirmation for 24 hours and auto-create a support ticket. No GPS is ever requested or stored.

## Rationale

- Traces `OBJ-07` (≥95% first-attempt code success, zero deliveries without code) and `OBJ-01` (block B08), under `C-16` (no GPS) and `C-17` (domestic only).
- The 6-digit code is the trust anchor replacing GPS: without it, escrow release (`C-12`) and review eligibility (`BR-REV-01`) would rest on unverifiable courier claims.
- Optimistic first-accept assignment (`BR-SHP-04`) prevents double-booking a single package across couriers.

## Requirements Detail

- Shipping zones limited to domestic Yemen coverage (`C-17`); fee = f(zone, package weight, method), zeroed by an applied `free_shipping` coupon (`BR-SHP-01`).
- Shipping fee applies per sub-order; package weight captured at READY_FOR_PICKUP to price the shipment (`C-10`, `BR-FIN-02`).
- Courier assignment offered to eligible couriers in the same zone; first accept wins via optimistic locking (`BR-SHP-04`).
- Assignment lifecycle: ASSIGNED → PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED; courier may release back to READY_FOR_PICKUP (`state-transitions.md` §2).
- At OUT_FOR_DELIVERY a 6-digit code is issued to the buyer by SMS/WhatsApp/in-app (`BR-SHP-02`, FR-017).
- Code attempts: 1–2 failures show remaining attempts; 3rd failure locks confirmation for 24 hours and auto-creates a support ticket (`BR-SHP-03`, `C-16`).
- Failed delivery attempt returns the order to IN_TRANSIT with the attempt recorded; 3 failed attempts escalate to admin review with full timeline (`BR-SHP-06`).
- DELIVERED requires successful code verification with attempts < 3 (`BR-ORD-08`, `C-16`).
- The platform never requests or stores courier GPS location — no location fields exist in the API contract (`BR-SHP-05`, `C-16`).
- Delivery proof = code + timestamp + courier identity; an optional photo may be stored (type/size validated, EXIF stripped) but is never required (`BR-SHP-07`, `SEC-REQ-011`).
- Couriers see only their own assignments/timelines; admins have the dispatch view (`BR-ORD-09`, `BR-VND-07` analog scoping).
- Duplicate code submissions are idempotent: first success wins (`state-transitions.md` §5).

## Preconditions

- Order exists in READY_FOR_PICKUP with stock already deducted at PLACED (FR-012).
- Shipping zone/method resolved at checkout (FR-011) and courier accounts exist for the zone (FR-002 actor Courier).
- Buyer contact channel available to receive the delivery code (FR-017).

## Expected Result

Packages move from vendor readiness to verified delivery under a race-free assignment process; delivery completes only with a correct code within 3 attempts; lockouts/escalations create operator work items instead of dead ends; and no location data is ever captured.

## Acceptance Criteria

- **AC-FR015-01** — Given the correct 6-digit code entered within 3 attempts, when verified, then the sub-order transitions to DELIVERED and escrow hold starts.
- **AC-FR015-02** — Given 3 incorrect code entries, when the 3rd fails, then confirmation locks for 24 hours and a support ticket is auto-created.
- **AC-FR015-03** — Given two couriers accepting the same assignment concurrently, when both requests are processed, then exactly one wins the assignment.
- **AC-FR015-04** — When the API contract is inspected, then no endpoint or schema requests/stores courier GPS coordinates (`C-16`).
- **AC-FR015-05** — Given the full delivery flow and API contract, when GPS/location would be requested or stored, then no location data is ever requested, stored or returned (`C-16`, `BR-SHP-05`).

## Business Rules Applied

- `BR-SHP-01` fee function + free-shipping coupon; `BR-SHP-02` code issued at OUT_FOR_DELIVERY; `BR-SHP-03` attempt limits and 24-hour lock.
- `BR-SHP-04` first-accept assignment; `BR-SHP-05` no GPS; `BR-SHP-06` 3-attempt escalation; `BR-SHP-07` proof composition.
- `BR-ORD-08` code-gated DELIVERED; `BR-ORD-09` timeline visibility.

## Constraints Honored

- `C-16` no GPS/real-time tracking; 6-digit code with 3 attempts → 24-hour lock + support ticket.
- `C-17` domestic Yemen fulfillment only.
- `C-09` delivery progression uses only canonical states from `state-transitions.md`.

## Dependencies

- **FR:** FR-011 (fee at checkout), FR-012 (state machine), FR-014 (escrow on DELIVERED), FR-016 (return pickups reuse assignment), FR-017 (code delivery), FR-019 (free-shipping coupons), FR-020 (escalation/lockout tooling).
- **NFR/INT:** NFR-012, INT-REQ-003 (SMS/WhatsApp for codes), INT-REQ-005 (delivery orchestration abstraction).

## Verification Method

- E2E delivery flow: assignment → pickup → transit → code → DELIVERED, in ar and en.
- Negative/security tests: wrong code ×3 → lock + ticket; contract test asserting absence of location fields (`C-16`).
- Concurrency tests: double-accept race, duplicate code entry idempotency; fee-calculation unit tests (zone × weight × method).

## Out of Scope Notes

- GPS tracking, live map views, proof-of-location and geofenced delivery (`C-16`).
- Cross-border/international shipping and carrier-rate APIs (`C-17`); third-party fleet integrations beyond the internal engine (`INT-REQ-005` abstraction only).
- COD collection (`C-01`), delivery time slots, customer-scheduled pickups and real-time ETA promises — not specified in v1.
