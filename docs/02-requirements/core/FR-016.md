# FR-016 — Returns & Refunds

**Block:** B09 Returns & Refunds · **Priority:** Critical · **Status:** approved · **Registry:** `DOC-REQ-001` §1

FR-016 executes the buyer-protected money-back path: a return window computed from delivery confirmation plus the product's `returnPeriodDays` (blocked when `isReturnable = false` or elapsed), the RETURN_REQUESTED → RETURN_APPROVED/RETURN_REJECTED → RETURN_RECEIVED → REFUNDED sub-flow inside the 17-state machine, vendor inspection within 72 hours (auto-approve on timeout), wallet credit within 3 business days, and proportional commission/escrow adjustments — with the admin as final arbiter.

## Rationale

- Traces `OBJ-02` (refunds settle to wallet, ledger stays balanced), `OBJ-01` (block B09) and `OBJ-12` (`C-11` return policy, `C-12` escrow interplay, `C-16` code-gated delivery start point).
- Merchant-configurable policy (`C-11`) balances buyer clarity with vendor autonomy; the auto-approve 72-hour rule (`BR-RET-05`) prevents vendors from stalling refunds by inaction.
- Wallet-only refund (`BR-PAY-07`) keeps the closed-loop model intact — no cash leaves the platform except vendor payouts.

## Requirements Detail

- Return window = delivery confirmation date + product `returnPeriodDays`; `isReturnable = false` or window elapsed → request rejected (`BR-RET-01`, `C-11`).
- Return states within the canonical machine: RETURN_REQUESTED → RETURN_APPROVED / RETURN_REJECTED → RETURN_RECEIVED → REFUNDED (`BR-RET-02`, `C-09`).
- Requests are openable from DELIVERED (and from COMPLETED while still inside the window, per `state-transitions.md` §2).
- Refund amount = item value; shipping is refunded only when the fault is platform/vendor-side (`BR-RET-03`).
- Refund credits the customer's wallet within 3 business days of the REFUNDED state, never externally (`BR-RET-04`, `BR-PAY-07`, `C-01`).
- Vendor inspection after RETURN_RECEIVED must conclude within 72 hours, otherwise the return auto-approves (`BR-RET-05`).
- Approval/rejection requires a reason; return pickup uses the delivery-provider flow (RETURN_APPROVED → RETURN_RECEIVED) (`BR-SHP-04` mechanics).
- Where policy and dispute conflict, the admin is final arbiter and the decision is written to the audit log (`BR-RET-06`, `BR-PLT-06`).
- Refund triggers proportional commission reversal and escrow adjustment (draw escrow first, then vendor payable) (`BR-RET-07`, `BR-ESC-04`, `BR-ESC-07`).
- Refund execution is idempotent via idempotency key; ledger posts balanced double-entry rows (`BR-PAY-08`, `BR-PAY-06`, `DATA-REQ-007`).
- The CANCELLED → REFUNDED path shares the same refund engine (cancellation always triggers refund, `BR-ORD-04`).
- Customer and vendor are notified at each transition in their locale (`BR-NTF-04`, FR-017).

## Preconditions

- Order reached DELIVERED (code-verified) or COMPLETED; the buyer owns the order (`BR-ORD-09`).
- Product/store return policy values exist (`C-11`); return window arithmetic is evaluated against delivery confirmation date.
- Wallet exists to receive the credit (FR-013); escrow/payable state known (FR-014).

## Expected Result

Eligible buyers open returns that flow through inspection to a wallet refund on time; ineligible requests are rejected with the policy reason; untimely inspections auto-approve; every refund is exactly once, ledgered, and mirrored by commission/escrow correction with full audit.

## Acceptance Criteria

- **AC-FR016-01** — Given a product with `isReturnable = false`, when a return is requested, then it is rejected citing the store policy.
- **AC-FR016-02** — Given `returnPeriodDays = 7` and delivery 10 days ago, when a return is requested, then it is rejected (window elapsed).
- **AC-FR016-03** — Given a received return left uninspected for 72 hours, when the timer expires, then it auto-approves and the refund executes.
- **AC-FR016-04** — Given an approved refund, when processed, then the customer wallet is credited exactly once within 3 business days.

## Business Rules Applied

- `BR-RET-01` window/policy gate; `BR-RET-02` return state sequence; `BR-RET-03` refund composition (shipping only if platform/vendor fault).
- `BR-RET-04` 3-business-day wallet credit; `BR-RET-05` 72-hour inspection auto-approve; `BR-RET-06` admin final arbiter + audit; `BR-RET-07` commission/escrow adjustment.
- `BR-PAY-07` refunds to wallet; `BR-PAY-08` idempotency; `BR-PAY-06` double-entry ledger.

## Constraints Honored

- `C-11` merchant-configurable return policy; window starts at delivery confirmation.
- `C-12` escrow-adjusted refunds (escrow first, then vendor payable liability).
- `C-09` return/refund states limited to the canonical 17.
- `C-01` refunds settle strictly to the wallet — no cash/card payouts.

## Dependencies

- **FR:** FR-012 (states), FR-013 (wallet credit), FR-014 (escrow/commission), FR-015 (return pickup), FR-017 (notifications), FR-020 (admin arbitration).
- **NFR/DATA:** NFR-008, DATA-REQ-007, DATA-REQ-006 (refund reconciliation).

## Verification Method

- Unit tests: window arithmetic (delivery + N days), refund composition (item vs shipping fault), auto-approve timer, commission reversal math.
- Integration/E2E: full return happy path, rejection path, 72-hour timeout path, double-refund idempotency.
- Ledger invariant checks after refund + reversal sequences; audit assertion for admin override decisions.

## Out of Scope Notes

- Product exchanges/swaps, store-credit vouchers and partial-quantity inspections beyond item-value refunds — refund-only in v1.
- Cash refunds to bank/card (`BR-PAY-07`) and third-party return-label carriers.
- Warranty claims, recalls and quality-inspection laboratories — handled outside the platform.
