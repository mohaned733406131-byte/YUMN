# NFR-013 — Bilingual RTL/LTR

## Description

**Arabic (`ar`) is the default locale with full right-to-left layout; English (`en`) has complete feature parity.** Exactly two locales exist (`C-24`). Every user-facing string, notification template, date, number and currency amount is locale-aware on all four surfaces (customer web, vendor panel, admin console, mobile). No hardcoded strings anywhere (`BR-PLT-05`).

## Metric / Target

- Translation completeness: **100% of i18n keys present in `ar` and `en`** — missing-key count **0** in the CI locale-coverage check; untranslated-key count 0 at release.
- Hardcoded user-facing strings: **0** (CI scan of source for raw text in JSX/labels fails the build).
- Currency/number formatting: amounts rendered per `BR-PAY-10` — integer YER with **Arabic-Indic numerals in `ar-YE`**; dates via locale-aware formatting (Hijri optional, Gregorian default); 0 mixed-locale renderings in visual tests.
- RTL defects on core journeys: **0** (`AC-S-11`); layout mirrors correctly (alignment, icons, directional gestures, focus order).
- Notification templates (SMS, WhatsApp, in-app, push): **2/2 locales** populated for every template (`BR-NTF-04`); user locale decides language, Arabic default.
- Locale switch applies across surfaces within **1 interaction** and persists per user profile.

## Rationale

`C-24` (Arabic-first RTL, full English parity, only two locales) is non-negotiable and explicitly drives `NFR-012` and the frontend design; `OBJ-03` and `AC-S-11` set the measurable gate. English parity matters for international vendors, testing and support staff.

## Measurement Method

- CI **i18n coverage script** (i18next scan): compares extracted keys against `ar`/`en` resource files — fails on missing/empty values.
- **RTL visual regression suite** (Playwright screenshots at 320/768/1280 px, `dir=rtl`) comparing against approved baselines for core journeys.
- Locale-format unit tests on the money/date formatters; template inventory diff (template count × 2 locales).

## Verification / Acceptance

`AC-NFR-013-01` — CI locale check reports 100% key coverage in both locales, 0 hardcoded strings, and every notification template exists in `ar` and `en`. `AC-NFR-013-02` — RTL visual regression shows 0 defects on core journeys and Arabic-Indic currency/date formatting passes unit tests. Both PASS (`AC-S-11`).

## Dependencies

- NFR-002 (font/bundle cost of bilingual payloads), NFR-011 (RTL accessibility), NFR-012 (usability in `ar`), NFR-019 (locale-correct legal/VAT text).
- FR-017 (templates), FR-019 (CMS content), SEC-REQ-001 (OTP messages), `DEP-11` (Arabic copy), `BR-PLT-05`.

## Failure Consequences

Mixed-language screens, broken RTL layouts and wrong numeral formats destroy the Arabic-first promise (`C-24`, `OBJ-03`); `AC-S-11` fails; users receive OTPs in the wrong language; support burden rises and the product feels foreign in its primary market.
